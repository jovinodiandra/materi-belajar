PgBouncer — resepsionis ringan di depan PostgreSQL.

Di deck induk kita belajar bahwa tiap koneksi Postgres = satu proses OS yang mahal, jadi jumlah koneksi adalah sumber daya langka. PgBouncer adalah jawaban standar: satu program kecil (~2 MB) yang menerima ribuan koneksi dari aplikasi tapi cuma memegang segelintir koneksi nyata ke Postgres, lalu membagikannya bergiliran. Kenalan · Apa itu PgBouncer

Connection pooler eksternal khusus PostgreSQL

PgBouncer adalah lightweight connection pooler untuk PostgreSQL. Ia satu proses kecil yang berdiri di antara aplikasi dan database. Aplikasi tersambung ke PgBouncer seolah-olah itu Postgres; PgBouncer yang memegang sedikit koneksi nyata ke Postgres dan menggilirkannya.

// lightweight

Sangat ringan

Satu proses, jejak memori cuma sekitar 2 MB, single-threaded berbasis event loop. Bisa menangani ribuan koneksi client tanpa membebani server.

// transparan

Tampak seperti Postgres

Bicara protokol wire Postgres. Aplikasi & driver tidak perlu diubah — cukup arahkan host/port ke PgBouncer.

// fokus

Satu tugas, dikerjakan baik

Bukan proxy serba bisa. Ia hanya mem-pool koneksi — justru itu yang membuatnya stabil & jadi standar de-facto.

◆ Mengapa "eksternal" itu penting

Pool di dalam aplikasi (mis. HikariCP, pg.Pool) hanya menghemat koneksi untuk satu proses. Saat kamu punya 100 pod atau ribuan invocation serverless, tiap proses punya poolnya sendiri — totalnya tetap membanjiri Postgres. PgBouncer duduk di luar semua proses itu dan meredam total koneksi ke satu angka kecil yang terkendali.

Arsitektur · Posisi di jalur

Di mana PgBouncer duduk

PgBouncer adalah lapisan perantara. Banyak client menumpuk di sisi kiri; sedikit koneksi nyata keluar di sisi kanan. Inilah inti "many in, few out".

Aplikasi

◆ Analogi — resepsionis bersama

Gedung dengan 100 kantor. Kalau tiap kantor punya saluran telepon langsung ke pusat, kabelnya habis. Solusinya: satu resepsionis (PgBouncer) menerima semua penelepon, tapi hanya memegang 20 saluran ke pusat (Postgres), lalu menyambungkan bergiliran. Pusat merasa hanya melayani 20 orang — padahal di depan ada ribuan.

◆ Dua sisi koneksi PgBouncer
Clientkoneksi dari aplikasi → PgBouncer (boleh ribuan)
Serverkoneksi PgBouncer → Postgres (sedikit, mahal)

Istilah ini muncul terus di konfigurasi & monitoring: client connection = sisi aplikasi, server connection = sisi Postgres. Tujuan PgBouncer: banyak client, sedikit server.

Inti · Pool mode

Tiga pool mode: seberapa "lengket" koneksinya

Ini konsep terpenting di PgBouncer. Pool mode menentukan kapan koneksi server (ke Postgres) dilepas kembali ke pool. Makin cepat dilepas, makin hemat — tapi makin banyak fitur level-sesi yang berisiko rusak.

// session

Session pooling

Koneksi server dipegang selama client tetap terhubung. Baru dilepas saat client disconnect. Paling aman & kompatibel — semua fitur sesi jalan — tapi paling sedikit menghemat.

// transaction ★

Transaction pooling

Koneksi server dipinjam per transaksi, lalu langsung balik begitu COMMIT/ROLLBACK. Rasio penghematan terbesar. Default pilihan untuk web & serverless.

// statement

Statement pooling

Koneksi dilepas tiap selesai satu statement. Paling agresif & hemat, tapi melarang transaksi multi-statement. Untuk kasus khusus (mis. mode auto-commit ketat).

◆ Spektrum: hemat ⟷ kompatibel
sessionpaling kompatibel · paling boros koneksi
transactiontitik tengah · paling umum dipakai ★
statementpaling hemat · paling banyak batasan

Aturan praktis: mulai dari transaction. Pakai session hanya jika aplikasimu butuh fitur sesi yang tak bisa ditawar (mis. LISTEN/NOTIFY, advisory lock antar transaksi).

◆
Di transaction pooling, koneksi server gonta-ganti tiap transaksi. Maka hal yang "menempel" ke satu sesi bisa rusak: SET level sesi, session-level advisory lock, LISTEN/NOTIFY, temporary table lintas transaksi, dan dulu prepared statement. Catatan penting: PgBouncer ≥ 1.21 sudah mendukung protocol-level prepared statements di mode transaction (max_prepared_statements), jadi batasan ini sebagian besar sudah hilang di versi modern.
Inti · pgbouncer.ini

Konfigurasi: file .ini yang sederhana

PgBouncer dikonfigurasi lewat satu file INI. Dua bagian wajib: [databases] (alias yang diteruskan ke Postgres asli) dan [pgbouncer] (perilaku pooler).

pgbouncer.ini — konfigurasi inti beranotasiini
[databases]
; alias 'app' yang dipakai aplikasi → diteruskan ke Postgres asli
app = host=127.0.0.1 port=5432 dbname=app

[pgbouncer]
listen_addr = 0.0.0.0            ; PgBouncer dengarkan di alamat ini
listen_port = 6432               ; port PgBouncer (app connect ke sini, bukan 5432)

pool_mode = transaction          ; mode paling umum
max_client_conn = 2000          ; ribuan client boleh nyambung ke PgBouncer...
default_pool_size = 20          ; ...tapi cuma 20 koneksi nyata ke Postgres per (db,user)
reserve_pool_size = 5           ; cadangan saat pool utama penuh
reserve_pool_timeout = 3        ; aktifkan cadangan setelah antri 3 detik
server_idle_timeout = 600       ; tutup koneksi server yang nganggur 10 menit
max_db_connections = 50         ; batas keras total koneksi ke satu database

auth_type = scram-sha-256        ; metode autentikasi (lihat bab berikut)
auth_file = /etc/pgbouncer/userlist.txt
◆ Parameter yang paling sering diutak-atik
pool_modesession | transaction | statement
max_clientmax_client_conn — batas koneksi dari aplikasi
pool_sizedefault_pool_size — koneksi nyata ke Postgres
reservereserve_pool_size — buffer saat puncak

Hubungan kuncinya: max_client_conn jauh lebih besar dari default_pool_size. Itulah rasio penghematannya — mis. 2000 client di depan, 20 koneksi nyata di belakang.

Inti · Autentikasi

Bagaimana PgBouncer memverifikasi user

Karena client login ke PgBouncer (bukan langsung ke Postgres), PgBouncer perlu tahu cara memverifikasi mereka. Ada dua pola umum: daftar statis (userlist.txt) atau menanyakan ke Postgres (auth_query).

userlist.txt — daftar user statistxt
; format: "username" "password-atau-hash-scram"
"app_user" "SCRAM-SHA-256$4096:..."
"readonly" "SCRAM-SHA-256$4096:..."
auth_query — tanyakan password ke Postgres (lebih dinamis)ini
; daripada me-list semua user manual, biar PgBouncer query ke DB
auth_type  = scram-sha-256
auth_user  = pgbouncer_auth          ; user khusus untuk lookup
auth_query = "SELECT usename, passwd FROM pg_shadow WHERE usename=$1"
; (praktik aman: bungkus dalam SECURITY DEFINER function, bukan akses pg_shadow langsung)
// scram

scram-sha-256

Metode auth modern & direkomendasikan untuk Postgres terbaru. Lebih aman dari md5.

// tls

TLS/SSL

client_tls_sslmode & server_tls_sslmode mengenkripsi kedua sisi. PgBouncer aman ditaruh sebagai gerbang depan.

// hba

auth_hba_file

Bisa meniru gaya pg_hba.conf untuk aturan akses berbasis host/user.

◆ Operasi · Sizing

Menentukan ukuran pool

Sama seperti pool di aplikasi: kecil-tapi-pas mengalahkan besar. default_pool_size adalah jumlah koneksi nyata ke Postgres — angka inilah yang melindungi (atau membahayakan) database.

menghitung default_pool_sizerule of thumb
# titik awal: mirip rumus pool aplikasi
default_pool_size ≈ (core_CPU_postgres × 2) + jumlah_disk

# contoh: Postgres 4 core, 1 SSD → ~9-10

# PENTING — hitung TOTAL ke Postgres:
# default_pool_size berlaku PER (database, user).
# Banyak db/user → kalikan. Batasi dengan max_db_connections
# agar total tak pernah melebihi max_connections Postgres.

// Pool kekecilan

  • Client antri lama menunggu koneksi server.
  • Latensi naik, bisa kena query_wait_timeout.
  • Postgres nganggur padahal app megap.

// Pool kebesaran

  • Postgres kebanjiran proses → rebutan CPU/lock.
  • Menghapus manfaat utama PgBouncer.
  • Risiko lewat max_connections Postgres.
◆ Hubungan dengan max_connections Postgres

Aturan emas: (total semua pool PgBouncer) + koneksi langsung lain (admin, migrasi, replikasi, monitoring) ≤ max_connections Postgres. PgBouncer melindungi Postgres justru dengan menjaga sisi kanan ini tetap kecil & pasti.

⚙ Operasi · Monitoring

Admin console & perintah SHOW

PgBouncer punya console admin bawaan: kamu sambung ke database virtual bernama pgbouncer lalu jalankan perintah SHOW untuk mengintip kondisi pool secara real-time — tanpa tool tambahan.

masuk console admin & lihat statuspsql
# sambung ke database admin virtual "pgbouncer"
psql -p 6432 -U admin pgbouncer

pgbouncer=# SHOW POOLS;     -- isi tiap pool: aktif, nunggu, idle
pgbouncer=# SHOW STATS;     -- throughput query/transaksi per db
pgbouncer=# SHOW CLIENTS;   -- koneksi dari aplikasi
pgbouncer=# SHOW SERVERS;   -- koneksi nyata ke Postgres
pgbouncer=# SHOW DATABASES; -- konfigurasi tiap database
pgbouncer=# SHOW CONFIG;    -- semua parameter aktif
// SHOW POOLS

Kesehatan pool

Kolom cl_waiting > 0 terus = pool kekecilan / Postgres lambat. Sinyal paling penting untuk tuning.

// SHOW STATS

Throughput

Lihat query/detik & rata-rata waktu. Berguna untuk kapasitas & deteksi anomali.

// metrics

Eksporter Prometheus

Untuk produksi, pasang pgbouncer_exporter agar metrik masuk Grafana/Prometheus.

⚙ Operasi · Maintenance

PAUSE, RESUME, RELOAD: maintenance tanpa downtime

Kemampuan operasional inilah yang membuat PgBouncer dicintai tim ops. Ia bisa menahan trafik sementara agar Postgres bisa di-restart/maintenance tanpa memutus aplikasi.

perintah kontrol di console adminpsql
pgbouncer=# PAUSE;      -- tahan: query baru diantrikan, tunggu transaksi selesai
-- ... lakukan restart / failover / maintenance Postgres di sini ...
pgbouncer=# RESUME;     -- lepas lagi: antrian mengalir, app tak pernah putus

pgbouncer=# RELOAD;     -- muat ulang pgbouncer.ini tanpa drop koneksi
pgbouncer=# SHOW CONFIG; -- verifikasi perubahan

pgbouncer=# RECONNECT;  -- minta koneksi server dibuat ulang (mis. setelah failover)
◆ Kenapa ini berharga

Tanpa PgBouncer, restart Postgres = semua aplikasi langsung kena error koneksi. Dengan PAUSE/RESUME, aplikasi cuma merasakan jeda sesaat (query-nya menunggu), lalu lanjut seolah tak terjadi apa-apa. Maintenance yang tadinya butuh "maintenance window" jadi nyaris tak terlihat user.

// RELOAD

Ganti config online

Ubah pgbouncer.ini lalu RELOAD — koneksi client yang sedang jalan tidak terputus.

// online restart

Restart mulus

PgBouncer baru bisa "mengambil alih" socket dari yang lama (-R / SO_REUSEPORT) saat upgrade PgBouncer sendiri.

// KILL

Kontrol granular

KILL db memutus koneksi satu database tertentu; berguna saat isolasi masalah.

Praktik · Jebakan

Batasan & jebakan yang harus diwaspadai

PgBouncer luar biasa, tapi bukan sihir. Hampir semua jebakannya berakar dari satu hal: di transaction/statement mode, koneksi server tidak lengket ke satu client.

// session state

Fitur level-sesi

SET sesi, LISTEN/NOTIFY, advisory lock antar transaksi, temp table lintas transaksi — bisa rusak di transaction mode. Pakai session mode kalau wajib.

// prepared

Prepared statement (versi lama)

Di PgBouncer lama, prepared statement bermasalah di transaction mode. Solusi: upgrade ke ≥ 1.21 & set max_prepared_statements, atau matikan di driver.

// SPOF

Titik kegagalan tunggal

Kalau cuma 1 instance PgBouncer, ia jadi single point of failure. Produksi: jalankan beberapa instance + load balancer / HAProxy.

// single thread

Single-threaded

Satu proses = satu core. Untuk throughput sangat tinggi, jalankan beberapa proses (mis. so_reuseport) di belakang LB.

// search_path

search_path & SET lain

Jangan andalkan SET search_path bertahan antar transaksi di pooling mode. Set eksplisit per transaksi atau di koneksi.

// transaksi panjang

Transaksi lama menahan

Satu transaksi panjang memegang koneksi server lama → mengurangi yang tersedia. Jaga transaksi tetap pendek.

◆
Cara cek aman: jalankan aplikasi di transaction mode di staging, perhatikan error aneh seputar prepared statement / SET / temp table. Kalau ada & tak bisa dihindari, naikkan ke session mode untuk pool itu — kamu kehilangan sebagian penghematan tapi mendapat kembali kompatibilitas penuh.
◆ Keputusan · Pakai atau jangan

Kapan butuh PgBouncer

PgBouncer paling bersinar saat jumlah proses aplikasi besar atau berumur pendek — situasi di mana pool di dalam app saja tidak cukup.

// Pakai PgBouncer saat…

  • Banyak instance app / auto-scaling (puluhan–ratusan pod).
  • Serverless (Lambda/Cloud Functions) — proses pendek.
  • Total koneksi mendekati max_connections Postgres.
  • Butuh maintenance Postgres tanpa memutus app.
  • Banyak app/bahasa berbagi satu Postgres.

// Mungkin belum perlu saat…

  • Satu app monolit berumur panjang dengan pool in-app yang sehat.
  • Jumlah koneksi jauh di bawah kapasitas DB.
  • Sangat bergantung fitur sesi (pertimbangkan biayanya).
◆ Dua lapis: pool app + PgBouncer

Pool in-app (mis. HikariCP) & PgBouncer saling melengkapi, bukan menggantikan. Pool app menghemat handshake untuk satu proses; PgBouncer meredam total koneksi dari semua proses ke Postgres. Alternatif terkelola dengan prinsip sama: RDS Proxy (AWS), pooler bawaan Supabase & Neon.

Penutup

PgBouncer dalam satu tarikan napas

Satu proses ringan di depan Postgres yang mengubah "ribuan koneksi mahal" jadi "segelintir koneksi yang digilirkan rapi". Pahami pool mode, jaga ukurannya, pantau lewat SHOW, dan manfaatkan PAUSE/RELOAD untuk operasi mulus.

  • Pooler eksternal ringan — ~2 MB, di antara app & Postgres.
  • Many in, few out — ribuan client → segelintir koneksi nyata.
  • Pool mode = kunci — transaction (default), session (aman), statement (agresif).
  • Sizing kecil-tapi-pas — total pool ≤ max_connections Postgres.
  • SHOW POOLS — pantau cl_waiting untuk tuning.
  • PAUSE/RESUME/RELOAD — maintenance tanpa memutus aplikasi.
  • Pelengkap pool in-app — dua lapis, bukan saling menggantikan.

Langkah belajar berikutnya

Jalankan PgBouncer lokal (Docker), arahkan aplikasimu ke port 6432 alih-alih 5432, set pool_mode = transaction & default_pool_size = 10. Lalu buka console admin dan jalankan SHOW POOLS sambil memberi beban — lihat cl_active, cl_waiting, & sv_active bergerak. Itu memperlihatkan "many in, few out" secara langsung.
