// Database — saat satu mesin sudah tidak sanggup lagi

Belah datamu jadi banyak potongan, sebar ke banyak mesin.

Suatu hari, data & traffic aplikasimu tumbuh melewati kapasitas satu server — CPU-nya penuh, disknya penuh, koneksinya antre. Sharding (partitioning) adalah cara membelah satu dataset besar jadi potongan-potongan lebih kecil yang disebar ke banyak mesin, supaya tiap mesin cuma menanggung sebagian. Deck ini buat pemula: dari kenapa ia dibutuhkan, strategi membagi data, bahaya hot spot, sampai tools yang biasa dipakai — diselingi kalimat dari buku rujukan.

Sakit
Satu server kehabisan napas — data & traffic melampaui kapasitas satu mesin
Ide
Belah data jadi partisi — sebar ke banyak server, tiap server pegang sebagian
Untung
Skala horizontal — tambah server, tambah kapasitas
Batas
Hot spot & query lintas-shard — salah pilih kunci, satu shard kebanjiran
Pakai
Saat skala sudah besar — jutaan user, miliaran baris/pesan

◆ Buat apa ini? Kenapa pakai ini?

Given — Awalnya semua data (user, transaksi, pesan) disimpan di satu database, satu server, dan itu cukup selama datanya masih kecil.

When — Data tumbuh jadi ratusan juta–miliaran baris, index tak lagi muat di RAM, CPU & disk mesin itu penuh, dan tiap query harus antre karena cuma ada satu pintu masuk ke data.

Then — Tanpa membelah data, satu-satunya jalan tersisa adalah vertical scaling (beli mesin makin besar) — mahal, ada batas fisiknya, dan begitu mentok, latency naik & downtime makin sering karena semua beban masih ditanggung satu mesin.

→ makanya kita pakai Sharding & Partitioning.

Akar masalah · Kapasitas satu mesin ada batasnya

Satu server tidak akan pernah cukup selamanya

Waktu aplikasimu masih kecil, satu database di satu server sudah lebih dari cukup. Tapi begitu user bertambah jutaan, tabel membengkak jadi ratusan juta baris, dan traffic baca-tulis terus naik — vertical scaling (beli server lebih besar) punya batas fisik & harga yang makin tidak masuk akal. Solusinya: horizontal scaling — bagi data ke banyak server yang lebih kecil, bukan satu server raksasa.

“Tujuan utama dari partitioning adalah scalability: berbagai partisi bisa disebar ke banyak mesin dalam sebuah cluster shared-nothing, sehingga volume data yang besar bisa disebar ke banyak disk, dan beban query bisa disebar ke banyak prosesor.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 6, Partitioning)
◆ Analogi — rak buku yang sudah penuh

Bayangkan satu perpustakaan dengan satu rak raksasa yang menyimpan semua buku. Awalnya muat. Tapi koleksi terus bertambah — akhirnya rak itu penuh, dan setiap kali orang mencari buku, mereka harus mengantre karena hanya ada satu jalur ke rak itu. Solusinya bukan membangun rak yang lebih besar dan lebih besar lagi tanpa batas — solusinya adalah membagi koleksi ke banyak rak di ruangan berbeda, masing-masing menyimpan sebagian buku, sehingga banyak orang bisa mencari & mengambil buku secara paralel tanpa saling menunggu.

Itulah inti sharding (juga disebut partitioning): membelah satu dataset besar menjadi potongan-potongan lebih kecil yang disebut shard atau partition, lalu menyebarnya ke banyak server. Tiap shard idealnya bisa berjalan sebagai mini-database mandiri — punya sebagian data, melayani sebagian query, tanpa harus tahu apa yang terjadi di shard lain.

Konsep inti · Dua strategi utama

Hash partitioning vs range partitioning

Pertanyaan intinya: baris data mana yang masuk ke shard mana? Ada dua strategi dasar yang paling umum dipakai — masing-masing punya kelebihan & kelemahannya sendiri.

◆ Padanan singkat
Hashkey → hash(key) % N shard → distribusi merata, acak
Rangekey → rentang nilai (A–M, N–Z, dst) → urut, mudah query range

Hash partitioning cocok kalau kamu butuh distribusi merata & jarang query berdasarkan rentang. Range partitioning cocok kalau kamu sering query rentang (misal tanggal), tapi rawan hot spot kalau kunci berurutan.

contoh — dua strategi partitioningSQL
-- 1) HASH PARTITIONING
-- kunci di-hash lalu dipetakan ke salah satu dari N shard
CREATE TABLE orders (
  order_id  uuid,
  user_id   uuid,
  created_at timestamp
) PARTITION BY HASH (user_id);

CREATE TABLE orders_p0 PARTITION OF orders
  FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE orders_p1 PARTITION OF orders
  FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- user_id "acak" → tersebar rata ke p0..p3

-- 2) RANGE PARTITIONING
-- kunci dipetakan berdasarkan rentang nilai berurutan
CREATE TABLE events (
  event_id  bigint,
  created_at timestamp
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
-- created_at selalu naik → tulisan terbaru numpuk di 1 partisi terakhir

Range partitioning enak untuk query seperti WHERE created_at BETWEEN ..., karena database cukup memindai partisi yang relevan saja. Tapi kalau kunci partisinya adalah nilai yang selalu bertambah (timestamp, auto-increment ID), semua tulisan baru akan selalu jatuh ke partisi paling ujung — inilah cikal bakal masalah yang kita bahas di bab berikutnya.

Bahaya tersembunyi · Hot spot & rebalancing

Kunci yang buruk bikin satu shard kebanjiran

Sharding hanya efektif kalau beban tersebar merata. Kalau salah memilih partition key, satu shard bisa menerima jauh lebih banyak traffic dibanding shard lain — disebut hot spot atau hot partition — sementara shard lainnya nyaris menganggur.

“Dalam kasus terburuk, semua beban tulisan berakhir di satu partisi, sehingga N-1 dari N node kamu menganggur, dan satu node yang kebanjiran itu menjadi bottleneck.”

— parafrase gagasan skewed workload & hot spots, Martin Kleppmann, DDIA (Bab 6)
partition key buruk — hot spotSQL
-- partisi berdasarkan timestamp berurutan
PARTITION BY RANGE (created_at)

-- semua request HARI INI selalu nulis
-- ke partisi paling baru yang sama
shard_2026_07  ← 100% traffic tulis hari ini
shard_2026_06  ← 0% (data lama, jarang disentuh)
shard_2026_05  ← 0% (data lama, jarang disentuh)
-- satu shard kepanasan, sisanya nganggur
partition key baik — merataSQL
-- partisi berdasarkan hash dari user_id
PARTITION BY HASH (user_id)

-- traffic tulis dari jutaan user
-- tersebar rata karena hash "mengacak" key
shard_0  ← ~25% traffic
shard_1  ← ~25% traffic
shard_2  ← ~25% traffic
shard_3  ← ~25% traffic
-- beban merata, tak ada shard yang jomplang

Selain memilih kunci yang baik sejak awal, sistem sharding juga perlu strategi rebalancing — memindahkan sebagian data antar-shard saat cluster bertumbuh (menambah shard baru) atau saat distribusi ternyata timpang di kemudian hari. Rebalancing yang baik dilakukan tanpa downtime: data dipindah bertahap di background, sambil traffic tetap dilayani, dan routing diperbarui begitu perpindahan selesai.

◆
Hati-hati dengan celebrity/viral key — walaupun partition key-mu sudah high-cardinality secara umum, satu nilai tertentu (misalnya akun selebriti dengan jutaan follower) tetap bisa jadi hot spot lokal di satu shard. Untuk kasus ekstrem seperti ini, kadang perlu teknik tambahan seperti menambah suffix acak pada key populer agar bebannya ikut tersebar.
◆ Praktik baik · Checklist sebelum sharding

Cara memilih partition key yang aman

Sebagian besar masalah sharding di production bisa dicegah sejak awal dengan memilih partition key yang tepat. Berikut langkah-langkah praktisnya.

  • Pilih key ber-cardinality tinggi & merata — pakai kolom dengan banyak nilai unik yang tersebar rata (mis. user_id), bukan kolom dengan sedikit nilai berulang (mis. status atau negara).
  • Hindari kunci berurutan untuk range partitioning — timestamp atau auto-increment ID yang selalu naik akan membuat semua tulisan baru numpuk di satu partisi ujung.
  • Simpan data yang sering diakses bersama di shard yang sama — hindari query yang harus menyapu banyak shard sekaligus (fan-out query), karena itu mahal & lambat.
  • Rencanakan strategi rebalancing sejak awal — jangan hardcode jumlah shard; siapkan mekanisme memindahkan data saat cluster bertambah.
  • Pantau distribusi beban per-shard — pasang monitoring supaya hot spot terdeteksi sebelum jadi insiden, bukan sesudahnya.
  • Pertimbangkan consistent hashing — untuk meminimalkan data yang perlu dipindah saat menambah/mengurangi jumlah shard.

🌱 Beginner

Paham konsep membelah data

Fokus dulu ke gambaran besar: kenapa sharding dibutuhkan, dan apa bedanya hash vs range partitioning.

  • Mengerti kenapa satu server ada batasnya.
  • Bisa jelaskan beda hash & range partitioning.
  • Tahu istilah shard, partition key, hot spot.
⚙ Middle

Memilih partition key yang tepat

Mulai terapkan ke kasus nyata: pilih kunci yang cocok dengan pola akses aplikasimu sendiri.

  • Bisa menilai cardinality & distribusi sebuah kolom.
  • Tahu kapan pakai range vs hash di aplikasi nyata.
  • Bisa mendeteksi potensi hot spot sebelum deploy.
🚀 Advance

Rebalancing & routing di skala besar

Level operasional: menjaga cluster tetap sehat saat data & traffic terus bertumbuh.

  • Bisa merancang rebalancing tanpa downtime.
  • Paham consistent hashing & minimisasi data movement.
  • Bisa merutekan request ke shard yang benar secara efisien.
◆ Harga · Tidak ada makan siang gratis

Trade-off: skala besar vs kompleksitas operasional

Sharding memberimu skala horizontal yang (nyaris) tak terbatas — tapi harganya adalah kompleksitas baru yang tidak ada saat datamu masih di satu server.

// Yang kamu dapat

  • Skala horizontal — tambah server, tambah kapasitas.
  • Beban baca/tulis tersebar, tiap shard lebih ringan.
  • Kegagalan satu shard tak selalu melumpuhkan semuanya.
  • Bisa menampung dataset jauh lebih besar dari 1 mesin.

// Yang kamu korbankan

  • Query lintas-shard (JOIN, agregasi) jadi rumit & mahal.
  • Transaksi lintas-shard sulit dijaga konsistensinya.
  • Operasional bertambah: routing, monitoring per-shard.
  • Rebalancing & migrasi skema butuh perencanaan matang.
  • Risiko hot spot kalau partition key salah pilih.
◆ Catatan realistis

Sharding menambah kompleksitas ke semua lapisan — aplikasi harus tahu cara merutekan request ke shard yang benar, tim ops harus memantau kesehatan tiap shard, dan developer harus berhenti mengandalkan JOIN lintas-tabel yang dulu gratis di satu database. Ini bukan keputusan yang diambil ringan.

◆ Keputusan · Pakai atau jangan

Kapan harus sharding, kapan belum perlu

Aturan praktisnya: sharding adalah solusi untuk masalah skala yang sudah nyata, bukan sesuatu yang dipasang di awal "buat jaga-jaga".

// Pertimbangkan sharding saat…

  • Satu server sudah mentok CPU/disk/koneksi meski di-tuning.
  • Vertical scaling (upgrade server) sudah tidak ekonomis.
  • Dataset & traffic diproyeksikan terus tumbuh besar.
  • Pola akses jelas: mayoritas query bisa diarahkan ke 1 shard.

// Belum perlu / hindari dulu saat…

  • Masalahnya sebenarnya query lambat / indeks kurang baik.
  • Skala masih bisa ditangani vertical scaling / read replica.
  • Banyak query butuh JOIN/agregasi lintas entitas.
  • Tim belum siap menanggung kompleksitas operasionalnya.
◆ Pertanyaan penentu

Sebelum sharding, tanyakan: "Sudah kucoba indexing, caching, read replica, dan vertical scaling — dan itu semua benar-benar tidak cukup lagi?" Sharding menyelesaikan masalah skala, tapi ia menambah kompleksitas permanen. Jangan pakai sebagai solusi pertama untuk masalah performa yang sebenarnya lebih murah diselesaikan dengan cara lain.

Studi kasus · Di dunia nyata

Bagaimana tim besar men-sharding data mereka

Beberapa contoh nyata perusahaan yang men-sharding datanya untuk menangani skala masif — perhatikan polanya: partition key dipilih berdasarkan bagaimana data itu diakses, bukan asal pilih.

// social media

Instagram — sharding Postgres

Kasus: Instagram men-sharding database Postgres mereka berdasarkan user ID untuk menangani pertumbuhan pengguna yang masif. Kenapa: mayoritas query aplikasi berpusat di sekitar satu user, jadi data terkait user bisa dikelompokkan di shard yang sama, meminimalkan query lintas-shard.

// chat platform

Discord — sharding by guild

Kasus: Discord memigrasikan arsitektur datanya untuk menangani volume pesan yang sangat besar, dengan mempartisi data berdasarkan guild/channel. Kenapa: pesan hampir selalu dibaca dalam konteks satu server/channel, jadi partition key mengikuti pola akses ini agar query tetap cepat.

// productivity

Notion — sharding konten berbasis block

Kasus: Notion mempartisi database Postgres mereka untuk menampung konten berbasis block yang terus bertumbuh seiring jumlah workspace & halaman pengguna. Kenapa: struktur data block-based sangat besar volumenya, dan sharding memungkinkan pertumbuhan itu diserap secara horizontal.

// e-commerce / SaaS

Multi-tenant SaaS — sharding by tenant

Kasus: banyak aplikasi SaaS mempartisi data berdasarkan tenant_id/organization_id, sehingga tiap pelanggan besar bisa diisolasi ke shard tertentu. Kenapa: query harian nyaris selalu di-scope ke satu tenant, jadi partition key ini alami mengikuti batas isolasi data pelanggan.

◆ Benang merahnya

Di semua contoh ini, partition key dipilih agar query yang paling sering dijalankan bisa dilayani oleh satu shard saja — bukan kunci yang dipilih asal, atau sekadar "yang gampang di-hash". Memahami pola akses aplikasi sebelum memilih partition key adalah pekerjaan paling penting dalam merancang sistem sharded.

⚙ Ekosistem · Alat yang dipakai

Tools & ekosistem sharding

Kamu jarang perlu membangun sistem sharding dari nol. Kenali nama-nama ini supaya tahu opsi apa yang tersedia saat kebutuhan skala itu datang.

// MySQL

Vitess

Layer sharding untuk MySQL yang awalnya dibangun YouTube. Menangani routing query, resharding, dan manajemen banyak shard MySQL sebagai satu database logis.

// PostgreSQL

Citus

Ekstensi Postgres yang mengubahnya jadi database terdistribusi. Mendukung sharding by tenant maupun by key, dengan query planner yang paham banyak node.

// document DB

MongoDB Sharding

Sharding bawaan MongoDB — kamu memilih shard key, lalu MongoDB otomatis mendistribusikan & merutekan dokumen ke shard yang sesuai lewat komponen mongos.

// algoritma

Consistent Hashing

Teknik hashing yang meminimalkan jumlah key yang perlu dipindah saat shard ditambah/dikurangi. Jadi dasar banyak sistem terdistribusi seperti DynamoDB & Cassandra.

// wide-column

Cassandra

Database terdistribusi yang sharding & replikasinya jadi bagian inti arsitekturnya sejak awal, dibangun di atas ide consistent hashing.

// cloud managed

DynamoDB · CockroachDB

Database terkelola yang otomatis mempartisi & menyeimbangkan data di belakang layar, sehingga kamu tak perlu mengelola shard secara manual.

◆ Tips pemula

Sebelum membangun sharding manual sendiri, cek dulu apakah database yang sudah kamu pakai punya solusi bawaan atau ekstensi resmi (seperti Citus untuk Postgres atau sharding bawaan MongoDB) — jauh lebih murah dari sisi risiko dibanding merancang sistem routing sendiri dari nol.

Penutup

Sharding menyelesaikan skala, bukan hal lain

Sharding lahir dari kebutuhan nyata: satu mesin ada batasnya. Ia memberimu skala horizontal yang luas, tapi hanya kalau partition key-nya dipilih dengan paham betul pola akses aplikasimu — kalau tidak, kamu hanya memindahkan masalah jadi hot spot yang lebih rumit.

  • Sharding = membelah data — sebar ke banyak mesin, tiap mesin pegang sebagian.
  • Hash partitioning — distribusi merata, kurang cocok untuk query rentang.
  • Range partitioning — enak untuk query rentang, rawan hot spot kalau kunci berurutan.
  • Hot spot — kunci yang buruk bikin satu shard kebanjiran, sisanya menganggur.
  • Rebalancing — rencanakan sejak awal, idealnya tanpa downtime.
  • Pilih key dari pola akses — bukan dari kemudahan implementasi semata.

Aturan emasnya

Sebelum menulis satu baris kode sharding, tanyakan: "Query apa yang paling sering dijalankan aplikasiku, dan bisakah query itu dilayani satu shard saja?" Kalau partition key-mu menjawab pertanyaan itu dengan baik, sharding akan memberimu skala tanpa drama. Kalau tidak, kamu akan menghabiskan waktu memburu hot spot & menulis query fan-out yang mahal.
