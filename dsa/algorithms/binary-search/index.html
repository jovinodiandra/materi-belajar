// DSA — Algorithms · cara paling efisien mencari di data terurut

Cari elemen dengan membagi dua ruang pencarian, tiap iterasi.

Kalau datamu terurut, kamu tidak perlu memeriksa satu-satu dari awal. Binary search memanfaatkan urutan itu: lihat titik tengah, bandingkan, lalu buang separuh ruang pencarian yang pasti tidak mungkin berisi jawabannya. Ulangi pada separuh yang tersisa. Hasilnya: kompleksitas O(log n) — jauh lebih cepat dari O(n) pada linear search. Deck ini juga membahas pola lanjutannya: binary search on answer, di mana teknik ini dipakai bukan di array, tapi langsung di ruang jawaban/nilai — diselingi kalimat dari buku rujukan.

Sakit
Linear search lambat — O(n), cek satu-satu dari awal
Ide
Cek tengah, buang separuh — manfaatkan data yang terurut
Untung
O(log n) — 1 juta data cukup ~20 langkah
Batas
Wajib terurut/monotonic — rawan off-by-one & overflow di mid
Pakai
Array terurut & ruang jawaban — pencarian nilai, optimization problems

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya array berisi 1 juta harga produk yang sudah terurut naik, dan perlu mengecek apakah harga tertentu ada di dalamnya.

When — fungsi pencarian dipanggil ribuan kali per detik saat user memfilter/scroll katalog, dan kamu masih memeriksa elemen satu per satu dari indeks 0.

Then — tiap pencarian bisa butuh sampai 1 juta perbandingan (O(n)) di kasus terburuk, latency menumpuk, dan urutan data yang sudah susah payah dijaga jadi mubazir karena tidak dimanfaatkan sama sekali.

→ makanya kita pakai binary search: cek titik tengah, buang separuh yang mustahil, ulangi — 1 juta data cukup ~20 langkah (O(log n)).

Akar masalah · Kenapa binary search powerful

Seperti mencari kata di kamus fisik, bukan membaca dari halaman satu

Bayangkan mencari kata "recursion" di kamus tebal. Tidak ada orang waras yang membuka dari halaman pertama dan membaca satu-satu sampai ketemu. Yang dilakukan: buka di tengah, lihat kata di halaman itu, lalu langsung tahu — "recursion" ada di separuh kanan atau separuh kiri. Separuh yang salah langsung dibuang tanpa dibaca sama sekali. Ulangi di separuh yang tersisa, dan lagi, sampai ketemu.

◆ Analogi — buka tengah, tahu arah, buang setengah, ulangi

Kamus punya satu properti penting: terurut secara alfabet. Properti inilah yang membuat trik "buka tengah lalu buang setengah" bisa dipercaya — kamu tahu pasti ke arah mana harus mencari, karena semua yang ada di kiri lebih kecil dan semua yang ada di kanan lebih besar. Tanpa urutan, trik ini tidak bisa dipakai sama sekali; kamu terpaksa balik ke cara linear, cek satu-satu.

Bandingkan dengan linear search: memeriksa elemen satu per satu dari awal sampai ketemu atau habis. Untuk 1 juta elemen, linear search bisa butuh sampai 1 juta perbandingan di kasus terburuk. Binary search, berkat properti "buang setengah tiap langkah", cukup butuh sekitar log₂(1.000.000) ≈ 20 perbandingan saja.

“Binary search mencontohkan strategi divide and conquer paling sederhana: setiap perbandingan membuang separuh ruang pencarian yang tersisa, menghasilkan kompleksitas logaritmik yang jauh lebih baik dibanding pendekatan linear.”

— parafrase dari Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest, Clifford Stein, Introduction to Algorithms (CLRS)
Konsep inti · Mid, ruang pencarian & overflow

mid = (low + high) / 2 — sederhana, tapi mudah salah

Inti algoritmanya: jaga dua penanda low dan high yang menandai batas ruang pencarian saat ini. Hitung mid di tengahnya, bandingkan dengan target, lalu persempit low atau high supaya separuh yang tidak mungkin berisi target dibuang. Ulangi sampai ketemu atau ruang pencarian habis.

“Meski konsepnya sederhana, riset menunjukkan mayoritas programmer profesional menuliskan binary search yang salah pada percobaan pertama — biasanya karena off-by-one error atau kesalahan menghitung titik tengah. Ini bukti bahwa algoritma sederhana pun butuh ketelitian penuh dalam implementasinya.”

— parafrase dari Jon Bentley, Programming Pearls
◆
Waspada integer overflow: menulis mid = (low + high) / 2 terlihat wajar, tapi kalau low dan high sama-sama besar, low + high bisa melebihi batas int dan meluber (overflow) sebelum sempat dibagi dua. Cara amannya: mid = low + (high - low) / 2 — secara matematis sama, tapi tidak pernah menjumlahkan dua angka besar sekaligus.
BinarySearch.java — versi iteratifJava
public class BinarySearch {

    static int search(int[] arr, int target) {
        int low = 0, high = arr.length - 1;
        while (low <= high) {
            int mid = low + (high - low) / 2; // hindari overflow
            if (arr[mid] == target) {
                return mid;
            } else if (arr[mid] < target) {
                low = mid + 1;  // buang separuh kiri
            } else {
                high = mid - 1; // buang separuh kanan
            }
        }
        return -1; // tidak ditemukan
    }

    public static void main(String[] args) {
        int[] data = { 2, 5, 8, 12, 16, 23, 38, 45, 56, 72, 91 };
        System.out.println(search(data, 23)); // 5
    }
}
BinarySearch.java — versi rekursifJava
static int searchRecursive(int[] arr, int target, int low, int high) {
    if (low > high) {
        return -1; // base case: ruang pencarian habis
    }
    int mid = low + (high - low) / 2;
    if (arr[mid] == target) {
        return mid;
    } else if (arr[mid] < target) {
        return searchRecursive(arr, target, mid + 1, high);
    } else {
        return searchRecursive(arr, target, low, mid - 1);
    }
}

Perhatikan: setiap iterasi (atau setiap panggilan rekursif) selalu memperkecil rentang [low, high] — inilah yang menjamin algoritma pasti berhenti, dan menjamin kompleksitas O(log n) karena rentangnya mengecil separuh-separuh, bukan satu-satu seperti linear search.

Pola lanjutan · Binary search on answer

Binary search tidak harus di array — bisa di ruang jawaban

Ini pergeseran cara pandang yang penting: binary search sebenarnya bekerja pada apa saja yang monotonic — di mana begitu satu titik "gagal" atau "berhasil", semua titik di satu sisinya juga pasti gagal/berhasil dengan cara yang sama. Array terurut cuma satu contoh struktur monotonic. Struktur lain yang monotonic: ruang nilai/jawaban itu sendiri.

◆ Contoh kasus — kecepatan minimum agar selesai tepat waktu

Misal: ada beberapa segmen perjalanan dengan jarak tertentu, dan kamu harus sampai tujuan dalam batasJam jam. Berapa kecepatan minimum (bulat) yang dibutuhkan? Kuncinya: kalau kecepatan v sudah cukup untuk sampai tepat waktu, maka semua kecepatan > v juga pasti cukup — inilah sifat monotonic di ruang jawaban "kecepatan". Karena monotonic, kamu bisa binary search langsung di rentang kecepatan yang mungkin, bukan di sebuah array.

MinSpeed.java — binary search on answerJava
// ruang jawaban = rentang kecepatan yang mungkin, bukan array
static int minKecepatan(int[] jarak, int batasJam) {
    int low = 1, high = 1_000_000; // batas atas kecepatan wajar
    while (low < high) {
        int mid = low + (high - low) / 2;
        if (cukupWaktu(jarak, mid, batasJam)) {
            high = mid;     // mid sudah cukup, coba yang lebih kecil
        } else {
            low = mid + 1; // mid belum cukup, butuh lebih cepat
        }
    }
    return low; // kecepatan minimum yang masih cukup
}

static boolean cukupWaktu(int[] jarak, int kecepatan, int batasJam) {
    double totalJam = 0;
    for (int d : jarak) {
        totalJam += Math.ceil((double) d / kecepatan);
    }
    return totalJam <= batasJam;
}

Polanya sama persis dengan binary search di array: cukupWaktu(mid) berperan seperti perbandingan arr[mid] dengan target — bedanya, yang dibandingkan bukan elemen array, tapi hasil sebuah fungsi predikat di ruang nilai. Selama predikat itu monotonic, binary search bisa dipakai.

cari di array terurut — linearJava
static int linearSearch(int[] arr, int target) {
    for (int i = 0; i < arr.length; i++) {
        if (arr[i] == target) return i;
    }
    return -1;
}
// O(n) — cek satu-satu, tak peduli terurut atau tidak
cari di array terurut — binaryJava
static int binarySearch(int[] arr, int target) {
    int low = 0, high = arr.length - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] == target) return mid;
        else if (arr[mid] < target) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}
// O(log n) — buang setengah tiap langkah, butuh data terurut
◆ Praktik · Kebiasaan aman menulis binary search

Best practice menulis binary search

Bentley benar — binary search gampang salah di detail kecil. Kebiasaan berikut menyelamatkanmu dari bug paling umum: off-by-one, overflow, sampai infinite loop.

  1. Pastikan datanya benar-benar terurut (atau ruang jawabannya monotonic) sebelum binary search dipakai — tanpa ini, hasilnya tidak bisa dipercaya sama sekali.
  2. Hati-hati kondisi low <= high vs low < high — ini sumber off-by-one paling umum. low <= high dipakai saat mencari kecocokan pasti (return -1 kalau habis); low < high dipakai saat mempersempit ke satu titik jawaban (pola binary search on answer).
  3. Gunakan low + (high - low) / 2, bukan (low + high) / 2, untuk menghindari integer overflow saat low dan high sama-sama besar.
  4. Pastikan tiap iterasi benar-benar mempersempit rentang — kalau update low/high salah (misal lupa +1/-1), rentang bisa berhenti mengecil dan menyebabkan infinite loop.
  5. Tentukan dulu: mencari kecocokan tepat atau batas (boundary)? Variasi seperti first occurrence/last occurrence butuh logika update yang berbeda dari pencarian kecocokan biasa.
  6. Uji edge case — array kosong, target di elemen pertama/terakhir, target tidak ada, dan array berisi satu elemen — sebelum percaya implementasinya benar.
◆ Roadmap · Bertahap sesuai levelmu

Tier belajar binary search

Binary search dasar cuma pintu masuk — variasinya banyak dipakai di soal interview maupun sistem production nyata. Berikut jalurnya dari dasar sampai lanjut.

Beginner

Binary search dasar di array

Mulai dari kasus paling standar: array terurut, cari satu nilai target, kembalikan index-nya.

  • Binary search iteratif di array int
  • Binary search rekursif di array int
  • Cari index atau -1 kalau tidak ada
  • Trace manual low/mid/high di kertas
Middle

Variasi pencarian

Bentuk soal mulai bergeser dari "cari satu nilai" ke "cari batas" atau "cari di struktur yang tidak sepenuhnya terurut".

  • Cari first occurrence & last occurrence
  • Search in rotated sorted array
  • Cari elemen terdekat (floor/ceiling)
  • Binary search pada array dengan duplikat
Advance

Binary search sebagai alat optimisasi

Di level ini, binary search bukan lagi soal "cari di array" — tapi alat umum untuk mempersempit ruang jawaban.

  • Binary search on answer untuk optimization problems
  • Binary search di matriks 2D terurut
  • Kombinasi binary search + greedy/feasibility check
  • Binary search pada fungsi kontinu/real number
◆ Harga · Binary search vs linear search

Trade-off: O(log n) yang cepat, tapi butuh syarat

Binary search hampir selalu menang dari segi kecepatan — tapi kecepatan itu bersyarat. Linear search tidak butuh syarat apa pun, dan itu sendiri adalah kekuatannya di kasus tertentu.

// Binary search — O(log n)

  • Sangat cepat untuk data besar — 1 juta elemen ≈ 20 langkah.
  • Skalanya logaritmik, hampir tak terasa saat data tumbuh.
  • Bisa diperluas ke ruang jawaban, bukan cuma array.

// Linear search — O(n)

  • Wajib jalan satu-satu — makin banyak data, makin lambat linier.
  • Tidak butuh data terurut sama sekali.
  • Lebih sederhana & lebih murah untuk data kecil / sekali pakai.
◆ Harga tersembunyi: menjaga data tetap terurut

Binary search butuh data terurut/monotonic — dan menjaga itu tidak gratis. Kalau datamu sering berubah (insert/delete), menjaga urutan tiap kali menambah biaya tersendiri (mis. O(log n) per insert kalau pakai struktur seperti TreeSet/B-tree, atau O(n) kalau array biasa harus digeser). Untuk data yang jarang berubah tapi sering dicari, biaya ini sangat sepadan; untuk data yang berubah terus-menerus tanpa dibaca berulang, linear search kadang justru lebih murah secara total.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai binary search

Sinyal paling kuat di soal: kata "terurut", atau frasa "cari nilai optimal dalam rentang" — kedua-duanya petunjuk kuat bahwa binary search relevan, entah di array maupun di ruang jawaban.

// Pakai binary search saat…

  • Data eksplisit sudah/bisa diurutkan.
  • Soal minta "cari nilai minimum/maksimum yang memenuhi syarat".
  • Ada fungsi predikat yang monotonic (feasibility check).
  • Data besar & dicari berkali-kali (biaya sort terbayar).

// Jangan / pertimbangkan lain saat…

  • Data tidak terurut & tidak bisa diurutkan murah.
  • Data kecil — overhead logika binary search tak sepadan.
  • Data berubah sangat sering (insert/delete terus-menerus).
  • Tidak ada relasi monotonic yang bisa dieksploitasi.
◆ Pertanyaan penentu

Tanyakan ke soalnya: "Kalau saya coba satu nilai/index, apakah saya bisa langsung tahu jawabannya ada di sisi kiri atau kanan dari situ?" Kalau ya — datanya terurut atau predikatnya monotonic — binary search akan bekerja. Kalau tidak, kamu perlu cara lain (atau urutkan dulu datanya).

Studi kasus · Di dunia nyata

Di mana prinsip binary search benar-benar dipakai

Tiga contoh nyata di mana ide "buang setengah ruang pencarian tiap langkah" dipakai jauh di luar soal "cari angka di array".

// debugging

git bisect

Kasus: mencari commit mana yang pertama kali memperkenalkan bug, di antara ratusan commit sejak versi terakhir yang diketahui baik. Kenapa binary search: riwayat commit bersifat monotonic terhadap waktu — git bisect menandai satu commit di tengah rentang sebagai "good" atau "bad", lalu membuang separuh rentang yang tidak mungkin berisi commit penyebab, persis seperti mencari di array terurut.

// database

B-tree index

Kasus: database perlu menemukan baris tertentu di antara jutaan baris tanpa memindai semuanya. Kenapa mirip binary search: struktur index B-tree secara konsep mempersempit pencarian bertahap dari root ke leaf — tiap langkah membuang sebagian besar cabang yang pasti tidak berisi nilai yang dicari, prinsip yang sama dengan "buang separuh" di binary search, walau strukturnya multi-cabang, bukan dua cabang.

// optimization

Cari threshold optimal

Kasus: sistem version control & rate limiting kadang perlu mencari nilai ambang batas optimal — misalnya batas rate limit terketat yang masih tidak menolak traffic normal, atau versi minimum dependency yang masih kompatibel. Kenapa binary search: begitu satu nilai ambang terbukti "terlalu ketat" atau "cukup longgar", semua nilai di satu sisinya berperilaku sama — ini pola binary search on answer.

◆ Benang merahnya

Di ketiga kasus di atas, yang dicari bukan selalu "angka di array" — tapi selalu ada ruang pencarian yang bisa dipersempit separuh-separuh berkat sifat monotonic-nya. Itulah kenapa binary search jauh lebih dari sekadar trik soal interview: ia adalah cara berpikir umum untuk mempersempit kemungkinan secara efisien.

Tools & referensi

Sebelum menulis binary search sendiri berulang-ulang, kenali dulu alat siap pakai yang sudah teruji — dan topik yang berkaitan langsung dengan analisis performanya.

// built-in

Arrays.binarySearch (Java)

Method bawaan java.util.Arrays untuk binary search di array yang sudah terurut. Mengembalikan index kalau ketemu, atau nilai negatif (posisi insert-nya) kalau tidak — sudah teruji & teroptimasi, dipakai daripada menulis ulang untuk kasus standar.

// CLI tool

git bisect

Perintah git yang menerapkan binary search langsung ke riwayat commit untuk mencari commit penyebab bug. Cara nyata melihat binary search bekerja di luar konteks array/soal algoritma.

Penutup

Buang setengah yang tidak mungkin, percaya sisanya

Binary search lahir dari satu wawasan sederhana: kalau kamu tahu arah mana yang salah, tidak perlu memeriksanya sama sekali. Ia bersinar di data terurut — dan meluas jauh lebih jauh lagi begitu kamu sadar "ruang pencarian" itu bisa berupa array, atau bisa berupa rentang nilai jawaban itu sendiri.

  • Analogi kamus — buka tengah, tahu arah, buang setengah, ulangi.
  • mid = low + (high - low) / 2 — hindari overflow, bukan (low+high)/2.
  • Wajib terurut/monotonic — tanpa itu binary search tidak valid.
  • Binary search on answer — bekerja di ruang nilai, bukan cuma array.
  • O(log n) — jauh lebih cepat dari O(n) linear search, dengan syarat.
  • Detail kecil menentukan — off-by-one & kondisi loop mudah salah.

Aturan emasnya

Sebelum menulis kode: pastikan datamu terurut atau predikatmu monotonic. Pakai low + (high - low) / 2. Tentukan dengan jelas apakah kamu mencari kecocokan pasti (low <= high) atau batas jawaban (low < high). Kalau tiga hal itu benar, sisanya tinggal percaya bahwa separuh yang dibuang memang tidak mungkin berisi jawaban.
