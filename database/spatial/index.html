// Database — saat datamu punya lintang & bujur, bukan cuma angka biasa

Cari yang terdekat, tanpa menghitung satu per satu.

"Restoran dalam radius 2 km" atau "titik yang jatuh di dalam area ini" terdengar seperti query biasa — sampai kamu coba jalankan di jutaan baris dengan rumus jarak manual dan tabelnya melambat drastis. Database spatial menyimpan lokasi sebagai tipe data geometri asli & mengindeksnya dengan struktur khusus (R-tree) supaya pencarian berbasis ruang tetap cepat. Deck ini buat pemula: dari kenapa ia dibutuhkan, cara kerja index-nya, trade-off-nya, sampai kapan dipakai di production — diselingi kalimat dari sumber rujukan.

Sakit
Hitung jarak manual — scan semua baris, lambat di skala besar
Ide
Simpan lokasi sebagai geometri — point, polygon, linestring asli
Kunci
Index R-tree — bounding box bersarang, singkirkan area tak relevan
Untung
Query radius & polygon jadi cepat — ST_DWithin, ST_Contains dalam milidetik
Pakai
Saat query-mu berbasis ruang — peta, ride-hailing, delivery, properti

◆ Kenapa pakai ini?

Given — lokasi cuma disimpan sebagai dua kolom angka biasa (lat, lng), diindeks pakai B-tree seperti kolom umur atau harga.

When — fitur "SPBU dalam radius 3 km" atau "titik yang masuk area pengiriman ini" mulai dipakai user, dan tabelnya tumbuh sampai jutaan baris.

Then — tiap query terpaksa menghitung jarak Haversine ke semua baris satu per satu (full table scan), karena B-tree cuma efisien mengurutkan satu dimensi, bukan menyaring dua dimensi sekaligus — waktu respons meledak dari milidetik jadi detik atau menit begitu data membesar.

→ makanya kita pakai Spatial Database (geometri asli + index R-tree).

Akar masalah · Query berbasis ruang itu beda

"Cari yang terdekat" bukan query biasa

Bayangkan aplikasi cari restoran terdekat. Cara paling naif: simpan lintang & bujur sebagai dua kolom angka biasa, lalu untuk tiap pencarian hitung jarak dari lokasi user ke semua restoran di tabel pakai rumus Haversine, urutkan, ambil yang terdekat. Di 100 baris data, itu instan. Di 5 juta baris, database harus membaca & menghitung jarak untuk tiap baris — full table scan yang jelas tidak akan skala.

◆ Analogi — mencari alamat tanpa peta

Index biasa (B-tree) itu seperti daftar nama di buku telepon — diurutkan satu dimensi, gampang dicari secara alfabetis. Tapi lokasi punya dua dimensi sekaligus (lintang dan bujur). Mencari "semua titik dalam radius 2 km" pakai index satu dimensi itu seperti mencari alamat rumah tanpa peta — kamu tetap harus mengecek satu per satu apakah rumah itu dekat atau tidak, karena urutan alfabetis nama jalan tidak berkorelasi dengan jarak fisik.

Index B-tree biasa dibangun untuk satu dimensi. Begitu kamu punya query dua dimensi sekaligus — lintang dan bujur secara bersamaan — index semacam itu tidak lagi efisien, sehingga dibutuhkan struktur index khusus yang bisa menangani banyak dimensi.

— parafrase dari Martin Kleppmann, Designing Data-Intensive Applications, Bab 3 (pembahasan multi-dimensional index)

Karena itu lahir spatial database: database (atau ekstensi database) yang menyimpan geometri sebagai tipe data asli & punya index khusus supaya query "titik dalam radius X km" atau "titik dalam polygon" bisa dijawab dalam milidetik, bukan dengan memindai seluruh tabel.

Konsep inti · Tipe data & index spasial

Lokasi disimpan sebagai geometri, dicari lewat index spasial

Spatial database punya tiga tipe data geometri dasar yang jadi fondasi hampir semua query lokasi:

◆ Tipe geometri dasar
PointPOINT(106.827 -6.175)
LineStringLINESTRING(0 0, 1 1, 2 0)
PolygonPOLYGON((0 0, 4 0, 4 4, 0 4, 0 0))

Point = satu titik (lokasi toko, driver, user). LineString = rangkaian titik membentuk garis (rute jalan, jalur pengiriman). Polygon = area tertutup (batas kota, zona pengiriman, radius jangkauan).

Supaya query lokasi cepat, kolom geometri diberi index spasial — paling umum berbentuk R-tree, yang mengelompokkan objek ke dalam bounding box (kotak pembungkus) yang saling bersarang. Di PostgreSQL, ekstensi PostGIS menyediakan tipe geometri ini lengkap dengan index GIST berbasis R-tree.

cari restoran dalam radius 2 km — PostGISSQL
-- tabel restoran, kolom lokasi bertipe geography (Point)
CREATE TABLE restoran (
  id       serial primary key,
  nama     text,
  lokasi   geography(Point, 4326)
);

-- index spasial: R-tree lewat GIST
CREATE INDEX idx_restoran_lokasi ON restoran USING GIST (lokasi);

-- cari yang dalam radius 2000 meter dari posisi user, urut dari terdekat
SELECT nama,
       ST_Distance(lokasi, ST_MakePoint(106.8272, -6.1751)::geography) AS jarak_meter
FROM restoran
WHERE ST_DWithin(lokasi, ST_MakePoint(106.8272, -6.1751)::geography, 2000)
ORDER BY jarak_meter
LIMIT 20;

ST_DWithin memakai index spasial untuk langsung membuang restoran yang jelas jauh, baru menghitung jarak presisi untuk kandidat yang tersisa. Untuk query titik dalam polygon (mis. "toko mana saja yang masuk zona pengiriman ini"), pakai ST_Contains:

titik di dalam polygon — zona pengirimanSQL
SELECT r.nama
FROM restoran r, zona_pengiriman z
WHERE z.nama_zona = 'Zona A'
  AND ST_Contains(z.area, r.lokasi::geometry);
Konsep penting · Di balik layar

R-tree: bounding box yang bersarang

Ide R-tree ditemukan oleh Antonin Guttman lewat papernya di SIGMOD 1984, dan gagasan intinya tetap dipakai sampai sekarang di PostGIS, MongoDB, hingga index spasial di banyak database lain.

Objek-objek spasial dikelompokkan ke dalam bounding box, dan bounding box-bounding box itu sendiri dikelompokkan lagi ke dalam bounding box yang lebih besar secara bersarang — sehingga saat mencari, mesin database bisa langsung menyingkirkan seluruh cabang yang bounding box-nya jelas tidak beririsan dengan area pencarian, tanpa perlu memeriksa objek di dalamnya satu per satu.

— parafrase dari Antonin Guttman, R-Trees: A Dynamic Index Structure for Spatial Searching, SIGMOD 1984
◆ Analogi — kotak di dalam kotak di dalam gudang

Bayangkan gudang besar berisi ribuan kotak kecil. Daripada menaruh semua kotak berserakan, kamu kelompokkan kotak-kotak yang berdekatan ke dalam kotak sedang, lalu kelompokkan kotak-kotak sedang yang berdekatan ke dalam kotak besar, dan seterusnya — persis seperti boneka Matryoshka. Saat mencari barang di area tertentu, kamu cukup buka kotak besar yang beririsan dengan area itu, abaikan sisanya sepenuhnya. Itulah cara R-tree bekerja: bounding box makin ke atas makin besar & makin sedikit, jadi pencarian bisa "loncat" langsung ke cabang yang relevan.

Setiap node di R-tree menyimpan bounding box yang membungkus semua anaknya. Saat query ST_DWithin atau ST_Contains dijalankan, database menelusuri pohon dari akar: kalau bounding box sebuah cabang tidak beririsan dengan area pencarian, seluruh cabang itu langsung dilewati — tidak peduli berapa ribu objek di dalamnya. Inilah kenapa query spasial dengan index bisa jauh lebih cepat daripada menghitung jarak untuk tiap baris satu per satu.

◆ Praktik · Supaya query spasial tetap cepat

Best practice query & index spasial

Punya PostGIS bukan jaminan query otomatis cepat. Beberapa kebiasaan ini yang membedakan query spasial yang kilat dengan yang tetap lambat walau sudah ada index.

  • Selalu index kolom geometry/geography dengan CREATE INDEX ... USING GIST (kolom). Tanpa index ini, query spasial jatuh ke seq scan walau tabelnya kecil sekalipun terasa cepat — begitu data membesar, langsung melambat drastis.
  • Pilih SRID yang tepat. 4326 (WGS84, lintang/bujur global) cocok untuk data dunia nyata & dipakai bareng tipe geography. Untuk perhitungan area/jarak presisi di wilayah kecil (kota, negara), pertimbangkan projected CRS lokal agar hasil metrik lebih akurat.
  • Gunakan bounding box dulu, presisi belakangan. Fungsi seperti ST_DWithin & operator && memakai index untuk membuang kandidat yang jelas jauh sebelum menghitung jarak geometris presisi — jauh lebih murah daripada langsung ST_Distance ke semua baris.
  • Pahami beda geometry vs geography. geometry lebih cepat dihitung (asumsi bidang datar), geography lebih akurat untuk jarak permukaan bumi tapi sedikit lebih berat. Pilih sesuai kebutuhan akurasi.
  • Cek query plan-nya. Jalankan EXPLAIN ANALYZE untuk memastikan index spasial benar-benar dipakai (index scan), bukan seq scan yang menandakan index tidak terpakai atau query-nya tidak "sargable".
  • Batasi radius/area pencarian di query, bukan di aplikasi — biarkan database yang membuang data tak relevan lewat index, jangan tarik semua baris lalu filter di kode.
◆ Jenjang · Dari dasar sampai skala besar

Tier belajar spatial database

Belajar spatial database bertahap — mulai dari query jarak sederhana, sampai desain index geospasial untuk skala jutaan titik.

🌱 Beginner

Query jarak & radius dasar

Fokus memahami tipe geometri & fungsi query paling sering dipakai.

  • Bikin kolom geography(Point) & pasang index GIST.
  • Pakai ST_Distance & ST_DWithin untuk cari titik terdekat.
  • Paham beda geometry vs geography.
  • Baca hasil EXPLAIN sederhana.
⚙ Middle

Fitur "cari di sekitar saya"

Mendesain fitur lokasi nyata untuk aplikasi produksi.

  • Gabungkan filter lokasi dengan filter lain (kategori, rating).
  • Urutkan & paginasi hasil berdasar jarak.
  • Query titik-dalam-polygon untuk zona layanan.
  • Caching hasil pencarian lokasi yang sering diakses.
🚀 Advance

Geospatial indexing skala besar

Menangani jutaan titik & query polygon kompleks.

  • Pakai grid hierarkis seperti H3 atau geohash.
  • Sharding/partitioning data berdasar wilayah.
  • Optimasi query polygon kompleks & spatial join.
  • Trade-off presisi vs performa di skala real-time.
◆ Harga · Tidak ada makan siang gratis

Trade-off: yang kamu dapat & yang kamu korbankan

Spatial database memberi kecepatan luar biasa untuk query lokasi — tapi kecepatan itu datang dengan kompleksitas setup & kurva belajar sistem koordinat.

// Yang kamu dapat

  • Query radius & polygon sangat cepat lewat index R-tree.
  • Hasil akurat secara geometris, bukan perkiraan kasar.
  • Operasi spasial lengkap: jarak, kontainment, intersection, union.
  • Skala baik dengan partitioning berbasis wilayah.

// Yang kamu korbankan

  • Butuh ekstensi khusus (PostGIS) yang harus dipasang & dikonfigurasi.
  • Kurva belajar sistem koordinat (SRID) cukup curam bagi pemula.
  • Storage index spasial lebih besar dari index biasa.
  • Migrasi/konversi data antar SRID bisa rumit & rawan salah.
◆ Catatan praktis

Kesalahan SRID adalah sumber bug paling umum di project spasial pemula — mencampur koordinat 4326 (lintang/bujur) dengan sistem proyeksi meter tanpa transformasi eksplisit bisa menghasilkan jarak yang salah total tanpa error apa pun. Selalu jelas soal SRID apa yang dipakai di tiap kolom.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai spatial database

Aturan praktisnya: kalau query utamamu bertanya soal jarak, radius, atau "apakah titik ini di dalam area itu" — pakai spatial index. Kalau lokasi cuma data pelengkap yang jarang di-query berbasis ruang, kolom lat/long biasa sudah cukup.

// Pakai spatial database saat…

  • Ada fitur "cari terdekat" atau "di sekitar saya".
  • Query titik-dalam-polygon (zona, area layanan).
  • Aplikasi peta, ride-hailing, delivery, properti.
  • Volume data lokasi besar & terus bertambah.
  • Butuh operasi spasial lain (intersection, buffer, union).

// Belum perlu saat…

  • Lokasi cuma disimpan untuk ditampilkan, tak pernah di-query.
  • Data lokasinya kecil & jarang bertambah.
  • Cukup filter kasar per kota/wilayah (bukan radius presisi).
  • Tim belum siap dengan kompleksitas SRID & ekstensi baru.
◆ Pertanyaan penentu

Tanyakan: "Apakah aplikasiku pernah bertanya soal jarak atau area secara langsung ke database?" Kalau ya — walau baru satu fitur "restoran terdekat" — index spasial akan menyelamatkanmu dari full table scan begitu datamu tumbuh. Kalau lokasi sekadar metadata yang ditampilkan di peta tanpa pernah difilter berdasar jarak, kolom biasa sudah cukup untuk saat ini.

Studi kasus · Di dunia nyata

Bagaimana produk besar menangani skala lokasi

Tiga skenario nyata di mana pencarian & indexing berbasis lokasi jadi bagian inti sistem — bukan sekadar fitur tempelan.

// ride-hailing

Uber & H3

Kasus: mencocokkan jutaan driver & penumpang secara real-time butuh cara cepat membagi peta jadi wilayah-wilayah kecil. Pendekatan: Uber membangun & mengembangkan H3, sistem indexing geospasial berbasis grid heksagonal hierarkis, untuk mempercepat matching & agregasi spasial. Tool: H3 (open source).

// ride-hailing & delivery

Grab di Asia Tenggara

Kasus: layanan ride-hailing & pengiriman makanan yang beroperasi lintas banyak kota dengan kepadatan & pola jalan yang beragam. Pendekatan: memanfaatkan geospatial indexing untuk pencarian driver terdekat & estimasi rute di wilayah operasional yang luas.

// marketplace properti

Airbnb — pencarian properti di peta

Kasus: pengguna mencari akomodasi dalam area peta tertentu atau radius dari lokasi favorit. Pendekatan: query berbasis lokasi (titik dalam area/polygon peta) memakai index spasial seperti PostGIS untuk menyaring listing secara cepat sebelum ranking lanjutan.

// on-demand services

Gojek — layanan berbasis lokasi

Kasus: berbagai layanan (ojek, delivery, layanan rumah) yang semuanya butuh pencarian mitra atau lokasi terdekat secara cepat. Pendekatan: PostGIS & index spasial jadi fondasi umum untuk query "siapa/apa yang terdekat" di banyak layanan sekaligus.

◆ Benang merahnya

Di semua kasus di atas, pola query intinya sama: "apa/siapa yang dekat dengan titik ini" — dijalankan berulang kali, dalam skala besar, dengan latensi rendah. Begitu volume & frekuensi query lokasi tinggi, index spasial (R-tree lewat PostGIS, atau grid hierarkis seperti H3) bukan lagi opsional, melainkan fondasi arsitektur.

◆
Detail implementasi & angka performa spesifik dari perusahaan-perusahaan di atas bervariasi & berubah seiring waktu — poin di sini adalah polanya: sistem berskala besar dengan query lokasi intensif butuh index spasial khusus, bukan filter jarak manual di aplikasi.
⚙ Ekosistem · Alat yang dipakai

Tools & ekosistem spatial database

Sebagai pemula, mulai dari PostGIS kalau kamu sudah pakai PostgreSQL — paling matang & dokumentasinya lengkap.

// paling matang

PostGIS

Ekstensi spasial untuk PostgreSQL. Tipe geometri lengkap, ratusan fungsi ST_*, index GIST berbasis R-tree. Standar de-facto untuk spatial database open source.

// document DB

MongoDB geospatial index

Mendukung tipe GeoJSON & index 2dsphere untuk query radius ($near) & polygon ($geoWithin) langsung di document database.

// hierarchical grid

Uber H3

Library indexing geospasial berbasis grid heksagonal hierarkis. Cocok untuk agregasi & matching skala besar, dipakai luas di luar Uber juga.

// search & analytics

Elasticsearch geo queries

Mendukung tipe geo_point & geo_shape dengan query geo_distance & geo_bounding_box — sering dipasangkan dengan pencarian teks.

// alternatif encoding

Geohash

Mengubah koordinat jadi string alfanumerik hierarkis — dua titik dengan prefix sama artinya berdekatan. Sederhana & mudah diindeks di database apa pun.

// cloud managed

PostgreSQL/PostGIS terkelola

Tersedia sebagai layanan terkelola di AWS RDS, Google Cloud SQL, Azure — tinggal aktifkan ekstensi PostGIS tanpa perlu kelola server sendiri.

◆ Tips pemula

Kalau kamu sudah pakai PostgreSQL, cukup CREATE EXTENSION postgis; — tak perlu database baru. Baru pertimbangkan H3/geohash saat kebutuhanmu benar-benar skala besar (jutaan titik, agregasi wilayah real-time).

Penutup

Ruang butuh index-nya sendiri

Spatial database lahir dari kesadaran bahwa lokasi punya dua dimensi sekaligus, dan index satu dimensi biasa tidak cukup. R-tree menjawabnya dengan mengelompokkan objek ke bounding box bersarang, sehingga query radius & polygon bisa membuang area tak relevan tanpa memeriksa tiap titik satu-satu.

  • Lokasi = dua dimensi — index B-tree biasa tidak cukup efisien untuknya.
  • Geometri asli — point, linestring, polygon sebagai tipe data, bukan sekadar angka.
  • R-tree — bounding box bersarang, singkirkan area tak relevan lebih dulu.
  • Bounding box dulu, presisi belakangan — itu rahasia query spasial yang cepat.
  • SRID itu penting — kesalahan sistem koordinat adalah sumber bug paling umum.
  • Skala besar, pikirkan H3/geohash — bukan cuma R-tree tunggal.

Aturan emasnya

Tanya: "Apakah query-ku bertanya soal jarak atau area, bukan cuma menampilkan koordinat?" Kalau ya, index spasial (R-tree lewat PostGIS, atau grid hierarkis seperti H3) akan menyelamatkanmu dari full table scan begitu datamu bertumbuh. Ruang butuh cara berpikir & index-nya sendiri — dan sekarang kamu tahu kenapa.
