// Problem Solving — bagian paling penting: bukan solusi, tapi PROSESNYA

Ini bukan solusi. Ini rekaman proses berpikir dari nol sampai solve.

Semua halaman sebelumnya ngomongin framework, pattern recognition, brute force → optimal, complexity, dan edge case secara terpisah. Di halaman ini, semuanya digabung jadi satu cerita utuh: kamu akan lihat aku membedah dua soal dari awal — termasuk kebingungan awal, ide yang salah & dibuang, sampai akhirnya ketemu solusinya. Kalau solusi rapi di buku/video terasa terlalu mulus sampai bikin minder ("kok aku nggak kepikiran ya"), halaman ini buat kamu.

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu cuma pernah lihat solusi final di editorial/tutorial: rapi, langsung optimal, seolah orangnya langsung kepikiran hash map atau sliding window sejak baris pertama.

When — kamu sendirian hadapi soal baru, brute force pertama masih kebayang, tapi begitu harus loncat ke solusi optimal, kamu macet — dan mulai mikir "kok orang lain bisa langsung kepikiran, aku kok nggak".

Then — tanpa lihat proses coba-coba & jalan buntunya, kamu cuma ngapalin pola hasil akhir, bukan cara menurunkannya; begitu soal berikutnya beda dikit dari yang dihafal, insight itu nggak muncul lagi.

→ makanya kita pakai worked walkthroughs.

Soal #1 · Two Sum

Mulai dari yang paling gampang kepikiran

Soal ini sengaja dipilih karena terkenal & termasuk ringan — tujuannya bukan soalnya, tapi proses yang kamu lihat di baliknya. Aku akan mikir keras (literally), termasuk bagian yang jalan buntu.

soal #1SOAL
// Two Sum
// Diberikan array integer `nums` dan integer `target`,
// kembalikan INDEKS dua angka yang jika dijumlahkan = target.
// Asumsi: tepat ada satu solusi, & kamu tidak boleh pakai
// elemen yang sama dua kali.

// Contoh:
Input:  nums = [2, 7, 11, 15], target = 9
Output: [0, 1]
// karena nums[0] + nums[1] = 2 + 7 = 9

Baca & pahami dulu

Sebelum nyentuh keyboard, aku ulang soalnya pakai kalimatku sendiri: "cari dua angka di dalam array yang kalau dijumlah hasilnya sama dengan target, terus balikin posisinya (bukan nilainya)." Kata kunci yang aku garis bawahi: indeks (bukan nilai), dua angka berbeda (nggak boleh elemen yang sama dipakai dua kali), dan tepat satu solusi (jadi begitu ketemu, langsung berhenti).

Coba brute force dulu

Cara paling jujur & paling gampang kepikiran: coba semua pasangan angka. Untuk tiap angka, bandingkan dengan semua angka setelahnya. Nggak elegan, tapi ini yang otak spontanku tawarkan duluan — dan itu wajar, brute force selalu jadi titik awal yang aman.

percobaan pertama — brute forceJS
function twoSumBrute(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) {
        return [i, j];
      }
    }
  }
  return [];
}
// dua loop bersarang → O(n²): tiap i, ngulang cek SEMUA j lagi

Sadar ada kerja berulang

Ini dijalankan, benar hasilnya, tapi ada rasa nggak enak. Aku coba jalanin di kepala dengan array yang lebih panjang: buat i = 0, aku scan ulang seluruh sisa array. Buat i = 1, aku scan ulang lagi hampir seluruh array. Tunggu — di setiap iterasi i, aku sebenarnya cuma butuh tahu satu hal: "apakah target - nums[i] sudah pernah aku lihat sebelumnya?" Tapi caranya sekarang malah nge-scan ke depan berulang-ulang, bukan mengingat apa yang sudah dilihat.

Insight: pakai struktur yang bisa "mengingat"

Kalau aku bisa mengecek "sudah pernah lihat angka ini belum" dalam O(1), aku nggak perlu loop kedua sama sekali. Struktur data yang pas untuk lookup cepat: hash map (di JS: Map atau objek biasa). Idenya dibalik: alih-alih "untuk tiap angka, cari pasangannya di depan", aku "untuk tiap angka, cek apakah pasangannya sudah ada di belakang (yang sudah aku simpan)".

solusi optimal — hash map, satu kali lewatJS
function twoSum(nums, target) {
  const seen = new Map(); // value → index yang sudah dilihat

  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) {
      return [seen.get(complement), i];
    }
    seen.set(nums[i], i);
  }
  return [];
}
// satu loop, satu kali lewat → O(n) waktu, O(n) ruang tambahan

Dry run manual — buktikan sebelum lega

Pakai contoh dari soal: nums = [2, 7, 11, 15], target = 9.

i=0 → nums[0]=2, complement = 9-2 = 7. seen masih kosong, 7 belum ada → simpan seen = {2: 0}.
i=1 → nums[1]=7, complement = 9-7 = 2. Cek seen: 2 ADA, disimpan di indeks 0 → langsung return [0, 1].

Hasilnya [0, 1] — cocok dengan output yang diharapkan. Satu kali lewat array, tanpa loop kedua.

Look back · Two Sum

Apa yang baru aja terjadi, sebenarnya?

Sebelum lanjut ke soal kedua, ada baiknya berhenti sebentar dan menamai apa yang baru saja dipelajari — ini langkah yang paling sering dilewatkan orang.

Cara paling efektif belajar problem solving bukan dengan menghafal solusi akhir yang sudah rapi, tapi dengan mengamati bagaimana orang lain bernalar dari kebingungan awal sampai ketemu jawaban — sebab solusi akhir yang sudah dipoles justru menyembunyikan jalan buntu yang paling berharga untuk dipelajari.

— diparafrasekan dari George Pólya, How to Solve It
◆ Yang bisa dipelajari

Insight-nya bukan "oh ternyata pakai hash map" — itu cuma hasilnya. Insight yang lebih berguna jangka panjang adalah caranya nemu: aku curiga ada kerja berulang saat membayangkan cara kerja brute force di kepala ("tiap i, scan ulang semua"), lalu bertanya "informasi apa yang sebenarnya aku butuh, dan bisakah aku menyimpannya alih-alih menghitung ulang?" Pertanyaan itu yang membawa ke hash map — bukan karena hafal "soal begini pasti pakai hash map".

◆ Pola yang baru dikenali

Ini contoh pola "tukar waktu dengan ruang" (time-space tradeoff): brute force hemat memori (tidak ada struktur tambahan) tapi boros waktu karena mengulang pencarian; solusi hash map memakai memori ekstra (Map) supaya setiap pencarian jadi O(1), dan waktu total turun dari O(n²) ke O(n). Setiap kali kamu ketemu loop bersarang yang isinya "cek apakah X sudah pernah muncul", pola ini layak dicurigai duluan.

Soal #2 · Longest Substring Without Repeating Characters

Naik level: soal yang naive-nya juga kerasa naive

Soal kedua ini lebih sulit — bukan cuma butuh struktur data yang tepat, tapi juga cara bergerak lewat data yang tepat. Proses berpikirnya aku ulang dari nol lagi, persis seperti soal pertama.

soal #2SOAL
// Longest Substring Without Repeating Characters
// Diberikan string `s`, cari PANJANG substring terpanjang
// yang semua karakternya unik (tidak berulang).

// Contoh:
Input:  s = "abcabcbb"
Output: 3
// jawabannya "abc", panjang 3

Input:  s = "pwwkew"
Output: 3
// jawabannya "wke", panjang 3 — perhatikan, harus SUBSTRING
// (berurutan & bersambung), bukan subsequence bebas

Baca & pahami dulu

Parafraseku: "geser sepanjang string, dan cari potongan bersambung terpanjang yang isinya semua karakter beda-beda." Kata kunci yang aku tandai: substring (harus bersambung — beda dari subsequence), dan tanpa karakter berulang. Aku juga sadar pertanyaannya minta panjang, bukan substring-nya sendiri — itu memudahkan, aku cuma perlu lacak angka, bukan string.

Coba pendekatan naive dulu

Ide paling jujur: coba semua kemungkinan substring, cek satu-satu apakah isinya unik, catat yang terpanjang. Ini analog dengan brute force di soal pertama — bukan solusi yang aku banggakan, tapi ini titik awal yang wajar untuk memastikan aku paham soalnya dengan benar.

percobaan pertama — cek semua substringJS
function lengthOfLongestSubstringNaive(s) {
  let maxLen = 0;
  for (let i = 0; i < s.length; i++) {
    for (let j = i; j < s.length; j++) {
      if (isUnique(s, i, j)) {
        maxLen = Math.max(maxLen, j - i + 1);
      }
    }
  }
  return maxLen;
}

function isUnique(s, start, end) {
  const seen = new Set();
  for (let k = start; k <= end; k++) {
    if (seen.has(s[k])) return false;
    seen.add(s[k]);
  }
  return true;
}
// dua loop untuk semua (i, j) + satu loop cek unik di dalamnya → O(n³)

Sadar ini terlalu lambat untuk constraint yang wajar

Di soal aslinya, panjang string bisa sampai puluhan ribu karakter. Kalau n = 50.000 dan kompleksitasnya O(n³), itu sekitar 125.000.000.000.000 operasi — jelas nggak akan selesai dalam waktu wajar. Ini bukan cuma "kurang elegan" seperti brute force Two Sum, ini gagal secara praktis. Constraint yang besar adalah sinyal keras: harus turun minimal ke O(n²), idealnya O(n).

Cari sumber pemborosannya

Aku perhatikan lagi: setiap kali i maju satu langkah, aku mulai ulang dari nol untuk cek keunikan window baru — padahal window [i, j] dan [i+1, j] itu tumpang tindih hampir seluruhnya, cuma beda satu karakter di ujung kiri. Aku membuang informasi yang sebenarnya masih valid.

Insight: sliding window dengan dua pointer

Alih-alih mulai ulang tiap kali, aku bisa jaga satu "jendela" [left, right] yang selalu berisi karakter unik, dan geser ujungnya saja: dorong right maju sambil menambah karakter baru, dan kalau ketemu karakter yang sudah ada di window, dorong left maju (buang karakter dari kiri) sampai duplikatnya hilang. Setiap karakter cuma masuk & keluar window maksimal satu kali — itu yang bikin ini jadi O(n), bukan O(n³).

Soal #2 lanjutan · Sliding Window

Dari insight ke kode yang benar-benar jalan

Insight-nya sudah ada. Sekarang dituangkan jadi kode, lalu dibuktikan lewat dry run — jangan percaya kode cuma karena "kelihatan benar".

solusi optimal — sliding window, dua pointerJS
function lengthOfLongestSubstring(s) {
  const seen = new Set();
  let left = 0;
  let maxLen = 0;

  for (let right = 0; right < s.length; right++) {
    while (seen.has(s[right])) {
      seen.delete(s[left]);
      left++;
    }
    seen.add(s[right]);
    maxLen = Math.max(maxLen, right - left + 1);
  }
  return maxLen;
}
// setiap karakter masuk & keluar window maksimal 1x → O(n)

Dry run manual — s = "abcabcbb"

right=0 'a': belum ada di seen → tambah, seen={a}, maxLen=1.
right=1 'b': belum ada → tambah, seen={a,b}, maxLen=2.
right=2 'c': belum ada → tambah, seen={a,b,c}, maxLen=3.
right=3 'a': sudah ada! buang s[left]='a', left=1 → seen={b,c}, 'a' sudah nggak ada, berhenti buang. Tambah 'a' → seen={b,c,a}, maxLen = 3-1+1 = 3.
right=4 'b': sudah ada! buang s[left]='b', left=2 → seen={c,a}. Tambah 'b' → maxLen = 4-2+1 = 3.
... pola ini berlanjut, dan window nggak pernah lebih panjang dari 3 lagi sampai akhir string.

Hasil akhir maxLen = 3 — cocok dengan jawaban yang diharapkan ("abc"). Dry run ini juga membuktikan while di dalam for tidak bikin ini balik jadi O(n²): left cuma pernah maju, nggak pernah mundur, jadi totalnya tetap linear.

Rangkuman visual: naive vs optimal, berdampingan.

naive — cek semua substringJS
for (i..) for (j..) {
  if (isUnique(s,i,j)) ...
}
// O(n³) — mulai ulang tiap window
optimal — sliding windowJS
for (right..) {
  while (seen.has(s[right])) { ...left++ }
  seen.add(s[right]);
}
// O(n) — window cuma bergerak maju
◆ Pola yang dikenali

Ini pola sliding window / two pointers: dipakai saat kamu mencari sesuatu di dalam rentang bersambung (substring, subarray) dan ada properti yang bisa dijaga secara bertahap saat window bergeser (di sini: "semua karakter unik"), alih-alih dihitung ulang dari nol tiap kali. Sinyalnya sering muncul dari kata "substring/subarray terpanjang/terpendek yang memenuhi X" di soal.

◆ Latihan bertingkat

Tier belajar: dari ikut alur sampai think aloud sendiri

Membaca walkthrough ini sekali saja tidak cukup. Ini kerangka bertahap supaya kebiasaan berpikirnya benar-benar menempel, bukan cuma nambah dua soal ke daftar "pernah dikerjain".

Beginner

Ikuti dulu, coba sebelum lihat jawaban

Buka lagi soal Two Sum & Longest Substring. Sebelum scroll ke bagian solusi, coba tulis brute force-mu sendiri dulu di kertas/editor. Baru cocokkan dengan proses di halaman ini — bandingkan cara berpikirnya, bukan cuma kodenya.

  • Tutup solusi, baca ulang soal saja
  • Tulis brute force versimu sendiri
  • Baru bandingkan dengan walkthrough ini
Middle

Replikasi proses di soal baru

Ambil soal yang belum pernah kamu lihat sama sekali, kasih waktu terbatas (misal 30 menit). Paksa dirimu lewat tahapan yang sama: pahami → brute force → cari redundant work → insight → optimal → dry run. Tulis catatan tiap tahap, jangan langsung loncat ke kode.

  • Pilih soal yang benar-benar baru
  • Batasi waktu, ikuti tahapan penuh
  • Catat di mana kamu "nyangkut"
Advance

Latih think aloud

Kerjakan soal sambil bicara keras (atau rekam suara/tulis narasi real-time) — verbalisasi tiap keputusan seperti gaya narasi di halaman ini. Ini keahlian terpisah dari sekadar "bisa solve"; penting banget untuk interview & kerja tim.

  • Ucapkan tiap asumsi & keputusan
  • Jelaskan kenapa buang satu ide & pilih ide lain
  • Kalau bisa, minta orang lain dengarkan/nilai
◆ Benang merah

Pola umum dari kedua walkthrough

Two Sum dan Longest Substring itu soal yang jauh berbeda topiknya, tapi kalau kamu perhatikan, urutan berpikirnya identik. Itulah yang sebenarnya mau ditransfer di halaman ini — bukan dua soal itu sendiri.

// 1

Mulai dari brute force

Jangan malu mulai dari solusi paling jujur & paling gampang kepikiran, meski lambat. Ini membuktikan kamu paham soalnya & memberi baseline yang pasti benar untuk dibandingkan nanti.

// 2

Cari kerja berulang

Bayangkan brute force jalan di kepalamu langkah demi langkah. Tanya: "informasi apa yang aku hitung ulang padahal sudah pernah aku tahu sebelumnya?"

// 3

Kenali polanya

Kerja berulang berupa "sudah pernah lihat?" biasanya mengarah ke hash map. Kerja berulang di atas rentang bersambung biasanya mengarah ke sliding window / two pointers.

// 4

Optimasi terarah

Bawa insight itu ke struktur data / teknik yang tepat, lalu tulis ulang solusinya. Optimasi yang baik selalu punya alasan jelas, bukan tebakan.

// 5

Verifikasi dengan dry run

Jangan percaya kode cuma karena "kelihatan benar". Jalankan manual dengan contoh konkret, langkah demi langkah, sampai yakin.

Konteks nyata · Kenapa "think aloud" ini penting

Ini bukan latihan akademis doang

Kebiasaan menarasikan proses berpikir seperti di halaman ini punya dua tempat nyata di mana ia benar-benar dipraktikkan — salah satunya mungkin sudah kamu duga.

Kandidat yang baik akan "berpikir keras" (think aloud) selama proses coding interview, menjelaskan tiap keputusan yang diambil — karena interviewer sebenarnya menilai bagaimana kamu bernalar, bukan cuma apakah kode akhirnya lolos test case.

Coding interview di tech company

Interviewer biasanya sudah tahu jawabannya sebelum kamu mulai. Yang mereka amati adalah bagaimana kamu sampai ke sana: apakah kamu mengklarifikasi soal dulu, apakah kamu sadar sendiri brute force-mu lambat, apakah kamu bisa menjelaskan alasan tiap keputusan. Diam sambil ngetik justru sering dinilai lebih buruk daripada narasi yang jujur meski belum sempurna.

Code review & pair programming

Di kerja nyata, kebiasaan menulis/mengucapkan alasan di balik sebuah pendekatan — lewat deskripsi PR, komentar kode, atau ngobrol saat pair programming — mempermudah rekan kerja memahami & mengevaluasi keputusanmu, bukan cuma menilai hasil akhirnya. Ini kebiasaan yang sama persis dengan yang dilatih di walkthrough ini.

◆ Intinya

Proses berpikir yang terlihat itu bisa dievaluasi & dikoreksi; proses yang tersembunyi di kepala tidak bisa. Baik di interview maupun di kerja tim, membiasakan diri menyuarakan proses adalah keterampilan yang berdiri sendiri — terpisah dari kemampuan menyelesaikan soal itu sendiri.

⚙ Praktik

Latihan lanjutan — ulangi prosesnya sendiri

Berikut beberapa soal klasik yang cocok untuk latihan tier Middle di atas. Semuanya soal terkenal yang memang ada di platform seperti LeetCode — kerjakan dengan proses yang sama: pahami, brute force, cari redundant work, insight, optimal, dry run.

// stack

Valid Parentheses

Cek apakah tanda kurung dalam string ter-pasang dengan benar. Bagus untuk latihan mengenali kapan sebuah struktur "last in, first out" (stack) cocok dipakai.

// array

Best Time to Buy and Sell Stock

Cari keuntungan maksimum dari satu kali beli-jual saham. Brute force-nya O(n²) mengecek semua pasangan hari; ada insight satu-pass yang menurunkannya ke O(n).

// array

Maximum Subarray

Cari subarray bersambung dengan jumlah terbesar. Brute force mengecek semua subarray; ada insight untuk menyelesaikannya dalam satu kali lewat (algoritma Kadane).

// hash

Contains Duplicate

Cek apakah ada elemen yang muncul lebih dari sekali di array. Latihan bagus untuk mengenali lagi pola "sudah pernah lihat?" dari soal Two Sum di halaman ini.

Penutup

Proses berpikirnya yang dibawa pulang, bukan dua soal ini

Two Sum dan Longest Substring akan kamu lupakan detailnya suatu saat. Yang seharusnya menempel adalah urutan berpikir yang membawamu ke sana — karena urutan itu yang bisa dipakai ulang di ratusan soal lain yang belum pernah kamu lihat.

  • Pahami dulu — parafrase soal pakai kalimatmu sendiri sebelum menyentuh kode.
  • Mulai dari brute force — solusi jujur & pasti benar, meski lambat, adalah baseline yang sah.
  • Cari kerja berulang — bayangkan brute force jalan langkah demi langkah, cari yang dihitung ulang.
  • Kenali pola optimasinya — hash map untuk "sudah pernah lihat?", sliding window untuk rentang bersambung.
  • Verifikasi lewat dry run — jangan percaya kode cuma karena kelihatan benar.
  • Suarakan prosesmu — baik di interview maupun code review, cara kamu bernalar dinilai, bukan cuma hasilnya.

Langkah selanjutnya

Sekarang kamu sudah lihat proses berpikir penuh dari nol sampai solve, dua kali. Langkah berikutnya: bawa kebiasaan ini ke setting yang lebih menekan waktu & observasi orang lain — yaitu interview coding sungguhan.
