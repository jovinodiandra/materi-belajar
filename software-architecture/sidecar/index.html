Sidecar Pattern

Pekerjaan pendukung (log, keamanan, retry) ditaruh di “kereta samping” yang menempel pada aplikasi — bukan di dalam kodenya.

$ Motor tetap motor. Bagasinya di kereta samping.

Tiap service menulis ulang kode log, TLS, dan retry. Bahasanya beda-beda pula.

📋

Kode pendukung di-copy ke mana-mana

Logging, metrics, TLS, retry di setiap service.

🔤

Beda bahasa, beda library

Service Java, Go, Node. Tiga versi kode yang sama.

🐞

Update keamanan = ubah semua service

Satu perbaikan, puluhan deploy.

Kereta samping

pekerjaan pendukung di proses terpisah

◆ Buat apa ini? Kenapa pakai ini?

Given — banyak service butuh pekerjaan pendukung yang sama: log, TLS, retry.

When — setiap service menulis sendiri di dalam kodenya, dengan bahasa masing-masing.

Then — kode dobel di mana-mana dan update kecil butuh deploy semua service.

→ makanya kita pakai Sidecar — supaya pekerjaan pendukung ditulis sekali dan dipasang di samping tiap service.

bagian 2 · contoh nyata

Contoh: Pod dengan sidecar

apiVersion: v1
kind: Pod
spec:
  containers:
    - name: order-app          # aplikasi kita
      image: order-service:1.4
    - name: log-shipper        # sidecar
      image: fluent-bit:3.0
      volumeMounts:
        - name: logs
          mountPath: /var/log/app

Gampangnya

  • Aplikasi cukup menulis log ke file.
  • Sidecar membaca file itu lalu mengirim ke sistem log.
  • Ganti sistem log? Ganti sidecar. Aplikasi tidak disentuh.
Ganti sistem log? Cukup ganti sidecar-nya.

Sidecar yang sering kamu temui

SidecarTugasnya
Envoy / Istio proxyTLS antar service, retry, timeout, circuit breaker
Fluent BitMengirim log ke sistem log pusat
Vault agentMengambil dan memperbarui secret (password, token)
DaprPub/sub, state, dan panggilan service lewat API seragam
Sidecar proxy di semua service = service mesh (mis. Istio).
