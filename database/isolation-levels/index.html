// Database — saat dua transaksi menyentuh data yang sama, bersamaan

Isolation level: pagar tak kasat mata antar transaksi.

Di dunia nyata, database tidak pernah cuma dipakai satu orang. Ratusan transaksi berjalan bersamaan, saling baca & tulis data yang sama. Tanpa aturan main, hasilnya bisa kacau: saldo salah, baris ke-overwrite, keputusan diambil berdasarkan data yang sudah basi. Isolation level adalah kontrak yang menentukan seberapa "terisolasi" satu transaksi dari transaksi lain — dari yang paling longgar (Read Uncommitted) sampai yang paling ketat (Serializable). Deck ini bahas keempatnya, race condition yang mengintai, sampai kapan kamu harus naik level di production.

Sakit
Concurrency tanpa aturan — dua transaksi rebutan baris yang sama
L0
Read Uncommitted — boleh baca data yang belum di-commit
L1
Read Committed — cuma baca data yang sudah final
L2
Snapshot Isolation (MVCC) — tiap transaksi lihat "foto" data yang konsisten
L3
Serializable — seolah semua transaksi jalan satu-satu, bergiliran

◆ Buat apa ini? Kenapa pakai ini?

Given — sebuah tabel stok atau saldo diakses banyak transaksi sekaligus, dan tim tidak menetapkan isolation level secara sadar (jadi jalan di default engine-nya).

When — dua transaksi membaca baris yang sama nyaris bersamaan (mis. dua checkout menarik stok terakhir, atau dua penarikan ATM dari saldo yang sama), lalu masing-masing menulis ulang berdasarkan angka yang sudah basi saat dibaca.

Then — terjadi lost update, dirty read, atau phantom read: stok bisa minus, satu penarikan hilang dari catatan, laporan finansial tidak konsisten — dan bug ini nyaris mustahil direproduksi di testing karena cuma muncul saat load tinggi.

→ makanya kita pakai Isolation Levels.

Akar masalah · Concurrency itu default, bukan pengecualian

Dua transaksi, satu saldo, satu waktu

Bayangkan saldomu Rp1.000.000. Kamu tarik Rp200.000 dari ATM di satu sisi kota. Bersamaan, pasanganmu yang pegang kartu tambahan tarik Rp300.000 dari ATM lain. Kalau database tidak punya aturan isolasi yang benar, kedua transaksi bisa sama-sama membaca saldo awal Rp1.000.000, lalu sama-sama menulis hasil kurangnya sendiri-sendiri — dan salah satu penarikan hilang dari catatan.

◆ Analogi — dua orang, satu ATM, satu saldo

Ini seperti dua orang membaca angka di buku tabungan yang sama di waktu yang sama: "Oh, saldonya 1 juta". Masing-masing menghitung sendiri saldo baru di kepala, lalu menulis ulang buku itu. Yang tertulis terakhir menimpa tulisan yang pertama — padahal keduanya berhak dicatat. Inilah race condition: hasil akhirnya bergantung pada timing, bukan pada logika bisnis yang benar.

Masalah ini bukan teori belaka — ini terjadi tiap detik di sistem yang punya banyak pengguna bersamaan: e-commerce saat flash sale, sistem booking kursi, atau aplikasi perbankan. Isolation level adalah cara database menjanjikan seberapa jauh transaksi-transaksi ini dilindungi satu sama lain — dan tiap level punya harga performanya sendiri.

Konsep inti · Empat tingkat isolasi

Dari yang paling longgar sampai paling ketat

Standar SQL mendefinisikan empat level isolasi. Makin ketat levelnya, makin sedikit race condition yang mungkin terjadi — tapi makin mahal juga secara performa & concurrency.

Database jarang benar-benar serializable secara default, karena biayanya mahal terhadap performa. Sebagian besar justru menawarkan level isolasi yang lebih lemah — yang melindungi dari sebagian masalah concurrency, tapi tidak semuanya. Karena itu, aplikasi yang memakainya harus paham betul race condition apa saja yang masih bisa lolos di level yang dipilih.

— diparafrasekan dari Martin Kleppmann, Designing Data-Intensive Applications, Bab 7 ("Weak Isolation Levels")
◆ Empat level isolasi (standar SQL)
L0Read Uncommitted → boleh baca data yang belum di-commit transaksi lain
L1Read Committed → hanya baca data yang sudah di-commit (default banyak DB)
L2Snapshot Isolation (MVCC) → baca "foto" data yang konsisten sepanjang transaksi
L3Serializable → hasil akhir seolah semua transaksi jalan satu per satu

Catatan: PostgreSQL tidak benar-benar mengimplementasikan READ UNCOMMITTED — kalau kamu minta level itu, ia otomatis diperlakukan sebagai Read Committed. MySQL/InnoDB adalah salah satu yang benar-benar mendukung keempatnya.

contoh — mengatur isolation level per transaksiSQL
-- pola umum di PostgreSQL / MySQL / SQL Server
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT saldo FROM akun WHERE id = 1;
UPDATE akun SET saldo = saldo - 200000 WHERE id = 1;

COMMIT;

-- level lain yang bisa dipilih:
-- SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
-- SET TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- default PostgreSQL
-- SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- = Snapshot Isolation di Postgres

Di PostgreSQL, level REPEATABLE READ pada dasarnya adalah implementasi Snapshot Isolation berbasis MVCC (Multi-Version Concurrency Control): tiap transaksi melihat "foto" database persis seperti saat transaksi itu dimulai, tidak peduli transaksi lain menulis apa setelahnya — sampai transaksi ini sendiri yang commit.

Inti masalah · Race condition yang mengintai

Dirty read, lost update, write skew

Tiap level isolasi menutup sebagian race condition, tapi tidak semuanya. Tiga yang paling penting untuk kamu kenali: dirty read, lost update, dan yang paling licik — write skew.

Dirty read terjadi di Read Uncommitted: transaksi A membaca data yang ditulis transaksi B, padahal B belum commit. Kalau B akhirnya ROLLBACK, A sudah terlanjur bekerja dengan data yang ternyata tidak pernah benar-benar terjadi.

lost update — dua transaksi timpa-menimpaSQL
-- Transaksi A                  -- Transaksi B
BEGIN;                          BEGIN;
SELECT stok FROM produk
  WHERE id=1; -- 10       SELECT stok FROM produk
                                WHERE id=1; -- 10
-- hitung di app: 10-1=9       -- hitung di app: 10-1=9
UPDATE produk SET stok=9
  WHERE id=1;
COMMIT;                         UPDATE produk SET stok=9
                                  WHERE id=1;
-- B menimpa hasil A, padahal   COMMIT;
-- 2 pembeli checkout, stok
-- akhir cuma turun 1, bukan 2
fix — kunci baris atau update atomikSQL
-- opsi 1: SELECT ... FOR UPDATE (kunci baris)
BEGIN;
SELECT stok FROM produk
  WHERE id=1 FOR UPDATE; -- B nunggu
UPDATE produk SET stok = stok - 1
  WHERE id=1;
COMMIT;

-- opsi 2: update atomik, tanpa read-modify-write
UPDATE produk
SET stok = stok - 1
WHERE id = 1 AND stok > 0;
-- database sendiri yang jamin urutan tulis
◆ Write skew — yang lolos bahkan di Snapshot Isolation

Contoh klasik: sebuah rumah sakit mewajibkan minimal 1 dokter jaga. Ada 2 dokter jaga, keduanya merasa capek dan sama-sama cek dulu "apakah masih ada dokter lain jaga?" — jawabannya sama-sama "ya, masih ada 2". Keduanya lalu sama-sama mengajukan cuti dari transaksi terpisah. Karena masing-masing hanya menulis ke baris miliknya sendiri (bukan baris yang sama), Snapshot Isolation tidak mendeteksi konflik apa pun — padahal hasil akhirnya melanggar aturan: 0 dokter jaga.

Write skew adalah race condition yang tetap bisa lolos bahkan di Snapshot Isolation. Polanya: dua transaksi membaca objek yang sama, lalu memperbarui objek yang berbeda berdasarkan apa yang mereka baca — dan karena keduanya menulis ke baris berlainan, mekanisme deteksi konflik berbasis baris tidak pernah tersentuh, padahal asumsi yang dipakai kedua transaksi itu sudah sama-sama usang.

— diparafrasekan dari konsep "write skew", Martin Kleppmann, Designing Data-Intensive Applications, Bab 7

Cuma Serializable (atau varian modern seperti Serializable Snapshot Isolation) yang benar-benar menutup celah write skew — karena ia menjamin hasil akhirnya seolah-olah semua transaksi berjalan satu per satu, bergiliran, tak peduli baris mana yang disentuh.

◆ Praktik · Cara aman pakai isolation level

Best practice yang layak kamu ingat

Kamu tidak perlu hafal teori concurrency control untuk aman di production. Pegang enam kebiasaan ini.

  • Percayai default-nya dulu. PostgreSQL & kebanyakan database relasional memakai Read Committed sebagai default — cukup aman untuk mayoritas kasus CRUD biasa.
  • Naik ke Serializable hanya untuk transaksi kritis — transfer saldo, booking kursi/tiket, alokasi stok terbatas — di mana konsistensi lebih penting dari sekadar throughput.
  • Pakai SELECT ... FOR UPDATE saat kamu tahu persis baris mana yang mau dikunci, tanpa perlu menaikkan isolation level seluruh transaksi.
  • Lebih suka update atomik (UPDATE ... SET x = x - 1 WHERE ...) daripada pola read-modify-write di level aplikasi — biarkan database yang menjamin urutan.
  • Tangani serialization failure. Transaksi Serializable bisa gagal & perlu di-retry — pastikan kode kamu siap mengulang transaksi yang di-abort database.
  • Uji dengan beban konkuren sungguhan, bukan cuma satu transaksi di satu waktu — race condition baru kelihatan saat dua request benar-benar tabrakan.
🎓 Tier belajar · Sesuaikan dengan levelmu

Belajar isolation level bertahap

Topik ini gampang terasa berat kalau langsung loncat ke teori formal. Ikuti tiga tahap ini sesuai levelmu sekarang.

🌱 Beginner

Paham 4 level dasar

Fokus dulu ke apa yang dijanjikan tiap level, bukan cara implementasinya di dalam mesin database.

  • Hafal urutan: Read Uncommitted → Read Committed → Snapshot Isolation → Serializable.
  • Paham bahwa makin ketat = makin aman, tapi makin lambat.
  • Coba jalankan SET TRANSACTION ISOLATION LEVEL di database lokalmu.
  • Kenali istilah "dirty read" secara konsep, tanpa perlu bikin contoh sendiri dulu.
⚙ Middle

Cegah race condition di kode

Mulai kenali pola berbahaya di kode aplikasi sehari-hari, dan tahu cara memperbaikinya.

  • Kenali pola read-modify-write yang rawan lost update di codebase-mu.
  • Biasa pakai SELECT ... FOR UPDATE atau update atomik.
  • Bisa menjelaskan lost update ke rekan tim dengan contoh nyata.
  • Paham kenapa transaksi butuh logika retry saat kena serialization failure.
🚀 Advance

Serializable & sistem terdistribusi

Masuk ke detail implementasi & kasus-kasus yang cuma muncul di skala besar.

  • Paham cara kerja Serializable Snapshot Isolation (SSI) mendeteksi konflik.
  • Bisa mengidentifikasi write skew dari gejalanya, bukan cuma dari definisi buku.
  • Paham trade-off isolasi ketat di database terdistribusi (mis. Spanner, CockroachDB).
  • Bisa merancang uji concurrency (mis. dengan Jepsen) untuk memverifikasi klaim isolasi.
◆ Harga · Tidak ada isolasi gratis

Trade-off: isolasi ketat vs performa

Isolation level bukan cuma soal "aman atau tidak" — ia soal berapa banyak concurrency yang kamu korbankan untuk mendapatkan jaminan itu.

// Isolasi ketat (Serializable)

  • Menutup hampir semua race condition, termasuk write skew.
  • Logika bisnis kamu jadi lebih sederhana — tidak perlu mikirin edge case concurrency.
  • Cocok untuk data yang tidak boleh salah: saldo, kursi, kuota.

// Harganya

  • Throughput turun — transaksi lebih sering saling menunggu / di-abort.
  • Butuh logika retry di aplikasi untuk serialization failure.
  • Di skala terdistribusi, biayanya makin mahal (koordinasi antar node).
  • Overkill untuk operasi baca yang toleran terhadap data sedikit basi.
◆ Kenapa Read Committed tetap jadi default di mana-mana

Sebagian besar query di aplikasi tipikal — tampilkan profil, tampilkan daftar produk, tampilkan riwayat — tidak butuh jaminan seketat Serializable. Menjalankan semuanya di Serializable cuma akan menambah abort rate tanpa manfaat nyata. Pilih level isolasi per kebutuhan transaksi, bukan satu level untuk semuanya.

◆ Keputusan · Pilih level yang pas

Kapan naik level, kapan cukup default

Aturan praktisnya: mulai dari Read Committed, naik ke Serializable (atau kunci eksplisit) hanya untuk transaksi yang benar-benar rawan race condition.

// Naik ke Serializable / kunci eksplisit saat…

  • Transaksi finansial: transfer, pembayaran, refund.
  • Alokasi sumber daya terbatas: kursi, tiket, kuota stok.
  • Ada aturan invarian lintas-baris (mis. "minimal 1 dokter jaga").
  • Konsekuensi race condition mahal secara bisnis / hukum.

// Cukup Read Committed (default) saat…

  • Query baca biasa: dashboard, listing, laporan non-kritis.
  • Update yang idempotent & tidak bergantung pada nilai lama.
  • Aplikasi CRUD standar tanpa aturan lintas-baris yang ketat.
  • Throughput tinggi lebih penting daripada konsistensi mutlak.
◆ Pertanyaan penentu

Tanyakan: "Kalau dua transaksi ini tabrakan tepat di detik yang sama, apakah hasilnya bisa merugikan orang atau melanggar aturan bisnis?" Kalau ya — naikkan level isolasi atau kunci barisnya secara eksplisit. Kalau tidak — default sudah cukup, jangan bayar mahal untuk risiko yang tidak ada.

Studi kasus · Di dunia nyata

Bagaimana tim production memilih isolation level

Beberapa pola nyata yang sering ditemui di industri — perhatikan bahwa keputusan level isolasi selalu mengikuti seberapa mahal konsekuensi race condition-nya, bukan sekadar ikut default.

// mayoritas startup

Default Read Committed di PostgreSQL

Pola: kebanyakan aplikasi web/startup tidak pernah mengubah isolation level sama sekali, tetap di default Read Committed PostgreSQL. Kenapa cukup: mayoritas operasinya bukan operasi finansial rawan-konflik, dan Read Committed sudah menutup dirty read.

// fintech / perbankan

Naik ke Serializable untuk transaksi kritis

Pola: sistem perbankan & fintech biasanya menaikkan isolation level (atau memakai kunci eksplisit) khusus untuk alur transfer dana & rekonsiliasi saldo. Kenapa: lost update atau write skew di jalur ini berarti uang salah hitung — konsekuensinya langsung finansial & legal.

// e-commerce skala besar

Row locking untuk cegah overselling

Pola: platform e-commerce besar seperti Shopify dikenal memakai kunci baris/antrean eksplisit di jalur checkout & pengurangan stok saat flash sale, bukan mengandalkan isolation level default begitu saja. Kenapa: race condition di stok berarti barang terjual melebihi stok yang ada (oversell).

// platform developer

Row locking di alur kritis GitHub

Pola: sistem skala besar seperti GitHub menangani operasi yang rawan konflik (mis. penomoran issue/PR, antrean job) dengan kombinasi transaksi & kunci baris eksplisit di titik-titik kritis. Kenapa: di titik-titik itu, urutan & keunikan data jauh lebih penting daripada throughput maksimal.

◆ Benang merahnya

Tidak ada satu level isolasi yang dipakai untuk semua query di satu sistem. Tim production biasanya memakai default yang longgar untuk mayoritas trafik, lalu menaikkan isolasi atau mengunci baris secara eksplisit hanya di jalur-jalur sempit yang benar-benar rawan & mahal kalau salah.

⚙ Ekosistem · Alat yang dipakai

Tools & mesin database seputar isolation level

Kamu tidak perlu membangun MVCC sendiri — pahami saja bagaimana mesin database populer mengimplementasikannya, dan alat yang bisa menguji klaim konsistensinya.

// paling umum

PostgreSQL — MVCC

Default Read Committed, dan REPEATABLE READ-nya sebenarnya adalah Snapshot Isolation berbasis MVCC. Punya SERIALIZABLE asli lewat teknik Serializable Snapshot Isolation (SSI).

// paling banyak dipakai web

MySQL / InnoDB

Mendukung keempat level standar SQL secara harfiah, termasuk READ UNCOMMITTED. Default-nya REPEATABLE READ, sedikit berbeda perilaku dari Snapshot Isolation murni.

// uji konsistensi

Jepsen

Framework pengujian yang dipakai untuk memverifikasi klaim konsistensi & isolasi database terdistribusi dengan menyuntikkan kegagalan jaringan & concurrency ekstrem — sering dipakai untuk membongkar klaim "serializable" yang ternyata bocor.

// terdistribusi

CockroachDB / Google Spanner

Database terdistribusi yang menawarkan Serializable sebagai default-nya, dengan trade-off latensi lebih tinggi karena butuh koordinasi antar node/region.

// ORM & app layer

Dukungan isolation level di ORM

Kebanyakan ORM (Sequelize, TypeORM, Hibernate, Django ORM) menyediakan opsi untuk mengatur isolation level per transaksi atau memakai SELECT ... FOR UPDATE tanpa raw SQL.

// observability

pg_stat_activity / lock monitoring

Tool bawaan seperti pg_stat_activity & pg_locks di PostgreSQL membantu mendiagnosis transaksi yang saling menunggu (lock contention) di production.

◆ Tips pemula

Kalau kamu memakai PostgreSQL, kamu sudah otomatis dapat perlindungan dirty read secara gratis (default Read Committed). Langkah belajar berikutnya yang paling berguna: kenali kapan kamu butuh SELECT ... FOR UPDATE, sebelum buru-buru loncat ke SERIALIZABLE di semua tempat.

Penutup

Isolasi itu kontrak, bukan jaminan otomatis

Isolation level adalah janji yang dibuat database — tapi kamu tetap harus tahu apa yang tidak dijanjikannya di level yang kamu pakai. Paham race condition di baliknya membuatmu bisa memilih level yang pas, bukan sekadar ikut default atau membabi buta naik ke Serializable.

  • Empat level — Read Uncommitted, Read Committed, Snapshot Isolation, Serializable.
  • Dirty read — baca data yang belum commit, cukup ditutup Read Committed.
  • Lost update — dua transaksi timpa-menimpa, butuh kunci atau update atomik.
  • Write skew — race condition licik yang lolos bahkan di Snapshot Isolation.
  • Pilih per kebutuhan — default longgar untuk mayoritas, ketat untuk yang kritis.
  • Uji, jangan cuma asumsi — concurrency nyata baru kelihatan di bawah beban tabrakan.

Aturan emasnya

Tanya untuk tiap transaksi kritis: "Kalau ini tabrakan dengan transaksi lain tepat di detik yang sama, apa yang bisa salah?" Kalau jawabannya membuatmu gelisah, naikkan isolasi atau kunci barisnya secara eksplisit. Kalau tidak, biarkan default bekerja — isolasi ketat itu alat, bukan kewajiban di mana-mana.
