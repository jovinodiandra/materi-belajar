// Database — satu mesin, banyak wajah

Satu database yang bisa bicara banyak bahasa data.

Aplikasi modern jarang cuma butuh satu bentuk data. Kamu butuh dokumen untuk katalog produk, graph untuk relasi & rekomendasi, dan key-value untuk cache session — kadang ketiganya dalam fitur yang sama. Database multi-model seperti ArangoDB, Azure Cosmos DB, dan PostgreSQL (dengan ekstensinya) mencoba menjawab ini: satu mesin, banyak cara mengakses data, tanpa harus memelihara sekumpulan database berbeda sekaligus. Deck ini buat pemula: dari kenapa ia lahir, konsep intinya, trade-off-nya, sampai kapan harus dipakai di production.

Sakit
Polyglot persistence — tiap kebutuhan data pakai database berbeda
Beban
Ops menumpuk — tiap DB butuh deploy, backup, monitoring sendiri
Ide
Satu mesin, banyak API — document, graph, key-value dalam satu engine
Untung
Operasional lebih sederhana — satu sistem untuk dijaga & diskalakan
Batas
Tak sekuat spesialis — generalist, bukan pemenang di tiap model

◆ Kenapa pakai ini?

Given — tim sudah punya MongoDB untuk katalog produk, Neo4j untuk graph rekomendasi pertemanan, dan Redis untuk session login — tiga database terpisah, tiga cara deploy, tiga backup policy, tiga skillset yang harus dikuasai on-call.

When — muncul fitur baru yang butuh ketiganya sekaligus, misalnya "rekomendasi produk berbasis riwayat belanja dan relasi pertemanan user", dan data yang sama (profil user, produk) harus tetap konsisten di ketiga sistem itu.

Then — tanpa satu mesin yang bisa jadi ketiganya, tim terjebak menulis job sinkronisasi antar-database yang rawan stale data & race condition, plus ongkos operasional naik tiap kali ada database baru masuk stack.

→ makanya kita pakai Multi-Model Database.

Akar masalah · Polyglot persistence

Satu aplikasi, banyak bentuk data, banyak database

Aplikasi e-commerce yang sehat biasanya butuh lebih dari satu model data sekaligus: katalog produk yang bentuknya fleksibel (cocok jadi document), rekomendasi "orang yang beli ini juga beli itu" (cocok jadi graph), dan session login yang harus dibaca super cepat (cocok jadi key-value). Solusi lama: pasang satu database khusus untuk tiap kebutuhan itu.

◆ Analogi — dapur dengan lima alat masak berbeda

Bayangkan satu dapur yang harus punya rice cooker khusus nasi, air fryer khusus gorengan, slow cooker khusus sup — masing-masing bagus di tugasnya, tapi kamu jadi sibuk mengurus lima alat: lima kali dibersihkan, lima manual berbeda, lima kali dicek kalau rusak. Itulah polyglot persistence — istilah untuk memakai beberapa jenis database berbeda dalam satu sistem, satu per kebutuhan.

Aplikasi modern sering paling baik dilayani dengan memakai beberapa jenis database berbeda untuk kebutuhan berbeda dalam satu sistem yang sama — alih-alih memaksakan satu jenis database untuk segalanya.

— parafrase dari Pramod Sadalage & Martin Fowler, NoSQL Distilled (Addison-Wesley)

Masalahnya bukan di ide polyglot persistence itu sendiri — memang benar tiap model data punya kekuatan berbeda. Masalahnya ada di ongkos operasionalnya: makin banyak jenis database berjalan, makin banyak yang harus dipelajari tim, di-deploy, di-backup, dipantau, dan disinkronkan satu sama lain saat data yang sama perlu muncul di lebih dari satu tempat.

Konsep inti · Satu representasi, banyak API

Bagaimana satu mesin bisa "jadi" banyak database

Trik utamanya: data disimpan secara internal dengan representasi yang sama (biasanya berbasis dokumen), lalu mesin database menyediakan beberapa API berbeda di atasnya — API document untuk baca/tulis dokumen biasa, API graph untuk menelusuri relasi antar dokumen (dianggap sebagai vertex & edge), dan akses cepat by-key yang berperilaku seperti key-value.

◆ Satu storage engine, tiga cara akses (contoh ArangoDB)
Document→ collection biasa, query pakai AQL/filter field
Graph→ edge collection: dokumen berisi _from & _to
Key-Value→ ambil dokumen langsung lewat _key, tanpa query

Grafik bukan struktur data terpisah dari dokumen — edge cuma dokumen biasa yang punya dua field penunjuk (_from, _to). Karena representasinya sama, satu query bisa mencampur filter dokumen dengan penelusuran graph.

contoh — filter document + traversal graph, dalam satu queryAQL
// cari user di Jakarta, lalu telusuri graph pertemanan 2 lompatan
FOR u IN users
  FILTER u.city == "Jakarta"
  LET teman = (
    FOR v, e IN 1..2 OUTBOUND u GRAPH "social_graph"
      RETURN v.name
  )
  RETURN { user: u.name, teman: teman }

Perhatikan: FILTER u.city == "Jakarta" adalah query document biasa, sedangkan OUTBOUND u GRAPH "social_graph" adalah traversal graph — keduanya jalan dalam satu query, di satu mesin, tanpa perlu memindahkan data ke database lain untuk "bagian graph"-nya.

◆ Perbandingan · Arsitektur

Polyglot persistence vs multi-model

Keduanya mengakui hal yang sama — satu model data tidak cukup — tapi menjawabnya dengan cara berbeda: polyglot menjawab dengan banyak mesin, multi-model menjawab dengan satu mesin, banyak API.

polyglot persistence — 4 database terpisahSTACK
# Katalog produk
MongoDB       → document store

# Rekomendasi & relasi user
Neo4j         → graph store

# Session & cache
Redis         → key-value store

# Transaksi & laporan
PostgreSQL    → relational store

## 4 mesin, 4 cara deploy & backup, sinkronisasi manual
multi-model — 1 mesin, banyak APISTACK
ArangoDB      → satu cluster

document API    → katalog produk
graph API       → rekomendasi & relasi user
akses by-key    → session & cache ringan

## 1 mesin, 1 cara deploy & backup, konsisten secara internal

Tidak ada satu model data yang menang untuk segala kebutuhan — wajar jika sistem database berevolusi untuk menawarkan lebih dari satu model data sekaligus, demi mengurangi kebutuhan mengoperasikan banyak sistem terpisah.

— parafrase dari Martin Kleppmann, Designing Data-Intensive Applications, penutup Bab 2
◆
Multi-model bukan pengganti mutlak polyglot persistence. Kalau salah satu kebutuhanmu ekstrem — misalnya butuh graph database yang dioptimalkan habis-habisan untuk traversal jutaan hop, atau key-value store dengan latensi sub-milidetik brutal — spesialis terpisah biasanya masih menang. Multi-model paling masuk akal saat kebutuhanmu cukup beragam tapi tidak ekstrem di tiap model.
◆ Praktik · Cara pakai yang sehat

Best practice memakai multi-model database

Godaan terbesar multi-model adalah "karena bisa, ya dipakai semua modelnya". Ini jebakan. Berikut beberapa hal yang perlu kamu pegang.

  1. Jangan pakai semua model sekaligus tanpa alasan. Hanya karena mesinnya mendukung document, graph, dan key-value, bukan berarti fitur kamu harus memakai ketiganya. Pakai yang benar-benar dibutuhkan pola akses datamu.
  2. Evaluasi dulu: benar-benar butuh multi-model, atau cukup satu model + ekstensi? Kalau kamu sudah pakai PostgreSQL dan cuma butuh sedikit fleksibilitas dokumen, kolom JSONB mungkin sudah cukup — tak perlu database baru.
  3. Rancang skema per-model dengan sadar. Bentuk dokumen untuk API document dan bentuk edge untuk API graph sebaiknya dirancang terpisah, bukan asal dipetakan 1:1 — traversal graph yang efisien butuh struktur edge yang ramping.
  4. Ukur, jangan asumsikan, performa tiap model. Query graph di mesin multi-model bisa jadi tidak secepat graph database khusus untuk traversal dalam. Benchmark pola akses kritismu sebelum production.
  5. Batasi jumlah tim/fitur yang "menyentuh" tiap model. Kalau semua orang bebas memakai API apa saja di collection yang sama, konsistensi skema gampang berantakan — tetap perlu konvensi & dokumentasi.
  6. Siapkan jalur keluar. Kalau suatu hari satu model tumbuh jadi kebutuhan dominan & ekstrem, rencanakan bagaimana memisahkannya ke database spesialis tanpa menulis ulang seluruh aplikasi.
🎓 Tier belajar · Jenjang paham

Sejauh mana kamu perlu memahami multi-model?

Tidak semua orang perlu menguasai topik ini sampai level yang sama. Berikut tiga jenjang, dari sekadar tahu sampai bisa merancang & migrasi.

🌱 Beginner

Paham kenapa multi-model ada

Cukup mengerti masalah yang dijawabnya & bisa menyebut contohnya saat diskusi arsitektur.

  • Tahu istilah polyglot persistence & kenapa ia mahal secara ops.
  • Tahu bahwa satu mesin bisa punya lebih dari satu API data.
  • Kenal minimal satu contoh: ArangoDB, Cosmos DB, atau Postgres+JSONB.
⚙ Middle

Memilih kapan 1 mesin cukup

Bisa menimbang: pakai fitur multi-model dari database yang sudah ada, atau tambah database spesialis baru?

  • Bisa membandingkan JSONB/PostGIS/pgvector vs pasang MongoDB/Neo4j terpisah.
  • Paham kapan kebutuhan sudah "ekstrem" hingga butuh spesialis.
  • Bisa mengukur trade-off ops vs performa untuk tim kecil-menengah.
🚀 Advance

Desain skema lintas-model & migrasi

Bisa merancang skema yang konsisten lintas API, dan memimpin migrasi arsitektur data.

  • Merancang struktur document & edge yang selaras untuk graph traversal efisien.
  • Memimpin migrasi dari polyglot ke multi-model, atau sebaliknya, tanpa downtime besar.
  • Menentukan strategi sharding/replikasi lintas model pada skala production.
◆ Harga · Tidak ada makan siang gratis

Trade-off: sederhana secara ops, tapi generalist

Multi-model menukar sesuatu yang nyata: kamu dapat kesederhanaan operasional, tapi biasanya melepas sedikit kekuatan puncak yang dimiliki database spesialis di tiap model.

// Yang kamu dapat

  • Satu sistem untuk di-deploy, di-backup, dipantau.
  • Query bisa menggabungkan model (mis. filter document + traversal graph).
  • Tidak perlu sinkronisasi manual data antar database berbeda.
  • Tim cukup belajar satu ekosistem, bukan banyak.

// Yang kamu korbankan

  • Query graph biasanya kalah cepat dari graph database khusus.
  • Fitur key-value-nya sering lebih sederhana dari Redis/DynamoDB murni.
  • Tuning satu mesin untuk banyak beban kerja sekaligus lebih rumit.
  • Vendor lock-in bisa lebih dalam kalau API multi-model-nya proprietary.
◆ Catatan jujur

"Multi-model" bukan berarti "sama kuatnya di semua model". Ia lebih tepat disebut generalist yang cukup baik di banyak hal — sangat berguna kalau kebutuhanmu memang beragam tapi tidak ekstrem di satu sisi tertentu.

◆ Keputusan · Pakai atau jangan

Kapan pakai multi-model, kapan tidak

Aturan praktisnya: kalau kebutuhan data kamu beragam tapi masih moderat, satu mesin multi-model bisa menyederhanakan hidupmu. Kalau salah satu kebutuhan ekstrem, spesialis terpisah lebih aman.

// Pakai multi-model saat…

  • Butuh 2-3 model data tapi masing-masing skala moderat.
  • Tim kecil, ingin minimalkan jumlah sistem yang dijaga.
  • Query lintas-model (document + graph) sering muncul.
  • Sudah pakai Postgres & ekstensinya (JSONB/PostGIS/pgvector) cukup menjawab kebutuhan.

// Jangan, pilih spesialis saat…

  • Traversal graph super dalam & frekuensi tinggi (butuh graph DB murni).
  • Latensi key-value harus sub-milidetik konsisten (butuh Redis dsb).
  • Volume salah satu model jauh lebih besar dari yang lain.
  • Butuh fitur khusus vendor spesialis (mis. full-text search canggih).
◆ Pertanyaan penentu

Tanyakan: "Apakah ada satu model data yang bebannya jauh lebih besar & kritis dibanding yang lain?" Kalau ya → pertimbangkan spesialis untuk model itu. Kalau kebutuhanmu relatif seimbang & tidak ekstrem → multi-model layak dicoba lebih dulu.

Studi kasus · Di dunia nyata

Siapa yang benar-benar memakai multi-model

Beberapa contoh nyata bagaimana tim memilih pendekatan multi-model — perhatikan alasannya: distribusi global, atau ingin menambah kemampuan tanpa mengganti database yang sudah ada.

// global scale

Azure Cosmos DB di Microsoft

Kasus: berbagai layanan internal Microsoft memakai Cosmos DB, termasuk kebutuhan awal yang mendorong pengembangannya untuk layanan seperti Skype. Kenapa multi-model: butuh distribusi global dengan latensi rendah, sambil tetap bisa diakses lewat beberapa API data (document, graph, key-value) sesuai kebutuhan tim yang berbeda-beda.

// praktis, tanpa migrasi

PostgreSQL + ekstensi

Kasus: tim yang sudah punya PostgreSQL sebagai database utama, lalu butuh menyimpan data semi-terstruktur, data spasial, atau embedding vector untuk fitur AI. Kenapa multi-model: JSONB untuk document, PostGIS untuk spatial, pgvector untuk vector — semua tanpa mengganti database utama.

// startup, graph + document

ArangoDB di startup

Kasus: startup yang produknya butuh graph (rekomendasi, jaringan relasi) sekaligus document (profil, konten) tapi belum punya sumber daya untuk mengoperasikan dua database spesialis terpisah. Kenapa multi-model: satu mesin cukup untuk kedua kebutuhan di tahap awal, mengurangi beban ops tim kecil.

// fitur AI tanpa DB baru

Tambah pgvector, bukan vector DB baru

Kasus: tim yang ingin menambah fitur pencarian semantik/RAG pada aplikasi yang sudah berjalan di atas Postgres. Kenapa multi-model: menambah ekstensi pgvector ke database yang sudah ada jauh lebih murah secara ops dibanding mengoperasikan vector database terpisah.

◆ Benang merahnya

Di semua kasus di atas, alasan memilih multi-model bukan "karena ikut tren", tapi karena mengurangi jumlah sistem yang harus dioperasikan — baik demi skala global (Cosmos DB), baik demi memanfaatkan database yang sudah dipercaya tim (Postgres), maupun demi menghemat sumber daya tim kecil (ArangoDB di startup).

⚙ Ekosistem · Alat yang dipakai

Tools multi-model database

Cukup kenali nama populernya & kapan kira-kira dipakai. Sebagai pemula, mulai dari PostgreSQL (kalau sudah pakai relasional) atau ArangoDB (kalau mulai dari nol & butuh document+graph).

// document + graph native

ArangoDB

Open-source, dirancang dari awal untuk multi-model: document, graph, dan akses key-value dalam satu mesin, satu bahasa query (AQL).

// cloud, global scale

Azure Cosmos DB

Layanan terkelola dari Microsoft. Satu database, banyak API kompatibel (SQL/document, MongoDB, Cassandra, Gremlin/graph, table/key-value), dengan distribusi global bawaan.

// relasional + ekstensi

PostgreSQL (dengan ekstensi)

Relasional yang jadi "multi-model praktis" lewat ekstensi: JSONB untuk document, PostGIS untuk data spasial, pgvector untuk vector/AI — tanpa ganti database.

// multi-model + multi-mesin

OrientDB

Open-source, menggabungkan document & graph dengan dukungan objek & sedikit rasa key-value. Salah satu pionir kategori multi-model sebelum ArangoDB populer.

◆ Tips pemula

Kalau tim kamu sudah pakai PostgreSQL, coba dulu ekstensinya sebelum menambah database baru — JSONB/PostGIS/pgvector sering sudah cukup. Kalau memang mulai dari nol & kebutuhan document+graph jelas sejak awal, ArangoDB atau Cosmos DB layak dicoba.

Penutup

Satu mesin, dipilih karena kebutuhan — bukan karena tren

Multi-model database lahir dari kejujuran bahwa satu model data jarang cukup untuk aplikasi modern — tapi memelihara banyak database berbeda juga mahal. Ia menawarkan jalan tengah: satu mesin, beberapa cara mengakses data, dengan ongkos operasional yang lebih ringan.

  • Polyglot persistence itu valid — tapi ongkos opsnya nyata & bertambah tiap database baru.
  • Multi-model = satu representasi, banyak API — document, graph, key-value di atas mesin yang sama.
  • Bukan pengganti mutlak spesialis — untuk kebutuhan ekstrem, database khusus masih menang.
  • Jangan pakai semua model tanpa alasan — pakai yang memang dibutuhkan pola aksesmu.
  • Cek dulu: butuh mesin baru, atau cukup ekstensi? — JSONB/PostGIS/pgvector sering sudah cukup.
  • Pilih berdasar keseimbangan kebutuhan — bukan karena ikut tren atau malas evaluasi.

Aturan emasnya

Tanya: "Apakah kebutuhan data saya beragam tapi seimbang, atau ada satu sisi yang ekstrem?" Kalau beragam & seimbang, multi-model memberimu kesederhanaan operasional yang berharga. Kalau ada satu sisi yang ekstrem, database spesialis di sisi itu akan menyelamatkanmu dari kompromi performa. Tidak ada satu model data yang menang untuk segalanya — begitu juga tidak ada satu mesin yang menang untuk segala beban kerja.
