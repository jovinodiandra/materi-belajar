// Struktur Data — saat hubungan antar data lebih penting daripada urutannya

Data yang saling terhubung, bukan cuma berurutan.

Array itu linear. Tree itu hierarkis — satu induk, banyak anak, tidak ada siklus balik. Tapi banyak data di dunia nyata bentuknya lebih liar: kota terhubung ke banyak kota lain lewat jalan, akun media sosial berteman dengan banyak akun lain, satu package bergantung ke banyak package lain (dan sebaliknya). Graph adalah struktur data untuk merepresentasikan relasi many-to-many seperti ini — kumpulan vertex (titik) yang dihubungkan oleh edge (garis). Catatan: ini bahas struktur data-nya — representasi & cara bacanya. Detail algoritma BFS/DFS ada di topik terpisah, dan kalau kamu cari graph database (Neo4j, Cypher), itu juga topik lain lagi.

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu memodelkan pertemanan media sosial, kota-kota dengan jalur penerbangan, atau package yang saling depend, dan representasinya masih array datar atau tree (satu induk, banyak anak).

When — satu titik ternyata perlu terhubung ke banyak titik lain sekaligus, relasinya dua arah, dan bisa balik lagi ke titik asal lewat jalur lain (A → B → C → A) — sementara kamu juga sering butuh cek cepat "apakah X terhubung ke Y?".

Then — tree jadi maksa (harus cari-cari mana yang "induk" padahal tidak ada), data relasinya kamu duplikasi ke banyak tempat biar "kebaca", dan query siklus/dua-arah jadi kode ad-hoc yang gampang salah mewakili bentuk data aslinya.

→ makanya kita pakai graph — vertex & edge yang memang dirancang untuk relasi many-to-many.

Akar masalah · Kenapa graph ada

Sebagian data memang bentuknya jaringan

Array cocok untuk urutan. Tree cocok untuk hierarki: satu induk, banyak anak, jelas siapa "di atas" siapa. Tapi bagaimana kalau datanya tidak berjenjang — setiap titik bisa terhubung ke titik mana pun, bahkan bisa balik lagi ke dirinya sendiri lewat jalur lain? Itulah bentuk data yang butuh graph.

◆ Analogi — peta kota dengan jalan penghubung

Bayangkan peta kota: tiap persimpangan adalah sebuah titik, dan tiap jalan yang menghubungkan dua persimpangan adalah garis penghubung. Dari satu persimpangan, kamu bisa punya banyak jalan keluar, menuju banyak persimpangan lain — dan bisa saja ada lebih dari satu rute untuk sampai ke tujuan yang sama. Tidak ada "induk" atau "akar" di peta kota. Itulah kenapa peta tidak bisa direpresentasikan sebagai tree — ia butuh graph.

Pola yang sama muncul di mana-mana: pertemanan di media sosial (A berteman dengan B, B berteman dengan C, C bisa balik berteman dengan A), package yang saling bergantung, kota-kota yang terhubung penerbangan, sampai jaringan komputer. Semuanya adalah relasi many-to-many yang tidak punya arah hierarki yang jelas — dan graph adalah struktur data paling natural untuk memodelkannya.

Konsep inti · Vertex, edge & jenisnya

Vertex adalah titik, edge adalah penghubungnya

Sebuah graph G = (V, E) terdiri dari dua hal: vertex (juga disebut node) — himpunan titik, dan edge — himpunan garis yang menghubungkan pasangan vertex. Dari dua bahan sederhana ini, graph punya beberapa varian penting.

“Graph adalah salah satu struktur data yang paling fleksibel untuk merepresentasikan relasi antar objek — pilihan cara merepresentasikannya bergantung sepenuhnya pada karakteristik graph itu sendiri.”

— parafrasa gagasan Thomas H. Cormen dkk., Introduction to Algorithms (CLRS)

// Directed vs Undirected

  • Undirected — edge tidak punya arah. "A berteman dengan B" otomatis berarti "B berteman dengan A".
  • Directed — edge punya arah (disebut arc). "A follow B" tidak berarti "B follow A".

// Weighted vs Unweighted

  • Unweighted — edge cuma menandakan "terhubung atau tidak".
  • Weighted — tiap edge punya bobot (jarak, biaya, waktu tempuh) — dipakai di shortest path.

Di kode, cara paling umum merepresentasikan graph adalah adjacency list: tiap vertex menyimpan daftar vertex tetangganya. Di Java, ini bisa ditulis pakai Map<Integer, List<Integer>> — kunci adalah vertex, nilai adalah daftar tetangganya.

Graph.java — adjacency list dasarJava
import java.util.*;

public class Graph {
    private final Map<Integer, List<Integer>> adj = new HashMap<>();

    public void addVertex(int v) {
        adj.putIfAbsent(v, new ArrayList<>());
    }

    public void addEdge(int u, int v) {
        addVertex(u);
        addVertex(v);
        adj.get(u).add(v);
        adj.get(v).add(u); // hapus baris ini kalau graph-nya directed
    }

    public List<Integer> neighbors(int v) {
        return adj.getOrDefault(v, Collections.emptyList());
    }
}
◆
Cara menjelajahi graph ini — mengunjungi semua vertex yang terhubung lewat BFS (breadth-first search) atau DFS (depth-first search) — sengaja tidak dibahas detail di sini. Itu topik tersendiri: Graph Traversal, di folder algorithms.
Inti keputusan · Dua cara merepresentasikan

Adjacency list vs adjacency matrix

Ada dua cara umum menyimpan graph di memori, dan keduanya punya trade-off yang berlawanan: adjacency matrix cepat cek edge tapi boros memori, adjacency list hemat memori tapi cek edge-nya lebih lambat.

adjacency matrix — grid V×VJava
int V = 5;
boolean[][] matrix = new boolean[V][V];

void addEdge(int u, int v) {
    matrix[u][v] = true;
    matrix[v][u] = true; // undirected
}

boolean hasEdge(int u, int v) {
    return matrix[u][v]; // O(1) — langsung cek sel
}
// 🐢 V = 10.000 → 100 juta sel, kebanyakan false (sparse graph = boros)
adjacency list — cuma simpan yang adaJava
Map<Integer, List<Integer>> adj = new HashMap<>();

boolean hasEdge(int u, int v) {
    return adj.getOrDefault(u, List.of()).contains(v);
    // O(degree) — harus scan daftar tetangga u
}
// ✅ hemat memori: cuma simpan edge yang benar-benar ada

Intinya: matrix = O(1) cek edge, tapi O(V²) memori — masuk akal kalau graph dense (banyak edge relatif ke jumlah vertex) dan V kecil. List = O(V+E) memori, cek edge O(degree) — lebih unggul untuk graph sparse (edge jauh lebih sedikit dari V²), yang justru paling sering muncul di kasus nyata (jalan, pertemanan, dependency).

“Kepadatan sebuah graph — apakah ia sparse atau dense — bersama dengan operasi yang paling sering dijalankan, adalah faktor penentu representasi mana yang lebih tepat dipakai.”

— parafrasa gagasan Thomas H. Cormen dkk., Introduction to Algorithms (CLRS)
◆ Praktik · Menghindari jebakan umum

Best practice kerja dengan graph

Graph terlihat sederhana di atas kertas, tapi gampang salah implementasi di kode. Beberapa kebiasaan berikut menyelamatkan kamu dari bug yang paling sering muncul.

  1. Pilih adjacency list untuk graph sparse — sebagian besar kasus nyata (jalan, pertemanan, dependency) jarang punya edge sebanyak V², jadi list lebih hemat & tetap cukup cepat.
  2. Pilih adjacency matrix untuk graph dense atau kecil — kalau V kecil (puluhan) dan hampir semua pasangan vertex terhubung, cek edge O(1) dari matrix jadi lebih berharga daripada hemat memorinya list.
  3. Hati-hati cycle di directed graph — traversal naif tanpa menandai vertex yang sudah dikunjungi bisa masuk infinite loop kalau ada siklus (A → B → C → A).
  4. Tentukan directed/undirected di awal, jangan campur — lupa menambahkan edge balik (atau menambahkannya padahal seharusnya directed) adalah sumber bug klasik.
  5. Pakai visited set/array saat traversal — tanpa ini, graph dengan banyak jalur ke vertex yang sama akan mengunjungi ulang vertex tersebut berkali-kali.
  6. Pertimbangkan graph terputus (disconnected) — tidak semua vertex tentu bisa dicapai dari satu titik awal; jangan asumsikan traversal dari satu vertex akan menjangkau seluruh graph.

◆ Harga · Tidak ada representasi sempurna

Trade-off: adjacency list vs matrix

Sama seperti pilihan struktur data lain, tidak ada yang menang mutlak — pilihannya bergantung pada bentuk graph & operasi apa yang paling sering kamu jalankan.

// Adjacency list

  • Hemat memori — O(V+E), cuma simpan edge yang ada.
  • Iterasi semua tetangga sebuah vertex cepat & alami.
  • Cocok untuk graph sparse (mayoritas kasus nyata).
  • Cek edge spesifik O(degree) — bisa lambat kalau degree besar.

// Adjacency matrix

  • Cek edge O(1) — langsung akses sel matrix.
  • Boros memori — O(V²), tetap segitu walau edge sedikit.
  • Cocok untuk graph dense & V relatif kecil.
  • Iterasi tetangga harus scan satu baris penuh (O(V)).

“Graph adalah salah satu struktur data paling universal dalam ilmu komputer — begitu banyak masalah dunia nyata, dari jaringan sampai ketergantungan hingga relasi sosial, secara alami bisa dimodelkan sebagai vertex dan edge.”

— parafrasa gagasan Robert Sedgewick & Kevin Wayne, Algorithms
◆ Keputusan · Pakai atau jangan

Kapan harus pakai graph

Pertanyaan penentunya sederhana: apakah relasi antar data kamu many-to-many, dan tidak punya arah hierarki yang jelas?

// Pakai graph saat…

  • Data punya relasi many-to-many (bukan one-to-many).
  • Butuh cari jalur/rute antar dua titik (shortest path).
  • Ada ketergantungan yang saling terkait (dependency).
  • Struktur bisa punya siklus balik (bukan hierarki murni).
  • Butuh analisis koneksi — siapa terhubung ke siapa.

// Jangan, pilih struktur lain saat…

  • Data cuma urutan linear → cukup array/list.
  • Data hierarkis murni, satu induk banyak anak → tree.
  • Cuma butuh cek keanggotaan/duplikat → hash set.
  • Relasinya sebenarnya one-to-many sederhana.
  • Butuh query relasi kompleks + persistence → pertimbangkan graph database (topik terpisah).
◆ Pengingat

Tree sebenarnya adalah kasus khusus dari graph — graph yang connected, acyclic, dan undirected. Kalau data kamu masih bisa dijelaskan sebagai "satu induk, banyak anak, tanpa jalur balik", tree sudah cukup dan lebih sederhana daripada graph umum.

Studi kasus · Di dunia nyata

Graph di balik layar sistem yang kamu pakai

Tiga contoh nyata di mana graph adalah struktur data yang mendasari fitur inti — perhatikan polanya: relasi many-to-many yang butuh dinavigasi atau diurutkan.

// navigasi

Peta & navigasi

Kasus: mencari rute tercepat dari titik A ke titik B di antara jutaan jalan. Kenapa graph: Google Maps merepresentasikan persimpangan sebagai vertex & jalan sebagai edge berbobot (jarak/waktu tempuh), lalu mencari shortest path.

// social network

Pertemanan & koneksi

Kasus: siapa terhubung ke siapa, rekomendasi "orang yang mungkin kamu kenal". Kenapa graph: pertemanan adalah relasi many-to-many klasik. Untuk penyimpanan & query relasi berskala besar yang persisten, lihat topik Graph Database di folder database.

// package manager

Dependency resolution

Kasus: package A butuh package B, B butuh C — package manager harus tahu urutan instalasi yang benar & mendeteksi dependency melingkar. Kenapa graph: dependency dimodelkan sebagai directed graph, diurutkan pakai topological sort.

◆ Benang merahnya

Di ketiga kasus di atas, graph dipilih karena relasinya tidak hierarkis — satu titik bisa terhubung ke banyak titik lain dengan cara yang tidak beraturan. Struktur data yang lebih sederhana (array, tree) akan kesulitan merepresentasikan pola ini secara alami.

Penutup

Vertex, edge, dan pilihan representasi yang tepat

Graph adalah jawaban untuk data yang bentuknya jaringan, bukan urutan atau hierarki. Kuasai representasinya dulu — sisanya (traversal, shortest path, dsb.) akan jauh lebih mudah dipahami.

  • Vertex & edge — titik dan penghubungnya, bisa directed/undirected, weighted/unweighted.
  • Adjacency list — hemat memori, cocok untuk graph sparse (mayoritas kasus nyata).
  • Adjacency matrix — cek edge O(1), tapi boros memori O(V²), cocok graph dense & kecil.
  • Tree adalah kasus khusus graph — connected, acyclic, undirected.
  • Traversal (BFS/DFS) — dibahas detail di topik terpisah, Graph Traversal.
  • Pilih dari bentuk relasi — many-to-many tanpa hierarki jelas → graph.
