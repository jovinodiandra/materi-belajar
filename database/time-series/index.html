// Database — data yang selalu bertambah, hampir tak pernah diubah

Data yang selalu menunjuk maju, jarang menoleh ke belakang.

Metrik CPU server, suhu dari sensor IoT, harga saham tiap detik — semuanya punya pola yang sama: ditulis jutaan kali, hampir selalu append (data baru, bukan update data lama), dan dibaca dengan pertanyaan seperti "bagaimana tren 1 jam terakhir?". Database time-series dirancang khusus untuk pola ini. Deck ini buat pemula: dari kenapa ia lahir, model datanya, kompresi & retention, sampai kapan harus dipakai di production — diselingi kalimat dari buku rujukan & desain sistem time-series modern.

Sakit
Volume tulis meledak — relasional biasa kewalahan menampung jutaan baris/detik
Ide
Timestamp + tag + value — model data yang dioptimalkan untuk rentang waktu
Untung
Tulis & query rentang waktu cepat — plus kompresi kolumnar yang efisien
Batas
Bukan buat data relasional umum — model query terbatas, tak jago JOIN
Pakai
Saat data = deret waktu — monitoring, IoT, observability, harga saham

◆ Buat apa ini? Kenapa pakai Time Series Database?

Given — tim monitoring nyimpen metrik CPU, memori, dan network dari 2.000 server ke tabel relasional biasa, satu baris per (server_id, timestamp, metric, value) tiap 5 detik.

When — volume tulis tembus jutaan baris per hari, lalu ada yang minta dashboard "tren CPU 30 hari terakhir, agregasi per menit" untuk ribuan server sekaligus.

Then — index B-tree terus membengkak dan direorganisasi tiap insert, tulis makin lambat, dan query rentang waktu jatuh jadi full table scan — dashboard yang seharusnya real-time malah lag bermenit-menit, sementara disk cepat penuh karena tiap angka disimpan mentah tanpa kompresi.

→ makanya kita pakai Time Series Database.

Akar masalah · Kenapa time-series database lahir

Relational biasa kewalahan menampung deret waktu

Bayangkan satu server yang melaporkan CPU, memori, dan network tiap detik. Kalikan dengan ribuan server, ribuan sensor IoT, atau tiap transaksi harga saham — datanya bisa jutaan baris per detik, dan hampir semuanya cuma ditulis sekali lalu dibaca ulang berdasarkan rentang waktu. Ia nyaris tidak pernah di-update.

◆ Analogi — grafik detak jantung di monitor EKG

Monitor detak jantung di rumah sakit menggambar garis yang terus bergerak maju — tiap detak baru ditambahkan di ujung kanan, detak lama tidak pernah ditulis ulang, dan dokter membacanya sebagai tren, bukan satu angka lepas. Menyimpan data ini di tabel relasional biasa ibarat mencoba mencatat tiap detak sebagai baris terpisah dengan index B-tree yang harus terus di-reorganisasi — cepat penuh, cepat lambat. Time-series database dirancang supaya menulis garis yang terus memanjang itu murah, dan membaca potongan rentangnya cepat.

Tiga ciri beban kerja ini yang bikin database umum kewalahan: write-heavy (tulisan jauh lebih sering dari baca-per-baris), append-only (data baru selalu punya timestamp lebih besar dari sebelumnya), dan query-by-range (hampir semua query berbentuk "dari waktu A sampai B"). Index relasional generik dioptimalkan untuk pola akses acak — bukan pola berurutan seperti ini.

Konsep inti · Model data time-series

Timestamp, tag, dan value — tiga bagian intinya

Setiap titik data (point) di time-series database punya tiga bagian: timestamp (kapan), tags/labels (dimensi untuk memfilter, misalnya nama server atau region), dan value/field (angka yang diukur, misalnya CPU usage).

Data time-series idealnya diberi label untuk dimensi yang dipakai memfilter — misalnya nama server atau region — bukan disimpan sebagai kolom bebas seperti tabel relasional biasa, karena pola query time-series selalu berbasis rentang waktu ditambah filter dimensi.

— gagasan inti desain Prometheus & InfluxDB (dokumentasi & desain sistem time-series modern)
◆ Anatomi satu titik data (point)
Waktutimestamp → 2026-07-16T09:00:05Z
Tagserver_id="web-03", region="jakarta"
Fieldcpu_usage=72.4, mem_usage=61.0

Tag di-index & dipakai untuk WHERE / GROUP BY — jaga jumlah kombinasi tag unik (cardinality) tetap terkendali. Field adalah angkanya sendiri, biasanya tidak di-index satu per satu.

TimescaleDB — hypertable & query rentang waktuSQL
-- metrics adalah "hypertable": tabel Postgres biasa yang dipartisi otomatis per waktu
CREATE TABLE metrics (
  time        TIMESTAMPTZ       NOT NULL,
  server_id   TEXT              NOT NULL,   -- tag
  region      TEXT              NOT NULL,   -- tag
  cpu_usage   DOUBLE PRECISION              -- field
);
SELECT create_hypertable('metrics', 'time');

-- rata-rata CPU per 5 menit, 1 hari terakhir, per server
SELECT time_bucket('5 minutes', time) AS bucket,
       server_id,
       avg(cpu_usage) AS avg_cpu
FROM metrics
WHERE time > now() - interval '1 day'
  AND region = 'jakarta'
GROUP BY bucket, server_id
ORDER BY bucket;

Bandingkan dengan gaya InfluxQL (bahasa query InfluxDB) untuk kebutuhan serupa — WHERE pada tag, GROUP BY time() untuk downsampling on-the-fly:

InfluxQL — rata-rata per intervalInfluxQL
SELECT mean("cpu_usage")
FROM "metrics"
WHERE "region" = 'jakarta' AND time > now() - 1h
GROUP BY time(5m), "server_id"
Konsep penting · Kompresi & downsampling

Data lama tak perlu resolusi setinggi data baru

Menyimpan tiap detik data mentah selamanya cepat membengkak. Time-series database mengandalkan dua trik: kompresi kolumnar (nilai-nilai berdekatan waktu cenderung mirip, jadi mudah dipadatkan) dan downsampling + retention policy (data lama disimpan dalam resolusi lebih rendah, lalu akhirnya dihapus).

Data yang bersifat mostly-append (jarang di-update) dan sering di-query berdasarkan rentang tertentu — seperti data time-series — sangat diuntungkan oleh penyimpanan kolumnar dan kompresi, karena nilai-nilai yang berdekatan dalam waktu cenderung mirip dan mudah dikompres.

— parafrase dari Martin Kleppmann, Designing Data-Intensive Applications (Bab 3, storage engine kolumnar)
simpan semua raw selamanyaSQL
-- tabel biasa, tanpa partisi waktu, tanpa retention
CREATE TABLE metrics_raw (
  time      TIMESTAMPTZ,
  server_id TEXT,
  cpu_usage DOUBLE PRECISION
);
-- data 3 tahun lalu tetap tersimpan resolusi per detik
-- tabel terus membesar, query "1 tahun terakhir" scan miliaran baris
-- storage & biaya query naik terus, tak pernah dibersihkan
downsample + retention policySQL
-- kompres chunk yang lebih tua dari 7 hari
SELECT add_compression_policy('metrics', INTERVAL '7 days');

-- agregat kontinu: ringkas jadi rata-rata per 5 menit
CREATE MATERIALIZED VIEW metrics_5m
WITH (timescaledb.continuous) AS
SELECT time_bucket('5 minutes', time) AS bucket,
       server_id, avg(cpu_usage) AS avg_cpu
FROM metrics GROUP BY bucket, server_id;

-- buang data mentah > 90 hari, sisakan agregatnya saja
SELECT add_retention_policy('metrics', INTERVAL '90 days');

Hasilnya: query "tren 1 tahun terakhir" cukup baca metrics_5m yang jauh lebih kecil, bukan miliaran baris mentah. Kamu tetap simpan detail penuh untuk data baru (butuh debugging presisi tinggi), tapi data lama cukup dalam bentuk ringkasan.

◆ Praktik · Supaya tidak menyesal nanti

Best practice memakai time-series database

Sebagian besar masalah production di TSDB berasal dari hal yang sama: cardinality tag yang meledak dan retention yang tak pernah diatur. Ikuti poin-poin ini sejak awal.

  • Atur retention policy sejak hari pertama. Tentukan berapa lama data mentah relevan (mis. 90 days) sebelum di-downsample atau dihapus — jangan tunggu disk penuh baru mikir.
  • Pakai tag untuk filter, bukan untuk nilai bebas. ID user unik atau UUID request sebaiknya jadi field, bukan tag — tiap kombinasi tag baru menambah series baru dan bisa meledakkan cardinality.
  • Downsample data lama secara terjadwal. Simpan resolusi tinggi (per detik) hanya untuk beberapa hari/minggu terakhir; sisanya cukup agregat per menit/jam.
  • Batch penulisan, jangan satu-satu. Kirim banyak point sekaligus per request tulis — jauh lebih efisien daripada satu HTTP call per metrik.
  • Pantau cardinality secara aktif. Jumlah series unik (kombinasi tag) adalah metrik kesehatan tersendiri — lonjakan tiba-tiba biasanya tanda ada tag yang salah desain.
  • Pisahkan metrik dari log/trace mentah. TSDB jago untuk angka teragregasi; log teks panjang atau trace detail lebih cocok di sistem lain (mis. object storage / search engine).
🎓 Tier belajar · Dari nulis metrik sampai skala jutaan point/detik

Jenjang belajar time-series database

Tidak perlu langsung paham semuanya. Berikut jenjang wajar dari pemula sampai level yang menangani beban production skala besar.

🌱 Beginner

Tulis & query metrik dasar

Fokus memahami bentuk data timestamp + tag + value, dan bisa menulis query rentang waktu sederhana.

  • Insert point ke InfluxDB/TimescaleDB via client library
  • Query "nilai 1 jam terakhir" dengan filter tag
  • Paham beda tag vs field
  • Coba dashboard sederhana di Grafana
⚙ Middle

Desain retention & downsampling nyata

Bisa merancang skema tag yang aman, retention policy, dan continuous aggregate untuk dashboard monitoring produksi.

  • Rancang retention policy multi-tier (raw → 5m → 1h)
  • Setup continuous aggregate / rollup job
  • Hindari cardinality explosion saat desain tag
  • Integrasi Prometheus + alerting rules
🚀 Advance

Skala jutaan point/detik

Menangani beban tulis masif, cardinality tinggi, dan optimasi kompresi kolumnar di level storage engine.

  • Sharding & partisi hypertable lintas node
  • Tuning kompresi kolumnar & chunk interval
  • Kelola cardinality jutaan series unik
  • Desain federasi/remote-write antar cluster TSDB
◆ Harga · Tidak ada makan siang gratis

Trade-off: yang kamu dapat & yang kamu korbankan

Time-series database bukan pengganti database relasional — ia spesialis untuk satu pola beban kerja tertentu.

// Yang kamu dapat

  • Tulis & query rentang waktu sangat cepat.
  • Kompresi kolumnar hemat storage untuk data mirip-mirip.
  • Downsampling & retention bawaan, bukan tempelan.
  • Skala tulis tinggi untuk beban append-only.

// Yang kamu korbankan

  • Bukan buat data relasional umum (users, orders, dll).
  • Model query terbatas — JOIN kompleks bukan kekuatannya.
  • Cardinality tag tinggi bisa merusak performa.
  • Update/delete baris individual mahal & jarang didukung baik.
◆ Catatan

Batas antar kategori database makin kabur — TimescaleDB adalah ekstensi Postgres, jadi kamu tetap bisa JOIN tabel relasional biasa dengan hypertable-nya. Tapi inti kekuatannya tetap sama: beban tulis append-only berbasis waktu.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai time-series database

Aturan praktisnya: kalau data kamu selalu punya timestamp, hampir tak pernah diubah, dan selalu di-query berdasarkan rentang waktu — pakai TSDB. Kalau butuh relasi kompleks & update sering — pakai relasional.

// Pakai TSDB saat…

  • Metrik server, aplikasi, atau infrastruktur.
  • Data sensor IoT yang mengalir terus-menerus.
  • Harga saham / data finansial berbasis tick.
  • Query selalu berbentuk "dari waktu A ke B".
  • Volume tulis sangat tinggi & append-only.

// Jangan, pilih lain saat…

  • Data punya banyak relasi many-to-many antar entitas.
  • Baris sering di-update setelah ditulis.
  • Butuh transaksi kompleks lintas banyak tabel.
  • Data teks panjang / dokumen (bukan angka berdimensi waktu).
◆
Jangan paksa data non-time-series masuk TSDB hanya karena "sedang tren observability". Kalau kebutuhanmu adalah menyimpan profil user atau relasi pesanan-item, itu pekerjaan relasional/document — TSDB tidak akan menyelamatkanmu di sana.
Studi kasus · Di dunia nyata

Time-series database di production

Beberapa contoh nyata di mana pola time-series jadi fondasi sistem berskala besar.

// cloud-native

Prometheus di dunia Kubernetes

Prometheus jadi standar de-facto untuk monitoring di ekosistem Kubernetes & cloud-native — hampir setiap tooling observability modern punya integrasi dengannya karena model metrik berbasis time-series-nya cocok dengan sifat container yang dinamis & berumur pendek.

// IoT / otomotif

Telemetri kendaraan skala besar

Perusahaan otomotif & IoT seperti Tesla dikenal mengumpulkan data telemetri kendaraan (posisi, baterai, sensor) dalam skala time-series yang masif — pola tulis konstan dari banyak perangkat, dianalisis berdasarkan rentang waktu perjalanan.

// observability

Datadog & Grafana

Platform observability modern seperti Datadog dan ekosistem Grafana dibangun di atas backend time-series untuk menyimpan & memvisualisasikan metrik, karena beban kerjanya persis: tulis terus-menerus, query berdasarkan rentang waktu.

// finansial

Data pasar & harga tick

Sistem trading & analitik pasar finansial menyimpan data harga berbasis tick (tiap perubahan harga = satu titik waktu) — pola akses "lihat pergerakan harga dalam rentang X" sangat pas dengan model time-series.

◆ Benang merahnya

Di semua kasus di atas: data selalu bertambah, jarang di-update, dan pertanyaannya selalu soal rentang waktu & tren — bukan relasi antar entitas. Begitu kebutuhan bergeser ke data relasional biasa (akun user, transaksi keuangan berelasi), tim biasanya menaruh itu di database lain di sampingnya.

⚙ Ekosistem · Alat yang dipakai

Tools time-series database

Cukup kenali nama populernya & kapan kira-kira dipakai. Sebagai pemula, mulai dari Prometheus (monitoring) atau TimescaleDB (kalau sudah pakai Postgres).

// purpose-built

InfluxDB

Time-series database native, dirancang dari nol untuk metrik & event. Punya bahasa query sendiri (InfluxQL/Flux), populer untuk IoT & monitoring custom.

// ekstensi Postgres

TimescaleDB

Ekstensi di atas PostgreSQL — kamu tetap dapat SQL penuh & relasi, ditambah hypertable, kompresi, dan continuous aggregate. Pilihan aman kalau tim sudah nyaman dengan Postgres.

// monitoring standar

Prometheus

Fokus pada metrik & alerting, model pull-based, bahasa query PromQL. Standar de-facto monitoring di dunia Kubernetes/cloud-native.

// analitik skala besar

Apache Druid

Time-series & analitik kolumnar untuk skala sangat besar — sering dipakai untuk dashboard analitik real-time dengan volume event tinggi.

// visualisasi

Grafana

Bukan database, tapi pendamping wajib — dashboard visualisasi yang bisa menyambung ke Prometheus, InfluxDB, TimescaleDB, dan lainnya sekaligus.

◆ Tips pemula

Bingung memilih? Kalau tim sudah pakai Postgres, coba TimescaleDB dulu — tak perlu belajar bahasa query baru. Kalau fokusnya murni monitoring infrastruktur/Kubernetes, Prometheus + Grafana adalah kombinasi paling umum dipakai.

Penutup

Rentang waktu adalah pertanyaannya, TSDB jawabannya

Time-series database lahir dari beban kerja yang sangat spesifik: data yang terus bertambah, jarang diubah, dan selalu ditanya lewat rentang waktu. Ia bersinar di sana, dan tersandung saat dipaksa jadi database serba guna.

  • Append-only, bukan update-heavy — metrik, sensor, harga, ditulis maju terus.
  • Timestamp + tag + value — tag untuk filter, field untuk angkanya.
  • Kompresi kolumnar — data berdekatan waktu mudah dipadatkan.
  • Downsampling & retention — data lama cukup ringkasannya, bukan mentahnya.
  • Jaga cardinality tag — jangan taruh nilai bebas/unik sebagai tag.
  • Pilih dari pola bebannya — bukan karena "observability lagi tren".

Aturan emasnya

Tanya: "Apakah data ini selalu punya timestamp, hampir tak pernah diubah setelah ditulis, dan selalu ditanya lewat rentang waktu?" Kalau ya, time-series database akan memberimu kecepatan tulis & query yang jauh lebih baik daripada memaksakannya ke tabel relasional biasa. Kalau tidak, database lain akan lebih pas.
