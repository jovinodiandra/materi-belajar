// DSA — Algorithms · overview strategi mencari elemen di kumpulan data

Mencari itu strategi, bukan cuma satu cara.

Setiap aplikasi, cepat atau lambat, harus mencari sesuatu — user berdasarkan ID, produk berdasarkan nama, baris data yang cocok dengan kondisi tertentu. Cara paling naif adalah cek satu per satu. Tapi begitu datamu terurut, ter-hash, atau tersimpan dalam pohon, ada jalan pintas yang jauh lebih cepat. Deck ini adalah peta besar-nya: linear vs binary search secara garis besar, dan bagaimana struktur data yang kamu pilih menentukan strategi search mana yang mungkin dipakai. Detail teknik binary search yang lebih dalam ada di topik terpisah.

Sakit
Data makin besar — cek satu per satu makin lambat
Ide
Manfaatkan struktur data — urutan, hash, atau pohon
Untung
Search jadi O(log n) bahkan O(1) — bukan lagi O(n)
Batas
Strategi cepat butuh syarat — terurut, ter-hash, atau seimbang
Pakai
Pilih sesuai bentuk & pola akses data — bukan asal ikut yang paling populer

◆ Buat apa ini? Kenapa pakai ini?

Given — tanpa strategi searching, satu-satunya cara mencari elemen adalah memeriksa data satu per satu dari awal (linear scan), tidak peduli apakah datanya terurut, ter-hash, atau tersimpan dalam pohon.

When — dataset tumbuh dari ribuan jadi jutaan baris (misal cari user berdasarkan ID di database, atau cari kata di kamus digital), dan operasi pencarian itu dipanggil berulang-ulang di jalur kritis aplikasi.

Then — waktu pencarian ikut membengkak linear terhadap jumlah data (O(n)): makin banyak baris, makin lama responsnya, sampai fitur "cari" terasa lag bahkan macet saat data sudah besar.

→ makanya kita pakai strategi Searching yang tepat — binary search di data terurut, hashing untuk lookup O(1), atau pohon pencarian seimbang — supaya waktu cari tidak ikut membesar seiring datanya bertambah.

Akar masalah · Kenapa strategi search penting

Cara kamu mencari menentukan seberapa cepat aplikasimu terasa

Bayangkan kamu harus mencari satu nama di buku telepon berisi satu juta orang. Kalau bukunya tidak diurutkan, satu-satunya cara adalah membuka halaman demi halaman dari awal — bisa jadi kamu baru ketemu di halaman terakhir. Tapi buku telepon asli selalu diurutkan berdasarkan nama, jadi kamu bisa langsung buka ke tengah, lihat apakah namanya "lebih awal" atau "lebih akhir", lalu persempit separuh sisa halaman berulang kali.

◆ Analogi — kamus vs tumpukan kertas acak

Kamus disusun alfabetis: mencari kata "senja" tidak pernah butuh membaca dari huruf A. Kamu langsung lompat ke bagian S, lalu persempit lagi. Bandingkan dengan tumpukan kertas acak di meja — satu-satunya cara memastikan sebuah kertas ada atau tidak di situ adalah membolak-balik semuanya, satu per satu, sampai ketemu atau tumpukannya habis. Urutan (atau struktur) adalah yang membuat jalan pintas itu mungkin.

"Pencarian adalah salah satu operasi paling dasar sekaligus paling sering dijalankan dalam pemrosesan data — begitu sering sehingga efisiensi sebuah sistem secara keseluruhan kerap ditentukan oleh seberapa tepat strategi pencariannya dipilih sesuai karakteristik datanya."

— parafrase dari Donald E. Knuth, The Art of Computer Programming, Volume 3: Sorting and Searching

Inti dari topik searching bukan cuma "algoritma apa yang dipakai", tapi keputusan yang lebih besar: apakah datamu punya struktur (urutan, hash, pohon) yang bisa dimanfaatkan? Kalau ya, strategi cerdas bisa mengubah pencarian dari "periksa jutaan baris" jadi "periksa belasan baris saja".

Konsep inti · Dua strategi paling dasar

Linear search vs binary search, garis besarnya

Linear search mengecek elemen satu per satu dari awal sampai ketemu atau habis — bekerja di data apa pun, terurut atau tidak, tapi kompleksitasnya O(n). Binary search memanfaatkan data yang sudah terurut: bandingkan target dengan elemen tengah, lalu buang separuh sisi yang mustahil berisi target — berulang sampai ketemu. Kompleksitasnya O(log n), jauh lebih cepat, tapi hanya sah kalau datanya terurut.

LinearSearch.java — O(n), data apa punJava
public class LinearSearch {

    static int cari(int[] data, int target) {
        for (int i = 0; i < data.length; i++) {
            if (data[i] == target) return i; // ketemu
        }
        return -1; // tidak ditemukan
    }
}
// tak butuh urutan apa pun, tapi worst-case periksa semua elemen
BinarySearch.java — O(log n), butuh terurutJava
public class BinarySearch {

    static int cari(int[] data, int target) {
        int lo = 0, hi = data.length - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (data[mid] == target) return mid;
            if (data[mid] < target) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1; // tidak ditemukan
    }
}
// PRASYARAT: data[] harus sudah terurut ascending

Untuk 1 juta elemen: linear search butuh rata-rata 500.000 kali pengecekan, binary search butuh sekitar 20 kali saja — karena tiap langkahnya membuang separuh sisa data. Selisih inilah yang membuat "apakah datamu terurut?" jadi pertanyaan yang sangat mahal harganya. Pembahasan mendalam soal binary search — variasi, bug umum, kompleksitas rekursif vs iteratif — ada di topik Binary Search tersendiri.

Konsep inti · Struktur data = strategi search

Struktur data yang kamu pilih menentukan search mana yang mungkin

Linear dan binary search cuma dua contoh dari gambaran yang lebih besar: tiap struktur data punya karakteristik search-nya sendiri. Array acak cuma bisa linear. Array terurut bisa binary. Hash table bisa O(1) tapi buta urutan. Binary search tree (BST) tetap terurut sekaligus mudah diubah.

◆ Search complexity per struktur data (rata-rata)
Array acakO(n) — cuma bisa linear search
Array terurutO(log n) — binary search, tapi insert/delete mahal
Hash TableO(1) — exact-match cepat, TAPI tidak terurut
BST seimbangO(log n) — tetap terurut & mudah diubah

Tak ada struktur yang menang di semua sisi: array terurut cepat dicari tapi mahal diubah (harus geser elemen agar tetap terurut), hash table sangat cepat untuk pencocokan persis tapi tidak bisa menjawab query seperti "semua nilai di antara X dan Y", sementara BST seimbang mengorbankan sedikit kecepatan demi tetap terurut dan mudah di-insert/delete.

"Memilih struktur data — array terurut, hash table, atau binary search tree — pada dasarnya adalah memilih strategi pencarian; memahami trade-off di antara strategi-strategi ini adalah keterampilan inti yang harus dikuasai sebelum menulis satu baris kode pencarian pun."

— parafrase dari Robert Sedgewick & Kevin Wayne, Algorithms

Pertanyaan yang lebih penting dari "linear atau binary?" sebenarnya adalah: data ini butuh disimpan dengan bentuk apa, supaya search yang paling sering kamu lakukan jadi semurah mungkin? Itulah kenapa memilih struktur data pada dasarnya sudah memilih strategi search-nya sekaligus.

◆ Praktik · Kebiasaan aman memilih strategi search

Best practice sebelum menulis kode pencarian

Beberapa kebiasaan ini akan menyelamatkanmu dari bug halus (binary search di data tak terurut) sampai keputusan struktur data yang menyesatkan di kemudian hari.

  1. Pastikan data benar-benar terurut sebelum memakai binary search — binary search di data yang tidak terurut bisa diam-diam salah, bukan sekadar lambat.
  2. Pertimbangkan hash table kalau kamu cuma butuh pencocokan persis (exact-match) tanpa perlu urutan, range query, atau "elemen terdekat" — O(1) rata-rata biasanya menang telak dari O(log n).
  3. Jangan optimasi prematur — untuk data kecil (puluhan hingga ratusan elemen), linear search yang sederhana sering cukup cepat dan jauh lebih mudah dijaga daripada menambah struktur data baru.
  4. Hitung biaya menjaga urutan — array terurut cepat dicari, tapi tiap insert/delete berpotensi menggeser banyak elemen; kalau data sering berubah, BST seimbang atau struktur lain bisa lebih pas.
  5. Pilih struktur data dari pola query dominan — kalau aplikasimu 90% melakukan exact-match, condong ke hash table; kalau butuh range query atau data terurut, condong ke array terurut/BST.
  6. Ukur, jangan tebak — kompleksitas rata-rata hash table bisa memburuk jadi O(n) saat banyak collision; sebelum percaya sepenuhnya, pastikan fungsi hash-nya cukup baik untuk pola data nyata.

Tier belajar searching

Searching kelihatannya sederhana, tapi makin dalam kamu masuk, makin ia terhubung ke pilihan struktur data dan bahkan arsitektur sistem pencarian skala besar.

◆ Harga · Simpel vs cepat

Trade-off: sederhana tanpa syarat vs cepat dengan syarat

Linear dan binary search bukan soal "mana yang lebih baik" — keduanya melayani situasi yang berbeda, dan harga yang dibayar juga berbeda.

// Linear search

  • Bekerja di data apa pun — terurut atau tidak.
  • Implementasinya sangat sederhana, minim bug.
  • Tidak butuh biaya menjaga struktur/urutan tambahan.
  • Untuk data kecil, bedanya nyaris tak terasa.

// Binary search

  • Wajib data terurut (atau tree/index setara) — syarat mutlak.
  • Butuh biaya menjaga urutan saat data sering berubah.
  • Jauh lebih cepat, tapi implementasinya lebih rawan bug tepi (edge case).
  • Cuma unggul telak begitu ukuran data cukup besar.
◆ Yang sering terlewat

Biaya binary search bukan cuma di algoritmanya sendiri, tapi di menjaga data tetap terurut dari waktu ke waktu. Kalau datamu sering di-insert/delete, kamu sedang membayar biaya itu berulang kali — kadang lebih mahal daripada penghematan yang didapat dari binary search itu sendiri.

◆ Keputusan · Pakai atau jangan

Kapan strategi mana yang harus dipakai

Aturan praktisnya: kalau data kecil atau tak pernah terurut, linear search cukup. Kalau data besar, jarang berubah, dan bisa diurutkan sekali, manfaatkan binary search atau struktur data lain yang lebih cepat.

// Linear search cukup saat…

  • Ukuran data kecil (puluhan–ratusan elemen).
  • Data sering berubah dan sulit dijaga tetap terurut.
  • Search cuma dilakukan sesekali, bukan operasi kritis.
  • Kesederhanaan & minim bug lebih penting daripada kecepatan mentah.

// Butuh strategi lebih cepat saat…

  • Data besar (ribuan–jutaan elemen) & search sering dilakukan.
  • Data relatif statis, bisa diurutkan/di-index sekali di awal.
  • Butuh exact-match super cepat → pertimbangkan hash table.
  • Butuh urutan/range query sekaligus kecepatan → pertimbangkan BST/index.
◆ Pertanyaan penentu

Tanyakan ke datamu: "Seberapa sering aku mencari di sini, dan seberapa sering datanya berubah?" Search jarang + data sering berubah → linear cukup. Search sering + data relatif stabil → investasi ke struktur yang lebih cepat biasanya terbayar.

Studi kasus · Di dunia nyata

Bagaimana tim production memilih strategi search

Tiga contoh nyata di mana pemilihan strategi search bukan soal "algoritma tercepat di atas kertas", tapi soal kecocokan dengan pola pemakaian sesungguhnya.

// fitur "cari"

Kotak pencarian di aplikasi

Kasus: fitur cari di daftar pendek (mis. daftar kontak lokal di satu layar) vs cari di jutaan baris data. Polanya: untuk list kecil yang sudah dimuat di memori, linear search sederhana cukup. Begitu datanya besar & tersimpan di database, tim beralih ke index database alih-alih linear scan — rujuk topik Database Indexing & Search di situs ini.

// autocomplete

Saran ketik otomatis

Kasus: menampilkan saran kata saat user mengetik prefix seperti "sea…". Polanya: ini bukan pekerjaan linear atau binary search — struktur yang cocok untuk pencarian berbasis prefix adalah trie, yang menyusuri karakter demi karakter alih-alih membandingkan seluruh string.

// desain sistem

Memilih struktur data dari pola query

Kasus: tim membangun layanan lookup ID→data dengan volume tinggi. Polanya: karena query dominannya adalah exact-match berdasarkan ID (bukan range atau urutan), tim memilih struktur berbasis hash daripada struktur terurut — keputusan diambil dari pola query yang paling sering terjadi, bukan dari struktur yang "terdengar canggih".

◆ Benang merahnya

Di ketiga kasus di atas, keputusannya selalu kembali ke pola akses yang sesungguhnya — ukuran data, seberapa sering data berubah, dan jenis query yang paling dominan. Strategi search yang tepat adalah yang cocok dengan pola itu, bukan yang paling rumit atau paling populer.

Penutup

Search yang cepat lahir dari struktur, bukan dari trik algoritma semata

Linear search selalu bekerja, tapi tidak pernah cepat untuk data besar. Binary search jauh lebih cepat, tapi menuntut syarat: data harus terurut. Di antara keduanya, ada pilihan struktur data — hash table, BST, index — yang masing-masing menawarkan trade-off sendiri antara kecepatan search dan biaya menjaga struktur itu tetap benar.

  • Linear search — O(n), bekerja di data apa pun, tak butuh syarat.
  • Binary search — O(log n), tapi wajib data terurut.
  • Struktur data = strategi search — array, hash, BST punya karakteristik berbeda.
  • Hash table — O(1) untuk exact-match, buta urutan.
  • Pilih dari pola query — bukan dari algoritma yang terdengar paling canggih.
  • Di skala besar — strategi search bergeser ke index & search engine terdistribusi.
