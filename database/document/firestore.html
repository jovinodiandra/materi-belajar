// Tool document database #2 — real-time, untuk mobile & web

Firestore — dokumen yang sinkron otomatis ke semua perangkat.

Cloud Firestore dari Firebase (Google) adalah document database yang fokus pada real-time dan offline-first. Begitu satu klien menulis, semua klien lain yang "mendengarkan" langsung dapat update — tanpa kamu menulis server. Ini cocok persis untuk contoh kasus chat & aplikasi mobile dari deck induk. Yang unik: di Firestore indexing nyaris otomatis, tapi query gabungan butuh composite index.

Kenalan · Apa itu Firestore

Database dokumen terkelola yang real-time

Firestore adalah document database terkelola (kamu tak mengurus server) dengan tiga sifat khas: real-time sync, offline-first, dan diakses langsung dari klien (browser/HP) dengan keamanan diatur oleh Security Rules.

// realtime

Sinkron otomatis

Pasang listener satu kali; setiap perubahan data langsung ter-push ke semua klien. Tak perlu polling atau WebSocket manual.

// offline

Offline-first

SDK menyimpan cache lokal. Aplikasi tetap jalan tanpa internet, lalu menyinkronkan saat online lagi.

// serverless

Tanpa server sendiri

Klien bicara langsung ke Firestore. Otorisasi diatur lewat Security Rules, bukan kode backend.

◆ Posisinya

Kalau MongoDB cocok untuk backend umum, Firestore bersinar saat kamu membangun aplikasi mobile/web yang butuh data hidup — chat, kolaborasi, notifikasi, dashboard live — dan ingin cepat rilis tanpa membangun infrastruktur.

Konsep · Struktur data

Collection, document, subcollection

Firestore menyusun data sebagai pohon yang berselang-seling: collection berisi document, dan tiap document bisa punya subcollection lagi di dalamnya. Inilah cara Firestore memodelkan one-to-many seperti chat room → pesan.

◆ Jalur (path) data di Firestore
Collectionrooms
Documentrooms/room_42
Subcollectionrooms/room_42/messages
Documentrooms/room_42/messages/msg_001

Pola: collection / document / collection / document … selalu bergantian. Pesan ditaruh di subcollection agar room tidak membengkak — beda gaya dari MongoDB yang sering meng-embed array di satu dokumen.

satu document di rooms/room_42/messagesJSON
{
  "teks":    "Halo, sudah sampai mana?",
  "dari":    "user_budi",
  "dibaca":  false,
  "waktu":   Timestamp("2026-06-28T09:12:00Z")
}
◆
Pilihan desain penting: embed (taruh data di dalam dokumen) vs subcollection (koleksi terpisah). Aturan praktis: kalau jumlah anak besar/tak terbatas (pesan chat, komentar) → subcollection. Kalau kecil & selalu dibaca bersama induk (alamat user) → embed.
◆ Operasi · Query

Mencari dengan where() & orderBy()

Query Firestore dirangkai dari where(), orderBy(), dan limit(). Ini jawaban untuk kebutuhan query pada kasus chat & katalog.

tulis & baca — Firebase Web SDK v9JS
import { collection, addDoc, query, where, orderBy, limit, getDocs }
  from "firebase/firestore";

// CREATE — kirim pesan baru ke subcollection
await addDoc(collection(db, "rooms/room_42/messages"), {
  teks: "Halo!", dari: "user_budi", dibaca: false, waktu: serverTimestamp()
});

// READ — pesan belum dibaca, terbaru dulu, maksimal 20
const q = query(
  collection(db, "rooms/room_42/messages"),
  where("dibaca", "==", false),
  orderBy("waktu", "desc"),
  limit(20)
);
const snap = await getDocs(q);
snap.forEach(d => console.log(d.id, d.data()));
◆ Operator where() yang tersedia

==, !=, <, <=, >, >=, in, not-in, array-contains (cek elemen di field array), array-contains-any. Untuk katalog: where("kategori", "in", ["buku","baju"]).

◆
Firestore tidak punya JOIN dan tidak ada query "cari teks bebas" seperti SQL LIKE '%kata%'. Filter rentang (<, >) juga hanya boleh pada satu field per query. Pencarian teks penuh? Sambungkan ke layanan seperti Algolia/Elasticsearch.
◆ Operasi · Real-time

onSnapshot(): data yang mengalir sendiri

Inilah fitur andalan Firestore. Ganti getDocs() (sekali ambil) dengan onSnapshot() (langganan): callback-mu dipanggil ulang setiap kali data yang cocok berubah — inilah yang membuat chat terasa instan.

listener real-time untuk chatJS
import { onSnapshot } from "firebase/firestore";

const unsub = onSnapshot(q, (snap) => {
  snap.docChanges().forEach((c) => {
    if (c.type === "added")    tampilkanPesan(c.doc.data());
    if (c.type === "modified") perbaruiPesan(c.doc.data());
    if (c.type === "removed")  hapusPesan(c.doc.id());
  });
});
// pesan baru dari user lain MUNCUL OTOMATIS — tanpa refresh ⚡

unsub(); // panggil saat komponen di-unmount agar hemat kuota
◆ Kenapa ini terasa ajaib

Tanpa Firestore, fitur "pesan muncul otomatis" butuh server WebSocket, manajemen koneksi, dan logika sinkronisasi. Firestore membungkus semua itu jadi satu fungsi onSnapshot() — termasuk menggabungkan perubahan dari cache offline saat koneksi pulih.

Indexing · Cara kerja

Index otomatis vs composite index

Indexing di Firestore berbeda total dari MongoDB. Di sini setiap field di-index otomatis — jadi query satu-field langsung jalan. Tapi query yang menggabungkan beberapa field butuh composite index yang kamu buat manual.

langsung jalan — index otomatisJS
// satu field saja → sudah ter-index
where("dibaca", "==", false)

// satu field + sort field yang sama
orderBy("waktu", "desc")

✅ tidak perlu setup apa pun
butuh composite indexJS
// filter 1 field + sort field LAIN
where("dibaca", "==", false)
orderBy("waktu", "desc")

❌ error sampai composite index dibuat
◆ Kabar baiknya

Saat query butuh composite index, Firestore menolak query & mencetak pesan error berisi link langsung ke Firebase Console untuk membuat index itu. Kamu tinggal klik — index dibuat otomatis dengan field yang tepat. Jadi kamu jarang perlu menebak.

◆ Analogi — perpustakaan yang rajin

Firestore seperti pustakawan yang otomatis membuat katalog untuk setiap atribut buku (judul, penulis, tahun). Pencarian satu atribut: instan. Tapi pencarian gabungan ("buku fiksi terbit setelah 2020, urut judul") butuh katalog silang khusus — itulah composite index yang harus kamu pesan dulu.

Indexing · Praktik

Membuat composite index

Dua cara: lewat link error (paling cepat) atau didefinisikan di file firestore.indexes.json lalu di-deploy (paling rapi untuk tim).

firestore.indexes.json — composite indexJSON
{
  "indexes": [
    {
      "collectionGroup": "messages",
      "queryScope":      "COLLECTION",
      "fields": [
        { "fieldPath": "dibaca", "order": "ASCENDING" },
        { "fieldPath": "waktu",  "order": "DESCENDING" }
      ]
    }
  ]
}
deploy via Firebase CLISH
# sekali deploy, index dibangun di sisi server
firebase deploy --only firestore:indexes
  • Urutan field di composite index harus cocok dengan urutan where() + orderBy() di query-mu.
  • Field equality (==) ditaruh sebelum field range/sort — pola yang sama dengan aturan ESR di MongoDB.
  • Index butuh waktu dibangun (beberapa menit untuk data besar); query-nya jalan setelah status "Enabled".
  • Kurangi index yang tak terpakai lewat index exemptions agar tulis lebih murah pada field yang tak pernah di-query.
⚙ Indexing · Batasan

Batas query yang wajib kamu tahu

Firestore sengaja membatasi query agar selalu cepat & murah berapa pun ukuran data — biaya query bergantung pada jumlah hasil, bukan jumlah total dokumen. Konsekuensinya, beberapa pola SQL tidak tersedia.

// Yang TIDAK bisa

  • JOIN antar collection.
  • Filter rentang (<,>) di lebih dari satu field.
  • Pencarian teks bebas (LIKE '%..%').
  • OR rumit lintas banyak field (terbatas).
  • Agregasi berat (hanya count/sum/avg dasar).

// Pola pengganti

  • Denormalisasi: salin field yang dibutuhkan.
  • Simpan field bantu (mis. tahun terpisah).
  • Sambungkan Algolia / Elasticsearch untuk search.
  • Pecah jadi beberapa query lalu gabung di klien.
  • Simpan counter yang dirawat lewat transaksi.
◆
Filosofi Firestore: query yang lambat dilarang sejak desain. Kalau sebuah pola terasa "tidak bisa", itu biasanya sinyal untuk mengubah bentuk data (denormalisasi) — bukan memaksa query yang akan mahal di skala besar.
Praktik · Kapan pakai

Firestore cocok untuk kasus apa

Polanya: aplikasi klien (mobile/web) yang butuh data hidup & cepat rilis, dengan relasi data yang sederhana.

// chat

Chat & pesan

Data per-room mandiri, sinkron real-time lewat onSnapshot. Contoh kasus langsung dari deck induk.

// kolaborasi

App kolaboratif

To-do bersama, papan tim, kursor live — semua peserta lihat perubahan seketika.

// mobile

Aplikasi mobile

Offline-first: jalan tanpa sinyal, sinkron saat online. Hemat membangun backend.

// MVP

Prototipe & startup

Auth, storage, hosting, DB dalam satu ekosistem Firebase. Cepat dari nol ke rilis.

// Pakai Firestore saat…

  • Butuh real-time / offline-first.
  • Klien (HP/web) akses DB langsung.
  • Ingin minim backend & cepat rilis.
  • Relasi data sederhana (sedikit JOIN).

// Pikir ulang saat…

  • Query analitik/agregasi kompleks.
  • Banyak JOIN & relasi many-to-many.
  • Pencarian teks jadi fitur inti.
  • Butuh kontrol penuh / hindari vendor lock-in.
◆ Harga · Trade-off

Yang kamu dapat & yang kamu korbankan

Firestore menukar fleksibilitas query demi kecepatan, real-time, & kesederhanaan operasional. Untuk kelas aplikasi yang tepat, itu pertukaran yang sangat menguntungkan.

// Yang kamu dapat

  • Real-time & offline gratis dari SDK.
  • Indexing dasar otomatis.
  • Skala otomatis, tanpa kelola server.
  • Security Rules → akses langsung dari klien.
  • Terintegrasi dengan Auth, Storage, Hosting.

// Yang kamu korbankan

  • Query terbatas (no JOIN, satu range field).
  • Composite index manual untuk query gabungan.
  • Biaya dihitung per operasi baca/tulis/hapus.
  • Vendor lock-in ke ekosistem Google.
  • Denormalisasi → tanggung jawab konsistensi pindah ke kode.
◆ Catatan biaya

Tagihan Firestore mengikuti jumlah operasi dokumen (read/write/delete), bukan ukuran query. Pola seperti listener yang lupa di-unsub() atau membaca seluruh collection berulang bisa membengkakkan biaya. Rancang query yang spesifik & pakai limit().

Penutup

Firestore dalam satu tarikan napas

Susun data sebagai pohon collection/document, query dengan where + orderBy, dengarkan perubahan lewat onSnapshot, dan biarkan indexing otomatis — sambil membuat composite index untuk query gabungan.

  • Collection / Document / Subcollection — pohon bergantian.
  • Query = where + orderBy + limit — tanpa JOIN, satu range field.
  • onSnapshot = real-time — data ter-push otomatis ke klien.
  • Index single otomatis — gabungan butuh composite index.
  • Batas query = fitur — memaksa data tetap cepat & murah.
  • Pilih untuk app klien real-time — bukan untuk analitik berat.

Langkah belajar berikutnya

Buat proyek gratis di Firebase Console, aktifkan Firestore (mode test), lalu dari web app sederhana: addDoc() beberapa pesan → pasang onSnapshot() dan lihat update real-time di dua tab → buat query where + orderBy dan ikuti link error untuk membuat composite index pertamamu. Satu putaran itu mengajarkan inti Firestore.
