// Data Structures & Algorithms — struktur khusus untuk string

Cari kata secepat membaca hurufnya, bukan sebanyak jumlah katanya.

Hash table bisa bilang "kata ini ada", tapi tidak bisa menjawab "kata apa saja yang diawali huruf ini?" secara efisien. Trie (dibaca "try", dari kata retrieval) adalah tree khusus untuk string: tiap node mewakili satu karakter, dan jalur dari root ke node itu adalah sebuah prefix. Deck ini buat pemula — dari kenapa trie lahir, konsep inti-nya, autocomplete, sampai kapan dipakai di production, diselingi kutipan dari buku rujukan.

Sakit
Hash table buta prefix — tidak ada konsep "urutan" antar key
Ide
Satu node = satu karakter — path root→node menyusun sebuah prefix
Untung
O(L), bukan O(N) — waktu cari cuma tergantung panjang kata

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya jutaan kata tersimpan (kamus, katalog produk, daftar kontak) di hash table, dan fitur autocomplete/spell-checker harus jalan saat user mengetik.

When — user mengetik prefix "pro", lalu "prod", lalu "produ" — tiap keystroke sistem harus menampilkan semua kata berawalan itu, secara instan.

Then — hash table cuma bisa jawab "kata lengkap ini ada atau tidak"; ia tidak punya konsep kedekatan prefix, jadi kamu terpaksa scan seluruh dataset (O(N×L)) tiap kali huruf berubah — lambat dan tidak scalable.

→ makanya kita pakai Trie.

Akar masalah · Hash table buta prefix

Hash table tahu "ada", tapi tidak tahu "urutan"

Autocomplete & spell-checker butuh menjawab pertanyaan: "kata apa saja yang diawali huruf ini?" Hash table mengubah key jadi angka acak lewat fungsi hash — dua string yang miripnya cuma satu huruf ("halo" vs "halo2") bisa mendarat di slot yang jauh berbeda. Tidak ada jejak "kedekatan prefix" yang bisa ditelusuri.

◆ Analogi — kamus tersusun per huruf awal

Kamus fisik disusun berdasarkan huruf awal: semua kata berawalan "ha" berdekatan halamannya. Kamu bisa buka satu halaman dan langsung lihat semua kata dengan awalan itu. Hash table itu seperti melempar tiap kata ke rak acak berdasarkan "kode rahasia" — cepat kalau tahu persis kata lengkapnya, tapi mustahil bilang "tunjukkan semua yang berawalan X" tanpa memeriksa seluruh rak satu per satu.

Trie — namanya dari kata retrieval — dirancang khusus untuk string, dan waktu operasinya tidak bergantung pada berapa banyak string yang tersimpan, hanya pada panjang string yang dicari.

— parafrase dari Robert Sedgewick & Kevin Wayne, Algorithms

Itulah properti yang tidak dimiliki hash table maupun binary search tree: keduanya tetap terpengaruh oleh N (jumlah data tersimpan) — entah lewat collision, resize, atau kedalaman pohon. Trie melepaskan diri dari N sepenuhnya; ia hanya peduli pada L, panjang string yang sedang dicari.

Konsep inti · Node, path & isEnd

Tiap node = satu karakter, path = prefix

Trie adalah tree berakar (root) tanpa isi karakter. Tiap edge menuju anak diberi label satu karakter, sehingga jalur dari root ke sebuah node menyusun sebuah prefix. Setiap node juga punya flag isEnd — penanda "sampai di sini, ada kata utuh yang berakhir".

◆ Contoh — trie berisi "cat", "car", "card"
root→ c
c→ a
ca→ t (isEnd) , r (isEnd)
car→ d → isEnd

Node ca-r punya dua peran sekaligus: ia isEnd = true (karena "car" adalah kata utuh) dan punya anak d (menuju "card"). Ini yang bikin trie bisa menyimpan kata yang saling menjadi prefix satu sama lain.

Trie adalah sebuah pohon pencarian digital (digital search tree) yang mengeksploitasi struktur internal dari key itu sendiri — urutan karakternya — alih-alih membandingkan key secara utuh seperti pada pohon pencarian biner.

— parafrase dari Donald Knuth, The Art of Computer Programming
Trie.java — insert & search dasarJAVA
class TrieNode {
    Map<Character, TrieNode> children = new HashMap<>();
    boolean isEnd = false;
}

class Trie {
    private final TrieNode root = new TrieNode();

    // insert: O(L), L = panjang kata
    public void insert(String word) {
        TrieNode node = root;
        for (char ch : word.toCharArray()) {
            node = node.children.computeIfAbsent(ch, k -> new TrieNode());
        }
        node.isEnd = true;
    }

    // search: O(L) juga, tidak peduli berapa ribu kata lain tersimpan
    public boolean search(String word) {
        TrieNode node = find(word);
        return node != null && node.isEnd;
    }

    private TrieNode find(String s) {
        TrieNode node = root;
        for (char ch : s.toCharArray()) {
            node = node.children.get(ch);
            if (node == null) return null;
        }
        return node;
    }
}
Kekuatan utama · startsWith & autocomplete

Cari SEMUA kata dengan prefix tertentu

Di sinilah trie unggul telak dibanding hash table: tinggal jalan ke node prefix (O(L)), lalu DFS ke semua sub-tree di bawahnya untuk mengumpulkan tiap node yang isEnd = true. Hash table harus memeriksa setiap key satu per satu.

Set<String> kamus = new HashSet<>(); // isi ribuan kata

List<String> hasil = new ArrayList<>();
for (String kata : kamus) {
    if (kata.startsWith("ca")) hasil.add(kata);
}

trie — cari kata berawalan "ca"JAVA
public List<String> autocomplete(String prefix) {
    List<String> hasil = new ArrayList<>();
    TrieNode node = find(prefix);      // O(L)
    if (node == null) return hasil;
    collect(node, new StringBuilder(prefix), hasil);
    return hasil;
}

private void collect(TrieNode n, StringBuilder jalur, List<String> out) {
    if (n.isEnd) out.add(jalur.toString());
    for (var e : n.children.entrySet()) {
        jalur.append(e.getKey());
        collect(e.getValue(), jalur, out);
        jalur.deleteCharAt(jalur.length() - 1);
    }
}
// 🚀 cuma jelajahi sub-tree "ca", tidak sentuh cabang lain sama sekali

Bedanya makin terasa saat kamusnya besar: hash table butuh O(N) untuk prefix search (periksa semua key), trie hanya butuh O(L + K) di mana K adalah jumlah kata yang cocok. Karena node prefix-nya dipakai bersama (shared) oleh banyak kata, trie juga otomatis mengelompokkan kata-kata yang mirip — persis seperti halaman kamus.

◆ Praktik · Cara mengimplementasi dengan benar

Best practice implementasi trie

Trie sederhana untuk dipahami, tapi pilihan implementasinya berdampak besar ke performa & memori. Beberapa hal yang perlu dipikirkan sebelum ngoding:

  1. Pakai array[26] kalau charset-nya cuma lowercase a–z dan performa penting — akses index array jauh lebih cepat & hemat memori daripada HashMap<Character, TrieNode>, karena tidak ada overhead hashing/boxing.
  2. Pakai HashMap atau Map<Character,·> kalau charset besar — Unicode, emoji, atau campuran huruf besar/kecil & simbol. Array 26 slot jadi tidak cukup atau boros kalau charset-nya jarang dipakai penuh.
  3. Simpan jumlah kata yang lewat tiap node (count) kalau butuh fitur seperti "berapa banyak kata berawalan X" tanpa harus DFS penuh setiap kali.
  4. Kompres trie jadi radix tree (compressed trie) untuk hemat memori — gabungkan rantai node yang cuma punya satu anak jadi satu edge berlabel string, bukan satu node per karakter.
  5. Hati-hati soal case sensitivity — putuskan di awal apakah "Cat" dan "cat" dianggap sama; kalau ya, normalisasi (toLowerCase()) sebelum insert/search, jangan di tengah jalan.
  6. Pertimbangkan trade-off delete — menghapus kata dari trie berarti menyusuri ulang, set isEnd = false, dan (opsional) membuang node yang jadi daun tak terpakai. Kalau delete jarang terjadi, sering lebih simpel biarkan node "mati" tetap ada.

◆ Harga · Tidak ada makan siang gratis

Trade-off: trie vs hash table

Trie tidak menggantikan hash table — keduanya menang di skenario berbeda. Pilih berdasarkan jenis query yang paling sering kamu lakukan.

// Trie

  • Prefix search super cepat & terstruktur — O(L).
  • Node prefix dipakai bersama → hemat untuk kata-kata mirip.
  • Waktu operasi tidak tergantung jumlah kata tersimpan.
  • Cocok untuk data yang berbentuk urutan karakter.

// Hash table

  • Butuh O(N) untuk prefix search — periksa semua key.
  • Tidak ada struktur "kedekatan" antar key.
  • Tidak cocok kalau butuh urutan / range / prefix.
  • Tapi lookup exact-match rata-rata O(1), sering lebih ringkas.
◆ Catatan soal memori

Harga yang dibayar trie: overhead memori per karakter. Tiap node butuh referensi ke anak-anaknya (array atau map), jadi menyimpan satu kata panjang bisa memakan lebih banyak memori dibanding satu entry hash table. Untuk dataset besar dengan banyak kata mirip, ini sering sepadan — untuk dataset kecil/acak, hash table biasanya lebih hemat.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai trie

Aturan praktisnya: kalau query utamamu soal prefix — "kata apa saja yang diawali X" — pilih trie. Kalau cuma butuh "apakah X ada", hash table biasanya sudah cukup dan lebih hemat memori.

// Pakai trie saat…

  • Butuh autocomplete / suggestion berbasis prefix.
  • Bikin spell checker atau validasi kata.
  • Banyak kata berbagi prefix yang sama (efisien memori bersama).
  • Butuh longest-prefix-match (IP routing, dsb).
  • Multi-pattern string matching (Aho–Corasick).

// Jangan, pakai hash table saat…

  • Cuma butuh exact-match lookup ("apakah X ada?").
  • Key-nya bukan string / tidak punya struktur urutan.
  • Dataset kecil & random, overhead node tidak sepadan.
  • Memori sangat terbatas & kata-kata jarang berbagi prefix.
◆ Pertanyaan penentu

Tanyakan satu hal: "Apakah aku sering butuh SEMUA kata dengan awalan tertentu, bukan cuma satu kata spesifik?" Kalau ya → trie. Kalau kamu hanya perlu tahu satu kata itu ada atau tidak, tanpa peduli hubungan prefix-nya dengan kata lain → hash table sudah cukup dan lebih ringan.

Trie (dan turunannya) di production

Tiga skenario nyata di mana ide dasar trie — menyusuri karakter demi karakter untuk mencocokkan prefix — jadi solusi inti.

// search & mobile

Autocomplete & keyboard mobile

Kasus: search engine & keyboard di HP menyarankan kata/kueri saat kamu baru mengetik beberapa huruf. Kenapa trie: setiap ketukan tambahan cukup turun satu level node, tidak perlu mencari ulang dari awal.

// text editor

Spell checker

Kasus: aplikasi pengolah kata & editor kode menandai kata yang tidak ada di kamus. Kenapa trie: cek keberadaan kata & cari kata terdekat (mirip) sama-sama bisa memanfaatkan struktur prefix yang sama.

// jaringan

IP routing table

Kasus: router jaringan harus memilih rute terbaik untuk sebuah alamat IP tujuan. Kenapa mirip trie: teknik longest prefix matching secara konseptual menyusuri bit/segmen alamat IP layaknya menyusuri karakter di trie, mencari kecocokan prefix terpanjang.

◆ Benang merahnya

Ketiganya sama-sama menyusuri data karakter/segmen demi segmen dan memanfaatkan kenyataan bahwa banyak entri berbagi awalan yang sama. Begitu pola aksesnya bergeser ke "cari satu key spesifik tanpa peduli awalannya", struktur seperti hash table biasanya lebih sederhana & cukup.

Penutup

Trie: bayar memori demi kecepatan prefix

Trie lahir dari satu kebutuhan spesifik yang tidak bisa dijawab hash table: mencari semua string dengan prefix tertentu, secepat mungkin. Ia bersinar saat query-mu tentang prefix, dan jadi berlebihan saat kamu cuma butuh exact-match biasa.

  • Node = karakter — path root→node menyusun sebuah prefix.
  • isEnd — penanda "di sini berakhir sebuah kata utuh".
  • O(L), bukan O(N) — waktu operasi lepas dari jumlah kata tersimpan.
  • Kuat di prefix search — autocomplete, spell checker, longest-prefix-match.
  • Harganya memori — tiap karakter butuh node & referensi sendiri.
  • Pilih dari jenis query — prefix-heavy → trie, exact-match saja → hash table.

Lanjut ke Union-Find

Trie menuntaskan soal pencarian string berbasis prefix. Struktur berikutnya, Union-Find (Disjoint Set), menuntaskan soal yang sama sekali berbeda: melacak dengan cepat elemen mana yang "satu kelompok" dengan elemen lain — dasar dari algoritma Kruskal, deteksi cycle, dan network connectivity.
