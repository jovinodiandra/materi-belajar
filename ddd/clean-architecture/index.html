Domain-Driven Design & Clean Architecture

Kumpulan catatan terstruktur — dari building block dasar DDD, strategic design, prinsip Clean Architecture, sampai topik lanjutan (CQRS, Event Sourcing, Saga) — ditutup dengan tiga studi kasus yang dikerjakan penuh dengan kode.

SHEET 00

Cara pakai dokumen ini

Dokumen ini disusun seperti satu set gambar kerja arsitek: setiap topik adalah satu sheet bernomor, bukan bab yang harus dibaca berurutan. Gunakan panel di kiri untuk lompat langsung ke topik yang dibutuhkan.

Setiap sheet punya penanda level seperti ini:

Level Menengah

Tiga contoh kasus di bagian akhir (CS·01–CS·03) memakai satu domain yang sama secara bertahap — e-commerce order — supaya konsep yang dipelajari di sheet fundamental langsung terlihat dipakai nyata, sebelum masuk ke dua kasus tambahan (ledger & ride-hailing) untuk pola yang tidak muncul di kasus pertama.

✎ Catatan kata milikmu sendiri
Setiap kata di seluruh teks (kecuali di dalam blok kode) bisa dicatat. Nemu istilah asing (mis. invariant, idempotent)? Klik kata itu untuk menulis penjelasan versimu sendiri. Butuh mencatat frasa lebih dari satu kata (mis. upstream context)? Klik-tahan lalu geser (drag) melewati kata-kata itu, baru lepas. Teks aslinya tidak pernah diubah — proses ini cuma menandai kata yang sudah ada, tidak memotong atau menyisipkan apa pun. Kata/frasa yang sudah dicatat akan bergaris bawah putus-putus; arahkan kursor (hover) ke situ kapan saja untuk memunculkan catatanmu lagi, di mana pun kata/frasa yang sama itu muncul lagi di dokumen. Semua catatan tersimpan otomatis di browser ini — buka tombol "✎ Catatanku" di pojok kiri bawah untuk melihat semua catatan sekaligus, atau meng-export/import-nya sebagai file JSON untuk cadangan.
DDD · 01

Masalah yang diselesaikan DDD

Level Dasar

Domain-Driven Design (Eric Evans, 2003) bukan tentang pola kode tertentu — ia adalah cara berpikir untuk sistem dengan kompleksitas bisnis yang tinggi, bukan sekadar kompleksitas teknis. Masalah yang dijawab: aplikasi besar perlahan berubah jadi "big ball of mud" karena logika bisnis tersebar di controller, service, dan query SQL, sementara istilah yang dipakai developer tidak lagi sama dengan istilah yang dipakai orang bisnis.

Dua sisi DDD

  • Strategic design — cara membagi sistem besar menjadi bounded context yang masing-masing punya model dan bahasa sendiri (lihat DDD·09).
  • Tactical design — building block untuk memodelkan satu bounded context: Entity, Value Object, Aggregate, Domain Event, Repository (lihat DDD·03–DDD·08).
Kapan DDD layak dipakai
Cocok untuk domain dengan aturan bisnis kompleks dan sering berubah (order management, perbankan, insurance, logistik). Untuk CRUD sederhana tanpa banyak invariant, DDD penuh biasanya overkill — cukup pakai transaction script.
DDD · 02

Ubiquitous Language

Level Dasar

Bahasa yang sama, dipakai konsisten oleh domain expert, product manager, dan developer — di percakapan, di dokumentasi, dan di kode (nama class, method, variabel). Kalau tim bisnis bicara "submit order" tapi kode menulis process(), setiap terjemahan bolak-balik itu adalah celah tempat bug dan kesalahpahaman bersembunyi.

Praktik
Ubiquitous language tidak global untuk seluruh perusahaan — ia berlaku per bounded context. Kata "Customer" di Sales context bisa punya atribut dan makna berbeda dari "Customer" di Billing context. Ini bukan inkonsistensi, ini justru inti dari bounded context.
DDD · 03

Entity

Level Dasar

Objek yang punya identitas yang bertahan sepanjang waktu, terlepas dari perubahan atributnya. Dua Order dengan isi field yang sama persis tetap dianggap berbeda kalau id-nya berbeda; sebaliknya satu Order yang atributnya berubah (status, total) tetap dianggap "entity yang sama".

OrderLine.java
public class OrderLine {
  private final ProductId productId;
  private int quantity;
  private final Money unitPrice;

  public OrderLine(ProductId productId, int quantity, Money unitPrice) {
    this.productId = productId;
    this.quantity = quantity;
    this.unitPrice = unitPrice;
  }

  public Money getSubtotal() {
    return unitPrice.multiply(quantity);
  }

  public void changeQuantity(int next) {
    if (next <= 0) {
      throw new IllegalArgumentException("Kuantitas harus lebih dari 0");
    }
    this.quantity = next;
  }
}

OrderLine di sini adalah entity lokal — identitasnya hanya bermakna di dalam aggregate Order, tidak punya repository sendiri. Entity yang jadi pintu masuk aggregate disebut Aggregate Root (DDD·05).

DDD · 04

Value Object

Level Dasar

Objek yang didefinisikan sepenuhnya oleh nilai atributnya, tanpa identitas. Dua Money senilai 50000 IDR dianggap sama persis. Value object bersifat immutable — operasi yang "mengubah" selalu mengembalikan instance baru — dan idealnya melindungi invariant-nya sendiri di constructor, sehingga objek yang sudah dibuat pasti valid.

Money.java
public final class Money {
  private final long amount;
  private final String currency;

  private Money(long amount, String currency) {
    if (amount < 0) {
      throw new IllegalArgumentException("Money tidak boleh negatif");
    }
    if (!currency.matches("[A-Z]{3}")) {
      throw new IllegalArgumentException("Kode currency tidak valid");
    }
    this.amount = amount;
    this.currency = currency;
  }

  public static Money of(long amount, String currency) {
    return new Money(amount, currency);
  }

  public Money add(Money other) {
    assertSameCurrency(other);
    return Money.of(this.amount + other.amount, this.currency);
  }

  @Override
  public boolean equals(Object obj) {
    if (!(obj instanceof Money other)) return false;
    return this.amount == other.amount && this.currency.equals(other.currency);
  }

  private void assertSameCurrency(Money other) {
    if (!this.currency.equals(other.currency)) {
      throw new IllegalStateException(
        "Tidak bisa menjumlahkan " + this.currency + " dengan " + other.currency);
    }
  }
}
Kenapa ini penting
Tanpa Money sebagai value object, aturan "jangan campur currency" akan diulang-ulang di setiap tempat yang menjumlahkan angka — dan cepat atau lambat ada satu tempat yang lupa memvalidasinya.
DDD · 05

Aggregate & Aggregate Root

Level Menengah

Aggregate adalah klaster entity dan value object yang diperlakukan sebagai satu unit konsistensi transaksional. Hanya Aggregate Root yang punya identitas global dan boleh diakses dari luar; semua perubahan pada objek di dalam aggregate wajib lewat root, supaya invariant selalu terjaga.

ROOTSatu-satunya pintu masuk publik ke aggregate.
INTERNAL ENTITYPunya identitas lokal, tak boleh diakses langsung dari luar.
VALUE OBJECTBagian dari state internal, tanpa identitas sendiri.
REFERENCE BY IDAggregate lain hanya disimpan sebagai ID, bukan objek penuh.
Order.java
public class Order {
  private final OrderId id;
  private final CustomerId customerId;
  private final List<OrderLine> lines = new ArrayList<>();
  private OrderStatus status = OrderStatus.DRAFT;
  private final List<DomainEvent> events = new ArrayList<>();

  private Order(OrderId id, CustomerId customerId) {
    this.id = id;
    this.customerId = customerId;
  }

  public static Order start(OrderId id, CustomerId customerId) {
    return new Order(id, customerId);
  }

  public void addLine(ProductId productId, int quantity, Money unitPrice) {
    assertDraft();
    lines.add(new OrderLine(productId, quantity, unitPrice));
  }

  public void submit() {
    assertDraft();
    if (lines.isEmpty()) {
      throw new IllegalStateException("Order tidak boleh disubmit tanpa item");
    }
    this.status = OrderStatus.SUBMITTED;
    events.add(new OrderSubmitted(this.id, total()));
  }

  public Money total() {
    return lines.stream()
      .map(OrderLine::getSubtotal)
      .reduce(Money.of(0, "IDR"), Money::add);
  }

  public List<DomainEvent> pullEvents() {
    List<DomainEvent> pending = new ArrayList<>(events);
    events.clear();
    return pending;
  }

  private void assertDraft() {
    if (status != OrderStatus.DRAFT) {
      throw new IllegalStateException("Order yang sudah disubmit tidak bisa diubah");
    }
  }
}
Aturan emas
Satu transaksi database = satu aggregate. Kalau terasa perlu mengubah dua aggregate sekaligus secara atomik, itu sinyal aggregate-nya salah digambar — lihat ADV·05.
DDD · 06

Domain Event

Level Menengah

Fakta yang telah terjadi di domain, dinyatakan dalam bentuk lampau: OrderSubmitted, bukan SubmitOrder (itu command). Aggregate root mengumpulkan event yang terjadi selama satu operasi, lalu memublikasikannya setelah state berhasil disimpan — sehingga bounded context lain, atau bagian lain dari sistem yang sama, bisa bereaksi tanpa aggregate asal perlu tahu siapa yang mendengarkan.

DomainEvent.java + OrderSubmitted.java
public interface DomainEvent {
  Instant occurredAt();
}

public record OrderSubmitted(OrderId orderId, Money total, Instant occurredAt)
    implements DomainEvent {

  public OrderSubmitted(OrderId orderId, Money total) {
    this(orderId, total, Instant.now());
  }
}
Domain event vs integration event
Domain event beredar di dalam satu bounded context (in-process, sinkron). Kalau event yang sama perlu diketahui bounded context lain, ia biasanya diterjemahkan jadi integration event yang dikirim lewat message broker — dengan skema yang stabil dan sengaja dipisahkan dari model internal, supaya perubahan model domain tidak langsung mematahkan konsumer eksternal.
DDD · 07

Domain Service & Application Service

Level Menengah

Dua jenis "service" yang sering tertukar:

  • Domain service — logika bisnis yang secara alami tidak milik satu entity/VO saja, misalnya PricingPolicy.calculateDiscount(order, customer) yang butuh dua aggregate. Tetap murni domain, tanpa I/O.
  • Application service (use case) — mengorkestrasi satu skenario: ambil aggregate dari repository, panggil method domain, simpan lagi, publikasikan event. Tidak berisi aturan bisnis, hanya alur.
SubmitOrderUseCase.java
public class SubmitOrderUseCase {
  private final OrderRepository orders;
  private final DomainEventBus bus;

  public SubmitOrderUseCase(OrderRepository orders, DomainEventBus bus) {
    this.orders = orders;
    this.bus = bus;
  }

  public void execute(SubmitOrderCommand command) {
    Order order = orders.findById(command.orderId())
        .orElseThrow(() -> new OrderNotFoundException(command.orderId()));

    order.submit();
    orders.save(order);

    for (DomainEvent event : order.pullEvents()) {
      bus.publish(event);
    }
  }
}
DDD · 08

Repository & Factory

Level Menengah

Repository memberi ilusi koleksi in-memory untuk aggregate — findById, save — sambil menyembunyikan detail penyimpanan. Selalu satu repository per aggregate root, bukan per tabel. Interface-nya didefinisikan di layer domain (ia adalah sebuah port); implementasinya ada di infrastructure (adapter) — lihat CA·01.

OrderRepository.java — port (domain layer)
public interface OrderRepository {
  OrderId nextId();
  Optional<Order> findById(OrderId id);
  void save(Order order);
}

Factory dipakai saat pembuatan aggregate cukup rumit sehingga tidak pantas ditaruh di constructor biasa — misalnya butuh menggabungkan beberapa parameter dan invariant lintas objek sebelum aggregate boleh "lahir" dalam keadaan valid.

DDD · 09

Bounded Context

Level Menengah

Batas eksplisit (biasanya = batas layanan/deploy unit) di mana satu model domain dan satu ubiquitous language berlaku konsisten. Di luar batas ini, istilah yang sama boleh berarti lain. Bounded context adalah alat membelah kompleksitas, bukan alat membelah database secara sembarangan — pembelahannya mengikuti perbedaan model dan bahasa bisnis, bukan tabel.

Sinyal butuh bounded context baru
Tim mulai menambahkan flag if (context === 'x') di model yang sama untuk menangani makna berbeda, atau satu entity punya lebih dari 20 atribut karena melayani beberapa "kepentingan" sekaligus.
DDD · 10

Context Mapping

Level Lanjut

Context map menggambarkan relasi kekuasaan dan integrasi antar bounded context — siapa mengikuti model siapa, dan lewat mekanisme apa.

ORDERINGCore domain — tempat keunggulan kompetitif dimodelkan paling detail.
CONFORMIST / CUSTOMER-SUPPLIEROrdering mengikuti model upstream apa adanya, atau upstream menyesuaikan demi downstream.
ANTI-CORRUPTION LAYERPayment eksternal diterjemahkan lewat lapisan penerjemah — lihat ADV·04.
OHS / PUBLISHED LANGUAGEShipping mengekspos API stabil + skema publik untuk dikonsumsi banyak context.
PolaKapan dipakai
PartnershipDua tim bergantung erat, sukses/gagal bersama; koordinasi rilis dilakukan manual bersama.
Shared KernelDua context sengaja berbagi sebagian kecil model/kode; perubahan butuh koordinasi eksplisit — dipakai hemat-hemat.

Big Ball of Mud (anti-pattern)Bukan pola yang dipilih, tapi kondisi yang dikenali: batas tidak jelas, model campur aduk — tandai untuk dipisah bertahap.
DDD · 11

Subdomain: Core, Supporting, Generic

Level Menengah

Klasifikasi ini menentukan ke mana effort tim dialokasikan — jangan investasi tactical design penuh di tempat yang tidak butuh.

  • Core domain — sumber keunggulan kompetitif; layak dimodelkan detail, dibangun in-house, terus dirawat (mis. algoritma pricing/matching).
  • Supporting subdomain — perlu ada, spesifik untuk bisnis ini, tapi bukan diferensiator (mis. manajemen katalog internal).
  • Generic subdomain — masalah yang sudah dipecahkan industri; beli/pakai off-the-shelf, jangan dibangun sendiri (mis. autentikasi, pengiriman email).
CA · 01

The Dependency Rule

Level Dasar

Inti Clean Architecture (Robert C. Martin) dalam satu kalimat: source code dependency hanya boleh menunjuk ke dalam — ke arah kebijakan yang lebih abstrak dan lebih stabil. Lapisan luar (framework, database, UI) boleh tahu tentang lapisan dalam (aturan bisnis); lapisan dalam tidak boleh tahu apa-apa tentang lapisan luar.

◆ Buat apa ini? Kenapa pakai ini?

Given — business logic bercampur langsung dengan kode framework/database (query SQL & aturan diskon jadi satu file, atau entity meng-import ORM).

When — framework atau database itu perlu diganti/di-upgrade (misalnya pindah ORM, ganti provider cloud, atau migrasi versi framework besar).

Then — business logic ikut rusak & harus ditulis ulang, padahal aturan bisnisnya sendiri tidak berubah sama sekali.

→ makanya kita pakai Clean Architecture: pisahkan logika bisnis dari detail teknis, supaya detail boleh berganti tanpa menyentuh aturan bisnis.

ENTITIESAturan bisnis paling umum & stabil — setara "domain layer" di DDD.
USE CASESAturan bisnis spesifik aplikasi — application service / orchestration.
INTERFACE ADAPTERSController, presenter, gateway — menerjemahkan data ke/dari use case.
FRAMEWORKS & DRIVERSWeb framework, DB, UI — detail yang paling mudah diganti.
Konsekuensi praktis
Kalau file di layer domain/ meng-import package ORM, HTTP framework, atau SDK cloud provider manapun — Dependency Rule sudah dilanggar, walau testnya masih hijau.
CA · 02

Empat Lapisan

Level Menengah
LapisanIsiPadanan di DDD

Data yang menyeberang batas lapisan sebaiknya berupa struktur data sederhana (DTO/plain object), bukan objek domain yang dibawa mentah — supaya lapisan luar tidak diam-diam bergantung pada bentuk internal aggregate.

CA · 03

Hexagonal vs Onion vs Clean Architecture

Level Lanjut

Tiga nama, satu prinsip inti yang sama: pisahkan logika bisnis dari detail teknis, dan pastikan dependency menunjuk ke arah logika bisnis. Bedanya hanya penekanan istilah.

NamaDiperkenalkanPenekanan istilah
Hexagonal (Ports & Adapters)Alistair Cockburn"Port" (interface) di dalam, "adapter" (implementasi) di luar. Sisi hexagon melambangkan banyaknya jenis adapter (HTTP, CLI, test) yang setara — bukan angka enam yang penting.
Onion ArchitectureJeffrey PalermoMenekankan lapisan konsentris eksplisit dan bahwa domain model ada di pusat, tanpa dependency keluar sama sekali.
Clean ArchitectureRobert C. MartinMerangkum keduanya + menambahkan Use Case sebagai lapisan eksplisit, dan menamai aturan intinya "The Dependency Rule".

Praktiknya: Port (istilah hexagonal) di kode Clean Architecture adalah interface repository/gateway yang didefinisikan di layer domain/use case — persis OrderRepository di DDD·08. Adapter adalah implementasi konkretnya di layer infrastructure.

CA · 04

Menyatukan DDD + Clean Architecture

Level Lanjut

DDD menjawab apa yang dimodelkan (bounded context, aggregate, ubiquitous language). Clean Architecture menjawab di mana kode itu ditaruh dan ke arah mana ia boleh bergantung. Keduanya saling melengkapi, bukan bersaing — satu bounded context biasanya jadi satu modul/service dengan struktur folder Clean Architecture di dalamnya.

struktur package — satu bounded context
src/main/java/com/shop/order/
  domain/                       // Entities — zero framework import
    Order.java
    OrderLine.java
    Money.java
    OrderRepository.java        // port (interface saja)
    events/
      OrderSubmitted.java
  application/                  // Use cases
    SubmitOrderUseCase.java
    SubmitOrderCommand.java
  infrastructure/                // Adapters
    PostgresOrderRepository.java
    OrderMapper.java
  interfaces/                   // Controllers/HTTP
    OrderController.java
PostgresOrderRepository.java — adapter
public class PostgresOrderRepository implements OrderRepository {
  private final JdbcClient db;

  public PostgresOrderRepository(JdbcClient db) {
    this.db = db;
  }

  @Override
  public OrderId nextId() {
    return OrderId.newId();
  }

  @Override
  public Optional<Order> findById(OrderId id) {
    return db.query("select * from orders where id = ?", id.value())
        .map(OrderMapper::toDomain);
  }

  @Override
  public void save(Order order) {
    var row = OrderMapper.toRow(order);
    db.upsert("orders", row);
  }
}
Cara verifikasi cepat
Aturan ini bisa ditegakkan otomatis di Java memakai ArchUnit: noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("..infrastructure..", "..interfaces.."). Kalau package domain mengimpor Spring, JPA, atau SDK cloud provider manapun, build gagal di CI — Dependency Rule benar-benar terjaga, bukan sekadar konvensi di kepala tim.
ADV · 01

CQRS

Level Lanjut

Command Query Responsibility Segregation: pisahkan jalur tulis (lewat aggregate, menegakkan invariant) dari jalur baca (query langsung ke model baca yang dioptimalkan, boleh berupa view/proyeksi denormalisasi). Aggregate dirancang untuk konsistensi menulis, bukan untuk melayani laporan lintas-aggregate yang butuh join berat — memaksakan keduanya lewat model yang sama biasanya berujung pada aggregate yang gemuk oleh method read-only.

Bukan wajib all-or-nothing
CQRS bisa diterapkan ringan (query langsung ke DB read-only tanpa lewat repository aggregate) sampai berat (model baca terpisah di database berbeda, disinkron lewat domain event). Mulai dari versi ringan; tingkatkan hanya kalau ada bukti kebutuhan skala/performa.
ADV · 02

Event Sourcing

Level Lanjut

Alih-alih menyimpan state akhir aggregate, simpan urutan event yang menyebabkan state itu terjadi. State saat ini didapat dengan me-replay semua event dari awal (atau dari snapshot terakhir). Cocok untuk domain yang butuh audit trail lengkap dan sering perlu menjawab "kenapa angka ini jadi begini" — akuntansi, ledger, perbankan.

Account.java — event-sourced aggregate
public class Account {
  private Money balance = Money.of(0, "IDR");
  private int version = 0;

  public static Account rehydrate(List<DomainEvent> events) {
    Account account = new Account();
    for (DomainEvent e : events) {
      account.apply(e);
    }
    return account;
  }

  private void apply(DomainEvent event) {
    if (event instanceof FundsDeposited e) {
      this.balance = this.balance.add(e.amount());
    }
    if (event instanceof FundsWithdrawn e) {
      this.balance = this.balance.subtract(e.amount());
    }
    this.version++;
  }

  public FundsWithdrawn withdraw(Money amount) {
    if (this.balance.lessThan(amount)) {
      throw new IllegalStateException("Saldo tidak mencukupi");
    }
    FundsWithdrawn event = new FundsWithdrawn(amount);
    apply(event);
    return event;
  }
}
Biaya tersembunyi
Event sourcing menambah kompleksitas nyata: skema event harus dijaga backward-compatible selamanya, butuh strategi snapshot untuk aggregate berumur panjang, dan query "state saat ini" jadi tidak trivial tanpa proyeksi baca terpisah (lihat CQRS). Jangan pilih ini hanya karena terdengar canggih.
ADV · 03

Saga / Process Manager

Level Lanjut

Karena satu transaksi hanya boleh menyentuh satu aggregate (DDD·05), alur bisnis yang melibatkan beberapa aggregate/bounded context — mis. reservasi driver → otorisasi pembayaran → konfirmasi ride — dikoordinasikan lewat saga: rangkaian langkah lokal, masing-masing dengan compensating action untuk membatalkan efek langkah sebelumnya bila ada kegagalan di tengah jalan.

RideBookingSaga.java
public class RideBookingSaga {
  private final CommandBus commands;

  public RideBookingSaga(CommandBus commands) {
    this.commands = commands;
  }

  public void onRideRequested(RideRequested event) {
    commands.send(new ReserveDriver(event.rideId()));
  }

  public void onDriverReserved(DriverReserved event) {
    commands.send(new AuthorizePayment(event.rideId()));
  }

  public void onPaymentAuthorizationFailed(PaymentAuthorizationFailed event) {
    // compensating actions — batalkan langkah sebelumnya
    commands.send(new ReleaseDriver(event.rideId()));
    commands.send(new CancelRide(event.rideId()));
  }
}

Saga tidak menggantikan konsistensi transaksional — ia mengganti "atomik" dengan "eventually consistent, dan bisa dibatalkan dengan bersih". Ini trade-off sadar, bukan kompromi darurat.

ADV · 04

Anti-Corruption Layer, lebih dalam

Level Lanjut

ACL adalah lapisan penerjemah di batas bounded context: mengubah model/protokol sistem eksternal menjadi model internal yang bersih, dan sebaliknya. Secara arsitektural, ACL adalah adapter (CA·02) yang isinya mostly mapping logic — ia hidup di infrastructure/interface layer, memanggil port yang didefinisikan domain, dan tidak pernah membiarkan tipe/istilah dari sistem eksternal bocor ke domain model.

  • Tanpa ACL: nama field, enum, dan asumsi dari API pihak ketiga menyebar ke seluruh domain — setiap perubahan API eksternal jadi refactor besar.
  • Dengan ACL: satu titik perubahan ketika API eksternal berubah; domain model tetap stabil dan mengekspresikan ubiquitous language milik sendiri.
ADV · 05

Aturan desain aggregate

Level Lanjut
  • Rancang aggregate sekecil mungkin — hanya sertakan objek yang benar-benar butuh konsistensi langsung (bukan eventual) dengan root.
  • Referensi aggregate lain hanya lewat ID, tidak pernah menyimpan objek aggregate lain secara langsung di dalam aggregate — mencegah graf objek raksasa dan transaksi yang menyentuh banyak tabel sekaligus.
  • Konsistensi antar-aggregate bersifat eventual, dijaga lewat domain event, bukan lewat transaksi database yang dipaksa mencakup keduanya.
  • Satu transaksi = satu aggregate. Kalau use case terasa perlu menyimpan dua aggregate root sekaligus secara atomik, itu sinyal untuk memikirkan ulang batasnya atau memakai saga.
Studi Kasus

Tiga sheet penutup, dikerjakan penuh

SheetCS·01
DomainE-Commerce Order
Pola utamaAggregate, Repository, Domain Event
KompleksitasMenengah

Konteks: Bounded context Ordering menerima permintaan submit order dari pelanggan. Order harus memiliki minimal satu item, total dihitung dari OrderLine, dan begitu disubmit, order tidak boleh diubah lagi (lihat DDD·05 untuk aggregate-nya, CA·04 untuk struktur foldernya).

Keputusan desain kunci:

  • Order jadi satu-satunya aggregate root; OrderLine adalah entity internal, Money adalah value object.
  • CustomerId disimpan sebagai referensi, bukan objek Customer penuh — Customer adalah aggregate root di bounded context lain (Identity).
  • Event OrderSubmitted dipublikasikan setelah save() berhasil, dikonsumsi context Shipping untuk memulai proses pengiriman — integrasi lewat OHS/PL (DDD·10), bukan panggilan langsung antar aggregate.
  • Controller HTTP (interface layer) hanya menerjemahkan request menjadi SubmitOrderCommand dan memanggil SubmitOrderUseCase — tidak ada logika bisnis di controller.
Hasil
Aturan "order kosong tidak boleh disubmit" hanya ada di satu tempat (Order.submit()), sehingga tidak mungkin dilewati lewat jalur API lain — berbeda dari desain anemic model di mana validasi ini gampang lupa ditaruh di salah satu endpoint.
SheetCS·02
DomainLedger / Perbankan
Pola utamaEvent Sourcing, Invariant ketat
KompleksitasLanjut

Konteks: Account harus mempertahankan invariant "saldo tidak boleh negatif" di bawah beban transaksi konkuren, dan regulator sewaktu-waktu bisa meminta riwayat lengkap kenapa saldo berubah — bukan cuma angka akhirnya.

Kenapa event sourcing di sini masuk akal (bandingkan dengan ADV·02): audit trail adalah kebutuhan fungsional, bukan nice-to-have, dan volume event per aggregate (satu akun) cukup kecil sehingga replay tetap murah.

  • Setiap mutasi saldo lahir sebagai event (FundsDeposited, FundsWithdrawn) sebelum diterapkan ke state in-memory — event adalah sumber kebenaran, state adalah proyeksinya.
  • Invariant "saldo tidak boleh negatif" dicek sebelum event dibuat, di dalam aggregate — bukan di application service, apalagi di database constraint saja.
  • Konkurensi ditangani dengan optimistic concurrency: setiap save menyertakan version yang diharapkan; event store menolak tulis kalau versi sudah berubah sejak rehydrate.
Jebakan umum
Mengekspos daftar event mentah langsung sebagai API publik ke tim lain. Skema event adalah kontrak internal aggregate — kalau context lain butuh tahu perubahan saldo, publikasikan integration event terpisah yang stabil (lihat DDD·06).
SheetCS·03
DomainRide-Hailing Dispatch
Pola utamaSaga, Context Mapping
KompleksitasLanjut

Konteks: Satu permintaan ride menyentuh minimal tiga bounded context — Dispatch (cari & kunci driver), Payment (otorisasi kartu), Trip (mulai perjalanan). Masing-masing punya aggregate sendiri; tidak ada satu transaksi database yang bisa mencakup ketiganya.

Kenapa saga, bukan transaksi terdistribusi: two-phase commit lintas tiga service berarti mengunci resource di tiga tempat sekaligus selama proses berjalan — buruk untuk latency dan availability. Saga menerima eventual consistency sebagai trade-off sadar, dengan compensating action yang eksplisit (lihat ADV·03).

  • Kegagalan otorisasi pembayaran men-trigger ReleaseDriver — driver yang sudah "dikunci" harus dilepas eksplisit, tidak otomatis lewat rollback database.
  • Context Payment di sini biasanya penyedia pihak ketiga → wajib ACL (ADV·04) supaya model Trip tidak tercemar istilah spesifik payment gateway.
  • State saga sendiri (langkah mana yang sudah selesai) disimpan sebagai aggregate tersendiri — process manager — bukan disebar sebagai flag di aggregate domain lain.
APPENDIX

Daftar anti-pattern

  • ✕
    Anemic Domain Model — entity cuma berisi getter/setter, semua logika bisnis pindah ke service. Kehilangan seluruh manfaat encapsulation DDD.
  • ✕
    God Aggregate — satu aggregate mencoba menjaga konsistensi untuk separuh sistem, jadi bottleneck lock dan sulit dipahami.
  • ✕
    Repository per tabel, bukan per aggregate root — membocorkan struktur database ke domain, dan memecah batas konsistensi aggregate.
  • ✕
    Entity ORM = entity domain — anotasi ORM menempel langsung di kelas domain, membuat domain layer diam-diam bergantung pada framework persistence.
  • ✕
    Application service gemuk — aturan bisnis (bukan sekadar orkestrasi) ditulis di use case, bukan di aggregate; aturan jadi sulit ditemukan dan mudah diduplikasi.
  • ✕
    Database bersama antar bounded context — dua context menulis ke tabel yang sama, sehingga batas context di kode tidak lagi berarti apa-apa secara nyata.
  • ✕
    DTO = domain object — struktur request/response API dipakai langsung sebagai objek domain, membuat kontrak eksternal dan model internal terikat erat.
  • ✕
    Tidak ada ubiquitous language — istilah di kode berbeda dari istilah di rapat bisnis, setiap diskusi butuh "penerjemahan" bolak-balik.
