◆ Buat apa ini? Kenapa pakai ini?

Given — AI bisa generate kode dengan cepat, dan developer menerima kode itu tanpa benar-benar paham struktur data, kompleksitas, atau alasan desainnya.

When — kode itu cuma dibaca sekilas, dites "jalan atau tidak", lalu di-merge — bukan diverifikasi lewat pemahaman atau test yang membuktikan kebenarannya.

Then — bug tersembunyi, struktur data yang salah pilih, dan kompleksitas yang harusnya bisa lebih cepat ikut lolos ke production tanpa disadari siapa pun.

→ makanya kita pakai fundamental engineering — supaya developer bisa menilai & memperbaiki kode dari AI, bukan cuma menyalinnya.

Hari ini: empat fundamental yang menunjukkan seperti apa "kode yang bagus" — supaya kita bisa memintanya ke agent.

Warm-up: kode ini jalan. Berani di-merge?

// Buatan AI: kembalikan user yang punya minimal satu order
// User.getId() dan Order.getUserId() sama-sama mengembalikan Long
public List<User> getUsersWithOrders(List<User> users,
                                     List<Order> orders) {
    List<User> result = new ArrayList<>();
    for (int i = 0; i < users.size(); i++) {
        for (int j = 0; j < orders.size(); j++) {
            if (orders.get(j).getUserId() == users.get(i).getId()) {
                result.add(users.get(i));
            }
        }
    }
    return result;
}
giliran kalian
  • Compile sukses.
  • Demo lancar.
  • Test-nya hijau.
  • Catat semua hal yang menurut kalian bermasalah.
Petunjuk: minimal ada empat masalah berbeda — salah satunya baru muncul kalau id-nya lebih besar dari 127.

Empat masalah — dan empat pilar yang memperbaikinya

→ diperbaiki oleh TDD

Hasilnya salah, tanpa error

Method ini seharusnya mengembalikan tiap user sekali. Tapi result.add() jalan sekali untuk setiap order yang cocok — tidak ada break. Telusuri: user A punya 3 order → hasilnya [A, A, A], ukurannya 3, padahal seharusnya 1. Di demo (1 order per user) terlihat aman; dengan data nyata, rusak. Test yang ditulis duluan akan menangkapnya.

→ diberi nama oleh Big O

O(n × m) — terlalu lambat

10 ribu user × 100 ribu order = 1.000.000.000 perbandingan. Cepat di demo, bermenit-menit di production.

→ diperbaiki oleh DSA

Salah pilih container

Kode ini men-scan seluruh List untuk tiap pencocokan. Kalau id order dimasukkan ke HashSet, tiap lookup cukup satu langkah.

→ dicegah oleh prompting

Satu prompt yang tidak jelas, akar dari semuanya

Prompt-nya tidak pernah menyebut: hasil harus unik, lookup harus cepat, atau cara membandingkan id. Jadi AI memilih opsi termudah — termasuk == untuk id bertipe Long. Kenapa salah: Long itu angka yang dibungkus object ("boxed"), dan untuk object, == bertanya "object-nya sama?", bukan "nilainya sama?". Java memakai ulang object Long dari −128 sampai 127, jadi di demo ber-id kecil terlihat aman — lalu diam-diam mengembalikan false di production. Selalu pakai equals().

Satu snippet, empat jenis kegagalan — dan itulah agenda kita hari ini.
pilar 1 · data structures

Enam struktur yang kalian pakai setiap hari

List / ArrayList

Item yang berurutan: hasil API, baris tabel, baris invoice.

Jago untuk loop dan menjaga urutan. Lemah untuk "cari berdasarkan nilai" — O(n).

Set / HashSet

Keanggotaan: id yang sudah pernah dilihat, menghapus duplikat, permission.

"Sudah pernah lihat ini?" dijawab dalam O(1).

Map / HashMap

Key → value: cache, cari berdasarkan id, counting, grouping.

Andalan sehari-hari — O(1) per key.

Stack / ArrayDeque

Riwayat undo, call stack, tombol back.

Last in, first out (LIFO).

Queue / BlockingQueue

Job queue, message broker, pola producer–consumer.

First in, first out (FIFO) — urutannya adil.

Tree / TreeMap

Key yang terurut, range query — dan semua index database (B-tree).

Pencarian O(log n).

Keenamnya sudah kalian pakai setiap hari. Mengenal namanya membantu kalian memilih dengan sadar. Berikutnya: satu contoh nyata untuk masing-masing.
pilar 1 · satu contoh untuk masing-masing — tiga yang harian

List, HashSet, HashMap di kode nyata

List<T>

Contoh: menampilkan baris invoice — urutan penting 
List<LineItem> items =
    invoice.getItems();

for (LineItem it : items) {
    render(it);
}
// urutan insert terjaga;
// jangan dipakai untuk cari nilai

HashSet<T>

Contoh: kirim ke tiap alamat email hanya sekali 
Set<String> seen =
    new HashSet<>();

for (String email : recipients) {
    if (seen.add(email)) {
        send(email);
    }
}
// add() mengembalikan false
// kalau sudah ada — O(1)

HashMap<K,V>

Contoh: menghitung jumlah login per user
Map<Long, Integer> logins =
    new HashMap<>();

for (Event ev : events) {
    logins.merge(
        ev.userId(), 1,
        Integer::sum);
}
// merge(): counter satu baris
Tiga ini mencakup ±90% keputusan harian: urutan → List · keanggotaan → HashSet · key-ke-value → HashMap.
pilar 1 · satu contoh untuk masing-masing — tiga yang struktural

Stack, Queue, TreeMap di kode nyata

Deque (sebagai Stack)

Contoh: cek palindrome — LIFO membalik urutan 
boolean isPalindrome(String s) {
  Deque<Character> stack =
      new ArrayDeque<>();

  for (char c : s.toCharArray())
      stack.push(c);          // masuk

  for (char c : s.toCharArray())
      if (stack.pop() != c)   // keluar, terbalik
          return false;
  return true;
}
// "level" → true · "java" → false
// pakai ArrayDeque, bukan
// java.util.Stack yang lama

Queue<T>

Contoh: job email di background — FIFO
Queue<EmailJob> jobs =
    new ArrayDeque<>();

jobs.offer(job);      // producer

EmailJob next = jobs.poll();
worker.process(next); // yang paling lama duluan
// antar-thread: BlockingQueue
// antar-service: Kafka / SQS

TreeMap<K,V>

Contoh: tier loyalti dari poin — terurut + range 
TreeMap<Integer, String> tiers =
    new TreeMap<>(Map.of(
        0, "BRONZE",
        1_000, "SILVER",
        5_000, "GOLD"));

String tier = tiers
    .floorEntry(points).getValue();
// tanpa rantai if; index DB
// memakai ide yang sama (B-tree)
Sekarang kalian tahu struktur di balik cek palindrome, fitur undo, job queue, dan query yang ber-index.
pilar 1 · data structures

Pilih container dari pertanyaan yang dijawabnya

Pakai Saat kodenya bertanya… Lookup
List "proses item-nya sesuai urutan" O(n) by value
HashSet "sudah pernah lihat ini?" O(1)
HashMap "apa yang terkait dengan key ini?" — counting, grouping, indexing O(1)
TreeMap "perlu urutan, nilai terdekat, atau range?" O(log n)

Sebagian besar kode AI yang lambat cukup diperbaiki dengan satu perubahan: ganti scan List dengan lookup HashSet atau HashMap.

Pola di balik kebanyakan report 
// kelompokkan order per customer — satu pass
Map<Long, List<Order>> byCustomer =
    new HashMap<>();

for (Order o : orders) {
    byCustomer
      .computeIfAbsent(o.getCustomerId(),
                       k -> new ArrayList<>())
      .add(o);
}
// atau: orders.stream().collect(
//        groupingBy(Order::getCustomerId))
Kebiasaan: setiap melihat lookup, tanyakan "pertanyaan apa yang sedang diajukan kode ini?" — lalu cek apakah container-nya cocok.
pilar 2 · big o

Big O itu sederhana

Big O = "seberapa banyak kerja bertambah kalau datanya bertambah?" Itu saja. Tidak perlu jago matematika.

Notasi Kode yang umum Dengan 1.000.000 record…
O(1) lookup HashMap / HashSet, list.get(i) instan — 1 langkah
O(log n) binary search, TreeMap, lookup index DB instan — ±20 langkah
O(n) satu loop untuk seluruh data, list.contains(x) aman — 1 juta langkah, hitungan milidetik
O(n log n) Collections.sort / stream().sorted() aman — ±20 juta langkah
O(n²) loop di dalam loop 10¹² langkah — bisa bermenit-menit sampai berjam-jam

Belajar lebih lanjut: bigocheatsheet.com — Big O untuk semua data structure dan algoritma sorting, lengkap di satu halaman.

Yang benar-benar menyakitkan di proyek nyata cuma baris terakhir — dan justru paling gampang dikenali.
pilar 2 · big o

Cara menemukan yang lambat di kode nyata

Jebakannya: list.contains() / indexOf() di dalam loop sama saja loop di dalam loop — O(n) yang bersembunyi di balik nama method.

AI suka menulis seperti ini ✗
// activeIds bertipe List<Long> → O(n × m)
List<User> active = new ArrayList<>();
for (User u : users) {
    if (activeIds.contains(u.getId())) {
        active.add(u);
    }
}
// 1jt × 1jt ≈ 10¹² pengecekan → berjam-jam
Minta yang seperti ini ✓
// O(n + m)
Set<Long> idSet = new HashSet<>(activeIds);
List<User> active = users.stream()
    .filter(u -> idSet.contains(u.getId()))
    .toList();


// ≈ 2jt langkah → hitungan milidetik
Masalah yang sama ada di database: panggilan repository di dalam loop itu masalah N+1 — minta join atau satu query batch saja.
pilar 3 · test-driven development

Tulis test sebelum kodenya

Red — tulis test yang gagal
→
Green — buat lolos
→
Refactor — rapikan dengan aman
↺
  • Test adalah spec. Berikan failing test ke agent dan biarkan dia membuatnya lolos — test tidak mungkin disalahartikan.
  • Yang kalian review test-nya, bukan hanya diff. 10 assertion pendek jauh lebih gampang dicek daripada 200 baris hasil generate.
  • Menutup jalan happy path. Edge case sudah jadi test sebelum kodenya ada.
  • Refactor jadi aman. Selama test suite hijau, agent bebas merombak tanpa rasa takut.
Prompt tip — tempel apa adanya 
"Test behavior, not implementation.
 Each test verifies an observable outcome —
 a returned value, an error, or a side
 effect — never the internal wiring. This
 lets us refactor and optimize the code
 without breaking any tests."
Test JUnit ini, kalau ditulis duluan, menangkap bug warm-up tadi 
@Test
void userWithThreeOrdersAppearsOnce() {
    List<User> users  = List.of(new User(1L));
    List<Order> orders = List.of(
        new Order(1L), new Order(1L), new Order(1L));

    assertEquals(1,
        getUsersWithOrders(users, orders).size());
    // versi AI-nya mengembalikan 3 ✗
}
Failing test adalah satu-satunya feedback yang tidak bisa dibantah oleh AI agent.
pilar 3 · test-driven development

Apakah TDD otomatis memberi semua ini?

umumnya iya

YAGNI

"You Aren't Gonna Need It" — jangan bangun fitur sebelum benar-benar dibutuhkan.

Kode hanya ditulis kalau ada failing test yang memintanya — jadi kode "siapa tahu nanti perlu" tidak pernah lahir. Tapi: kalau kalian menulis test untuk fitur yang tidak diminta siapa pun, TDD tetap akan membantu membangunnya.

hanya kalau refactor jalan

KISS

"Keep It Simple" — pilih desain paling sederhana yang berfungsi.

Langkah green meminta kode seminimal mungkin. Tapi: test tidak peduli sejelek apa kodenya. Kesederhanaan datang dari langkah refactor — dan itu soal disiplin. Kalau dilewati terus, hasilnya spaghetti yang ter-test rapi.

iya, tapi ada jebakannya

Coverage tinggi

Coverage = seberapa banyak kode yang dijalankan oleh test.

Kalau tiap baris lahir karena diminta test, coverage kode baru otomatis tinggi. Tapi: coverage menghitung baris yang dijalankan, bukan perilaku yang dicek — TDD hanya menutup edge case yang sempat terpikirkan oleh kalian.

TDD mempermudah ketiganya — tapi tidak menjamin satu pun. Test membatasi kodenya, refactor menjaganya tetap sederhana, dan coverage mengikuti dengan sendirinya.

Bukan cuma kata kami — tool-nya pun mewajibkan

Salah satu toolkit agent terpopuler di GitHub (200 ribu+ stars): skills framework yang mengajarkan metode engineering lengkap ke coding agent kalian — brainstorming, planning, debugging… dan TDD yang ketat.

  • Bahkan alasan-alasan yang biasa dipakai agent untuk skip testing ("terlalu sederhana untuk di-test", "test-nya nanti saja") ikut didaftar — dan dilarang.

pilar 4 · better prompting

Prompt adalah spec — tulislah layaknya spec

Begini lahirnya bug warm-up tadi ✗
"buatkan method untuk mencari
 user yang punya order"

Prompt yang tidak jelas → AI mengisi tiap celah dengan jawaban termudah yang tetap jalan: nested loop, == bukannya equals(), tanpa cek null, happy path saja.

Tiap pilar jadi satu baris ✓
"Tulis getUsersWithOrders(users, orders):
 - tulis failing JUnit test-nya DULUAN:
   kosong, duplikat, id tidak ada         ← TDD
 - tiap user muncul maksimal sekali
 - masukkan id order ke HashSet           ← DSA
 - O(n + m), tanpa nested scan            ← Big O
 - equals() untuk id, cek null/kosong"
Tiap konsep yang bisa kalian sebut namanya, bisa kalian minta sebagai requirement. Itulah kenapa fundamental membuat prompt kalian lebih baik.
pilar 4 · better prompting

Lima kebiasaan untuk prompt yang lebih baik

  • Spesifik. Prompt yang tidak jelas akan mendapat tafsiran termudah — sebutkan persis apa yang kalian butuhkan.
  • Beri satu contoh. Satu contoh input → output yang diharapkan lebih jelas daripada deskripsi panjang.
  • Sebutkan constraint-nya. Performa, error handling, penamaan — kalau memang penting, tulis.
  • Suruh bertanya, jangan biarkan menebak. Agent bisa menebak saat ada yang kurang jelas — justru itu masalahnya. Requirement hasil tebakan akan jadi bug nanti. Minta dia bertanya dulu → prompt-nya di sebelah kanan.
  • Minta kejujuran. Agent cenderung selalu setuju dengan kalian. Honesty clause membuat agent mengkritisi cara berpikir kalian, bukan memujinya.
Prompt "tanya dulu" — pilih salah satu 
"Ask me more questions for clarification."

"If the requirements are unclear,
 ask me first — do not guess."
Honesty clause — tempel apa adanya 
"Never agree with me just to be agreeable.
 If I'm wrong, say so directly. You are not
 here to make me feel validated. Find the
 weak spots and blind spots in my thinking.
 Point them out, even if I didn't ask.
 If I ever seem to want validation more
 than truth, call it out."

Tips: prompt yang sering dipakai bisa disimpan di agent config, supaya otomatis termuat di tiap sesi.

Kebiasaan ini berlaku untuk bahasa apa pun dan agent apa pun — bagian dari workflow engineering, bukan pekerjaan tambahan.
