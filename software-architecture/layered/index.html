Layered Architecture

Kode dibagi jadi lapisan bertumpuk. Tiap lapisan punya satu tugas, dan cuma boleh bicara ke lapisan di bawahnya.

$ Kayak kue lapis: tiap lapis jelas tempatnya.

Semua kode di satu kelas: HTTP, aturan bisnis, dan SQL campur aduk.

🍝

Controller berisi SQL

Satu method 200 baris, susah dibaca.

🧪

Susah dites

Mau tes aturan diskon, harus nyalakan database dan HTTP.

🔁

Logika di-copy

Aturan yang sama ditulis ulang di beberapa controller.

Satu lapis, satu tugas

terima request · atur bisnis · simpan data

◆ Buat apa ini? Kenapa pakai ini?

Given — aplikasi mulai besar dan dikerjakan banyak orang.

When — semua jenis kode ditulis campur dalam satu tempat.

Then — kode jadi spaghetti: susah dibaca, dites, dan diubah.

→ makanya kita pakai Layered Architecture — supaya setiap jenis kode punya tempatnya sendiri.

Dari campur aduk jadi berlapis

✗ Sebelum: semua di controller
@PostMapping("/orders")
Order create(@RequestBody OrderReq r) {
    var p = jdbc.queryForObject(
        "SELECT * FROM product WHERE id=?", ..);
    if (p.stock() < r.qty()) throw ...;
    var total = p.price() * r.qty() * 0.9;
    jdbc.update("INSERT INTO orders ...");
    return ...;
}
✓ Sesudah: tiap lapis satu tugas
// Controller: urusan HTTP saja
@PostMapping("/orders")
Order create(@RequestBody OrderReq r) {
    return orderService.place(r);
}
// Service: aturan bisnis
Order place(OrderReq r) {
    var p = productRepo.find(r.productId());
    p.ensureStock(r.qty());
    return orderRepo.save(Order.of(p, r.qty()));
}
Aturan bisnis sekarang bisa dites tanpa HTTP dan database.
yang perlu dijaga

Jebakan yang sering kejadian

jebakan

Service cuma meneruskan

Service isinya cuma return repo.find(). Tidak apa-apa untuk CRUD, jangan dipaksa.

jebakan

Lompat lapisan

Controller langsung panggil Repository. Aturan bisnis jadi bocor.

jebakan

Entity bocor ke response

Entity JPA dikirim langsung ke JSON. Pakai DTO.

batas

Bisnis bergantung ke DB

Lapisan bisnis masih tahu database. Mau lebih bersih? Lihat Hexagonal.

Jangan kirim entity database ke luar

✗ entity bocor ke response
@GetMapping("/users/{id}")
UserEntity get(@PathVariable long id) {
  return repo.findById(id).orElseThrow();
}   // ← password hash ikut terkirim!
✓ pakai DTO
record UserDto(long id, String name) {}

@GetMapping("/users/{id}")
UserDto get(@PathVariable long id) {
  return service.find(id);   // service memetakan
}
DTO = bungkusan khusus untuk dikirim ke luar. Isinya cuma yang perlu.

variasi

Package per lapisan atau per fitur?

per lapisan

controller/ service/ repository/

Gampang dipahami pemula. Tapi satu fitur tersebar di 3 folder.

per fitur

order/ payment/ user/

Tiap folder berisi controller-service-repo miliknya. Lebih mudah dirawat saat besar.

Untuk aplikasi yang tumbuh, per fitur biasanya lebih enak.
