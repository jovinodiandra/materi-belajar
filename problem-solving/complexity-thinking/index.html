// Problem Solving — membaca angka sebelum menulis baris kode pertama

Angka constraint sudah membisikkan algoritma apa yang kamu butuhkan.

Ini bukan halaman tentang definisi Big-O — itu ada di halaman lain. Ini tentang kebiasaan yang lebih praktis: begitu kamu lihat 1 ≤ n ≤ 10⁵ di soal, kamu harusnya langsung punya perkiraan kasar "pendekatan O(n²) akan meledak, aku butuh sesuatu di sekitar O(n log n)" — sebelum menulis satu baris kode pun. Deck ini tentang melatih intuisi itu: menerjemahkan angka batas jadi peta kasar teknik yang layak dicoba.

◆ Buat apa ini? Kenapa pakai Complexity Thinking?

Given — kamu baca soal atau tiket, langsung mikir "gimana cara nyelesainnya secara logis" dan mulai ngoding brute force tanpa pernah melirik baris kecil 1 ≤ n ≤ 10⁵ di spesifikasinya.

When — solusi itu di-submit ke online judge, atau di-deploy ke production lalu datanya tumbuh dari ratusan baris jadi ratusan ribu baris dalam beberapa bulan.

Then — loop bersarang yang tadinya "kelihatan wajar" jadi Time Limit Exceeded di kompetisi, atau bikin endpoint production mendadak lemot/timeout begitu n membesar — dan kamu baru sadar setelah ada laporan, bukan sebelum menulis baris kode pertama.

→ makanya kita pakai Complexity Thinking.

Akar masalah · Constraint diabaikan

Baris kecil di soal itu bukan formalitas

Hampir semua soal — kompetitif, technical interview, bahkan tiket JIRA di kantor — punya baris kecil semacam "1 ≤ n ≤ 10⁵". Banyak orang melompatinya, langsung mikir "gimana cara nyelesain ini secara logis", lalu baru sadar solusinya timeout setelah submit. Padahal baris kecil itu sudah menjawab pertanyaan "seberapa cepat solusiku harus jalan" — kamu tinggal menerjemahkannya.

Constraint ukuran input pada soal dunia nyata (atau kompetisi) memberi petunjuk langsung tentang kompleksitas algoritma yang dibutuhkan — problem solver yang baik selalu mengaitkan ukuran input dengan anggaran waktu sebelum memilih pendekatan.

— parafrase gagasan Steven Skiena, The Algorithm Design Manual
◆ Analogi — rambu batas kecepatan

Rambu 60 km/jam di jalan bukan sekadar angka — ia memberitahumu ini jalan kota, bukan tol. Kamu tidak perlu melihat aspalnya untuk tahu jenis jalannya; angka di rambu sudah cukup. Sama halnya, n ≤ 10⁵ adalah rambu yang bilang "ini soal untuk solusi di sekitar O(n log n)". Kamu tidak perlu mencoba semua algoritma untuk tahu — angka batasnya sudah memberi tahu kelas solusi yang relevan, jauh sebelum kamu menulis kode.

Efeknya kalau diabaikan bisa dua arah: solusi O(n²) di kompetisi dengan n ≤ 10⁵ akan Time Limit Exceeded — itu yang paling sering dibicarakan. Tapi ada juga arah sebaliknya yang jarang disorot: menghabiskan waktu membangun struktur data rumit O(log n) untuk kasus yang n-nya cuma puluhan, di mana solusi brute force O(n²) sebenarnya sudah lebih dari cukup dan jauh lebih cepat ditulis.

Konsep inti · Peta cepat

Tabel kasar: angka n → kompleksitas yang aman

Ini bukan hukum matematika, tapi heuristik kerja yang dipakai hampir semua competitive programmer. Asumsinya: mesin modern kira-kira sanggup menjalankan 10⁸ operasi sederhana per detik, dan batas waktu tipikal soal adalah 1–2 detik.

peta-kasar.txt — n → kompleksitas aman (asumsi ~10⁸ ops/detik, limit ~1-2 detik)PANDUAN
n ≤ 10-12        →  O(2^n) atau O(n!)        // brute force / backtracking penuh
n ≤ 20-25        →  O(2^n · n)               // bitmask DP, subset enumeration
n ≤ 100          →  O(n^4)                   // nested loop 4 lapis, DP 2D berat
n ≤ 500-1.000    →  O(n^3)                   // Floyd-Warshall, DP 3D
n ≤ 2.000-10.000 →  O(n^2)                   // nested loop 2 lapis, DP 2D ringan
n ≤ 10^5-10^6    →  O(n log n)               // sorting, divide & conquer, heap
n ≤ 10^6-10^8    →  O(n)                     // sliding window, prefix sum, satu pass
n ≤ 10^9         →  O(log n) atau O(√n)      // binary search, math, factorization
n ≤ 10^18        →  O(1) atau O(log n)       // biasanya soal matematis murni

// aturan cepat: hitung operasi = f(n), lalu bandingkan dengan ~10^8
// contoh: n = 10^5, O(n^2) = 10^10 operasi → JAUH di atas budget → TLE

Cara pakainya sederhana: ambil n dari soal, coba masukkan ke tiap kandidat kompleksitas, lihat berapa total operasi-nya, lalu bandingkan dengan anggaran ~10⁸. Kalau hasilnya jauh di atas anggaran, coret kandidat itu dari daftar — sebelum kamu capek-capek mengimplementasikannya.

Pertanyaan "seberapa besar skalanya?" harus dijawab dengan angka konkret, bukan sekadar "besar" atau "kecil" — karena solusi yang tepat untuk skala kecil bisa sangat buruk di skala besar, dan sebaliknya solusi untuk skala besar bisa berlebihan (over-engineering) untuk skala kecil.

— parafrase gagasan Martin Kleppmann, Designing Data-Intensive Applications, Bab 1
Latihan reasoning · Kasus konkret

Menelusuri: soal dengan n ≤ 10⁵

Soal: "Diberi array A berisi n bilangan (1 ≤ n ≤ 10⁵). Untuk tiap pasangan indeks (i, j) di mana i < j, hitung berapa pasangan yang A[i] + A[j] genap." Mari telusuri reasoning-nya seperti yang harusnya terjadi di kepala, langkah demi langkah.

  1. Baca constraint dulu, sebelum mikir logika. n ≤ 10⁵. Cocokkan ke tabel: ini masuk rentang yang butuh O(n log n) atau lebih cepat — O(n) jika bisa.
  2. Coba pendekatan paling naif secara logika. Solusi paling jelas: dua nested loop, cek semua pasangan (i, j) — ini O(n²). Logikanya benar, tapi jangan langsung nulis kode.
  3. Hitung estimasi operasi sebelum implementasi. Dengan n = 10⁵, O(n²) = 10¹⁰ operasi. Anggaran ~10⁸ per detik → butuh ~100 detik. Limit soal biasanya 1-2 detik → pasti TLE. Kandidat ini gugur di atas kertas, tanpa perlu ditulis dulu.
  4. Cari sifat matematis yang memangkas kompleksitas. Jumlah dua bilangan genap kalau keduanya sama paritasnya (sama-sama genap atau sama-sama ganjil). Jadi cukup hitung g = banyak bilangan genap dan j = banyak bilangan ganjil — tidak perlu memeriksa tiap pasangan satu per satu.
  5. Turunkan solusi O(n). Satu pass untuk menghitung g dan j, lalu jawabannya adalah C(g,2) + C(j,2) — kombinasi memilih 2 dari tiap kelompok. Total operasi ≈ n = 10⁵, jauh di bawah anggaran → aman, bahkan longgar.
  6. Cocokkan lagi ke tabel sebagai sanity check. n ≤ 10⁵ menyarankan O(n log n), tapi kita justru dapat O(n) — itu bagus, berarti ada solusi yang lebih baik dari "batas aman minimal". Ini menunjukkan tabel constraint adalah batas atas kompleksitas yang boleh dipakai, bukan target yang harus dikejar pas-pasan.
◆
Tabel constraint memberi batas atas (kompleksitas apa yang masih lolos), bukan jaminan bahwa solusi dengan kompleksitas itu otomatis benar atau optimal. Kamu tetap harus mencari logika yang tepat — tabel cuma menyaring pendekatan mana yang layak dicoba lebih dulu, supaya waktumu tidak habis mengimplementasikan sesuatu yang jelas-jelas akan gagal di batas waktu.
◆ Kebiasaan · Yang harus jadi refleks

Best practice membaca constraint

Beberapa kebiasaan ini murah dilakukan tapi menghemat banyak waktu — baik saat kompetisi, interview, maupun saat merancang sistem production.

  • Selalu baca constraint SEBELUM mikir algoritma. Bukan setelah punya ide — angka n harus jadi filter pertama sebelum kamu mulai brainstorm pendekatan.
  • Hafal anggaran kasar ~10⁸ operasi per detik. Ini bukan angka presisi (tergantung bahasa, mesin, jenis operasi), tapi cukup untuk estimasi order-of-magnitude dalam hitungan detik.
  • Hitung total operasi tiap kandidat kompleksitas sebelum menulis kode. Masukkan n, kalikan, bandingkan dengan anggaran. Coret kandidat yang jelas meledak.
  • Waspada integer overflow di angka besar. Kalau n bisa sampai 10⁹ dan kamu menjumlahkan/mengalikan banyak elemen, hasilnya bisa melebihi batas int 32-bit (~2.1 × 10⁹) — pakai tipe 64-bit atau modulo sesuai kebutuhan soal.
  • Cek apakah ada constraint kedua yang tersembunyi. Soal sering punya lebih dari satu batas — misalnya n ≤ 10⁵ tapi juga q ≤ 10⁵ query, yang berarti kompleksitas per-query juga harus diperhitungkan (total bisa jadi O(n·q), bukan cuma O(n)).
  • Kalau constraint sangat longgar (n kecil), jangan over-engineer. Solusi brute force yang jelas benar & cepat ditulis lebih baik daripada solusi rumit yang berisiko bug, kalau anggaran waktu jelas-jelas mengizinkan.
◆ Jenjang · Dari hafalan ke insting

Tier belajar: dari tabel ke intuisi

Kemampuan ini berkembang bertahap — dari sekadar tahu tabelnya ada, sampai bisa mengendus kapan tabel itu sendiri bisa menipu.

Beginner

Hafal tabel dasar

Kamu bisa menyebutkan kira-kira kompleksitas aman untuk n ≤ 10, n ≤ 1.000, n ≤ 10⁵, dan n ≤ 10⁹ tanpa harus membuka catatan.

  • Tahu anggaran ~10⁸ operasi/detik.
  • Bisa membedakan O(n²) vs O(n log n) secara kasar dari n.
  • Mulai membiasakan diri membaca constraint di awal, bukan di akhir.
Middle

Pakai untuk mempersempit pilihan

Constraint bukan cuma dihafal, tapi jadi alat aktif untuk menyaring algoritma mana yang layak dicoba lebih dulu, secara konsisten setiap kali latihan.

  • Menghitung estimasi operasi sebelum menulis kode, bukan setelah TLE.
  • Mengenali constraint ganda (n dan q sekaligus) dan menggabungkan efeknya.
  • Sudah refleks curiga saat melihat angka besar tanpa disertai batas waktu jelas.
Advance

Kenali kapan constraint menipu

Paham bahwa tabel constraint adalah heuristik, bukan hukum — dan tahu kasus-kasus di mana ia perlu ditafsirkan lebih hati-hati.

  • Paham kompleksitas amortized bisa membuat solusi "terlihat" O(n²) tapi sebenarnya O(n) rata-rata.
  • Mengenali constraint tersembunyi (mis. jumlah total elemen di semua test case dibatasi, bukan tiap test case sendiri-sendiri).
  • Tahu konstanta tersembunyi bisa membuat O(n log n) yang "aman di atas kertas" tetap lambat kalau konstantanya besar.
! Anti-pola · Kebiasaan yang menjebak

Jebakan umum seputar constraint

Perbedaan antara solver yang efisien dan yang sering TLE / lambat di production biasanya bukan soal kepandaian, tapi soal kebiasaan kecil ini.

// ✅ Kebiasaan baik

  • Cek constraint sebelum mulai mikir algoritma.
  • Menaksir total operasi di kepala / kertas dulu.
  • Cek tipe data — apakah butuh 64-bit untuk hasil penjumlahan/perkalian.
  • Mencari constraint kedua atau ketiga yang tersembunyi di soal.
  • Menulis "target complexity" sebagai catatan sebelum ngoding.

// ❌ Kebiasaan buruk

  • Asumsi "input pasti kecil" tanpa mengecek angkanya.
  • Lupa integer overflow saat n atau nilainya besar.
  • Langsung ngoding solusi pertama yang terpikir, baru sadar TLE setelah submit / deploy.
  • Mengabaikan bahwa constraint di production bisa tumbuh seiring waktu (data user makin banyak).
  • Menganggap tabel n→kompleksitas berlaku mutlak, padahal ada konstanta & kasus amortized.
? Kalibrasi · Longgar vs ketat

Kapan constraint longgar, kapan ketat

// Constraint longgar

  • n kecil (puluhan – ratusan) → banyak pendekatan valid, termasuk brute force.
  • Batas waktu longgar (mis. 5-10 detik) → beri ruang error estimasi.
  • Fokus bisa dipindah ke kejelasan & kebenaran kode, bukan kecepatan mentah.

// Constraint ketat

  • n besar (10⁶ ke atas) → sering hanya satu kelas kompleksitas yang lolos.
  • Batas waktu ketat (1 detik) + n besar → konstanta di dalam O(n) pun mulai penting.
  • Salah pilih struktur data (mis. list vs hash map) bisa langsung gagal walau kompleksitas "benar".
◆ Ringkasan keputusan

Satu pertanyaan penentu sebelum ngoding

Sebelum menulis baris kode pertama, tanyakan ke soal atau spesifikasi di depanmu satu hal ini.

◆ Pertanyaan penentu

"Kalau n paling besar yang mungkin, berapa lama solusiku ini akan jalan?" Kalau kamu tidak bisa menjawabnya dalam hitungan detik di kepala — itu tandanya kamu belum benar-benar mengaitkan constraint dengan pilihan algoritmamu. Jawab dulu pertanyaan ini, baru pilih pendekatan.

Ingat juga: constraint yang longgar bukan alasan untuk berhenti berpikir sama sekali — tetap perhatikan kebenaran logika. Dan constraint yang ketat bukan alasan untuk panik — ia justru mempersempit ruang pencarianmu, membuat lebih sedikit pendekatan yang perlu dipertimbangkan.

Studi kasus · Tiga konteks nyata

Di mana kebiasaan ini benar-benar dipakai

Ini bukan cuma kebiasaan untuk lomba coding — pola pikir yang sama muncul di tiga konteks yang sangat berbeda.

// competitive programming

TLE karena salah baca constraint

Pola yang sering terjadi: solusi dengan logika benar tapi kompleksitasnya terlalu tinggi untuk n yang diberikan, sehingga submit berakhir Time Limit Exceeded — bukan karena logikanya salah, tapi karena kompleksitasnya tidak dicek dulu terhadap batas n sebelum menulis kode.

// production system

Endpoint API melambat seiring data tumbuh

Sebuah query atau loop yang kompleksitasnya O(n²) terhadap jumlah baris tabel terasa cepat saat data masih kecil di awal development. Begitu data user bertambah dari ribuan ke jutaan baris, endpoint yang sama jadi lambat — masalah yang sebenarnya sudah bisa diprediksi kalau kompleksitasnya diperhitungkan terhadap proyeksi pertumbuhan data, bukan cuma data uji yang kecil.

// technical interview

Interviewer menaikkan constraint sengaja

Setelah kandidat memberi solusi brute force yang benar, interviewer sering melanjutkan dengan pertanyaan susulan: "bagaimana kalau n-nya sampai satu juta?" Pertanyaan ini menguji apakah kandidat sadar bahwa constraint yang berubah menuntut pendekatan yang berbeda — bukan sekadar menguji apakah solusi awalnya benar.

◆ Benang merahnya

Di ketiga konteks itu, masalahnya bukan ketidaktahuan algoritma — tapi tidak mengaitkan algoritma yang dipilih dengan angka skala yang dihadapi. Kompetisi punya batas eksplisit di soal, production punya batas implisit di pertumbuhan data, interview punya batas yang sengaja digeser untuk menguji kesadaran itu.

⚙ Praktik · Alat bantu sederhana

Tools & kebiasaan menaksir kompleksitas

Tidak perlu alat canggih — ini soal kebiasaan menghitung di kepala atau di kertas, dilakukan konsisten setiap kali menghadapi soal baru.

// kalkulator mental

Estimasi runtime kasar

Rumus sederhana: operasi = f(n), lalu perkiraan detik = operasi / 10^8. Kalau hasilnya jauh melewati batas waktu soal (biasanya 1-2 detik), kompleksitas itu perlu diturunkan sebelum diimplementasikan.

// kebiasaan menulis

Tulis "target complexity" di awal

Sebelum ngoding, tulis satu baris komentar: // target: O(n log n). Ini memaksa kamu memilih arah sebelum tersesat menulis solusi yang ternyata terlalu lambat — dan jadi pengingat saat solusi mulai melenceng dari target.

// kebiasaan baca

Baca semua batas, bukan cuma n

Selain n, perhatikan batas nilai elemen, jumlah query, jumlah test case per file, dan batas memori. Semuanya ikut membentuk anggaran kompleksitas yang sebenarnya diizinkan.

// kebiasaan uji

Uji dengan n di batas maksimum

Sebelum submit atau deploy, coba jalankan solusi dengan n sebesar batas maksimum yang disebutkan constraint — bukan cuma contoh kecil di soal — untuk melihat apakah waktunya masih masuk akal.

Penutup

Angka batas itu petunjuk, bukan gangguan

Complexity thinking bukan soal menghafal notasi Big-O — itu sudah dibahas di halaman lain. Ini soal membangun refleks: setiap kali kamu melihat angka batas, kepalamu otomatis menerjemahkannya jadi kelas kompleksitas yang layak dicoba.

  • Baca constraint dulu — sebelum mikir algoritma sama sekali.
  • Anggaran ~10⁸ operasi/detik — patokan cepat untuk menaksir.
  • Tabel n → kompleksitas — batas atas, bukan target yang harus dikejar pas-pasan.
  • Waspada constraint ganda & overflow — angka besar sering datang berpasangan dengan jebakan lain.
  • Tabelnya heuristik, bukan hukum — amortized & konstanta tersembunyi bisa menipu di level advance.
  • Constraint di production ikut tumbuh — desain untuk skala yang akan datang, bukan cuma data uji hari ini.

Langkah belajar berikutnya

Tahu kompleksitas yang aman itu langkah pertama. Langkah berikutnya adalah memastikan solusimu benar di kasus-kasus ekstrem — bukan cuma cepat, tapi juga tidak gagal saat inputnya kosong, duplikat, atau berada tepat di batas constraint. Lanjut ke halaman "Edge Case & Testing" untuk melatih kebiasaan itu.
