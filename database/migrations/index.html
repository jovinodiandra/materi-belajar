// Database — mengubah skema yang sudah hidup di production

Ubah skema database tanpa mematikan lampu untuk pengguna.

Skema database jarang selesai di hari pertama. Kamu akan terus menambah kolom, mengubah tipe, memecah tabel, atau mengganti nama field — sementara aplikasi tetap harus jalan dan data tetap harus aman. Migration adalah cara terkontrol untuk melakukan itu: perubahan skema yang tercatat, bisa diulang, dan (idealnya) bisa dibatalkan. Deck ini membahas kenapa migration butuh disiplin, pola expand-contract untuk perubahan tanpa downtime, sampai tools yang dipakai tim beneran di production.

Sakit
ALTER TABLE — sekali jalan langsung mengunci tabel besar
Ide
Migration terkontrol — forward & rollback, tercatat, teruji
Pola
Expand-contract — ubah bertahap, tak pernah "big bang"
Batas
Tabel jutaan baris — migration biasa tetap bisa mengunci lama
Pakai
Online schema change — gh-ost, pt-osc, dsb untuk skala besar

◆ Buat apa ini? Kenapa pakai migration?

Given — tim mengubah skema lewat query manual langsung ke production, tanpa catatan urutan atau versi yang tersimpan di kode.

When — developer baru clone project lalu setup database lokal, atau tim men-deploy skema yang sama ke staging lalu ke production.

Then — skema di tiap environment perlahan drift (tidak ada yang tahu pasti versi mana yang jalan di mana), dan perubahan besar seperti ALTER TABLE dijalankan langsung tanpa rencana rollback yang jelas — persis skenario "cerita yang sering terulang" di bawah.

→ makanya kita pakai Database Migrations.

Akar masalah · Skema production itu hidup

Satu ALTER TABLE ceroboh bisa mematikan aplikasi

Di database yang masih kosong, ALTER TABLE terasa sepele — jalan dalam hitungan detik. Masalahnya muncul begitu tabel itu sudah berisi jutaan baris dan sedang dipakai user. Sebagian jenis perubahan skema butuh database menulis ulang seluruh tabel, dan selama itu terjadi, tabel bisa terkunci — semua query yang menyentuhnya ikut antre.

Perubahan skema database semestinya diperlakukan sebagai disiplin operasional — bukan sekadar developer menulis ALTER TABLE lalu berharap yang terbaik. Tiap migration butuh rencana rollback yang jelas dan pengujian sebelum menyentuh production.

— parafrase dari Laine Campbell & Charity Majors, Database Reliability Engineering (O'Reilly)
◆ Cerita yang sering terulang

Bayangkan sebuah tim menjalankan ALTER TABLE orders ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'pending' di tabel orders yang berisi puluhan juta baris, langsung di jam sibuk. Di banyak mesin database (versi lama, atau kombinasi tipe kolom tertentu), perintah ini menulis ulang seluruh tabel dan menahan lock sepanjang proses. Hasilnya: request checkout mulai timeout, tim baru sadar setelah dashboard error rate merah — padahal niatnya cuma menambah satu kolom kecil.

◆
Ini bukan soal "developer-nya ceroboh". Ini soal perubahan skema diperlakukan sama entengnya dengan commit kode biasa, padahal efeknya menyentuh data yang sedang dipakai ribuan orang secara bersamaan. Begitu kamu sadar bedanya, migration mulai butuh proses sendiri: direview, diuji dengan volume data mirip production, dan punya jalan mundur.
Konsep inti · Migration file & tool

Migration = perubahan skema yang tercatat & bisa diulang

Secara sederhana, migration adalah file berisi instruksi untuk mengubah skema database — biasanya diberi nomor urut atau timestamp, dan disimpan di repo bersama kode aplikasi. Tool migration (golang-migrate, Flyway, Prisma Migrate, dll) menjalankannya secara berurutan & mencatat migration mana saja yang sudah diterapkan ke database itu.

Tiap migration idealnya punya dua arah:

◆ Dua arah sebuah migration
Forwardup — terapkan perubahan (mis. tambah kolom)
Rollbackdown — batalkan perubahan (mis. hapus kolom itu)

Kalau up ternyata bermasalah di production, tim bisa jalankan down untuk mengembalikan skema — asal rollback-nya memang ditulis & diuji, bukan cuma formalitas kosong.

000123_add_email_verified.up.sqlSQL
-- forward: tambah kolom baru, nullable dulu supaya cepat
ALTER TABLE users
  ADD COLUMN email_verified BOOLEAN DEFAULT false;

-- index dibuat CONCURRENTLY biar tidak mengunci tabel saat build
CREATE INDEX CONCURRENTLY idx_users_email_verified
  ON users(email_verified);
000123_add_email_verified.down.sqlSQL
-- rollback: balikkan persis apa yang dilakukan up.sql
DROP INDEX IF EXISTS idx_users_email_verified;
ALTER TABLE users
  DROP COLUMN email_verified;

Nomor 000123 di depan nama file memastikan urutan eksekusi jelas & tidak ambigu antar developer. Tool migration menyimpan tabel kecil (mis. schema_migrations) untuk melacak migration mana yang sudah dijalankan di database itu, supaya migration yang sama tidak dieksekusi dua kali.

Pola inti · Expand & contract

Jangan ubah skema sekaligus — perluas dulu, baru persempit

Masalah terbesar migration bukan sintaks SQL-nya, tapi momen deploy: kode lama & kode baru sering hidup berdampingan sesaat (rolling deploy, beberapa instance masih versi lama). Kalau migration langsung mengubah/menghapus struktur lama, kode lama itu akan error seketika.

Daripada mengubah skema dalam satu langkah besar yang berisiko, ubah secara bertahap: tambahkan dulu struktur baru dan jalankan berdampingan dengan yang lama (expand), baru setelah semua konsumen pindah, struktur lama barulah dihapus (contract) — sehingga tak pernah ada momen "big bang" yang menegangkan.

— konsep expand and contract, dipopulerkan a.l. oleh Martin Fowler & komunitas continuous delivery
bad — satu migration, langsung gantiSQL
-- 002_rename_username.sql (satu langkah, satu deploy)
ALTER TABLE users
  RENAME COLUMN username TO handle;

-- kode lama yang masih SELECT/INSERT "username"
-- ERROR seketika migration ini jalan --
good — expand-contract, bertahapSQL
-- Tahap 1 (expand): tambah kolom baru, keduanya hidup
ALTER TABLE users ADD COLUMN handle VARCHAR(50);
-- app: dual-write ke username & handle sekaligus

-- Tahap 2: backfill data lama ke kolom baru
UPDATE users SET handle = username WHERE handle IS NULL;

-- Tahap 3: app baca dari "handle", tulis ke keduanya
-- Tahap 4 (contract, migration TERPISAH, setelah yakin aman):
ALTER TABLE users DROP COLUMN username;

Intinya: expand menambah tanpa merusak yang lama (kolom baru, tabel baru, index baru), lalu ada masa transisi di mana kode dual-write atau dual-read ke keduanya, dan baru setelah semua konsumen — semua service, semua instance — dipastikan pindah, contract menghapus struktur lama lewat migration terpisah. Tidak ada momen di mana skema & kode yang jalan tiba-tiba tidak sinkron.

◆ Praktik · Kebiasaan tim yang aman

Enam kebiasaan supaya migration tidak jadi insiden

Sebagian besar insiden migration bisa dicegah dengan kebiasaan sederhana ini — bukan tool canggih, tapi disiplin proses.

  • Migration kecil & reversible. Satu migration = satu perubahan logis. Selalu tulis & uji down-nya, jangan biarkan rollback jadi angan-angan.
  • Hindari lock lama di tabel besar. Pakai kolom nullable / default ringan dulu, index dengan CONCURRENTLY, dan hindari operasi yang mem-rewrite seluruh tabel di jam sibuk.
  • Backward-compatible dulu. Skema baru harus tetap bisa dibaca & ditulis oleh kode versi lama selama masa rolling deploy — itulah kenapa expand-contract penting.
  • Uji di staging dengan data realistis. Volume & bentuk data yang mirip production akan membongkar masalah lock/waktu eksekusi yang tak terlihat di database kosong.
  • Pisahkan deploy skema dari deploy perilaku. Migration & perubahan kode aplikasi yang bergantung padanya sebaiknya dipisah jadi beberapa deploy, supaya rollback lebih presisi.
  • Pantau saat & setelah migration jalan. Perhatikan lock wait, replication lag, dan error rate — migration yang "selesai tanpa error" tidak selalu berarti aman.
◆ Jenjang · Dari basic sampai skala besar

Tier belajar migration

Kedalaman yang kamu butuhkan soal migration bergantung pada skala datamu. Ini peta jenjangnya.

🌱 Beginner

Jalankan migration tool dasar

Fokus: paham alur up/down & menjalankannya lewat satu tool migration.

  • Buat migration baru dengan CLI (mis. golang-migrate, Prisma, Rails).
  • Pahami tabel pelacak versi migration.
  • Biasa menulis rollback, bukan cuma forward.
  • Jalankan migration di lokal & staging sebelum production.
⚙ Middle

Desain migration untuk aplikasi yang live

Fokus: migration yang backward-compatible saat aplikasi sedang dipakai user.

  • Terapkan pola expand-contract untuk rename/ubah tipe kolom.
  • Pisahkan deploy migration dari deploy kode yang bergantung.
  • Tahu operasi mana yang mengunci tabel & kapan hindari.
  • Uji migration dengan data volume mendekati production.
🚀 Advance

Migration tanpa downtime di tabel jutaan baris

Fokus: skala besar, traffic 24/7, toleransi lock nyaris nol.

  • Pakai online schema change tool (gh-ost, pt-osc) untuk tabel raksasa.
  • Kelola dual-write & backfill bertahap di traffic tinggi.
  • Rancang migration lintas-service dengan koordinasi rilis.
  • Punya observability khusus untuk migration (lag, lock, error).
◆ Harga · Terkontrol vs ad-hoc

Trade-off: migration lewat tool vs migration manual

Ada tim yang menjalankan migration lewat tool terkontrol, ada yang masih klik-klik langsung di database production. Bedanya bukan soal gengsi tool — tapi soal jejak & kemampuan mundur.

// Migration otomatis & terkontrol (tool)

  • Riwayat perubahan tercatat & bisa direview lewat PR.
  • Urutan eksekusi konsisten di semua environment.
  • Rollback jelas — tinggal jalankan down.
  • Bisa dijalankan otomatis di pipeline CI/CD.
  • Mudah direplikasi ke staging / environment baru.

// Migration manual / ad-hoc

  • Perubahan hanya ada di kepala orang yang menjalankannya.
  • Rawan beda skema antara staging & production.
  • Rollback = mengingat-ingat & menulis ulang query mundur.
  • Sulit direview sebelum menyentuh data nyata.
  • Susah diulang persis sama di environment lain.
◆ Catatan jujur

Migration lewat tool bukan jaminan aman — tool cuma menjamin tercatat & berurutan. Kamu tetap bisa menulis migration yang mengunci tabel besar lewat tool paling canggih sekalipun. Disiplin desain (expand-contract, migration kecil) tetap yang paling menentukan.

◆ Keputusan · Cukup migration biasa atau butuh tool khusus

Kapan migration biasa cukup, kapan butuh online schema change

Tidak semua migration butuh tool online schema change — itu overhead tambahan yang cuma masuk akal untuk kasus tertentu.

// Migration tool biasa cukup saat…

  • Tabel masih kecil/menengah (ratusan ribu baris ke bawah).
  • Ada maintenance window yang bisa ditoleransi.
  • Operasi ringan: tambah kolom nullable, index baru dengan CONCURRENTLY.
  • Trafik aplikasi rendah/menengah, bukan 24/7 kritikal.

// Butuh online schema change tool saat…

  • Tabel berisi puluhan/ratusan juta baris.
  • Aplikasi harus tetap up 24/7, nyaris tanpa maintenance window.
  • Operasi berat: ubah tipe kolom, rewrite index besar, rename yang menyentuh storage.
  • Lock sekecil apapun berdampak nyata ke SLA/uptime.
◆ Pertanyaan penentu

Tanyakan: "Kalau migration ini menahan lock 30 detik saja di jam sibuk, apakah itu masalah?" Kalau jawabannya "ya, jelas masalah" — dan tabelnya besar — saatnya lirik online schema change tool, bukan menjalankan ALTER TABLE polos.

Studi kasus · Di dunia nyata

Bagaimana tim besar menangani migration di production

Beberapa contoh nyata bagaimana tim dengan skala besar & data sensitif menangani perubahan skema — pola yang berulang: disiplin proses & tooling khusus untuk tabel besar.

// MySQL @ scale

GitHub & gh-ost

GitHub membangun gh-ost, tool open-source untuk menjalankan schema migration di MySQL tanpa mengunci tabel dan tanpa bergantung pada trigger di database — dirancang supaya perubahan skema di tabel besar tetap aman berjalan di belakang layar sambil aplikasi tetap melayani trafik.

// data finansial

Stripe & disiplin migration

Sebagai perusahaan pembayaran, Stripe dikenal menerapkan disiplin ketat pada perubahan skema data finansial — migration backward-compatible, ditinjau matang, dan dijalankan bertahap, karena kesalahan pada data transaksi punya konsekuensi nyata bagi pengguna & kepatuhan.

// multi-tenant scale

Shopify & skema di database besar

Shopify mengoperasikan armada database MySQL besar untuk menopang banyak toko sekaligus. Perubahan skema di skala ini butuh koordinasi & tooling migration yang konsisten agar perubahan pada satu bagian sistem tidak mengganggu toko-toko yang sedang aktif berjualan.

// pola umum industri

Online schema change jadi standar

Di banyak perusahaan dengan tabel besar & uptime kritikal, tool seperti pt-online-schema-change atau gh-ost menjadi bagian standar pipeline deploy — migration berat tidak lagi dijalankan langsung sebagai ALTER TABLE polos.

◆ Benang merahnya

Di semua kasus di atas, polanya sama: begitu skala data & risiko downtime naik, tim berhenti memperlakukan migration sebagai "jalankan SQL lalu selesai". Mereka membangun atau mengadopsi tooling khusus, menambah proses review, dan menganut perubahan bertahap — persis semangat expand-contract.

⚙ Ekosistem · Alat yang dipakai

Tools migration & online schema change

Kenali dulu nama-nama populernya. Sebagai pemula, cukup mulai dari satu tool migration yang cocok dengan bahasa/framework-mu (golang-migrate, Prisma, atau ActiveRecord).

// online schema change

gh-ost

Buatan GitHub. Menjalankan migration MySQL tanpa lock lama & tanpa trigger di database, dengan mengontrol beban lewat proses eksternal.

// multi-database

Flyway

Tool migration berbasis SQL file bernomor urut, populer di ekosistem Java tapi bisa dipakai lintas bahasa. Kuat di versioning & audit trail.

// Go ecosystem

golang-migrate

CLI & library migration ringan untuk Go, mendukung banyak database, format file up/down sederhana seperti contoh di atas.

// Node/TypeScript

Prisma Migrate

Bagian dari Prisma ORM. Migration di-generate otomatis dari perubahan schema, cocok untuk tim yang mendefinisikan model data secara deklaratif.

// Ruby on Rails

ActiveRecord Migrations

Sistem migration bawaan Rails yang lahir lama & jadi rujukan banyak tool migration lain — migration ditulis sebagai kelas Ruby dengan method up/down atau change.

// MySQL, Percona

pt-online-schema-change

Bagian dari Percona Toolkit. Menjalankan perubahan skema MySQL lewat tabel bayangan & trigger, lalu menukarnya — pendahulu pendekatan yang menginspirasi gh-ost.

◆ Tips pemula

Jangan buru-buru pakai online schema change tool kalau tabelmu masih kecil — itu menambah kompleksitas operasional yang belum kamu butuhkan. Kuasai dulu migration tool dasar & pola expand-contract; online schema change baru relevan begitu tabelmu benar-benar besar & downtime benar-benar mahal.

Penutup

Migration itu disiplin operasional, bukan sekadar SQL

Skema database yang sehat bukan yang tidak pernah berubah — tapi yang perubahannya bisa dilacak, diuji, dan dibatalkan kalau perlu. Itulah inti dari migration yang baik.

  • Migration = perubahan tercatat — punya arah forward & rollback yang jelas.
  • Tabel besar & live berbeda — operasi yang aman di tabel kosong bisa mengunci production.
  • Expand-contract dulu — tambah struktur baru, transisi, baru hapus yang lama.
  • Migration kecil & backward-compatible — lebih mudah direview & dibatalkan.
  • Uji dengan data realistis — database kosong menyembunyikan masalah lock & waktu eksekusi.
  • Online schema change saat perlu saja — bukan default, tapi jawaban untuk skala besar.

Aturan emasnya

Sebelum menjalankan migration ke production, tanyakan: "Kalau ini salah, seberapa cepat aku bisa membatalkannya — dan apakah kode lama masih bisa jalan selama transisi?" Kalau kamu bisa menjawab keduanya dengan yakin, migration-mu sudah di jalur yang aman.
