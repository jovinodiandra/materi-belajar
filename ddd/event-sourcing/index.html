Event Sourcing deep dive

Di materi DDD utama, Event Sourcing cuma dapat satu bab. Di sini kita bongkar mesinnya: anatomi event store, siklus decide → append → replay, dua contoh lengkap (dompet driver & siklus hidup trip), sampai bagian yang jarang diceritain orang: schema evolution, snapshot, dan cara-cara nyakitin diri sendiri. Tetap di dunia ride-hailing (RideGo).

◆ Buat apa ini? Kenapa pakai ini?

Given — sistem cuma menyimpan state/kondisi terakhir suatu data (misal saldo dompet driver di-UPDATE menimpa nilai lama).

When — ada kebutuhan audit trail, sengketa saldo, atau tim harus tahu kenapa data bisa jadi begini (bukan cuma tahu nilainya sekarang).

Then — riwayat perubahannya sudah hilang duluan, ditimpa UPDATE demi UPDATE, dan tidak bisa direkonstruksi lagi.

→ makanya kita pakai Event Sourcing: simpan setiap perubahan sebagai rekaman peristiwa (event) yang append-only, bukan cuma state akhir — state terkini tinggal hasil fold(events).

01
Ide dasar

Simpan log-nya, bukan fotonya

Cara nyimpan data yang biasa itu kayak foto: tiap perubahan, fotonya ditimpa foto baru — yang lama hilang. Event Sourcing nyimpan film-nya: semua kejadian direkam berurutan, dan "foto terkini" tinggal diputar ulang dari awal.

dua cara menyimpan kebenaranFOTO vs FILM
// STATE-ORIENTED — foto terkini, ditimpa terus
UPDATE dompet SET saldo = 150000 WHERE driver_id = 'D-4471';
// saldo kemarin? kenapa jadi segini? riwayatnya? → hilang. semoga ada tabel audit…

// EVENT-SOURCED — film lengkap, append-only
TripEarningCredited { amount: 100000, tripId: "T-991" }
Withdrawn           { amount:  30000, payoutId: "P-14" }
TripEarningCredited { amount:  80000, tripId: "T-1004" }
// saldo sekarang = fold(events) = 150.000 — dan SELURUH ceritanya masih ada
Analogi

Bank nggak pernah cuma nyimpan angka saldomu. Yang mereka simpan itu mutasi — rekening koran. Saldo hanyalah kesimpulan dari mutasi. Kalau ada sengketa, yang dibuka bukan "saldo", tapi riwayat transaksinya. Akuntansi udah "event sourcing" sejak ratusan tahun lalu — append-only ledger, nggak boleh dihapus, koreksi lewat entry baru. Software cuma baru menamainya.

Konsekuensi mendasarnya satu: log event = sumber kebenaran (source of truth). State terkini cuma turunan — bisa dihitung ulang kapan pun, bisa dibuang dan dibangun lagi. Ini bukan "nyimpan event di samping data" — event-nya adalah datanya.

02
Mesinnya

Anatomi Event Store

Event store itu sebenarnya sederhana: satu tabel append-only. Yang bikin dia "store" beneran cuma dua hal: stream (urutan event milik satu aggregate) dan version (nomor urut di dalam stream — kunci concurrency).

event_store.sql — cuma segini, seriusAPPEND-ONLY
CREATE TABLE event_store (
  stream_id    TEXT        NOT NULL,   -- milik siapa: 'wallet-D-4471'
  version      BIGINT      NOT NULL,   -- urutan ke berapa di stream itu: 1,2,3,…
  event_type   TEXT        NOT NULL,   -- 'TripEarningCredited'
  payload      JSONB       NOT NULL,   -- isi event-nya
  occurred_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (stream_id, version)      -- ← INI kuncinya (lihat bab 03)
);
-- aturan rumah: INSERT only. Nggak ada UPDATE. Nggak ada DELETE. Titik.

Isinya kira-kira begini — satu stream per dompet driver:

stream_idversionevent_typepayloadoccurred_at
wallet-D-44711WalletOpened{}07-01 09:00
wallet-D-44712TripEarningCredited{amount: 100000, tripId: "T-991"}07-24 08:14
wallet-D-44713Withdrawn{amount: 30000, payoutId: "P-14"}07-24 10:02
wallet-D-44714TripEarningCredited{amount: 80000, tripId: "T-1004"}07-24 13:47

◆ Pakai apa nyimpannya?

Bisa tabel PostgreSQL kayak di atas (paling umum buat mulai), bisa store khusus (EventStoreDB, Axon), bisa ledger khusus untuk domain uang. Yang penting jaminannya, bukan mereknya: append-only, urutan per stream terjaga, dan tulis-nya atomik. Mesinnya detail; disiplinnya yang wajib.

03
Siklus tulis

Menulis: load → decide → append

Di dunia ES, aggregate nggak pernah di-UPDATE. Menangani command artinya tiga langkah: load event lama → decide (cek aturan, hasilkan event baru) → append ke stream. Aturan bisnis tetap di aggregate — cuma outputnya sekarang berupa event, bukan mutasi.

DriverWallet.java — pola decide / applyAGGREGATE ala ES
public final class DriverWallet {
    private Money saldo = Money.ZERO;
    private long version = 0;

    // DECIDE — cek invariant, hasilkan event. NGGAK mengubah state di sini.
    public Withdrawn withdraw(Money amount, PayoutId payout) {
        if (saldo.lessThan(amount))
            throw new InsufficientBalanceException(saldo, amount);  // invariant!
        return new Withdrawn(amount, payout);
    }

    // APPLY — satu-satunya tempat state berubah. Dipanggil saat replay JUGA.
    private void apply(TripEarningCredited e) { saldo = saldo.plus(e.amount()); }
    private void apply(Withdrawn e)           { saldo = saldo.minus(e.amount()); }
}
alur satu command + concurrency checkOPTIMISTIC LOCKING
1. LOAD    events stream 'wallet-D-4471'          → dapat 4 event, versi terakhir = 4
2. FOLD    apply satu-satu                          → saldo di memori = 150.000
3. DECIDE  wallet.withdraw(50.000)                  → OK, hasilkan Withdrawn(50.000)
4. APPEND  INSERT (stream, version=5, Withdrawn…)   → sukses ✓

// kalau ADA YANG NYELIP di antara langkah 1 dan 4 (append versi 5 duluan):
4'. APPEND version=5  → GAGAL: duplicate key (stream_id, version)
5'. ulangi dari LOAD  → saldo terbaru ternyata tinggal 20.000 → withdraw DITOLAK ✓
// primary key (stream_id, version) = optimistic locking gratisan.
// dua transaksi nggak mungkin sama-sama nulis versi 5. uang aman.
◆ Kenapa decide & apply dipisah?

Karena apply() punya dua majikan: dipanggil saat replay (muat dari store) dan saat event baru diterima. Makanya dia harus polos total — nggak boleh ada validasi, nggak boleh ada side effect, cuma mutasi state. Semua aturan hidup di decide. Kalau kamu naruh if bisnis di apply(), event lama yang sah bisa mendadak "ditolak" waktu di-replay pakai aturan baru — dan aggregate-mu gagal dimuat. Aturan boleh berubah; sejarah nggak boleh ditolak.

04
Siklus baca

Membaca: replay → fold

"Terus tiap mau tahu saldo harus muter ulang semua event? Nggak lambat?" — pertanyaan pertama semua orang. Jawabannya: replay itu per-stream (satu dompet = puluhan–ribuan event, bukan jutaan), dan buat layar/list, yang dibaca bukan event store — tapi read model hasil proyeksi (bab 07).

Repository ala ES — reconstitute = replayFOLD
public final class EventSourcedWalletRepository implements DriverWalletRepository {

    public DriverWallet findById(DriverId id) {
        var events = store.readStream("wallet-" + id.value());  // urut by version
        var wallet = new DriverWallet();
        events.forEach(wallet::apply);      // ← fold: state = hasil lipatan semua event
        return wallet;
    }

    public void save(DriverWallet w, List<DomainEvent> newEvents) {
        store.append(w.streamId(), w.version(), newEvents);   // expectedVersion check
    }
}

Perhatikan yang menarik: interface repository-nya sama dengan dunia state-oriented (findById, save). Use case dan aggregate nggak sadar di bawahnya event store atau tabel biasa — itu detail persistence di balik port. Hexagonal architecture bikin ES jadi keputusan yang bisa diganti, bukan pernikahan seumur hidup.

◆ Bonus yang sering kelupaan: time travel

Karena state = fold(events), kamu bisa fold sebagian: "saldo dompet ini tanggal 30 Juni jam 23:59" = fold semua event sampai timestamp itu. Buat rekonsiliasi akhir bulan, investigasi sengketa, atau debugging "kok kemarin bisa gini?" — nggak ada padanannya di dunia UPDATE-menimpa.

05
Contoh 1 · Uang

Dompet driver: satu hari, satu stream

Ikuti satu hari dompet D-4471 dari sisi event — perhatikan kolom "saldo hasil fold" itu nggak pernah disimpan, dia selalu dihitung:

veventpayloadsaldo hasil foldcerita di baliknya
1WalletOpened{}0Driver lolos verifikasi, dompet dibuka
2TripEarningCredited{100.000, T-991}100.000Trip pagi selesai → event dari context Trip
3Withdrawn{30.000, P-14}70.000Driver narik buat bensin
4TripEarningCredited{80.000, T-1004}150.000Trip siang selesai
5WithdrawalRejected{500.000, "insufficient"}150.000Percobaan tarik 500rb — ditolak pun dicatat
6EarningAdjusted{-20.000, "refund T-991"}130.000Komplain penumpang valid → koreksi = event baru, bukan edit v2

Dua baris terakhir itu inti mentalitas ES: penolakan dicatat (v5 — emas buat deteksi fraud: "driver ini nyoba narik melebihi saldo 40× minggu ini"), dan koreksi = event kompensasi (v6 — bukan mengedit v2, persis kayak akuntan bikin jurnal koreksi, bukan men-tip-ex buku besar).

◆ Saat CS nanya "kok saldo saya berkurang 20 ribu?"

Di dunia state-oriented, jawabannya arkeologi: bongkar log aplikasi, tebak-tebakan. Di dunia ES, jawabannya baris v6: "ada refund atas trip T-991, ini waktunya, ini alasannya" — lengkap, pasti, dan nggak bisa dibantah, karena itulah datanya sendiri.

06
Contoh 2 · State machine

Trip lifecycle: event sebagai cerita perjalanan

Trip itu state machine — dan state machine itu kandidat alami buat ES, karena tiap transisi memang sebuah kejadian bermakna:

trip-state-machine.txt — transisi = eventSTATE MACHINE
  TripRequested ──▶ DriverAssigned ──▶ PassengerPickedUp ──▶ TripCompleted
        │                  │                    │
        └── TripCancelled(who, reason)         └── TripCancelled(who, reason, fee!)
            sebelum dapat driver: gratis        setelah dijemput: kena cancellation fee

Sekarang lihat satu trip bermasalah lewat kacamata event — ini stream trip-T-2210:

veventpayload pentingjam
1TripRequestedpickup: Kemang, dest: SCBD, estimasi: 42.00017:02:11
2DriverAssignedD-8102, eta: 4 menit17:02:19
3PassengerPickedUplokasi jemput aktual: 300m dari titik17:09:40
4TripCancelledby: PASSENGER, reason: "changed_mind", fee: 10.00017:11:05

Penumpang komplain: "kok saya kena biaya 10 ribu?!" CS tinggal baca streamnya kayak baca cerita: dibatalkan 90 detik setelah dijemput (v3 → v4), oleh penumpang sendiri, dengan alasan berubah pikiran → sesuai aturan, fee berlaku. Sengketa selesai dengan fakta, bukan debat. Dan tim fraud dapat bonus: pola "cancel setelah pickup" per user bisa di-query dari event historis kapan pun.

◆ Kejujuran dulu: apakah Trip WAJIB di-ES?

Nggak. Trip bisa hidup nyaman sebagai state biasa + domain event + tabel audit. ES jadi menarik buat trip kalau kebutuhan investigasi/audit/analitik historisnya berat (sengketa sering, fraud analysis, replay skenario). Kalau cuma butuh status terkini — state biasa lebih murah. Bandingkan dengan dompet (contoh 1) yang hampir selalu layak ES karena dia memang buku besar uang.

07
Jembatan ke layar

Projection: dari log jadi read model

Event store itu jago nyimpan kebenaran, tapi jelek buat query layar ("semua trip Kemang minggu ini yang dibatalkan"). Solusinya: projection — proses yang melahap event dan membangun read model berbentuk apa pun yang layar butuhkan. Di sinilah ES dan CQRS jadi pasangan alami.

satu log, banyak wajah1 SUMBER → N PROYEKSI
                        ┌──▶ [ projector saldo ]      ─▶ tabel wallet_balances      (aplikasi driver)
[ EVENT STORE ] ──feed──┼──▶ [ projector earnings ]   ─▶ tabel driver_daily_earnings (dashboard)
  (source of truth)     ├──▶ [ projector fraud ]      ─▶ tabel suspicious_patterns  (tim risk)
                        └──▶ [ projector analytics ]  ─▶ columnar DB                (BI / laporan)

// tiap projector: konsumen independen dengan posisi baca (checkpoint) sendiri.
// satu mati? yang lain jalan terus. nyusul dari checkpoint pas hidup lagi.
BalanceProjector.java — polos, idempotent, bisa diulangPROJECTOR
public final class BalanceProjector {
    public void on(TripEarningCredited e) { db.addToBalance(e.driver(), e.amount()); }
    public void on(Withdrawn e)           { db.addToBalance(e.driver(), e.amount().negate()); }
    // nggak ada keputusan bisnis di sini — cuma nyalin fakta ke bentuk lain
}
◆ Fitur pembunuhnya: REBUILD

Read model rusak? Salah hitung? Butuh dashboard baru yang kemarin belum kepikiran? Truncate tabelnya, replay semua event dari nol. Dashboard "pendapatan per area per jam" yang baru diminta PO hari ini bisa langsung terisi data setahun ke belakang — karena kebenarannya nggak pernah hilang. Di dunia state-oriented, data historis yang nggak sempat dicatat ya sudah, hilang selamanya.

08
Bagian yang jarang diceritain

Schema evolution: event lama ketemu kode baru

Ini pajak terbesar ES yang jarang masuk demo: event yang tersimpan itu immutable dan hidup selamanya, sementara kodemu terus berubah. Event Withdrawn versi 2024 harus tetap bisa dibaca kode versi 2027. Strateginya:

PerubahanStrategiContoh
Nambah fieldAdditive + default — event lama dibaca dengan nilai defaultWithdrawn dapat field baru channel; event lama dibaca sebagai channel = "BANK"
Ubah strukturUpcaster — penerjemah v1→v2 yang jalan saat bacaDulu amount long rupiah, sekarang object {amount, currency} → upcaster bungkus otomatis
Makna berubah totalEvent type BARU; yang lama tetap dibaca & di-handleWithdrawn dipecah jadi InstantPayoutRequested + ScheduledPayoutRequested
Salah data di event lamaEvent kompensasi — bukan editEarningAdjusted kayak di bab 05, ala jurnal koreksi akuntan
Edit / hapus event lama❌ Nggak pernah.— (sekali kamu edit sejarah, seluruh kepercayaan pada store runtuh)
WithdrawnUpcaster.java — penerjemah antar generasiUPCASTER
// jalan di jalur BACA, sebelum payload sampai ke apply(). event tersimpan nggak disentuh.
public final class WithdrawnUpcaster {
    public JsonNode upcast(JsonNode old) {
        if (old.has("currency")) return old;              // udah v2, lewat
        return json.object()                              // v1 → v2
            .put("amount",   old.get("amount"))
            .put("currency", "IDR")                      // default historis yang aman
            .put("payoutId", old.get("payoutId"));
    }
}
◆ Satu lagi yang WAJIB dipikirin di awal: data pribadi

"Nggak pernah dihapus" bentrok sama regulasi privasi (hak untuk dihapus). Praktik umumnya: PII jangan ditaruh di payload event — event simpan driverId, data pribadinya di store terpisah yang bisa dihapus. Alternatifnya crypto-shredding: payload PII dienkripsi per-user; "menghapus" = membuang kuncinya. Mikirin ini setelah jutaan event tersimpan = proyek migrasi yang menyakitkan.

09
Performa

Snapshot: biar nggak replay dari zaman batu

Dompet driver aktif 3 tahun = puluhan ribu event. Replay semuanya tiap ada command? Mulai kerasa. Solusinya snapshot: tiap N event, simpan "foto" state + nomor versinya. Load = foto terakhir + sisa event setelahnya.

load dengan snapshot — dari O(semua) jadi O(sisa)SNAPSHOT
// tanpa snapshot: fold 41.532 event  😵
// dengan snapshot tiap 1.000 event:

1. LOAD SNAPSHOT  wallet-D-4471 @ version 41000   → saldo: 230.000   (1 baris)
2. LOAD EVENTS    version > 41000                 → 532 event sisa
3. FOLD           apply 532 event                  → state mutakhir  ✓

CREATE TABLE snapshots (
  stream_id  TEXT   NOT NULL,
  version    BIGINT NOT NULL,   -- state ini hasil fold sampai versi berapa
  state      JSONB  NOT NULL,
  PRIMARY KEY (stream_id)        -- cukup simpan yang terbaru
);
◆ Aturan emas snapshot

Snapshot itu cache, bukan kebenaran. Boleh dihapus semua kapan pun — sistem tetap benar, cuma lebih lambat sampai snapshot kebentuk lagi. Konsekuensinya enak: format snapshot berubah? Buang aja semua, nggak perlu migrasi. Jangan pernah kebalik: yang disayang-sayang itu event-nya, bukan snapshotnya. Dan jangan bikin snapshot sebelum kerasa perlu — banyak stream (kayak trip: belasan event terus tamat) nggak akan pernah butuh.

10
Jebakan

Anti-pattern & kapan JANGAN pakai

ES itu alat tajam. Ini daftar cara paling populer orang teriris:

SMELL 1

Event rasa CRUD

DriverUpdated {field: "status", value: "x"} — itu bukan peristiwa bisnis, itu diff tabel. Event harus bermakna: DriverSuspended(reason). Kalau event-mu cuma mencerminkan kolom, kamu dapat semua ongkos ES tanpa satu pun manfaatnya.

SMELL 2

ES di mana-mana

Master data promo, profil, setting — di-ES semua "biar konsisten". Padahal nggak ada yang butuh sejarah NamaTokoDiubah. ES per aggregate/context, bukan per sistem.

SMELL 3

Ngedit event lama

"Ada typo di payload, update dikit ya" — begitu sejarah bisa diedit, seluruh nilai store-nya runtuh: audit nggak bisa dipercaya, replay nggak deterministik. Koreksi = event baru. Selalu.

SMELL 4

Query layar ke event store

Layar list yang fold ribuan stream on-the-fly. Event store itu buat nulis & replay per-stream; layar dilayani projection (bab 07).

SMELL 5

Event = kereta barang

Satu event bawa 40 field "biar lengkap". Event yang gemuk = kontrak yang rapuh + PII nyangkut di tempat yang nggak bisa dihapus. Bawa fakta secukupnya.

SMELL 6

"Kita udah pakai domain event, berarti udah ES"

Belum. Domain event = pemberitahuan; state-mu masih tabel biasa. ES = event-nya adalah state. Dua komitmen beda kelas — jangan ngaku-ngaku, nanti keliru ekspektasi.

Pakai ES kalau…

  • Domain-nya memang buku besar: uang, saldo, inventory
  • Audit & riwayat = kebutuhan inti, bukan nice-to-have
  • Sering ada sengketa/investigasi "kok bisa gini?"
  • Analitik historis & rebuild read model bernilai tinggi

Jangan ES kalau…

  • Cuma butuh state terkini (profil, master data, setting)
  • Tim belum nyaman dengan async, versioning, projection
  • Motivasinya "biar canggih" / ikut-ikutan
  • Domain masih sering berubah total — event yang salah desain itu selamanya
11
Sintesis

Penutup

Event Sourcing itu satu keputusan sederhana dengan konsekuensi panjang: jangan simpan kesimpulannya — simpan kejadiannya. Kesimpulan bisa dihitung ulang kapan aja; kejadian yang nggak dicatat hilang selamanya.

  • State = fold(events) — log-nya sumber kebenaran, state cuma turunan.
  • Decide vs apply — aturan di decide; apply polos biar replay selalu jalan.
  • (stream_id, version) — primary key sederhana yang sekaligus optimistic locking.
  • Koreksi = event kompensasi — sejarah nggak diedit, ditambah. Ala akuntan.
  • Layar dilayani projection — dan projection bisa di-rebuild dari nol, kapan pun.
  • Pajaknya nyata: schema evolution, snapshot, PII. Bayar cuma di domain yang pantas: uang & buku besar.

Lanjut ke mana

Kalau belum baca CQRS deep dive, baca — projection di bab 07 itu persis "Level 3"-nya CQRS, dan dua materi ini memang dua sisi koin yang sama. Habis itu, latihan terbaiknya: ambil satu aggregate di produkmu yang paling "buku besar", dan coba tulis daftar event-nya di kertas. Kalau daftar itu kebaca kayak cerita — dia kandidat ES.
