// Database — saat datamu penuh relasi, bukan sekadar dokumen mandiri

Pecah data jadi tabel rapi, sambungkan lagi lewat JOIN.

Kalau di halaman document kita bahas data yang bentuknya pohon mandiri, di sini kebalikannya: data yang saling merujuk ke mana-mana — pelanggan punya banyak pesanan, pesanan berisi banyak produk, produk dipakai oleh ribuan pesanan lain. Model relational (SQL) memecah data itu jadi tabel-tabel rapi yang saling terhubung lewat key, lalu menyatukannya kembali lewat JOIN — supaya satu fakta cuma hidup di satu tempat. Deck ini buat pemula: dari kenapa model ini lahir, konsep inti-nya, trade-off-nya, sampai kapan dipakai di production — diselingi kalimat dari sumber rujukan.

Akar masalah · Sebelum ada model relational

Data yang disalin ke mana-mana, gampang tak sinkron

◆ Buat apa ini? Kenapa pakai Relational Database?

Given — data disimpan tanpa struktur relasi (tabel + key): tiap entitas berdiri sendiri, tidak ada cara resmi buat menyambungkan satu fakta ke fakta lain.

When — satu pelanggan pesan berkali-kali, atau satu produk dipakai di banyak pesanan: data pelanggan/produk itu disalin ulang di banyak tempat, dan developer harus rakit sendiri relasinya di level aplikasi.

Then — data jadi tersebar & redundant, gampang tak sinkron (update di satu tempat, lupa di tempat lain), dan integritas mudah rusak karena tidak ada constraint yang menjaga relasi antar data.

→ makanya kita pakai Relational Database — pecah data jadi tabel yang saling terhubung lewat key, satu fakta cukup hidup di satu tempat, dan integritas dijaga lewat constraint & JOIN.

Sebelum Codd mengusulkan model relational, sistem penyimpanan data umumnya berupa flat file atau struktur hierarkis/network yang terikat erat dengan cara penyimpanan fisiknya. Kalau kamu pernah kerja dengan satu spreadsheet raksasa berisi semua data — nama pelanggan, alamat, daftar pesanan — dalam satu sheet datar, kamu sudah pernah rasakan masalah yang sama.

◆ Analogi — satu spreadsheet raksasa yang menampung segalanya

Bayangkan satu sheet Excel: tiap baris adalah satu item pesanan. Kolomnya berisi nama pelanggan, alamat, email, sekaligus nama produk & harga. Kalau satu pelanggan pesan 5 produk berbeda, namanya & alamatnya diketik ulang 5 kali. Suatu hari pelanggan itu pindah rumah — kamu harus mengganti alamat di 5 baris sekaligus. Lupa satu baris, datamu jadi tidak konsisten: alamat lama & baru hidup berdampingan di sheet yang sama.

Tiga masalah klasik yang muncul dari desain seperti ini biasa disebut anomali:

// Anomali yang muncul

  • Update anomaly — satu fakta disalin banyak baris, ubah satu berarti harus ubah semua salinannya.
  • Insert anomaly — mau tambah pelanggan baru tapi belum ada pesanan? Tidak ada tempat buat menyimpannya.
  • Delete anomaly — hapus satu-satunya pesanan seorang pelanggan, data pelanggannya ikut lenyap.

// Yang ditawarkan Codd

  • Data direpresentasikan sebagai relasi (tabel) yang berdiri sendiri.
  • Aplikasi tak perlu tahu detail penyimpanan fisik di baliknya.
  • Satu fakta cukup hidup di satu baris, dirujuk lewat key.

"Data semestinya direpresentasikan sebagai relasi — tabel — yang independen dari cara ia disimpan secara fisik, supaya aplikasi tidak perlu bergantung pada detail struktur penyimpanan internalnya."

— parafrase dari E.F. Codd, "A Relational Model of Data for Large Shared Data Banks" (1970)
Konsep inti · Tabel, key & normalisasi

Satu fakta, satu tempat — disambung lewat key

Model relational menyimpan data sebagai tabel (baris & kolom). Tiap tabel punya primary key (PK) — penanda unik tiap baris — dan tabel lain bisa merujuknya lewat foreign key (FK). Proses merapikan tabel supaya minim duplikasi disebut normalisasi.

◆ Normalisasi ringkas (1NF → 3NF)
1NFTiap kolom berisi nilai atomic — tidak ada daftar/array yang dijejalkan ke satu sel.
2NFSudah 1NF, dan tiap kolom non-key bergantung penuh pada seluruh primary key (relevan saat PK gabungan).
3NFSudah 2NF, dan tidak ada kolom non-key yang bergantung pada kolom non-key lain (hilangkan ketergantungan transitif).

Untuk kebanyakan aplikasi, sampai 3NF sudah cukup: data tersegmentasi rapi, minim duplikasi, gampang dijaga konsistensinya.

Contoh: satu pelanggan bisa punya banyak pesanan, satu pesanan berisi banyak item. Alih-alih menjejalkan semua ke satu tabel, kita pecah jadi tiga tabel yang saling terhubung lewat key:

skema relational — pelanggan, pesanan, item pesananSQL
CREATE TABLE customers (
  id          SERIAL PRIMARY KEY,
  nama        VARCHAR(120) NOT NULL,
  email       VARCHAR(160) UNIQUE NOT NULL
);

CREATE TABLE orders (
  id          SERIAL PRIMARY KEY,
  customer_id INTEGER NOT NULL REFERENCES customers(id),
  created_at  TIMESTAMP DEFAULT now()
);

CREATE TABLE order_items (
  id           SERIAL PRIMARY KEY,
  order_id     INTEGER NOT NULL REFERENCES orders(id),
  product_name VARCHAR(160) NOT NULL,
  qty          INTEGER NOT NULL,
  price        NUMERIC(12,2) NOT NULL
);

-- ambil 1 pesanan lengkap: sambung lagi lewat JOIN
SELECT o.id AS order_id, c.nama, oi.product_name, oi.qty, oi.price
FROM orders o
JOIN customers c   ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
WHERE o.id = 1042;

Nama & email pelanggan cukup hidup satu kali di tabel customers. Seribu pesanan dari pelanggan yang sama tidak perlu menyalin ulang datanya — cukup merujuk customer_id. Itulah inti normalisasi: satu fakta, satu tempat.

Konsep inti · JOIN & (de)normalisasi

Jenis JOIN, dan kapan boleh melanggar normalisasi

JOIN adalah cara menyatukan kembali tabel-tabel yang sudah dipecah. Jenisnya menentukan baris mana yang tetap muncul walau tidak ada pasangannya di tabel lain.

jenis-jenis JOINSQL
-- INNER JOIN: hanya baris yang punya pasangan di kedua tabel
SELECT c.nama, o.id
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;

-- LEFT JOIN: semua customer ikut, walau belum pernah pesan (o.id = NULL)
SELECT c.nama, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;

-- RIGHT JOIN: kebalikan LEFT — semua baris tabel kanan ikut
SELECT c.nama, o.id
FROM customers c
RIGHT JOIN orders o ON o.customer_id = c.id;

-- FULL OUTER JOIN: gabungan LEFT + RIGHT, semua baris dari kedua sisi
SELECT c.nama, o.id
FROM customers c
FULL OUTER JOIN orders o ON o.customer_id = c.id;

Aturan praktis: pakai INNER JOIN saat kamu hanya butuh data yang lengkap di kedua sisi, dan LEFT JOIN saat kamu ingin tetap menampilkan baris "utama" meski belum punya pasangan (mis. semua pelanggan, termasuk yang belum pernah checkout).

normalized — 3 tabel, dibaca lewat JOINSQL
-- orders + order_items, JOIN tiap kali baca
SELECT o.id, SUM(oi.qty * oi.price) AS total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;
-- akurat, tapi tiap laporan re-agregasi ulang
denormalized — kolom total disimpan langsungSQL
ALTER TABLE orders ADD COLUMN total_cache NUMERIC(12,2);

-- dibaca langsung, tanpa JOIN/agregasi
SELECT id, total_cache FROM orders;
-- cepat, tapi harus rajin disinkronkan tiap item berubah
◆ Kapan denormalisasi masuk akal

Normalisasi bukan dogma. Kalau satu query agregasi berat itu dijalankan ribuan kali per detik untuk dashboard atau laporan read-heavy, menyimpan kolom hasil hitungan (total_cache) yang di-update saat item berubah bisa jauh lebih murah daripada JOIN & GROUP BY berulang-ulang. Trade-off-nya: kamu memegang tanggung jawab menjaga total_cache tetap sinkron dengan order_items — biasanya lewat trigger, job terjadwal, atau ditulis eksplisit di kode aplikasi.

◆ Praktik · Kebiasaan yang menyelamatkanmu

Best practice kerja dengan database relational

Sebagian besar masalah performa & bug data di production bukan soal "SQL vs NoSQL" — tapi soal disiplin dasar yang dilewatkan. Beberapa yang paling sering menyelamatkan:

  • Index-kan foreign key. FK yang sering dipakai untuk JOIN atau WHERE tapi tidak diindeks bikin database melakukan full table scan setiap kali query jalan.
  • Hindari SELECT *. Sebutkan kolom yang benar-benar dipakai — lebih hemat bandwidth, lebih tahan terhadap perubahan skema, dan query planner bisa memakai index-only scan kalau kolomnya cocok.
  • Kelola skema lewat migration terkontrol. Setiap perubahan struktur tabel harus lewat file migration yang di-review & dijalankan berurutan — bukan diubah manual langsung di production.
  • Bungkus operasi multi-tabel dalam transaksi. Kalau menulis ke orders lalu order_items harus sukses bersamaan, pakai BEGIN … COMMIT supaya tidak ada state setengah jadi kalau salah satu gagal.
  • Waspadai N+1 query. Loop yang menjalankan satu query per baris (biasa muncul lewat ORM yang lazy-load relasi) bisa mengubah satu halaman jadi ratusan round-trip ke database — pakai JOIN atau eager loading.
  • Baca EXPLAIN sebelum menebak. Sebelum menambah index atau menulis ulang query, lihat dulu rencana eksekusinya — jangan optimasi berdasarkan asumsi.
◆ Jenjang · Belajar bertahap

Tier belajar relational database

Tidak perlu langsung paham query planner. Berikut jenjang yang masuk akal — dari bisa CRUD sampai bisa scaling database di production.

🌱 Beginner

Kenal skema, bisa CRUD & JOIN dasar

Fokus: paham struktur tabel dan bisa membaca/menulis data dengan benar.

  • Bikin tabel sederhana, tentukan primary & foreign key
  • SELECT dengan WHERE, ORDER BY, LIMIT
  • INSERT, UPDATE, DELETE yang aman (selalu pakai WHERE)
  • INNER JOIN & LEFT JOIN dua tabel
⚙ Middle

Desain skema untuk aplikasi nyata

Fokus: merancang skema yang tahan lama, bukan cuma jalan sekali coba.

  • Normalisasi sampai 3NF, tahu kapan boleh denormalisasi
  • Migration terkontrol & versioned
  • Index, constraint (UNIQUE, CHECK), transaksi dasar
  • Paham level isolasi transaksi secukupnya untuk hindari race condition
🚀 Advance

Optimasi & scaling di production

Fokus: menjaga database tetap cepat & tersedia saat traffic besar.

  • Membaca EXPLAIN / EXPLAIN ANALYZE untuk tuning query
  • Desain index lanjutan (composite, partial, covering index)
  • Replikasi & read replica untuk skala baca
  • Partitioning / sharding & connection pooling di skala besar
◆ Harga · Tidak ada makan siang gratis

Trade-off: integritas kuat vs fleksibilitas skema

Relational bukan "lebih baik" dari document/NoSQL — ia berbeda. Ia menang saat kamu butuh konsistensi & relasi yang rumit, dan terasa lebih berat saat kamu butuh iterasi skema super cepat.

"Model relational berhasil menggeneralisasi cara pemrosesan transaksi maupun pemrosesan batch dilakukan — dan JOIN serta query yang fleksibel itulah yang membuatnya tetap relevan puluhan tahun setelah pertama kali diperkenalkan."

— parafrase dari Martin Kleppmann, "Designing Data-Intensive Applications", Bab 2

// Kekuatan relational

  • Integritas data dijaga ketat oleh database (FK, constraint).
  • JOIN & query lintas-entitas sangat fleksibel.
  • Transaksi ACID matang — aman untuk data kritikal.
  • Skema eksplisit → bug bentuk data ketahuan lebih awal.

// Yang kamu korbankan

  • Ubah struktur data = migrasi, bukan sekadar tulis field baru.
  • Skema kaku kurang cocok untuk data yang bentuknya sangat beragam.
  • Query lintas banyak tabel/JOIN besar bisa mahal di skala sangat besar.
  • Scaling horizontal (sharding) lebih rumit dibanding banyak NoSQL.
◆ Pertanyaan penentu

Tanyakan ke datamu: "Apakah data ini saling merujuk ke banyak entitas lain, dan aku butuh laporan/JOIN lintas-entitas?" Kalau ya — pesanan-pelanggan-produk, transaksi keuangan, relasi many-to-many — relational akan menyelamatkanmu dari duplikasi. Kalau datamu justru berbentuk dokumen mandiri yang jarang dihubungkan ke entitas lain, pertimbangkan document DB (lihat halaman document).

◆ Catatan zaman sekarang

Garis pemisahnya makin kabur. Postgres & MySQL kini punya tipe JSON/JSONB untuk menyimpan dokumen di dalam tabel relational, jadi kamu tak selalu harus memilih satu model secara mutlak. Banyak aplikasi production memakai relational sebagai tulang punggung, lalu menambah NoSQL/cache di tempat yang memang butuh fleksibilitas atau kecepatan baca ekstrem.

Studi kasus · Di dunia nyata

Kenapa tim besar tetap bertahan dengan relational

Empat contoh di mana database relational jadi tulang punggung sistem berskala besar — perhatikan polanya: butuh konsistensi kuat, relasi kompleks, atau query fleksibel yang sulit digantikan.

// fintech

Stripe

Kasus: memproses pembayaran & data finansial yang tidak boleh salah sedikit pun. Kenapa relational: transaksi ACID & integritas ketat sangat penting saat uang berpindah tangan. Tool: PostgreSQL.

// design tool

Figma

Kasus: menyimpan struktur file desain, tim, & kepemilikan objek yang saling terhubung di skala besar. Kenapa relational: relasi antar entitas (user, tim, file, permission) kompleks & butuh konsistensi. Tool: PostgreSQL.

// social media

Instagram

Kasus: data pengguna, follow-graph, & postingan dalam jumlah sangat besar. Kenapa relational: tetap memilih model relational, lalu di-shard secara horizontal untuk menampung skala. Tool: PostgreSQL (sharded).

// dev platform

GitLab & GitHub

Kasus: repository, issue, pull request, permission — semuanya saling terhubung erat. Kenapa relational: relasi antar-entitas yang padat butuh JOIN & integritas referensial yang solid. Tool: PostgreSQL / MySQL.

◆ Benang merahnya

Di semua kasus di atas: datanya saling merujuk ke banyak entitas lain, butuh konsistensi kuat (uang, izin akses, kepemilikan), dan sering butuh query/laporan lintas-entitas yang tidak diketahui bentuknya di muka. Itulah kekuatan relational — skema eksplisit & JOIN yang fleksibel membuatnya tahan menghadapi kebutuhan query baru tanpa mendesain ulang seluruh model data.

◆
Bukan berarti relational selalu jadi satu-satunya database. Tim-tim di atas juga memakai cache (Redis), search engine, atau data warehouse di sampingnya untuk kebutuhan spesifik — relational tetap jadi sumber kebenaran (source of truth) untuk data inti yang butuh integritas.
⚙ Ekosistem · Alat yang dipakai

Tools relational database

Cukup kenali nama populernya & kapan kira-kira dipakai. Sebagai pemula, mulai dari SQLite (lokal, tanpa setup) lalu PostgreSQL (paling lengkap fiturnya).

// paling lengkap

PostgreSQL

Open-source, sangat matang, fitur lengkap (JSONB, full-text search, extension). Pilihan default yang aman untuk hampir semua aplikasi baru.

// paling populer

MySQL

Cepat & sederhana untuk kasus umum, ekosistem hosting & tooling luas. Tulang punggung banyak aplikasi web besar.

// tanpa server

SQLite

Database dalam satu file, tanpa proses server terpisah. Cocok untuk aplikasi lokal/mobile atau belajar SQL tanpa setup rumit.

// fork MySQL

MariaDB

Fork open-source dari MySQL, kompatibel API-nya, sering dipakai sebagai pengganti drop-in di banyak distro & hosting.

// akses lewat kode

ORM populer

Menulis query lewat objek/kode, bukan SQL mentah: Prisma & TypeORM (Node), SQLAlchemy & Django ORM (Python), ActiveRecord (Rails).

// cloud managed

Amazon RDS · Cloud SQL

Layanan terkelola (AWS / GCP / Azure) untuk PostgreSQL/MySQL — backup, replikasi, & patching diurus penyedia.

◆ Tips pemula

Bingung memilih? Mulai belajar SQL dasar dengan SQLite (tidak perlu instalasi server), lalu pindah ke PostgreSQL begitu kamu mulai membangun aplikasi sungguhan — fiturnya paling lengkap & jadi default de-facto di banyak tim.

Penutup

Pecah rapi, sambung lewat JOIN — bukan sesuai tren

Model relational lahir dari kebutuhan menyimpan data tanpa duplikasi & tanpa terikat detail penyimpanan fisik. Ia bersinar saat datamu penuh relasi & butuh konsistensi kuat, dan terasa lebih berat saat kamu butuh skema yang berubah-ubah cepat.

  • Satu fakta, satu tempat — normalisasi menghindari duplikasi & anomali data.
  • Key menyambungkan tabel — primary key & foreign key adalah tulang punggungnya.
  • JOIN itu fleksibel — bisa menjawab pertanyaan lintas-entitas yang belum terpikirkan di muka.
  • Denormalisasi itu pilihan sadar — bukan default, dipakai saat performa baca benar-benar menuntutnya.
  • Skema eksplisit — bug bentuk data ketahuan lebih awal, ditukar dengan migrasi saat berubah.
  • Pilih dari bentuk relasi datamu — bukan karena ikut tren SQL atau NoSQL.

Aturan emasnya

Tanya: "Apakah datamu saling merujuk ke banyak entitas lain, dan aku butuh integritas & laporan lintas-entitas yang fleksibel?" Kalau ya, relational memberimu fondasi yang kokoh & tahan lama. Kalau datamu lebih sering berdiri sendiri sebagai dokumen mandiri, lihat kembali halaman document — tidak ada model yang menang untuk segalanya, pilih yang paling pas dengan bentuk relasi datamu.
