Akar masalah · Cek terhubung berulang kali

Jaringan terus bertambah, pertanyaannya terus datang

Bayangkan kamu mengelola peta jaringan jalan antar kota. Jalan baru terus dibangun, dan tiap saat ada pertanyaan: "apakah kota A bisa dicapai dari kota B?" Kalau tiap pertanyaan dijawab dengan BFS/DFS dari nol ke seluruh graf, itu O(V + E) per query — dan kalau ada ribuan query di tengah ribuan penambahan jalan, biayanya menumpuk cepat.

◆ Buat apa ini? Kenapa pakai ini?

Given — sistem cuma punya daftar edge mentah (pertemanan, sambungan jalan, sambungan pixel gambar); untuk tahu "apakah A dan B satu grup?" satu-satunya cara adalah BFS/DFS ulang dari A menelusuri seluruh graf.

When — edge baru terus ditambahkan (union) sambil query "sudah tersambung?" (find) datang bergantian ribuan kali — misalnya saat membangun Kruskal's MST, deteksi cycle di graf, hitung connected components pada gambar, atau cek friend-circle di jejaring sosial.

Then — tanpa struktur khusus, tiap query re-traversal O(V + E), dan tiap edge baru berpotensi harus scan ulang seluruh graf cuma untuk cek "bikin cycle atau tidak" — totalnya meledak jadi lambat begitu graf dan jumlah query membesar.

→ makanya kita pakai Union-Find (Disjoint Set).

◆ Analogi — lingkaran pertemanan yang melebur

Pikirkan grup teman di sekolah. Awalnya tiap orang "grup sendiri". Ketika dua orang berteman, grup mereka digabung jadi satu lingkaran. Nanti ada yang tanya: "apakah Budi dan Sari satu circle pertemanan?" — kamu tidak perlu menelusuri ulang semua pertemanan dari awal, cukup lihat siapa "kepala grup" masing-masing. Kalau kepala grupnya sama, mereka satu circle. Itulah inti union-find: tiap grup punya satu representative, dan mengecek "satu grup?" cukup membandingkan dua representative.

Union-Find dirancang persis untuk pola ini: union (gabungkan dua grup) dan find (cari representative/root dari grup suatu elemen) yang dipanggil berulang-ulang, diselingi satu sama lain, pada struktur yang terus berubah. Dua operasi ini yang jadi jantung struktur datanya.

Konsep inti · Struktur & dua operasi

Parent array, find(), dan union()

Intinya cuma satu array: parent[i] menyimpan "siapa induk dari elemen i". Root sebuah grup adalah elemen yang parent[i] == i (induknya diri sendiri). find(x) menyusuri parent sampai ketemu root. union(x, y) menyambungkan root dari grup x ke root dari grup y.

◆ Dua operasi inti
find(x)→ telusuri parent[x] sampai akar grup ditemukan
union(x,y)→ find root keduanya, sambungkan satu root ke root lain
connected?→ find(x) == find(y)

Inisialisasi: tiap elemen adalah parent-nya sendiri — parent[i] = i untuk semua i. Artinya di awal, setiap elemen adalah grupnya sendiri-sendiri.

UnionFind.java — path compression + union by rankJava
class UnionFind {
    private final int[] parent;
    private final int[] rank;

    public UnionFind(int n) {
        parent = new int[n];
        rank = new int[n];
        for (int i = 0; i < n; i++) {
            parent[i] = i;   // tiap elemen jadi parent-nya sendiri
            rank[i] = 0;
        }
    }

    // find dengan PATH COMPRESSION
    public int find(int x) {
        if (parent[x] != x) {
            parent[x] = find(parent[x]); // ratakan pohon sambil naik
        }
        return parent[x];
    }

    // union dengan UNION BY RANK
    public void union(int x, int y) {
        int rootX = find(x);
        int rootY = find(y);
        if (rootX == rootY) return; // sudah satu grup

        if (rank[rootX] < rank[rootY]) {
            parent[rootX] = rootY;
        } else if (rank[rootX] > rank[rootY]) {
            parent[rootY] = rootX;
        } else {
            parent[rootY] = rootX;
            rank[rootX]++;
        }
    }

    public boolean connected(int x, int y) {
        return find(x) == find(y);
    }
}

Perhatikan baris parent[x] = find(parent[x]) — inilah path compression: setiap kali find() menyusuri rantai parent, ia langsung menempelkan tiap node yang dilewati ke root, sehingga pemanggilan berikutnya jadi jauh lebih pendek. Sedangkan rank[] memastikan pohon kecil selalu menempel ke pohon yang lebih "tinggi", bukan sebaliknya — itu union by rank.

Kenapa cepat · Dua optimasi, satu keajaiban

Path compression + union by rank = hampir O(1)

Tanpa optimasi, union-find naif bisa berubah jadi rantai panjang (linked-list terselubung) — find() jadi O(n) per panggilan di kasus terburuk. Dengan dua trik sederhana, ia jadi nyaris konstan.

“Path compression & union by rank mengubah struktur data ini dari performa buruk menjadi hampir konstan secara amortized — sebuah pencapaian algoritmik yang elegan.”

— berdasarkan pembahasan Robert Sedgewick & Kevin Wayne, Algorithms
naif — tanpa optimasiJava
int find(int x) {
    while (parent[x] != x) {
        x = parent[x]; // jalan satu-satu, tidak diratakan
    }
    return x;
}

void union(int x, int y) {
    int rootX = find(x);
    int rootY = find(y);
    parent[rootX] = rootY; // asal tempel, bisa bikin pohon miring
}
// union berurutan 0-1, 1-2, 2-3, ... bikin rantai lurus
// find() elemen terjauh = O(n)
optimized — path compression + rankJava
int find(int x) {
    if (parent[x] != x) {
        parent[x] = find(parent[x]); // ratakan sambil naik
    }
    return parent[x];
}

void union(int x, int y) {
    int rootX = find(x), rootY = find(y);
    if (rootX == rootY) return;
    // pohon pendek nempel ke pohon tinggi
    if (rank[rootX] < rank[rootY]) parent[rootX] = rootY;
    else if (rank[rootX] > rank[rootY]) parent[rootY] = rootX;
    else { parent[rootY] = rootX; rank[rootX]++; }
}
// pohon tetap pendek & rata → find() nyaris O(1)

Intuisinya begini: union by rank mencegah pohon jadi tinggi sejak awal — pohon pendek selalu ditempel di bawah pohon tinggi, jadi tinggi pohon paling banter naik logaritmik. Path compression lalu meratakan rantai setiap kali dilewati, sehingga panggilan find() berikutnya nyaris langsung mengenai root. Gabungan keduanya membuat biaya rata-rata per operasi mendekati konstan — secara formal dibatasi oleh inverse Ackermann function (ditulis α(n)), yang nilainya untuk data seukuran apa pun yang realistis (bahkan sampai jumlah atom di alam semesta) tidak pernah lebih dari 4-5. Jadi cukup dianggap "konstan kecil" dalam praktik, tanpa perlu menghafal rumusnya.

◆
"Hampir O(1)" itu amortized, bukan garansi tiap panggilan tunggal instan. Panggilan find() pertama pada rantai panjang tetap harus menyusuri jalur itu sekali — tapi setelah dikompres, semua panggilan berikutnya jadi sangat murah. Rata-rata sepanjang banyak operasi itulah yang mendekati konstan.
◆ Praktik · Cara pakai yang benar

Best practice implementasi union-find

Union-find gampang salah pakai kalau optimasinya dilupakan sebagian. Berikut kebiasaan yang bikin implementasimu selalu cepat dan benar.

  1. Selalu pakai path compression + union by rank/size bersamaan. Salah satu saja masih bisa O(log n) per operasi; keduanya bareng yang memberi hampir O(1) amortized.
  2. Inisialisasi tiap elemen sebagai parent-nya sendiri — parent[i] = i. Ini menandakan "grup awal" sebelum union pertama terjadi.
  3. Tulis find() secara rekursif untuk path compression yang bersih, atau versi iteratif dua-pass kalau khawatir stack overflow pada n sangat besar.
  4. Pakai union by size sebagai alternatif rank — keduanya setara secara teori; size kadang lebih intuitif karena langsung merepresentasikan jumlah elemen dalam grup.
  5. Cek root dulu sebelum union — kalau find(x) == find(y), jangan lakukan apa-apa; ini juga cara alami mendeteksi cycle di graf undirected.
  6. Jangan bandingkan elemen mentah untuk cek "satu grup" — selalu bandingkan hasil find() keduanya, bukan parent langsungnya, karena parent belum tentu root.

◆ Harga · Tidak ada makan siang gratis

Union-find vs BFS/DFS ulang

Union-find bukan pengganti BFS/DFS — ia unggul untuk pola pemakaian yang spesifik: banyak query "terhubung?" yang diselingi banyak penggabungan grup.

// Union-Find unggul saat…

  • Query connected(x, y) dipanggil berulang kali.
  • Graf terus berubah (edge ditambah seiring waktu).
  • Kamu cuma butuh ya/tidak terhubung, bukan path-nya.
  • Banyak union & find diselingi dalam satu proses (mis. Kruskal).

// BFS/DFS lebih cocok saat…

  • Cek terhubung cuma sekali, tidak berulang.
  • Kamu butuh path aktual-nya, bukan cuma status terhubung.
  • Butuh jarak/langkah terpendek antar node.
  • Graf tidak berubah & dieksplor sekali di awal.

“Disjoint-set data structure mendukung aplikasi yang butuh melacak partisi elemen ke dalam grup yang saling lepas, lewat operasi MAKE-SET, UNION, dan FIND-SET.”

— berdasarkan pembahasan Thomas H. Cormen dkk., Introduction to Algorithms (CLRS)
◆ Catatan penting

Union-find tidak menyimpan struktur graf yang lengkap — hanya "siapa satu grup dengan siapa". Kalau kamu butuh tahu jalur konkret dari A ke B (bukan cuma status terhubung), union-find tidak bisa membantu; kamu tetap butuh BFS/DFS atau algoritma pencarian jalur lainnya.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai union-find

Aturan praktisnya: kalau kamu berulang kali menjawab "apakah dua elemen ini satu grup?" di graf yang terus digabung, pakai union-find. Kalau butuh detail jalur atau graf statis yang cukup dieksplor sekali, BFS/DFS lebih pas.

// Pakai union-find saat…

  • Deteksi cycle saat membangun graf undirected.
  • Menghitung jumlah connected components.
  • Membangun MST dengan Kruskal's algorithm.
  • Dynamic connectivity — edge ditambah seiring waktu.
  • Grouping/clustering elemen berdasarkan relasi.

// Jangan, pilih cara lain saat…

  • Butuh jalur aktual, bukan cuma status terhubung.
  • Butuh jarak/bobot jalur terpendek (pakai Dijkstra/BFS).
  • Edge bisa dihapus — union-find susah menangani "un-union".
  • Graf statis & cuma dieksplor satu kali saja.
◆ Pertanyaan penentu

Tanyakan: "Apakah aku akan bertanya 'terhubung atau tidak' berkali-kali, sambil graf terus bertambah edge-nya?" Kalau ya → union-find. Kalau kamu cuma butuh jawaban sekali, atau butuh tahu jalurnya — BFS/DFS (atau algoritma shortest-path) lebih tepat.

Studi kasus · Di dunia nyata

Di mana union-find dipakai di production

Tiga skenario nyata di mana union-find jadi struktur data yang tepat — perhatikan polanya: grup yang terus digabung, lalu ditanya berulang kali.

// network design

Kruskal's algorithm — jaringan biaya minimum

Kasus: membangun jaringan kabel, pipa, atau listrik yang menghubungkan banyak titik dengan total biaya seminimal mungkin. Kenapa union-find: Kruskal mengurutkan edge dari termurah, lalu union-find dipakai untuk cek cepat "kalau edge ini ditambah, apakah bikin cycle?" — tanpa itu, deteksi cycle jadi lambat.

// social graph

Deteksi komponen terhubung di social network

Kasus: mencari kelompok-kelompok pengguna yang saling terhubung (langsung/tidak langsung) lewat pertemanan atau interaksi. Kenapa union-find: tiap relasi pertemanan baru cukup satu union(); menghitung jumlah komunitas terpisah cukup hitung jumlah root unik.

// image processing

Connected component labeling di gambar biner

Kasus: memberi label pada gugusan piksel yang saling bersebelahan dalam gambar biner (mis. mendeteksi objek terpisah dalam citra hasil segmentasi). Kenapa union-find: tiap piksel awalnya grup sendiri; piksel tetangga yang sama-sama "aktif" di-union, hasil akhirnya tiap objek punya satu root/label unik.

◆ Benang merahnya

Di semua kasus di atas: ada banyak elemen kecil yang digabung secara bertahap menjadi grup-grup lebih besar, dan yang ditanyakan berulang-ulang cukup soal keanggotaan grup — bukan jalur atau jarak antar elemen. Begitu kebutuhan bergeser ke jalur konkret atau bobot jalur terpendek, tim biasanya menambah BFS/DFS/Dijkstra di sampingnya, bukan memaksakan union-find untuk itu.

Penutup

Struktur kecil, dampak besar di algoritma graf

Union-find lahir dari kebutuhan sederhana: cek "satu grup atau tidak" berkali-kali, tanpa mengulang penelusuran graf dari nol. Dengan path compression & union by rank, ia jadi salah satu struktur data paling efisien yang bisa kamu tulis dalam belasan baris kode.

  • Masalah — cek terhubung berulang kali di graf yang terus berubah.
  • Struktur — parent array, tiap elemen mulai sebagai parent-nya sendiri.
  • find() — telusuri sampai root, ratakan dengan path compression.
  • union() — sambungkan root, pohon kecil ke pohon besar (union by rank/size).
  • Hasilnya — hampir O(1) amortized, dibatasi inverse Ackermann function.
  • Dipakai di — Kruskal's MST, connected components, dynamic connectivity.
