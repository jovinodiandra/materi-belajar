Config Management

Satu image aplikasi, banyak lingkungan. Yang berbeda hanya konfigurasinya — dan konfigurasi itu dikelola dengan rapi.

$ Satu mobil, beda setelan kursi untuk tiap pengemudi.

Build ulang aplikasi hanya untuk mengganti URL database staging.

🔨

Config ditanam di build

Beda lingkungan = beda build.

🔀

Yang dites ≠ yang dirilis

Image staging dan produksi berbeda.

🎲

Config tersebar

Sebagian di kode, sebagian di server, sebagian di kepala orang.

Build sekali, atur di luar

satu image + config per lingkungan

◆ Buat apa ini? Kenapa pakai ini?

Given — aplikasi berjalan di beberapa lingkungan: dev, staging, produksi.

When — konfigurasi ditanam di kode atau di build.

Then — harus build ulang untuk tiap lingkungan, dan yang dites bukan yang dirilis.

→ makanya kita pakai config management — supaya satu image berjalan di semua lingkungan dengan config berbeda.

Gagal cepat kalau config salah

✗ ketahuan saat dipakai
String url = System.getenv("PAYMENT_URL");
// null, tapi aplikasi tetap start…
// 3 jam kemudian user checkout:
// NullPointerException
✓ divalidasi saat start
@ConfigurationProperties("payment")
@Validated
record PaymentConfig(
    @NotNull URI url,
    @Min(100) int timeoutMs) {}
// config salah → aplikasi menolak start
Lebih baik gagal saat deploy daripada gagal di depan user.
