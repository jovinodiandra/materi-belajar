// Problem Solving — dari jawaban paling naive ke jawaban paling efisien

Mulai dari solusi yang pasti benar, baru cari yang cepat.

Brute force itu bukan solusi buangan yang malu-malu kamu tulis lalu buru-buru dihapus. Ia adalah titik berangkat yang sah — coba semua kemungkinan, pasti dapat jawaban yang benar, meski lambat. Dari sana kamu mengamati di mana kerja yang berulang-ulang terjadi, lalu memangkasnya sedikit demi sedikit sampai jadi solusi yang optimal. Deck ini bukan katalog algoritma — ini tentang proses-nya: mindset iteratif dari naive ke efisien.

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu dikasih soal baru, belum ada satu baris kode pun yang jalan, dan kepalamu langsung berusaha mikirin algoritma paling efisien dari awal.

When — waktu berjalan, kamu bolak-balik mikirin pendekatan "pintar" (misal langsung cari trik O(n log n) atau formula matematis) tapi belum berhasil membuktikannya benar.

Then — deadline mendekat, editor masih kosong, tidak ada solusi yang bisa dites atau diserahkan sama sekali — padahal solusi lambat yang benar sebenarnya lebih baik daripada solusi cepat yang tidak pernah selesai ditulis.

→ makanya kita pakai Brute Force to Optimal: tulis dulu solusi coba-semua-kemungkinan yang pasti benar, baru amati kerja berulang di dalamnya dan pangkas sedikit demi sedikit jadi optimal.

Akar masalah · Kenapa mulai dari brute force

Kamu stuck bukan karena soal sulit — tapi karena maunya langsung optimal

Pola yang sering terjadi: dikasih soal, kepala langsung mikir "algoritma paling efisien apa ya" — dan karena insight itu belum kelihatan, tangan berhenti mengetik sama sekali. Bukan soalnya yang mustahil, tapi target awalnya kebesaran. Kamu melompat ke langkah terakhir sebelum menyelesaikan langkah pertama.

Kalau kamu tidak bisa memecahkan masalah yang diberikan, coba cari dulu masalah yang lebih sederhana atau lebih longgar syaratnya yang berkaitan dengannya — pecahkan itu dulu, lalu pakai sebagai pijakan.

— parafrase gagasan George Pólya, How to Solve It
◆ Analogi — memahat patung, bukan mengukir detail wajah dari balok kosong

Pemahat tidak langsung mengukir lekuk mata dari balok marmer utuh. Dia mulai dari bentuk kasar — buang bagian besar yang jelas-jelas bukan bagian patung, sampai dapat siluet yang mendekati. Detail wajah, lipatan kain, semuanya dikerjakan belakangan, setelah bentuk dasarnya ada dan bisa dilihat. Brute force adalah bentuk kasar itu: jawaban yang jelek & lambat, tapi bentuknya sudah benar — dan dari situ kamu punya sesuatu untuk dihaluskan.

Menulis brute force dulu punya efek psikologis yang sering diremehkan: begitu kamu punya satu solusi yang jalan, rasa panik hilang. Sisa waktumu berubah dari "harus menemukan sesuatu dari nol" jadi "harus membuat yang sudah ada ini lebih cepat" — masalah yang jauh lebih sempit dan lebih mudah dipegang.

Konsep inti · Coba semua kemungkinan

Contoh: cari dua angka dalam array yang jumlahnya = target

Soal klasik: diberi larik angka nums dan sebuah target, cari indeks dua angka yang kalau dijumlah hasilnya sama dengan target. Cara paling naive: coba semua pasangan yang mungkin, satu per satu, sampai ketemu.

brute-force.js — coba semua pasangan (i, j)JS
// Coba SEMUA pasangan (i, j) dengan i < j
function twoSumBruteForce(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) {
        return [i, j];
      }
    }
  }
  return null; // tidak ada pasangan yang cocok
}

Kenapa ini benar? Karena tidak ada satu pun pasangan (i, j) yang terlewat — loop luar mencoba tiap angka sebagai kandidat pertama, loop dalam mencoba semua angka setelahnya sebagai kandidat kedua. Kalau jawabannya ada, pasti ketemu. Ongkosnya: O(n²) waktu (loop bersarang), O(1) ruang tambahan. Untuk n kecil, ini cepat lebih dari cukup — dan yang paling penting, ini benar.

◆ Prioritas pertama: benar, baru cepat

Solusi brute force yang benar selalu lebih berharga daripada solusi optimal yang belum tentu benar. Sebelum mikirin kecepatan, pastikan dulu kamu paham betul apa yang harus dihitung — kode di atas adalah cara paling literal untuk menerjemahkan definisi soal jadi kode.

Optimasi · Dari coba-semua ke hash map

Redundant work: kita menghitung ulang hal yang sama berkali-kali

Lihat lagi loop dalam di brute force: untuk tiap i, kita scan ulang sisa array mencari pasangannya. Tapi setiap kali kita geser i ke depan, angka-angka sebelumnya sudah pernah kita lihat — kita cuma tidak mengingatnya. Itulah redundant work-nya: informasi yang sudah ada, dibuang, lalu dihitung ulang dari nol.

Solusinya: simpan yang sudah dilihat di sebuah hash map (angka → indeks). Untuk tiap angka baru, tinggal tanya "apakah pasangannya (target - angka) sudah pernah aku lihat?" — pengecekan ini O(1), bukan O(n) seperti scan ulang.

brute force — O(n²)JS
// tiap i, SCAN ULANG seluruh sisa array
function twoSumBruteForce(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) { // diulang tiap i
      if (nums[i] + nums[j] === target) return [i, j];
    }
  }
  return null;
}
optimal — O(n)JS
// simpan yang sudah dilihat, jangan scan ulang
function twoSumOptimal(nums, target) {
  const seen = new Map(); // angka -> indeks
  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) return [seen.get(complement), i];
    seen.set(nums[i], i);
  }
  return null;
}

Perhatikan: kita tidak "menemukan algoritma baru dari langit". Kita cuma menjawab satu pertanyaan sederhana — "informasi apa dari iterasi sebelumnya yang bisa aku simpan, supaya tidak dihitung ulang?" — lalu memilih struktur data (hash map) yang pas untuk menyimpannya. Ini yang disebut trade space for time: solusi optimal memakai O(n) ruang tambahan untuk memangkas waktu dari O(n²) jadi O(n).

◆ Kebiasaan · Best practice

Kebiasaan yang bikin proses brute force → optimal jalan mulus

Ini bukan bakat, ini kebiasaan. Enam hal ini yang membedakan orang yang "kebetulan nemu solusi optimal" dengan orang yang selalu punya proses untuk sampai ke sana.

  • Selalu tulis brute force dulu, meski kamu sudah menduga itu tidak optimal — supaya kamu punya pijakan yang benar untuk dioptimasi, bukan mulai dari kosong.
  • Jadikan brute force sebagai safety net. Simpan sebagai jawaban rujukan, lalu bandingkan output solusi optimalmu dengannya di input-input kecil — kalau beda, solusi optimalmu yang salah.
  • Cari bagian yang "diulang-ulang." Loop di dalam loop yang mengecek hal serupa, pemanggilan fungsi yang sama dengan argumen yang sama berkali-kali — itu semua sinyal ada redundant work yang bisa dipangkas.
  • Tanyakan apa yang bisa "diingat." Informasi apa dari langkah sebelumnya yang kalau disimpan, bikin langkah berikutnya tidak perlu menghitung ulang dari nol?
  • Optimasi setelah paham, bukan sebelum. Jangan buru-buru mengganti struktur data atau algoritma sebelum kamu benar-benar mengerti kenapa versi brute force-nya lambat.
  • Ukur, jangan menebak. Uji brute force vs optimal pada input kecil dulu — pastikan hasilnya identik sebelum kamu percaya penuh pada versi cepatnya.

Optimasi yang dilakukan sebelum kamu benar-benar tahu di mana letak masalahnya seringkali cuma buang waktu dan bikin kode lebih rumit tanpa manfaat nyata — sering disingkat: akar dari segala kejahatan adalah optimasi prematur.

— parafrase Donald Knuth, "Structured Programming with go to Statements" (1974)

Di konteks problem solving, "profiling" itu setara dengan benar-benar paham solusi dasarnya dulu — baru kamu tahu bagian mana yang layak dioptimasi, dan bagian mana yang sudah cukup cepat sehingga tidak perlu disentuh.

◆ Kesiapan · Tier belajar

Di tahap mana progresmu sekarang?

Kemampuan berpindah dari brute force ke optimal itu bertingkat. Kamu tidak perlu langsung jago menaikkan level — cek dulu kamu ada di mana.

Beginner

Bisa menulis brute force yang benar

Fokus utama: dapat solusi yang jalan & benar untuk soal-soal sederhana, tanpa panik soal kompleksitas.

  • Bisa menerjemahkan definisi soal jadi kode langsung, apa adanya.
  • Belum terlalu peduli Big-O — yang penting output-nya cocok.
  • Terbiasa mencoba semua kemungkinan (nested loop, brute enumerate).
Middle

Bisa melihat & memangkas redundant work

Sudah bisa mengenali pola "ini dihitung ulang" secara konsisten, lalu menaikkannya ke solusi yang lebih baik.

  • Bisa mengidentifikasi loop/kerja yang berulang di solusi sendiri.
  • Tahu kapan pakai hash map, memoization, atau pointer dua arah.
  • Bisa membandingkan brute force vs optimal untuk validasi.
Advance

Melompat langsung ke insight optimal

Untuk soal yang lebih kompleks, sudah bisa melihat insight optimal dari awal — tapi tetap sadar trade-off-nya.

  • Bisa langsung melompati brute force untuk pola yang sudah dikenal.
  • Paham trade-off time vs space saat memilih arah optimasi.
  • Tetap menulis brute force sebagai validator saat soalnya baru/asing.
◆ Harga · Tidak ada makan siang gratis

Brute-force-dulu vs langsung cari optimal

Dua strategi memulai, dengan trade-off yang berbeda. Tidak ada yang mutlak benar — tapi salah satunya jelas lebih aman sebagai kebiasaan default.

// Brute force dulu

  • Pasti dapat solusi yang benar dulu, baru pikirkan performa.
  • Ada "baseline" untuk testing & validasi solusi optimal nanti.
  • Progres selalu kelihatan — tidak ada rasa stuck total karena blank.
  • Kalau waktu habis, kamu tetap punya jawaban (walau lambat).

// Langsung cari optimal

  • Berisiko stuck total kalau insight optimalnya belum kelihatan.
  • Susah divalidasi — tidak ada pembanding kalau logikanya salah.
  • Kalau berhasil, hemat banyak waktu & langsung dapat solusi cepat.
  • Cocok kalau kamu sudah pernah lihat pola soal yang serupa.
◆ Bukan lawan, tapi urutan

Ini bukan "pilih salah satu selamanya" — ini urutan default. Brute-force-dulu adalah kebiasaan aman untuk sehari-hari, sementara melompat ke optimal adalah kemampuan yang tumbuh seiring jam terbang di pola-pola yang sudah pernah kamu temui (lihat tier Advance di bab sebelumnya).

◆ Keputusan · Berhenti atau lanjut

Kapan brute force sudah cukup, kapan wajib dioptimasi

Tidak semua brute force perlu dioptimasi. Pertanyaannya bukan "apakah bisa lebih cepat" (hampir selalu bisa), tapi "apakah perlu".

// Brute force sudah cukup saat…

  • Ukuran data kecil, selisih performa tidak terasa.
  • Deadline dekat & butuh solusi jalan sekarang juga.
  • Kode sekali pakai (skrip one-off, bukan dipakai berulang).
  • Belum ada bukti bagian ini jadi bottleneck nyata.

// Wajib dioptimasi saat…

  • Constraint soal besar (misal n hingga jutaan).
  • Dipakai di production dengan traffic / skala tinggi.
  • Dipanggil berulang-ulang di jalur kritis (hot path).
  • Kompetitive programming dengan batas waktu ketat (TLE).
◆
Jangan optimasi hanya karena "kelihatannya bisa lebih cepat." Kalau brute force-mu sudah memenuhi constraint & tidak jadi bottleneck yang terukur, membiarkannya apa adanya bukan kemalasan — itu keputusan yang tepat. Kompleksitas ekstra yang tidak perlu punya harga: lebih susah dibaca, lebih rawan bug.
Studi kasus · Di dunia nyata

Tiga konteks di mana proses ini benar-benar dipakai

Bukan cuma latihan soal — proses brute force → optimal muncul di banyak konteks nyata, dengan alasan yang berbeda-beda di tiap konteks.

// interview

Interview coding

Konteks: diberi soal baru di depan interviewer, waktu terbatas. Kenapa brute force dulu: menyampaikan brute force yang benar biasanya sudah dapat partial credit — menunjukkan kamu paham soalnya. Optimasi dilakukan sambil bicara, di depan interviewer, sebagai bagian dari proses berpikir yang mereka nilai.

// production

Kode production yang "quick fix"

Konteks: fitur baru butuh rilis cepat, solusi paling sederhana ditulis dulu supaya jalan. Kenapa jadi masalah nanti: begitu traffic naik atau data bertambah besar, bagian yang dulunya "cukup cepat" bisa jadi bottleneck & butuh dioptimasi ulang — kali ini dengan data nyata sebagai bukti.

// competitive programming

Competitive programming & TLE

Konteks: solusi brute force dikirim, hasilnya Time Limit Exceeded (TLE) karena constraint soal terlalu besar untuk kompleksitasnya. Kenapa perlu insight: TLE adalah sinyal paling langsung bahwa redundant work di brute force harus dicari & dipangkas sebelum submit ulang.

◆ Benang merahnya

Di ketiga konteks, brute force bukan langkah yang dilewati — ia langkah yang selalu dilalui lebih dulu. Yang beda cuma pemicunya untuk naik ke optimal: waktu interview yang terbatas, traffic production yang naik, atau TLE dari judge.

⚙ Ekosistem · Tools & teknik pendukung

Alat bantu untuk proses brute force → optimal

Bukan algoritma spesifik, tapi teknik & kebiasaan yang membantu proses menaikkan level solusi — apa pun soalnya.

// teknik

Memoization

Jembatan paling umum dari brute force ke optimal: simpan hasil pemanggilan yang sudah pernah dihitung (biasanya di hash map), supaya pemanggilan berikutnya dengan input sama tinggal diambil dari cache, bukan dihitung ulang.

// kebiasaan

Profiling sebelum optimasi

Sebelum mengubah apa pun, ukur dulu bagian mana yang benar-benar lambat. Mengoptimasi bagian yang bukan bottleneck cuma menambah kompleksitas tanpa hasil — inti dari peringatan Knuth soal optimasi prematur.

// vocabulary

Notasi Big-O

Bahasa untuk menjelaskan seberapa "boros" sebuah solusi & seberapa besar penghematan yang didapat setelah optimasi. Berguna untuk mengenali pola redundant work secara lebih sistematis.

// validasi

Uji dua implementasi berdampingan

Jalankan brute force & solusi optimal pada set input kecil yang sama, bandingkan hasilnya. Cara murah untuk menangkap bug di solusi optimal sebelum dipakai di skala besar.

Penutup

Naive dulu, cepat kemudian

Brute force to optimal bukan tentang menghafal trik-trik optimasi — ini tentang membangun kebiasaan untuk selalu punya jawaban yang benar dulu, lalu secara sadar mencari & memangkas pemborosan di dalamnya.

  • Mulai dari yang pasti benar — brute force adalah bentuk kasar, bukan solusi buangan.
  • Brute force = safety net — jadi pembanding untuk menguji solusi optimalmu.
  • Cari yang "diulang-ulang" — itu sinyal paling jelas ada redundant work.
  • Optimasi setelah paham — bukan sebelum, mengikuti semangat Knuth.
  • Trade-off itu nyata — time vs space, aman vs berisiko, semuanya kontekstual.
  • Tidak semua wajib optimal — optimasi ada harganya, pastikan memang perlu.

Langkah belajar berikutnya

Sekarang kamu punya proses untuk berpindah dari naive ke efisien. Langkah selanjutnya: mempertajam cara kamu mengukur & membicarakan seberapa efisien sebuah solusi — supaya kamu bisa mengenali redundant work lebih cepat, bahkan sebelum menulis kodenya.
