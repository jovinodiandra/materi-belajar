// Database — saat query-mu bukan cuma "WHERE = ini", tapi "cari yang paling relevan"

Cari jutaan dokumen dalam milidetik — bukan dengan LIKE '%kata%'.

Database relasional jago menjawab pertanyaan yang pasti: cari user dengan id = 5. Tapi begitu pertanyaannya jadi "cari produk yang mirip dengan kata ini" — dengan typo, sinonim, dan hasil yang harus diurutkan dari paling relevan — database relasional biasa mulai kewalahan. Search database (Elasticsearch, OpenSearch, dkk) lahir khusus untuk soal ini. Deck ini adalah overview kategori search database: kenapa ia perlu ada, konsep inverted index & ranking relevansi di baliknya, sampai kapan kamu benar-benar butuh menambahkannya ke stack-mu.

Sakit
LIKE '%kata%' lambat — scan seluruh tabel, tak paham relevansi
Ide
Inverted index — balik peta: dari kata, temukan dokumennya
Untung
Ranking & filter — hasil paling relevan di atas, bisa difilter facet
Batas
Bukan source of truth — butuh sinkronisasi dari database utama
Pakai
Saat full-text search jadi fitur inti — e-commerce, log, code search

◆ Buat apa ini? Kenapa pakai search database?

Given — fitur pencarianmu masih jalan di atas database relasional biasa, query-nya WHERE nama LIKE '%kata%' ke tabel produk/artikel yang isinya sudah ratusan ribu baris.

When — user mulai mengetik dengan typo ("sepatu lart"), pakai sinonim ("running shoes" vs "sepatu lari"), atau berharap hasil yang paling relevan muncul duluan — bukan cuma urutan id.

Then — tiap pencarian jadi full table scan yang makin lambat seiring data bertambah, typo bikin hasil kosong, dan tidak ada cara wajar untuk meranking "seberapa cocok" tiap baris.

→ makanya kita pakai search database (Elasticsearch, OpenSearch, dkk).

Akar masalah · Kenapa search butuh database khusus

SQL LIKE bukan search engine

Coba bayangkan tabel produk dengan sejuta baris, lalu kamu jalankan WHERE nama LIKE '%sepatu lari%'. Database harus memindai satu-satu baris karena tidak ada index yang bisa dipakai untuk pola seperti itu. Dan meski ketemu, hasilnya tidak diurutkan berdasarkan relevansi, tidak toleran typo ("sepatu lart"), dan tidak paham sinonim ("running shoes" vs "sepatu lari").

relasional — full table scan, tanpa relevansiSQL
SELECT * FROM produk
WHERE nama LIKE '%sepatu lari%'
   OR deskripsi LIKE '%sepatu lari%';

-- 🐢 scan SEMUA baris, index B-tree biasa tak terpakai
-- 🐢 typo "sepatu lart" = 0 hasil, tak ada toleransi
-- 🐢 hasil tak diurutkan dari yang paling relevan
inverted index — dari kata langsung ke dokumenkonsep
// bukan "baca semua dokumen, cek satu-satu"
// tapi "kata ini ada di dokumen mana saja?"

"sepatu" → [doc_12, doc_45, doc_88, doc_101, ...]
"lari"   → [doc_12, doc_50, doc_88, ...]

// irisan kedua daftar = kandidat jawaban, ranking tinggal
// dihitung dari SEBERAPA SERING kata muncul & seberapa langka ia
◆ Analogi — indeks di belakang buku

Kalau kamu cari kata "rekursi" di sebuah buku tebal tanpa indeks, kamu harus membaca semua halaman satu-satu. Tapi kalau ada halaman indeks di belakang ("rekursi — hal. 42, 88, 130"), kamu langsung lompat ke halaman yang tepat. Inverted index adalah "halaman indeks" itu, tapi dibangun otomatis untuk setiap kata di setiap dokumen — dan itulah yang tidak dimiliki database relasional biasa secara native.

“Struktur data sentral di mesin pencari adalah inverted index: untuk setiap term, ia menyimpan daftar dokumen yang memuat term itu — sehingga pencarian tidak perlu memindai isi setiap dokumen satu per satu.”

— parafrase dari Christopher D. Manning, Prabhakar Raghavan, Hinrich Schütze, Introduction to Information Retrieval (Cambridge University Press)
Konsep inti · Inverted index & tokenisasi

Dari kalimat mentah jadi peta kata → dokumen

Sebelum dokumen bisa dicari, teksnya harus dipecah dulu jadi satuan-satuan kecil yang disebut token — proses ini namanya tokenisasi. Baru dari token-token itu, search engine membangun inverted index.

◆ Alur tokenisasi sederhana
Input"Sepatu Lari Terbaik 2024!"
Lowercase"sepatu lari terbaik 2024!"
Split[sepatu, lari, terbaik, 2024]
Stopwordbuang kata umum: "yang", "di", "dan" (kalau ada)
Stemming"berlari" → "lari" (bentuk dasar)

Rangkaian langkah ini disebut analyzer di Elasticsearch/OpenSearch. Analyzer yang kamu pakai menentukan kualitas pencarian — analyzer bahasa Inggris tidak otomatis paham imbuhan bahasa Indonesia seperti me-, -kan, atau ber-.

Setelah tokenisasi, hasilnya dipetakan terbalik — bukan "dokumen ini berisi kata apa saja", tapi "kata ini muncul di dokumen mana saja". Begini kira-kira query nyata ke Elasticsearch/OpenSearch untuk mencari lewat inverted index itu:

query DSL — full-text search dengan toleransi typoJSON
{
  "query": {
    "multi_match": {
      "query": "sepatu lart",
      "fields": ["nama^2", "deskripsi"],
      "fuzziness": "AUTO"
    }
  }
}
// "nama^2" = field "nama" bobotnya 2x lebih penting
// "fuzziness: AUTO" = toleran typo 1-2 huruf ("lart" tetap ketemu "lari")
Konsep inti · Ranking & filter

Bukan cuma "ketemu", tapi "yang paling relevan duluan"

Menemukan dokumen yang cocok baru separuh jalan. Bagian sulitnya: mengurutkan ratusan hasil dari yang paling relevan. Di sinilah skema scoring seperti TF-IDF dan penerusnya, BM25, berperan.

◆ TF-IDF & BM25 secara ringkas (tanpa rumus rumit)

Skor relevansi sebuah dokumen terhadap kata pencarian dihitung dari dua hal yang ditimbang bersama: Term Frequency (TF) — makin sering kata yang dicari muncul di dokumen itu, makin relevan dokumennya; dan Inverse Document Frequency (IDF) — kata yang jarang muncul di seluruh koleksi dokumen (mis. "titanium") lebih berbobot daripada kata umum (mis. "yang", "produk"). BM25 menyempurnakan ini dengan juga mempertimbangkan panjang dokumen, supaya dokumen pendek yang kebetulan padat kata kunci tidak otomatis menang dari dokumen panjang yang relevan secara wajar.

“Relevansi sebuah dokumen dihitung dari seberapa sering kata yang dicari muncul di dalamnya, lalu diseimbangkan dengan seberapa umum kata itu muncul di seluruh koleksi dokumen serta panjang dokumen itu sendiri.”

— parafrase gagasan BM25, evolusi dari TF-IDF, default relevance scoring di Lucene/Elasticsearch

Di samping ranking, search database juga jago untuk faceted search — filter interaktif yang biasa kamu lihat di e-commerce ("Merek", "Ukuran", "Rentang harga") sekaligus dengan hitungan jumlah hasil per kategori.

query DSL — faceted search dengan aggregationsJSON
{
  "query": { "match": { "nama": "sepatu lari" } },
  "aggs": {
    "per_merek": {
      "terms": { "field": "merek.keyword" }
    },
    "per_rentang_harga": {
      "range": {
        "field": "harga",
        "ranges": [
          { "to": 300000 },
          { "from": 300000, "to": 700000 },
          { "from": 700000 }
        ]
      }
    }
  }
}
// hasil "aggs" inilah yang jadi angka di samping tiap checkbox filter
◆ Praktik · Supaya tidak menyesal di production

Best practice pakai search database

Search database punya karakter berbeda dari database utamamu. Beberapa kebiasaan ini yang membedakan tim yang lancar dari yang berantakan.

  • Jangan jadikan search engine sebagai source of truth. Simpan data asli di database utama (Postgres/MySQL/dsb); search engine hanya salinan yang dioptimalkan untuk dicari.
  • Rancang strategi sinkronisasi data — via event/CDC (change data capture), message queue, atau reindex berkala — supaya data di search engine tidak basi dibanding sumber aslinya.
  • Rancang mapping & analyzer sesuai bahasa pengguna. Analyzer default berbahasa Inggris sering tidak cocok untuk imbuhan bahasa Indonesia; pertimbangkan analyzer custom atau plugin stemming Bahasa Indonesia.
  • Pisahkan field untuk pencarian dan field untuk filter/sort. Field teks bebas (text) untuk full-text search, field keyword untuk exact match & agregasi facet.
  • Uji ulang relevansi, jangan cuma uji "ketemu atau tidak". Hasil bisa "ketemu" tapi urutannya salah — cek dengan data & query nyata dari pengguna.
  • Rencanakan skala sejak awal — jumlah shard, replica, dan resource cluster sulit diubah drastis setelah data besar; salah rencana di awal jadi migrasi mahal belakangan.

Tier belajar search database

Tidak perlu langsung paham cluster tuning di hari pertama. Ini tahapan wajar dari pemula sampai mahir.

🌱 Beginner

Full-text query dasar

Fokus paham konsep inti: dokumen, index, dan query pencarian sederhana.

  • Paham beda LIKE SQL vs full-text search
  • Bisa index & cari dokumen JSON sederhana
  • Coba query match & multi_match
  • Mengerti apa itu inverted index secara konsep
⚙ Middle

Relevansi & faceted search nyata

Bangun fitur pencarian produk yang sungguh dipakai, bukan sekadar demo.

  • Atur boosting field & fuzziness untuk relevansi
  • Implementasi faceted search dengan aggregations
  • Desain mapping: field text vs keyword
  • Sinkron data dari database utama ke index
🚀 Advance

Skala & custom analyzer

Operasikan search engine di skala production dengan data terus berubah.

  • Sinkronisasi data real-time (CDC/event streaming)
  • Skala cluster: sharding, replica, resiliency
  • Custom analyzer & stemming Bahasa Indonesia
  • Tuning relevansi lanjutan & A/B testing hasil cari
◆ Harga · Tidak ada makan siang gratis

Trade-off & kapan (tidak) pakai search database

Search database luar biasa untuk mencari, tapi itu satu-satunya kekuatannya. Ia bukan pengganti database utama — ia pendamping yang butuh perhatian ekstra.

// Yang kamu dapat

  • Pencarian super cepat di jutaan dokumen.
  • Ranking berbasis relevansi (BM25), bukan cuma cocok/tidak.
  • Toleran typo, sinonim, & pencarian bahasa alami.
  • Faceted search & aggregation siap pakai.

// Yang kamu korbankan

  • Bukan source of truth — butuh database utama di belakangnya.
  • Butuh pipeline sinkronisasi data terpisah (bisa jadi titik gagal baru).
  • Konsistensi biasanya eventual, bukan real-time strict.
  • Operasional cluster (shard, replica, resource) makin rumit seiring skala.
◆ Pertanyaan penentu

Tanyakan: "Apakah pengguna butuh mencari dengan bahasa bebas, typo-toleran, dan hasil terurut relevansi?" Kalau ya — pencarian produk, dokumentasi, log, kode — search database sangat membantu. Kalau kebutuhanmu cuma WHERE kolom = nilai yang pasti, database relasional biasa (dengan index yang tepat) sudah cukup, tanpa perlu menambah komponen baru yang harus disinkronkan.

Studi kasus · Di dunia nyata

Siapa saja yang pakai search database di production

Beberapa skenario nyata di mana pencarian bukan fitur pelengkap, tapi jantung produknya.

// e-commerce

Shopify

Shopify menggunakan Elasticsearch untuk melayani pencarian produk di skala jutaan toko online, di mana tiap toko punya katalog & atribut produk yang berbeda-beda.

// developer tools

GitHub — code search

GitHub memakai Elasticsearch untuk menopang pencarian kode & repository — menelusuri isi jutaan repositori butuh indexing teks berskala besar, bukan sekadar query nama file.

// search-as-a-service

Algolia

Algolia dibangun dari awal khusus sebagai layanan search-as-a-service, dipakai banyak startup & toko online yang butuh pencarian instan tanpa mengelola cluster search sendiri.

// konten & ensiklopedia

Wikipedia — CirrusSearch

Wikipedia memakai Elasticsearch (lewat ekstensi CirrusSearch) untuk pencarian artikel lintas bahasa dengan volume konten yang sangat besar.

◆ Benang merahnya

Di semua kasus di atas, database utama (produk, repositori, akun) tetap ada di tempat lain — search engine hanyalah lapisan pencarian di atasnya, disinkronkan lewat pipeline data tersendiri. Tak satu pun dari mereka menjadikan search engine sebagai satu-satunya tempat data hidup.

⚙ Ekosistem · Alat yang dipakai

Tools search database

Ada dua jalur besar: kelola sendiri (self-hosted) atau pakai layanan terkelola (managed). Sebagai pemula, cukup kenali nama & posisinya dulu.

Elasticsearch

Search engine berbasis Lucene paling banyak dipakai. Fleksibel: full-text search, log analytics, sampai vector search modern.

Penutup

Cari itu soal berbeda dari simpan

Search database lahir karena "mencari dengan relevan" adalah masalah yang secara fundamental berbeda dari "menyimpan & mengambil data yang pasti". Ia bersinar saat jadi lapisan pencarian, dan berbahaya kalau diperlakukan sebagai database utama.

  • Inverted index — dari kata, temukan dokumennya, bukan sebaliknya.
  • Tokenisasi & analyzer — kualitas pencarian ditentukan di sini, termasuk bahasa yang dipakai.
  • Relevansi (BM25) — hasil diurutkan, bukan sekadar dicocokkan.
  • Faceted search — filter & hitungan kategori jadi murah lewat aggregations.
  • Bukan source of truth — selalu ada database utama di belakangnya.
  • Sinkronisasi adalah pekerjaan nyata — rencanakan sejak awal, bukan belakangan.

Aturan emasnya

Tanya: "Apakah pengguna perlu mencari dengan bahasa bebas & mengharapkan hasil yang paling relevan duluan?" Kalau ya, search database akan menyelamatkanmu dari LIKE '%kata%' yang lambat & buta relevansi. Tapi selalu perlakukan ia sebagai lapisan pencarian di atas database utamamu — bukan pengganti tempat datamu benar-benar hidup.
