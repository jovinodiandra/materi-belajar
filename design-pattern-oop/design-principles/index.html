// Panduan lapangan untuk kode liar — prinsip, smell & anti-pattern

Belajar mengenali kode sehat — dan satwa buas yang memangsanya.

Kode di alam liar penuh "spesies". Yang sehat ngikutin prinsip desain. Yang buas muncul pas prinsip dilanggar: code smell (gejala), design smell (pembusukan struktur), dan anti-pattern (jebakan yang kelihatan masuk akal). Panduan ini ngajarin kamu mengenali tiap spesies — ciri-ciri, habitat, tingkat bahaya — dan penangkal-nya. Tiap entri dikasih contoh kode (Java) dan, kalau pas, sebuah analogi. Bahasa santai.

↓ SCROLL ATAU TEKAN →

◆ Buat apa ini? Kenapa pakai ini?

Given — class/module dibangun tanpa prinsip desain yang jelas: tanggung jawab campur aduk dalam satu class, dependency mengarah sembarangan, antar bagian saling nempel erat.

When — requirement berubah atau fitur baru ditambahkan (hal yang pasti terjadi di kode hidup).

Then — perubahan kecil merembet ke banyak tempat yang kelihatannya nggak berhubungan, gampang bikin bug baru, dan kode makin takut disentuh (rigidity & fragility).

→ makanya kita pakai Design Principles (SOLID, DRY, KISS, YAGNI, dkk) — supaya kode gampang berubah tanpa efek domino.

Cara baca panduan ini

Taksonomi: tiga jenis "kode buruk" (dan kenapa beda)

Orang sering nyampur semua jadi "kode jelek". Padahal "bad design" itu payung; di bawahnya ada tiga kategori yang beda level. Bedain mereka bikin kamu tahu obatnya apa.

Lokal · gejala

Code Smell

Tanda permukaan di kode—"ada yang nggak beres", belum tentu salah. Obat: refactor. Cth: Long Method, Duplicated Code.

Struktural · gejala

Design Smell

Pembusukan level desain. Inilah yang SOLID dirancang buat cegah. Cth: Rigidity, Fragility, Opacity.

Pola berulang

Anti-Pattern

Solusi yang sering dipakai, kelihatan masuk akal, tapi hasilnya jelek. Punya nama & jalan keluar. Cth: God Object, Golden Hammer.

Kunci bedanya: smell itu gejala; anti-pattern itu praktik yang menghasilkan gejala. Duplicated Code (smell) ← Copy-Paste Programming (anti-pattern). Dan design principles (SOLID, DRY, …) = panduan positif; dilanggar → muncul smell & anti-pattern.

Kode Sehat · Struktural · kenapa repot?

Di balik SOLID: software itu mestinya soft

Sebelum hafalin lima huruf SOLID, satu pertanyaan dulu: kenapa harus? SOLID itu bukan hukum, bukan tradisi turun-temurun, bukan jaminan. Dia ada buat satu tujuan praktis.

Kuncinya di namanya: software—mestinya gampang diubah, itu nilai jualnya dibanding hardware. Dan kode pasti berubah: requirement geser, bisnis pivot, bug nongol. Biaya terbesar sebuah sistem bukan pas ditulis pertama kali, tapi semua perubahan setelahnya—berbulan, bertahun. Kode lebih sering dibaca & diubah daripada ditulis.

◈ IntiBuat apa SOLID

SOLID = sekumpulan heuristik buat ngatur ketergantungan (dependency) antar bagian, biar perubahan tetap murah & lokal: ubah satu hal → cukup sentuh satu tempat, nggak ngerembet ke mana-mana.

Tanpa ngatur dependency, struktur kode pelan-pelan membusuk: sekali ubah, banyak yang ikut rusak (fragility); pengen ubah tapi takut nyenggol (rigidity). Itu "design smell" yang kita bahas nanti. SOLID = obat pencegahnya—tiap huruf nyasar ke satu cara dependency bikin susah.

◆ Jujur: ini heuristik, bukan jaminan

Kamu bisa patuh SOLID tapi desain tetap jelek; bisa juga "langgar" SOLID dan baik-baik aja buat skrip sekali pakai atau kode kecil yang stabil. Ini panduan, bukan bukti matematis—dan ngikutin tanpa paham = Cargo Cult. Pertanyaan sebenarnya selalu: "apakah ini bikin kode lebih murah diubah, sesuai cara dia bakal berkembang?" Kalau kodenya sekali-buang, SOLID malah bisa overkill (YAGNI).

« Aturan tata-kota bukan biar kota cakep di foto—tapi biar pas mau nambah jalan atau gedung, kamu nggak perlu ngebongkar separuh kota dulu. »

Jadi tiap prinsip berikutnya, baca dengan satu lensa: "ini ngurangin biaya perubahan yang mana?" Jelas manfaatnya buat kode-mu → pakai. Enggak → jangan dipaksa.

Kode Sehat · Struktural · SOLID — S

Single Responsibility — satu class, satu alasan untuk berubah

"Satu tanggung jawab" itu diukur dari alasan untuk berubah, bukan jumlah baris. Kalau sebuah class berubah karena aturan bisnis dan format database dan tampilan PDF, dia punya tiga alasan—tiga tuan. Pisahkan.

◈ Aturan LapanganSingle Responsibility Principle

Sebuah class sebaiknya punya satu, dan hanya satu, alasan untuk berubah.

Invoice.java — sebelum & sesudah
// ❌ satu class, tiga alasan berubah (bisnis + DB + presentasi)
class Invoice {
    BigDecimal total()       { ... }   // aturan bisnis
    void saveToDatabase()    { ... }   // persistence
    String renderAsPdf()    { ... }   // presentasi
}

// ✓ pisah: tiap class satu alasan berubah
class Invoice        { BigDecimal total() { ... } }
class InvoiceRepository { void save(Invoice inv) { ... } }
class InvoicePrinter  { String toPdf(Invoice inv) { ... } }
« Pisau dapur, talenan, panci—satu alat satu tugas. Kamu nggak motong bawang pakai panci cuma karena "sama-sama di dapur". »
◈ Penangkal untuk

SRP yang dilanggar bikin God Object (anti-pattern) dan Divergent Change (smell): satu class diutak-atik dari banyak arah, tiap perubahan berisiko nabrak yang lain.

Kode Sehat · Struktural · SOLID — O

Open/Closed — terbuka buat nambah, tertutup buat ngutak-atik

Module yang sehat itu bisa nambah perilaku tanpa kamu harus ngedit kode yang udah jalan. Caranya: tambahin lewat extension—class atau implementasi baru—bukan dengan ngebongkar class lama yang udah dites dan dipercaya.

◈ Aturan LapanganOpen/Closed Principle

Entitas software sebaiknya terbuka buat extension, tertutup buat modifikasi. Nambah kasus baru = nambah kode, bukan ngedit yang lama.

Gampang dilihat di kode yang ber-instanceof berderet. Tiap kali ada bentuk baru, kamu kepaksa buka lagi class kalkulator dan nyolok satu cabang if lagi. Itu tanda OCP-nya bocor.

AreaCalculator.java — sebelum & sesudah
// ❌ tiap Shape baru → buka kalkulator, tambah cabang lagi
class AreaCalculator {
    double area(Object shape) {
        if (shape instanceof Circle) {
            Circle c = (Circle) shape;
            return Math.PI * c.r * c.r;
        } else if (shape instanceof Square) {
            Square s = (Square) shape;
            return s.side * s.side;
        }
        // + Triangle? + Hexagon? → edit lagi di sini
        throw new IllegalArgumentException("shape?");
    }
}

// ✓ tiap Shape tahu luasnya sendiri; kalkulator nggak disentuh
interface Shape { double area(); }

class Circle implements Shape {
    double r;
    public double area() { return Math.PI * r * r; }
}
class Square implements Shape {
    double side;
    public double area() { return side * side; }
}

class AreaCalculator {
    double area(Shape shape) { return shape.area(); }
}
// Triangle baru? Bikin class baru. Kalkulator nggak berubah.
« Stop-kontak di tembok: mau colok kipas, charger, atau lampu baru—tinggal colok. Kamu nggak perlu bongkar instalasi listrik tiap beli alat. »

Inti triknya: titik yang berpotensi berubah disembunyiin di balik abstraksi (di sini interface Shape). Kode klien cuma kenal abstraksinya, jadi varian baru muncul lewat polymorphism—bukan lewat editan di tempat lama.

◈ Penangkal untuk

OCP yang dijaga nangkal Shotgun Surgery (smell): satu perubahan kecil nyebar jadi editan di banyak file. Juga Switch-Statement Smell—rentetan if instanceof / switch (type) yang harus dibuka ulang tiap ada kasus baru. Polymorphism bikin keduanya nggak perlu ada.

Kode Sehat · Struktural · SOLID — L

Liskov Substitution — anak harus bisa gantiin orang tuanya tanpa drama

Kalau kode kamu nerima sebuah Rectangle, dia harus tetap jalan benar walau yang dikasih ternyata subtype-nya. Itu inti LSP: subtype wajib bisa menggantikan base-nya tanpa bikin program ngaco atau ngagetin. Warisan extends itu janji—"aku ini sah jadi kamu"—dan janji itu nggak boleh diam-diam dibatalkan.

◈ Aturan LapanganLiskov Substitution Principle

Objek subtype harus bisa menggantikan objek base-nya tanpa mengubah kebenaran program. Kalau substitusi bikin hasil ngaget, warisannya bohong.

Contoh klasik yang bocor: Square extends Rectangle. Terdengar masuk akal—bujur sangkar kan memang persegi panjang? Tapi is-a di matematika nggak otomatis jadi is-a yang sah di kode. Begitu Square maksa width == height, setWidth() diam-diam ikut ngubah height—dan kode yang cuma pegang Rectangle langsung kena tipu.

Square extends Rectangle Design Smell bahaya 4/5
Ciri-ciriSubclass memperketat kontrak induk: override yang punya efek samping tak terduga, lempar UnsupportedOperationException, atau bikin instanceof bertebaran di pemanggil.
AkibatKode yang nerima tipe induk diam-diam ngaco pas dikasih subclass-nya—bug muncul jauh di pemanggil yang nggak curiga, dan kamu kepaksa nambal pakai instanceof yang justru ngerusak polymorphism.
HabitatHierarki yang dibangun dari "is-a" bahasa sehari-hari—Square/Rectangle, Penguin/Bird, ReadOnlyList/List—bukan dari kesamaan perilaku.
Square.javaSPESIMEN
class Rectangle {
    protected int w, h;
    void setWidth(int w)  { this.w = w; }
    void setHeight(int h) { this.h = h; }
    int area() { return w * h; }
}

class Square extends Rectangle {
    @Override void setWidth(int w) {
        this.w = w; this.h = w;  // diam2 ubah height!
    }
    @Override void setHeight(int h) {
        this.w = h; this.h = h;  // dan sebaliknya
    }
}

// kode yang cuma kenal Rectangle — ngarep aman:
int areaAfterResize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    return r.area();  // ngarep 20. Square balikin 16. KAGET.
}
Kenapa bocorPemanggil berpegang pada kontrak Rectangle: "set width, lalu set height, keduanya independen". Square melanggar invariant itu. Substitusi yang harusnya transparan malah ngubah hasil—warisannya nggak sah.
PenangkalLSP: jangan paksa warisan yang melanggar kontrak. Bikin Shape jadi immutable (set lewat constructor, nggak ada setter yang bisa dibohongin), atau pisahkan jadi tipe sejajar—Square dan Rectangle bukan parent–child, cuma sama-sama Shape yang punya area().
« Resep minta "telur". Telur bebek harus bisa gantiin telur ayam tanpa bikin kue gagal. Kalau "telur" kamu meledak pas dikocok, itu bukan substitusi yang sah—itu bukan telur. »

// ✓ immutable + tipe sejajar: tak ada kontrak yang bisa dibohongi

◈ Cara cepat ngecek

Kalau kamu nemu instanceof atau if (x instanceof Square) di kode pemanggil cuma buat "handle kasus khusus" subtype, itu bau LSP bocor: subtype-nya nggak benar-benar bisa gantiin base. Aturan turunan: override boleh melonggarkan precondition dan memperketat postcondition—jangan kebalik. Dan jangan lempar exception baru yang base-nya nggak janjiin.

◈ Jangan keliru

LSP bukan cuma soal "method-nya match". Compiler bahagia walau LSP dilanggar—Square di atas kompile sempurna. Pelanggarannya ada di perilaku & kontrak, bukan di tipe. Inilah kenapa ini Design Smell (busuk struktur), bukan sekadar Code Smell.

Kode Sehat · Struktural · SOLID — I

Interface Segregation — jangan paksa orang implement yang nggak kepake

Interface yang gemuk itu jebakan. Pas kamu bikin satu interface besar isinya semua method, tiap class yang implement kepaksa nulis semua—termasuk yang nggak relevan buat dia. Ujungnya muncul throw new UnsupportedOperationException() atau method kosong yang bohong. Pecah jadi interface kecil per-peran.

◈ Aturan LapanganInterface Segregation Principle

Client nggak boleh dipaksa bergantung ke method yang nggak dia pakai. Banyak interface kecil & spesifik lebih baik daripada satu interface gemuk.

Contoh klasik: interface Worker ngurus kerja dan makan sekaligus. Manusia oke. Tapi pas datang RobotWorker—dia bisa kerja, tapi nggak makan. Kepaksa implement eat() yang nggak masuk akal.

Worker.java — interface gemukSPESIMEN
// ❌ satu interface gemuk: dua peran dijadiin satu
interface Worker {
    void work();
    void eat();
}

class HumanWorker implements Worker {
    public void work() { ... }
    public void eat()  { ... }   // wajar
}

class RobotWorker implements Worker {
    public void work() { ... }
    public void eat() {            // robot nggak makan!
        throw new UnsupportedOperationException();
    }
}

Penangkalnya: pisah per peran. Workable buat yang kerja, Eatable buat yang makan. Tiap class cuma implement yang dia beneran butuh.

class HumanWorker implements Workable, Eatable {

}

class RobotWorker implements Workable {

◈ Penangkal untuk

ISP yang dilanggar bikin Refused Bequest (smell): class "menolak warisan" lewat method kosong atau throw. Tanda fat interface gampang dikenali—begitu satu implementor nge-throw UnsupportedOperationException, interface-nya kegemukan, waktunya dipecah.

Kode Sehat · Struktural · SOLID — D

Dependency Inversion — gantung ke abstraksi, jangan ke detail

Bayangin OrderService yang langsung new MySqlOrderRepo() di dalemnya. Begitu kamu mau ganti ke Postgres atau mau nge-mock buat test, kamu kebuka kode bisnisnya. Modul penting malah gantung ke detail—kebalik.

DIP bilang: modul high-level (aturan bisnis) dan modul low-level (detail teknis) sama-sama harus gantung ke abstraksi. Dan abstraksinya nggak boleh ikut detail—justru detail yang ikut abstraksi. Arah ketergantungan dibalik, makanya namanya inversion.

◈ Aturan LapanganDependency Inversion Principle

Modul high-level jangan gantung ke modul low-level. Dua-duanya gantung ke abstraksi—dan detail yang ikut abstraksi, bukan sebaliknya.

OrderService.java — sebelum & sesudah
// ❌ high-level gandeng langsung ke detail low-level
class OrderService {
    private MySqlOrderRepo repo = new MySqlOrderRepo();
    void place(Order o) {
        repo.save(o);   // terkunci ke MySQL, susah di-test
    }
}

// ✓ kedua sisi gantung ke abstraksi; repo di-inject
interface OrderRepository { void save(Order o); }

class OrderService {
    private final OrderRepository repo;
    OrderService(OrderRepository repo) {
        this.repo = repo;   // MySQL, Postgres, mock—bebas
    }
    void place(Order o) { repo.save(o); }   // lewat abstraksi
}

class MySqlOrderRepo implements OrderRepository { ... }
« Lampu gantung ke stop-kontak standar, bukan disolder ke kabel merek listrik tertentu. Mau ganti merek? Cabut, colok yang lain. »
◈ Penangkal untuk

DIP yang dilanggar bikin coupling ketat: kode bisnis nempel ke detail teknis (DB, library, vendor). Akibatnya susah di-test, susah diganti, dan satu perubahan low-level merembet ke mana-mana. Inilah pondasi Rigidity & Fragility (design smell).

Kode Sehat · Struktural · Kesederhanaan

DRY, KISS, YAGNI — tiga aturan kesederhanaan

SOLID ngatur struktur; tiga ini ngatur kesederhanaan. Inti semuanya sama: kode yang nggak ada itu nggak bisa rusak, nggak bisa bingungin, nggak perlu dirawat. Tapi hati-hati — ketiganya gampang disalahpahami jadi alasan over-engineering.

◈ Aturan LapanganDRY — Don't Repeat Yourself

Tiap pengetahuan punya satu sumber kebenaran. Aturan bisnis yang sama jangan ditulis di dua tempat — nanti satu diubah, satu lupa, jadi beda diam-diam. Tapi: kode yang cuma kebetulan mirip dengan alasan-berubah beda jangan disatukan — itu false DRY.

PriceCalculator.java
// ❌ rumus pajak digandakan — ubah satu, lupa satu
BigDecimal cartTotal() {
    return sub.multiply(new BigDecimal("1.11"));
}
BigDecimal invoiceTotal() {
    return sub.multiply(new BigDecimal("1.11"));
}

// ✓ satu sumber kebenaran — ekstrak method
BigDecimal withTax(BigDecimal sub) {
    return sub.multiply(TAX_RATE);
}
« Satu sumber air bersih buat seluruh kampung. Kalau ada dua sumur, suatu hari yang satu keruh dan kamu nggak sadar minum yang mana. »
◈ Aturan LapanganKISS — Keep It Simple, Stupid

Pilih solusi paling sederhana yang jalan. Kepintaran yang dipamerin itu beban, bukan prestasi — orang berikutnya (sering kamu sendiri, tiga bulan lagi) harus baca dan paham. Yang gampang dibaca menang dari yang keren tapi bikin pusing.

« Mau buka botol? Pakai pembuka botol. Jangan rakit mesin Rube Goldberg pakai bola, domino, dan ayam — keren di video, mimpi buruk pas rusak. »
◈ Aturan LapanganYAGNI — You Aren't Gonna Need It

Jangan bangun buat masa depan khayalan. Fitur, parameter, atau abstraksi "buat jaga-jaga nanti" biasanya nggak kepakai — dan keburu jadi kode mati yang harus dirawat. Tambahin pas beneran perlu, bukan pas kamu nebak bakal perlu.

« Jangan beli sofa, lemari, dan meja makan buat rumah yang fondasinya aja belum dicor. Pas rumahnya jadi, ukuran ruangannya beda dari bayanganmu. »
◈ Awas tarik-menarik

DRY ketemu YAGNI: jangan ekstrak abstraksi cuma karena lihat satu kemiripan — itu Speculative Generality. Tunggu konsumen kedua yang sungguh-sungguh. Dan ingat: SRP menang dari DRY — dua kode mirip dengan alasan-berubah beda itu kebetulan, bukan duplikasi.

Kode Sehat · Struktural · Gandengan & susunan

Composition, Demeter & Cohesion — cara komponen saling nyambung

SOLID ngurus tiap kelas biar rapi. Tiga prinsip ini ngurus relasi antar kelas: gimana kamu nyusun ulang kelakuan, ke siapa boleh ngobrol, dan seberapa erat satu modul nempel ke yang lain. Salah di sini, desainnya kaku walau tiap kelasnya kelihatan bersih.

◈ Aturan LapanganFavor Composition over Inheritance

Rakit kelakuan dari objek lain (HAS-A), jangan diwarisi dari induk (IS-A). Warisan ngiket kamu ke implementasi induk; rantai extends yang dalam itu rapuh—ganti induk, semua turunan ikut goyang.

« Mau robot yang bisa terbang? Pasangin jetpack (komposisi), jangan paksa dia lahir dari keluarga burung (warisan). Jetpack bisa dilepas-pasang; silsilah nggak. »

Komposisi itu tulang punggung Design Patterns: Strategy nyolok algoritma sebagai field, Decorator mbungkus objek, Adapter mbalut yang lama. Semua milih HAS-A ketimbang nambah cabang warisan. Inilah kenapa "favor composition" nyambung ke deck OOP & pola desain—begitu kamu mikir komposisi, banyak pola jadi kelihatan natural.

◈ Aturan LapanganLaw of Demeter (Least Knowledge)

Sebuah method cuma boleh ngobrol ke teman dekat: dirinya sendiri, parameternya, field-nya, dan objek yang dia bikin. Jangan ngajak ngomong kenalan dari kenalan. Rantai a.b().c().d() itu train wreck—kamu jadi tahu terlalu banyak soal isi perut orang lain.

« Bayar kasir, biar dia yang ngurus laci. Kamu nggak nyelonong ke dompet pelanggan lain buat ngambil kembalian. »
Checkout.java — train wreck vs minta langsung
// ❌ rantai panjang: nyelonong ke kenalan-dari-kenalan
int pos = order.getCustomer()
             .getAddress()
             .getCity()
             .getPostalCode();   // 4 lapis jeroan

// ✓ tanya teman dekat; biar dia yang ngurus dalamnya
int pos = order.shippingPostalCode();

Bedain dari fluent API (mis. builder.x().y().z()): di builder tiap langkah ngembaliin objek yang sama, jadi itu bukan train wreck. Demeter dilanggar pas tiap .get() nyeret kamu ke objek baru yang makin dalam.

◈ Aturan LapanganHigh Cohesion & Loose Coupling

Cohesion = isi satu modul nyambung & fokus ke satu tujuan—naikin setinggi mungkin. Coupling = seberapa erat antar-modul saling gantung—turunin selonggar mungkin. Targetnya: cohesion tinggi, coupling longgar. Ganti satu modul nggak bikin yang lain ikut pecah.

« Tim yang sehat: di dalam satu tim semua sefrekuensi (cohesion tinggi), antar tim cukup ngobrol lewat kontrak jelas (coupling longgar)—bukan saling ngacak meja masing-masing. »
◈ Penangkal untuk

Langgar ketiganya dan kamu manggil monster: warisan dalam → Fragile Base Class; train wreck → smell Message Chains; cohesion rendah + coupling erat → God Object dan ujungnya Big Ball of Mud. Tiga prinsip ini yang jaga arsitektur tetap bisa diutak-atik.

Kode Sehat · Disiplin

Jangan biarkan jendela pecah

Prinsip struktural tadi (SOLID, DRY, KISS) itu arsitektur. Tapi kode busuk bukan cuma soal desain awal—busuk itu proses. Pelan-pelan, satu kompromi kecil yang dibiarkan. Dua kartu di bawah ini soal disiplin harian: kenapa pembusukan mulai, dan gimana kamu nge-rem-nya tiap kali lewat.

◈ Aturan LapanganBroken Window Theory

Satu "jendela pecah"—smell, hack, atau bug—yang dibiarkan ngirim sinyal: "nggak ada yang peduli di sini." Sinyal itu ngundang kompromi berikutnya. Lama-lama tim ngikut standar terendah yang kelihatan, dan entropi naik sampai modul jadi tak tersentuh. Benerin segera, atau setidaknya papan-tutup (TODO + tiket) biar nggak kelihatan ditelantarin.

« Gedung kosong, satu kaca pecah dibiarkan. Seminggu kemudian semua kaca pecah—bukan karena vandal lebih banyak, tapi karena yang pecah pertama bilang "tempat ini nggak ada yang jaga." »
◈ Aturan LapanganBoy Scout Rule

Penangkal aktifnya: "tinggalin kode lebih bersih daripada pas kamu nemu." Bukan refactor heroik—cukup yang kecil sambil lewat: kasih nama variabel yang jelas, hapus impor mati, pecah satu method gendut. Tiap commit nutup satu jendela. Kebersihan jadi arah default, bukan proyek khusus.

« Aturan pramuka: tinggalin tempat kemah lebih bersih dari pas kamu datang. Nggak usah bersihin seluruh hutan—cukup pungut sampah di sekitar tendamu sendiri tiap pagi. »
PriceCalculator.java — lewat sini? tutup jendelanya
// ❌ jendela pecah: nama ngasal + magic number dibiarkan
int calc(int x) {
    return x * 11 / 10;   // ...ini apaan? pajak?
}

// ✓ Boy Scout: kamu cuma lewat, tapi rapihin dikit
static final BigDecimal TAX_RATE = new BigDecimal("0.10");

BigDecimal withTax(BigDecimal price) {
    return price.multiply(BigDecimal.ONE.add(TAX_RATE));
}
◈ Awas perangkapnya

Boy Scout bukan izin refactor liar di luar scope PR. Rapihin yang kamu sentuh, bukan ngubah 30 file yang nggak ada hubungannya—itu bikin review susah dan malah nambah risiko. Bersih sedikit, sering, dan nyambung sama perubahan kamu.

Disiplin ini—nutup jendela tiap lewat—jaga modul tetap sehat dari hari ke hari. Tapi disiplin harian butuh teman: aturan biar kode nggak bikin kaget dan tiap bagian nggak nyampur urusan. Lanjut ke POLA & Separation of Concerns.

Tidak mengagetkan, dan tahu batas

Dua disiplin yang gampang diremehin tapi nyelametin tim. Pertama: kode kamu kelakuannya harus sesuai yang orang duga dari namanya. Kedua: jangan campur aduk urusan yang beda jadi satu—pisahkan ke lapisan masing-masing.

◈ Aturan LapanganPrinciple of Least Astonishment

Sebuah komponen sebaiknya berperilaku seperti yang diduga sebagian besar orang. Kalau kelakuannya bikin kaget, dia salah—biarpun "benar" secara teknis.

Nama itu janji. getX() dan isValid() kedengarannya cuma baca—nggak ada yang nyangka dia diam-diam ngubah state atau ngehapus data. Method yang ngelanggar dugaan ini namanya astonishing: orang manggil sambil ngira aman, eh malah ada efek samping.

UserSession.java
// ❌ getter yang diam-diam punya efek samping
public User getCurrentUser() {
    User u = cache.lookup(token);
    cache.clear();        // LAH?! manggil getX malah hapus cache
    return u;
}

// ✓ getter cuma baca; mutasi dikasih nama jujur
public User getCurrentUser() {
    return cache.lookup(token);
}
public void invalidateSession() {
    cache.clear();        // niat mutasi → nama yang nunjukin itu
}

Pasangin juga sama konvensi yang udah ada: argumen (source, target) jangan dibalik diam-diam, equals() jangan ngelempar exception, unit "milidetik" jangan tiba-tiba "detik". Makin sesuai dugaan, makin sedikit bug yang lahir dari salah paham.

« Tombol bertuliskan "Off" yang ternyata mem-format harddisk. Secara teknis "berfungsi"—tapi nggak ada yang menduga itu. »
◈ Aturan LapanganSeparation of Concerns

Pisahkan urusan yang beda ke modul/lapisan yang beda. Tiap bagian fokus ke satu perhatian—domain, persistence, presentation—dan nggak bocor ke yang lain.

SoC itu prinsip arsitektural: bukan soal satu class (itu SRP), tapi soal nge-petakan sistem jadi area perhatian terpisah. Logika bisnis nggak boleh tahu SQL; HTTP controller nggak boleh ngitung pajak; lapisan presentasi nggak boleh nge-query DB. Persis pola berlapis hexagonal: core (domain) ← adapter (persistence/HTTP), atau MVC—Model, View, Controller masing-masing satu urusan.

OrderService.java
// ❌ satu method: bisnis + SQL + render HTML campur aduk
public String checkout(Order order) {
    BigDecimal total = order.subtotal().add(tax);
    jdbc.execute("INSERT INTO orders ...");   // persistence
    return "<h1>Total: " + total + "</h1>";  // presentation
}

// ✓ tiap urusan di lapisannya sendiri
class OrderService {            // domain: aturan bisnis
    BigDecimal total(Order o) { ... }
}
interface OrderRepository {       // persistence: port
    void save(Order o);
}
class OrderView {               // presentation: render
    String html(BigDecimal total) { ... }
}
« Rumah yang sehat punya dapur, kamar tidur, dan kamar mandi sebagai ruang terpisah. Kamu nggak masak di kasur cuma karena "sama-sama di dalam rumah". »
◈ Sepupu, bukan kembar

SRP jagain satu class (satu alasan berubah); SoC jagain seluruh sistem (pisahkan area perhatian jadi lapisan). SoC dilanggar → muncul God Object, Big Ball of Mud, dan logika bisnis yang sandera ke detail framework. POLA dilanggar → bug halus yang susah dilacak karena semua orang ngira kodenya "aman".

Yang kegedean

Dua satwa pertama gampang dikenali dari ukurannya: method yang kepanjangan dan class yang kegemukan. Keduanya jarang lahir gede—mereka numpuk pelan-pelan, satu tambahan kecil tiap kali. Pas kamu sadar, scroll-nya udah nggak ketemu ujung.

Long Method Code Smell bahaya 3/5
Ciri-ciriSatu method puluhan baris, banyak level indentasi (if dalam for dalam try), butuh scroll buat lihat ujungnya. Ngerjain validasi, hitung, simpan, kirim—semua dalam satu napas.
AkibatSusah dibaca dan dites (logikanya kelilit jadi satu, nggak bisa dicek per bagian), gampang nyelipin bug pas diutak-atik, dan tiap orang harus paham seluruh method cuma buat ngubah satu langkah kecil.
HabitatLogika yang numpuk seiring waktu—mulai 5 baris, tiap fitur baru nambah "satu blok lagi" sampai nggak ada yang berani megang.
OrderService.javaSPESIMEN
void checkout(Cart cart) {
    // validasi
    if (cart.isEmpty()) { ... }
    for (Item i : cart.items()) {
        if (i.stock() < 1) { ... }
        // hitung diskon, pajak, ongkir...
    }
    // simpan ke DB
    // kirim email + SMS + push
    // ...40 baris lagi di bawah
}
PenangkalExtract Method → pecah tiap blok jadi method bernama (validate, price, persist, notify). Satu method satu hal; nama method jadi dokumentasi.
« Esai 3 halaman tanpa satu pun titik. Secara teknis "satu kalimat", tapi kamu kehabisan napas sebelum nangkap maksudnya. »
Large Class Code Smell bahaya 3/5
Ciri-ciriClass kebanyakan field dan method yang nggak nyambung satu sama lain. Banyak tanggung jawab dalam satu atap—kamu buka file-nya cuma buat ngubah satu hal, tapi harus scroll lewat 30 hal lain.
AkibatJadi titik tabrakan banyak orang sekaligus (merge conflict langganan), perubahan di satu fitur diam-diam bisa ngerusak fitur lain yang nebeng di class yang sama, dan makin lama makin nggak ada yang ngerti isi penuhnya.
HabitatKelas bernama Manager, Util, atau Helper—nama yang nggak janji apa-apa, jadi apa pun boleh ditaruh di situ.
UserManager.javaSPESIMEN
class UserManager {           // ngurus apa aja sih?
    Db db; Mailer mailer;
    Cache cache; PdfWriter pdf;  // field campur aduk

    void login(...) { ... }
    void resetPassword(...) { ... }
    void exportToPdf(...) { ... }
    void refreshCache(...) { ... }  // ...20 method lagi
}
PenangkalSRP + Extract Class → kelompokkan field & method yang saling pakai, lalu tarik jadi class sendiri (Authenticator, UserExporter, UserCache). Nama yang spesifik bikin orang ragu naruh barang asal-asalan.
« Lemari yang dijejali baju, kabel, dokumen, sama obat sekaligus. Nyari satu benda? Bongkar semua dulu. »
◈ Catatan lapangan

Ukuran cuma petunjuk, bukan vonis. Method 50 baris yang lurus dan datar masih lebih sehat daripada 12 baris dengan 5 level nesting. Yang kamu kejar bukan "baris pendek", tapi satu tanggung jawab yang jelas—pendeknya datang sendiri sebagai bonus.

Parameter berserakan

Dua smell yang sering jalan bareng. Satu method nuntut terlalu banyak argumen; dan beberapa data yang selalu nongol berkelompok tapi nggak pernah dibungkus jadi satu. Keduanya tanda: ada konsep yang belum kamu kasih nama.

Long Parameter List Code Smell bahaya 3/5
Ciri-ciriMethod nuntut 4 parameter atau lebih. Ribet dipanggil, dan deretan tipe yang sama (String, String, String) gampang banget ketuker urutannya tanpa ketahuan compiler.
AkibatArgumen ketuker urutan lolos kompilasi tapi jebol pas runtime, dan tiap nambah field kamu kebuka signature-nya — semua pemanggil ikut harus disunting.
HabitatConstructor & factory yang "tumbuh" tiap ada field baru; method create/register yang terus ditambahin argumen.
UserService.javaSPESIMEN
// ❌ 6 argumen — siapa yang inget urutannya?
User createUser(
    String name, String email, String phone,
    int age, boolean active, String role) {
  ...
}

// pemanggilan: gampang ketuker email <-> phone
createUser("Budi", "0812..", "budi@x.id",
           30, true, "ADMIN");
PenangkalBungkus argumen jadi satu Parameter Object / Command Object (mis. CreateUserCommand). Pemanggilan jadi pakai nama field, urutan nggak relevan lagi, dan field baru = nambah ke objek, bukan ke signature.
« Belanja ngafal 9 barang di kepala vs nyodorin secarik daftar belanja — daftar nggak bakal ketuker telur sama tepung. »
Data Clumps Code Smell bahaya 2/5
Ciri-ciriSekumpulan data yang selalu muncul bareng ke mana-mana — startX, startY, endX, endY atau street, city, zip. Kalau satu jalan, yang lain pasti ikut. Mereka sebenarnya satu konsep yang dipecah-pecah.
AkibatKarena rombongan datanya disebar manual, satu perubahan kecil di kelompok itu maksa kamu ngedit banyak tempat sekaligus, dan validasinya nggak punya rumah jadi di-copy ulang ke mana-mana.
HabitatField di class yang nempel berurutan; daftar parameter yang itu-itu lagi di banyak method (sering jadi sumber Long Parameter List juga).
Geometry.javaSPESIMEN
// ❌ 4 angka yang selalu jalan bareng
double distance(
    double startX, double startY,
    double endX,   double endY) {
  ...
}

// ✓ jadiin objek — dua titik, bukan empat angka
double distance(Point start, Point end) {
  ...
}
PenangkalJadikan kelompoknya satu objek — Point, Address, DateRange. Ini sering jadi pintu masuk ke value object: begitu dibungkus, validasi & perilaku (jarak, format alamat) punya rumah yang jelas.
« Garam, merica, pala selalu dipakai barengan — taruh di satu rak bumbu, bukan disebar tiga sudut dapur. »
◈ Catatan lapangan

Data Clumps sering jadi akar Long Parameter List: begitu kamu bungkus si rombongan data jadi satu objek, daftar parameter ikut mengkerut sendiri. Obatin yang clumps dulu, biasanya yang panjang ikut sembuh.

Logika nyasar — disalin ke mana-mana, atau ngurusin urusan tetangga

Dua smell ini soal logika yang ada di tempat yang salah. Yang satu logika-nya kebanyakan kembar—nempel di banyak titik. Yang satu lagi logika-nya numpang di class yang salah—sibuk ngutak-atik data milik orang lain. Dua-duanya bikin perubahan jadi mahal.

Duplicated Code Code Smell bahaya 4/5
Ciri-ciriBlok kode atau aturan yang sama nongol di banyak tempat. Mau benerin satu bug? Kamu harus benerin di N tempat—dan pasti ada satu yang kelewat.
AkibatSatu bug fix gampang ketinggalan di salah satu copy, jadi versi-versinya pelan-pelan beda sendiri—dan kamu bayar ongkos maintenance berlipat tiap kali aturannya berubah.
HabitatHasil copy-paste yang "biar cepat", validasi yang diulang per controller, rumus diskon yang dihitung ulang di tiap layar.
PriceCalc.javaSPESIMEN
// rumus pajak yang sama, dua tempat
BigDecimal cartTotal() {
    BigDecimal tax = sub.multiply(new BigDecimal("0.11"));
    return sub.add(tax);
}
BigDecimal invoiceTotal() {
    BigDecimal tax = sub.multiply(new BigDecimal("0.11"));
    return sub.add(tax);   // pajak naik? edit DUA-duanya
}
PenangkalExtract Method / Extract Class jadi satu addTax() bersama; itu DRY. Tapi hati-hati false DRY: kalau dua blok kebetulan mirip padahal alasan berubahnya beda, jangan paksa gabung—itu malah bikin kopling palsu.
« Satu nomor telepon ditulis di lima buku. Pindah rumah, kamu harus inget update kelimanya—dan satu pasti ketinggalan. »
Feature Envy Code Smell bahaya 3/5
Ciri-ciriSebuah method lebih sibuk ngutak-atik data class lain daripada data class-nya sendiri—penuh other.getX(), other.getY() lalu ngitung sendiri. Method-nya "iri" sama fitur class tetangga.
AkibatLogika kepisah dari datanya, jadi tiap kali struktur si tetangga berubah method ini ikut jebol—dan domain-nya keburu jadi kantong data kosong yang susah dilindungi aturannya.
HabitatService yang nyedot getter dari domain object, lalu nyusun logika di luar—domain-nya cuma jadi kantong data (anemic).
PriceService.javaSPESIMEN
class PriceService {
    BigDecimal finalPrice(Order o) {
        // sibuk ngurus data milik Order, bukan dirinya
        BigDecimal sub = o.getQty().multiply(o.getUnitPrice());
        BigDecimal disc = sub.multiply(o.getDiscountRate());
        return sub.subtract(disc);
    }
}
PenangkalMove Method ke class pemilik data: pindahin finalPrice() jadi Order.finalPrice(), biar logika nempel sama data-nya. Prinsip Tell, Don't Ask—suruh object yang ngitung, jangan nanya isinya terus kamu yang ngitung.
« Kamu bolak-balik ngubek kulkas tetangga buat masak di dapur sendiri. Mendingan masak di dapur dia—isinya kan punya dia. »
◈ Benang merah

Dua-duanya nyembuhinnya dengan memindahkan logika ke rumahnya: Duplicated Code → satu sumber kebenaran lewat ekstrak; Feature Envy → logika ikut ke class yang punya datanya. Tapi ingat: jangan asal gabung yang cuma kebetulan mirip—itu false DRY.

Tipe yang malas

Konsep domain itu punya aturan—uang nggak boleh negatif, nomor HP punya format, mata uang cuma boleh "IDR" atau "USD". Tapi sering kita tampung semuanya pakai String dan int telanjang. Tipe-nya betul secara compiler, tapi malas: dia nggak nyimpen satu pun aturan domain. Akibatnya validasi kesebar dan keputusan "ini tipe apa" jadi switch di mana-mana.

Primitive Obsession Code Smell bahaya 3/5
Ciri-ciriKonsep domain dipaksa masuk ke tipe primitif telanjang—String currency, long amount, String phone—tanpa value object. Validasi & aturannya kesebar di tiap pemanggil.
AkibatBegitu satu pemanggil lupa satu cek, data invalid lolos diam-diam dan jadi bug senyap; mau ubah aturannya pun kamu harus berburu ke semua pemanggil—gampang kelewat.
HabitatParameter method yang panjang, DTO mentah, "ah pakai String dulu deh". Tumbuh subur di kode yang buru-buru.
Wallet.javaSPESIMEN
// uang & mata uang jadi primitif telanjang
void transfer(long amount, String currency,
              String phone) {
    // validasi diulang di SETIAP pemanggil
    if (amount < 0) throw new IllegalArgumentException();
    if (!currency.equals("IDR")) throw ...;
    if (!phone.matches("\\+62...")) throw ...;
    // lupa salah satu cek di pemanggil lain = bug senyap
}
PenangkalValue Object bertipe: bungkus jadi Money, Currency, PhoneNumber. Aturan & validasi hidup satu kali di dalam tipe-nya, bukan kesebar di pemanggil. Selaras ADR-001 (aggregate ID = VO, bukan String/UUID raw).
« Nyimpen obat keras di botol air mineral bekas: "kan sama-sama cairan". Sampai ada yang minum salah. Botol yang benar = label + tutup pengaman. »
Switch Statements Code Smell bahaya 3/5
Ciri-ciriCabang switch/if-else atas "tipe" atau "type-code" yang sama muncul di banyak tempat. Tiap tipe baru maksa kamu nyunting semua switch sekaligus—gampang kelewat satu.
AkibatNambah satu tipe baru jadi operasi berisiko di banyak file sekaligus; satu switch kelewat = perilaku nggak konsisten yang baru ketahuan pas produksi.
HabitatSering nempel di Primitive Obsession: ada String role / int type, lalu di-switch ulang-ulang di service, controller, dan reporting.
FeeCalculator.javaSPESIMEN
int fee(String accountType) {
    switch (accountType) {        // switch yang sama...
        case "BASIC":   return 2000;
        case "PREMIUM": return 0;
        default:        return 5000;
    }
}
// ...di-copy lagi di limit(), di label(), di icon()
// tambah "VIP"? edit SEMUA switch, satu kelewat = bug
PenangkalPolymorphism (OCP): Replace Conditional with Polymorphism. Bikin tipe AccountType dengan method fee()/limit(); tiap subtipe jawab sendiri. Tambah varian = tambah satu kelas, nol switch disentuh.
« Daripada satu satpam yang hafal aturan tiap penghuni gedung, kasih tiap penghuni kunci sendiri. Pendatang baru tinggal bawa kuncinya—satpam nggak perlu belajar ulang. »
◈ Dua gejala, satu akar

Primitive Obsession dan Switch Statements sering jalan berpasangan: tipe yang malas (String type) memaksa keputusan dipindah keluar jadi switch. Obatin akarnya—ganti primitif jadi tipe yang "ngerti dirinya sendiri"—maka switch-nya ikut lenyap.

Perubahan yang merembet

Dua satwa ini muncul gara-gara tanggung jawab kececer dan klien kepo sama struktur orang lain. Satu perubahan kecil, eh malah ngerembet ke mana-mana.

Bedanya sama Divergent Change: di sana satu class diutak-atik dari banyak arah. Di Shotgun Surgery kebalikannya — satu perubahan maksa kamu nyentuh banyak class sekaligus. Sama-sama gejala cohesion yang berantakan, beda arah aja.

Shotgun Surgery Code Smell bahaya 4/5
Ciri-ciriSatu perubahan kecil—misal nambah field di User—maksa kamu ngedit banyak class berserakan: DTO, mapper, validator, repo, logger. Lupa satu, langsung bug. Kebalikan dari Divergent Change.
AkibatTiap fitur kecil jadi melelahkan & lambat—kamu keliling banyak file, dan satu titik kelewat langsung jadi bug halus yang lolos ke produksi.
HabitatLogika satu konsep nyebar tipis di seluruh codebase; cohesion rendah, coupling tinggi antar modul.
PenangkalKumpulin yang berubah bareng ke satu tempat lewat Move Method / Move Field—naikin high cohesion biar satu perubahan = satu sentuhan.
« Ganti satu warna logo, tapi harus keliling ke 12 ruangan buat nimpa stiker satu-satu. »
Message Chains Code Smell bahaya 3/5
Ciri-ciriRantai panggil panjang: a.getB().getC().getD().doIt(). Klien kenal terlalu dalam struktur internal objek lain—langgar Law of Demeter ("cuma ngobrol sama tetangga langsung").
AkibatKlien jadi nempel ketat ke struktur dalam objek lain—begitu salah satu lapisan dirombak, semua kode yang nyusurin rantai itu ikut pecah & harus diperbaiki bareng.
HabitatKode yang nge-navigasi objek buat ngambil data, bukan nyuruh objek ngerjain tugasnya sendiri.
CheckoutService.javaSPESIMEN
// ❌ klien nyusurin 4 lapis struktur orang lain
String kota = order.getCustomer()
                  .getAddress()
                  .getCity()
                  .getName();
// putus satu getter = seluruh rantai ambruk
PenangkalHide Delegate—sembunyiin rantai di balik satu method (order.shippingCity()). Atau tell-don't-ask: suruh objek ngerjain, jangan ditanyain isi dalemnya.
« Kereta gerbong panjang—makin banyak sambungan, makin gampang putus di tengah jalan. »
Bestiary · Code Smells

Niat baik yang jadi beban

Dua smell ini lahir dari maksud baik. Yang satu: "siapa tahu nanti butuh fleksibilitas". Yang satu lagi: "biar gampang dibaca, aku kasih komentar". Masalahnya, keduanya malah nambah beban tanpa nambah nilai—dan ngumpetin masalah yang sebenarnya.

Speculative Generality Code Smell bahaya 3/5
Ciri-ciriAbstraksi, hook, atau parameter yang dibikin "buat jaga-jaga nanti"—tapi nggak pernah kepakai. interface dengan satu implementasi, abstract base tanpa subclass kedua, parameter yang selalu dikirim nilai sama. Ini YAGNI yang dilanggar.
AkibatTiap pembaca kepaksa nelusurin lapisan indireksi kosong yang nggak ngapa-ngapain, jadi kode lebih susah dipahami & dites—kamu mikul ongkos fleksibilitas yang nilainya nggak pernah cair.
HabitatDibikin developer yang "mikir ke depan", framework rumahan, kode yang ngarep jadi library padahal cuma dipakai sekali.
PaymentGateway.javaSPESIMEN
// satu interface, satu impl, selamanya
interface PaymentGateway {
    void pay(Money amount);
}
class CreditCardGateway implements PaymentGateway {
    public void pay(Money amount) { ... }
}
// parameter "biar fleksibel" yang nggak pernah dipakai
void export(Report r, boolean compress,
            String futureMode) { ... } // compress slalu false
PenangkalYAGNI → hapus yang nggak dipakai. Inline-kan interface 1-impl, buang parameter mati, abstraksi-kan nanti pas konsumen kedua benar-benar muncul—bukan sebelumnya.
« Bangun jembatan ke pulau yang belum ada penghuninya. Pas akhirnya ada yang pindah ke sana, ternyata maunya naik perahu. »
Comments (deodoran) Code Smell bahaya 2/5
Ciri-ciriKomentar dipakai nutupin kode jelek—penjelasan panjang buat blok yang mestinya cukup dikasih nama yang jelas. Atau komentar yang cuma ngulang kode (redundan), atau udah basi nggak nyambung sama kodenya lagi.
AkibatKomentar basi bikin pembaca percaya yang salah lalu nulis bug dengan pede, sementara kode jeleknya tetap ngumpet di balik penjelasan—jadi yang busuk nggak pernah kelihatan buat dibenerin.
HabitatMethod panjang yang dipotong-potong pakai komentar "// validasi", "// hitung", kode warisan yang udah berubah tapi komentarnya ketinggalan.
OrderService.javaSPESIMEN
// cek apakah user boleh checkout
if (u.getAge() >= 18 && u.getBalance() > 0
        && !u.isBanned()) { ... }

// naikkan harga 10%  <- basi, sekarang 20%
BigDecimal p = base.multiply(new BigDecimal("1.20"));

int i = i + 1; // tambah i dengan satu
PenangkalTulis ulang kode biar ngomong sendiri: ekstrak ke method bernama (canCheckout(u)), konstanta bernama (PRICE_MARKUP). Komentar simpan buat "kenapa", bukan "apa".
« Nyemprot deodoran di atas keringat seharian. Wanginya nutupin sebentar—padahal yang dibutuhin cuma mandi. »
◈ Garis tipisnya

Komentar nggak selalu jahat—yang jahat itu komentar pengganti nama dan komentar basi. Komentar bagus jawab "kenapa begini" (keputusan, trade-off, workaround bug pihak ketiga) yang nggak bisa dititipkan ke nama. Sama soal Speculative Generality: aturan tiganya—abstraksi-kan pas kejadian kedua, bukan dugaan pertama.

Bestiary · Design Smells (special)

Pembusukan struktur (rotting design)

Beda dari code smell yang sifatnya lokal (satu method, satu class), design smell itu gejala di level desain—penyakit yang nyebar ke struktur sistem. Inilah tujuh "satwa" yang SOLID dirancang khusus buat cegah. Kenali mereka cepat: satu baris ciri, satu prinsip penangkal.

Rigidity Design Smell bahaya 4/5
Ciri-ciriSusah diubah—satu perubahan kecil ngerembet panjang ke modul-modul lain yang nggak nyangka.
AkibatEstimasi tugas kecil meleset jauh—tiap perubahan jadi proyek dadakan, tim takut nyentuh kode, fitur baru makin lama keluar.
PenangkalOCP + DIP → tambah fitur lewat ekstensi, bukan ngedit yang stabil; gantung ke abstraksi.
« Geser satu meja, eh seluruh ruangan harus ditata ulang. »
Fragility Design Smell bahaya 4/5
Ciri-ciriUbah satu tempat, malah rusak di bagian yang sama sekali nggak berhubungan secara konsep.
AkibatBug muncul terus dari tempat tak terduga—tiap rilis bikin deg-degan, butuh regression test masif cuma buat berani deploy.
PenangkalSRP + OCP → satu alasan berubah per class; isolasi yang volatil dari yang stabil.
« Ketuk paku di dinding dapur, lampu kamar mandi mati. »
Immobility Design Smell bahaya 3/5
Ciri-ciriSusah dipakai-ulang—bagian yang berguna keseret baggage dependensi yang nggak kamu butuh.
AkibatOrang malah nulis ulang dari nol daripada reuse—jadi duplikasi numpuk, effort kebuang, padahal solusinya udah ada.
PenangkalDIP + ISP → bergantung ke interface ramping, bukan ke modul gemuk penuh kabel.
« Mau pinjam obeng, tapi dia terbaut mati ke seluruh kotak perkakas. »
Viscosity Design Smell bahaya 3/5
Ciri-ciriNge-hack jalan pintas lebih gampang daripada benerin dengan cara yang benar—jadi orang milih jalan pintas.
AkibatTiap orang nambah hack kecil, desain makin lama makin amburadul—utang teknis numpuk diam-diam sampai sistem susah diselamatkan.
PenangkalJaga lingkungan & desain → build cepat, test mudah, struktur jelas; bikin "cara benar" jadi cara termudah.
« Tempat sampah jauh, tetangga deket—lama-lama semua nimbun di pojok tetangga. »
Needless Complexity Design Smell bahaya 3/5
Ciri-ciriInfrastruktur & abstraksi buat kebutuhan yang belum ada—"siapa tahu nanti perlu".
AkibatTiap baca kode harus nyusurin lapisan abstraksi yang nggak kepake—onboarding lama, maintenance berat, padahal fiturnya nggak pernah datang.
PenangkalYAGNI → bangun yang dibutuhkan sekarang; ekstensi nanti pas konsumen kedua benar-benar muncul.
« Bikin garasi 6 mobil padahal cuma punya sepeda. »
Needless Repetition Design Smell bahaya 3/5
Ciri-ciriStruktur yang sama di-copas berkali-kali—sekali ada bug, kamu mesti betulin di banyak tempat.
AkibatFix di satu salinan, lupa lima lainnya—bug yang sama hidup lagi, perilaku mulai beda-beda diam-diam antar copy-an.
PenangkalDRY → satu sumber kebenaran; ekstrak abstraksi yang memang sama alasan berubahnya.
« Resep yang sama ditulis ulang di 12 buku—ganti satu bumbu, harus revisi semuanya. »
Opacity Design Smell bahaya 3/5
Ciri-ciriKode susah dipahami—niat penulisnya kabur, butuh waktu lama buat ngerti satu blok.
AkibatTiap sentuhan butuh jam-jaman ngeraba dulu—perubahan jadi lambat, salah paham bikin bug baru, dan pengetahuannya nyangkut di kepala satu orang.
PenangkalKejelasan / Clean Code → nama jujur, fungsi pendek, struktur yang membaca seperti niatnya.
« Peta harta karun, tapi petunjuknya ditulis pakai sandi yang penulisnya sendiri lupa. »
◈ Gambaran besarnya

Ketujuh smell ini jarang datang sendirian—biasanya satu memicu yang lain. Bedanya dengan code smell: ini soal bentuk sistem, bukan satu potongan kode. Obatnya pun struktural: SOLID, DRY, YAGNI, plus disiplin jaga lingkungan kerja.

« Rumah yang dibiarkan membusuk—atap mulai bocor, fondasi retak halus, pintu seret. Tiap gejala kelihatan kecil, tapi makin lama dibiarkan, makin mahal (dan kadang mustahil) buat diperbaiki. »
Bestiary · Anti-Pattern

Raksasa & kekusutan

Dua satwa paling sering ketemu di kode legacy. Yang satu bertubuh raksasa—nelan tanggung jawab seantero sistem. Yang satu lagi nggak gede, tapi alurnya kusut kayak benang tumpah. Keduanya tumbuh dari hal yang sama: kode nambah terus tanpa ada yang nge-desain.

Di taksonomi (seksi 01) sempat dipreview, sekarang entri resminya. Catat ciri-cirinya—biar pas ketemu di rimba kamu langsung kenal.

God Object Anti-Pattern bahaya 4/5
Ciri-ciriSatu class megang & ngendaliin hampir semua hal di sistem—data, alur, aturan. Ribuan baris, puluhan method nggak nyambung, dan tiap class lain nge-import dia. Hapus satu method, separuh app rusak.
AkibatTiap ganti satu hal kecil bisa nyenggol fitur yang nggak ada hubungannya, nggak bisa dites terpisah, dan jadi titik macet—semua orang ngantri ngedit file yang sama, merge conflict di mana-mana, lama-lama nggak ada yang berani nyentuh.
HabitatKode legacy, OOP setengah jadi (objek cuma kantong global), dan tim yang kebiasaan "taruh di Manager dulu deh, nanti rapiin".
SystemManager.javaSPESIMEN
class SystemManager {        // 3100 baris, raja segalanya
    void login() { ... }
    void chargeCard() { ... }
    void sendEmail() { ... }
    void renderHtml() { ... }
    void writeLog() { ... }  // ...60 method lagi
}
PenangkalSRP → pecah per tanggung jawab. Tarik tiap kelompok method jadi class sendiri (Auth, Payment, Mailer, View), terus si raksasa cuma jadi koordinator tipis—atau hilang sama sekali.
« Satu raja yang mengurus dapur, tentara, dan pajak sekaligus: begitu dia sakit, seluruh kerajaan lumpuh. »
Spaghetti Code Anti-Pattern bahaya 4/5
Ciri-ciriAlur kontrol kusut—if nested dalam-dalam, flag boolean ke mana-mana, lompatan (break/continue/early return) yang bikin pusing. Susah diikuti, susah diubah; ngerti satu cabang butuh nelusurin lima yang lain.
AkibatTiap perubahan jadi lambat & ngeri-ngeri sedap karena kamu nggak bisa nebak cabang mana yang ikut kena, bug ngumpet di nesting yang dalam, dan dev baru butuh berhari-hari cuma buat ngerti satu fungsi.
HabitatKode yang tumbuh tanpa desain, tambal-sulam "fix dikit-dikit", dan fitur baru yang dijejalin pakai if tambahan ketimbang dipikirin strukturnya.
OrderFlow.javaSPESIMEN
void process(Order o) {
    if (o != null) {
        if (o.isPaid()) {
            if (!o.shipped()) {
                boolean ok = true;
                for (Item it : o.items()) {
                    if (it.stock() < 1) { ok = false; break; }
                }
                if (ok) { ship(o); } else { hold(o); }
            }
        }
    }
}
PenangkalStructured programming + ekstrak fungsi. Pakai guard clause biar null/belum-bayar keluar duluan, ekstrak cek stok jadi method allInStock(o), kurangi level nesting. Tiap blok jadi satu nama yang kebaca.
« Sepiring spageti: tarik satu helai, semuanya ikut goyang—nggak ada awal-akhir yang jelas. »
◈ Sering jalan bareng

God Object dan Spaghetti suka muncul di tempat yang sama: satu class raksasa yang isinya alur kusut. Obatnya pun nyambung—pecah per tanggung jawab (SRP) bikin tiap potongan kecil, dan begitu kecil, ngeluruskan alurnya jadi gampang.

Bestiary · Anti-Pattern

Alat & ritual: satu palu buat semua, dan nyalin tanpa ngerti

Dua satwa ini lahir dari kenyamanan, bukan kemalasan. Satu maksa satu alat favorit buat tiap masalah. Satu lagi niru praktik orang tanpa paham kenapa praktik itu ada. Dua-duanya kelihatan produktif—sampai masalahnya nggak cocok sama cetakannya.

Golden Hammer Anti-Pattern bahaya 3/5
Ciri-ciriMaksa satu tool/framework/pattern buat segala masalah. "Kalau cuma punya palu, semua keliatan paku." Tiap fitur baru jawabannya selalu sama: pakai X aja—padahal X nggak pas.
AkibatSolusi yang dipaksain bikin kode rapuh & bertele-tele—regex buat JSON gampang jebol di edge case, dan tim kebablasan ngehindari alat yang justru lebih pas, jadi tiap masalah baru makin susah dibereskan.
HabitatTim yang baru jago satu hal; orang yang nyaman sama satu solusi dan ogah belajar yang lain.
ReportService.javaSPESIMEN
// "Regex bisa apa aja!" — semua diparse pakai regex,
// termasuk yang harusnya pakai parser beneran
String sum = extract(json, "\"total\":(\\d+)");
String tag = extract(xml,  "<name>(.*?)</name>");
String dt  = extract(csv,  "^[^,]+,([^,]+)");
// JSON parser, XML parser, CSV reader? Nggak, palu doang.
PenangkalPilih alat sesuai bentuk masalah, bukan sebaliknya. Perluas perkakas: tiap solusi punya zona nyamannya—JSON pakai parser JSON, bukan regex. Sadari kapan palu favoritmu udah mentok.
« Tukang yang cuma bawa palu akan memukul sekrup, baut, dan engsel—lalu heran kenapa pintunya nggak nutup. »
Cargo Cult Programming Anti-Pattern bahaya 3/5
Ciri-ciriNyalin kode/praktik/pattern tanpa paham kenapa-nya—ritual tanpa pemahaman. Copas dari StackOverflow tanpa ngerti, atau nambahin synchronized, try/catch kosong, anotasi "biar aman" karena katanya gitu.
AkibatKode penuh ritual yang nggak ada gunanya—try/catch kosong yang nelan error diam-diam bikin bug jadi mustahil dilacak, dan nggak ada yang berani benerin karena nggak ada yang ngerti kenapa baris itu ada di situ.
HabitatCodebase warisan dengan "begini caranya dari dulu"; dev yang niru senior tanpa nanya alasannya.
UserLoader.javaSPESIMEN
User load(long id) {
    try {
        return findById(id);
    } catch (Exception e) {
        // "katanya wajib try/catch di tiap method"
        return null;   // error ditelan, nggak ngerti kenapa
    }
}
PenangkalPahami dulu sebelum pakai. Tiap baris yang kamu salin harus bisa kamu jelasin alasannya. Kalau nggak tahu kenapa sebuah pattern ada, jangan tiru—cari tahu masalah apa yang dia selesaikan, baru putuskan apakah masalah itu masalahmu.
« Suku cargo cult bikin menara kontrol dari bambu dan headphone dari batok kelapa, berharap pesawat pembawa barang datang lagi—niru bentuknya, tanpa paham mesin yang bikin pesawat terbang. »
◈ Sepupu dekat

Dua-duanya soal relasi kamu sama alat. Golden Hammer terlalu sayang sama satu alat; Cargo Cult pakai alat tanpa ngerti cara kerjanya. Obatnya sama: tahu kenapa sebelum tahu caranya.

Bestiary · Anti-Pattern

Sampah yang dibiarkan

Nggak semua bahaya itu kode yang aktif berbuat jahat. Kadang yang bikin codebase berat justru yang diam—kode mati yang takut disentuh, dan barang yang disimpan "siapa tahu kepakai". Dua spesimen ini sama-sama beban mati, beda cara munculnya.

Lava Flow Anti-Pattern bahaya 3/5
Ciri-ciriKode mati atau usang yang membeku di codebase—nggak ada yang berani hapus karena "jangan disentuh, nanti rusak". Nggak ada yang tahu fungsinya, jadi dibiarin.
AkibatTiap baca file kamu kebuang waktu nebak "ini kepakai nggak sih?"; orang baru makin lama paham; dan tiap refactor jadi ekstra ribet karena harus mutar-mutar batu beku yang nggak boleh disentuh.
HabitatProyek lama tanpa test, sering ganti orang, dokumentasi nol—jadi takut nyentuh apa pun.
PaymentService.javaSPESIMEN
class PaymentService {
    // JANGAN HAPUS — dipakai 2019? entah. takut rusak.
    private void legacyReconcile(String mode) {
        if (mode.equals("OLD")) { ... }   // gak ada pemanggil
    }
    // TODO(2020): cleanup nanti — nggak pernah datang
    private String oldHash() { return null; }
}
PenangkalTulis test dulu buat kunci perilaku yang masih dipakai, lalu hapus dead code—Git tetap nyimpen sejarahnya, jadi nggak benar-benar hilang. Biasakan Boy Scout Rule: tinggalkan lebih bersih dari pas datang.
« Lava yang mengalir lama-lama mengeras jadi batu. Sekali membeku, dia jadi permanen di lanskap—dan semua orang cuma jalan memutarinya. »
Boat Anchor Anti-Pattern bahaya 2/5
Ciri-ciriKomponen, library, atau kode disimpan "siapa tahu nanti kepakai"—padahal nggak pernah dipanggil. Cuma nambah berat: dependency, build time, dan beban mikir tiap orang baca.
AkibatBuild makin lama & artifact makin gemuk gara-gara dependency yang nggak dipakai; tiap upgrade atau audit keamanan kamu mesti ngurusin barang yang harusnya nggak ada di sana.
HabitatSisa eksperimen, fitur yang batal, library yang dulu dipertimbangin tapi nggak jadi—masih nempel di pom.xml.
pom.xml — dependency matiSPESIMEN
<!-- "mungkin dipakai buat reporting nanti" -->
<!-- (nggak ada satu pun import-nya) -->
<dependency>
  <groupId>org.apache.poi</groupId>
  <artifactId>poi-ooxml</artifactId>
</dependency>
PenangkalYAGNI—You Aren't Gonna Need It. Kalau belum dipakai sekarang, hapus. Butuh nanti? Tambah lagi nanti; Git inget.
« Jangkar kapal itu berat. Diseret terus padahal kapal lagi jalan—bukannya menahan, malah bikin pelan. »
◈ Beda tipisnya

Keduanya beban mati, tapi bedanya di kenapa ada. Lava Flow lahir dari takut—dulu aktif, sekarang membeku karena nggak berani dihapus. Boat Anchor lahir dari harapan—disimpan buat masa depan yang nggak pernah datang. Obatnya sama: berani hapus, karena Git nggak pernah lupa.

Bestiary · Anti-Pattern

Buru-buru & misterius

Dua kebiasaan yang kelihatan "pinter" tapi malah bikin susah. Yang satu ngebut sebelum tahu jalannya; yang satu ninggalin angka misterius di kode buat ngebingungin orang besok—termasuk kamu sendiri.

Premature Optimization Anti-Pattern bahaya 3/5
Ciri-ciriNgoptimasi sebelum ada bukti—nggak ada profiling, cuma firasat "ini pasti lambat". Kejelasan dikorbanin demi kecepatan yang belum tentu perlu: cache rumit, micro-tweak bit, hindari method call demi "ngirit". Kata Knuth: ini "root of all evil".
AkibatKode jadi ruwet & susah dibaca demi ngejar kecepatan yang ternyata nggak ngefek—waktu kebuang di tempat salah, sementara bottleneck asli malah kelewat.
HabitatEngineer yang baru baca artikel performa, hot-path imajiner, code review yang ribut soal nanodetik di kode yang jalan sekali sehari.
PenangkalBikin jelas & benar dulu. Lalu profil buat nemu bottleneck asli. Baru optimasi bagian yang terbukti jadi masalah—dengan benchmark sebelum/sesudah.
« Ngebut di jalan yang belum tahu arahnya. Bukannya cepet sampai, malah cepet nyasar. »
Magic Numbers / Strings Anti-Pattern bahaya 2/5
Ciri-ciriAngka atau string telanjang nongol di tengah kode tanpa nama—if (status == 3), delay(86400). Yang baca harus nebak: 3 itu apa? 86400 itu detik sehari atau cuma kebetulan?
AkibatPas nilainya berubah kamu harus berburu tiap copy-nya satu-satu—kelewat satu langsung bug, dan orang baru butuh lama buat ngerti maksud angka itu.
HabitatCek status, timeout, indeks array, kode rate/diskon, validasi panjang field—di mana pun "tau-tau ada angka".
Order.javaSPESIMEN
if (order.status() == 3) {        // 3 itu apa???
    scheduler.retry(86400);          // detik? jam?
}
PenangkalKasih nama: enum untuk status, static final bernama untuk konstanta. if (order.status() == SHIPPED) & retry(ONE_DAY_SECONDS)—nilainya jadi cerita, bukan teka-teki.
« Resep yang nulis "masukkan 220" — 220 apa? Gram? Derajat? Detik? Tanpa nama & satuan, masakannya jadi judi. »
Bestiary · Anti-Pattern

Duplikat & bikin ulang

Dua kebiasaan yang kelihatan produktif tapi mahal di belakang: nyalin kode yang udah jalan biar cepet, dan nulis ulang dari nol sesuatu yang udah ada matang. Satu bikin duplikasi, satu bikin roda yang gak bulat.

Keduanya anti-pattern karena kelihatan masuk akal pas dikerjain—"tinggal copas dikit", "ah, gampang kok bikin sendiri"—tapi ninggalin jejak yang nyiksa tim berbulan-bulan kemudian. Kenalin ciri-cirinya.

Copy-Paste Programming Anti-Pattern bahaya 4/5
Ciri-ciriNyelesaiin masalah baru dengan nyalin blok kode yang mirip, terus di-tweak dikit. Blok yang sama nyebar di banyak file—logika identik, beda variabel doang.
HabitatDeadline mepet, "yang penting jalan dulu", tim yang gak kenal helper/util yang udah ada.
PriceCalc.javaSPESIMEN
class PriceCalc {
    BigDecimal withTaxA(BigDecimal p) {
        return p.multiply(new BigDecimal("1.11"));
    }
    // copas, ganti 1.11 -> 1.05 doang
    BigDecimal withTaxB(BigDecimal p) {
        return p.multiply(new BigDecimal("1.05"));
    }
}
AkibatMenghasilkan Duplicated Code (smell). Pas ada bug atau aturan berubah, kamu harus fix di banyak tempat—lupa satu, sisanya diam-diam salah.
PenangkalExtract & reuse + DRY: tarik blok ke satu method/class yang diparameterkan, panggil dari mana-mana. Satu sumber kebenaran, fix sekali.
« Fotokopi catatan yang ada typo-nya buat 20 orang. Pas typo ketahuan, kamu harus ngejar 20 lembar—bukan benerin satu master. »
Reinventing the Wheel Anti-Pattern bahaya 3/5
Ciri-ciriNulis sendiri sesuatu yang udah ada versi matang & teruji: parser tanggal bikinan sendiri, hashing/crypto rakitan sendiri, JSON serializer kustom. Edge case yang udah lama dipikirin orang lain, kamu temuin lagi satu-satu—lewat bug produksi.
AkibatKamu nanggung beban maintenance + edge-case yang sebenernya udah dipecahin orang lain—bug bermunculan di produksi, dan waktu yang harusnya buat fitur kebuang nge-debug roda yang harusnya gak perlu kamu bikin.
HabitatSindrom "not invented here", gengsi teknis, atau gak tahu librarynya udah ada.
MyDate.javaSPESIMEN
class MyDate {
    // parser tanggal sendiri — leap year? timezone? lupa.
    static int[] parse(String s) {
        String[] p = s.split("-");
        return new int[] {
            Integer.parseInt(p[0]),
            Integer.parseInt(p[1]),
            Integer.parseInt(p[2])
        }; // validasi? 31 Feb lolos.
    }
}
PenangkalPakai library teruji: java.time.LocalDate, lib crypto standar, JSON lib mapan. Mereka udah lewat ribuan jam pengujian & edge case.
Tapi awasLawannya juga jebakan: nambah dependency asal-asalan buat hal sepele. Timbang dulu—footprint, maintenance, lisensi, keamanan (lihat dependency-hygiene). Crypto: jangan pernah bikin sendiri. Util 3 baris: gak perlu lib.
« Mau nyebrang sungai, mending naik jembatan yang udah berdiri puluhan tahun—daripada nge-las jembatan sendiri pagi ini terus dilewatin truk sore ini. »
◈ Garis tipisnya

Copy-paste = males reuse. Reinvent = males cari. Obatnya beda arah: yang satu nyatuin kode jadi satu, yang satu mindahin kerjaan ke kode orang yang udah teruji. Sama-sama soal "jangan kerja dua kali", tapi jangan kebablasan jadi tukang tempel dependency.

Bestiary · Anti-Pattern

Tanpa bentuk & hantu lewat

Dua satwa yang gampang ketuker sama "biasa aja". Satu gede banget sampai kamu nggak sadar lagi bentuknya kayak apa; satu kecil dan sekilas lewat, numpang lewat doang. Beda ukuran, sama-sama bikin pusing.

Big Ball of Mud Anti-Pattern bahaya 5/5
Ciri-ciriSistem tanpa arsitektur yang jelas: semua nyambung ke semua, batas modul lebur, nggak ada lapisan. Mau utak-atik satu sudut, efeknya ngerembet ke mana-mana yang nggak kamu duga.
AkibatTiap fitur baru makin lama dikerjain dan makin sering meledakin bagian lain yang nggak nyangkut; dev baru butuh berbulan-bulan baru paham, dan akhirnya semua takut nyentuh apa pun sampai sistemnya beku.
HabitatKode yang tumbuh organik tanpa desain, terus-terusan di bawah tekanan deadline. Tambal sana-sini, "yang penting jalan", bertahun-tahun nggak pernah ada yang berani benerin strukturnya.
OrderModule.javaSPESIMEN
class OrderModule {            // "modul" tapi tau segalanya
    DbConnection db; HttpClient http; UiPanel ui;
    void checkout() {
        String sql = "SELECT ...";   // SQL mentah di sini
        ui.render();                // UI dipanggil langsung
        http.post("/payment");     // jaringan nyempil juga
        InventoryModule.stock--;   // colek modul tetangga
    }
}
PenangkalTetapkan batas & lapisan (Separation of Concerns): pisahkan domain, persistence, UI, jaringan. Lalu refactor bertahap—bungkus modul di balik antarmuka, potong ketergantungan silang satu per satu. Jangan rewrite total sekaligus.
« Kayak gumpalan lumpur raksasa: dari jauh kelihatan satu objek, tapi pas dipegang nggak ada pegangan, nggak ada bentuk—tangan kamu cuma masuk ke dalamnya. »
Poltergeist Anti-Pattern bahaya 2/5
Ciri-ciriClass "hantu" berumur pendek: dibuat, dipakai sebentar buat manggil class lain, terus langsung dibuang. Dia nggak nambah nilai—cuma perantara yang numpang lewat, nyimpan state sebentar, lalu hilang.
AkibatBaca alur jadi capek karena tiap aksi mesti loncat lewat perantara kosong dulu; class numpuk tanpa guna, dan saat debug kamu buang waktu nelusurin objek yang ternyata cuma nerusin panggilan.
HabitatKode yang dibikin "biar rapi": tiap aksi dikasih class koordinator sendiri, padahal isinya cuma satu baris yang nerusin ke objek lain.
ReportStarter.javaSPESIMEN
class ReportStarter {        // hantu: cuma numpang lewat
    private ReportEngine engine;
    ReportStarter(ReportEngine e) { this.engine = e; }
    void start() {
        engine.generate();        // itu doang isinya
    }
}

Tutup · Cara pakai panduan ini

Panduan, bukan kitab suci.

Kamu udah jalan jauh: dari prinsip yang sehat, lewat code smell, design smell, sampai anti-pattern. Sebelum tutup buku, satu hal yang paling penting—semua ini alat bantu mikir, bukan hukum yang dilanggar bikin kamu masuk neraka.

Empat tipe "satwa" tadi punya peran beda. Ingat ini aja:

◈ Aturan LapanganEmpat alat, satu kompas

Prinsip = kompas (arah ke mana). Code smell = alarm dini (gejala lokal). Design smell = pembusukan struktur (busuk dari dalam). Anti-pattern = jebakan yang kelihatan masuk akal—tapi selalu ada jalan keluarnya.

« Peta dan kompas nggak nyetir mobilnya buat kamu. Mereka cuma bikin kamu nggak nyasar. Yang megang setir tetap kamu. »

Kompas nunjuk utara, tapi kadang jalannya emang harus belok. Di sinilah orang sering salah: nganggap prinsip itu aturan absolut, terus jadi dogmatis—malah bikin kode lebih jelek demi "kemurnian". Itu bahaya beneran:

◈ Anti-dogma — baca ini

Semua di panduan ini HEURISTIK, bukan hukum. Konteks menang. Kadang "melanggar" itu justru tepat: duplikasi sengaja dua kode yang reason-to-change-nya beda (mirip kebetulan, bukan DRY violation), optimasi yang udah kamu profil dan kebukti perlu, abstraction yang kamu tahan sampai konsumen kedua muncul (YAGNI > DRY). Tujuan akhirnya bukan skor SOLID sempurna—tapi kode yang gampang diubah & dipahami. Kalau "memurnikan" malah bikin lebih ribet, kamu lagi nyembah aturan, bukan nyelesain masalah.

Jadi gimana cara pakainya tiap hari? Rekap singkat—tempel di kepala:

  • Kenali sebelum benerin — tahu ini smell, design smell, atau anti-pattern dulu, baru pilih obatnya.
  • Prinsip dilanggar → smell muncul — gejala itu sinyal, bukan musuh. Lacak balik ke prinsip mana yang kebobol.
  • Refactor pas lewat — Boy Scout — tinggalin kode sedikit lebih bersih dari pas kamu datang. Nggak usah nunggu izin.
  • Aturan itu heuristik, bukan dogma — konteks > kemurnian. Boleh "melanggar" kalau sadar & ada alasan.
◈ Panduan pendamping

Deck ini fokus ke prinsip, smell & anti-pattern. Buat lebih dalam, ada deck saudara: Clean Code (penamaan, fungsi kecil, komentar yang jujur), OOP (encapsulation, polymorphism, kapan objek bener-bener objek), dan Design Patterns (solusi baku buat masalah berulang).
