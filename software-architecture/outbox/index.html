Outbox Pattern

Cara aman menyimpan data dan mengirim event — tanpa ada yang hilang di tengah jalan.

$ Tulis dulu di buku, baru dikirim pak pos.

Simpan ke database + kirim event = dua pekerjaan. Bisa gagal salah satu.

💾

Kita simpan order ke database

Ini pekerjaan pertama.

📨

Lalu kirim event ke Kafka

Ini pekerjaan kedua. Supaya service lain tahu ada order baru.

💥

Kalau server mati di tengah-tengah?

Satu berhasil, satu gagal. Data jadi tidak cocok.

Satu transaksi

dua pekerjaan → dijadikan satu

◆ Buat apa ini? Kenapa pakai ini?

Given — kita perlu simpan data dan kasih tahu service lain.

When — dua pekerjaan itu dilakukan terpisah, lalu salah satunya gagal.

Then — event hilang, atau event terkirim padahal datanya tidak ada.

→ makanya kita pakai Outbox Pattern — supaya data dan event selalu kompak.

Tiga hal yang kita pelajari

bagian 1

Masalahnya

Kenapa simpan + kirim bisa bikin data kacau. Namanya dual write.

Cara kerja outbox

Tabel “kotak surat keluar” + petugas yang rajin mengirim.

Yang perlu dijaga

Masalah → solusi → jebakan.

Warm-up: kode ini kelihatan benar. Aman?

@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);      // 1. simpan ke DB
    kafka.send("order-created",       // 2. kirim event
               order.toEvent());
}   // <- transaksi DB commit di sini

Coba tebak 🤔

  • Kalau Kafka lagi mati, apa yang terjadi?
  • Kalau Kafka sukses, tapi commit DB gagal?
  • Kalau server mati di antara baris 1 dan 2?
Waktu: 2 menit. Tulis tebakanmu di chat.
bagian 1 · dual write

Jawaban: ada dua cara gagal

👻

Event hantu

Kafka sudah kirim “order dibuat”. Lalu commit DB gagal. Service lain memproses order yang tidak ada.

🕳️

Event hilang

DB sudah simpan order. Lalu Kafka gagal atau server mati. Service lain tidak pernah tahu ada order.

🔁

Retry tidak menyelamatkan

Kalau server mati, tidak ada yang ingat untuk retry. Ingatannya ikut hilang.

Dual write

menulis ke dua tempat yang tidak bisa di-commit bersama

Database dan Kafka tidak bisa ikut dalam satu transaksi yang sama.

bagian 2 · cara kerja

Ubah “kirim langsung” jadi “taruh di kotak”

✗ Sebelum: kirim langsung
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    kafka.send("order-created",   // <- di luar
               order.toEvent());  //    transaksi DB
}
✓ Sesudah: simpan ke outbox
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    outboxRepository.save(new OutboxEvent(
        "Order", order.getId(),
        "OrderCreated", toJson(order)));
}   // <- dua-duanya commit bareng
Tidak ada lagi “setengah berhasil”. Semua berhasil, atau semua batal.
bagian 2 · cara kerja

Isi tabel outbox: cukup sederhana

CREATE TABLE outbox (
  id            UUID PRIMARY KEY,
  aggregate     VARCHAR(50),  -- contoh: 'Order'
  aggregate_id  VARCHAR(50),  -- id order-nya
  type          VARCHAR(50),  -- 'OrderCreated'
  payload       JSONB,        -- isi event
  created_at    TIMESTAMP,
  sent_at       TIMESTAMP     -- null = belum dikirim
);

Gampangnya

  • id = nomor unik tiap surat.
  • payload = isi suratnya.
  • sent_at kosong = surat belum dikirim.
  • Satu baris = satu event.
Tabel ini tinggal di database yang sama dengan tabel orders.
bagian 2 · cara kerja

Siapa “pak pos”-nya? Ada dua pilihan

Relay = petugas yang membaca outbox lalu mengirim ke Kafka.

CaraGampangnyaKelebihanKekurangan
PollingCek tabel outbox tiap beberapa detikSimpel, cukup pakai @ScheduledAda jeda, beban query ke DB
CDC (Debezium)Baca “buku harian” database (log transaksi)Cepat, tidak membebani queryButuh setup tambahan (Kafka Connect)
Baru mulai? Pakai polling dulu. Sudah ramai? Pindah ke CDC.
bagian 2 · cara kerja

Contoh relay polling (versi simpel)

@Scheduled(fixedDelay = 1000)  // tiap 1 detik
public void publish() {
    var events = outboxRepository
        .findTop100BySentAtIsNullOrderByCreatedAt();
    for (var ev : events) {
        kafka.send(ev.getType(), ev.getPayload()).get();
        ev.markSent();                // isi sent_at
        outboxRepository.save(ev);
    }
}

Perhatikan

  • Ambil yang belum terkirim, urut dari yang lama.
  • Kirim dulu, baru tandai terkirim.
  • Kalau mati setelah kirim tapi sebelum tandai → nanti dikirim lagi.
Event pasti terkirim minimal sekali. Kadang dua kali.
bagian 3 · yang perlu dijaga

Penerima harus kebal terhadap event dobel

✗ Penerima polos
@KafkaListener(topics = "order-created")
public void on(OrderCreated ev) {
    emailService.sendConfirmation(ev);
    // event dobel = email dobel
}
✓ Penerima idempotent
@KafkaListener(topics = "order-created")
@Transactional
public void on(OrderCreated ev) {
    if (processed.exists(ev.eventId())) return;
    emailService.sendConfirmation(ev);
    processed.save(ev.eventId()); // ingat id
}
Idempotent = kayak tombol lift: ditekan 5 kali, lift tetap datang sekali.
bagian 3 · yang perlu dijaga

Jebakan yang sering kejadian

jebakan

Outbox di DB lain

Tabel outbox harus di DB yang sama. Kalau beda DB, balik lagi ke dual write.

jebakan

Tabel makin gendut

Hapus atau arsipkan baris yang sudah terkirim secara rutin.

jebakan

Urutan kacau

Kalau urutan penting, kirim pakai key = aggregate_id supaya masuk partisi yang sama.

jebakan

Lupa idempotent

Relay pasti pernah mengirim dobel. Penerima wajib siap.

ringkasan

Kapan pakai outbox, kapan tidak perlu

SituasiPakai outbox?
Simpan data + kirim event ke service lain✅ Ya, ini kasus utamanya
Event penting: pembayaran, order, stok✅ Ya, tidak boleh hilang
Satu aplikasi, tidak ada service lain❌ Tidak perlu
Event cuma log/analitik, hilang sedikit tidak apa-apa❌ Boleh kirim langsung
Teman dekatnya: Saga, Event Driven, dan CQRS.

Empat hal untuk diingat

❯ masalah

Simpan ke DB + kirim event itu dua pekerjaan. Bisa gagal salah satu.

❯ solusi

Simpan event ke tabel outbox di transaksi yang sama dengan datanya.

❯ relay

Petugas terpisah mengirim isi outbox. Mulai pakai polling.

❯ idempotent

Event bisa datang dua kali. Penerima harus kebal dobel.
