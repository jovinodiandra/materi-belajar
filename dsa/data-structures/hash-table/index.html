// Data Structures & Algorithms — struktur key-value dengan akses rata-rata O(1)

Cari data secepat menebak, bukan menyisir satu per satu.

Array cuma paham index angka: arr[0], arr[1]. Tapi di dunia nyata kamu mau cari data pakai key apa saja — username, kode produk, kata dalam kalimat. Hash table menjembatani keduanya: sebuah hash function mengubah key jadi index array, sehingga insert/cari/hapus jadi rata-rata O(1). Deck ini bahas konsepnya, cara collision ditangani (chaining vs open addressing), load factor & resize otomatis, sampai kapan struktur ini paling pas dipakai.

Sakit
Array cuma index angka — cari by key harus scan satu-satu, O(n)
Ide
Hash function — ubah key jadi index array secara instan
Untung
Rata-rata O(1) — insert, cari, hapus secepat menebak alamat
Batas
Tidak terurut & bisa collision — worst-case O(n) kalau hash-nya jelek
Pakai
Lookup fleksibel by key — cache, dedup, hitung frekuensi, index DB

Akar masalah · Array cuma paham angka

Kamu mau cari by key, bukan by nomor urut

Array itu cepat kalau kamu sudah tahu index-nya — arr[7] langsung nyampe. Masalahnya, kebanyakan data dunia nyata tidak dicari pakai angka urut. Kamu mau cari user pakai username, produk pakai kode SKU, kata pakai kata itu sendiri. Kalau dipaksa pakai array biasa, satu-satunya cara adalah menyisir dari depan sampai ketemu — O(n), makin banyak data makin lambat.

◆ Analogi — lemari arsip dengan kode indeks

Bayangkan gudang arsip berisi ribuan map dokumen. Cara bodoh: buka map satu-satu dari rak pertama sampai ketemu nama yang dicari — lama sekali. Cara pintar: setiap nama dihitung lewat rumus tertentu jadi sebuah kode rak-laci-slot, lalu map itu ditaruh persis di slot hasil hitungan itu. Saat mau ambil, kamu hitung ulang rumus yang sama dari nama itu, langsung jalan ke slot yang tepat — tanpa menyisir satu map pun. Rumus penghitung kode itulah hash function; raknya adalah array di belakang layar.

Itulah gagasan hash table: gabungkan kecepatan akses array (by index) dengan fleksibilitas key (apa saja) — lewat satu fungsi penerjemah di tengahnya.

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya banyak data yang harus dicari lewat key (username, kode SKU, kata), bukan lewat nomor index, dan struktur yang tersedia cuma array/list biasa.

When — tiap kali ada pencarian, penyisipan, atau penghapusan, kode terpaksa menyisir elemen satu per satu dari awal sampai key-nya cocok.

Then — waktunya jadi O(n): 100 data masih terasa instan, tapi begitu datanya jutaan baris, tiap lookup makin lambat dan aplikasi mulai ngelag.

→ makanya kita pakai Hash Table — hash function menerjemahkan key langsung jadi index array, jadi cari/insert/hapus data rata-rata O(1) tanpa perlu menyisir satu-satu.

Konsep inti · Hash function

Hash function: penerjemah key jadi index

Hash function mengambil sebuah key (string, angka, objek apa saja) dan mengembalikan sebuah angka — biasanya lalu di-mod dengan kapasitas array untuk jadi index bucket. Key yang sama selalu menghasilkan index yang sama, sehingga get tinggal hitung ulang hash-nya, lompat langsung ke bucket itu.

“Hashing memungkinkan tabel dengan ukuran O(1) rata-rata untuk operasi dictionary — insert, search, delete — dengan asumsi hash function mendistribusikan key secara merata.”

— Thomas H. Cormen dkk., Introduction to Algorithms (CLRS)
hitung frekuensi kata pakai HashMapJava
import java.util.HashMap;
import java.util.Map;

public class WordFreq {
    public static void main(String[] args) {
        Map<String, Integer> freq = new HashMap<>();
        String[] words = { "apel", "jeruk", "apel", "apel", "jeruk" };

        for (String w : words) {
            // hash function ubah "w" jadi index bucket di belakang layar
            int count = freq.getOrDefault(w, 0);
            freq.put(w, count + 1);
        }

        if (freq.containsKey("apel")) {
            int total = freq.get("apel");   // O(1) rata-rata
            System.out.println("apel: " + total); // apel: 3
        }
    }
}

put, get, dan containsKey semuanya lewat jalur yang sama: hitung hash dari key, lompat ke bucket, selesai. Tidak ada loop menyisir seluruh isi map.

Konsep penting · Collision handling

Dua key beda, hash-nya bisa sama — lalu apa?

Array bucket-nya terbatas, sementara key bisa tak terhingga — cepat atau lambat dua key berbeda akan menghasilkan index yang sama. Ini collision, dan tidak bisa dihindari sepenuhnya. Ada dua strategi utama menanganinya.

chaining — tiap bucket simpan daftarJava
class Bucket<K, V> {
    LinkedList<Entry<K, V>> chain = new LinkedList<>();

    void put(K key, V value) {
        for (Entry<K, V> e : chain) {
            if (e.key.equals(key)) {
                e.value = value; return;
            }
        }
        chain.add(new Entry<>(key, value)); // collision? tinggal nambah di list
    }
}
open addressing — geser ke slot lainJava
V get(K key) {
    int idx = hash(key) % capacity;
    int tried = 0;

    while (table[idx] != null && tried < capacity) {
        if (table[idx].key.equals(key)) {
            return table[idx].value;
        }
        idx = (idx + 1) % capacity; // linear probing: geser ke slot berikut
        tried++;
    }
    return null;
}

Chaining: tiap bucket menyimpan sebuah list (atau tree) berisi semua entry yang nge-hash ke index sama. Open addressing: kalau slot sudah terisi, cari slot kosong berikutnya di dalam array itu sendiri (linear probing, atau varian lain seperti quadratic probing / double hashing) — tanpa struktur tambahan.

◆ Load factor & resize otomatis
Rumusload factor = jumlah entry ÷ kapasitas array
Ambangdi Java HashMap, default threshold = 0.75
Resizelampaui threshold → kapasitas digandakan, semua entry di-rehash

Makin penuh bucket (load factor tinggi), makin sering collision, makin dekat ke O(n). Karena itu hash table otomatis resize (biasanya x2) begitu kepenuhan — harganya: sekali-sekali ada operasi insert yang mahal karena harus menghitung ulang hash semua entry lama ke tabel baru.

◆ Praktik · Biar tidak jebak diri sendiri

Best practice pakai hash table di Java

Sebagian besar bug hash table bukan soal algoritmanya, tapi soal key yang dipakai. Beberapa kebiasaan yang menyelamatkan kamu dari bug aneh nan susah dilacak:

  1. Override equals() dan hashCode() BARENGAN. Kalau cuma override salah satu, dua objek yang "sama" bisa mendarat di bucket berbeda dan get() gagal menemukannya.
  2. Pilih initial capacity kalau kamu sudah tahu perkiraan ukuran datanya — new HashMap<>(1024) menghindari resize berkali-kali saat insert masif.
  3. Hindari mutable object sebagai key. Kalau field yang dipakai hashCode() berubah setelah objek jadi key, entry-nya jadi "hilang" — hash-nya sudah beda dari saat pertama dimasukkan.
  4. Pakai key yang immutable — String, Integer, record/enum, atau kelas custom yang semua field-nya final.
  5. Jangan andalkan urutan iterasi dari HashMap/HashSet — urutannya tidak dijamin. Kalau butuh urutan insersi, pakai LinkedHashMap.
  6. Sebar hash secara merata. Hash function yang buruk (mis. selalu balikin angka yang sama) membuat semua entry numpuk di satu bucket — hash table berubah jadi linked list, O(1) berubah jadi O(n).
◆ Jalur belajar · Bertahap

Tier belajar hash table

Jangan langsung lompat ke consistent hashing kalau put/get dasar saja belum lancar. Naik bertahap sesuai tier berikut.

Beginner

Operasi dasar

Kuasai API-nya dulu sebelum mikirin internal-nya.

  • put / get / containsKey di HashMap
  • getOrDefault untuk hindari null check manual
  • Hitung frekuensi kemunculan elemen (word count)
  • Cek keberadaan elemen pakai HashSet
Middle

Pola pemecahan masalah

Hash map sebagai alat bantu algoritma, bukan cuma tempat simpan.

  • Two-sum — simpan angka+index sambil scan sekali jalan
  • Deteksi duplikat dalam array/list
  • Group anagram / kelompokkan berdasarkan pola key
  • Sliding window pakai hash map sebagai penghitung
Advance

Desain & skala

Merancang hashing-nya sendiri, bukan cuma memakainya.

  • Desain hash function sendiri & ukur distribusinya
  • Trade-off chaining vs open addressing pada skala besar
  • Consistent hashing untuk sistem terdistribusi — lihat topik sharding & partitioning
◆ Harga · Tidak ada makan siang gratis

Hash table vs tree map: cepat vs terurut

Alternatif hash table yang sering dibanding-bandingkan adalah tree map (mis. TreeMap di Java, berbasis red-black tree). Keduanya struktur key-value, tapi trade-off-nya berlawanan.

// Hash table (HashMap)

  • get/put rata-rata O(1).
  • Urutan key tidak terjaga (acak).
  • Tidak bisa query range ("key antara A dan M").
  • Worst-case bisa O(n) kalau hash jelek.

// Tree map (TreeMap)

  • get/put O(log n) — sedikit lebih lambat.
  • Key selalu terurut saat di-iterasi.
  • Bisa query range & cari "terdekat" (floorKey, dst).
  • Worst-case tetap O(log n), lebih terjamin.
◆ Intinya

Pilih hash table kalau kamu cuma butuh lookup exact-match secepat mungkin dan tidak peduli urutan. Pilih tree map kalau kamu butuh data selalu terurut atau perlu query range. Tidak ada yang "lebih baik" secara mutlak — beda kebutuhan akses, beda struktur.

◆ Keputusan · Pakai atau jangan

Kapan pakai hash table, kapan tidak

Aturan praktisnya: kalau kamu cuma butuh "cari by key secepat mungkin" tanpa peduli urutan, hash table adalah default yang tepat.

// Pakai hash table saat…

  • Butuh lookup/insert/delete secepat mungkin by key.
  • Urutan data tidak penting.
  • Cek keberadaan elemen (dedup, set membership).
  • Cache in-memory (key → value).
  • Hitung frekuensi / kelompokkan data.

// Jangan, pilih struktur lain saat…

  • Butuh data selalu terurut → pakai tree map.
  • Butuh query range (antara X dan Y) → tree map.
  • Butuh cari elemen "terdekat"/"ke-berapa" → tree/array terurut.
  • Kunci gampang collision masif (data adversarial) tanpa mitigasi.
  • Memori sangat terbatas — bucket kosong tetap makan alokasi.
Studi kasus · Di dunia nyata

Hash table di balik layar sistem production

Hash table jarang "terlihat" langsung sebagai fitur — ia biasanya jadi fondasi diam-diam di balik sistem yang kamu pakai tiap hari.

“Hash index sederhana — key dipetakan ke offset di file — adalah salah satu struktur index database paling dasar: sangat cepat untuk exact-match lookup, tapi tidak bisa dipakai untuk range query karena hash tidak mempertahankan urutan.”

— berdasar Martin Kleppmann, Designing Data-Intensive Applications (Bab 3)
// database

Hash index

Kasus: mencari baris lewat exact-match key (mis. WHERE id = ?). Kenapa hash table: key → offset di file, lookup O(1) tanpa perlu menyisir. Batasnya: tidak bisa untuk range query — di situlah B-tree index unggul.

Pelajari indexing database →
// in-memory cache

Redis

Kasus: cache key-value super cepat di depan database. Kenapa hash table: struktur data fundamental Redis untuk tipe string/hash adalah hash table in-memory — itu sebabnya GET/SET nyaris instan.

// compiler

Symbol table

Kasus: compiler/interpreter perlu tahu tiap identifier (nama variabel, fungsi) sudah dideklarasikan di mana & tipenya apa. Kenapa hash table: lookup nama identifier saat parsing harus cepat — dilakukan ribuan kali per file.

◆ Benang merahnya

Ketiganya butuh exact-match lookup super cepat pada volume yang besar, dan tidak (atau jarang) butuh urutan/range. Begitu kebutuhan bergeser ke range query atau data harus terurut, sistem-sistem ini biasanya menambah struktur lain di sampingnya (mis. B-tree index) — bukan memaksakan hash table untuk semua.

⚙ Ekosistem · Alat yang dipakai

Tools & referensi hash table

Sebagai pemula di Java, cukup kenal tiga hal ini dulu — sisanya tinggal dipelajari saat butuh.

// key-value

HashMap

Implementasi hash table standar Java untuk pasangan key-value. Default: chaining (linked list, treeified jadi red-black tree kalau satu bucket terlalu penuh), initial capacity 16, load factor 0.75.

// membership

HashSet

Set berbasis hash table — sebenarnya wrapper tipis di atas HashMap (value-nya dummy). Dipakai untuk cek keberadaan & hilangkan duplikat dengan cepat.

// urutan insersi

LinkedHashMap

Sama seperti HashMap, tapi menjaga urutan insersi (atau urutan akses, jika diatur) saat di-iterasi — cocok untuk cache LRU sederhana.

// belajar visual

Visualizer hashing

Alat visualisasi interaktif (mis. VisuAlgo, USFCA Data Structure Visualizations) yang memperagakan langkah-langkah hashing, collision, dan resize secara animasi — bagus untuk membangun intuisi sebelum baca kode.

Penutup

Cepat itu ada harganya: urutan

Hash table memberimu kecepatan lookup rata-rata O(1) dengan menukar key jadi index lewat hash function. Ia bersinar untuk exact-match lookup masif, dan tersandung saat kamu butuh data terurut atau query range.

  • Hash function — mengubah key jadi index array secara instan.
  • Collision tak terhindarkan — ditangani chaining atau open addressing.
  • Load factor — makin penuh, makin sering collision, makin butuh resize.
  • equals() + hashCode() — override bareng, atau map-mu jadi tidak bisa diandalkan.
  • Rata-rata O(1), bukan terjamin — worst-case tetap bisa O(n).
  • Tidak terurut — butuh urutan/range? pakai tree map, bukan hash table.

Aturan emasnya

Tanya: "Apakah aku cuma butuh cari data ini persis lewat key-nya, secepat mungkin, tanpa peduli urutan?" Kalau ya, hash table adalah pilihan default yang benar. Kalau kamu butuh data terurut, cari "terdekat", atau query range — lanjut ke struktur pohon berikutnya.
