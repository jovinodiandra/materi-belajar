// Head First Design Patterns — diceritakan ulang, santai

Pattern itu nggak diciptakan. Ditemukan.

Orang lain udah kena masalah desain yang sama berkali-kali—dan nyaring jalan keluar yang paling tahan banting. Itulah design pattern: resep yang udah teruji, bukan trik pamer. Deck ini ngikutin cara buku Head First Design Patterns: mulai dari satu aplikasi bebek yang berantakan gara-gara inheritance, lihat gimana tiap pattern lahir dari rasa sakit yang nyata. Contoh ikonik bukunya dipakai apa adanya (SimUDuck, Starbuzz, Weather Station, Remote Control…). Bahasa santai, kode Java.

↓ SCROLL ATAU TEKAN →

◆ Buat apa ini? Kenapa pakai ini?

Given — tim nyelesain masalah desain yang sama berulang-ulang, tapi tiap kali pakai solusi ad-hoc yang beda-beda (kayak Joe langsung nambah fly() di superclass Duck).

When — kodebase makin gede, dan solusi ad-hoc itu makin susah dikomunikasikan & dipahami developer lain—tiap orang motong masalah yang sama dengan cara sendiri-sendiri.

Then — muncul inkonsistensi desain, duplikasi, dan bug yang susah dilacak (bebek karet tiba-tiba ikut terbang).

→ makanya kita pakai design pattern: kosakata & solusi desain yang udah teruji, dipahami bersama tim.

Studi kasus · SimUDuck

Awalnya rapi. Lalu bos minta bebeknya bisa terbang.

Joe kerja di perusahaan yang bikin game simulasi kolam bebek, SimUDuck. Desain awalnya OOP yang "benar": ada superclass Duck, lalu macam-macam bebek mewarisinya. Rapi, semua orang senang.

Duck.java — desain awal
public abstract class Duck {
    public void quack() { System.out.println("Quack"); }
    public void swim()  { /* semua bebek ngambang */ }
    public abstract void display();   // tiap jenis beda tampilan
}

public class MallardDuck extends Duck {
    @Override public void display() { /* gambar mallard */ }
}
BOS:

"Kompetitor bikin bebeknya terbang. Kita butuh bebek terbang juga—minggu depan rilis!"

Gampang, pikir Joe. Tinggal tambah fly() di superclass Duck, semua bebek otomatis bisa terbang. Dia commit, pulang. Besoknya... rapat ribut.

Duck.java — "tinggal tambah fly()"BENCANA
public abstract class Duck {
    public void quack() { ... }
    public void fly()   { System.out.println("Terbang!"); }  // ditaruh di induk
}

public class RubberDuck extends Duck {
    @Override public void quack() { System.out.println("Squeak"); }
    // ...tapi RubberDuck sekarang IKUT terbang. Bebek karet terbang?! 🐤💥
}

Bebek karet melayang-layang di layar. Satu perubahan di superclass nyebar ke semua subclass—termasuk yang nggak seharusnya. Dan bentar lagi ada DecoyDuck (bebek umpan dari kayu): nggak bisa terbang, nggak bisa bersuara. Inheritance mulai berasa salah.

Studi kasus · SimUDuck

Interface? Malah lebih parah.

Joe mikir: "Oke, override fly() di RubberDuck biar nggak ngapa-ngapain." Tapi tiap ada bebek baru yang aneh, dia harus inget override lagi. Lupa sekali = bug. Lalu dia coba ide kedua: interface Flyable dan Quackable.

pakai interface — duplikasi di mana-manaSMELL
interface Flyable   { void fly(); }
interface Quackable { void quack(); }

class MallardDuck extends Duck implements Flyable, Quackable {
    public void fly()   { /* kode terbang ditulis ULANG */ }
    public void quack() { /* kode quack ditulis ULANG */ }
}
// 48 subclass bebek? tulis ulang fly() di tiap yang terbang.
// mau ubah cara terbang? edit 48 file. interface = nol reuse kode.

Interface ngilangin masalah "bebek karet terbang" (cuma yang perlu yang implement), tapi ngebunuh reuse kode: tiap bebek nulis ulang fly() sendiri. Mau ganti perilaku terbang buat semua? Sentuh puluhan file. Joe stuck di antara dua jalan jelek.

Di sinilah pelajaran pertama Head First. Lihat apa yang sebenarnya jadi sumber masalah: perilaku yang berubah-ubah (cara terbang, cara bersuara) ditempel ke hierarki yang kaku.

◆ Design Principle

Kenali bagian aplikasi yang berubah-ubah, lalu pisahkan dari yang tetap.
— Encapsulate what varies.

Artinya: cabut fly() dan quack() keluar dari Duck. Jadikan mereka keluarga perilaku yang berdiri sendiri. Itu langsung nuntun kita ke pattern pertama.

Pattern 01 · Strategy · "family of algorithms"

Strategy — perilaku jadi komponen yang bisa dicolok

Cabut yang berubah-ubah. fly() jadi keluarga FlyBehavior; quack() jadi keluarga QuackBehavior. Tiap varian = satu class kecil. Lalu Duck punya (HAS-A) sebuah perilaku, bukan mewarisinya.

FlyBehavior.java — keluarga algoritmaCLEAN
public interface FlyBehavior { void fly(); }

public class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("Terbang pakai sayap"); }
}
public class FlyNoWay implements FlyBehavior {
    public void fly() { /* diam — nggak bisa terbang */ }
}
// QuackBehavior: Quack, Squeak, MuteQuack — pola yang sama.
Duck.java — komposisi, bukan warisanCLEAN
public abstract class Duck {
    protected FlyBehavior flyBehavior;        // HAS-A, bukan IS-A
    protected QuackBehavior quackBehavior;

    public void performFly() { flyBehavior.fly(); }   // delegasi
    public void setFlyBehavior(FlyBehavior fb) { flyBehavior = fb; }  // ganti saat runtime!
}

public class RubberDuck extends Duck {
    public RubberDuck() {
        flyBehavior   = new FlyNoWay();   // karet: nggak terbang
        quackBehavior = new Squeak();     // karet: nyicit
    }
}

Bebek baru? Rakit dari perilaku yang udah ada. Cara terbang baru (mis. FlyWithRocket)? Bikin satu class, colok ke bebek mana pun—bahkan duck.setFlyBehavior(new FlyWithRocket()) di tengah jalan. Nol file lama disentuh.

◆ Design Principle

Program ke interface, bukan ke implementasi. Dan: favor composition over inheritance.

Definisi · Strategy Pattern

Mendefinisikan sekeluarga algoritma, membungkus tiap satunya, dan membuatnya bisa ditukar-tukar. Strategy bikin algoritma berubah independen dari klien yang memakainya.

◆ Nyambung ke deck OOP kita

Inilah payoff dari pilar "composition > inheritance" di deck OOP. Notifikasi yang "meledak jadi subclass" di sana, dan SimUDuck di sini, masalahnya sama—dan Strategy adalah obat resminya.

Pattern 02 · Observer · "one-to-many"

Observer — satu sumber data, banyak yang ikut update

Studi kasus baru: Weather Station. Ada objek WeatherData yang nyimpen tiga pengukuran—suhu, kelembapan, tekanan. Tiap kali stasiun cuaca baca data baru, ada banyak display yang harus ikut berubah: CurrentConditionsDisplay, StatisticsDisplay, ForecastDisplay. Pertanyaannya: gimana cara WeatherData ngasih tahu mereka semua?

SPEC:

"Begitu pengukuran berubah, semua display di-update otomatis. Dan ke depan kita mau bisa nambah display baru kapan aja—tanpa nyentuh kode lama."

Cara naif: di method measurementsChanged(), panggil tiap display satu-satu. Kelihatan jalan. Tapi lihat baik-baik.

WeatherData.java — panggil display hardcodedSMELL
public class WeatherData {
    public void measurementsChanged() {
        float t = getTemperature();
        float h = getHumidity();
        float p = getPressure();
        currentDisplay.update(t, h, p);   // nama konkret dipanggil langsung
        statsDisplay.update(t, h, p);     // nambah display = edit method ini
        forecastDisplay.update(t, h, p);  // kode jadi area yang berubah terus
    }
}

Tiap display di-panggil pakai nama konkretnya. Mau nambah HeatIndexDisplay? Buka WeatherData, tambah baris. Mau cabut satu display saat runtime? Nggak bisa. WeatherData jadi kenal semua display secara detail—coupling-nya ketat, dan bagian yang harusnya stabil malah ikut berubah tiap ada display baru.

Polanya udah kebaca: ini hubungan satu-ke-banyak. Satu subject (sumber data) ke banyak observer (yang nyimak). Bikin aja kontraknya eksplisit lewat dua interface.

Subject.java & Observer.java — kontrakCLEAN
public interface Subject {
    void registerObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

public interface Observer {
    void update(float temp, float humidity, float pressure);
}
WeatherData.java — implements SubjectCLEAN
public class WeatherData implements Subject {
    private List<Observer> observers = new ArrayList<Observer>();
    private float temperature, humidity, pressure;

    public void registerObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o)   { observers.remove(o); }

    public void notifyObservers() {
        for (Observer o : observers) {        // nggak kenal tipe konkretnya
            o.update(temperature, humidity, pressure);
        }
    }

    public void measurementsChanged() { notifyObservers(); }  // itu aja
}
CurrentConditionsDisplay.java — sebuah ObserverCLEAN
public class CurrentConditionsDisplay implements Observer {
    private Subject weatherData;
    private float temperature, humidity;

    public CurrentConditionsDisplay(Subject weatherData) {
        this.weatherData = weatherData;
        weatherData.registerObserver(this);   // daftar sendiri ke subject
    }

    public void update(float t, float h, float p) {
        this.temperature = t;
        this.humidity = h;
        display();
    }
    public void display() { /* tampilkan suhu & kelembapan terkini */ }
}
// StatisticsDisplay & ForecastDisplay: pola yang sama persis.

Sekarang nambah display baru = bikin satu class yang implements Observer lalu register ke subject. WeatherData nggak disentuh sama sekali—dia cuma kenal interface Observer, bukan nama-nama display. Mau berhenti nyimak? Panggil removeObserver(this), bahkan saat runtime.

◆ Design Principle

Usahakan desain yang longgar kopling-nya antar objek yang berinteraksi.
— Strive for loosely coupled designs between objects that interact.

Definisi · Observer Pattern

Mendefinisikan ketergantungan satu-ke-banyak antar objek: saat satu objek (subject) berubah state, semua tanggungannya (observers) diberi tahu dan di-update otomatis.

◆ Jangan pakai java.util.Observable

JDK punya java.util.Observable (class) dan Observer, tapi keduanya deprecated sejak Java 9—lagipula Observable itu class, jadi maksa kamu extends dan ngunci satu slot inheritance. Bikin interface Subject & Observer sendiri seperti di atas: lebih fleksibel dan tetap longgar kopling-nya.

Pattern 03 · Decorator · "attach responsibilities dynamically"

Starbuzz Coffee — menu yang meledak jadi ratusan class

Starbuzz tumbuh kilat. Mereka butuh sistem pemesanan. Desain awalnya gampang: satu abstract Beverage punya cost(), lalu tiap jenis kopi mewarisinya—HouseBlend, DarkRoast, Espresso. Sampai sini aman.

Beverage.java — desain awal
public abstract class Beverage {
    protected String description = "Minuman tak dikenal";

    public String getDescription() { return description; }
    public abstract double cost();   // tiap kopi hitung sendiri
}

public class DarkRoast extends Beverage {
    public DarkRoast() { description = "Dark Roast"; }
    public double cost() { return 0.99; }
}
BOS:

"Pelanggan bisa nambah condiment: Steamed Milk, Mocha, Soy, Whip. Tiap tambahan nambah harga. Sistemnya harus ngitung total otomatis."

Joe mikir cepat: bikin subclass buat tiap kombinasi. Kan tinggal extend? Sebentar kemudian papan tulis penuh.

ledakan subclass — satu class per kombinasiBENCANA
class DarkRoastWithMocha            extends Beverage { ... }
class DarkRoastWithMochaWhip        extends Beverage { ... }
class DarkRoastWithSoyMocha         extends Beverage { ... }
class HouseBlendWithSteamedMilkMocha extends Beverage { ... }
// ...3 kopi x tiap kombinasi condiment = puluhan class.
// mau Mocha dobel? class baru lagi. mimpi buruk maintenance.

Tiap condiment baru = kombinasi baru meledak berlipat. Joe nyerah, coba jalan kedua: taruh semua condiment sebagai boolean di superclass Beverage, lalu cost() jumlahin yang aktif. Kelihatan lebih ramping... di awal.

Beverage.java — boolean di superclassSMELL
public abstract class Beverage {
    private boolean milk, soy, mocha, whip;   // flag tiap condiment

    public boolean hasMocha() { return mocha; }
    public void setMocha(boolean m) { mocha = m; }
    // ...getter/setter serupa buat milk, soy, whip

    public double cost() {           // dihitung di induk
        double c = 0.0;
        if (hasMilk())  c += 0.10;
        if (hasSoy())   c += 0.15;
        if (hasMocha()) c += 0.20;
        if (hasWhip())  c += 0.10;
        return c;          // subclass nambah harga kopi dasar
    }
}

Lihat yang busuk di sini. Condiment baru (Caramel?) = edit superclass: tambah field, tambah getter/setter, tambah satu if lagi di cost(). Naik harga Soy? Edit superclass—padahal class itu udah jalan dan dipakai semua minuman. Mau dobel Mocha? boolean nggak bisa, ribet lagi. Dan tiap minuman mewarisi flag yang nggak relevan (teh ikut bawa whip).

Subclass tiap kombinasi

  • Jumlah class meledak eksponensial
  • Kombinasi baru = class baru terus
  • Dobel condiment? mustahil rapi

Boolean di superclass

  • Condiment baru = bedah superclass
  • Ubah harga = sentuh kode lama yang udah jalan
  • Minuman bawa flag yang nggak relevan
◆ Design Principle

Class harus terbuka untuk ekstensi, tapi tertutup untuk modifikasi.
— Open-Closed Principle.

◆ Akar masalahnya

Dua-duanya gagal di prinsip yang sama: nambah perilaku (condiment) memaksa ngutak-atik kode lama—entah bikin subclass turunan baru, entah membedah Beverage. Tiap edit ke kode yang udah jalan = risiko bug baru.

Yang kita mau: bisa nambah perilaku ke cost() sebuah objek tanpa nyentuh class Beverage atau kopi-kopinya. Caranya? Jangan mewarisi condiment-nya—bungkus objek minumannya. Ambil DarkRoast, balut Mocha, balut Whip; tiap pembungkus nambah harganya sendiri. Itu Decorator—dan kita rakit pelan-pelan di slide berikutnya.

Pattern 03 · Decorator · "attach responsibilities dynamically"

Decorator — bungkus objek lapis demi lapis, biar tambahannya nempel saat runtime

Ingat ledakan subclass kopi tadi? HouseBlendWithSteamedMilkAndMocha dan teman-temannya yang nggak ada habisnya itu? Idenya sekarang dibalik: jangan bikin satu class buat tiap kombinasi. Mulai dari minuman polos, lalu bungkus dia pakai topping. Tiap topping adalah objek yang membungkus minuman di dalamnya.

Kuncinya: si topping itu sendiri juga sebuah Beverage (IS-A, biar bisa dipasang di tempat yang sama), dan dia menyimpan Beverage yang dibungkusnya (HAS-A, biar bisa nimpalin biaya & deskripsi). Dua hubungan itu sekaligus—itulah inti Decorator.

CondimentDecorator.java — induk semua toppingCLEAN
public abstract class Beverage {
    protected String description = "Minuman tak dikenal";
    public String getDescription() { return description; }
    public abstract double cost();
}

// Topping IS-A Beverage -> bisa dipasang di slot Beverage mana pun.
public abstract class CondimentDecorator extends Beverage {
    @Override public abstract String getDescription();
}
Mocha.java — topping yang membungkus minumanCLEAN
public class Mocha extends CondimentDecorator {
    private Beverage beverage;        // HAS-A: yang dibungkus

    public Mocha(Beverage beverage) {
        this.beverage = beverage;
    }

    @Override public String getDescription() {
        return beverage.getDescription() + ", Mocha";
    }

    @Override public double cost() {
        return beverage.cost() + 0.20;   // biaya minuman + biaya mocha
    }
}
// Whip & SoyMilk: pola yang sama, beda angka & label.

Lihat cost()-nya: dia nggak ngitung sendirian. Dia tanya dulu ke objek di dalamnya (beverage.cost()), baru nambahin jatahnya. Begitu juga getDescription()—nyambung ke deskripsi dalam, lalu nempelin ", Mocha". Bungkus berlapis = panggilan yang ngalir ke dalam, lalu numpuk balik ke luar.

StarbuzzCoffee.java — racik pesanannyaCLEAN
Beverage b = new DarkRoast();          // minuman polos, $0.99
b = new Mocha(b);                       // bungkus mocha, +$0.20
b = new Whip(b);                        // bungkus whip,  +$0.10

System.out.println(b.getDescription());
// -> "Dark Roast, Mocha, Whip"
System.out.println(b.cost());           // -> 1.29

// b.cost() = Whip(0.10) + Mocha(0.20) + DarkRoast(0.99)

Mau mocha dobel? b = new Mocha(new Mocha(b))—tumpuk aja. Tambah topping baru (mis. Caramel)? Bikin satu class decorator, nol class lama disentuh. Inilah yang dijanjiin Open-Closed tadi: terbuka buat perluasan, tertutup buat perubahan.

◆ Design Principle

Class harus terbuka untuk diperluas, tapi tertutup untuk dimodifikasi.
— Open-Closed Principle.

Definisi · Decorator Pattern

Decorator melekatkan tanggung jawab tambahan ke sebuah objek secara dinamis (saat runtime). Decorator memberi alternatif yang fleksibel untuk subclassing demi memperluas fungsionalitas.

◆ Kamu udah sering pakai ini

Buka java.io—seluruhnya Decorator. new BufferedInputStream(new FileInputStream(f)): BufferedInputStream membungkus FileInputStream dan nambahin buffering, tanpa FileInputStream tahu apa-apa. Persis Mocha membungkus DarkRoast. JDK udah pakai pattern ini dari dulu.

Pattern 04 · Factory · "instansiasi diserahkan"

Factory — keputusan "class mana yang di-new" itu pindahin

Kita bikin PizzaStore. Pesanan masuk, kita pilih jenis pizza, panggang, potong, kotakin. Awalnya cuma sebaris dua baris. Lalu menu nambah terus—dan tiap kali menu berubah, kamu balik ngedit method yang sama.

PizzaStore.java — orderPizza() ngurusin semuaBENCANA
public class PizzaStore {
    public Pizza orderPizza(String type) {
        Pizza pizza;
        if (type.equals("cheese"))      pizza = new CheesePizza();
        else if (type.equals("pepperoni")) pizza = new PepperoniPizza();
        else if (type.equals("clam"))      pizza = new ClamPizza();
        else                            pizza = new VeggiePizza();

        pizza.prepare();   pizza.bake();
        pizza.cut();       pizza.box();
        return pizza;
    }
}

Bagian prepare/bake/cut/box itu nggak pernah berubah—itu yang bikin "pizza ya pizza". Yang berubah-ubah cuma blok if-nya: menu hapus VeggiePizza, tambah GreekPizza, kamu wajib bedah orderPizza() lagi. Method ini juga nempel ke semua class konkret—tiap new bikin dia kenal nama class spesifik.

◆ Design Principle

Pisahkan bagian yang berubah dari yang tetap. Di sini: instansiasi yang berubah, ritual prepare/bake/cut/box yang tetap.

Langkah 1 — Simple Factory. Cabut blok if itu, taruh di satu objek yang kerjanya cuma bikin pizza: SimplePizzaFactory. orderPizza() tinggal nanya ke factory.

SimplePizzaFactory.java — new dikumpulin di satu tempatSMELL
public class SimplePizzaFactory {
    public Pizza createPizza(String type) {
        if (type.equals("cheese"))      return new CheesePizza();
        else if (type.equals("pepperoni")) return new PepperoniPizza();
        else if (type.equals("clam"))      return new ClamPizza();
        else                            return new VeggiePizza();
    }
}

// orderPizza() sekarang cuma minta, nggak tahu cara bikinnya:
//   pizza = factory.createPizza(type);

Lumayan—sekarang kode "new" cuma di satu tempat, dipakai bareng PizzaMenu, HomeDelivery, dll. Tapi ini belum pattern beneran, baru idiom rapi. Masalah baru muncul pas bisnis sukses: tiap kota minta gaya pizza sendiri—New York tipis, Chicago tebal—dan tiap toko punya cara cut/box beda.

Pattern 04 · Factory ·2 · "subclass yang mutusin"

Factory Method — instansiasi diturunkan ke subclass

FRANCHISE:

"Aku mau buka cabang. Tapi pizza-ku harus gaya New York—dan jangan ganggu ritual proses standar perusahaan ya."

Langkah 2 — Factory Method. Daripada nyolok factory dari luar, jadikan PizzaStore itu abstract dengan satu factory method: abstract Pizza createPizza(type). orderPizza() tetap di superclass, panggil createPizza()—tapi subclass yang mutusin class mana yang di-new.

PizzaStore.java — orderPizza final, createPizza diserahkanCLEAN
public abstract class PizzaStore {
    // ritual tetap, sama buat SEMUA cabang — nggak boleh diubah
    public final Pizza orderPizza(String type) {
        Pizza pizza = createPizza(type);   // ← factory method
        pizza.prepare();   pizza.bake();
        pizza.cut();       pizza.box();
        return pizza;
    }

    // subclass yang mutusin class konkret mana yang lahir:
    protected abstract Pizza createPizza(String type);
}
Cabang per-region — tiap toko bikin pizza ala-nyaCLEAN
public class NYPizzaStore extends PizzaStore {
    @Override protected Pizza createPizza(String type) {
        if (type.equals("cheese")) return new NYStyleCheesePizza();
        else                          return new NYStyleClamPizza();
    }
}

public class ChicagoPizzaStore extends PizzaStore {
    @Override protected Pizza createPizza(String type) {
        if (type.equals("cheese")) return new ChicagoStyleCheesePizza();
        else                          return new ChicagoStyleClamPizza();
    }
}

// Pesan: PizzaStore ny = new NYPizzaStore(); ny.orderPizza("cheese");

Lihat pembagian kerjanya: superclass nulis apa yang terjadi ke setiap pizza (proses), subclass nulis pizza mana yang dibuat (produk). orderPizza() ngolah objek Pizza abstrak—dia nggak pernah tahu dapet NY atau Chicago. Buka cabang baru = bikin satu subclass, nol baris lama disentuh.

Sebelum — orderPizza() nge-new sendiri

  • Kenal tiap class konkret (new CheesePizza())
  • Menu berubah = bedah orderPizza()
  • Tambah region = if-else makin gendut
  • Proses & instansiasi nyampur jadi satu

Sesudah — createPizza() diserahkan ke subclass

  • Cuma kenal abstraksi Pizza
  • Ritual orderPizza() dikunci sekali (final)
  • Region baru = subclass baru, kode lama aman
  • Keputusan "apa" vs "mana" terpisah bersih
◆ Design Principle

Depend upon abstractions. Do not depend upon concrete classes.
— Dependency Inversion: PizzaStore sandar ke Pizza, bukan ke NYStyleCheesePizza.

Definisi · Factory Method Pattern

Mendefinisikan sebuah interface untuk membuat objek, tapi membiarkan subclass yang memutuskan class mana yang diinstansiasi. Factory Method membuat sebuah class menunda (defer) instansiasi ke subclass-nya.

◆ Jangan ketuker

Simple Factory itu cuma idiom, bukan pattern GoF—objek terpisah yang nge-new buat orang lain. Factory Method baru jadi pattern: instansiasi-nya jadi abstract dan diturunkan lewat inheritance ke subclass. Beda alat, beda kapan dipakai.

Pattern 05 · Singleton · "satu instance"

Singleton — cuma boleh ada satu, titik.

Ada barang yang emang harus tunggal: satu connection pool, satu registry, satu ChocolateBoiler di pabrik cokelat. Kalau sampai ada dua objek boiler yang ngira mereka masing-masing kosong, dua-duanya isi cokelat panas barengan—dan pabrikmu meledak. Jadi gimana caranya satu class dijamin cuma punya satu instance?

JOE:

"Gampang, bikin variabel global aja: public static ChocolateBoiler boiler. Kelar."

Masalahnya, kalau objeknya mahal dibikin dan kamu langsung instansiasi di awal, kamu bayar ongkos itu walaupun nggak kepakai. Dan global variable nggak benar-benar mencegah orang bikin instance kedua pakai new. Trik klasiknya: kunci constructor-nya, dan biar class itu sendiri yang ngurus instance-nya.

ChocolateBoiler.java — pola Singleton klasikCLEAN
public class ChocolateBoiler {
    private static ChocolateBoiler instance;   // satu-satunya slot

    private ChocolateBoiler() { /* constructor DIKUNCI */ }

    public static ChocolateBoiler getInstance() {
        if (instance == null) {          // lazy: bikin saat pertama dipakai
            instance = new ChocolateBoiler();
        }
        return instance;
    }

    public void fill()  { /* isi kalau lagi kosong */ }
    public void boil()  { /* didihkan campuran */ }
    public void drain() { /* tiriskan cokelat matang */ }
}

Constructor private bikin new ChocolateBoiler() dari luar nggak bisa dikompilasi. Satu-satunya pintu masuk adalah getInstance()—dan dia cuma bikin objek sekali, sisanya ngembaliin yang itu-itu lagi. Selesai? Belum. Begitu ada dua thread, polanya bocor.

BOS:

"Pabrik kita jalan multi-thread sekarang. Kenapa kemaren ada DUA boiler kedeteksi barengan?!"

getInstance() — race conditionBENCANA
public static ChocolateBoiler getInstance() {
    if (instance == null) {        // Thread A & B sama-sama lolos...
        instance = new ChocolateBoiler();  // ...lalu dua-dua new(). DUA!
    }
    return instance;
}

Thread A masuk, lihat instance == null, tapi keburu di-pause sebelum sempat assign. Thread B masuk, juga lihat null, lalu bikin boiler. A bangun, bikin boiler lagi. Dua instance. Cara paling lugas nutupnya: bikin getInstance() jadi synchronized.

tiga cara aman threadCLEAN
// 1) synchronized — paling simpel, tapi tiap panggil kena kunci
public static synchronized ChocolateBoiler getInstance() {
    if (instance == null) instance = new ChocolateBoiler();
    return instance;
}

// 2) eager init — kalau ongkos bikin nggak masalah; JVM jamin sekali
private static final ChocolateBoiler INSTANCE = new ChocolateBoiler();
public static ChocolateBoiler getInstance() { return INSTANCE; }

// 3) double-checked locking — volatile + kunci cuma saat pertama
private static volatile ChocolateBoiler instance;
public static ChocolateBoiler getInstance() {
    if (instance == null) {
        synchronized (ChocolateBoiler.class) {
            if (instance == null) instance = new ChocolateBoiler();
        }
    }
    return instance;
}

Pilihannya tergantung kebutuhan. synchronized gampang tapi tiap panggil bayar ongkos kunci—oke kalau jarang dipanggil. Eager init paling bersih kalau objeknya pasti dipakai dan nggak mahal. Double-checked locking ngunci cuma sekali pas inisialisasi; volatile wajib, biar half-built object nggak kelihatan dari thread lain.

Definisi · Singleton Pattern

Memastikan sebuah class cuma punya satu instance, dan menyediakan satu titik akses global ke instance itu.

◆ Jujur dulu: Singleton itu kontroversial

Singleton pada dasarnya global state berbaju OOP. Class yang diam-diam manggil getInstance() di dalamnya punya dependency tersembunyi—nggak kelihatan di constructor, susah di-mock, bikin test saling bocor lewat state yang sama. Gampang banget disalahgunakan jadi tempat naruh "barang global" sembarangan. Seringnya jawaban yang lebih sehat adalah inject dependency-nya (kasih lewat constructor) dan biar satu objek itu dirakit sekali di composition root—bukan dipaksa tunggal oleh class-nya sendiri. Pakai Singleton kalau emang ada batasan fisik "harus satu" (boiler, device driver), bukan cuma karena males ngoper objek.

Kalau dipaksa Singleton sembarangan

  • Dependency tersembunyi, nggak kebaca dari signature
  • Test bocor satu sama lain lewat state global
  • Susah di-mock / di-swap buat skenario beda
  • Coupling diam-diam ke seluruh codebase

Kalau di-inject sebagai dependency

  • Kebutuhan jelas dari constructor
  • Tinggal kasih fake/mock saat test
  • Tunggal-nya diatur di satu tempat rakit
  • Coupling eksplisit dan bisa dibalik arahnya

VENDOR:

"Tiap slot harus bisa di-set ke device apa pun. Kami nggak tahu device apa yang bakal kamu colok—dan kami nggak mau remote-nya tahu juga."

Masalahnya: tiap device API-nya beda total. Light punya on()/off(). Stereo punya on(), setCD(), setVolume(). GarageDoor punya up()/down(). Kalau remote-nya yang harus mikir "slot ini device apa, manggil method apa", jadinya begini:

Definisi · Command Pattern

Membungkus sebuah permintaan sebagai objek, sehingga kamu bisa memparameterkan objek lain dengan permintaan yang berbeda-beda, memisahkan objek yang memanggil (invoker) dari objek yang tahu cara melakukannya (receiver).

◆ Lanjut di slide berikut

Slot remote belum kita isi. Di Command ·2 kita pasang Command[] ke remote (si invoker): tiap tombol nyimpen satu command lalu manggil execute(). Plus bonus yang gampang banget begitu permintaan jadi objek—tombol undo.

Pattern 06 · Command · "encapsulate a request"

Remote Control — satu invoker, tujuh slot, dan tombol undo

Di bagian sebelumnya kita udah bungkus tiap permintaan jadi objek Command. Sekarang kita rakit invoker-nya: sebuah remote control dengan tujuh slot ON/OFF. Tiap slot nyimpen satu Command. Pencet tombol, remote tinggal panggil execute()—dia nggak peduli yang dieksekusi itu lampu, kipas, atau pintu garasi.

RemoteControl.java — sang INVOKERCLEAN
public class RemoteControl {
    Command[] onCommands;            // satu per slot
    Command[] offCommands;

    public RemoteControl() {
        onCommands  = new Command[7];
        offCommands = new Command[7];
        Command noCommand = new NoCommand();   // null object
        for (int i = 0; i < 7; i++) {
            onCommands[i]  = noCommand;          // slot kosong = aman
            offCommands[i] = noCommand;
        }
    }

    public void setCommand(int slot, Command on, Command off) {
        onCommands[slot]  = on;
        offCommands[slot] = off;
    }

    public void onButtonWasPushed(int slot) {
        onCommands[slot].execute();         // itu aja. nggak tahu apa-apa.
    }
}

Perhatiin RemoteControl nggak pernah nyebut Light, CeilingFan, atau receiver apa pun. Dia cuma kenal Command. Mau colok perintah baru? Panggil setCommand(slot, on, off)—remote-nya nggak perlu di-edit sama sekali. Itu yang bikin invoker dan receiver terlepas total.

◆ Invoker buta soal receiver

Remote (invoker) nggak tahu lampu (receiver) itu apa, gimana cara nyalainnya, atau bahkan kalau nanti dia diganti jadi mesin kopi. Semua detail itu kebungkus di dalam objek Command. Invoker cuma kenal satu kata kerja: execute(). Decoupled.

Tadi sempet ngeganjel: slot yang belum di-set itu gimana? Kalau dibiarin null, pencet tombolnya langsung NullPointerException. Daripada nyebar cek if (cmd != null) di mana-mana, kita pasang NoCommand—sebuah Command yang sengaja nggak ngapa-ngapain. Ini namanya pola null object.

NoCommand.java — null objectCLEAN

    public void execute() { /* sengaja diam */ }
    public void undo()    { /* sengaja diam */ }
}

Sekarang bos balik lagi—pasti dong.

BOS:

"Bagus. Tambahin satu tombol undo di remote. Kalau aku nyalain lampu terus nyesel, sekali pencet harus balik mati. Berlaku buat semua tombol."

Karena tiap perintah udah jadi objek, undo gampang banget. Kita tambah satu method undo() di interface Command—kebalikan dari execute(). LightOnCommand.undo() ya tinggal matiin lampu. Remote cukup nyimpen perintah terakhir yang dijalanin.

}

RemoteControl — ingat perintah terakhirCLEAN
public class RemoteControl {

    Command[] offCommands;

◆ Design Principle

Bungkus permintaan jadi objek, dan invoker cukup tahu satu hal: cara memanggil execute().
— Encapsulate the request.

Definisi · Command Pattern

Command mengenkapsulasi sebuah permintaan sebagai objek, sehingga kamu bisa memparameterkan klien dengan permintaan yang berbeda, mengantre atau mencatat (log) permintaan, dan mendukung operasi undo.

Pattern 07 · Adapter · "ubah satu interface jadi interface lain"

Adapter — colokan beda, tinggal kasih sambungan

Kamu punya kode klien yang ngerti Duck. Tapi sekarang stok bebekmu habis, yang ada cuma kalkun. Kalkun punya interface beda: dia gobble(), bukan quack(). Mau ngubah klien? Banyak yang harus disentuh. Mau ngubah Turkey? Itu kode pihak ketiga. Jalan tengahnya: bikin adapter.

KAMU:

"Klienku cuma mau ngomong sama Duck. Tapi yang tersedia Turkey. Aku nggak boleh ubah dua-duanya. Gimana?"

Duck.java & Turkey.java — dua colokan beda
public interface Duck {
    void quack();
    void fly();
}

public interface Turkey {
    void gobble();          // kalkun "gobble", bukan "quack"
    void fly();             // kalkun terbang, tapi cuma pendek
}

public class WildTurkey implements Turkey {
    public void gobble() { System.out.println("Gobble gobble"); }
    public void fly()    { System.out.println("Terbang pendek"); }
}

Klien manggil duck.quack() dan duck.fly(). Kalkun nggak punya quack(), dan terbangnya cuma sebentar. Adapter berdiri di tengah: di luar dia kelihatan kayak Duck, di dalam dia punya (HAS-A) sebuah Turkey dan nerusin tiap panggilan ke method kalkun yang cocok.

TurkeyAdapter.java — object adapter (komposisi)CLEAN
public class TurkeyAdapter implements Duck {   // di luar: Duck
    private Turkey turkey;                          // di dalam: HAS-A Turkey

    public TurkeyAdapter(Turkey turkey) {
        this.turkey = turkey;
    }

    public void quack() {
        turkey.gobble();              // quack() di-terjemah ke gobble()
    }

    public void fly() {
        for (int i = 0; i < 5; i++) {   // kalkun terbang pendek,
            turkey.fly();             // jadi diulang 5x biar setara
        }
    }
}

Klien nggak sadar apa-apa. Dia pegang Duck, manggil quack() — di belakang layar yang bunyi malah gobble. Dia manggil fly() — adapter ngelooping terbang kalkun 5x biar jaraknya kira-kira sebanding sama bebek. Nol perubahan di sisi klien, nol perubahan di WildTurkey.

DuckTestDrive.java — klien tetap ngomong Duck

Duck turkeyAdapter = new TurkeyAdapter(gobbler);

// klien nggak tahu ini kalkun — dia cuma lihat Duck
turkeyAdapter.quack();   // → "Gobble gobble"
turkeyAdapter.fly();     // → "Terbang pendek" ×5
◆ Design Principle

Bungkus objek yang interfacenya beda, biar klien tetap ngomong pakai bahasa yang dia kenal.
— Wrap, jangan ubah.

Definisi · Adapter Pattern

Adapter mengubah interface sebuah class menjadi interface lain yang diharapkan klien. Adapter bikin class yang interfacenya nggak cocok jadi bisa kerja bareng—yang tadinya mustahil karena beda colokan.

◆ Bedanya sama Facade

Gampang ketuker. Adapter nyocokin satu interface ke interface lain—tujuannya kompatibilitas, jumlah method bisa tetap. Facade nyederhanain sekumpulan class yang ribet jadi satu pintu masuk yang gampang. Beda niat: Adapter ganti bentuk colokan, Facade kurangi jumlah tombol. Facade-nya kita bahas habis ini.

Pattern 09 · Template Method · "kerangka algoritma"

Template Method — resepnya superclass yang pegang, langkah uniknya subclass

Kopi dan teh itu resepnya mirip banget: didihin air, seduh, tuang ke cangkir, kasih bumbu. Yang beda cuma dua langkah—cara nyeduhnya, dan bumbunya. Daripada nulis dua resep yang 80% sama, taruh kerangkanya di satu tempat.

BOS:

"Resep Kopi dan resep Teh hampir identik. Kok aku lihat boilWater() dan pourInCup() di-copy-paste di dua class? Satuin dong."

Coffee.java & Tea.java — dua resep nyaris kembarSMELL
public class Coffee {
    void prepareRecipe() {
        boilWater();              // sama persis...
        brewCoffeeGrinds();
        pourInCup();             // ...dengan Tea
        addSugarAndMilk();
    }
}
public class Tea {
    void prepareRecipe() {
        boilWater();              // duplikat lagi
        steepTeaBag();
        pourInCup();
        addLemon();
    }
}

Lihat strukturnya: empat langkah, urutan sama, dua langkah identik (boilWater + pourInCup), dua langkah beda (seduh & bumbu). Itu pola yang minta diabstraksi. Naikkan kerangkanya ke superclass, jadiin langkah-yang-beda abstract.

CaffeineBeverage.java — kerangka yang finalCLEAN
public abstract class CaffeineBeverage {

    final void prepareRecipe() {      // template — gak boleh di-override
        boilWater();
        brew();                       // langkah subclass
        pourInCup();
        if (customerWantsCondiments()) { // hook
            addCondiments();             // langkah subclass
        }
    }

    abstract void brew();             // diisi Coffee / Tea
    abstract void addCondiments();

    void boilWater()  { System.out.println("Mendidihkan air"); }
    void pourInCup() { System.out.println("Menuang ke cangkir"); }

    boolean customerWantsCondiments() { return true; } // hook, default ya
}

Perhatiin prepareRecipe() ditandai final—itu si template method. Dia yang memegang urutan algoritma; subclass nggak boleh ngubah strukturnya. boilWater() & pourInCup() konkret (sama buat semua). brew() & addCondiments() abstract—wajib diisi subclass.

Coffee.java & Tea.java — tinggal isi yang bedaCLEAN

    public void brew() {
        System.out.println("Menyeduh bubuk kopi");
    }
    public void addCondiments() {
        System.out.println("Menambahkan gula dan susu");
    }
}

public class Tea extends CaffeineBeverage {
    public void brew() {
        System.out.println("Mencelup teh celup");
    }
    public void addCondiments() {
        System.out.println("Menambahkan lemon");
    }
}

Nol duplikasi. Kerangka resep cuma ada di satu tempat. Mau bikin HotChocolate? extends CaffeineBeverage, isi brew() & addCondiments(), selesai—kamu nggak akan pernah salah urutan, karena urutannya bukan urusanmu.

    public void brew()         { System.out.println("Mencelup teh"); }
    public void addCondiments() { System.out.println("Tambah lemon"); }

    public boolean customerWantsCondiments() {  // override hook
        return getUserInput().toLowerCase().startsWith("y");

Itu yang namanya hook: method konkret di superclass yang isinya kosong atau default, ada cuma supaya subclass boleh nyangkut ke titik tertentu dalam algoritma. Kalau nggak di-override, ya jalan default. Beda dari abstract yang wajib diisi.

◆ Design Principle

The Hollywood Principle: "Don't call us, we'll call you." Superclass yang manggil method subclass, bukan sebaliknya. Komponen low-level boleh ikut, tapi nggak nentuin kapan dia dipanggil.

Definisi · Template Method Pattern

Mendefinisikan kerangka sebuah algoritma di dalam sebuah method, menunda beberapa langkahnya ke subclass. Template Method bikin subclass meredefinisi langkah tertentu sebuah algoritma tanpa mengubah struktur algoritmanya.

Strategy

  • Bungkus seluruh algoritma, ditukar via komposisi (HAS-A)
  • Flexibel saat runtime—ganti objek strategi
  • Tiap varian = class lengkap berdiri sendiri

Template Method

  • Bungkus kerangkanya, subclass isi langkah lewat warisan (IS-A)
  • Ditentukan saat compile—subclass override langkah
  • Pakai ulang banyak langkah konkret yang sama
◆ Hati-hati

Jangan jadiin semua langkah abstract—semakin banyak yang wajib diisi, semakin berat bikin subclass baru. Sebaliknya kalau terlalu sedikit, polanya jadi nggak fleksibel. Tandai prepareRecipe() final biar subclass nggak diam-diam mengganti urutan resepnya.

    }
}

Akar masalahnya: printMenu() nge-loop dengan cara yang bocor ke detail penyimpanan tiap menu. Yang berubah-ubah di sini bukan menunya, tapi cara iterasi-nya. Cabut itu, bungkus jadi objek sendiri: sebuah Iterator.

Iterator.java — kontrak jalan-jalanCLEAN
public interface Iterator {
    boolean hasNext();   // masih ada elemen lagi?
    Object  next();      // kasih yang berikutnya
}
DinerMenuIterator.java — jalan di atas arrayCLEAN
public class DinerMenuIterator implements Iterator {
    MenuItem[] items;
    int position = 0;

    public DinerMenuIterator(MenuItem[] items) {
        this.items = items;
    }
    public boolean hasNext() {
        return position < items.length && items[position] != null;
    }
    public Object next() {
        MenuItem item = items[position];
        position = position + 1;
        return item;
    }
}
// PancakeHouseMenuIterator: sama, tapi pakai ArrayList di dalam.

Tiap menu sekarang nyediain createIterator() yang balikin Iterator versinya sendiri. Detail "array vs ArrayList" terkubur di dalam masing-masing iterator—Waitress nggak peduli lagi.

DinerMenu.java — bikin iterator-nya sendiriCLEAN
public class DinerMenu {
    MenuItem[] menuItems;   // disimpan sebagai array

    public Iterator createIterator() {
        return new DinerMenuIterator(menuItems);
    }
}
// PancakeHouseMenu.createIterator() balikin iterator versi ArrayList.
◆ Design Principle

Sebuah class semestinya cuma punya satu alasan untuk berubah (Single Responsibility). Koleksi tugasnya nyimpen data; urusan iterasi diserahin ke iterator terpisah.

Waitress.java — cuma pegang IteratorCLEAN
public class Waitress {
    public void printMenu() {
        Iterator pancakeIt = pancakeMenu.createIterator();
        Iterator dinerIt   = dinerMenu.createIterator();
        printMenu(pancakeIt);   // satu loop, dipakai ulang
        printMenu(dinerIt);
    }
    private void printMenu(Iterator it) {
        while (it.hasNext()) {
            MenuItem item = (MenuItem) it.next();
            System.out.println(item.getName());
        }
    }
}

Satu while (it.hasNext()), dipakai buat semua menu. Menu ketiga muncul pakai HashMap? Bikin iterator-nya, kasih createIterator()—Waitress nol disentuh.

Tanpa Iterator

  • Waitress tahu array dan ArrayList
  • Tiap menu baru = cabang if baru
  • Loop iterasi nyebar, di-copy ke mana-mana

Dengan Iterator

  • Waitress cuma kenal interface Iterator
  • Menu baru = satu iterator baru, klien diam
  • Iterasi terkumpul rapi di satu objek
Definisi · Iterator Pattern

Menyediakan cara untuk mengakses elemen sebuah agregat secara berurutan, tanpa membuka representasi dalamnya.

◆ Kamu udah pakai ini tiap hari

java.util.Iterator itu persis pola ini—lengkap dengan hasNext() dan next(). Tiap kali kamu nge-loop List, Set, atau koleksi lain di JDK, kamu lagi pakai Iterator pattern.

Pattern 11 · Composite · "pohon: daun & ranting diperlakukan sama"

Composite — menu di dalam menu, dan klien nggak peduli yang mana

Iterator tadi rapi: satu cara jalan-jalan ke semua menu. Tapi lalu kafe kasih kabar—mereka mau nambah menu dessert di dalam menu makan siang. Submenu. Menu di dalam menu. Iterator doang nggak nutup ini.

BOS:

"DinerMenu butuh submenu Dessert. Dan nanti bakal ada submenu di dalam submenu. Klien tetap mau satu cara aja buat print semua—jangan ribet."

Masalahnya: Iterator jago buat koleksi datar. Begitu strukturnya bersarang—menu punya menu item dan menu lain—klien harus tahu "ini menu atau item?" di tiap langkah. Loop di dalam loop di dalam loop. Kode klien jadi kenal seluruh bentuk pohonnya. Itu rapuh.

Yang kita mau: perlakukan satu item dan sekumpulan item (yang mungkin berisi item lagi) lewat tipe yang sama. Itu inti Composite.

◆ Design Principle

Satu antarmuka untuk daun dan ranting. Klien manggil print() tanpa nanya "kamu menu atau item?".
— Perlakukan objek tunggal & komposisi secara seragam.

Caranya: bikin satu superclass abstrak MenuComponent yang punya semua operasi umum—getName(), print(), sampai add(). Lalu ada dua peran yang mewarisinya: MenuItem (daun) dan Menu (komposit yang nyimpan anak).

MenuComponent.java — superclass abstrak untuk semuaCLEAN
public abstract class MenuComponent {
    // default: lempar. tiap peran override yang relevan.
    public void add(MenuComponent c) {
        throw new UnsupportedOperationException();
    }
    public void remove(MenuComponent c) {
        throw new UnsupportedOperationException();
    }
    public MenuComponent getChild(int i) {
        throw new UnsupportedOperationException();
    }

    public String getName() {
        throw new UnsupportedOperationException();
    }
    public void print() {
        throw new UnsupportedOperationException();
    }
}

MenuItem = daun. Dia ujung pohon: nggak punya anak, print() cuma cetak dirinya sendiri.

MenuItem.java — LEAF (cetak dirinya)CLEAN
public class MenuItem extends MenuComponent {
    private String name;
    private boolean vegetarian;
    private double price;

    public MenuItem(String name, boolean veg, double price) {
        this.name = name; this.vegetarian = veg; this.price = price;
    }

    @Override public String getName() { return name; }

    @Override public void print() {
        System.out.print("  " + name);
        if (vegetarian) System.out.print(" (v)");
        System.out.println(", " + price);   // daun: cuma dirinya
    }
}

Menu = komposit. Dia simpan List<MenuComponent> anak. Anaknya bisa MenuItem, bisa Menu lain—Menu nggak peduli. print()-nya cetak header, lalu loop ke tiap anak dan panggil print() mereka. Karena anak juga MenuComponent, kalau anaknya Menu lagi, dia bakal print isinya sendiri—rekursif, turun ke seluruh pohon.

Menu.java — COMPOSITE (punya anak, print rekursif)CLEAN
public class Menu extends MenuComponent {
    private List<MenuComponent> children = new ArrayList<MenuComponent>();
    private String name;

    public Menu(String name) { this.name = name; }

    @Override public void add(MenuComponent c) { children.add(c); }
    @Override public String getName() { return name; }

    @Override public void print() {
        System.out.println("\n" + name);          // header menu ini
        for (MenuComponent c : children) {       // item ATAU submenu
            c.print();                            // rekursi turun pohon
        }
    }
}

Sekarang lihat sisi klien. Dessert dibikin Menu biasa, lalu dinerMenu.add(dessertMenu)—submenu masuk persis kayak item biasa. Untuk cetak seluruhnya, klien cukup pegang menu paling atas dan panggil satu method:

Waitress.java — klien cuma kenal MenuComponentCLEAN
public class Waitress {
    private MenuComponent allMenus;   // tipe yang SAMA buat semua

    public Waitress(MenuComponent allMenus) { this.allMenus = allMenus; }

    public void printMenu() { allMenus.print(); }  // satu panggilan, beres
}

// dinerMenu.add(dessertMenu);  // submenu = anak biasa
// dessertMenu.add(new MenuItem("Apple Pie", true, 1.59));
// new Waitress(allMenus).printMenu();  // cetak SEMUA, sampai pucuk

Waitress nggak pernah nanya "ini item atau menu?". Dia panggil print() ke MenuComponent—item cetak dirinya, menu cetak header lalu suruh anak-anaknya cetak. Tambah submenu di dalam submenu di dalam submenu? Kode klien nol perubahan.

Definisi · Composite Pattern

Composite menyusun objek ke dalam struktur pohon untuk merepresentasikan hierarki bagian-keseluruhan. Composite membuat klien bisa memperlakukan objek tunggal dan komposisi objek secara seragam.

◆ Trade-off · transparansi vs keamanan

Karena add()/remove() taruh di MenuComponent, daun (MenuItem) ikut punya method itu—itu yang bikin klien seragam (transparan). Harganya: menuItem.add(...) tetap bisa dipanggil dan baru meledak saat runtime. Mau lebih aman? Taruh add() cuma di Menu—tapi klien jadi harus cek tipe lagi. Composite sengaja pilih transparansi; ini trade-off sadar, bukan lupa.

Pattern 12 · State · "objek ganti kelakuan saat state berubah"

State — mesin permen yang jadi pinter sendiri

Ada mesin permen gumball. Empat keadaan: NoQuarter (belum ada koin), HasQuarter (koin masuk), Sold (lagi ngeluarin permen), SoldOut (habis). Empat aksi: insertQuarter(), ejectQuarter(), turnCrank(), dispense(). Apa yang boleh terjadi tergantung lagi di keadaan mana.

GumballMachine.java — versi konstanta int + if/elseSMELL
public class GumballMachine {
    final static int SOLD_OUT    = 0;
    final static int NO_QUARTER  = 1;
    final static int HAS_QUARTER = 2;
    final static int SOLD        = 3;
    int state = SOLD_OUT;

    public void insertQuarter() {
        if (state == HAS_QUARTER)      { ... "udah ada koin" }
        else if (state == SOLD_OUT)  { ... "habis" }
        else if (state == SOLD)      { ... "tunggu, lagi keluar" }
        else if (state == NO_QUARTER){ state = HAS_QUARTER; ... }
    }
    // turnCrank(), ejectQuarter(), dispense(): if/else RAKSASA yang SAMA
}
BOS:

"Bikin seru—1 dari 10 putaran menang, dapat 2 permen sekaligus. Tambahin state Winner ya."

Kedengerannya kecil. Tapi nambah satu state berarti: tambah satu konstanta int, lalu bongkar tiap method—insertQuarter, turnCrank, ejectQuarter, dispense—buat nyelipin satu cabang else if baru di masing-masing. Empat method, empat tempat lupa, empat peluang bug. Kode yang harusnya "ketutup buat modifikasi" malah dibedah ulang tiap kali aturan berubah.

◆ Design Principle

Yang berubah-ubah di sini adalah perilaku per-state. Bungkus tiap state jadi objeknya sendiri.
— Encapsulate what varies.

Balik logikanya. Daripada satu kelas raksasa yang ngecek "lagi di state mana", bikin satu class per state. Tiap state tahu sendiri gimana harus bereaksi ke keempat aksi, dan kemana mesin harus pindah berikutnya.

State.java — kontrak yang sama buat semua stateCLEAN
public interface State {
    void insertQuarter();
    void ejectQuarter();
    void turnCrank();
    void dispense();
}

public class NoQuarterState implements State {
    GumballMachine machine;
    public NoQuarterState(GumballMachine m) { machine = m; }

    public void insertQuarter() {
        System.out.println("Koin masuk");
        machine.setState(machine.getHasQuarterState());  // pindah!
    }
    public void ejectQuarter() { System.out.println("Belum ada koin"); }
    public void turnCrank()   { System.out.println("Masukin koin dulu"); }
    public void dispense()    { System.out.println("Bayar dulu"); }
}
GumballMachine.java — cuma nyimpen state + delegasiCLEAN
public class GumballMachine {
    State noQuarterState;
    State hasQuarterState;
    State soldState;
    State soldOutState;
    State state;   // state yang lagi aktif sekarang
    int count = 0;

    public GumballMachine(int jumlah) {
        noQuarterState  = new NoQuarterState(this);
        hasQuarterState = new HasQuarterState(this);
        // ...soldState, soldOutState juga
        count = jumlah;
        state = (jumlah > 0) ? noQuarterState : soldOutState;
    }

    public void insertQuarter() { state.insertQuarter(); }  // delegasi
    public void turnCrank()     { state.turnCrank();
                                  state.dispense(); }
    public void setState(State s) { state = s; }
    public State getHasQuarterState() { return hasQuarterState; }
}

Lihat insertQuarter() di mesinnya: nggak ada if sama sekali, cuma state.insertQuarter(). Mesin nggak peduli lagi di state mana—objek state-nya yang ngatur. Sekarang ke permintaan bos: state Winner? Bikin satu class baru WinnerState, colok transisinya. Empat method lama di GumballMachine nggak disentuh sama sekali.

Definisi · State Pattern

Memungkinkan sebuah objek mengubah perilakunya saat state internalnya berubah. Objeknya seolah-olah berganti class.

if/else raksasa

  • Logika tiap state nyebar di keempat method
  • Nambah state = bedah semua method
  • Transisi state susah dilacak

satu class per state

  • Perilaku satu state ngumpul di satu file
  • Nambah state = bikin class baru, mesin utuh
  • Transisi eksplisit: machine.setState(...)
◆ Mirip Strategy? Strukturnya iya, niatnya beda

Diagram kelasnya kembar sama Strategy—objek konteks delegasi ke objek lain di balik satu interface. Bedanya di niat: di Strategy, klien yang milih algoritma dan biasanya nge-set sekali. Di State, state-state itu sendiri yang menentukan transisi—konteks berganti perilaku seiring waktu tanpa klien ikut campur.

Pattern 13 · Proxy · "control access to an object"

Proxy — pasang penjaga di depan objek aslinya

Mesin permen GumballMachine kamu udah laku ke ratusan lokasi. Sekarang bos pengin mantau stok permen dari kantor pusat—tanpa terbang ke tiap kota. Masalahnya: objek mesinnya hidup di JVM lain, di komputer lain. Kamu butuh sesuatu yang berlagak jadi mesin itu di sisimu, padahal cuma wakil.

BOS:

"Aku mau satu layar monitor yang nampilin lokasi, stok permen, sama state tiap mesin—dari semua mesin yang udah kepasang. Real-time."

Idenya: bikin GumballMonitor yang manggil getCount(), getLocation(), getState() di objek mesin. Tapi objeknya nun jauh di sana. Trik Proxy: kasih monitor sebuah stub lokal yang antarmukanya sama persis dengan mesin asli. Monitor manggil seperti biasa; di balik layar stub-nya yang ngurus jaringan.

GumballMonitor.java — nggak sadar dia ngomong ke proxyCLEAN
public class GumballMonitor {
    GumballMachineRemote machine;     // cuma tau interface-nya

    public GumballMonitor(GumballMachineRemote machine) {
        this.machine = machine;
    }

    public void report() {
        try {
            System.out.println("Lokasi: " + machine.getLocation());
            System.out.println("Stok  : " + machine.getCount());
            System.out.println("State : " + machine.getState());
        } catch (RemoteException e) {
            e.printStackTrace();
        }
    }
}

Di RMI, mesin asli kamu jadikan remote service (implement Remote, method-nya throws RemoteException). Yang dipegang monitor cuma stub—proxy lokal yang otomatis dibikin RMI. Tiap panggilan method dibungkus, dikirim lewat soket ke JVM mesin, dijalankan di sana, hasilnya dikirim balik. Monitor nggak tau (dan nggak peduli) ada jaringan di tengah.

GumballMachineRemote.java — kontrak yang dipakai dua sisiCLEAN
public interface GumballMachineRemote extends Remote {
    String getLocation() throws RemoteException;
    int    getCount()    throws RemoteException;
    State  getState()    throws RemoteException;
}

// Objek ASLI hidup di mesin permen, di JVM-nya sendiri:
public class GumballMachine
        extends UnicastRemoteObject
        implements GumballMachineRemote {
    public String getLocation() { return location; }
    public int    getCount()    { return count; }
    // ...state machine permen jalan di sini, lokal.
}

Itu Remote Proxy: stub lokal mewakili objek yang ada di JVM lain. Tapi proxy nggak cuma soal jaringan. Kadang objek aslinya mahal banget dibikin—dan kamu pengin nundanya sampai benar-benar perlu.

Kasus buku: galeri sampul album musik. Tiap gambar diambil dari internet, lambat. Kamu nggak mau jendela ngehang nungguin semua gambar download. Pengennya layar langsung muncul, nampilin "Loading...", lalu gambar masuk pelan-pelan begitu siap. Solusinya Virtual Proxy: proxy berdiri sebagai pengganti gambar yang berat.

ImageProxy.java — placeholder sampai gambar siapCLEAN
class ImageProxy implements Icon {
    ImageIcon imageIcon;              // objek ASLI, belum dibikin
    URL imageURL;
    boolean retrieving = false;

    public ImageProxy(URL url) { imageURL = url; }

    public void paintIcon(Component c, Graphics g, int x, int y) {
        if (imageIcon != null) {
            imageIcon.paintIcon(c, g, x, y);     // udah ada: delegasi
        } else {
            g.drawString("Loading album cover...", x + 300, y + 190);
            if (!retrieving) {
                retrieving = true;
                loadImageInBackground(c);       // ambil di thread lain
            }
        }
    }
    // loadImageInBackground(): new ImageIcon(imageURL), lalu repaint.
}

Klien (galeri) kira dia megang Icon biasa. Selama gambar belum turun, proxy gambar tulisan "Loading...". Begitu ImageIcon asli jadi, panggilan berikutnya diteruskan ke objek asli. Antarmuka sama, kontrol bertambah.

◆ Inti Proxy

Proxy implements interface yang sama dengan objek asli, megang referensi ke objek itu (atau bikin saat perlu), lalu nyelipin kontrol—akses, lazy-load, jaringan—sebelum mendelegasikan.

Definisi · Proxy Pattern

Menyediakan sebuah surrogate atau placeholder bagi objek lain, demi mengontrol akses ke objek itu. Klien ngomong ke proxy persis seperti ke objek asli; proxy yang nentuin kapan dan gimana panggilan diteruskan.

◆ Tiga rasa Proxy yang sering kepakai

Remote proxy — wakil lokal objek di JVM/mesin lain (RMI, monitor GumballMachine). Virtual proxy — nunda bikin objek mahal sampai dibutuhkan (ImageProxy "Loading..."). Protection proxy — kontrol akses berdasar hak; teruskan panggilan cuma kalau penelepon boleh. Beda niat, struktur sama.

◆ Proxy vs Decorator vs Adapter

Bentuk-nya mirip (semua membungkus lewat interface yang sama), tapi niatnya beda: Adapter mengubah antarmuka, Decorator menambah tanggung jawab, Proxy mengontrol akses ke objek—tanpa mengubah apa yang objek itu lakukan.

Penutup · Bukan pattern baru · "shared vocabulary"

Pattern itu kosakata, bukan agama.

Kita udah keliling belasan pattern. Tapi nilai terbesarnya bukan kode yang bisa kamu reuse. Yang paling kepakai tiap hari adalah kosakata bersama. Bilang ke tim "pakai Strategy di sini"—dan semua orang langsung ngerti: perilaku dicabut jadi keluarga yang bisa dicolok. Satu kata, satu kalimat, ngewakilin satu paragraf desain plus semua trade-off-nya.

Bandingin dua review ini. Yang satu jelasin pelan-pelan; yang satu sebut nama pattern. Maksudnya sama persis—tapi yang kedua nyampe dalam sedetik.

Tanpa kosakata

  • "Bikin interface buat tiap algoritma terus simpan satu di field, jadi bisa ditukar pas runtime…"
  • "Bungkus objek lama biar tampak kayak interface yang baru…"
  • "Satu titik akses buat objek yang cuma boleh ada satu instance…"

Dengan kosakata

  • "Pakai Strategy."
  • "Bungkus pakai Adapter."
  • "Itu Singleton."

Itu inti Head First: pattern naikin level obrolan tim. Diskusi desain pindah dari detail bit-per-bit ke level pattern—lebih cepat, lebih sedikit salah paham. Tapi di balik tiap pattern, yang sebenarnya kerja adalah prinsip desain OO. Pattern itu cuma cara prinsip-prinsip ini ketemu di lapangan. Ini dia tembok sticky-note-nya:

◆ Design Principle · 1

Kenali yang berubah-ubah, pisahkan dari yang tetap.
— Encapsulate what varies.

◆ Design Principle · 2

Program ke interface, bukan ke implementasi.

◆ Design Principle · 3

Utamakan komposisi ketimbang warisan.
— Favor composition over inheritance.

◆ Design Principle · 4

Usahakan kopling longgar antar objek yang saling kenal.
— Strive for loosely coupled designs.

◆ Design Principle · 5

Terbuka buat ekstensi, tertutup buat modifikasi.

◆ Design Principle · 6

Bergantunglah pada abstraksi, jangan pada class konkret.

◆ Design Principle · 7

Ngobrol cuma sama teman dekat.
— Least Knowledge (Demeter).

◆ Design Principle · 8

Jangan telepon kami, kami yang telepon kamu.

◆ Design Principle · 9

Satu class, satu alasan buat berubah.
— Single Responsibility.

Hafal sembilan ini, dan tiap pattern berasa wajar—karena tinggal kombinasi dari prinsip yang udah kamu pahami. Tapi sekarang bagian yang paling penting, dan paling sering kelupaan.

JUNIOR:

"Aku abis belajar Visitor. Bagian login kita kayaknya bisa direfactor pakai Visitor + Factory + Strategy biar lebih 'proper'."

Ini jebakan klasik. Begitu kenal palu, semua kelihatan kayak paku. Pattern itu alat, bukan tujuan. Maksa pattern ke masalah yang nggak butuh = over-engineering: kamu nambah class, indireksi, dan beban mental—buat masalah yang sebenarnya cukup satu if.

◆ Anti-dogma

Pattern punya ongkos: kompleksitas tambahan. Bayar ongkos itu cuma kalau masalahnya beneran cocok—kalau ada perilaku yang berubah-ubah, ada titik ekstensi yang nyata, ada kopling yang bikin sakit. Kalau belum kerasa sakitnya, jangan dibungkus pattern. Pattern terbaik kadang justru TANPA pattern.

Definisi · Kapan pakai pattern

Pakai pattern saat masalahnya cocok, bukan saat patternnya keren. Awali dari kode paling sederhana yang jalan; biarkan pattern muncul saat rasa sakitnya nyata (YAGNI). Pattern adalah jawaban atas masalah yang berulang—bukan dekorasi buat masalah yang belum ada.

  • Pelajari prinsipnya, bukan cuma hafal nama pattern.
  • Pakai kosakata pattern biar tim ngobrol di level yang sama.
  • Tahan diri: pattern itu solusi buat masalah yang ada—bukan buat masalah yang dibayangin.
  • Mulai simpel. Biarkan desain berkembang; refactor ke pattern saat sudah perlu.

"Kuasai prinsipnya, kenali kosakatanya, lalu lupakan aturannya sampai masalahnya datang menjemput." 🐤
