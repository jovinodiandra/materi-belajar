// Data Structures & Algorithms — mengukur "cepat" secara objektif

Seberapa cepat algoritmamu, tanpa nyalakan stopwatch?

Dua orang menulis solusi berbeda untuk soal yang sama. Yang satu "terasa" lebih cepat di laptop kamu — tapi itu bisa jadi karena laptopnya lebih baru, bukan karena algoritmanya lebih pintar. Big-O dan kerabatnya (Big-Omega, Big-Theta) adalah bahasa formal untuk membicarakan pertumbuhan waktu & memori algoritma — independen dari mesin, bahasa, atau mood compiler hari itu. Deck ini fokus ke definisi formalnya: notasi, cara menghitung dari kode baris per baris, sampai kapan analisis ini cukup dan kapan harus turun ke benchmark nyata.

Masalah
"Cepat" itu relatif — tergantung mesin, bahasa, beban saat itu
Ide
Hitung langkah, bukan detik — notasi asimptotik O / Ω / Θ
Alat
Kelas pertumbuhan — O(1) sampai O(2ⁿ), diurutkan
Batas
Abaikan konstanta — kadang konstanta itu yang menentukan di dunia nyata
Pakai
Bandingkan algoritma — sebelum data tumbuh dari ribuan ke jutaan
↓ SCROLL ATAU TEKAN → UNTUK MULAI
◆ Buat apa ini? Kenapa pakai ini?

Given — dua kandidat algoritma dibandingkan dengan menjalankan keduanya lalu menimbang waktunya pakai stopwatch / System.currentTimeMillis() di satu laptop, dengan data uji yang masih kecil (ratusan baris).

When — kode itu di-deploy dan datanya tumbuh jadi jutaan baris di production, di mesin server yang beda CPU & beban dari laptop developer.

Then — algoritma yang "menang" di laptop (kebetulan cache warm, CPU kencang) ternyata O(n²) dan melambat eksponensial seiring n membesar, sementara yang "kalah" di benchmark lokal sebenarnya O(n log n) dan jauh lebih skalabel — keputusan desain jadi salah karena membandingkan detik, bukan laju pertumbuhannya.

→ makanya kita pakai Big-O (dan kerabatnya Ω, Θ).

Akar masalah · Kenapa butuh notasi kompleksitas

"Cepat di laptop saya" bukan ukuran yang bisa dipercaya

Kalau kamu mengukur algoritma A dan B dengan System.currentTimeMillis(), hasilnya dipengaruhi banyak hal yang tidak ada hubungannya dengan algoritmanya sendiri: kecepatan CPU, bahasa pemrograman, JIT compiler yang sedang warm up, bahkan proses lain yang kebetulan jalan di background. Butuh cara membandingkan algoritma yang independen dari mesin & bahasa — yang tetap valid entah dijalankan di laptop kentang atau server data center.

◆ Analogi — bandingkan resep dari jumlah langkah, bukan waktu masak

Membandingkan dua resep dengan menimbang berapa menit masing-masing matang itu curang: dapur A punya kompor gas cepat panas, dapur B pakai kompor listrik tua. Cara yang adil adalah menghitung jumlah langkah yang harus dikerjakan — berapa kali mengiris, berapa kali mengaduk, berapa lapis proses — lalu lihat bagaimana jumlah langkah itu bertambah kalau porsi masakannya dilipatgandakan. Notasi kompleksitas melakukan hal yang sama untuk kode: menghitung pertumbuhan jumlah operasi seiring ukuran input n membesar, bukan detik di stopwatch.

Ini juga kenapa dua implementasi algoritma yang sama — satu di Java, satu di Python — bisa dibicarakan dengan notasi Big-O yang sama persis. Notasinya bicara soal bentuk pertumbuhan, bukan angka detik absolut. Itulah yang membuatnya jadi bahasa universal lintas bahasa & platform.

Notasi asimptotik (O, Ω, Θ) memungkinkan kita membandingkan algoritma berdasarkan cara pertumbuhannya seiring ukuran input membesar — tanpa terikat pada detail implementasi atau kecepatan mesin tertentu.

— parafrasa dari Thomas H. Cormen dkk., Introduction to Algorithms (CLRS)
Konsep inti · Notasi asimptotik

Big-O, Big-Omega, Big-Theta: tiga sisi dari batas yang sama

Ketiganya membicarakan batas pertumbuhan fungsi waktu/memori terhadap ukuran input n, tapi dari arah berbeda.

◆ Tiga notasi, tiga arah batas
O(f(n))→ Upper bound — "tidak akan lebih lambat dari ini" (biasanya worst case)
Ω(f(n))→ Lower bound — "tidak akan lebih cepat dari ini" (best case)
Θ(f(n))→ Tight bound — O dan Ω bertemu, batas atas = batas bawah

Dalam obrolan sehari-hari, orang sering bilang "kompleksitasnya O(n)" padahal maksudnya Θ(n) — batas ketat. Itu tidak apa-apa selama kamu paham bedanya saat diperlukan presisi (misalnya di soal ujian atau paper).

Contoh paling gampang dibayangkan: mencari elemen di array yang tidak terurut dengan linear search.

// Best case → Ω

  • Elemen yang dicari ada di posisi pertama.
  • Cuma butuh 1 perbandingan → Ω(1).

// Worst case → O

  • Elemen ada di posisi terakhir (atau tidak ada).
  • Harus cek semua n elemen → O(n).
analisis kompleksitas per barisJAVA
public class Matrix {

    // O(1) — akses array by index, sekali eksekusi
    static int first(int[] arr) {
        return arr[0];                      // 1 operasi, tidak peduli n
    }

    // O(n) — satu loop sepanjang n
    static int sum(int[] arr) {
        int total = 0;
        for (int i = 0; i < arr.length; i++) {  // jalan n kali
            total += arr[i];                    // O(1) di dalam loop O(n) → total O(n)
        }
        return total;
    }

    // O(n^2) — nested loop, masing-masing sepanjang n
    static boolean hasDuplicate(int[] arr) {
        for (int i = 0; i < arr.length; i++) {      // n kali
            for (int j = i + 1; j < arr.length; j++) { // ~n kali lagi → n * n
                if (arr[i] == arr[j]) return true;
            }
        }
        return false;                        // worst case: O(n^2)
    }

    // O(log n) — separuh ruang pencarian dibuang tiap iterasi
    static int binarySearch(int[] arr, int target) {
        int lo = 0, hi = arr.length - 1;
        while (lo <= hi) {                    // tiap putaran, n dibagi 2
            int mid = (lo + hi) / 2;
            if (arr[mid] == target) return mid;
            else if (arr[mid] < target) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1;                          // worst case: O(log n)
    }
}

Pola membacanya: satu loop sepanjang n → O(n). Loop di dalam loop, masing-masing sepanjang n → O(n²). Ruang pencarian dibelah dua tiap iterasi → O(log n). Akses langsung tanpa loop → O(1). Ini bukan hafalan — ini konsekuensi langsung dari menghitung berapa kali tiap baris dieksekusi.

Peta besar · Kelas kompleksitas umum

Dari konstan sampai eksponensial, diurutkan

Ada segelintir kelas pertumbuhan yang paling sering muncul. Hafalkan urutannya — ini yang jadi patokan cepat saat membandingkan dua algoritma tanpa harus menghitung ulang dari nol.

◆ Urutan pertumbuhan (kecil → besar) & ilustrasi n = 10.000
O(1)→ 1 operasi — akses array by index, push/pop stack
O(log n)→ ~13 operasi — binary search, cari di balanced BST
O(n)→ 10.000 operasi — linear search, satu kali loop penuh
O(n log n)→ ~130.000 operasi — merge sort, quicksort (rata-rata)
O(n²)→ 100 juta operasi — nested loop, bubble sort, selection sort
O(2ⁿ)→ angka astronomis — brute force subset, rekursi fibonacci naif

Lompatan dari O(n) ke O(n²) saja sudah mengubah 10.000 operasi jadi 100 juta. Ini kenapa "cuma nested loop tambahan" bisa jadi keputusan yang mahal saat data membesar.

Selain time complexity, ada space complexity — seberapa banyak memori ekstra (bukan input aslinya) yang dipakai algoritma seiring n membesar. Linear search hanya butuh satu variabel index → O(1) space. Merge sort butuh array sementara sebesar input → O(n) space. Rekursi juga makan memori lewat call stack: rekursi sedalam n level → O(n) space, meski tidak ada array yang dialokasikan secara eksplisit.

◆
Jangan tertukar: O(n²) berarti waktu tumbuh kuadratik — bukan berarti algoritmanya "jelek" secara mutlak. Untuk n kecil (puluhan elemen), O(n²) yang sederhana kadang lebih cepat di dunia nyata daripada O(n log n) yang overhead-nya lebih besar. Notasi ini bicara soal tren pertumbuhan, bukan angka mutlak di satu titik n.
◆ Best practice · Cara menghitung dengan benar

Enam kebiasaan supaya analisismu tidak meleset

Menghitung kompleksitas itu mekanis begitu kamu tahu aturan mainnya. Berikut kebiasaan yang mencegah kesalahan paling umum.

  1. Default ke worst case — kecuali soal secara eksplisit minta best/average case, "kompleksitas algoritma ini" berarti O untuk skenario terburuk. Ini konvensi paling aman & paling sering dipakai di industri.
  2. Buang konstanta — O(2n) ditulis O(n), O(500) ditulis O(1). Konstanta tidak mengubah bentuk pertumbuhan seiring n → ∞.
  3. Buang lower-order term — O(n² + n) ditulis O(n²) karena saat n besar, suku n² mendominasi total operasi jauh di atas suku n.
  4. Nested loop dihitung hati-hati — dua loop bersarang yang sama-sama sepanjang n → O(n²). Tapi loop dalam yang panjangnya tetap (misal selalu 5 iterasi) tidak menambah pangkat — tetap O(n).
  5. Loop berurutan (bukan bersarang) dijumlah, bukan dikali — satu loop O(n) diikuti loop lain O(n) secara berurutan → O(n) + O(n) = O(n), bukan O(n²).
  6. Rekursi dianalisis lewat jumlah pemanggilan × kerja per pemanggilan — jangan cuma lihat satu baris return f(n-1); hitung berapa kali fungsi itu total dipanggil sampai base case.
◆ Jenjang · Tier belajar

Dari hitung loop sampai amortized analysis

Kompleksitas asimptotik punya kedalaman bertingkat — mulai dari yang wajib dikuasai semua orang, sampai analisis yang baru relevan saat kamu mendesain struktur data sendiri.

Beginner

Hitung dari kode langsung

Baca kode baris per baris, kenali pola loop-nya.

  • Single loop sepanjang n → O(n).
  • Nested loop dua tingkat → O(n²).
  • Akses array/hashmap by key → O(1).
  • Bedakan best case vs worst case pada linear search.
Middle

Rekursi & recursion tree

Fungsi yang memanggil dirinya sendiri butuh cara hitung berbeda.

  • Gambar recursion tree — tiap level berapa pemanggilan?
  • Master theorem sederhana: T(n) = aT(n/b) + f(n).
  • Merge sort: T(n) = 2T(n/2) + O(n) → O(n log n).
  • Fibonacci naif: T(n) = T(n-1) + T(n-2) → O(2ⁿ).
Advance

Amortized & kasus bercabang

Analisis yang butuh melihat lebih dari satu operasi sekaligus.

  • Amortized analysis — dynamic array resize: O(1) amortized meski sesekali O(n).
  • Algoritma dengan banyak cabang kondisional — hitung tiap cabang, ambil yang terburuk.
  • Kompleksitas struktur data self-balancing (mis. red-black tree) lintas operasi.
  • Membedakan worst case per-operasi vs worst case rata-rata sepanjang eksekusi.
◆ Harga · Tidak ada makan siang gratis

Trade-off: waktu cepat sering berarti memori boros

Time complexity & space complexity sering tarik-menarik. Mempercepat waktu biasanya berarti menyimpan lebih banyak data bantu di memori — atau sebaliknya.

// Menang di waktu

  • Hashmap untuk lookup O(1) — tapi butuh O(n) memori ekstra di luar array asli.
  • Memoization pada rekursi — cache hasil supaya tak dihitung ulang, tapi cache itu makan memori.
  • Precompute / index tambahan — query jadi cepat, tapi struktur index butuh ruang sendiri.

// Menang di memori

  • In-place sort (mis. heapsort) — O(1) space, tapi umumnya lebih lambat & kurang stabil dibanding merge sort.
  • Rekursi tanpa memoization — hemat memori cache, tapi mengulang kerja yang sama berkali-kali.
  • Streaming/iteratif tanpa index — hemat RAM, tapi tiap query harus scan ulang.
◆ Contoh konkret

Fibonacci rekursif naif itu O(1) space tapi O(2ⁿ) waktu — lambat sekali. Tambahkan memoization (menyimpan hasil tiap n yang sudah dihitung) → waktu turun jadi O(n), tapi space naik jadi O(n) untuk cache-nya. Kamu membeli kecepatan dengan memori — trade-off yang sadar, bukan kebetulan.

◆ Keputusan · Kapan Big-O cukup, kapan tidak

Big-O adalah peta, bukan GPS dengan angka pasti

Big-O memberitahu tren pertumbuhan, bukan angka detik yang persis. Untuk banyak keputusan itu sudah cukup — tapi ada situasi yang butuh pengukuran nyata.

// Big-O cukup saat…

  • Membandingkan pendekatan yang beda kelas (O(n) vs O(n²)).
  • Input diperkirakan akan tumbuh besar seiring waktu.
  • Tahap desain — memilih struktur data/algoritma sebelum implementasi.
  • Interview / diskusi teknis yang butuh bahasa bersama.

// Butuh benchmark nyata saat…

  • Dua algoritma punya kelas Big-O yang sama tapi konstanta beda jauh.
  • n di production selalu kecil — overhead konstan lebih menentukan.
  • Faktor mesin nyata: cache CPU, I/O, garbage collector, jaringan.
  • Sebelum optimisasi production — profiler dulu, jangan menebak dari teori saja.

Memahami kompleksitas bukan sekadar latihan matematis, tapi alat praktis untuk memprediksi apakah sebuah program akan tetap berjalan cepat ketika data yang diprosesnya tumbuh dari ribuan menjadi jutaan.

— parafrasa dari Robert Sedgewick & Kevin Wayne, Algorithms
Studi kasus · Di dunia nyata

Saat kompleksitas berpindah dari teori ke insiden

Tiga skenario nyata di mana pemahaman Big-O langsung berdampak ke keputusan teknis — bukan cuma soal ujian.

// sorting adaptif

Timsort: satu algoritma, dua strategi

Kasus: Java (Arrays.sort untuk objek) & Python (sorted()) memakai Timsort — hybrid antara insertion sort & merge sort. Kenapa penting: untuk potongan data kecil yang hampir terurut, insertion sort (O(n) best case) lebih cepat daripada overhead merge sort penuh; untuk data besar, sifat O(n log n) merge sort yang menang. Timsort mendeteksi run terurut & memilih strategi sesuai ukurannya.

// database

Full table scan vs index

Kasus: query WHERE email = ? tanpa index harus memeriksa tiap baris tabel — O(n), makin lambat linear seiring tabel tumbuh. Menambah index B-tree pada kolom itu mengubahnya jadi pencarian O(log n). Dampak: tabel yang tumbuh dari ribuan ke jutaan baris membuat selisih O(n) vs O(log n) makin terasa — lihat topik indexing di situs ini untuk detail struktur B-tree-nya.

// skala pengguna

O(n²) yang dulu aman, kini bottleneck

Kasus: fitur "cari duplikat" atau "bandingkan tiap pasangan user" yang ditulis dengan nested loop lolos review saat n masih kecil — beberapa ribu baris data terasa instan. Yang berubah: seiring basis pengguna tumbuh, jumlah operasi n² ikut meledak kuadratik, dan endpoint yang dulu responsif mulai timeout. Solusinya bukan "server lebih kuat" — tapi turunkan kelas kompleksitasnya (mis. pakai hashmap/set untuk O(n)).

◆ Benang merahnya

Di ketiga kasus, masalahnya baru kelihatan saat n membesar. Kode yang "cukup cepat" di data kecil bisa menyembunyikan kelas kompleksitas yang buruk — dan Big-O adalah alat untuk melihat itu sebelum insiden terjadi, bukan sesudahnya.

Penutup

Hitung langkahnya, bukan detiknya

Big-O bukan sekadar simbol matematis yang harus dihafal untuk lulus ujian. Ini bahasa objektif untuk memprediksi apakah kodemu masih akan sehat saat datanya tumbuh sepuluh, seratus, seribu kali lipat — jauh sebelum kamu punya kesempatan mengukurnya di production.

  • O, Ω, Θ — upper bound, lower bound, tight bound dari pertumbuhan.
  • Default worst case — kecuali dinyatakan lain secara eksplisit.
  • Buang konstanta & lower-order term — fokus ke suku yang dominan.
  • Nested loop = kali, sequential loop = jumlah — jangan tertukar.
  • Time vs space — sering trade-off, pilih sesuai kebutuhan nyata.
  • Teori + profiler — Big-O untuk desain, benchmark untuk verifikasi.

Lanjut ke bab berikutnya

Setelah paham cara membaca & menghitung kompleksitas, langkah alami berikutnya adalah melihatnya bekerja di algoritma nyata: bagaimana Sorting — dari yang O(n²) sederhana sampai yang O(n log n) — dirancang, dan kenapa pilihan algoritma sorting yang tepat bisa jadi perbedaan antara sistem yang responsif & yang tidak.
