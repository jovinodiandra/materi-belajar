MongoDB — simpan dokumen JSON, query & index seperti biasa.

Di deck sebelumnya kita belajar kenapa document database ada. Sekarang kita praktik dengan tool paling populer: MongoDB. Datanya dokumen mirip JSON (BSON di balik layar), tapi kamu tetap bisa mencari (query) dan mempercepat pencarian (index) — bahkan menelusuri field yang bersarang di dalam array. Deck ini pakai contoh kasus yang sama: profil/CV & katalog produk.

Kenalan · Apa itu MongoDB

Database document open-source paling umum

MongoDB adalah database document: ia menyimpan data sebagai dokumen mirip-JSON, bukan baris di tabel. Setiap dokumen bisa bersarang (objek di dalam objek, array di dalam dokumen) — persis seperti objek di kode aplikasimu.

“Sebuah dokumen biasanya disimpan sebagai satu string menerus, dikodekan dalam JSON, XML, atau varian biner seperti BSON milik MongoDB.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 2)
// format

BSON di balik layar

Kamu menulis seperti JSON, tapi MongoDB menyimpannya sebagai BSON (Binary JSON) — lebih cepat dibaca mesin & punya tipe ekstra seperti Date dan ObjectId.

// _id

Setiap dokumen punya _id

Field _id otomatis dibuat (ObjectId) sebagai primary key unik. Ia otomatis ter-index.

// skala

Dibangun untuk skala

Mendukung replikasi (salinan untuk keandalan) & sharding (sebar data ke banyak server) sejak awal.

◆ Posisinya

Kalau kamu pemula dan ingin mencoba document database, MongoDB adalah titik awal yang paling masuk akal: dokumentasinya banyak, ada GUI gratis (MongoDB Compass), dan ada layanan cloud gratis untuk belajar (MongoDB Atlas).

Konsep · Model data & istilah

Collection, document, field

Kalau kamu datang dari SQL, peta istilahnya sederhana. Yang berubah hanya bentuk datanya: dari baris datar jadi dokumen bersarang.

◆ Padanan istilah SQL ↔ MongoDB
Database→ Database
Tabel→ Collection
Baris→ Document (objek mirip-JSON)
Kolom→ Field
PK→ _id (ObjectId, otomatis)
JOIN→ embedding / $lookup

Inti MongoDB: "data yang diakses bersama, disimpan bersama". Profil + pengalaman + pendidikan cukup jadi satu dokumen dalam collection users.

satu dokumen di collection "users"JSON
{
  "_id": ObjectId("665f1a..."),
  "nama": "Budi",
  "kota": "Bandung",
  "pengalaman": [
    { "jabatan": "Engineer", "di": "Acme", "tahun": 2019 },
    { "jabatan": "Lead",     "di": "Globex", "tahun": 2022 }
  ],
  "skill": [ "go", "mongodb", "docker" ]
}
◆ Operasi · CRUD & query

Menyimpan & mencari dengan find()

Query di MongoDB ditulis sebagai dokumen filter — kamu mendeskripsikan "bentuk" yang dicari. Inilah jawaban langsung untuk kebutuhan query dari contoh kasus profil & katalog.

create / read — mongoshJS
// CREATE — sisipkan satu dokumen
db.users.insertOne({
  nama: "Budi", kota: "Bandung",
  skill: ["go", "mongodb"],
  pengalaman: [{ jabatan: "Lead", di: "Globex", tahun: 2022 }]
})

// READ — semua user di Bandung, tampilkan nama saja
db.users.find({ kota: "Bandung" }, { nama: 1, _id: 0 })

// READ — operator perbandingan: pengalaman sejak >= 2020
db.users.find({ "pengalaman.tahun": { $gte: 2020 } })

// READ — cari di dalam array: punya skill "mongodb"
db.users.find({ skill: "mongodb" })   // otomatis cek tiap elemen array
update / delete + filter gabunganJS
// UPDATE — tambah skill baru ke Budi (tanpa duplikat)
db.users.updateOne(
  { nama: "Budi" },
  { $addToSet: { skill: "kubernetes" } }
)

// DELETE — hapus user tanpa skill sama sekali
db.users.deleteMany({ skill: { $size: 0 } })

// FILTER GABUNGAN — (kota Bandung ATAU Jakarta) DAN punya skill go
db.users.find({
  $and: [
    { $or: [ { kota: "Bandung" }, { kota: "Jakarta" } ] },
    { skill: "go" }
  ]
}).sort({ nama: 1 }).limit(20)
◆ Operator yang sering dipakai

$gt $gte $lt $lte (banding), $in $nin (di dalam daftar), $and $or $not (logika), $exists (field ada/tidak — berguna di skema fleksibel), $regex (cocok pola teks), $elemMatch (satu elemen array memenuhi banyak syarat sekaligus).

◆ Operasi · Aggregation pipeline

Query lanjutan: hitung, kelompokkan, gabung

Saat find() tak cukup — kamu butuh menghitung, mengelompokkan, atau menggabungkan — MongoDB pakai aggregation pipeline: data mengalir lewat tahap demi tahap ($match → $group → $sort).

berapa user per kota? (mirip GROUP BY di SQL)JS
db.users.aggregate([
  { $match:  { skill: "go" } },              // 1. filter dulu (pakai index)
  { $group:  { _id: "$kota", jumlah: { $sum: 1 } } }, // 2. kelompokkan per kota
  { $sort:   { jumlah: -1 } }              // 3. urutkan terbanyak
])
// hasil: [ { _id: "Bandung", jumlah: 12 }, { _id: "Jakarta", jumlah: 7 } ]
$lookup — "JOIN" antar collection (pesanan ↔ produk)JS
db.pesanan.aggregate([
  { $lookup: {
      from:         "produk",        // collection lain
      localField:   "produk_id",     // field di pesanan
      foreignField: "_id",            // field di produk
      as:           "detail_produk"  // hasil gabungan ditaruh di sini
  } }
])
// $lookup ADA, tapi inilah sinyal: kalau kamu sering JOIN,
// mungkin datamu sebenarnya relasional (lihat deck Document DB, bab 03).
◆
Aggregation kuat, tapi tahap pertama sebaiknya $match supaya bisa memanfaatkan index dan menyaring data sedini mungkin. Pipeline yang mulai dengan $group di atas jutaan dokumen akan lambat karena harus memindai semuanya.
Indexing · Kenapa butuh index

Tanpa index, query memindai SEMUA dokumen

Index adalah inti performa. Tanpa index, sebuah query harus membaca setiap dokumen satu per satu (collection scan) untuk mencari yang cocok. Dengan index, MongoDB melompat langsung ke datanya.

◆ Analogi — daftar isi buku

Mencari kata di buku tanpa daftar isi = membalik semua halaman satu per satu (collection scan). Index ibarat indeks di belakang buku: kamu cari kata, ia bilang "halaman 142", kamu loncat ke sana. Cepat — tapi indeks itu sendiri butuh kertas tambahan & harus diperbarui tiap buku berubah.

tanpa indexJS
db.users.find({ kota: "Bandung" })

// MongoDB harus memeriksa
// SEMUA dokumen di koleksi:
COLLSCAN — baca 1.000.000 dokumen 🐢
dengan index di "kota"JS
db.users.createIndex({ kota: 1 })
db.users.find({ kota: "Bandung" })

// loncat langsung ke entri "Bandung":
IXSCAN — baca ~12 dokumen ⚡
◆ Di balik layar

Index MongoDB adalah struktur B-tree terurut yang menyimpan nilai field + pointer ke dokumen. Karena terurut, ia juga mempercepat sort() dan query rentang ($gte, $lt), bukan hanya pencocokan persis.

Indexing · Jenis index

Empat index yang wajib kamu kenal

Jawaban langsung untuk kebutuhan indexing dari contoh kasus: tunggal untuk satu field, compound untuk filter gabungan, multikey untuk array, dan text untuk pencarian kata.

createIndex — empat jenis utamaJS
// 1. SINGLE FIELD — satu field, 1 = naik, -1 = turun
db.users.createIndex({ kota: 1 })

// 2. COMPOUND — beberapa field; URUTAN PENTING (lihat bab berikut)
db.users.createIndex({ kota: 1, "pengalaman.tahun": -1 })
// → mempercepat: find({kota}).sort({"pengalaman.tahun": -1})

// 3. MULTIKEY — otomatis saat field-nya array (mis. skill[])
db.users.createIndex({ skill: 1 })
// → mempercepat: find({ skill: "mongodb" })

// 4. TEXT — pencarian kata di dalam teks (mis. deskripsi produk)
db.produk.createIndex({ nama: "text", deskripsi: "text" })
db.produk.find({ $text: { $search: "kabel usb" } })
// unique

Unique index

createIndex({ email: 1 }, { unique: true }) — menolak nilai duplikat. Inilah cara mengembalikan sebagian "integritas" relasional.

// ttl

TTL index

{ expireAfterSeconds: 3600 } — dokumen otomatis terhapus setelah waktu tertentu. Pas untuk sesi login atau cache.

// partial

Partial index

Hanya meng-index dokumen yang memenuhi syarat (mis. { aktif: true }). Lebih kecil & hemat.

◆
Untuk pencarian teks yang serius (relevansi, typo-tolerant, bahasa Indonesia), $text bawaan MongoDB cukup terbatas — di sinilah Elasticsearch biasanya dipasang berdampingan. Lihat elasticsearch.html.
⚙ Indexing · Verifikasi

explain(): pastikan index benar-benar dipakai

Membuat index tidak menjamin query memakainya. Selalu buktikan dengan explain() — cari IXSCAN (pakai index), bukan COLLSCAN (memindai semua).

explain() — baca rencana eksekusiJS
db.users.find({ kota: "Bandung" }).explain("executionStats")

// yang dicari di output:
//   stage: "IXSCAN"      ✅ pakai index
//   stage: "COLLSCAN"    ❌ memindai semua — perlu index
//   totalDocsExamined ≈ nReturned  → index efisien
◆ Aturan ESR untuk compound index

Urutan field di compound index harus mengikuti pola ESR: Equality dulu (field yang dicocokkan persis, mis. kota), lalu Sort (field untuk pengurutan), terakhir Range (rentang seperti $gte). Salah urutan = index tidak terpakai penuh.

  • Index field yang sering kamu filter & sort — bukan semua field. Index yang tak terpakai hanya membebani tulis.
  • Satu compound index sering mengalahkan banyak index tunggal untuk query yang sama.
  • Cek index yang ada dengan db.users.getIndexes(); hapus yang sia-sia dengan dropIndex().
  • Ingat trade-off: tiap index mempercepat baca tapi memperlambat tulis & memakan disk.
Praktik · Kapan pakai

MongoDB cocok untuk kasus apa

Polanya sama dengan prinsip document DB: data mandiri yang dibaca utuh, skema beragam/berubah, dan butuh skala. Ini contoh nyata dari deck induk.

// e-commerce

Katalog produk

Tiap kategori beda atribut (buku vs elektronik vs baju). Skema fleksibel — tiap produk bawa field sendiri tanpa kolom kosong.

// CMS

Konten & artikel

Satu halaman = satu dokumen (blok konten + metadata + komentar), dibaca utuh saat ditampilkan.

// IoT / log

Event & telemetri

Tulis cepat, skema bebas, skala horizontal lewat sharding. TTL index untuk auto-hapus data lama.

// profil

Profil & CV

One-to-many (pengalaman, pendidikan, skill) yang hampir selalu diambil bersama si user.

// Pakai MongoDB saat…

  • Data = pohon one-to-many yang mandiri.
  • Skema sering berubah / antar item beda bentuk.
  • Butuh skala horizontal & tulis cepat.
  • Ingin objek kode ≈ dokumen DB.

// Pikir ulang saat…

  • Banyak relasi many-to-many & JOIN.
  • Butuh transaksi rumit lintas banyak entitas.
  • Laporan/analitik lintas-tabel jadi kebutuhan utama.
  • Pencarian teks canggih jadi fitur inti (→ Elasticsearch).
◆ Harga · Trade-off

Yang kamu dapat & yang kamu jaga

MongoDB modern sudah jauh lebih matang (transaksi multi-dokumen, agregasi kuat), tapi prinsipnya tetap: ia bersinar untuk dokumen mandiri, bukan untuk relasi padat.

// Yang kamu dapat

  • Baca dokumen utuh cepat (lokalitas).
  • Skema fleksibel, iterasi kilat.
  • Index kaya: compound, multikey, text, TTL, geo.
  • Skala horizontal mulus (sharding).
  • Aggregation pipeline yang ekspresif.

// Yang harus kamu jaga

  • Many-to-many & JOIN bukan kekuatannya.
  • Duplikasi data → risiko update anomaly.
  • Skema tak dipaksa DB → butuh disiplin (atau JSON Schema validation).
  • Index salah/berlebih → tulis lambat & boros disk.
◆ Tips disiplin skema

Karena MongoDB schema-on-read, banyak tim menambahkan JSON Schema validation di level collection (db.createCollection(..., { validator: ... })) untuk menolak dokumen berbentuk salah — mengembalikan sebagian keamanan relasional tanpa kehilangan fleksibilitas.

Penutup

MongoDB dalam satu tarikan napas

Simpan dokumen apa adanya, cari dengan filter & aggregation, percepat dengan index yang tepat, lalu buktikan dengan explain(). Itu inti yang perlu kamu kuasai.

  • Collection → Document → Field — tabel jadi koleksi dokumen BSON.
  • Query = dokumen filter — find() untuk dasar, aggregate() untuk hitung & gabung.
  • Index = kunci performa — single, compound, multikey, text.
  • Compound ikut aturan ESR — Equality, Sort, Range.
  • Selalu explain() — kejar IXSCAN, hindari COLLSCAN.
  • Pilih dari bentuk data — dokumen mandiri, bukan relasi padat.

Langkah belajar berikutnya

Coba gratis di MongoDB Atlas (cloud) atau jalankan lokal lewat Docker, lalu pakai mongosh / Compass. Buat collection users, masukkan beberapa profil, lalu latih: find() dengan filter array → buat createIndex() → bandingkan explain() sebelum & sesudah index. Itu satu putaran belajar yang lengkap.
