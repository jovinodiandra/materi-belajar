// The Boy Scout Rule — Robert C. Martin

Tinggalin kode lebih bersih daripada pas kamu nemu

Clean Code itu bukan soal cakep-cakepan. Ini soal biaya. Kode dibaca 10× lebih sering daripada ditulis. Tiap kali kamu bikin orang berikutnya mikir lama, kamu lagi bayar bunga atas utang yang nggak pernah kamu pinjam. Deck ini pakai contoh nyata dari codebase wallet-infrastructure — dari yang salah sampai yang benar.

Dibikin buat tim · contoh diambil dari modul core (hexagonal, zero-framework)

◆ Buat apa ini? Kenapa pakai ini?

Given — kode berantakan: nama variabel x, tmp, fungsi 200 baris ngerjain lima hal sekaligus, nggak ada niat yang kebaca dari kodenya sendiri.

When — developer baru (atau kamu sendiri 6 bulan lagi) harus baca kode itu buat nambah fitur atau nge-fix bug.

Then — dia salah paham maksud kode, nebak-nebak, takut ubah karena efek sampingnya nggak jelas — hasilnya bug baru dan waktu debug yang harusnya 10 menit jadi berjam-jam.

→ makanya kita pakai Clean Code.

01
Meaningful Names

Nama harus mengungkap niat

Nama yang bagus langsung jawab tiga hal: kenapa dia ada, dia ngapain, dan cara pakainya gimana. Kalau sebuah nama masih butuh komentar biar kebaca, berarti namanya belum bener.

Analogi

Bayangin rak rempah di dapur tanpa label. Cuma toples bening isi bubuk cokelat. Lada? Kayu manis? Kopi? Kamu mesti buka dan cicipi satu-satu. Variabel bernama d, tmp, data ya kayak toples tanpa label gitu. Kode yang bagus itu dapur yang labelnya rapi.

BankService.javaSMELL
// berapa? milik siapa? satuan apa?
long d = acc.getD();
long m = acc.getM();
if (d >= m1 && d <= m2) {
    process(acc, d);   // "process" — proses apa?
}
// m1/m2 = magic, d = disinformasi (deposit? debt?)
⟶REFACTOR
MasterBank.javaCLEAN
TransactionAmountRange depositRange = bank.depositRange();
long requestedAmount = command.amount();

if (depositRange.contains(requestedAmount)) {
    acceptDeposit(bank, requestedAmount);
}
// niat terbaca tanpa komentar:
// "terima deposit jika dalam rentang yang diizinkan"
Nama menjawab kenapa ada, apa fungsinya, bagaimana dipakai — tanpa perlu komentar. int d;int elapsedDays; Jangan pakai nama yang menyiratkan hal yang keliru atau beda dari kenyataannya. List<Account> accountGroup;Set<Account> accounts; Nama yang gampang di-grep; hindari satu huruf dan angka ajaib. if (s == 7)if (status == ACTIVE) Bisa diucapkan saat diskusi — kalau tak bisa dieja, tak bisa didiskusikan. Date genymdhms;Date generationTimestamp; Jangan kodekan tipe/scope ke dalam nama. Compiler sudah tahu tipenya; saat tipe berubah, prefiks itu jadi basi dan berbohong. String strName; int m_count;String name; int count;
◆ Di codebase ini

Di sini kita nggak pakai UUID mentah atau String buat ID. MasterBankId itu value object. Namanya sendiri udah jelasin apa yang dia pegang, dan compiler bakal nolak kalau kamu ketuker pakai MasterBankId di tempat BankGroupId. Ini ADR-001 (Aggregate ID = value object). Nama yang udah bertipe itu nama yang nggak bisa bohong.

02
Functions

Kecil. Melakukan satu hal. Satu level abstraksi.

Aturan pertama function: harus kecil. Aturan kedua: harus lebih kecil dari itu. Satu function ngerjain SATU hal, ngerjainnya dengan benar, dan cuma itu.

Analogi

Resep yang bagus nggak nulis “buat kue” dalam satu paragraf raksasa. Resepnya dipecah jadi langkah selevel: siapkan adonan → panggang → hias. Tiap langkah punya resep sendiri di level bawahnya. Function itu kayak paragraf — harus kebaca dari atas ke bawah kayak prosa, satu tingkat abstraksi per paragraf.

handler.javaSMELL
void handle(Req r, boolean notify, boolean dryRun) {
  // validasi + bikin id + simpan + kirim email
  if (r.name == null) throw ...;     // level: validasi
  var id = UUID.randomUUID();         // level: infra
  db.exec("INSERT ...");              // level: SQL
  if (notify && !dryRun) smtp.send(...); // flag args!
}
// 4 hal, 3 level abstraksi, 2 boolean flag
⟶REFACTOR
CreateBankGroupUseCase.javaCLEAN
@Override
protected CreateBankGroupResult doExecute(CreateBankGroupCommand command) {
  return txRunner.inTransaction(() -> {
    BankGroup group = BankGroup.create(
        new BankGroupId(idGenerator.generate()),
        command.actor().organizationId(),
        new BankName(command.name()),
        clock.now());
    bankGroups.save(group);
    return new CreateBankGroupResult(group.id(), group.name().value());
  });
}
// satu hal: "buat bank group". satu level abstraksi.

Tanda bahaya

  • Lebih dari ~20 baris, atau kamu sampai perlu scroll
  • Argument ke-4 dan seterusnya (idealnya cukup ≤ 2–3)
  • Flag argument (boolean) — tandanya function ngerjain dua hal sekaligus
  • Indentasi bersarang lebih dari 2 level
  • Diam-diam nyimpen side effect di balik nama yang kayak query (cuma nanya)

Yang kita kejar

  • Kebaca top-to-bottom kayak prosa
  • Namanya kata kerja yang jujur (doExecute, save)
  • Command–Query Separation: ubah ATAU jawab, jangan dua-duanya
  • Argument kebanyakan? Bungkus jadi Command object
  • Nggak ada output argument
◆ Di codebase ini

Lihat, argument-nya nggak dilempar satu-satu — semua dibungkus dalam satu CreateBankGroupCommand. Itu jawaban Clean Code buat “argument-nya kebanyakan”: argument object. Terus doExecute dipanggil dari base AuthenticatedUseCase setelah permission dicek — satu function, satu tanggung jawab.

03
Comments

Komentar adalah kegagalan untuk berekspresi dalam kode

Komentar yang bagus itu jarang. Kebanyakan komentar cuma permintaan maaf karena kodenya kurang jelas. Aturannya gampang: jangan komentari kode jelek — tulis ulang aja.

Analogi

Komentar itu kayak deodoran di atas keringat. Kadang perlu. Tapi kalau kamu butuh banyak-banyak, masalahnya bukan kurang deodoran — kamu perlu mandi. Komentar lama-lama basi dan berbohong. Kode selalu jujur karena itu yang beneran dijalanin.

Komentar jelek

  • Cuma ngulang kode: i++; // tambah i
  • Commented-out code (hapus aja! git inget semuanya)
  • Misleading / udah basi
  • Jurnal perubahan di file (itu kerjaan git)
  • Noise: // constructor

Komentar bagus

  • Jelasin kenapa, bukan apa
  • Aturan bisnis yang nggak kelihatan di kode
  • Peringatan konsekuensi
  • Referensi sumber kebenaran (Confluence/ADR)
  • Javadoc pada API publik
TransactionAmountRange.java — komentar yang BENARCLEAN
/**
 * Min/max amount bounds untuk sebuah tipe transaksi pada bank.
 *
 * <p>{@code min == 0 && max == 0} berarti tipe transaksi ini
 * <b>disabled</b> untuk bank tersebut (Confluence 122716163).
 */
public record TransactionAmountRange(long min, long max) {

  // Override AGENT tak boleh lebih longgar dari default COMPANY (ISP-209)
  public boolean withinBounds(TransactionAmountRange company) {
    return this.min >= company.min && this.max <= company.max;
  }
}

Komentar di atas bagus karena nggak ngulang kode. Dia nyambungin ke aturan bisnis (Confluence, tiket ISP-209) yang mustahil kamu tebak cuma dari baca min sama max. Itu pengetahuan yang bakal hilang kalau nggak ditulis. Sisanya, biarin kodenya yang ngomong.

04
Formatting

Format adalah komunikasi, dan komunikasi adalah prioritas

Tim sepakat satu aturan format, lalu semua ikut tooling—bukan selera masing-masing. Yang penting konsisten, bukan rapi versi kamu sendiri.

Analogi · Koran

Artikel koran yang bagus: judul ngasih tahu topiknya, paragraf atas ngasih ringkasan, makin ke bawah makin teknis. File kode juga gitu—konsep penting di atas, detail di bawah. Hal yang nyambung ditaruh berdekatan: baris kosong (vertical openness) misahin antar-konsep, rapat-rapat di dalam satu konsep.

Baris yang berhubungan erat dirapatkan — tanpa komentar atau baris kosong yang menyela. Baris kosong memisahkan konsep yang berbeda, persis seperti jeda antar paragraf dalam tulisan. Fungsi pemanggil diletakkan di atas fungsi yang dipanggilnya — file terbaca mengalir dari atas ke bawah. Deklarasikan variabel sedekat mungkin dengan tempat ia dipakai — bukan menumpuk semuanya di puncak method. Batasi lebar baris (~100–120 kolom) agar tak perlu scroll horizontal; tim menyepakati satu angka dan tooling yang menjaganya.
◆ Di codebase ini

Format itu bukan bahan debat di PR. Kita serahin ke gate otomatis: mvn verify, aturan SonarQube, sama ArchUnit. Manusia ngecek logika, mesin yang jaga format. Gitu caranya Clean Code tetap kepakai di tim 10+ developer tanpa ribut soal gaya kurung kurawal.

05
Objects & Data Structures

Beri tahu, jangan bertanya

Object itu nyembunyiin data dan ngasih perilaku. Data structure kebalikannya: data-nya kebuka, perilakunya nggak ada. Masalahnya muncul kalau kamu campur keduanya. Kamu bikin object anemik yang isinya cuma getter/setter, terus logikanya bocor ke mana-mana.

Analogi · Hukum Demeter

Pas bayar ke kasir, kamu nggak ngerogoh dompet dia, narik laci, terus ngitung kembalian sendiri. Kamu cukup bilang “ini uangnya”, sisanya kasir yang urus. Jangan bicara pada orang asing — a.b().c().d() itu sama aja kayak ngerogoh dompet orang lain.

caller.javaSMELL
// "ask": rogoh isi object, putuskan di luar
long min = bank.getRange().getMin();
long max = bank.getRange().getMax();
if (amount >= min && amount <= max
    && !(min == 0 && max == 0)) {
  ...
}
// aturan "disabled" tersebar di setiap pemanggil
⟶REFACTOR
TransactionAmountRange.javaCLEAN
// "tell": perilaku tinggal di pemilik data
public boolean isDisabled() {
  return min == 0 && max == 0;
}
public boolean contains(long amount) {
  return !isDisabled() && amount >= min && amount <= max;
}
// pemanggil cukup: range.contains(amount)
◆ Di codebase ini

Aturan bisnis “range 0/0 = disabled” cuma hidup di satu tempat: di dalam TransactionAmountRange. Nggak ada pemanggil yang perlu tahu isinya kayak apa di dalam. Itu yang namanya enkapsulasi. Dan itu juga alasan kenapa value object lebih bagus daripada primitive telanjang (primitive obsession itu code smell).

06
Error Handling

Pakai exception, bukan kode-balikan. Jangan pernah return null.

Error handling itu penting, tapi jangan sampai bikin logika utamanya kabur. Begitu kamu return null, kamu lagi nanam ranjau NullPointerException buat orang yang manggil. Begitu kamu nerima null sebagai argumen, kamu lagi ngundang bug.

Analogi

Return code itu kayak pelayan yang naruh nota “pesananmu gagal” diam-diam di tumpukan piring, berharap kamu ngecek. Exception itu pelayan yang dateng dan ngomong langsung ke kamu. Kamu nggak bakal lupa nanganinya tanpa sadar.

legacy.javaSMELL
Bank find(String id) {
  if (id == null) return null;   // null masuk
  Bank b = repo.get(id);
  return b;                       // null keluar
}
// pemanggil:
if (find(x) != null && find(x).isActive()) ... // 💥
// -1 / "ERROR" / null tersebar sebagai sinyal
⟶REFACTOR
MasterBankId.java + repositoryCLEAN
public MasterBankId(UUID value) {
  Objects.requireNonNull(value, "value must not be null");
}
// fail-fast di tepi: null ditolak SEKARANG

Optional<MasterBank> findById(MasterBankId id);
// "tidak ada" diekspresikan oleh tipe, bukan null
bank.findById(id).map(MasterBank::isActive).orElse(false);
◆ Di codebase ini

Dua disiplin: (1) Objects.requireNonNull(...) di compact constructor — null ditolak di perbatasan, bukan dibiarin merembet ke dalam. (2) Error yang nyampe ke HTTP dibungkus jadi RFC 7807 ProblemDetail (ADR-006) — bukan null, bukan stack trace yang bocor, tapi kontrak error yang konsisten dan kebaca sama klien.

07
Boundaries

Jaga perbatasan: kode kita tak boleh tahu detail dunia luar

Tiap hal dari luar — database, jam sistem, generator UUID, SMTP — itu perbatasan. Bungkus di balik port yang kita miliki. Biar domain nggak pernah nyentuh detail framework.

Analogi · Colokan listrik

Alat-alat di rumahmu nggak disolder langsung ke kabel PLN. Ada stop kontak — antarmuka standar. Ganti penyedia listrik, kulkasmu nggak peduli. Port itu stop kontaknya; adapter itu colokan spesifik PLN/TigerBeetle/PostgreSQL. Domain tinggal nancep.

DomainService.javaSMELL
class BankService {
  UUID id = UUID.randomUUID();      // infra di domain
  Instant now = Instant.now();          // jam asli → test rapuh
  conn.prepareStatement("INSERT...");  // JDBC di domain
}
// domain menikah dengan framework. tak bisa diuji
// tanpa DB nyata & tanggal hari ini.
⟶REFACTOR
core/...outport (ports)CLEAN
interface IdGenerator   { UUID generate(); }
interface Clock         { Instant now(); }
interface BankGroupRepository { void save(BankGroup g); }

// domain hanya bergantung pada interface (port):
new BankGroupId(idGenerator.generate());
// di test → fake; di prod → adapter Postgres. Domain tak tahu.
◆ Di codebase ini

Ini jantung arsitektur kita: Hexagonal / Ports & Adapters (ADR-004). core/ itu zero-framework — dilarang import Micronaut, Spring, atau JPA. Larangan UUID.randomUUID() di domain itu ADR-002, dan ArchUnit (ADR-008) yang menjaganya otomatis. Perbatasan bukan cuma niat baik — ada test yang ngecek.

08
Unit Tests

Kode test sama pentingnya dengan kode produksi

Test yang kotor lebih buruk daripada nggak ada test. Test kotor itu lama-lama menua, membusuk, akhirnya kamu buang. Pas dibuang, jaring pengamanmu ikut hilang. Test yang bersih bikin kamu berani ngubah kode.

Analogi · F.I.R.S.T

Fast, Independent, Repeatable, Self-validating, Timely. Anggap test itu jaring pengaman pemain trapeze. Kalau cepat, mandiri, dan jujur, kamu berani melompat alias refactor. Kalau lambat dan saling bergantung, kamu malah takut gerak.

FlakyTest.javaSMELL
@Test void test1() {
  var svc = new BankService(realDb);  // butuh DB
  svc.create("BCA");
  Instant t = Instant.now();         // hasil beda tiap run
  assertTrue(svc.count() > 0);        // bergantung test lain
  // nama "test1"? menguji apa? lambat? flaky.
}
⟶REFACTOR
CreateBankGroupUseCaseTest.javaCLEAN
@Test
void createsGroupInActorOrganizationScope() {
  // Arrange — fake port, jam tetap (deterministik)
  var idGen = FixedIdGenerator.of(GROUP_ID);
  var clock = FixedClock.at(T0);
  var useCase = new CreateBankGroupUseCase(repo, tx, idGen, clock);

  // Act
  var result = useCase.execute(commandFrom(owner));

  // Assert — satu konsep diverifikasi
  assertThat(result.id()).isEqualTo(GROUP_ID);
}
Satu test memverifikasi satu konsep — boleh beberapa assert asalkan menguji satu ide yang sama. assertThat(result.id()).isEqualTo(GROUP_ID); Susun test dalam tiga blok: Arrange (siapkan), Act (jalankan satu aksi), Assert (verifikasi hasilnya). Nama test adalah kalimat spesifikasi perilaku yang dijamin — bukan nomor urut. void test1()void createsGroupInActorOrganizationScope() Unit test pakai fake port (cepat & deterministik). DB nyata hanya untuk integration test (Testcontainers). FixedClock.at(T0); FixedIdGenerator.of(ID);
◆ Di codebase ini

Karena dependensi semuanya lewat port (Bab 07), unit test cukup pakai fake sederhana: cepat dan deterministik. Integration test (Failsafe + Testcontainers) yang ngetes adapter ke PostgreSQL beneran. Gate-nya: JaCoCo ≥ 87% line+branch per modul (ADR-019). Test di sini bukan formalitas, tapi syarat merge.

09
Classes

Satu class, satu alasan untuk berubah

Class itu harus kecil. Tapi ukurannya bukan jumlah baris, melainkan tanggung jawab. Single Responsibility Principle bilang: satu class cuma boleh punya satu alasan untuk berubah. Cohesion tinggi, coupling rendah.

Analogi · Kotak perkakas

Pisau Swiss Army emang keren, tapi tukang kayu beneran pakai perkakas terpisah: satu buat motong, satu buat ngukur. God class itu kayak pisau Swiss Army dengan 40 fungsi. Begitu satu engsel rusak, semuanya kena risiko. Class kecil yang fokus jauh lebih bisa diandalkan.

God class (smell)

  • BankManager: validasi + SQL + email + format + audit
  • Berubah gara-gara banyak alasan beda
  • Banyak field nggak dipakai bareng → cohesion rendah
  • Susah dikasih nama tanpa kata “And” / “Manager” / “Util”

Class kecil & kohesif

  • CreateBankGroupUseCase — satu use case
  • TransactionAmountRange — satu konsep nilai
  • BankGroupRepository — satu peran (port)
  • Namanya nunjukin persis satu tanggung jawab
◆ Di codebase ini

Struktur paket kita memaksa SRP: satu use case = satu class (...application.usecase), satu value object = satu record (...domain), satu port = satu interface (...outport). Class gendut nggak punya tempat buat ngumpet. Open–Closed kita wujudkan lewat port: mau nambah perilaku, bikin adapter baru, jangan ngutak-atik domain.

10
Emergence · Simple Design

Empat aturan desain sederhana

Desain bagus nggak datang dari diagram megah di awal. Dia muncul (emerge) pelan-pelan dari disiplin kecil yang kamu ulang terus. Kent Beck merangkumnya jadi empat aturan, urut sesuai prioritas.

  • 1. Lulus semua test. Sistem yang nggak teruji nggak bisa kamu percaya buat diubah.
  • 2. Tidak ada duplikasi. Duplikasi itu musuh nomor satu. Satu aturan, satu tempat.
  • 3. Ekspresikan niat programmer. Nama jelas, function kecil, struktur yang ngomong sendiri.
  • 4. Minimalkan jumlah class & method. Tapi ini nomor empat, setelah tiga aturan di atas. Jangan kebablasan bikin padat.
Analogi · DRY vs YAGNI

Hapus duplikasi, tapi jangan bikin abstraksi buat sesuatu yang baru muncul sekali. Dua kode yang mirip cuma kebetulan, dan alasan berubahnya beda, itu bukan duplikasi. Kesederhanaan itu soal nyari titik tengah: DRY narik ke satu sisi, YAGNI nahan di sisi lain.

◆ Di codebase ini

Aturan kita jelas soal ini (design-principles-rules.md): jangan ekstrak abstraksi cuma buat 1 occurrence (YAGNI > DRY), jangan hapus duplikasi yang alasan-berubahnya beda (SRP > DRY), jangan bikin extension point sebelum ada konsumen kedua. Yang kita jaga itu kesederhanaan, bukan kepintaran yang dipamerin.

11
Smells & Heuristics

Katalog bau kode — belajar mencium sebelum membusuk

Bab penutup Clean Code itu daftar “bau” kode. Nggak perlu kamu hafal — yang penting hidungmu terlatih. Ini yang paling sering muncul, lengkap sama penawarnya.

G5 · Duplication

Duplikasi

Aturan yang sama nyebar di banyak tempat. Penawar: tarik jadi satu method / value object.

G23 · Magic Number

Angka ajaib

if (s == 3) — 3 itu apa? Penawar: konstanta bernama / enum yang ngejelasin maknanya.

F1 · Too Many Args

Argumen berlebih

Parameternya lebih dari 3. Penawar: bungkus jadi Command / parameter object.

G15 · Flag Args

Argumen flag

boolean yang ngubah perilaku. Penawar: pecah jadi dua method dengan nama yang jelas.

N1 · Bad Names

Nama menyesatkan

d, tmp, data, Manager — nggak ngomong apa-apa. Penawar: nama yang ngungkap niat.

G36 · Demeter

Rantai pemanggilan

a.b().c().d() — merogoh isi orang lain. Penawar: tell-don't-ask, pindahin perilakunya ke pemilik data.

P1 · Primitive Obsession

Obsesi primitif

Pakai String/long buat konsep domain. Penawar: value object bertipe.

C2 · Obsolete Comment

Komentar basi

Komentar yang udah bohong. Penawar: hapus, biarin kodenya yang ngomong.

G14 · Feature Envy

Iri fitur

Method-nya lebih sibuk ngurusin data class lain. Penawar: pindahin ke class itu.

G9 · Dead Code

Kode mati

Nggak pernah dipanggil. Penawar: hapus aja — git yang inget.

T2 · Null Return

Return / pass null

Ranjau NPE buat pemanggil. Penawar: Optional, fail-fast, jangan terima null.

G6 · Wrong Level

Level abstraksi campur

SQL & aturan bisnis nyampur di method yang sama. Penawar: pisahin per level.

12
Penutup · The Craftsman

Bersih itu sebuah praktik, bukan tujuan akhir

Nggak ada yang nulis kode bersih di percobaan pertama. Kamu nulis dulu, baru dibersihin. Jadi profesional itu bukan soal nggak pernah bikin berantakan. Tapi soal nggak pernah ninggalin berantakan itu buat orang lain.

  • Nama mengungkap niat — kalau masih butuh komentar, ganti namanya.
  • Function kecil — satu hal, satu level abstraksi.
  • Komentar jelasin kenapa, bukan apa.
  • Perilaku nempel bersama datanya — tell, don't ask.
  • Null nggak boleh lewat; error itu eksplisit.
  • Perbatasan dijaga port; domain tetap bersih.
  • Test bersih = berani buat ngubah kode.
