// Database — cara menyimpan file & blob dalam skala masif

Simpan miliaran file, tanpa pernah menyentuh filesystem.

Foto profil, video, backup database, file PDF — semuanya butuh disimpan dalam jumlah besar dan diakses cepat dari mana saja. Menaruhnya di kolom database atau di disk satu server terasa masuk akal di awal, tapi cepat runtuh begitu jumlahnya jutaan. Object storage — seperti Amazon S3 dan Google Cloud Storage — lahir untuk soal ini: menyimpan objek (data + metadata) datar di dalam bucket, diakses lewat HTTP API, bukan lewat filesystem biasa. Deck ini buat pemula: dari kenapa ia lahir, konsep inti-nya, trade-off, sampai kapan dipakai di production.

Sakit
Filesystem kewalahan — satu server tak sanggup menyimpan jutaan file besar
Ide
Simpan sebagai objek datar — data + metadata + key unik, lewat HTTP API
Untung
Skala nyaris tak terbatas — murah, sangat durabel, terdistribusi otomatis
Batas
Bukan pengganti database — lambat untuk update sebagian & query kompleks
Pakai
Saat data = blob mandiri — gambar, video, dokumen, backup

◆ Buat apa ini? Kenapa pakai ini?

Given — file profil & video pengguna disimpan sebagai kolom BLOB di database relasional, atau ditaruh di disk satu server aplikasi.

When — jumlah pengguna naik ke jutaan: database membengkak jadi puluhan terabyte, proses backup & replikasi jadi berjam-jam, dan disk server aplikasi itu penuh atau servernya mati.

Then — restore database jadi lambat sekali karena ukurannya raksasa, file yang cuma ada di satu mesin hilang total saat server itu down, dan menambah kapasitas berarti beli disk lebih besar (bukan tinggal skala horizontal).

→ makanya kita pakai Object Storage.

Akar masalah · Skala file yang tak masuk akal untuk database biasa

Jutaan file besar tak muat di satu server

Bayangkan aplikasimu punya satu juta pengguna, masing-masing mengunggah foto profil & beberapa video. Itu bisa puluhan terabyte data biner. Menaruhnya sebagai kolom BLOB di database relasional membuat backup & replikasi jadi berat. Menaruhnya di disk satu server aplikasi berarti kapasitasnya terbatas pada disk itu — dan kalau server itu mati, filenya ikut hilang.

◆ Analogi — gudang logistik raksasa dengan barcode

Menyimpan file di server aplikasi ibarat menumpuk barang di lemari kantor sendiri: cepat penuh, rawan hilang kalau kantornya kebakaran, dan cuma bisa diambil orang yang datang ke kantor itu. Object storage ibarat gudang logistik raksasa — dirancang khusus menampung apa saja dalam jumlah nyaris tak terbatas. Tiap barang yang masuk diberi nomor barcode unik (key). Kamu tidak perlu tahu barang itu ada di rak fisik mana; cukup sebut barcode-nya, gudang akan mengurus penyimpanan, penggandaan, dan pengambilannya — dari cabang gudang mana pun di dunia.

Karena itulah object storage dirancang berbeda dari awal: bukan sebagai perluasan filesystem satu server, tapi sebagai layanan terdistribusi yang otomatis mereplikasi data ke banyak mesin & lokasi, diakses lewat jaringan (HTTP), dan diskalakan secara horizontal — tambah kapasitas cukup dengan menambah mesin di baliknya, tanpa aplikasi kamu perlu tahu detailnya.

Konsep inti · Object storage

Objek = data + metadata + key unik, bukan folder

Object storage menyimpan tiap file sebagai objek di dalam wadah bernama bucket. Satu objek terdiri dari tiga bagian: data (isi file dalam bytes mentah), metadata (content-type, ukuran, tag custom), dan key — string unik yang jadi satu-satunya cara mengenali objek itu di dalam bucket. Semua diakses lewat HTTP API (mis. PUT, GET, DELETE), bukan dengan memasang bucket sebagai drive di sistem operasi.

Objek disimpan datar sebagai pasangan key-value di dalam bucket — bukan struktur direktori bertingkat seperti filesystem tradisional — sehingga sistemnya bisa didistribusikan & diskalakan secara horizontal dengan sangat sederhana.

— parafrasa dari konsep desain object storage, dokumentasi Amazon S3
upload & baca objek lewat AWS CLIbash
# upload file lokal ke bucket, disimpan dengan key "images/avatar-budi.jpg"
aws s3 cp ./avatar.jpg s3://materi-belajar-bucket/images/avatar-budi.jpg

# lihat daftar objek dengan prefix "images/" (bukan folder sungguhan)
aws s3 ls s3://materi-belajar-bucket/images/

# ambil objek lewat REST API biasa, kalau bucket/objek diatur public-read
curl -O https://materi-belajar-bucket.s3.amazonaws.com/images/avatar-budi.jpg

# hapus objek — cukup rujuk key-nya, tidak perlu tahu lokasi fisik data
aws s3 rm s3://materi-belajar-bucket/images/avatar-budi.jpg
◆ Padanan istilah filesystem ↔ object storage
Nama file→ Key (string unik dalam satu bucket)
Folder→ Prefix (bagian dari key, cuma ilusi tampilan)
Isi file→ Data / value (bytes mentah objek)
Atribut→ Metadata (content-type, ukuran, tag custom)

Console yang menampilkan images/2024/avatar.jpg seperti struktur folder bertingkat sebenarnya cuma mengelompokkan key berdasarkan karakter / — di balik layar, tidak ada direktori fisik sama sekali. Semua objek berada datar dalam satu bucket.

Perbandingan · Tiga jenis storage yang sering tertukar

Object, file, & block storage itu tiga hal berbeda

Orang sering menyamakan "storage" begitu saja, padahal ketiganya dirancang untuk kebutuhan berbeda. Bedanya ada di bagaimana data diakses, bukan sekadar di mana data itu disimpan.

◆ Object vs File vs Block storage
Block→ Volume mentah spt hard disk virtual, dipasang di 1 server, dibaca lewat OS filesystem — cocok utk database & OS (mis. AWS EBS)
File→ Filesystem bersama spt NFS, punya struktur direktori sungguhan, dipasang & diakses banyak server sekaligus
Object→ Bucket datar berisi key-value, diakses via HTTP API, skala nyaris tak terbatas — bukan utk update sebagian isi objek

Semakin ke atas (block), semakin cepat & mirip disk lokal tapi semakin terbatas skalanya. Semakin ke bawah (object), semakin murah & terskala tapi semakin jauh dari semantik filesystem tradisional — kamu tidak bisa seek() atau menimpa sebagian byte di tengah objek seperti mengubah sebagian file di disk.

Praktiknya, ketiganya sering dipakai bersamaan dalam satu sistem: block storage untuk disk database, file storage untuk berbagi file antar service lama yang butuh mount NFS, dan object storage untuk aset besar seperti gambar, video, & backup.

◆ Praktik baik · Supaya tidak bocor biaya & performa

Best practice memakai object storage

Object storage mudah dipakai, tapi ada beberapa kebiasaan yang membedakan setup asal-jalan dari setup yang siap production.

  • Taruh CDN di depan bucket untuk asset publik (gambar, video, file statis) — CDN meng-cache dekat pengguna & mengurangi beban langsung ke bucket, sekaligus mempercepat akses.
  • Atur lifecycle policy supaya objek yang jarang diakses otomatis pindah ke storage class lebih murah (mis. Glacier, Coldline), atau otomatis terhapus setelah periode tertentu — jangan biarkan bucket menumpuk data selamanya secara manual.
  • Jangan simpan data yang butuh update sering/parsial. Object storage optimal untuk pola write-once-read-many, bukan untuk field yang berubah tiap detik — itu tugas database.
  • Desain key naming yang tidak jadi hot spot — pada beban tulis sangat tinggi, key yang berurutan (mis. timestamp berurutan di depan) bisa membebani satu partisi; tambahkan prefix acak kalau throughput-nya besar.
  • Jangan expose bucket publik sembarangan. Atur IAM/bucket policy secara eksplisit & pakai signed URL untuk akses privat yang sementara, alih-alih membuka seluruh bucket ke publik.
  • Aktifkan versioning untuk data penting, supaya overwrite atau delete yang tidak sengaja masih bisa dipulihkan.
◆ Roadmap · Belajar object storage bertahap

Tier belajar: dari upload file sampai skala global

Tidak perlu langsung paham semuanya. Ini jalur bertahap dari sekadar bisa upload file sampai mendesain sistem object storage untuk aplikasi berskala besar.

🌱 Beginner

Upload & Download File Dasar

Fokus ke operasi dasar objek — upload, download, list, hapus — lewat console, CLI, atau SDK.

  • Buat bucket & upload file lewat AWS CLI/console.
  • Pahami perbedaan bucket, key, dan public vs private access.
  • Coba generate signed URL sederhana untuk file privat.
⚙ Middle

Desain Key & Lifecycle Aplikasi Nyata

Mulai merancang skema key naming yang scalable & mengatur automasi lifecycle untuk aplikasi sungguhan.

  • Rancang naming convention key (mis. per-tenant, per-tanggal).
  • Atur lifecycle policy untuk pindah tier / auto-hapus objek lama.
  • Integrasikan CDN di depan bucket untuk asset publik.
🚀 Advance

Multipart, Tiering & Konsistensi Global

Menangani file raksasa dan distribusi data lintas region tanpa mengorbankan durabilitas.

  • Implementasi multipart upload untuk file besar (video, backup).
  • Desain strategi cross-region replication & storage tiering otomatis.
  • Pahami trade-off konsistensi (eventual vs strong) di skala global.
◆ Harga · Tidak ada makan siang gratis

Trade-off: murah & tak terbatas, tapi bukan database

Object storage sangat murah & durabel, tapi itu bukan berarti ia bisa menggantikan semua jenis storage lain. Ia sengaja mengorbankan sejumlah kemampuan demi bisa diskalakan sesederhana mungkin.

// Yang kamu dapat

  • Sangat murah per GB dibanding block/file storage.
  • Durabilitas tinggi — replikasi otomatis lintas mesin/zona/region.
  • Skala nyaris tak terbatas, tanpa perlu provisioning kapasitas manual.
  • Diakses dari mana saja lewat HTTP, tanpa mengurus server file sendiri.

// Yang kamu korbankan

  • Bukan pengganti database — tak ada query kompleks, index, atau JOIN.
  • Tidak cocok untuk data yang sering di-update sebagian isinya.
  • Latency lebih tinggi dibanding block storage yang menempel lokal.
  • Sebagian layanan awalnya memilih model konsistensi eventually consistent.

Sistem penyimpanan terdistribusi skala besar sering harus memilih antara konsistensi ketat dan ketersediaan tinggi — dan banyak layanan object storage pada awalnya memilih model "eventually consistent", supaya data tetap bisa diakses meski sebagian infrastrukturnya sedang bermasalah.

— parafrasa dari Werner Vogels (CTO Amazon), "Eventually Consistent"
◆ Catatan

Model konsistensi terus membaik seiring waktu — banyak layanan object storage populer sekarang menawarkan strong read-after-write consistency untuk operasi dasar. Tapi arsitektur intinya tetap sama: dioptimalkan untuk skala & durabilitas, bukan untuk pola akses seperti database transaksional.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai object storage

Aturan praktisnya: kalau data kamu adalah blob mandiri yang jarang berubah dan cuma butuh ambil-taruh, pilih object storage. Kalau butuh query, update sebagian, atau latency sangat rendah, itu tugas alat lain.

// Pakai object storage saat…

  • Menyimpan file besar/blob: gambar, video, dokumen, backup.
  • Pola aksesnya write-once-read-many.
  • Butuh distribusi global & durabilitas tinggi.
  • Menaruh asset statis di depan CDN.
  • Backup & arsip jangka panjang.

// Jangan, pakai alat lain saat…

  • Butuh query/transaksi kompleks → pakai database.
  • Data berubah sangat sering/parsial → pakai database.
  • Butuh latency setara disk lokal → pakai block storage (mis. EBS).
  • Butuh struktur direktori asli & semantik POSIX → pakai file storage/NFS.
◆ Pertanyaan penentu

Tanyakan: "Apakah ini blob mandiri yang jarang berubah, dan aku cuma butuh ambil-taruh (GET/PUT) lewat HTTP?" Kalau ya → object storage. Kalau kamu butuh mengubah sebagian isi file berulang kali per detik, atau butuh JOIN/query kompleks lintas data → itu tugas database atau block storage, bukan object storage.

Studi kasus · Di dunia nyata

Object storage di sistem production nyata

Empat pola nyata di mana object storage jadi lapisan penyimpanan inti — perhatikan benang merahnya: data berupa blob mandiri, dibaca apa adanya, dalam volume yang terus tumbuh.

// streaming media

Netflix menyimpan aset media di S3

Netflix menaruh master file video, gambar, dan aset produksi di Amazon S3 sebagai lapisan penyimpanan utamanya, lalu mendistribusikannya lewat jaringan CDN ke seluruh dunia — S3 dipilih karena durabilitasnya & kemampuannya menampung volume data sangat besar tanpa harus mengurus infrastruktur storage sendiri.

// self-built storage

Dropbox membangun "Magic Pocket"

Dropbox awalnya memakai S3, tapi seiring skalanya tumbuh ke miliaran file, mereka membangun sistem object storage sendiri bernama Magic Pocket agar bisa mengontrol biaya & infrastruktur secara langsung — bukti bahwa prinsip object storage (key-value datar, replikasi, skala horizontal) bisa diterapkan sendiri, bukan cuma lewat cloud publik.

// aplikasi modern

Upload pengguna di hampir semua aplikasi

Foto profil, dokumen, lampiran chat, hasil ekspor laporan — hampir semua aplikasi modern menaruh file yang diunggah pengguna langsung ke S3/GCS, bukan di disk server aplikasi, supaya server aplikasi tetap stateless & mudah diskalakan horizontal.

// data lake & arsip

Fondasi data lake & backup jangka panjang

Object storage kerap jadi lapisan penyimpanan dasar untuk data lake — data mentah yang nanti dianalisis pakai tool query terpisah — serta tujuan backup/arsip, karena biaya per GB yang rendah & tersedianya storage tier dingin untuk data yang jarang diakses.

◆ Benang merahnya

Di semua kasus di atas, datanya adalah blob mandiri — bukan baris yang perlu di-JOIN — dan volumenya terus tumbuh dari waktu ke waktu. Begitu kebutuhan bergeser ke query terstruktur atau update sebagian data berulang kali, tim biasanya menambah database atau cache di sampingnya, bukan memaksakan object storage untuk peran itu.

⚙ Ekosistem · Alat yang dipakai

Tools object storage

Sebagai pemula, cukup kenali nama populernya dulu. Amazon S3 adalah titik awal paling umum karena dokumentasinya luas & API-nya jadi standar de-facto yang ditiru layanan lain.

// paling populer

Amazon S3

Object storage paling banyak dipakai di industri. API-nya (S3 API) jadi standar de-facto yang ditiru banyak layanan lain, termasuk yang self-hosted.

// google cloud

Google Cloud Storage

Setara S3 di ekosistem Google Cloud. Terintegrasi rapi dengan BigQuery & tool data lain di GCP, dengan pilihan storage class serupa (standard, nearline, coldline, archive).

// microsoft azure

Azure Blob Storage

Layanan object storage di Microsoft Azure. Sering jadi pilihan default kalau stack aplikasi kamu sudah banyak berjalan di Azure.

// self-hosted

MinIO

Object storage open-source yang kompatibel dengan S3 API, bisa dijalankan sendiri di server/on-premise. Cocok untuk lingkungan yang tidak boleh atau tidak mau pakai cloud publik.

◆ Tips pemula

Karena API S3 sudah jadi standar de-facto, banyak SDK & tool (termasuk MinIO) dibuat kompatibel dengannya. Belajar S3 API dengan baik berarti skill itu ikut terpakai di hampir semua layanan object storage lain.

Penutup

Gudang raksasa untuk blob, bukan pengganti database

Object storage lahir dari kebutuhan menyimpan file besar dalam jumlah masif — dengan cara yang murah, sangat durabel, dan mudah diskalakan. Ia bersinar untuk blob mandiri, dan tersandung saat dipaksa berperan seperti database.

  • Objek = data + metadata + key — disimpan datar di dalam bucket, bukan folder sungguhan.
  • Diakses lewat HTTP API — PUT/GET/DELETE, bukan mounting filesystem.
  • Beda dari file & block storage — object storage bukan pengganti keduanya.
  • Murah & sangat durabel — cocok untuk skala yang terus tumbuh.
  • Bukan pengganti database — hindari data yang sering di-update sebagian.
  • CDN & lifecycle policy — dua kebiasaan yang membuat setup siap production.

Aturan emasnya

Tanya: "Apakah ini blob mandiri yang jarang berubah, dan aku cuma butuh ambil-taruh lewat HTTP?" Kalau ya, object storage memberimu skala & durabilitas tanpa harus mengurus server file sendiri. Kalau datamu butuh diperbarui sebagian berulang kali atau butuh query kompleks, itu tugas database — pilih alat sesuai bentuk & pola akses datanya, bukan karena ingin satu alat untuk semua.
