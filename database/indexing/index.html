// Database — kenapa query yang sama bisa 1000× lebih cepat

Database itu seperti buku. Indeks bikin kamu loncat, bukan baca semua.

Pernah lihat query yang awalnya kilat, lalu makin lama makin lemot seiring data membesar? Hampir selalu biang keroknya satu: tidak ada indeks. Tanpa indeks, database membaca seluruh tabel baris demi baris hanya untuk menemukan satu data. Dengan indeks yang tepat, dia langsung loncat ke tempatnya. Deck ini buat pemula: dari kenapa indeks dibutuhkan, cara kerjanya, sampai kasus nyata dan jebakannya — diselingi kalimat dari buku-buku rujukan.

Masalah
Full table scan — baca semua baris demi cari satu
Ide
Index = papan petunjuk — struktur terurut untuk loncat cepat
Mesin
B-Tree — pohon seimbang, cari dalam langkah sedikit
Harga
Write jadi lebih lambat — tiap index harus ikut diperbarui
Seni
Pilih yang tepat — bukan indeks-kan semuanya

◆ Kenapa pakai index?

Given — Tabel orders punya puluhan juta baris, dan endpoint checkout rutin menjalankan WHERE user_id = ? untuk menampilkan riwayat transaksi user.

When — Data terus bertambah tiap hari, tapi query itu tetap harus memeriksa baris satu per satu dari awal tabel karena tidak ada struktur yang bisa langsung "loncat" ke baris yang dicari.

Then — Waktu respons checkout naik linier mengikuti ukuran tabel: awalnya 5ms, lalu ratusan ms, sampai akhirnya timeout saat tabelnya sudah besar — padahal tidak ada bug baru di kode, cuma jumlah datanya yang bertambah.

→ makanya kita pakai index.

Akar masalah · Full table scan

Mencari satu baris di antara sejuta

Bayangkan tabel users dengan satu juta baris. Kamu cari satu orang lewat email-nya. Tanpa indeks, database tidak punya pilihan selain membaca baris satu per satu dari awal sampai ketemu — ini disebut full table scan (di Postgres: Sequential Scan).

◆ Analogi — mencari kata di buku tanpa indeks

Kamu punya buku 1.000 halaman dan ingin tahu di mana kata "fotosintesis" dibahas. Tanpa indeks di belakang buku, kamu harus membaca halaman 1, 2, 3… sampai ketemu. Kalau katanya ada di halaman 947, kamu baru menemukannya nyaris di akhir. Itulah yang database lakukan saat tidak ada indeks — dan ia mengulanginya untuk setiap pencarian.

tanpa index — database baca semua barisSQL
EXPLAIN SELECT * FROM users WHERE email = 'budi@mail.com';

-- hasilnya:
Seq Scan on users  (cost=0.00..18584.00 rows=1)   -- 🐢 baca SEMUA 1.000.000 baris
  Filter: (email = 'budi@mail.com')

Selagi datanya ribuan baris, ini masih terasa cepat dan tidak ada yang sadar. Tapi begitu tabel tumbuh ke jutaan baris, waktu pencarian ikut membengkak linier — dua kali data, dua kali lambat. Inilah jebakan klasik: kode yang "baik-baik saja saat demo" tapi melambat pelan-pelan di production seiring data nyata menumpuk.

◆
Gejala khasnya: aplikasi cepat saat baru rilis, lalu makin lemot dari bulan ke bulan tanpa ada perubahan kode. Yang berubah cuma satu: jumlah data. Hampir selalu, obatnya adalah indeks.
Konsep inti · Index

Indeks: papan petunjuk menuju data

Sebuah index adalah struktur tambahan yang database simpan di samping data aslinya, khusus untuk membuat pencarian jadi cepat. Ia tidak mengubah datamu — ia hanya menambahkan "peta" agar database tahu harus melompat ke mana.

“Idenya adalah menyimpan metadata tambahan di samping, yang berfungsi sebagai papan petunjuk dan membantumu menemukan data yang kamu cari.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 3)

Persis seperti indeks di belakang buku: daftar kata yang diurutkan A–Z, masing-masing menunjuk ke nomor halaman. Kamu tidak membaca seluruh buku — kamu buka indeks, temukan katanya, lalu loncat langsung ke halamannya. Membuatnya di database semudah satu baris perintah:

membuat index pada kolom emailSQL
CREATE INDEX idx_users_email ON users (email);

-- query yang sama, sekarang:
Index Scan using idx_users_email  (cost=0.42..8.44 rows=1)  -- ⚡ langsung loncat

// Tanpa index

  • Baca 1.000.000 baris untuk cari 1.
  • Waktu naik seiring data membesar.
  • Seq Scan — kerja sia-sia berulang.

// Dengan index

  • Cukup beberapa langkah untuk sampai.
  • Tetap cepat walau data jutaan.
  • Index Scan — loncat ke sasaran.
Di balik layar · B-Tree

Kenapa indeks bisa secepat itu?

Indeks bukan sekadar daftar berurutan — kalau cuma daftar panjang, mencarinya juga lama. Rahasianya: kebanyakan indeks database disimpan sebagai B-Tree (pohon seimbang). Strukturnya memungkinkan pencarian dalam sangat sedikit langkah, bahkan untuk data raksasa.

◆ Analogi — menebak angka 1–100

Aku memikirkan angka 1–100, kamu harus menebak. Strategi bodoh: tebak 1, 2, 3… (sampai 100 tebakan). Strategi pintar: tebak 50 → "terlalu kecil" → tebak 75 → "terlalu besar" → tebak 62… Tiap tebakan membuang separuh kemungkinan. Hanya butuh ~7 tebakan untuk angka berapa pun. B-Tree bekerja begitu: tiap langkah memangkas ruang pencarian, jadi cari 1 dari 1 juta cukup ~20 langkah.

“Sebuah indeks membuat query menjadi cepat.”

— Markus Winand, Use The Index, Luke!

Karena data di B-Tree tersimpan terurut, indeks tidak cuma jago untuk pencocokan persis (=). Ia juga cepat untuk:

// equality

Pencocokan persis

WHERE email = '...' — loncat langsung ke satu nilai.

// range

Rentang nilai

WHERE umur BETWEEN 20 AND 30 — temukan awal, lalu baca berurutan.

// prefix

Awalan teks

WHERE nama LIKE 'Bud%' — bisa pakai index (tapi '%budi' tidak).

// sort

Pengurutan

ORDER BY pada kolom ber-index sering gratis — datanya sudah urut.

◆ Untuk pemula

Kamu tidak perlu hafal cara kerja B-Tree sampai detail. Cukup ingat dua hal: (1) indeks itu terurut, makanya cocok untuk =, rentang, awalan, dan ORDER BY; (2) karena berbentuk pohon seimbang, mencarinya butuh sangat sedikit langkah berapa pun ukuran datanya.

Level berikutnya · Composite index

Satu indeks untuk beberapa kolom — urutannya penting!

Sering kita menyaring lebih dari satu kolom sekaligus, misalnya WHERE kota = 'Bandung' AND umur = 25. Untuk ini ada composite index (indeks gabungan beberapa kolom). Tapi ada satu aturan yang sering bikin pemula bingung: urutan kolom sangat menentukan.

◆ Analogi — buku telepon (diurutkan nama belakang, lalu nama depan)

Buku telepon diurutkan berdasarkan nama belakang dulu, baru nama depan. Cari "Santoso, Budi"? Gampang — buka ke "Santoso", lalu cari "Budi". Tapi cari semua orang bernama depan "Budi" tanpa tahu nama belakangnya? Buku telepon tidak membantu sama sekali — kamu harus baca semua halaman. Composite index persis begitu: urut dari kolom pertama, lalu kolom kedua.

composite index (kota, umur) — aturan "prefix kiri"SQL
CREATE INDEX idx_kota_umur ON users (kota, umur);

WHERE kota = 'Bandung' AND umur = 25   -- ✅ pakai index penuh
WHERE kota = 'Bandung'                 -- ✅ pakai index (kolom pertama)
WHERE umur = 25                        -- ❌ index TIDAK terpakai (lewati kolom pertama)
◆ Aturan praktis

Index (A, B) berguna untuk query yang menyaring A, atau A dan B — tapi tidak untuk yang hanya menyaring B. Ini disebut aturan leftmost prefix. Maka taruh kolom yang paling sering & paling selektif di depan.

Aturan ini juga alasan kenapa kamu tidak perlu bikin indeks terpisah untuk (kota) kalau sudah punya (kota, umur) — yang gabungan sudah mencakup pencarian per kota saja.

◆ Harga · Tidak ada makan siang gratis

Indeks mempercepat baca, tapi memperlambat tulis

Kalau indeks sehebat itu, kenapa database tidak meng-indeks semua kolom otomatis? Karena indeks ada harganya. Tiap kali kamu INSERT, UPDATE, atau DELETE, semua indeks pada tabel itu juga harus diperbarui supaya tetap akurat.

“Indeks yang dipilih dengan baik mempercepat query baca, tetapi setiap indeks memperlambat penulisan.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 3)
◆ Analogi — indeks buku yang harus selalu akurat

Indeks di belakang buku mempercepat pembaca. Tapi setiap kali penulis menyisipkan paragraf baru di tengah, semua nomor halaman di indeks bisa bergeser dan harus diperbaiki. Makin banyak indeks (indeks istilah, indeks nama, indeks gambar…), makin berat pekerjaan tiap kali bukunya diubah. Begitu juga tabel: tiap tulis = perbarui semua indeksnya.

// Yang indeks berikan

  • Query SELECT jauh lebih cepat.
  • ORDER BY & JOIN lebih ringan.
  • Bisa menjamin keunikan (UNIQUE).

// Yang indeks minta

  • INSERT/UPDATE/DELETE lebih lambat.
  • Memakan ruang disk tambahan.
  • Indeks tak terpakai = beban murni.

Inilah trade-off inti penyimpanan data: kamu menukar kecepatan tulis demi kecepatan baca. Untuk aplikasi yang lebih sering membaca daripada menulis (kebanyakan aplikasi web), pertukaran ini hampir selalu sepadan — asalkan indeksnya memang dipakai.

Kasus nyata · Membaca rencana query

Dari 2 detik jadi 2 milidetik

Skenario yang sering terjadi: halaman dashboard tiba-tiba lambat. Pelan-pelan kamu temukan satu query yang makan 2 detik. Cara membuktikan penyebab & solusinya bukan menebak — tapi pakai EXPLAIN ANALYZE, perintah yang menunjukkan bagaimana database menjalankan query-mu.

SEBELUM — tanpa indexSQL
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id = 42;

Seq Scan on orders
  rows=2.000.000
  actual time=1985 ms   🐢
SESUDAH — + indexSQL
CREATE INDEX idx_orders_cust
  ON orders (customer_id);

Index Scan using idx_orders_cust
  rows=18
  actual time=0.2 ms   ⚡
◆ Yang perlu dilihat di EXPLAIN

"Seq Scan" pada tabel besar = sinyal merah (database baca semua). "Index Scan" = indeks dipakai. Bandingkan rows yang dibaca vs. yang dikembalikan — kalau baca 2 juta untuk hasilkan 18, ada indeks yang hilang. Dan selalu lihat actual time, bukan tebakan.

“Aturan pertama optimasi: jangan lakukan. Aturan kedua (khusus ahli): jangan lakukan dulu — ukur terlebih dahulu.”

— prinsip umum performa, sejalan dengan Donald Knuth
◆ Peta · Tidak cuma satu macam

Jenis-jenis index yang berguna diketahui

B-Tree adalah indeks serba-guna dan yang paling sering kamu pakai. Tapi ada beberapa jenis lain yang berguna untuk kebutuhan khusus. Sebagai pemula, cukup kenali namanya dan kapan kira-kira dipakai.

// B-Tree

Serba-guna (default)

Untuk =, rentang, awalan, ORDER BY. 90% kebutuhan terjawab di sini.

// UNIQUE

Unik

Mempercepat sekaligus menjamin tak ada nilai kembar (mis. email, username).

// Composite

Gabungan kolom

Beberapa kolom dalam satu index. Ingat aturan urutan (leftmost prefix).

// Partial

Sebagian baris

Index hanya untuk baris tertentu, mis. WHERE status = 'aktif'. Lebih kecil & cepat.

// Covering

Mencakup kolom hasil

Index memuat semua kolom yang dibutuhkan query → DB tak perlu sentuh tabel sama sekali.

// Hash

Hash

Sangat cepat untuk = persis, tapi tidak untuk rentang atau urutan.

// GIN / Full-text

Pencarian teks & JSON

Untuk cari kata di dalam dokumen teks atau di dalam kolom JSON/array.

// Spatial

Geospasial

Untuk data lokasi/peta (mis. "restoran dalam radius 2 km"). Contoh: R-Tree / GiST.

◆
Jangan kewalahan dengan daftar ini. Mulai dari B-Tree dan UNIQUE — itu sudah menyelesaikan mayoritas kasus. Jenis lain dipelajari saat kamu benar-benar menemui masalahnya, bukan dihafal di depan.
× Realita · Jebakan umum

Kesalahan indeks yang sering dilakukan pemula

Indeks ampuh, tapi gampang disalahgunakan. Lebih banyak indeks bukan berarti lebih cepat — sering malah sebaliknya. Ini jebakan yang paling sering ditemui.

// over-indexing

Indeks-kan semuanya

Tiap indeks memperlambat tulis & makan disk. Indeks yang tak pernah dipakai = beban murni tanpa manfaat.

// low selectivity

Kolom bernilai sedikit

Index pada kolom seperti jenis_kelamin (cuma 2 nilai) hampir percuma — separuh tabel tetap kena. Index berguna saat nilainya beragam.

// function on column

Fungsi membungkus kolom

WHERE LOWER(email) = '...' membuat index biasa pada email tidak terpakai. Solusinya index ekspresi, atau simpan datanya sudah ternormalisasi.

// leading wildcard

LIKE '%kata'

Awalan bebas ('%budi') tak bisa pakai B-Tree. Hanya 'budi%' (awalan tetap) yang bisa.

// duplikat

Index tumpang tindih

Punya (kota, umur) dan (kota) terpisah = mubazir; yang gabungan sudah mencakup.

// menebak

Optimasi tanpa mengukur

Menambah index berdasar firasat, bukan data EXPLAIN. Sering salah sasaran & menambah beban sia-sia.

“Optimasi prematur adalah akar dari segala keburukan.”

— Donald Knuth

Maksudnya bukan "jangan pernah pakai indeks", tapi: tambahkan indeks karena ada masalah nyata yang terukur (query lambat yang kamu lihat di EXPLAIN), bukan karena menebak-nebak. Ukur dulu, baru indeks.

Penutup

Indeks: loncat, jangan baca semua

Indeks adalah cara paling ampuh dan paling sering dipakai untuk membuat database cepat. Konsepnya sesederhana indeks di belakang buku — tapi dampaknya bisa mengubah query 2 detik jadi 2 milidetik.

  • Tanpa index — database baca seluruh tabel (full scan); lambat saat data besar.
  • Index = papan petunjuk — struktur terurut untuk loncat ke data.
  • B-Tree — pohon seimbang; cari 1 dari sejuta cukup ~20 langkah.
  • Composite — urutan kolom penting; pakai aturan leftmost prefix.
  • Ada harganya — mempercepat baca, memperlambat tulis & makan disk.
  • Ukur dengan EXPLAIN — tambah index karena bukti, bukan firasat.

Aturan emasnya

Indeks-kan kolom yang sering kamu cari dan yang nilainya beragam — terutama kolom di WHERE, JOIN, dan ORDER BY. Jangan indeks-kan semuanya: tiap indeks adalah janji yang harus database tepati di setiap penulisan. Mulai dari B-Tree dan UNIQUE, buktikan dampaknya lewat EXPLAIN, dan biarkan masalah nyata yang memandu indeks berikutnya.
