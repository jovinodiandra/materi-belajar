// Database — saat sebagian operasi berhasil, sebagian gagal, siapa yang bereskan?

Semua berhasil, atau tidak sama sekali.

Bayangkan transfer saldo bank: uang dikurangi dari rekeningmu, lalu ditambahkan ke rekening tujuan. Dua langkah, satu maksud. Tapi kalau server crash tepat di antara keduanya — uangmu hilang, tidak pernah sampai ke mana-mana. Transaksi database adalah jawaban untuk masalah ini: membungkus beberapa operasi baca/tulis jadi satu unit yang tak bisa dipecah. Deck ini buat pemula: dari kenapa transaksi lahir, bedah ACID satu-satu, sampai kapan kamu benar-benar butuh jaminan ini — diselingi kalimat dari buku & paper rujukan.

◆ Buat apa ini? Kenapa pakai ini?

Given — aplikasi transfer saldo menjalankan dua UPDATE terpisah (kurangi saldo Budi, lalu tambah saldo Sari) langsung ke database, tanpa pembungkus apa pun.

When — koneksi ke database putus, server crash, atau transaksi lain ikut membaca data tepat di celah antara UPDATE pertama dan kedua.

Then — saldo Budi sudah terlanjur berkurang secara permanen, tapi saldo Sari tidak pernah bertambah; uang "melayang" tanpa jejak, dan tidak ada mekanisme otomatis untuk membatalkan langkah yang sudah terlanjur jalan.

→ makanya kita pakai Transactions & ACID.

Akar masalah · Kegagalan di tengah jalan

Kalau aplikasi crash di tengah, siapa yang bereskan?

Bayangkan Budi mentransfer Rp500.000 ke Sari. Secara logika, prosesnya dua langkah: kurangi saldo Budi, lalu tambah saldo Sari. Kalau kamu menulis dua langkah ini sebagai dua perintah SQL terpisah tanpa pembungkus apa pun, ada jendela waktu di antara keduanya — dan di dunia nyata, server bisa crash, koneksi bisa putus, atau proses lain bisa menyela tepat di celah itu.

◆ Analogi — mengirim uang lewat dua kurir terpisah

Bayangkan kamu mengirim uang tunai lewat dua kurir berbeda: kurir pertama mengambil uang dari brankasmu, kurir kedua mengantarkannya ke brankas Sari. Kalau kurir pertama sudah jalan tapi kurir kedua ketiduran di jalan — uangmu melayang di udara, tidak ada di brankasmu, tidak juga di brankas Sari. Transaksi database adalah cara memastikan satu kurir yang membawa kedua tugas itu sekaligus: kalau ia gagal di tengah jalan, seluruh pekerjaannya dibatalkan dan uang kembali utuh ke brankas asal.

“Transaksi adalah cara aplikasi mengelompokkan beberapa operasi baca dan tulis menjadi satu unit logis — sehingga aplikasi tidak perlu menangani sendiri semua kemungkinan error yang bisa muncul di tengah jalan.”

— parafrasa dari Martin Kleppmann, Designing Data-Intensive Applications, Bab 7 “Transactions”

Tanpa transaksi, tanggung jawab menangani partial failure — kegagalan yang cuma menyentuh sebagian operasi — jatuh ke pundak kode aplikasi. Setiap developer harus mengingat untuk menulis logika pembatalan manual di setiap tempat yang melakukan multi-step write. Sekali saja lupa, atau ada bug di jalur error-handling itu sendiri, data jadi tidak konsisten. Transaksi memindahkan beban ini ke database: kamu cukup bilang BEGIN, lakukan operasinya, lalu COMMIT — database yang menjamin semua-atau-tidak-sama-sekali.

Konsep inti · Empat jaminan dalam satu kata

ACID: Atomicity, Consistency, Isolation, Durability

ACID bukan fitur satu produk — ia akronim empat properti yang idealnya dipenuhi sebuah transaksi. Namanya diciptakan sebagai istilah baku di dunia database sejak awal 1980-an.

“Konsistensi transaksi harus dijamin oleh empat sifat: Atomicity, Consistency, Isolation, dan Durability.”

— parafrasa dari Theo Härder & Andreas Reuter (1983), Principles of Transaction-Oriented Database Recovery — paper asal akronim ACID
// A

Atomicity

Semua operasi dalam transaksi dianggap satu unit tak terbagi. Kalau satu langkah gagal, seluruh transaksi dibatalkan (ROLLBACK) — bukan setengah-setengah. "Atomic" di sini bukan soal konkurensi, tapi soal tidak bisa dipecah.

// C

Consistency

Transaksi membawa database dari satu state valid ke state valid lain, sesuai aturan yang kamu definisikan — constraint, foreign key, invariant aplikasi (mis. total saldo semua akun harus tetap sama). Ini tanggung jawab bersama aplikasi & database.

// I

Isolation

Transaksi yang berjalan bersamaan tidak saling mengintip state setengah-jadi milik satu sama lain. Seolah-olah tiap transaksi berjalan sendirian, meski sebenarnya dieksekusi paralel demi performa.

// D

Durability

Begitu transaksi COMMIT, perubahannya permanen — bertahan walau server mati listrik sedetik kemudian. Biasanya dijamin lewat write-ahead log yang ditulis ke disk sebelum transaksi dianggap sukses.

transfer_saldo.sql — transaksi bank yang validSQL
BEGIN;

  -- kurangi saldo Budi
  UPDATE accounts
  SET balance = balance - 500000
  WHERE id = 'A001';

  -- tambah saldo Sari
  UPDATE accounts
  SET balance = balance + 500000
  WHERE id = 'B002';

  -- pastikan tidak ada saldo minus (aturan Consistency)
  -- kalau constraint CHECK (balance >= 0) dilanggar, DB otomatis batalkan

COMMIT;
-- kalau semua langkah sukses: perubahan permanen (Durability)
-- kalau ada error di tengah, jalankan ROLLBACK; sebagai gantinya

Perhatikan: BEGIN membuka transaksi, dua UPDATE di dalamnya diperlakukan sebagai satu paket (Atomicity), constraint database menjaga saldo tidak pernah minus (Consistency), transaksi lain yang membaca saldo Budi/Sari di saat bersamaan tidak akan melihat state "sudah dikurangi tapi belum ditambah" (Isolation), dan begitu COMMIT dieksekusi, perubahan itu selamat walau listrik padam sedetik kemudian (Durability).

Studi perbandingan · Partial failure

Tanpa transaksi vs dengan transaksi, saat error terjadi

Bandingkan dua versi kode transfer saldo yang sama, tapi satu tanpa pembungkus transaksi dan satu dengan. Bayangkan di kedua kasus, koneksi ke database putus tepat setelah langkah pertama.

tanpa transaksi — dua UPDATE lepasSQL
UPDATE accounts SET balance = balance - 500000
WHERE id = 'A001';
-- 💥 koneksi putus di sini

-- baris di bawah TIDAK PERNAH dieksekusi:
UPDATE accounts SET balance = balance + 500000
WHERE id = 'B002';

-- hasil: saldo Budi berkurang Rp500rb,
-- saldo Sari TIDAK bertambah. Uang hilang.
dengan transaksi — dibungkus BEGIN/COMMITSQL
BEGIN;
  UPDATE accounts SET balance = balance - 500000
  WHERE id = 'A001';
  -- 💥 koneksi putus di sini

  -- database mendeteksi koneksi terputus
  -- sebelum COMMIT tercapai →
  ROLLBACK; -- otomatis oleh DB

-- hasil: saldo Budi DIKEMBALIKAN seperti semula.
-- tidak ada uang yang hilang atau nyangkut.

Ini inti dari Atomicity: database melacak semua perubahan yang belum di-COMMIT, dan kalau transaksi tidak selesai secara bersih — baik karena error eksplisit, koneksi putus, atau server crash — semua perubahan itu dibuang, bukan dibiarkan setengah jalan. Aplikasi tidak perlu menulis kode "kalau langkah 2 gagal, batalkan langkah 1 secara manual"; database yang menjamin ini di level rendah lewat mekanisme rollback & log transaksi.

◆
Rollback bukan solusi ajaib untuk semua bug. Ia hanya membatalkan perubahan yang belum di-commit di database. Kalau transaksimu sudah memicu efek samping di luar database — mengirim email, memanggil API pembayaran eksternal, menulis file — efek itu tidak ikut dibatalkan oleh ROLLBACK. Ini kenapa banyak praktik terbaik bilang: jangan taruh I/O eksternal di dalam transaksi database.
◆ Praktik · Cara pakai transaksi yang sehat

Best practice menulis transaksi di aplikasi nyata

Transaksi itu alat yang kuat, tapi juga alat yang bisa menahan resource dalam waktu lama kalau dipakai sembarangan. Beberapa aturan praktis berikut membantu kamu memakainya dengan aman.

  • Buat transaksi sesingkat mungkin. Semakin lama transaksi terbuka, semakin lama lock ditahan — makin besar peluang transaksi lain menunggu atau bahkan deadlock.
  • Jangan taruh I/O eksternal di dalam transaksi — panggilan API pihak ketiga, kirim email, HTTP request. Kalau layanan eksternal itu lambat, transaksimu ikut lambat & menahan lock database lebih lama dari perlu.
  • Pilih isolation level yang sesuai kebutuhan, bukan asal pakai default. Level yang lebih ketat (mis. SERIALIZABLE) lebih aman tapi lebih lambat; level longgar (mis. READ COMMITTED) lebih cepat tapi rawan anomali tertentu.
  • Siapkan logika retry untuk error yang wajar terjadi di lingkungan konkuren, seperti deadlock atau serialization failure — biasanya cukup mengulang transaksi dari awal.
  • Pakai idempotency key untuk operasi yang bisa terkirim dobel (mis. request pembayaran yang di-retry oleh client), supaya transaksi yang sama tidak dieksekusi dua kali walau permintaannya datang berkali-kali.
  • Jangan andalkan transaksi database untuk mengganti validasi di level aplikasi. Constraint di database itu jaring pengaman terakhir, bukan pengganti validasi input yang seharusnya sudah dicek lebih awal.

◆ Harga · Tidak ada makan siang gratis

Trade-off: jaminan kuat vs performa & skala

Transaksi memberi jaminan yang kuat, tapi jaminan itu tidak gratis. Semakin ketat isolasi & semakin luas cakupan transaksi, semakin besar biaya locking & koordinasi yang harus dibayar sistem.

// Yang kamu dapat

  • Tidak ada state "setengah jadi" yang bocor keluar.
  • Kode aplikasi jauh lebih sederhana — tak perlu penanganan error manual di tiap langkah.
  • Konsistensi data terjaga otomatis lewat constraint.
  • Reasoning tentang concurrency jadi jauh lebih mudah.

// Yang kamu korbankan

  • Lock menahan resource → transaksi lain harus menunggu.
  • Isolation level ketat menurunkan konkurensi & throughput.
  • Transaksi lintas-database/lintas-service (distributed transaction) mahal & rapuh.
  • Sulit di-scale horizontal begitu transaksi menyentuh banyak node.
◆ Kapan pakai vs kapan tidak

Pakai transaksi kuat saat uang, stok, atau state kritis dipertaruhkan — transfer saldo, checkout, pengurangan inventory. Pertimbangkan alternatif yang lebih longgar (mis. eventual consistency, saga) saat sistemmu sudah tersebar lintas banyak service/database, dan kamu bisa menoleransi konsistensi yang menyusul belakangan demi skala & ketersediaan yang lebih tinggi — misalnya notifikasi, log aktivitas, atau rekomendasi yang tidak fatal kalau telat sedetik.

Studi kasus · Di dunia nyata

Di mana transaksi jadi penentu, di production

Tiga skenario nyata di mana tanpa jaminan transaksi, kerugiannya langsung terasa — uang hilang, barang terjual dobel, atau pelanggan ditagih dua kali.

// fintech / bank

Transfer saldo antar rekening

Kasus: memindahkan dana antara dua akun harus mengurangi satu sisi & menambah sisi lain sebagai satu kesatuan. Kenapa transaksi: Atomicity memastikan tidak ada dana yang "hilang di udara" saat terjadi kegagalan di tengah proses.

// e-commerce

Checkout & pembayaran (mis. Stripe)

Kasus: permintaan pembayaran bisa terkirim dua kali akibat retry jaringan dari sisi client. Kenapa transaksi: dikombinasikan dengan idempotency key, sistem memastikan permintaan yang sama tidak diproses/ditagih dua kali walau requestnya dobel.

// inventory

Pengurangan stok saat checkout

Kasus: dua pembeli mengklik "beli" hampir bersamaan untuk stok terakhir. Kenapa transaksi: Isolation mencegah keduanya membaca stok "masih ada" secara bersamaan lalu sama-sama lolos checkout — mencegah overselling.

// booking / reservasi

Pemesanan kursi/tiket

Kasus: dua orang mencoba memesan kursi yang sama di detik yang sama. Kenapa transaksi: transaksi memastikan hanya satu yang berhasil mengunci & menyelesaikan pemesanan; yang lain gagal dengan jelas, bukan berebut diam-diam.

◆ Benang merahnya

Di semua kasus di atas, ada state bersama yang diperebutkan oleh operasi-operasi yang berpotensi tumpang tindih. Tanpa transaksi, celah antar-langkah itu jadi tempat bug konkurensi bersembunyi — dan biasanya bug jenis ini paling sulit direproduksi karena hanya muncul saat beban tinggi atau timing tertentu.

⚙ Ekosistem · Alat yang dipakai

Tools & dukungan transaksi di ekosistem umum

Hampir semua database relasional utama mendukung ACID secara native. Yang sering berbeda adalah cara kamu memicunya dari kode aplikasi.

// database

PostgreSQL

Dukungan transaksi ACID penuh sejak awal, termasuk SERIALIZABLE isolation lewat teknik serializable snapshot isolation. Sering jadi rujukan implementasi transaksi yang benar.

// database

MySQL (InnoDB)

Storage engine InnoDB memberi dukungan ACID lewat MVCC & row-level locking. Engine lama seperti MyISAM tidak mendukung transaksi — penting diperhatikan saat memilih engine tabel.

// ORM · Python

Django atomic()

Context manager transaction.atomic() membungkus blok kode jadi satu transaksi database, dengan rollback otomatis kalau exception tak tertangani muncul di dalamnya.

// ORM · Node.js

Sequelize transaction()

Menyediakan API transaksi eksplisit maupun managed (auto commit/rollback), memudahkan membungkus beberapa query jadi satu unit atomik dari kode JavaScript/TypeScript.

// ORM · Node.js

Prisma $transaction

Mendukung transaksi interaktif maupun batch, cocok untuk operasi multi-model yang harus sukses/gagal bersamaan dalam satu request.

// distributed

Saga orchestrator (mis. Temporal)

Untuk kasus lintas-service yang tak bisa pakai transaksi ACID biasa, tool orkestrasi workflow membantu mengelola langkah & kompensasi (rollback manual) ala pola saga.

◆ Tips pemula

Kalau kamu baru mulai, cukup kenali cara transaksi dipakai lewat ORM yang kamu pakai sehari-hari (mis. atomic() di Django atau $transaction di Prisma). Konsep distributed transaction & saga baru relevan setelah sistemmu benar-benar terpecah jadi banyak service/database.

Penutup

Bungkus yang tepat, untuk state yang berharga

Transaksi lahir dari kebutuhan sederhana: memastikan beberapa operasi yang saling bergantung tidak pernah berhenti di tengah jalan. ACID adalah janji yang dipegang database supaya kamu tidak perlu menebak-nebak sendiri.

  • Transaksi = satu unit logis — semua-atau-tidak-sama-sekali, aplikasi tak perlu menangani partial failure sendiri.
  • Atomicity — kegagalan di tengah jalan, seluruh transaksi dibatalkan lewat rollback.
  • Consistency — database berpindah dari state valid ke state valid lain sesuai aturan.
  • Isolation — transaksi konkuren tidak saling mengintip state setengah-jadi.
  • Durability — sekali commit, perubahan bertahan walau server mati mendadak.
  • Kuat itu berharga, bukan gratis — pilih cakupan & isolation level sesuai seberapa kritis datamu.

Aturan emasnya

Tanya: "Kalau proses ini berhenti di tengah jalan, apakah aku bisa hidup dengan data yang setengah berubah?" Kalau jawabannya tidak — saldo, stok, status pembayaran — bungkus dalam transaksi. Kalau kamu bisa menoleransi ketidakkonsistenan sesaat demi skala & ketersediaan, pertimbangkan pola yang lebih longgar seperti saga atau eventual consistency. Tidak ada satu jawaban untuk semua kasus — pilih sesuai seberapa mahal harga kegagalan setengah jalan bagi bisnismu.
