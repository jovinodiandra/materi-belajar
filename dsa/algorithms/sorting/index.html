// DSA — Algorithms · dasar dari hampir semua optimasi lain

Data yang terurut membuka jalan untuk semua yang lebih cepat.

Sorting adalah salah satu masalah paling tua & paling sering dipakai di ilmu komputer: mengubah kumpulan data acak jadi berurutan. Deck ini bertahap: mulai dari bubble/selection/ insertion sort yang O(n²) — lambat tapi paling mudah dipahami sebagai fondasi konsep — lalu naik ke merge sort & quick sort yang O(n log n) lewat pendekatan divide-and-conquer, sampai kapan sebaiknya kamu pakai sort bawaan bahasa vs menulis sendiri.

Sakit
Data acak susah dicari & dianalisis — binary search & dedup butuh data terurut
Ide
Algoritma sorting sistematis — dari O(n²) sederhana ke O(n log n) divide-and-conquer
Untung
Membuka optimasi lain — binary search, dedup cepat, merge dua list terurut
Batas
Comparison-based dibatasi O(n log n) — kecuali kasus khusus non-comparison
Pakai
Nyaris di mana-mana — Collections.sort, ORDER BY, leaderboard, feed

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya daftar mentah: log transaksi, daftar nama, skor pemain — urutannya cuma urutan kedatangan, bukan urutan yang berguna.

When — kamu butuh cari satu elemen cepat, deteksi duplikat, ambil top-N/terkecil, atau gabungkan dua daftar jadi satu yang rapi.

Then — tanpa data terurut, tiap pencarian jadi O(n) linear scan, deteksi duplikat butuh struktur tambahan (hash set), dan "cari yang terbesar" harus memindai ulang semua elemen tiap kali — makin lambat seiring data membesar.

→ makanya kita pakai sorting: sekali investasi mengurutkan, banyak operasi lain jadi jauh lebih murah.

Akar masalah · Kenapa sorting fundamental

Data terurut membuka banyak optimasi lain

Kalau data tidak terurut, mencari satu elemen berarti memeriksa satu-satu dari awal — O(n). Begitu data terurut, kamu bisa pakai binary search — O(log n) — atau mendeteksi duplikat cukup dengan melihat tetangga kiri-kanan, tanpa hash set. Sorting sendiri bukan tujuan akhir; ia adalah investasi yang membayar banyak operasi lain jadi jauh lebih murah.

◆ Analogi — menyusun kartu remi di tangan

Saat main kartu remi, kamu otomatis menyusun kartu di tangan dari kecil ke besar begitu menerimanya — bukan karena diminta, tapi karena kartu yang terurut membuat semua langkah berikutnya lebih mudah: gampang melihat kombinasi, gampang tahu kartu apa yang hilang, gampang membandingkan dengan kartu lawan. Komputer melakukan hal yang sama pada data: sekali diurutkan, banyak pekerjaan lain jadi lebih murah.

Itulah kenapa sorting jadi salah satu topik paling awal di ilmu komputer — bukan cuma latihan akademis, tapi blok bangunan yang dipakai ulang di database, search engine, sistem file, sampai algoritma grafik.

Konsep inti · Titik awal memahami sorting

Insertion sort — cara manusia mengurutkan kartu

Insertion sort bekerja persis seperti kamu menyusun kartu remi satu per satu: ambil kartu berikutnya, lalu sisipkan ke posisi yang benar di antara kartu-kartu yang sudah tersusun rapi di tangan kiri. Bagian array di sebelah kiri selalu terjaga terurut; bagian kanan belum disentuh.

InsertionSort.javaJava
import java.util.Arrays;

public class InsertionSort {

    static void insertionSort(int[] arr) {
        for (int i = 1; i < arr.length; i++) {
            int key = arr[i];          // kartu yang mau disisipkan
            int j = i - 1;
            while (j >= 0 && arr[j] > key) {
                arr[j + 1] = arr[j];     // geser kartu lebih besar ke kanan
                j--;
            }
            arr[j + 1] = key;           // sisipkan di posisi yang benar
        }
    }

    public static void main(String[] args) {
        int[] data = { 5, 2, 9, 1, 5, 6 };
        insertionSort(data);
        System.out.println(Arrays.toString(data)); // [1, 2, 5, 5, 6, 9]
    }
}

Kompleksitasnya O(n²): untuk tiap elemen (n kali), worst-case kamu menggeser hampir seluruh bagian yang sudah terurut (n kali lagi). Lambat untuk data besar, tapi sangat cepat untuk data kecil atau data yang sudah hampir terurut — best-case-nya mendekati O(n) kalau tinggal sedikit yang perlu digeser.

◆ Keluarga sorting O(n²) — sederhana untuk belajar konsep
Bubbletukar pasangan tetangga berulang sampai tak ada lagi yang perlu ditukar
Selectioncari elemen terkecil sisa, tukar ke posisi depan, ulangi
Insertionsisipkan tiap elemen ke posisi benar di bagian yang sudah terurut

Ketiganya O(n²) di kasus rata-rata & terburuk, dan jarang dipakai untuk data besar di production — tapi memahami cara kerjanya adalah fondasi untuk mengerti kenapa algoritma O(n log n) di bab berikutnya jauh lebih baik untuk data besar.

Konsep lanjutan · Divide-and-conquer

Merge sort & quick sort — membagi lalu menaklukkan

Saat data makin besar, O(n²) mulai terasa sakit. Merge sort & quick sort memakai pendekatan divide-and-conquer: pecah array jadi bagian lebih kecil, selesaikan tiap bagian secara rekursif, lalu gabungkan — hasilnya turun ke O(n log n).

“Merge sort mencontohkan pendekatan divide-and-conquer secara sempurna: membagi masalah jadi subproblem yang lebih kecil, menyelesaikannya secara rekursif, lalu menggabungkan hasilnya — dengan jaminan waktu O(n log n) di semua kasus, berbeda dari quick sort yang rata-rata cepat namun bisa memburuk menjadi O(n²).”

— parafrase dari Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest, Clifford Stein, Introduction to Algorithms (CLRS)
MergeSort.javaJava
public class MergeSort {

    static void mergeSort(int[] arr, int left, int right) {
        if (left >= right) return;     // base case: 0 atau 1 elemen
        int mid = (left + right) / 2;
        mergeSort(arr, left, mid);       // urutkan separuh kiri
        mergeSort(arr, mid + 1, right);  // urutkan separuh kanan
        merge(arr, left, mid, right);   // gabungkan dua bagian terurut
    }

    static void merge(int[] arr, int left, int mid, int right) {
        int[] temp = new int[right - left + 1]; // butuh array bantu
        int i = left, j = mid + 1, k = 0;
        while (i <= mid && j <= right) {
            temp[k++] = (arr[i] <= arr[j]) ? arr[i++] : arr[j++]; // <= menjaga stabil
        }
        while (i <= mid)   temp[k++] = arr[i++];
        while (j <= right) temp[k++] = arr[j++];
        System.arraycopy(temp, 0, arr, left, temp.length);
    }
}

Merge sort selalu membagi tepat di tengah, jadi kedalaman rekursinya selalu log n, dan langkah gabung (merge) selalu O(n) — hasilnya O(n log n) di semua kasus, dan karena perbandingan <= menjaga urutan elemen yang sama, ia juga stabil. Harganya: butuh array bantu (temp) seukuran data — memori ekstra O(n).

Quick sort berbeda strategi: pilih satu pivot, lalu partition array supaya elemen lebih kecil dari pivot ada di kiri & lebih besar di kanan — semuanya di tempat (in-place), tanpa array bantu. Rata-rata juga O(n log n), tapi kalau pivot yang dipilih selalu jadi elemen terkecil/terbesar (misalnya array sudah terurut & pivot selalu elemen terakhir), partisinya jadi timpang & kompleksitas memburuk ke O(n²).

merge sort — predictable, extra memoryJava
// selalu bagi tepat tengah → kedalaman = log n
int mid = (left + right) / 2;
int[] temp = new int[right - left + 1]; // alokasi tiap merge()
// jaminan O(n log n) di SEMUA kasus, dan stabil (arr[i] <= arr[j])
// harga: memori ekstra O(n), tidak in-place
quick sort — in-place, worst case burukJava
static int partition(int[] arr, int low, int high) {
    int pivot = arr[high];        // pivot naif: elemen terakhir
    int i = low - 1;
    for (int j = low; j < high; j++) {
        if (arr[j] < pivot) { i++; swap(arr, i, j); } // tukar di tempat
    }
    swap(arr, i + 1, high);
    return i + 1;
}
// array sudah terurut + pivot = elemen terakhir → partisi timpang → O(n²)
◆ Praktik · Kebiasaan aman menyortir data

Best practice — kapan menulis sendiri, kapan tidak

Di production, kamu hampir tidak pernah menulis ulang merge sort atau quick sort dari nol untuk kode sehari-hari. Berikut kebiasaan yang menghindarkanmu dari bug & kode yang lebih lambat dari seharusnya.

“Tidak ada satu algoritma sorting yang “terbaik” untuk semua situasi — pilihan bergantung pada ukuran data, apakah stabilitas urutan penting, apakah memori terbatas, dan seberapa acak data awal; itulah sebabnya sistem modern sering memakai algoritma hybrid seperti Timsort.”

— parafrase dari Robert Sedgewick & Kevin Wayne, Algorithms
  1. Pakai sort bawaan bahasa untuk kebanyakan kasus — Arrays.sort() & Collections.sort() di Java sudah dioptimasi & hybrid (Timsort untuk objek), hasil rekayasa bertahun-tahun yang sulit dikalahkan kode sendiri.
  2. Pakai Comparator custom untuk objek — jangan ubah struktur data cuma supaya bisa diurutkan; tulis Comparator<T> atau Comparable<T> yang jelas & teruji.
  3. Perhatikan stabil vs tidak stabil — penting untuk multi-key sort (urutkan berdasarkan tanggal, lalu nama): sort stabil menjaga urutan relatif elemen dengan key sama dari sort sebelumnya; Arrays.sort() untuk primitif tidak dijamin stabil, tapi untuk objek (Timsort) dijamin stabil.
  4. Sadari harga memori — kalau data terlalu besar untuk muat di RAM, sort in-memory biasa (termasuk built-in) bukan solusinya; itulah kenapa ada teknik external sort.
  5. Tulis sort manual sendiri hanya untuk belajar, wawancara kerja, atau kasus sangat khusus (mis. constraint memori ekstrem, kebutuhan non-comparison sort seperti counting sort).
  6. Uji dengan data ekstrem — array kosong, satu elemen, sudah terurut, terurut terbalik, dan banyak duplikat — sebelum percaya sort custom-mu benar & cepat.
◆ Roadmap · Bertahap sesuai levelmu

Tier belajar sorting

Sorting adalah topik yang tumbuh bersama pengalamanmu — dari mengerti cara kerja dasar, sampai memahami kenapa satu algoritma dipilih di atas yang lain untuk kasus tertentu.

Beginner

Sorting manual & O(n²)

Kuasai dulu algoritma paling dasar dengan tangan sendiri, sampai benar-benar paham kenapa kompleksitasnya kuadratik.

  • Bubble sort dari nol
  • Selection sort dari nol
  • Insertion sort dari nol
  • Paham & bisa jelaskan kenapa O(n²)
Middle

Divide-and-conquer

Naik ke algoritma yang benar-benar dipakai untuk data besar — di sinilah rekursi & kompleksitas mulai terasa nyata.

  • Implementasi merge sort dari nol
  • Implementasi quick sort dari nol
  • Paham konsep divide-and-conquer
  • Bisa jelaskan trade-off stabil vs in-place
Advance

Analisis mendalam & kasus khusus

Di level ini kamu tidak cuma bisa menulis sortnya, tapi menganalisis & memilih strategi yang tepat untuk situasi nyata.

  • Analisis worst-case quick sort & mitigasinya (random pivot)
  • Counting sort untuk rentang nilai kecil
  • Radix sort — non-comparison-based, O(n)
  • Kapan pakai external sort untuk data raksasa
◆ Harga · Tidak ada sort yang menang segalanya

Trade-off: stabil, cepat, in-place, dan batas teoretis

Tiap algoritma sorting menukar satu hal demi hal lain. Memahami trade-off ini yang membuatmu bisa memilih dengan alasan, bukan sekadar hafalan nama algoritma.

// Stabil (merge sort, insertion sort, Timsort)

  • Menjaga urutan relatif elemen dengan key sama.
  • Aman untuk multi-key sort bertahap.
  • Biasanya butuh memori ekstra untuk jaminan ini.

// Cepat & in-place (quick sort, selection sort)

  • Tidak butuh (banyak) memori tambahan.
  • Umumnya tidak menjaga urutan elemen dengan key sama.
  • Performa bisa memburuk drastis di kasus tertentu (pivot buruk).
◆ Batas teoretis: comparison-based vs non-comparison

Algoritma sorting yang bekerja dengan membandingkan pasangan elemen (merge sort, quick sort, insertion sort, dst.) tidak bisa lebih cepat dari O(n log n) di kasus umum — ini batas matematis, bukan soal implementasi. Tapi untuk kasus khusus (misalnya rentang nilai integer yang diketahui & kecil), algoritma non-comparison-based seperti counting sort atau radix sort bisa mencapai O(n) — karena mereka tidak membandingkan elemen satu-satu, melainkan menghitung/mengelompokkan berdasarkan nilai.

◆ Keputusan · Pakai atau jangan

Kapan pakai algoritma sorting yang mana

Aturan praktisnya: untuk kode aplikasi sehari-hari, sort bawaan bahasa nyaris selalu menang. Tulis atau pilih algoritma spesifik hanya kalau ada alasan konkret — memori terbatas, kebutuhan stabilitas eksplisit, atau data dengan karakteristik khusus.

// Pakai sort bawaan / hybrid saat…

  • Kode aplikasi umum — 99% kasus sehari-hari.
  • Data berupa objek yang butuh Comparator.
  • Butuh stabilitas tanpa mikirkan detail implementasi.
  • Ukuran data wajar & muat di memori.

// Pertimbangkan algoritma khusus saat…

  • Rentang nilai integer diketahui & kecil → counting/radix sort.
  • Memori sangat terbatas → quick sort in-place custom.
  • Data tak muat di RAM → external sort (merge dari disk).
  • Wawancara kerja / belajar internal algoritma bahasa.
◆ Pertanyaan penentu

Tanyakan ke dirimu: "Apakah aku punya alasan konkret untuk tidak percaya pada sort bawaan bahasa?" Kalau tidak — dan kebanyakan kasus memang tidak — pakai Arrays.sort() / Collections.sort(). Kalau ya, pastikan alasannya jelas: memori, stabilitas, atau bentuk data yang benar-benar khusus.

Studi kasus · Di dunia nyata

Di mana sorting benar-benar dipakai di production

Tiga contoh nyata yang menunjukkan bagaimana pilihan algoritma sorting terhubung langsung ke kebutuhan sistem — stabilitas, keterbatasan memori, atau tampilan data terurut ke pengguna.

// bahasa pemrograman

Timsort di Java Collections.sort

Kasus: mengurutkan List<T> berisi objek — misalnya daftar pengguna yang diurutkan berdasarkan tanggal daftar, lalu (kalau sama) nama. Kenapa Timsort: algoritma hybrid gabungan merge sort & insertion sort ini stabil — penting supaya urutan sekunder tidak kacau saat sort bertingkat — sekaligus cepat untuk data yang sudah sebagian terurut.

// database

ORDER BY & external sort

Kasus: query ORDER BY pada tabel yang jauh lebih besar dari memori yang tersedia. Kenapa external sort: database mengurutkan data per-blok yang muat di memori, menulisnya ke disk, lalu menggabungkan (merge) blok-blok terurut itu — pola yang persis mengikuti ide merge step pada merge sort, hanya dilakukan lintas disk, bukan lintas array.

// tampilan data

Leaderboard & feed berurutan waktu

Kasus: menampilkan papan peringkat game berdasarkan skor, atau feed media sosial berdasarkan waktu posting terbaru. Kenapa sorting relevan: data harus konsisten terurut setiap kali ditampilkan; sistem semacam ini sering mengandalkan struktur data yang menjaga urutan saat insert (mis. indeks terurut di database) daripada mengurutkan ulang seluruh data tiap kali dibaca.

◆ Benang merahnya

Di ketiga kasus di atas, pilihan algoritma bukan soal "mana yang paling cepat di atas kertas" saja — Timsort dipilih karena stabilitas, external sort dipilih karena keterbatasan memori, dan sistem leaderboard/feed sering menghindari sort ulang berulang dengan menjaga data tetap terurut di struktur penyimpanannya. Konteks pemakaian yang menentukan, bukan hanya kompleksitas Big-O.

Penutup

Paham dasarnya, percaya sort bawaan untuk sisanya

Sorting adalah fondasi yang membuat banyak operasi lain jadi mungkin & murah. Paham insertion sort mengajarkanmu cara berpikir dasar; paham merge sort & quick sort mengajarkanmu divide-and-conquer; dan paham kapan memakai sort bawaan bahasa menyelamatkanmu dari menulis ulang sesuatu yang sudah dioptimasi bertahun-tahun.

  • Sorting membuka optimasi lain — binary search, dedup, merge cepat.
  • O(n²) untuk belajar konsep — bubble, selection, insertion sort.
  • O(n log n) untuk data besar — merge sort (stabil, extra memory), quick sort (in-place, worst-case buruk).
  • Comparison-based dibatasi O(n log n) — non-comparison (counting/radix) bisa O(n) untuk kasus khusus.
  • Pakai sort bawaan bahasa — Timsort & sejenisnya sudah dioptimasi & hybrid.
  • Pilih berdasarkan konteks — stabilitas, memori, ukuran data — bukan hafalan nama algoritma.

Aturan emasnya

Kalau sedang belajar: implementasikan bubble/insertion/merge/quick sort dari nol sampai benar-benar paham cara kerjanya. Kalau sedang membangun aplikasi: pakai sort bawaan bahasa, dan simpan energi analisismu untuk hal yang lebih penting — kecuali kamu punya alasan konkret untuk tidak melakukannya.
