// Data Structures & Algorithms — mencari secepat array, menyisip secepat linked list

Pohon yang tetap terurut sambil terus tumbuh.

Array terurut enak dicari (binary search, O(log n)) tapi menyisip data baru mahal — semua elemen setelahnya harus digeser. Linked list enak disisip (O(1)) tapi cari data harus telusuri satu-satu. Binary Search Tree (BST) mencoba mengambil yang terbaik dari keduanya: struktur bercabang yang tetap menjaga urutan, sehingga search, insert, dan delete bisa sama-sama cepat — selama pohonnya tidak "timpang".

Masalah
Array vs linked list — cepat cari ATAU cepat sisip, tak pernah keduanya

Pohon biner terurut — left < node < right, di tiap simpul
Untung
O(log n) rata-rata — search, insert, delete sama cepatnya
Batas
Bisa jadi O(n) — kalau data masuk sudah terurut, pohon jadi mirip list
Solusi
Self-balancing tree — AVL & Red-Black menjaga tinggi pohon tetap kecil

Akar masalah · Dua struktur, dua kelemahan berlawanan

Array cepat dicari, linked list cepat disisip — tidak pernah dua-duanya

Kalau data disimpan di array terurut, binary search bisa menemukan elemen dalam O(log n). Tapi menyisipkan satu elemen baru di tengah berarti menggeser semua elemen setelahnya — O(n). Sebaliknya, linked list bisa menyisip di mana saja dalam O(1) asal sudah punya posisinya, tapi untuk menemukan posisi itu kamu harus menelusuri node satu per satu — O(n) juga, hanya di sisi yang berbeda.

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya kumpulan data (misal ID pelanggan, kamus kata, index database) yang sama-sama sering dicari dan sering berubah (ditambah/dihapus), lalu kamu simpan sebagai array terurut atau linked list.

When — sistem terus menerima insert baru sambil pengguna terus melakukan pencarian pada data yang sama, jumlahnya bertambah dari ratusan jadi jutaan entri.

Then — array terurut membuat tiap insert jadi O(n) karena menggeser elemen, sedangkan linked list membuat tiap search jadi O(n) karena harus ditelusuri satu per satu — tidak ada pilihan yang cepat di kedua operasi sekaligus.

→ makanya kita pakai Binary Search Tree — struktur yang menjaga urutan seperti array tapi menyisip seperti linked list, sehingga search, insert, dan delete rata-rata sama-sama O(log n).

◆ Analogi — buku telepon vs rak buku

Buku telepon (array terurut) enak sekali dicari: buka di tengah, bandingkan, lipat ke kiri atau kanan, ketemu dalam hitungan langkah. Tapi mau menambahkan satu nama baru di tengah abjad? Kamu harus mencetak ulang & menggeser semua halaman setelahnya. Rak buku yang bisa disisipi (linked list) sebaliknya — selipkan saja buku baru di antara dua buku lain, selesai. Tapi untuk menemukan judul tertentu, kamu harus menyusuri rak dari ujung, satu per satu, karena tidak ada "jalan pintas" ke tengah.

BST lahir dari pertanyaan: bisakah struktur data menjaga urutan seperti buku telepon, tapi tetap semudah rak buku untuk disisipi? Jawabannya: susun data sebagai pohon bercabang. Tiap simpul punya "wilayah" sendiri (semua yang lebih kecil ke kiri, semua yang lebih besar ke kanan), jadi pencarian tetap bisa membuang separuh kemungkinan di tiap langkah — tanpa perlu menggeser data lain saat menyisipkan simpul baru.

“Pohon pencarian biner mendukung operasi dictionary dasar — search, insert, delete — dalam waktu yang sebanding dengan tinggi pohonnya.”

— parafrase dari Thomas H. Cormen dkk., Introduction to Algorithms (CLRS), bab Binary Search Trees
Konsep inti · Aturan pembentuk BST

Satu aturan sederhana di tiap simpul

Untuk setiap simpul (node) di BST berlaku aturan yang sama, berulang di seluruh pohon: semua nilai di subtree kiri lebih kecil dari nilai simpul itu, dan semua nilai di subtree kanan lebih besar. Aturan ini berlaku rekursif — subtree kiri & kanan juga BST yang sah.

◆ Aturan BST, di tiap simpul
Kirisubtree kiri < node.key
Kanansubtree kanan > node.key
Berulangberlaku di SETIAP subtree, bukan cuma root

Konsekuensinya: kalau kamu jalankan inorder traversal (kiri → simpul → kanan) di BST mana pun, hasilnya otomatis data terurut — ini bukan kebetulan, tapi akibat langsung dari aturan di atas.

BST.java — insert & search rekursifJava
class Node {
    int key;
    Node left, right;

    Node(int key) { this.key = key; }
}

class BST {
    Node root;

    // insert: taruh key di posisi yang menjaga aturan BST
    void insert(int key) {
        root = insertRec(root, key);
    }

    private Node insertRec(Node node, int key) {
        if (node == null) return new Node(key);
        if (key < node.key) {
            node.left = insertRec(node.left, key);
        } else if (key > node.key) {
            node.right = insertRec(node.right, key);
        }
        // key == node.key -> anggap duplikat, tidak disisipkan lagi
        return node;
    }

    // search: buang separuh subtree di tiap langkah
    boolean search(int key) {
        return searchRec(root, key);
    }

    private boolean searchRec(Node node, int key) {
        if (node == null) return false;
        if (key == node.key) return true;
        return key < node.key
            ? searchRec(node.left, key)
            : searchRec(node.right, key);
    }
}

Perhatikan pola di searchRec: setiap perbandingan membuang satu subtree penuh dari pencarian — persis seperti binary search di array. Bedanya, di BST kamu tidak perlu menggeser data untuk menyisipkan; insertRec cukup menambahkan satu Node baru di posisi yang tepat, tanpa menyentuh simpul lain.

Titik lemah · Bentuk pohon bergantung urutan input

Kalau data masuk sudah terurut, BST berubah jadi linked list

O(log n) di BST itu rata-rata, bukan jaminan. Performa BST sepenuhnya bergantung pada tinggi pohonnya — dan tinggi itu ditentukan oleh urutan data saat disisipkan, bukan oleh jumlah datanya saja.

insert acak: 50,30,70,20,40,60,80 → seimbangtree
          50
        /      \
     30          70
    /  \        /  \
  20   40     60   80

tinggi = 3, n = 7  ->  search ~ O(log n)
insert terurut: 10,20,30,40,50,60,70 → timpangtree
10
  \
   20
     \
      30
        \
         40
           \
            50 ...

tinggi = 7, n = 7  ->  search = O(n), persis linked list

Ini bukan kasus langka — data yang sudah terurut atau hampir terurut (log timestamp, ID auto-increment, hasil query yang di-ORDER BY) sangat umum di dunia nyata. Setiap insert selalu jatuh ke satu sisi (kanan atau kiri saja), sehingga pohon tumbuh memanjang, bukan melebar.

◆ Solusinya — self-balancing tree

Struktur seperti AVL tree dan Red-Black tree memecahkan ini dengan menambahkan langkah rotasi setiap kali insert/delete berpotensi membuat pohon timpang — memutar sebagian simpul supaya tinggi kiri & kanan tetap mendekati seimbang. Hasilnya, tinggi pohon dijaga tetap O(log n) walau data masuk dalam urutan terburuk sekalipun. AVL lebih ketat menjaga keseimbangan (lookup sedikit lebih cepat), Red-Black lebih longgar tapi rotasinya lebih murah saat insert/delete — makanya Red-Black lebih umum dipakai di library standar.

“Performa BST sangat bergantung pada seberapa seimbang bentuknya — inilah motivasi lahirnya struktur self-balancing seperti red-black tree.”

— parafrase dari Thomas H. Cormen dkk., Introduction to Algorithms (CLRS)
◆ Panduan · Praktik yang perlu dipegang

Best practice kerja dengan BST

BST manual paling sering ditemui saat belajar & interview. Untuk pemakaian nyata, ada beberapa kebiasaan yang layak dipegang.

  1. Untuk production, jangan implementasi BST manual — pakai struktur self-balancing bawaan bahasa (mis. TreeMap/TreeSet di Java) yang sudah menjaga keseimbangan otomatis.
  2. Inorder traversal = data terurut — kalau butuh data terurut dari BST, cukup traversal kiri → simpul → kanan, tanpa perlu sorting terpisah.
  3. Waspadai urutan insert — kalau kamu terpaksa membangun BST sendiri dari data yang sudah terurut, acak dulu urutannya sebelum insert supaya pohon tidak langsung timpang.
  4. Delete adalah operasi paling rumit — hapus simpul dengan 0 atau 1 anak itu mudah, tapi simpul dengan 2 anak butuh mencari inorder successor (nilai terkecil di subtree kanan) untuk menggantikannya.
  5. Hindari duplikat ambigu — putuskan sejak awal bagaimana BST memperlakukan key yang sama (ditolak, atau disimpan sebagai count di node) supaya perilaku insert/delete konsisten.
  6. Ukur, jangan asumsi — kalau harus pilih antara BST manual vs hash table vs library balanced tree, uji pola akses & ukuran data sebenarnya, bukan cuma bawa reputasi "BST itu O(log n)".
◆ Roadmap · Urutan belajar yang disarankan

Tier belajar Binary Search Tree

BST sering muncul di technical interview dengan tingkat kesulitan yang melebar jauh. Berikut peta belajarnya dari dasar sampai internal struktur database.

Beginner

Operasi dasar

Paham bentuk & operasi paling inti sebelum masuk ke kasus yang lebih rumit.

  • Insert & search rekursif maupun iteratif
  • Delete: kasus 0, 1, dan 2 anak
  • Traversal: inorder, preorder, postorder
  • Cari nilai minimum & maksimum di pohon
Middle

Soal interview umum

Variasi soal yang sering keluar begitu operasi dasar sudah lancar.

  • Validate BST (cek apakah pohon benar-benar sah)
  • Cari kth smallest / kth largest element
  • Inorder successor & predecessor
  • Lowest common ancestor (LCA) di BST
Advance

Internal & self-balancing

Bagaimana BST dijaga tetap seimbang & dipakai sebagai fondasi struktur lain.

  • AVL tree: cara kerja rotasi LL, RR, LR, RL
  • Red-Black tree: properti & aturan rekoloran
  • BST sebagai basis TreeMap/TreeSet
  • B-tree (varian multi-child) sebagai index database
◆ Harga · BST vs Hash Table

Trade-off: urutan & range query, atau kecepatan mentah

Perbandingan paling relevan untuk BST bukan array atau linked list lagi, tapi hash table — sama-sama struktur "cari cepat", tapi dengan filosofi berbeda.

// Binary Search Tree

  • Data selalu terurut (lewat inorder traversal).
  • Mendukung range query — "ambil semua antara 10 dan 50".
  • Mudah cari min, max, successor, predecessor.
  • Search/insert/delete O(log n) — kalau seimbang.

// Hash Table

  • Data tidak terurut — hanya bisa ditebak lewat iterasi penuh.
  • Tidak mendukung range query secara natural.
  • Search/insert/delete rata-rata O(1) — lebih cepat murni.
  • Performa bisa turun kalau banyak collision pada hash function buruk.
◆ Ringkasnya

Pilih hash table kalau kamu cuma butuh "ada atau tidak" / "ambil by key" secepat mungkin, dan urutan tidak penting. Pilih BST (atau turunannya) kalau kamu butuh data tetap terurut, butuh range query, atau butuh tahu tetangga terdekat dari sebuah nilai.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai (turunan) BST

Aturan praktisnya: kalau butuh data tetap terurut atau butuh range query, BST (atau library balanced tree) unggul. Kalau cuma butuh lookup by key secepat mungkin tanpa peduli urutan, hash table lebih sederhana & kompetitif.

// Pakai BST / balanced tree saat…

  • Butuh data selalu terurut (mis. leaderboard, jadwal).
  • Butuh range query — "semua antara X dan Y".
  • Butuh floor/ceiling/successor/predecessor.
  • Membangun index untuk pencarian rentang (database, filesystem).

// Jangan, pilih hash table saat…

  • Cuma butuh "cek ada" / "ambil by key" secepat mungkin.
  • Urutan data sama sekali tidak relevan.
  • Ingin implementasi paling sederhana dengan performa rata-rata terbaik.
  • Tidak butuh range query maupun traversal terurut.
◆
Jangan pernah implementasi BST manual tanpa self-balancing di production kalau data yang masuk bisa datang dalam urutan yang bisa ditebak (mis. ID berurutan). Tanpa balancing, kamu diam-diam membangun linked list dengan overhead pointer ekstra — bukan struktur O(log n) yang kamu kira.
Studi kasus · Di dunia nyata

Di mana BST (dan turunannya) bekerja di production

BST murni jarang ditulis tangan di production — tapi turunannya ada di mana-mana, tersembunyi di balik struktur data & sistem yang kamu pakai tiap hari.

// java collections

TreeMap & TreeSet

Kasus: butuh Map/Set yang key-nya selalu terurut. Kenapa BST: di balik layar Java mengimplementasikan TreeMap/TreeSet dengan red-black tree — self-balancing BST — supaya get, put, dan iterasi terurut sama-sama O(log n).

// database index

B-tree index

Kasus: hampir semua database relasional butuh index yang cepat untuk lookup dan range query. Kenapa BST: B-tree adalah generalisasi BST dengan banyak child per node, dan menjadi struktur index utama di database relasional selama puluhan tahun (lihat topik indexing di situs ini).

// filesystem

Indexing filesystem

Kasus: filesystem modern (mis. NTFS, ext4 dengan HTree/B-tree) perlu mencari entri direktori & blok data dengan cepat di antara jutaan file. Kenapa BST: struktur berbasis pohon terurut (varian B-tree/B+tree) dipakai untuk menjaga lookup tetap cepat walau jumlah entri sangat besar.

◆ Benang merahnya

Di semua kasus di atas, BST murni tidak dipakai apa adanya — yang dipakai adalah varian self-balancing atau multi-child darinya (red-black tree, B-tree, B+tree). Konsep dasarnya tetap sama: pohon terurut yang membuang separuh kemungkinan di tiap langkah pencarian.

Penutup

Terurut itu bagus, tapi seimbang lebih penting

BST memberi jalan tengah antara array terurut & linked list — tapi janji O(log n)-nya hanya berlaku selama pohonnya seimbang. Begitu paham ini, kamu juga paham kenapa struktur seperti Red-Black tree & B-tree ada di mana-mana di balik layar.

  • Aturan BST — subtree kiri lebih kecil, subtree kanan lebih besar, berulang di tiap simpul.
  • Inorder traversal = terurut — konsekuensi langsung dari aturan tersebut.
  • O(log n) itu rata-rata — worst case bisa jatuh ke O(n) kalau data masuk terurut.
  • Self-balancing menyelamatkan — AVL & Red-Black menjaga tinggi pohon lewat rotasi.
  • Bandingkan dengan hash table — pilih BST saat butuh urutan/range query.
  • Manual BST jarang ke production — dunia nyata pakai TreeMap, B-tree, dsb.

Lanjut ke Heap

BST unggul saat kamu butuh semua data terurut dan bisa diakses dari mana saja. Tapi kalau kamu cuma butuh tahu elemen terkecil/terbesar berikutnya — tanpa peduli urutan sisanya — ada struktur yang lebih ringan & lebih cocok: Heap. Materi berikutnya membahas kenapa heap ada, dan kenapa ia jadi pilihan utama untuk priority queue.
