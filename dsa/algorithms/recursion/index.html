// DSA — Algorithms · fondasi paling dasar dari banyak topik lain

Fungsi yang memanggil dirinya sendiri, sampai masalahnya cukup kecil untuk dijawab langsung.

Sebagian masalah secara alami didefinisikan dalam dirinya sendiri: faktorial dari n butuh faktorial dari n-1, sebuah pohon terdiri dari node yang anak-anaknya juga pohon. Rekursi adalah cara menulis solusi yang mengikuti bentuk masalah itu apa adanya — fungsi yang memanggil versi lebih kecil dari dirinya sendiri, sampai berhenti di sebuah base case. Deck ini buat pemula: dari kenapa rekursi ada, cara berpikirnya, bahaya rekursi tanpa base case, sampai kapan dipakai di dunia nyata — diselingi kalimat dari buku rujukan.

Sakit
Masalah bersarang — solusi natural-nya juga bersarang
Ide
Fungsi panggil dirinya sendiri — pada subproblem yang lebih kecil
Untung

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya masalah yang secara alami bersarang: hitung n!, jelajahi semua node di tree atau folder bertingkat, atau pecah array jadi bagian-bagian kecil (divide and conquer).

When — kedalaman strukturnya tidak tetap — tree bisa 3 level atau 30 level, folder bisa nested berapa pun — sementara loop for/while biasa butuh tahu batas iterasinya sejak awal.

Then — kalau dipaksa pakai loop, kamu harus menulis manajemen stack manual (push/pop posisi sendiri) yang rumit dan gampang salah, atau nge-hardcode kedalaman tertentu sehingga kodenya gagal begitu strukturnya lebih dalam dari yang diasumsikan.

→ makanya kita pakai rekursi.

Akar masalah · Masalah yang mendefinisikan diri

Sebagian masalah secara natural terdiri dari versi kecil dirinya sendiri

Coba definisikan faktorial tanpa menyebut faktorial itu sendiri — susah. Definisi paling wajar justru: n! = n × (n-1)!, dengan 0! = 1 sebagai titik berhenti. Begitu juga fibonacci, dan struktur seperti tree — sebuah pohon adalah node akar yang anak-anaknya juga pohon (lebih kecil). Ketika definisi masalahnya sendiri rekursif, solusi yang paling natural juga rekursif.

◆ Analogi — cermin berhadap-hadapan & boneka Rusia (matryoshka)

Berdiri di antara dua cermin yang saling berhadapan: bayanganmu memuat bayangan dari bayangan, terus sampai jauh ke dalam. Atau bayangkan boneka Rusia — buka satu boneka, di dalamnya ada boneka yang sama persis, cuma lebih kecil, sampai akhirnya kamu sampai ke boneka terkecil yang tidak bisa dibuka lagi. Boneka terkecil itulah base case-nya — titik di mana proses "buka boneka" berhenti dengan sendirinya.

“Sebuah algoritma rekursif menyelesaikan masalah dengan memanggil dirinya sendiri pada satu atau lebih subproblem yang lebih kecil, mengombinasikan hasilnya untuk membentuk jawaban dari masalah asli.”

— parafrase dari Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest, Clifford Stein, Introduction to Algorithms (CLRS)

Traversal (menjelajahi) tree adalah contoh paling jelas: untuk mengunjungi seluruh node sebuah pohon, kamu cukup mengunjungi akarnya, lalu lakukan hal yang sama pada setiap anaknya — yang juga sebuah pohon (lebih kecil). Tak perlu tahu berapa dalam pohonnya; definisi rekursif itu otomatis mencakup semua kedalaman.

Konsep inti · Anatomi fungsi rekursif

Dua bagian wajib: base case & recursive case

Setiap fungsi rekursif yang benar punya dua bagian: base case — kondisi paling sederhana yang dijawab langsung tanpa memanggil diri sendiri lagi, dan recursive case — bagian yang memanggil fungsi yang sama pada input yang lebih kecil, lalu menggabungkan hasilnya.

Factorial.java — faktorial rekursifJava
public class Factorial {

    static long factorial(int n) {
        if (n == 0) {          // base case: berhenti di sini
            return 1;
        }
        return n * factorial(n - 1); // recursive case: makin kecil
    }

    public static void main(String[] args) {
        System.out.println(factorial(5)); // 120
    }
}

Jejak call stack-nya kalau dipanggil factorial(5): setiap panggilan menumpuk di stack sambil menunggu hasil panggilan di bawahnya, baru mengalikan saat kembali (unwinding):

◆ Jejak call stack factorial(5)
turunfactorial(5) → 5 * factorial(4)
turunfactorial(4) → 4 * factorial(3)
turunfactorial(3) → 3 * factorial(2)
turunfactorial(2) → 2 * factorial(1)
turunfactorial(1) → 1 * factorial(0)
basefactorial(0) → return 1
naik1*1 → 1*1 → 2*1 → 6*1 → 24 → 120

Tiap panggilan yang belum selesai menunggu di stack — makan memori — sampai factorial(0) menyentuh base case dan mulai mengembalikan nilai ke pemanggilnya satu per satu.

Cara berpikir · Trust the recursion

Jangan trace semua level — percaya rekursi menyelesaikan subproblem-nya

Cara paling bikin pusing belajar rekursi: mencoba membayangkan semua level panggilan sekaligus di kepala. Cara yang lebih sehat: percaya (trust) bahwa panggilan rekursif ke input yang lebih kecil sudah menghasilkan jawaban yang benar — tugasmu cuma memastikan cara menggabungkannya di level ini benar, dan base case-nya jelas.

“Memahami sebuah proses rekursif berarti memahami bagaimana bentuk (shape) proses komputasi itu terbentuk dari definisi prosedurnya — bukan sekadar menghafal sintaksnya; perbedaan antara rekursi linear biasa dengan rekursi ber-akumulator (tail recursive) adalah salah satu contoh penting dari perbedaan bentuk itu.”

— parafrase dari Harold Abelson & Gerald Jay Sussman, Structure and Interpretation of Computer Programs (SICP)

Tapi kepercayaan itu cuma aman kalau base case-nya benar-benar ada dan setiap panggilan rekursif memang mendekatinya. Tanpa itu, fungsi memanggil dirinya sendiri selamanya — tiap panggilan menumpuk di call stack sampai stack-nya penuh dan program crash.

tanpa base case — infinite recursionJava
static long factorial(int n) {
    return n * factorial(n - 1); // tidak pernah berhenti!
}
// factorial(5) → factorial(4) → ... → factorial(-999999) → ...
// java.lang.StackOverflowError
dengan base case jelas — berhenti amanJava
static long factorial(int n) {
    if (n <= 0) return 1; // base case
    return n * factorial(n - 1); // mendekat ke base case
}
// factorial(5) → 4 → 3 → 2 → 1 → 0 → berhenti, return 120
◆
Base case saja tidak cukup kalau parameternya tidak pernah mendekatinya — misalnya factorial(n) yang justru memanggil factorial(n + 1), atau base case yang salah syarat sehingga tidak pernah tercapai untuk input tertentu. Selalu periksa: apakah input di panggilan rekursif benar-benar lebih kecil / lebih dekat ke base case dibanding sebelumnya?
◆ Praktik · Kebiasaan aman menulis rekursi

Best practice menulis fungsi rekursif

Beberapa kebiasaan ini akan menyelamatkanmu dari bug rekursi yang paling umum — dari StackOverflowError sampai kode yang lambat tanpa disadari.

  1. Definisikan base case dulu, sebelum menulis recursive case. Tanyakan: "kasus paling kecil/sederhana yang bisa saya jawab langsung itu apa?"
  2. Pastikan tiap panggilan rekursif mendekati base case — parameternya harus mengecil, memendek, atau bergerak menuju kondisi berhenti secara konsisten.
  3. Percaya rekursinya (trust the recursion) — jangan paksa diri men-trace semua level di kepala; fokus benarkan satu langkah: base case dan cara menggabungkan hasil subproblem.
  4. Waspada rekursi dalam — tiap panggilan menambah stack frame. Rekursi pada input besar (misal traversal jutaan node) bisa memicu StackOverflowError; pertimbangkan iteratif atau tail recursion kalau bahasanya mendukung optimisasi tersebut.
  5. Hindari kerja berulang tanpa perlu — rekursi naif seperti fibonacci (fib(n-1) + fib(n-2)) menghitung ulang subproblem yang sama berkali-kali dan bisa meledak secara eksponensial; tambahkan memoization kalau subproblem-nya tumpang tindih.
  6. Uji dari input kecil dulu, lalu edge case-nya — 0, angka negatif, list kosong, node null — sebelum percaya fungsi itu benar untuk input besar.
◆ Roadmap · Bertahap sesuai levelmu

Tier belajar rekursi

Rekursi bukan topik sekali paham langsung selesai — makin dalam, ia jadi fondasi untuk teknik-teknik yang lebih rumit. Berikut jalurnya dari dasar sampai lanjut.

Beginner

Rekursi dasar pada angka

Mulai dari fungsi rekursif paling sederhana yang cuma bekerja dengan angka dan satu base case jelas.

  • Faktorial rekursif
  • Fibonacci rekursif (naif)
  • Jumlah angka 1..n secara rekursif
  • Pangkat (power) rekursif
Middle

Rekursi pada struktur data

Pindah dari angka ke struktur bersarang — di sinilah rekursi mulai terasa benar-benar dibutuhkan, bukan sekadar latihan.

  • Traversal linked list rekursif
  • Traversal tree (pre/in/post-order)
  • Menghitung tinggi/jumlah node sebuah tree
  • Rekursi pada struktur folder/JSON bersarang
Advance

Rekursi sebagai fondasi teknik lain

Di level ini, rekursi bukan tujuan akhir — ia jadi alat untuk teknik algoritma yang lebih besar.

  • Tail recursion & optimisasinya
  • Konversi rekursi → iteratif (pakai stack sendiri)
  • Basis untuk backtracking
  • Basis untuk divide-and-conquer & dynamic programming
◆ Harga · Rekursi vs iteratif

Trade-off: kode ringkas vs overhead call stack

Hampir semua fungsi rekursif bisa ditulis ulang secara iteratif (pakai loop) — tapi keduanya punya harga yang berbeda. Pilih bukan karena "rekursi lebih keren", tapi karena cocok dengan bentuk masalahnya.

// Rekursi

  • Kode lebih ringkas & mengikuti bentuk masalah (tree, nested structure).
  • Base case & recursive case sering lebih mudah dibaca & dibuktikan benar.
  • Natural untuk backtracking, divide-and-conquer, parsing bersarang.

// Iteratif

  • Tidak menambah stack frame → tak ada risiko StackOverflowError.
  • Biasanya sedikit lebih hemat memori & overhead panggilan fungsi.
  • Kode kadang lebih panjang/kurang jelas untuk struktur yang memang bersarang.
◆ Soal overhead call stack

Setiap panggilan rekursif menambah satu stack frame berisi parameter, variabel lokal, dan alamat kembali — semuanya makan memori sampai panggilan itu selesai. Untuk rekursi yang dalam (misalnya traversal struktur dengan jutaan level), overhead ini bisa jadi masalah nyata, dan sebagian bahasa/compiler menyediakan optimisasi tail call untuk mengurangi biaya ini — walau Java sendiri tidak melakukan optimisasi tail call secara otomatis.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai rekursi

Aturan praktisnya: kalau masalahnya secara natural terdiri dari versi lebih kecil dari dirinya sendiri, rekursi biasanya lebih jernih. Kalau kedalamannya bisa sangat besar atau performa jadi kritis, pertimbangkan iteratif.

// Pakai rekursi saat…

  • Struktur datanya sendiri rekursif — tree, graph, nested JSON.
  • Masalahnya natural didekomposisi jadi subproblem serupa (divide-and-conquer).
  • Butuh mengeksplor banyak kemungkinan (backtracking).
  • Kedalaman rekursi terkendali/terbatas & kejelasan kode diprioritaskan.

// Pertimbangkan iteratif saat…

  • Kedalaman rekursi bisa sangat besar (risiko stack overflow).
  • Performa & penggunaan memori sangat kritis.
  • Solusinya sebenarnya cuma loop linear sederhana, tanpa subproblem bersarang.
  • Bahasa/runtime-nya tidak mendukung optimisasi tail call.
◆ Pertanyaan penentu

Tanyakan ke masalahmu: "Apakah masalah ini bisa saya definisikan dalam bentuk versi lebih kecil dari dirinya sendiri, plus satu kasus dasar?" Kalau ya, dan kedalamannya wajar, rekursi biasanya menghasilkan kode yang lebih mudah dibaca & dibuktikan benar dibanding versi iteratifnya yang berbelit.

Studi kasus · Di dunia nyata

Di mana rekursi benar-benar dipakai di production

Tiga contoh nyata di mana rekursi bukan sekadar latihan buku teks, tapi jadi cara paling natural menyelesaikan masalah yang memang berbentuk bersarang.

// parsing

Parser & compiler

Kasus: mem-parsing struktur bersarang seperti JSON, XML, atau expression di dalam bahasa pemrograman — objek di dalam objek, tanda kurung di dalam tanda kurung. Kenapa rekursi: aturan grammar-nya sendiri rekursif (sebuah "value" JSON bisa berisi "object" yang berisi "value" lagi), jadi fungsi parseValue() yang memanggil dirinya sendiri mengikuti struktur itu persis.

// filesystem

Traversal file system

Kasus: menghitung total ukuran sebuah folder, termasuk semua file di subfolder-subfoldernya, sedalam apa pun struktur foldernya. Kenapa rekursi: folder berisi file dan folder lain (yang juga folder) — fungsi hitungUkuran(folder) memanggil dirinya sendiri pada tiap subfolder lalu menjumlahkan hasilnya.

// divide-and-conquer

Merge sort & quick sort

Kasus: mengurutkan array besar dengan cara membagi jadi bagian lebih kecil, mengurutkan tiap bagian, lalu menggabungkannya. Kenapa rekursi: "urutkan array" didefinisikan sebagai "urutkan separuh kiri, urutkan separuh kanan, gabungkan" — definisi divide-and-conquer ini pada dasarnya rekursif.

◆ Benang merahnya

Di ketiga kasus di atas, struktur datanya sendiri bersarang (grammar bahasa, folder di dalam folder, array yang dibagi terus) — dan rekursi cuma mengikuti bentuk itu. Bukan rekursi yang dipaksakan ke masalah datar, tapi masalahnya sendiri memang berbentuk rekursif sejak awal.

Penutup

Percaya pada base case, dan pada langkah yang lebih kecil

Rekursi lahir dari masalah yang memang bisa didefinisikan dalam dirinya sendiri. Ia bersinar saat kamu berhenti mencoba men-trace semua level di kepala, dan mulai percaya bahwa subproblem yang lebih kecil akan terselesaikan — asal base case-nya jelas & setiap langkah benar-benar mendekatinya.

  • Base case — kondisi paling sederhana yang dijawab langsung.
  • Recursive case — memanggil diri sendiri pada input yang lebih kecil.
  • Trust the recursion — percaya subproblem kecil terselesaikan, jangan trace semua level.
  • Tanpa base case = bahaya — infinite recursion, StackOverflowError.
  • Call stack punya harga — tiap panggilan menambah stack frame.
  • Fondasi teknik lain — backtracking, divide-and-conquer, dynamic programming.

Aturan emasnya

Tulis base case dulu, baru recursive case. Pastikan tiap panggilan mendekati base case. Dan begitu kamu yakin satu langkahnya benar — percayai rekursinya untuk sisanya. Rekursi bukan sihir, ia cuma cara menulis solusi yang mengikuti bentuk masalah apa adanya.
