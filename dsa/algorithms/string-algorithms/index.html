// DSA — Algorithms · algoritma khusus untuk mengolah teks

Mencari kalimat di dalam buku tebal, tanpa membaca ulang dari awal tiap kali gagal.

String terlihat seperti array karakter biasa, tapi punya karakteristik unik: di banyak bahasa (termasuk Java) ia immutable, dan pola pencarian naif bisa jadi lambat begitu teksnya panjang. String algorithms adalah kumpulan teknik yang mengeksploitasi pola berulang di dalam teks untuk membuat pencarian & manipulasi jauh lebih cepat. Deck ini buat pemula: dari kenapa string butuh perlakuan khusus, KMP yang menghindari mundur ulang, sampai kapan semua ini dipakai di dunia nyata — diselingi kalimat dari sumber rujukan.

KMP / Rabin-Karp — O(n+m) — linear, tanpa backtrack berulang

◆ Buat apa ini? Kenapa pakai ini?

Given — kamu punya mesin pencari plagiarisme / log server / genome sequencer yang harus mencari satu pattern (kalimat, ID error, urutan DNA) di dalam text berukuran jutaan karakter, dan implementasinya masih pencocokan naif huruf-demi-huruf.

When — pattern-nya punya karakter berulang (mis. "ACGTACGTT" di DNA, atau "aaaab") sehingga tiap kali ketemu mismatch di tengah, pencarian mundur total dan mulai lagi dari posisi berikutnya — plus tiap concat string di loop pakai += biasa, bukan StringBuilder.

Then — pencarian jadi O(n×m) alih-alih linear, dan pembangunan string di loop diam-diam jadi O(n²) karena tiap += membuat objek String baru — pada teks panjang (log produksi, genom, dokumen tebal) ini terasa lambat bahkan untuk satu query.

→ makanya kita pakai String Algorithms (KMP, Rabin-Karp, StringBuilder) — memanfaatkan info yang sudah diketahui dari pencocokan sebelumnya supaya pencarian & manipulasi teks jadi O(n+m), tanpa mundur ulang dan tanpa buang-buang objek.

Akar masalah · Karakteristik unik string

String bukan sekadar array karakter biasa

Secara teknis, string memang array karakter — tapi ia punya kebiasaan yang bisa menjebak pemula. Di Java, String itu immutable: setiap kali kamu "mengubah" isinya (misalnya += di dalam loop), sebenarnya Java membuat objek string baru di memori, bukan menimpa yang lama. Kalau ceroboh dilakukan berulang-ulang di dalam loop, ini bisa diam-diam jadi O(n²). Di sisi lain, mencari satu kata di dalam dokumen panjang secara naif juga bisa lambat kalau teksnya besar.

◆ Analogi — mencari kalimat di dalam buku tebal

Bayangkan mencari satu kalimat spesifik di dalam buku setebal seribu halaman, tanpa indeks. Cara paling naif: baca dari kata pertama, cocokkan huruf demi huruf, begitu gagal di tengah — tutup buku, mulai lagi dari halaman satu. Itulah yang terjadi kalau kamu mencocokkan string secara naif tanpa strategi: setiap mismatch, pencarian mundur dan mengulang dari awal, padahal sebagian informasi yang sudah dibaca sebenarnya masih berguna.

Dua masalah inilah yang membuat string layak punya "algoritma sendiri": manipulasi (concat, build, ubah) butuh struktur yang tidak membuang-buang objek baru tiap langkah, dan pencarian pattern butuh strategi yang tidak mengulang kerja yang sudah dilakukan.

String, meskipun terlihat seperti sekadar array karakter, membutuhkan algoritma khusus karena pola-pola berulang di dalamnya — baik di teks maupun pattern yang dicari — bisa dieksploitasi untuk mempercepat pencarian jauh melampaui pendekatan naive.

— diparafrasakan dari gagasan Robert Sedgewick & Kevin Wayne, Algorithms
Konsep inti · Immutability & pencarian naif

Immutable string, StringBuilder, dan naive matching

Di Java, String bersifat immutable — sekali dibuat, isinya tidak pernah berubah. Operasi seperti s = s + "x" sebenarnya membuat objek String baru dan membuang yang lama. Dilakukan sekali dua kali tidak masalah, tapi di dalam loop yang berjalan ribuan kali, ini membuang banyak memori & waktu — makin panjang string, makin mahal tiap penyalinan.

NaiveMatch.java — pencarian pattern paling dasarJava
public class NaiveMatch {

    // cari indeks pertama pattern muncul di text, -1 kalau tidak ada
    static int search(String text, String pattern) {
        int n = text.length(), m = pattern.length();
        for (int i = 0; i <= n - m; i++) {   // geser posisi awal, O(n)
            int j = 0;
            while (j < m && text.charAt(i + j) == pattern.charAt(j)) {
                j++;                                // cocokkan huruf demi huruf, O(m)
            }
            if (j == m) return i;                  // pattern ketemu utuh
            // mismatch di tengah → i digeser satu, j direset ke 0 (mundur total!)
        }
        return -1;
    }

    public static void main(String[] args) {
        System.out.println(search("abcxabcdabcy", "abcdabcy")); // 4
    }
}

Kompleksitasnya O(n×m) — untuk tiap posisi i di teks (n posisi), pencarian bisa mencocokkan sampai m karakter pattern sebelum mismatch. Untuk teks pendek ini cukup cepat; untuk teks jutaan karakter dengan pattern yang panjang & berulang, ini bisa terasa lambat.

StringBuilder — concat berulang tanpa buang objekJava
static String buildCsv(List<String> kata) {
    // BURUK: tiap += membuat objek String baru → O(n²) untuk n kata
    String hasil = "";
    for (String w : kata) hasil += w + ",";

    // BAIK: StringBuilder pakai buffer internal yang bisa membesar, O(n) total
    StringBuilder sb = new StringBuilder();
    for (String w : kata) sb.append(w).append(",");
    return sb.toString();
}

StringBuilder penting karena ia mutable — punya buffer karakter internal yang bisa ditambah tanpa membuat objek baru tiap kali. Untuk concat sekali-dua kali, String biasa sudah cukup; begitu ada loop yang membangun string sedikit demi sedikit, StringBuilder mengubah kerja yang berpotensi O(n²) jadi O(n).

Teknik inti · Knuth-Morris-Pratt

KMP: jangan mundur, manfaatkan yang sudah kamu tahu

KMP (Knuth-Morris-Pratt) mencari pattern dalam teks dengan kompleksitas O(n+m) — linear, tanpa backtrack berulang. Intuisinya: saat mismatch terjadi di tengah pencocokan, kamu sudah tahu sebagian teks yang baru saja cocok dengan awal pattern. Alih-alih membuang informasi itu & mengulang dari awal, KMP memakai informasi itu untuk langsung melompat ke posisi yang masuk akal — tanpa pernah mundur di teks.

Ketika mismatch terjadi di tengah pencarian pattern, sebagian teks yang baru saja cocok sebenarnya sudah memberi informasi berharga — informasi itu bisa dipakai untuk menghindari mundur & mengulang perbandingan dari awal, sehingga pencarian tetap berjalan linear meski pattern-nya punya banyak pengulangan internal.

— parafrase dari Donald Knuth, James H. Morris, Vaughan Pratt, "Fast Pattern Matching in Strings" (1977)

Caranya: KMP membangun failure function (disebut juga prefix table) dari pattern-nya sendiri — sebuah tabel yang untuk tiap posisi menyimpan "seberapa panjang awalan pattern yang juga jadi akhiran dari bagian yang sudah dicocokkan sejauh ini". Saat mismatch, tabel ini langsung memberitahu ke posisi mana di pattern pencocokan harus dilanjutkan, tanpa perlu mengecek ulang karakter teks yang sudah pasti cocok.

naive matching — banyak backtrackJava
// text = "aaaaaaaab", pattern = "aaaab"
// tiap mismatch di posisi ke-4, i digeser 1, j direset ke 0
i=0: aaaa[a] vs aaaa[b] → mismatch, mundur total, i=1
i=1: aaaa[a] vs aaaa[b] → mismatch, mundur total, i=2
i=2: aaaa[a] vs aaaa[b] → mismatch, mundur total, i=3
i=3: aaaa[a] vs aaaa[b] → mismatch, mundur total, i=4
// setiap kegagalan mengulang perbandingan 4 huruf "a" dari nol lagi
// worst case: O(n * m)
KMP — tanpa mundur, pakai failure functionJava
// pattern = "aaaab" → failure function: [0,1,2,3,0]
// text tidak pernah dibaca mundur; hanya index pattern (j) yang disesuaikan
i=0..3: cocok terus sampai j=4, mismatch di 'b'
        → failure[3]=3, lanjut dari j=3, TANPA mundurkan i
i lanjut maju terus, j mengikuti tabel
// tiap karakter teks dibaca (relatif) sekali → O(n + m)
KMP.java — failure function & pencarianJava
public class KMP {

    // bangun failure function / prefix table dari pattern
    static int[] buildFailure(String pattern) {
        int m = pattern.length();
        int[] fail = new int[m];
        int len = 0;
        for (int i = 1; i < m; ) {
            if (pattern.charAt(i) == pattern.charAt(len)) {
                fail[i++] = ++len;                 // perpanjang awalan yang cocok
            } else if (len > 0) {
                len = fail[len - 1];               // mundur di TABEL, bukan di teks
            } else {
                fail[i++] = 0;
            }
        }
        return fail;
    }

    static int search(String text, String pattern) {
        int[] fail = buildFailure(pattern);
        int n = text.length(), m = pattern.length(), j = 0;
        for (int i = 0; i < n; i++) {
            while (j > 0 && text.charAt(i) != pattern.charAt(j)) {
                j = fail[j - 1];                   // lompat pakai info yang sudah diketahui
            }
            if (text.charAt(i) == pattern.charAt(j)) j++;
            if (j == m) return i - m + 1;      // pattern ketemu
        }
        return -1;
    }
}
◆ Praktik · Kebiasaan aman mengolah string

Best practice string di Java

Kebanyakan bug performa string bukan dari algoritma yang salah, tapi dari kebiasaan kecil yang diulang ribuan kali. Beberapa kebiasaan ini menyelamatkanmu dari jebakan paling umum.

  1. Pakai StringBuilder untuk concat di dalam loop — hindari s += x berulang, karena tiap operasi membuat objek String baru dan bisa jadi O(n²).
  2. Gunakan library built-in seperti String.indexOf() untuk kasus pencarian umum sehari-hari — implementasinya sudah teruji & cukup cepat untuk kebanyakan kebutuhan. Tulis KMP/Rabin-Karp sendiri hanya kalau memang butuh optimasi ekstrem atau kontrol penuh atas algoritmanya.
  3. Hati-hati perbandingan string pakai == vs .equals() — == membandingkan referensi objek, bukan isi. Dua string dengan isi sama bisa jadi objek berbeda di memori; selalu pakai .equals() untuk membandingkan isi.
  4. Ingat string itu immutable — method seperti substring(), replace(), toUpperCase() selalu mengembalikan objek baru, tidak pernah mengubah string aslinya. Jangan lupa menampung hasilnya.
  5. Pilih struktur data yang tepat untuk pencarian berulang — kalau pattern yang sama dicari di banyak teks berbeda (atau sebaliknya), pertimbangkan pre-processing seperti Trie atau suffix structure, bukan mengulang naive search tiap kali.
  6. Uji dengan kasus tepi — string kosong, pattern lebih panjang dari teks, karakter berulang penuh ("aaaa..."), dan karakter unicode/multi-byte yang kadang meleset dari asumsi charAt() sederhana.

◆ Harga · Simpel vs efisien

Trade-off: naive matching vs KMP/Rabin-Karp

Algoritma pencarian pattern yang lebih cepat tidak datang gratis — ia menukar kesederhanaan dengan setup yang lebih rumit. Pilih sesuai kebutuhan, bukan karena "yang lebih canggih pasti lebih baik".

// Naive matching

  • Kode sangat sederhana, mudah dibaca & dipahami.
  • Tidak butuh struktur data tambahan (prefix table, hash).
  • Cukup cepat untuk teks & pattern pendek.

// KMP / Rabin-Karp

  • Setup lebih kompleks — perlu bangun failure function / rolling hash.
  • Kode lebih panjang & lebih mudah salah implementasi.
  • Manfaat kecepatannya baru terasa di teks/pattern yang besar.
◆ Soal kompleksitas waktu

Naive matching berjalan O(n×m) di kasus terburuk — teks panjang n dikali panjang pattern m. KMP dan Rabin-Karp menurunkan ini jadi O(n+m) — linear terhadap total ukuran input. Untuk teks pendek, perbedaan ini nyaris tak terasa; untuk teks jutaan karakter (log server, genom, dokumen besar), perbedaannya jadi signifikan.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai algoritma pattern matching khusus

Aturan praktisnya: naive matching cukup untuk teks pendek atau pencarian sekali pakai. Algoritma khusus seperti KMP/Rabin-Karp jadi penting untuk teks sangat panjang atau pencarian yang dilakukan berulang-ulang.

// Naive matching cukup saat…

  • Teks & pattern relatif pendek (mis. validasi form, teks UI).
  • Pencarian hanya dilakukan sesekali, bukan berulang.
  • Kejelasan kode lebih penting daripada mikro-optimasi.
  • Sudah ada String.indexOf() bawaan yang cukup cepat.

// Butuh KMP/Rabin-Karp saat…

  • Teks sangat panjang (log, dokumen besar, genom).
  • Pattern yang sama dicari berulang kali di banyak teks.
  • Pattern punya banyak pengulangan internal (naive jadi lambat).
  • Butuh mencari banyak pattern sekaligus (Rabin-Karp cocok).
◆ Pertanyaan penentu

Tanyakan ke kasusmu: "Seberapa besar teksnya, dan seberapa sering pencarian ini dijalankan?" Kalau sekali jalan di teks kecil, naive matching (atau String.indexOf()) sudah cukup. Kalau berulang di teks besar, biaya setup KMP/Rabin-Karp terbayar lunas oleh kecepatan linear-nya.

Studi kasus · Di dunia nyata

Di mana string matching efisien benar-benar dipakai

Tiga contoh nyata di mana pencarian pattern yang efisien bukan sekadar latihan akademik, tapi fondasi langsung dari fitur yang dipakai jutaan orang.

// editor / IDE

Find & replace

Kasus: mencari & mengganti kata di dalam file kode/dokumen yang bisa berukuran besar, seringkali berulang saat kamu mengetik query pencarian. Kenapa perlu efisien: pencarian dijalankan berkali-kali secara real-time saat kamu mengetik — pattern matching yang lambat akan langsung terasa sebagai lag di editor.

// akademik / konten

Plagiarism detector

Kasus: membandingkan kemiripan teks antara satu dokumen dengan ribuan dokumen lain untuk mendeteksi bagian yang disalin. Kenapa perlu efisien: intinya adalah mencari banyak potongan teks (pattern) di dalam kumpulan dokumen besar — pencarian pattern yang lambat membuat proses deteksi tidak praktis untuk skala besar.

// bioinformatika

DNA sequence matching

Kasus: mencari kemunculan suatu urutan gen (pattern) di dalam untai DNA yang sangat panjang. Kenapa perlu efisien: fundamentalnya adalah string matching di alfabet terbatas (A, C, G, T) pada teks yang bisa mencapai jutaan karakter — kompleksitas linear jadi krusial di skala ini.

◆ Benang merahnya

Di ketiga kasus di atas, kesamaannya adalah skala teks yang besar dan/atau pencarian yang dilakukan berulang-ulang. Semakin besar & semakin sering, semakin terasa perbedaan antara pencarian O(n×m) dan O(n+m) — inilah kenapa algoritma pattern matching khusus punya tempatnya sendiri di luar buku teks.

StringBuilder (Java)

Kelas bawaan Java untuk membangun string secara efisien lewat buffer mutable. Jadi pilihan default setiap kali kamu perlu concat string berulang di dalam loop, tanpa harus menulis struktur data sendiri.

// pattern matching tingkat tinggi

Regular Expression (regex)

Bahasa pola tingkat tinggi untuk pencarian & validasi teks yang lebih fleksibel dari sekadar mencari substring persis — dibangun di atas konsep automata & pattern matching yang sama.

// topik lanjutan

Trie

Struktur data pohon yang dioptimalkan untuk pencarian berdasarkan prefix — cocok untuk autocomplete & pencarian kata berulang pada kumpulan string besar, melanjutkan langsung dari ide efisiensi pencarian di bab ini.

Penutup

Jangan mundur & mengulang — manfaatkan yang sudah kamu tahu

String terlihat sederhana, tapi menyimpan jebakan performa yang mudah luput: concat naif yang diam-diam kuadratik, dan pencarian yang mengulang kerja yang sudah dilakukan. String algorithms — dari StringBuilder sampai KMP — semuanya berputar pada satu ide: jangan buang informasi yang sudah kamu punya.

  • String immutable di Java — tiap modifikasi bikin objek baru.
  • StringBuilder untuk concat berulang — hindari O(n²) diam-diam.
  • Naive matching — simpel, O(n×m), banyak backtrack.
  • KMP — manfaatkan failure function, O(n+m), tanpa mundur.
  • == vs .equals() — referensi vs isi, jangan tertukar.
  • Pilih dari skala & frekuensi — bukan karena algoritma yang "lebih canggih".

Aturan emasnya

Untuk manipulasi string berulang, pakai StringBuilder. Untuk pencarian pattern sehari-hari, library built-in (indexOf()) sudah cukup. Baru saat teksnya besar & pencariannya berulang-ulang, algoritma seperti KMP atau Rabin-Karp terbayar — karena keduanya menghindari kerja yang sama diulang berkali-kali, persis seperti tidak perlu menutup buku & mulai dari halaman satu setiap kali gagal.
