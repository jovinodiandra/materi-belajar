// Pendalaman dari deck Connection Pooling — pool in-app #1 untuk Java/JVM

HikariCP — pool koneksi tercepat & teringan di dunia JVM.

Kalau PgBouncer adalah pooler eksternal di depan Postgres, HikariCP adalah pool di dalam aplikasi — pustaka Java/JDBC yang dipakai tiap proses untuk menyimpan koneksi siap pakai. Ia terkenal karena kecil, cepat, & andal, dan jadi default di Spring Boot. Deck ini membahas lengkap: kenapa ia cepat, cara setup, parameter penting, rumus sizing legendarisnya, sampai jebakan production.

Identitas
Pool JDBC di dalam app — "hikari" = cahaya (Jepang)
Sifat
Zero-overhead — ~130 KB, lock-free, sangat cepat
Status
Default Spring Boot — standar de-facto JVM
Kunci
Sizing kecil-tapi-pas — sumber rumus pool terkenal

Kenalan · Apa itu HikariCP

Connection pool JDBC di dalam aplikasi

HikariCP adalah pustaka connection pool untuk JDBC (Java Database Connectivity). Ia hidup di dalam proses aplikasimu, menyediakan objek DataSource yang memberi koneksi siap pakai saat kode memanggil getConnection() — lalu menerima kembali koneksi itu saat di-close().

// tiny

Sangat kecil

JAR hanya sekitar 130 KB tanpa dependensi berat. Filosofinya: lakukan satu hal — mengelola pool — secepat & seringan mungkin.

// default

Default Spring Boot

Sejak Spring Boot 2.0, HikariCP adalah DataSource bawaan. Kalau kamu pakai Spring Boot, kemungkinan besar sudah memakainya.

// reliable

Andal & benar

Bukan cuma cepat — perilakunya saat error, timeout, & koneksi mati dirancang ketat. "Fast + correct".

◆ JDBC standard interface

HikariCP mengimplementasikan javax.sql.DataSource standar. Artinya kode aplikasimu (atau JPA/Hibernate, jOOQ, MyBatis) tidak perlu tahu soal HikariCP — mereka cuma minta Connection dari DataSource. HikariCP-lah yang diam-diam mengelola kolamnya di belakang.

Inti · Rekayasa performa

Kenapa HikariCP begitu cepat

Nama "Hikari" (cahaya) bukan sekadar gaya — kecepatan adalah tujuan desainnya. Kecepatannya datang dari beberapa keputusan rekayasa yang menghilangkan overhead di jalur panas (hot path).

// ConcurrentBag

ConcurrentBag custom

Struktur penyimpan koneksi lock-free buatan sendiri, dioptimalkan agar thread sering mendapat kembali koneksi yang baru saja ia pakai (thread-local) — minim kontensi antar-thread.

// FastList

FastList

Pengganti ArrayList yang membuang pengecekan range & mempercepat operasi remove dari belakang — list yang dipakai melacak statement/koneksi.

// bytecode

Bytecode ramping

Kode inti dijaga kecil agar muat di cache instruksi CPU & ramah JIT inlining. Lebih sedikit instruksi = lebih cepat.

// no overhead

Zero-overhead proxy

Proxy koneksi/statement dibuat efisien (codegen via Javassist) sehingga membungkus JDBC nyaris tanpa biaya tambahan.

◆ Yang sebenarnya bikin cepat: koneksi sudah siap

Semua optimasi mikro di atas penting, tapi keuntungan terbesar tetap sama dengan prinsip pooling di deck induk: handshake mahal (TCP+TLS+auth) sudah dibayar sekali di awal. HikariCP "cuma" menyerahkan koneksi yang sudah nyala secepat mungkin — dan ia melakukannya lebih cepat dari pool lain.

◆
Jangan terjebak mengejar angka benchmark. Untuk hampir semua aplikasi, perbedaan microsecond antar pool tak terasa dibanding latensi query & jaringan. Alasan nyata memilih HikariCP: default yang waras, perilaku error yang benar, & dokumentasi sizing yang bagus — bukan sekadar "tercepat".
Pakai · Setup dasar

Memakai HikariCP langsung (tanpa framework)

Inti penggunaannya: buat HikariConfig, bungkus jadi HikariDataSource sekali saat aplikasi start, lalu pinjam koneksi dengan try-with-resources agar otomatis dikembalikan.

App.java — buat DataSource sekali, pinjam amanJava
import com.zaxxer.hikari.*;

// 1) KONFIG — dibuat SEKALI saat startup
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://localhost:5432/app");
cfg.setUsername("app_user");
cfg.setPassword("secret");
cfg.setMaximumPoolSize(10);

// 2) DATASOURCE — objek bersama, jangan dibuat per request!
HikariDataSource ds = new HikariDataSource(cfg);

// 3) PINJAM — try-with-resources → conn.close() otomatis = RELEASE ke pool
try (Connection conn = ds.getConnection();
     PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id=?")) {
  ps.setLong(1, id);
  ResultSet rs = ps.executeQuery();
  // ... pakai hasil ...
} // ← conn.close() di sini TIDAK menutup koneksi, tapi MENGEMBALIKANNYA ke pool
◆ Kunci: close() = release, bukan tutup

Di dunia pool, connection.close() tidak benar-benar menutup koneksi TCP — ia mengembalikannya ke kolam. try-with-resources menjamin ini terjadi bahkan saat exception, jadi ia adalah versi Java dari finally { release() } di deck induk. Lupa close() = connection leak.

Pakai · Spring Boot

Di Spring Boot: cukup konfigurasi properties

Karena HikariCP adalah default Spring Boot, kamu jarang menyentuh kode. Cukup atur lewat application.properties/yml dengan prefix spring.datasource.hikari.*.

application.properties — konfigurasi HikariCPproperties
# koneksi dasar
spring.datasource.url=jdbc:postgresql://localhost:5432/app
spring.datasource.username=app_user
spring.datasource.password=secret

# tuning pool HikariCP
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=10
spring.datasource.hikari.connection-timeout=30000    # 30s tunggu pinjam
spring.datasource.hikari.idle-timeout=600000        # 10m
spring.datasource.hikari.max-lifetime=1800000       # 30m
spring.datasource.hikari.pool-name=AppHikariPool
◆ Rekomendasi resmi: minimumIdle = maximumPoolSize

Tim HikariCP menyarankan tidak memakai pool yang menyusut-membesar untuk beban produksi. Set minimum-idle = maximum-pool-size agar pool berukuran tetap — menghindari spike latensi saat pool harus membuka koneksi baru mendadak di tengah lonjakan.

◆
Spring Boot membuat satu DataSource bersama untuk seluruh aplikasi — itu benar. Jangan tergoda membuat HikariDataSource manual per modul/request; itu mengulang anti-pola "pool per request" dari deck induk.
◆ Tuning · Parameter

Parameter kunci yang wajib dimengerti

HikariCP sengaja punya sedikit knob — itu fitur, bukan kekurangan. Ini yang paling penting; pahami artinya, bukan cuma namanya.

◆ Tujuh parameter inti
maximumPoolSizejumlah koneksi maksimum (paling penting)
minimumIdlekoneksi idle minimum (saran: = max)
connectionTimeoutmaks tunggu pinjam koneksi (default 30s)
idleTimeoutkoneksi idle ditutup setelah ini (default 10m)
maxLifetimeumur maks koneksi, lalu diremajakan (default 30m)
keepaliveTimeping berkala agar koneksi tak mati diam-diam
leakDetection...peringatkan koneksi dipinjam kelamaan
// maximumPoolSize

Batas atas koneksi

Paling krusial. Inilah yang melindungi DB dari kebanjiran. Bab berikut khusus soal angka ini.

// connectionTimeout

Sabar menunggu giliran

Semua koneksi dipakai → kode menunggu. Lewat batas → lempar SQLException, daripada hang selamanya. Ini bukan query timeout.

// maxLifetime

Peremajaan berkala

Koneksi tua ditutup & diganti. Mencegah koneksi basi & masalah saat DB failover. Harus lebih pendek dari timeout DB/firewall.

// keepaliveTime

Jaga tetap hidup

Ping koneksi idle berkala supaya firewall/DB tak diam-diam memutusnya. Tambahan modern untuk koneksi yang sangat lama idle.

◆ Tuning · Sizing

Pool sizing: kecil-tapi-pas (sumber rumusnya)

Dokumen "About Pool Sizing" dari HikariCP adalah rujukan yang dikutip deck induk. Temuannya kontra-intuitif: pool kecil sering memberi throughput lebih tinggi daripada pool besar.

“Pool koneksi yang lebih kecil, secara mengejutkan, sering memberi throughput yang lebih tinggi.”

— HikariCP wiki, About Pool Sizing
rumus titik-awal (PostgreSQL)rule of thumb
# formula klasik untuk beban berat CPU/disk:
koneksi = (jumlah_core_CPU_db × 2) + jumlah_disk_efektif

# contoh: DB 4 core, 1 SSD
koneksi = (4 × 2) + 1 = 9     # ya, ~10 — bukan 100!

# INGAT: ini per-aplikasi. Kalau app jalan di 10 instance,
# maximumPoolSize=10 → 100 koneksi ke DB. Hitung totalnya.
◆ Kenapa kecil menang — analogi jalan tol

Core CPU itu seperti lajur tol. Punya 4 lajur (core) tapi memaksa 100 mobil (koneksi) jalan bareng tidak bikin lebih cepat — malah macet karena terus ganti-ganti lajur (context switch). Dengan ~8-10 mobil di 4 lajur, semua mengalir lancar. Lebih sedikit koneksi yang sibuk > banyak koneksi yang rebutan.

◆ Rumus cuma titik awal — ukur!

Angka ini permulaan, bukan harga mati. Pantau metrik HikariCP (lewat JMX/Micrometer): hikaricp.connections.active, hikaricp.connections.pending (antrian!), & hikaricp.connections.usage. Kalau pending sering > 0 dan DB belum jenuh, naikkan sedikit. Selalu jaga: (pool × jumlah instance) ≤ max_connections DB.

⚙ Tuning · Keandalan

Deteksi leak & validasi koneksi

Deck induk menyebut connection leak sebagai bug paling sering. HikariCP punya alat bawaan untuk memburunya — plus mekanisme memastikan koneksi yang dipinjam benar-benar hidup.

leakDetectionThreshold — log koneksi yang dipinjam kelamaanproperties
# jika sebuah koneksi dipinjam lebih lama dari ini (ms),
# HikariCP menulis stack trace si peminjam ke log → ketahuan siapa yang bocor
spring.datasource.hikari.leak-detection-threshold=20000   # 20 detik

# gejala leak (dari deck induk): app melambat perlahan lalu hang,
# tanpa lonjakan trafik. Aktifkan ini di staging untuk berburu.
// leak detection

leakDetectionThreshold

Bukan memperbaiki leak, tapi menunjukkan kode mana yang menahan koneksi terlalu lama — lewat stack trace di log. Pasang saat investigasi.

// validation

Validasi otomatis

Sebelum diserahkan, HikariCP memvalidasi koneksi via Connection.isValid() (JDBC4). Tak perlu connectionTestQuery untuk driver modern.

// validationTimeout

validationTimeout

Batas waktu validasi tersebut. Koneksi yang gagal dicek dibuang & diganti — kamu tak pernah dapat koneksi yang diam-diam mati.

◆
Solusi nyata untuk leak tetap sama seperti di deck induk: selalu pinjam koneksi dengan try-with-resources (atau biarkan Spring/JPA mengelola transaksi). leakDetectionThreshold hanya alat diagnosis — pencegahan ada di disiplin kode.
Praktik · Production

Jebakan production yang sering bikin pusing

HikariCP punya default yang waras, tapi beberapa interaksi dengan DB/jaringan tetap perlu kamu sadari di produksi.

// maxLifetime

maxLifetime ≥ timeout DB

Kalau DB/firewall memutus koneksi idle pada 5 menit tapi maxLifetime 30 menit, kamu dapat error "connection closed". Aturan: maxLifetime beberapa detik LEBIH PENDEK dari timeout terpendek di jalur (DB, firewall, load balancer).

// connTimeout

connectionTimeout ≠ query timeout

Sering ketukar. Yang ini "berapa lama nunggu dapat koneksi dari pool", bukan "berapa lama query boleh jalan". Set query timeout terpisah (JDBC/JPA).

// instance count

Lupa kalikan instance

maximumPoolSize × jumlah pod = total ke DB. Auto-scaling ke 50 pod dengan pool 20 = 1.000 koneksi. Inilah pemicu butuh PgBouncer.

// long tx

Transaksi/query lambat menahan

Satu transaksi panjang menahan koneksi dari pool. Beberapa saja sudah bisa mengosongkan pool kecil walau ukurannya "cukup". Jaga transaksi pendek.

// pending

Abai metrik pending

hikaricp.connections.pending > 0 terus = ada yang antri. Sinyal pool kekecilan ATAU query lambat. Pantau, jangan menebak.

// autoCommit

autoCommit & reset state

HikariCP mereset state koneksi saat dikembalikan (autoCommit, isolation). Andalkan ini, jangan biarkan state "bocor" antar peminjaman.

◆ Arsitektur · Dua lapis

HikariCP + PgBouncer: bukan saling menggantikan

Pertanyaan umum: "kalau sudah pakai PgBouncer, masih perlu HikariCP?" Jawabannya ya — keduanya bekerja di lapisan berbeda dan saling melengkapi.

// HikariCP (in-app)

  • Menghemat handshake untuk satu proses JVM.
  • Memberi koneksi ke kode/JPA secepat mungkin.
  • Mengelola lifecycle, validasi, leak detection.
  • Tahu konteks aplikasi (thread, transaksi).

// PgBouncer (eksternal)

  • Meredam total koneksi dari SEMUA proses.
  • Wajib untuk auto-scaling & serverless.
  • Maintenance Postgres tanpa memutus app.
  • Tahu konteks armada (banyak instance, satu DB).
◆
Saat HikariCP berada di depan PgBouncer dengan pool_mode = transaction: matikan fitur yang mengasumsikan koneksi lengket. Khususnya, untuk PgBouncer lama, atur driver/Hibernate agar tidak bergantung pada server-side prepared statement (atau pakai PgBouncer ≥ 1.21). Set maxLifetime HikariCP lebih pendek dari server_idle_timeout PgBouncer.
◆ Aturan praktis dua lapis

HikariCP maximumPoolSize per instance dijaga kecil (mis. 5–10). PgBouncer default_pool_size menjaga total koneksi nyata ke Postgres tetap kecil & pasti, berapa pun jumlah instance app. Hasilnya: cepat di tiap proses (HikariCP) dan aman di tingkat armada (PgBouncer). Lihat deck PgBouncer →.

Penutup

HikariCP dalam satu tarikan napas

Pool JDBC kecil, cepat, & benar yang jadi default JVM. Buat DataSource sekali, pinjam dengan try-with-resources, ukur poolnya kecil-tapi-pas, dan jaga maxLifetime lebih pendek dari timeout di jalur.

  • Pool JDBC in-app — ~130 KB, default Spring Boot.
  • Cepat karena hot path ramping — ConcurrentBag, FastList, proxy ringan.
  • close() = release — pakai try-with-resources, cegah leak.
  • Sedikit knob — maximumPoolSize paling penting.
  • Kecil-tapi-pas — (core × 2) + disk; ukur lewat metrik pending.
  • maxLifetime < timeout jalur — hindari koneksi basi.
  • Pelengkap PgBouncer — in-app + eksternal, dua lapis.

Langkah belajar berikutnya

Di proyek Spring Boot, set spring.datasource.hikari.maximum-pool-size=10 & minimum-idle=10, aktifkan metrik via Micrometer/Actuator, lalu beri beban (mis. dengan k6/JMeter). Amati hikaricp.connections.active & .pending di Grafana — turunkan/naikkan pool size & lihat efeknya pada throughput & latensi. Itu membuktikan sendiri "kecil-tapi-pas".
