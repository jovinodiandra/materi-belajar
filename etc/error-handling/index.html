Error Handling

Error pasti terjadi. Yang membedakan sistem bagus dan buruk: error ditangani di tempat yang tepat, dengan pesan yang jelas, dan tidak disembunyikan.

$ Jatuh itu biasa. Yang penting tahu cara bangun.

Error ditangkap di 5 lapisan, dicatat 5 kali, dan pesannya hilang di tengah jalan.

🙈

Error ditelan

catch kosong. Program lanjut dengan data rusak.

📢

Dicatat berkali-kali

Satu error = 5 baris log di 5 lapisan.

❓

Pesan tidak membantu

“Something went wrong.” Untuk user dan developer.

Tangani di tempat yang tepat

jangan telan, jangan dobel, beri konteks

◆ Buat apa ini? Kenapa pakai ini?

Given — kode memanggil banyak lapisan yang bisa gagal.

When — setiap lapisan menangani error dengan caranya sendiri.

Then — error hilang, dobel di log, dan sulit dilacak.

→ makanya kita pakai strategi error handling — supaya setiap error ditangani sekali, di tempat yang tepat.

warm-up

Berapa kali error ini tercatat?

// repository
catch (SQLException e) { log.error("db error", e); throw new RepoException(e); }
// service
catch (RepoException e) { log.error("service error", e); throw new ServiceException(e); }
// controller
catch (ServiceException e) { log.error("api error", e); return 500; }
  • Satu kejadian, berapa stack trace di log?

Aturan praktis

jangan

Telan error

jangan

Log sekali, di tempat penanganan terakhir.

lakukan

Bungkus dengan konteks

“Gagal memuat order 42: timeout ke payment”.

lakukan

Gagal cepat

Input salah? Tolak di awal, jangan biarkan masuk lebih dalam.

satu tempat

Penanganan error terpusat

@RestControllerAdvice
@ExceptionHandler(OrderNotFound.class)
ProblemDetail notFound(OrderNotFound e) {
  return ProblemDetail.forStatusAndDetail(
      NOT_FOUND, e.getMessage());
}

@ExceptionHandler(Exception.class)
ProblemDetail unexpected(Exception e) {
  log.error("unexpected", e);   // log di sini saja
  return ProblemDetail.forStatus(INTERNAL_SERVER_ERROR);
}
hasilnya
✓ Controller bersih dari try-catch
✓ Format error seragam
✓ Error bisnis (404) tidak jadi ERROR log
✓ Error tak terduga dicatat sekali,
  detail tidak bocor ke user
Lapisan lain cukup melempar. Satu tempat yang menangani.
retry

Error sementara: coba lagi dengan bijak

Panggilan gagal (timeout)
→
Tunggu 200 ms, coba lagi
→
Gagal: tunggu 400 ms, 800 ms
→
Maksimal 3x, lalu menyerah
  • Hanya retry error sementara (timeout, 503). Jangan retry 400 atau 404.
  • Aksi yang di-retry harus idempotent.
pesan

Pesan untuk siapa?

untuk user

Jelas & bisa ditindaklanjuti

"Pembayaran gagal. Saldo tidak terpotong. Coba lagi."

untuk developer

Lengkap & bisa dicari

orderId, traceId, penyebab asli, stack trace — di log.

untuk penyerang

Tidak ada

Jangan tampilkan stack trace, query SQL, atau versi server.
