// Database — saat servernya adalah aplikasimu sendiri

Database yang tinggal di dalam aplikasimu, bukan di server lain.

Tidak semua aplikasi hidup dengan koneksi internet yang selalu menyala. Aplikasi mobile, desktop, dan perangkat edge tetap butuh tempat menyimpan data — tanpa harus menelepon server database yang entah di mana. Embedded database seperti SQLite menjawabnya: database yang di-link langsung ke dalam proses aplikasimu, hidup sebagai satu file di disk. Deck ini buat pemula: dari kenapa ia lahir, konsepnya, kapan cukup untuk production, sampai tools di sekitarnya — diselingi kutipan dari dokumentasi resminya.

Sakit
Gak selalu ada server DB — mobile, desktop, edge sering offline
Ide
Database jadi library — di-link ke app, data = satu file
Untung
Zero-config & cepat — tanpa install server, tanpa network round-trip
Batas
Concurrency terbatas — satu writer, bukan untuk banyak server
Pakai
Saat app itu sendiri = tempatnya — mobile, desktop, cache, format file

◆ Kenapa pakai ini?

Given — aplikasi notes di HP, software kasir toko kecil, atau sensor IoT nggak selalu tersambung ke server database pusat, tapi tetap wajib menyimpan data dengan rapi di perangkatnya sendiri.

When — developer akhirnya menyimpan data lewat fopen()/file teks manual biar praktis, atau sebaliknya memaksa instal PostgreSQL/MySQL terpisah di tiap perangkat cuma untuk data lokal yang kecil.

Then — file teks manual gampang korup, susah di-query, dan rawan race condition; sedangkan server DB terpisah bikin instalasi berat, butuh koneksi jaringan yang belum tentu tersedia, dan boros resource untuk beban kerja yang sebenarnya sepele.

→ makanya kita pakai embedded database.

Akar masalah · Kenapa embedded database ada

Tidak semua aplikasi punya server database di dekatnya

Waktu kamu bikin API backend, wajar mengasumsikan ada server database terpisah yang selalu menyala di jaringan yang sama. Tapi coba pikirkan: aplikasi notes di HP-mu, aplikasi desktop akuntansi kantor kecil, atau sensor IoT di pabrik — mereka tidak selalu online, dan menaruh database terpisah untuk tiap instalasi itu berlebihan.

“SQLite tidak bersaing dengan database client/server. SQLite bersaing dengan fopen().”

— paraphrase dari dokumentasi resmi SQLite, “Appropriate Uses For SQLite” (sqlite.org)

Maksudnya: SQLite tidak dirancang untuk menggantikan PostgreSQL atau MySQL di beban kerja yang butuh banyak penulis dari banyak mesin sekaligus. Ia dirancang untuk menggantikan cara aplikasi biasa menyimpan data — file teks, file konfigurasi, atau struktur data yang ditulis manual ke disk lewat fopen() — dengan cara yang jauh lebih tertata: lewat SQL.

◆ Analogi — dompet vs brankas bank

Database server terpisah itu seperti brankas di bank: aman, kuat, bisa diakses banyak orang sekaligus — tapi kamu harus pergi ke sana, dan kalau bank tutup atau jaringanmu putus, uangmu tak terjangkau. Embedded database itu seperti dompet di kantongmu: selalu ada, siap dipakai kapan saja, tanpa perlu izin atau koneksi ke pihak lain — cocok untuk kebutuhan sehari-hari yang tidak butuh skala brankas bank.

Konsep inti · Database sebagai library

Databasenya hidup di dalam proses aplikasimu

Embedded database bukan proses terpisah yang kamu hubungi lewat jaringan. Ia adalah library yang di-link langsung ke dalam program aplikasimu, dan seluruh datanya disimpan dalam satu file biasa di disk. Tidak ada proses server, tidak ada port, tidak ada login — database-nya ya aplikasi itu sendiri.

◆ Padanan istilah client/server ↔ embedded
Server DB→ Tidak ada, jadi bagian dari proses aplikasi
host:port→ Path file, mis. app.db
Install→ Cukup tambah 1 library ke project
Akses→ Panggilan fungsi in-process, bukan lewat jaringan

Inti bedanya: di client/server, aplikasi & database adalah dua proses berbeda yang bicara lewat jaringan; di embedded, keduanya adalah satu proses yang sama.

notes.py — SQLite langsung dari Python, tanpa serverPython
import sqlite3

# "app.db" adalah SATU FILE di disk — bukan alamat server
conn = sqlite3.connect("app.db")
cur = conn.cursor()

cur.execute("""
    CREATE TABLE IF NOT EXISTS notes (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        title TEXT NOT NULL,
        body TEXT,
        created_at TEXT DEFAULT CURRENT_TIMESTAMP
    )
""")

cur.execute(
    "INSERT INTO notes (title, body) VALUES (?, ?)",
    ("Belanja", "Beli kopi & susu")
)
conn.commit()

cur.execute("SELECT id, title, body FROM notes ORDER BY id DESC")
for row in cur.fetchall():
    print(row)

conn.close()  # tak ada koneksi jaringan yang perlu ditutup, cuma file handle

“Format file database SQLite bersifat lintas-platform — kamu bisa membuat & mengisinya di satu mesin lalu memakainya di mesin lain dengan arsitektur berbeda, tanpa konversi apa pun.”

— paraphrase gagasan dari dokumentasi SQLite, bagian “Well-Known Uses” (sqlite.org)

Gagasan ini yang membuat SQLite dipakai sebagai format file aplikasi, cache lokal, dan format pertukaran data — satu file .db yang portabel, bisa dikirim, disalin, atau dibuka di perangkat lain tanpa perlu menginstal apa pun selain aplikasinya sendiri.

Meluruskan mitos · Bukan cuma buat mainan

Kapan SQLite cukup dipakai di production

Banyak yang menyangka SQLite cuma cocok untuk prototyping atau testing, lalu wajib pindah ke Postgres/MySQL begitu masuk production. Kenyataannya, SQLite adalah salah satu database yang paling banyak dipakai di dunia — hanya saja untuk bentuk beban kerja tertentu, bukan segala beban kerja.

◆
Mitos: "SQLite cuma buat mainan/testing." Faktanya: SQLite dirancang untuk menjadi pengganti fopen() — cara aplikasi menyimpan data ke file — bukan pengganti database server untuk beban kerja dengan banyak penulis dari banyak mesin. Untuk aplikasi single-node yang membaca jauh lebih sering daripada menulis, SQLite bisa sangat andal di production — dipakai jutaan perangkat & aplikasi setiap hari.

// SQLite cukup untuk production saat…

  • Aplikasi mobile / desktop — satu pengguna, satu proses.
  • Beban baca jauh lebih dominan daripada tulis.
  • Skala tim/traffic kecil–menengah, satu server aplikasi.
  • Perangkat edge / IoT yang harus jalan tanpa jaringan.
  • Butuh file data yang portabel & mudah di-backup.

// Kurang cocok saat…

  • Banyak server aplikasi menulis ke database yang sama.
  • Traffic tulis tinggi & konkuren dari banyak klien jaringan.
  • Butuh kontrol akses & user management ala DB server.
  • Butuh replikasi multi-writer bawaan lintas region.
◆ Praktik · Supaya tetap sehat di production

Best practice pakai SQLite di production

SQLite ramah dipakai, tapi tetap ada kebiasaan yang membedakan setup yang tangguh dari yang rawan bermasalah saat traffic naik.

  • Aktifkan WAL mode — PRAGMA journal_mode=WAL; memungkinkan pembaca & satu penulis jalan bersamaan tanpa saling mengunci, jauh lebih baik untuk concurrency dibanding mode default.
  • Set busy_timeout — PRAGMA busy_timeout=5000; supaya proses yang bentrok menunggu sejenak dan retry, bukan langsung gagal dengan error "database is locked".
  • Backup file .db secara rutin — karena semua data ada di satu file, backup-nya sesederhana menyalin file (idealnya lewat VACUUM INTO atau alat seperti Litestream, bukan menyalin file mentah saat sedang ditulis).
  • Hindari banyak writer bersamaan — SQLite hanya mengizinkan satu penulis aktif dalam satu waktu; desain aplikasimu supaya penulisan berat diantre, bukan ditembakkan paralel dari banyak proses.
  • Jaga transaksi tetap pendek — transaksi yang lama menahan lock lebih panjang & memperbesar peluang "database is locked" pada penulis lain.
  • Pasang index sesuai pola query — sama seperti database lain, tanpa index yang tepat, query lambat walau datanya di file lokal sekalipun.
🌱 Jenjang · Tier belajar

Belajar embedded database selangkah demi selangkah

Tidak perlu langsung paham replikasi. Ini peta belajar dari dasar sampai siap pakai di production.

🌱 Beginner

CRUD dasar dengan SQLite

Fokus dulu ke operasi paling dasar: bikin tabel, insert, select, update, delete lewat satu file .db.

  • Buka koneksi ke file .db lokal
  • CREATE TABLE, INSERT, SELECT
  • Pakai parameter query, jangan string concat
  • Coba lewat CLI sqlite3 langsung
⚙ Middle

Pakai di aplikasi mobile/desktop nyata

Integrasikan SQLite ke dalam aplikasi sungguhan yang punya siklus hidup & state.

  • Android (Room) / iOS (Core Data, GRDB)
  • Desktop: Electron (better-sqlite3), Tauri
  • Migrasi skema antar versi aplikasi
  • Query builder / ORM ringan
🚀 Advance

WAL, replikasi, & kapan migrasi

Menjadikan SQLite andal di production skala kecil-menengah, sekaligus tahu batasnya.

  • WAL mode & tuning PRAGMA
  • Replikasi dengan Litestream ke object storage
  • SQLite terdistribusi (Turso/libSQL)
  • Kenali sinyal kapan harus pindah ke DB server
◆ Harga · Tidak ada makan siang gratis

Trade-off: yang kamu dapat & yang kamu korbankan

Embedded database bukan "lebih sederhana jadi lebih lemah" — ia menukar hal yang berbeda dibanding database server. Paham trade-off-nya bikin kamu memilih dengan sadar, bukan ikut-ikutan.

// Yang kamu dapat

  • Zero-config — tidak perlu install & kelola server terpisah.
  • Sangat cepat untuk baca — panggilan fungsi lokal, tanpa round-trip jaringan.
  • Satu file portabel — gampang dikirim, disalin, di-backup.
  • Jalan tanpa koneksi internet sama sekali.

// Yang kamu korbankan

  • Concurrency terbatas — hanya satu writer aktif dalam satu waktu.
  • Tak cocok untuk banyak writer bersamaan dari banyak server.
  • Tidak ada akses jaringan bawaan / user management ala server DB.
  • Skala horizontal (banyak app server ke satu DB) bukan kekuatannya.
◆ Catatan zaman sekarang

Batas ini mulai melunak. Dengan WAL mode, concurrency baca-tulis SQLite jauh lebih baik dari dulu. Dan dengan proyek seperti Litestream atau Turso/libSQL, keterbatasan "satu file di satu mesin" mulai bisa direplikasi/didistribusikan — tanpa kehilangan kesederhanaan SQLite.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai embedded database

Aturan praktisnya: kalau aplikasimu sendiri adalah satu-satunya yang menulis ke datanya, embedded database cocok. Kalau datanya harus ditulis bersama oleh banyak proses/server, pakai database server.

◆ Pertanyaan penentu

Tanyakan satu hal: "Apakah data ini hanya diakses oleh satu proses aplikasi dalam satu waktu?" Kalau ya (app mobile, app desktop, satu proses backend kecil) → embedded database. Kalau datanya harus dibaca & ditulis bersamaan oleh banyak server/instance → database client/server.

// Pakai embedded saat…

  • Aplikasi mobile, desktop, atau CLI single-user.
  • Perangkat edge/IoT yang harus tetap jalan offline.
  • Cache lokal, format file aplikasi, atau data uji.
  • Backend kecil dengan satu instance & traffic moderat.

// Pilih database server saat…

  • Banyak instance aplikasi menulis ke data yang sama.
  • Butuh akses jaringan terkontrol dari banyak klien.
  • Traffic tulis tinggi & konkuren dari banyak sumber.
  • Butuh fitur enterprise: role, audit, replikasi multi-writer.
Studi kasus · Di dunia nyata

Embedded database di production, tiap hari

Kamu mungkin memakai puluhan embedded database tiap hari tanpa sadar. Ini beberapa contoh nyata di mana SQLite jadi tulang punggung, bukan sekadar alat belajar.

// mobile OS

Android & iOS

Kasus: SQLite tertanam di hampir setiap ponsel — dipakai oleh sistem operasi maupun banyak aplikasi pihak ketiga untuk penyimpanan data lokal. Kenapa embedded: tiap perangkat butuh database sendiri, offline-first, tanpa server terpusat.

// browser

Chrome & Firefox

Kasus: browser modern seperti Chrome dan Firefox memakai SQLite untuk menyimpan berbagai data lokal di sisi klien. Kenapa embedded: data milik satu instalasi browser di satu mesin, tak perlu server terpisah.

// web production

Litestream & Fly.io

Kasus: proyek seperti Litestream mempopulerkan SQLite sebagai database production untuk aplikasi web berskala kecil–menengah, dengan replikasi terus-menerus ke object storage sebagai backup/disaster recovery. Kenapa embedded: kesederhanaan & kecepatan baca lokal, dengan jaring pengaman replikasi.

// desktop apps

Aplikasi desktop

Kasus: banyak aplikasi desktop memakai file .db SQLite sebagai format penyimpanan datanya sendiri — mulai dari aplikasi produktivitas sampai tools developer. Kenapa embedded: satu file portabel yang gampang dibuka, disalin, dan di-backup pengguna.

◆ Benang merahnya

Di semua kasus di atas: data itu milik satu proses/perangkat pada satu waktu, dan kesederhanaan + kecepatan baca lokal jauh lebih berharga daripada fitur database server. Begitu kebutuhan bergeser ke banyak penulis dari banyak mesin sekaligus, tim biasanya menambah database server di samping — atau memakai lapisan replikasi seperti Litestream/Turso, bukan menulis ulang semuanya dari nol.

◆
Anti-pola yang bikin menyesal: menaruh file SQLite di network share lalu diakses banyak server aplikasi sekaligus lewat NFS/SMB. Ini melanggar asumsi dasar SQLite tentang locking file lokal & sering berujung korupsi data atau lock yang tidak jelas.
⚙ Ekosistem · Alat yang dipakai

Tools di sekitar embedded database

Cukup kenali nama populernya & kapan kira-kira dipakai. Sebagai pemula, mulai dari SQLite — sisanya adalah lapisan tambahan begitu kebutuhanmu bertumbuh.

// paling populer

SQLite

Embedded database paling banyak dipakai di dunia. Satu file, zero-config, tersedia hampir di semua bahasa pemrograman. Titik awal wajib untuk belajar.

// replikasi

Litestream

Mereplikasi file SQLite secara terus-menerus ke object storage (mis. S3). Memberi SQLite jaring pengaman backup & disaster recovery ala database server.

// terdistribusi

Turso / libSQL

Fork SQLite yang dibuat mendukung replikasi & distribusi lintas region, tetap kompatibel dengan API SQLite yang sudah familiar.

// analytics

DuckDB

Embedded database yang fokus ke analytics (kolom, agregasi berat) — "SQLite-nya dunia OLAP". Cocok untuk analisis data lokal tanpa infrastruktur besar.

◆ Tips pemula

Bingung mulai dari mana? Instal sqlite3, buat satu file .db, dan coba CRUD dasar lewat CLI atau driver bahasa pemrogramanmu. Baru pikirkan Litestream/Turso setelah kamu benar-benar butuh replikasi — jangan mengoptimalkan masalah yang belum kamu punya.

Penutup

Pilih sesuai siapa yang menulis datamu

Embedded database lahir dari kebutuhan yang sangat manusiawi: aplikasi butuh menyimpan data, tapi tidak selalu punya server database di dekatnya. SQLite mengisi celah itu dengan menjadi database yang hidup di dalam aplikasimu sendiri.

  • Bukan pengganti server DB — SQLite bersaing dengan fopen(), bukan dengan Postgres/MySQL.
  • Satu file, satu proses — database di-link sebagai library, tanpa server terpisah.
  • Cukup untuk production — selama satu proses yang menulis, bukan cuma buat mainan.
  • WAL mode = teman baikmu — concurrency baca-tulis jauh lebih baik.
  • Backup file-nya rutin — data selokal itu, tanggung jawabnya jadi milikmu.
  • Pilih dari siapa penulisnya — satu proses → embedded, banyak server → database client/server.

Aturan emasnya

Tanya: "Apakah hanya satu proses aplikasi yang menulis ke data ini dalam satu waktu?" Kalau ya, embedded database memberimu kesederhanaan & kecepatan tanpa infrastruktur tambahan. Kalau datamu harus ditulis bersama oleh banyak server sekaligus, database client/server akan menyelamatkanmu dari lock & konflik. Tidak ada yang menang untuk segalanya — pilih sesuai siapa yang mengakses data, dan dari mana.
