Cache Stampede

Cache habis, lalu ribuan request serentak menyerbu database. Database pun tumbang.

$ Kayak pintu mal dibuka pas diskon besar: semua lari bareng.

kejadiannya

Urutan kejadian stampede

Cache key populer expired
→
1000 request: "cache kosong!"
→
1000 query sama ke DB
→
DB lemot / mati
  • Semua request mengerjakan hal yang sama persis di waktu yang sama.
  • Padahal cukup satu yang ambil ke DB, sisanya tinggal nunggu.
warm-up

Kenapa database mati tepat jam 12:00:00?

Setiap hari jam 12.00 tepat, CPU database melonjak ke 100% selama beberapa detik.

// dijalankan saat deploy jam 11:00:00
cache.set("home", data, ttl = 3600)
  • Apa hubungan jam deploy dengan lonjakan jam 12?
contoh

Semua ke DB vs satu yang ke DB

✗ Semua request ke DB
data = cache.get("home")
if (data == null) {
  data = db.query(...)   // ← 1000x serentak
  cache.set("home", data, 60)
}
✓ Pakai kunci (lock)
data = cache.get("home")
if (data == null) {
  if (lock.tryAcquire("home")) {
    data = db.query(...)   // ← cuma 1x
    cache.set("home", data, 60)
    lock.release("home")
  } else {
    sleep(50); return retry()
  }
}
cara lain

Trik lain biar tidak serentak

trik

TTL acak

Jangan semua 60 detik. Pakai 55–65 detik biar tidak habis bareng.

trik

Refresh sebelum habis

Kalau sisa umur cache tinggal sedikit, perbarui di belakang layar.

trik

Sajikan data lama dulu

Kasih data basi sebentar sambil satu proses ambil yang baru.

Tujuannya sama: jangan biarkan semua request jadi "yang pertama".
Caffeine

Satu loader per key, otomatis

Java: Caffeine
LoadingCache<String, Page> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .refreshAfterWrite(Duration.ofMinutes(8))
    .build(key -> db.loadPage(key));

cache.get("home");
yang terjadi
1000 request bersamaan untuk "home"
→ hanya 1 yang memanggil db.loadPage
→ 999 lainnya menunggu hasil yang sama

refreshAfterWrite 8 menit:
→ diperbarui di belakang sebelum habis
→ user tetap dapat data lama sementara
Cache lokal yang bagus sudah punya pengaman stampede bawaan.
studi kasus

Kronologi: restart Redis

Redis di-restart, cache kosong
→
Semua key miss bersamaan
→
DB menerima 50x query normal
→
DB timeout, aplikasi ikut error
  • Perbaikan: pemanasan cache (warm-up) sebelum menerima trafik, dan batas konkurensi ke DB.
checklist

Checklist anti-stampede

  • TTL diberi jitter acak.
  • Hanya satu yang mengisi ulang per key (lock / single-flight).
  • Key populer diperbarui di belakang layar sebelum kedaluwarsa.
  • Ada rencana kalau cache kosong total (warm-up, batas query ke DB).

Tiga hal untuk diingat

❯ penyebab

Key populer expired, semua request ke DB bareng.

❯ obat utama

Lock: cuma satu yang isi ulang cache.

❯ pencegahan

TTL acak dan refresh sebelum expired.
