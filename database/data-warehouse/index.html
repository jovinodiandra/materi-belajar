// Database — saat kamu butuh bertanya, bukan mencatat

Database produksi untuk mencatat. Data warehouse untuk bertanya.

Database aplikasi kamu jago melayani jutaan transaksi kecil: tambah pesanan, ubah saldo, simpan profil. Tapi begitu bos minta laporan "total penjualan per wilayah per kuartal selama 3 tahun", database yang sama bisa megap-megap — query berat itu mengunci tabel dan bikin aplikasi lemot untuk semua orang. Data warehouse lahir dari rasa sakit ini: database terpisah, khusus untuk analisis. Deck ini buat pemula — dari kenapa ia ada, cara kerjanya, trade-off-nya, kapan dipakai, sampai tools-nya, diselingi kalimat dari buku rujukan.

Sakit
Analitik bikin OLTP lemot — query berat mengunci database produksi
Pisah
Bikin database khusus analisis — salinan data, terpisah dari produksi
Isi
ETL dari banyak sumber — kumpulkan, bersihkan, satukan
Tata
Star schema + columnar — ditata supaya query analitik kilat
Pakai
BI, dashboard, tren — ambil keputusan dari data

◆ Buat apa ini? Kenapa pakai Data Warehouse?

Given — database produksi (OLTP) kamu dioptimalkan untuk transaksi kecil-cepat: checkout, update stok, simpan profil — bukan untuk menjumlahkan jutaan baris sekaligus, dan datanya tersebar di banyak sistem terpisah (order, stok, CRM) dengan format masing-masing.

When — tim bisnis minta laporan gabungan seperti "total penjualan per wilayah per kuartal, 3 tahun terakhir", yang berarti scan & join tabel raksasa lintas sistem sekaligus.

Then — kalau query analitik itu dijalankan langsung di database produksi, ia mengunci tabel, menyedot CPU & memori, dan bikin aplikasi yang melayani pelanggan ikut lemot untuk semua orang — sementara datanya sendiri tetap tercerai-berai dan sulit disatukan.

→ makanya kita pakai Data Warehouse: database terpisah, berisi salinan data yang sudah dirapikan & ditata khusus untuk pertanyaan analitik besar, tanpa mengganggu database produksi.

Study kasus · Rasa sakit yang melahirkannya

Saat satu laporan membuat seluruh aplikasi tersendat

Bayangkan sebuah perusahaan ritel. Database produksinya sibuk 24 jam: pelanggan checkout, stok berkurang, pembayaran masuk. Lalu tim bisnis bertanya: "Berapa total penjualan per kategori, per wilayah, per bulan, selama 3 tahun terakhir?"

query analitik di database PRODUKSISQL
SELECT wilayah, kategori, date_trunc('month', tanggal) AS bulan,
       SUM(total) AS omzet
FROM orders
JOIN order_items USING (order_id)
JOIN products  USING (product_id)
WHERE tanggal >= '2022-01-01'
GROUP BY wilayah, kategori, bulan;
-- 🐢 memindai PULUHAN JUTA baris, mengunci tabel,
-- aplikasi checkout ikut melambat untuk SEMUA pelanggan

Dua masalah menumpuk sekaligus, dan keduanya nyata:

// Mengganggu produksi

  • Query analitik berat memakan CPU, memori, & mengunci tabel.
  • Aplikasi yang melayani pelanggan ikut tersendat.
  • DBA pun ogah mengizinkan analis bermain di DB produksi.

// Data tercerai-berai

  • Penjualan di satu sistem, stok di lain, CRM di lain lagi.
  • Mau gabungkan semua untuk satu laporan? Rumit & rapuh.
  • Tiap sistem punya format & istilah berbeda.
◆ Analogi — dapur restoran vs. ruang manajer

Dapur restoran (database produksi) dirancang untuk kecepatan melayani pesanan satu per satu saat jam sibuk. Kalau kamu menyuruh seorang analis berdiri di tengah dapur untuk menghitung total bahan yang terpakai sepanjang tahun, dia akan menghalangi semua koki. Solusinya: pindahkan analisis ke ruang terpisah berisi salinan catatan — itulah data warehouse.

Konsep inti · Dua pola beban berbeda

OLTP vs OLAP: mencatat vs. menganalisis

Akar persoalannya: ada dua jenis beban kerja yang sangat berbeda, dan satu database sulit jago di keduanya sekaligus. Database produksi adalah OLTP (Online Transaction Processing); data warehouse adalah OLAP (Online Analytical Processing).

“Data warehouse adalah database terpisah yang bisa dikueri analis sepuasnya, tanpa mengganggu operasi OLTP.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 3)
◆ Membandingkan dua dunia
OLTPbanyak transaksi kecil — "tambah 1 pesanan"
OLAPsedikit query besar — "rata-rata semua pesanan 3 tahun"
OLTPbaca/tulis beberapa baris per ID (acak)
OLAPmemindai jutaan baris, hanya beberapa kolom

OLTP mengutamakan tulis cepat & konsisten (kasir). OLAP mengutamakan baca & agregasi masif (analis). Karena polanya berlawanan, cara penyimpanan optimalnya pun berbeda — itu sebabnya keduanya dipisah.

// OLTP — database aplikasi

  • Contoh: PostgreSQL, MySQL melayani aplikasi.
  • Pertanyaan: "ambil pesanan #12345".
  • Data terbaru, real-time, sering berubah.

// OLAP — data warehouse

  • Contoh: BigQuery, Snowflake, Redshift.
  • Pertanyaan: "tren omzet 5 tahun per wilayah".
  • Data historis, read-only, diperbarui berkala.
Definisi · Kata para pendirinya

Jadi, apa itu data warehouse?

Dua nama besar mendefinisikan bidang ini, dan dua-duanya layak kamu kenal: Bill Inmon (sering disebut "bapak data warehouse") dan Ralph Kimball (pelopor dimensional modeling).

“Data warehouse adalah kumpulan data yang berorientasi subjek, terintegrasi, terikat-waktu, dan tidak berubah, untuk mendukung proses pengambilan keputusan manajemen.”

— Bill Inmon, Building the Data Warehouse (1992)

Empat kata kunci Inmon, diterjemahkan ke bahasa sehari-hari:

// subject-oriented

Berorientasi subjek

Ditata seputar topik bisnis ("penjualan", "pelanggan"), bukan seputar satu aplikasi.

// integrated

Terintegrasi

Data dari banyak sistem disatukan & diseragamkan formatnya menjadi satu kebenaran.

// time-variant

Terikat waktu

Menyimpan sejarah bertahun-tahun, bukan cuma kondisi "sekarang". Bisa lihat tren.

// nonvolatile

Tidak berubah

Data dimuat lalu jarang diubah/dihapus — dibaca, bukan ditransaksikan ulang.

“Data warehouse adalah salinan data transaksi yang secara khusus distrukturkan untuk kueri dan analisis.”

— Ralph Kimball, The Data Warehouse Toolkit
◆
Perhatikan kata "salinan". Data warehouse tidak menggantikan database produksi — ia menyalin datanya secara berkala ke tempat yang aman untuk dianalisis. Produksi tetap jadi sumber kebenaran untuk operasi sehari-hari.
Aliran data · ETL / ELT

Bagaimana data masuk ke gudang?

Data tidak ajaib muncul di warehouse. Ia dipindahkan lewat pipeline bernama ETL: Extract (ambil dari sumber), Transform (bersihkan & seragamkan), Load (muat ke warehouse). Varian modern membalik urutannya jadi ELT — muat dulu, baru transformasi di dalam warehouse yang kuat.

◆ Analogi — gudang & rantai pasok

Bayangkan gudang besar yang menerima barang dari banyak pemasok. Extract = truk menjemput barang dari tiap pemasok (sistem penjualan, stok, CRM). Transform = barang dicek, dibersihkan, diberi label seragam, dirapikan ke ukuran standar. Load = ditata di rak gudang sesuai kategori. Sekali tertata rapi, siapa pun bisa mengambil & menghitung stok dengan cepat.

alur pipeline (disederhanakan)pipeline
# EXTRACT — tarik dari banyak sumber
penjualan  <- baca dari Postgres (produksi)
stok       <- baca dari API gudang
pemasaran  <- baca dari CSV / Google Sheets

# TRANSFORM — bersihkan & seragamkan
- samakan format tanggal & mata uang
- buang duplikat, perbaiki nilai kosong
- gabungkan "Jkt"/"DKI"/"Jakarta" -> "Jakarta"

# LOAD — muat ke warehouse, terjadwal (mis. tiap malam)
muat ke  warehouse.fact_sales
◆ ETL vs ELT

ETL (transform sebelum load) klasik, dipakai saat warehouse mahal/terbatas. ELT (load dulu, transform di dalam) populer sekarang karena warehouse cloud sangat kuat & murah untuk mengolah data mentah — alat seperti dbt melakukan transformasi langsung di dalam warehouse.

Pemodelan · Dimensional modeling (Kimball)

Star schema: fakta di tengah, dimensi mengelilingi

Database produksi ditata ternormalisasi (dipecah jadi banyak tabel kecil agar hemat & konsisten saat menulis). Warehouse justru sebaliknya: ditata denormalisasi agar query analitik sederhana & cepat. Pola paling terkenal dari Ralph Kimball adalah star schema.

Bentuknya seperti bintang: satu tabel fakta (angka yang diukur, mis. nilai penjualan) di tengah, dikelilingi tabel dimensi (konteks: siapa, apa, kapan, di mana).

star schema — fact dikelilingi dimensionmodel
        dim_waktu          dim_produk
              \              /
               \            /
            ┌─────────────────┐
            │   fact_sales     │   <- angka: qty, omzet
            │  (jutaan baris) │
            └─────────────────┘
               /            \
              /              \
        dim_pelanggan      dim_wilayah

-- query analitik jadi sederhana & cepat:
SELECT w.nama_wilayah, SUM(f.omzet)
FROM fact_sales f JOIN dim_wilayah w USING(wilayah_id)
GROUP BY w.nama_wilayah;
◆ Analogi — struk belanja & buku katalog

Tabel fakta ibarat tumpukan jutaan struk belanja: tiap baris satu peristiwa terukur (produk X, 3 buah, Rp90.000). Tabel dimensi ibarat buku katalog yang menjelaskan kode-kode di struk: siapa pelanggannya, produk apa, di toko mana, tanggal berapa. Untuk menganalisis, kamu tinggal menumpuk struk dan melihat katalog — tanpa menggali ke banyak tabel rumit.

◆
Di OLTP, denormalisasi itu "dosa" karena bikin data ganda & sulit dijaga saat sering menulis. Di warehouse, denormalisasi justru diinginkan — karena datanya jarang diubah (nonvolatile) dan tujuannya membaca secepat mungkin. Konteks menentukan aturan.
Pemodelan · Bukan cuma star

Keluarga schema: snowflake, galaxy, OBT, data vault

Star schema paling populer, tapi bukan satu-satunya cara menata gudang. Tiap pola punya trade-off & kasus pakai sendiri. Sebagai pemula, cukup kenali bentuk & kapan masing-masing masuk akal.

1 · Snowflake schema — seperti star, tapi tabel dimensinya dinormalisasi (dipecah jadi sub-tabel). Bentuknya bercabang seperti kepingan salju.

STAR — dimensi gepeng (denormal)model
fact_sales ── dim_produk
   (produk_id, nama, kategori,
    departemen)   # semua jadi satu

# 1 JOIN, query simpel
SNOWFLAKE — dimensi dipecahmodel
fact_sales ── dim_produk ── dim_kategori
                              └─ dim_departemen

# hemat ruang, tapi lebih banyak JOIN
◆ Analogi — alamat ditulis lengkap vs. pakai kode pos

Star = tiap baris menulis alamat lengkap berulang ("Jl. Merdeka, Bandung, Jawa Barat"). Boros tapi langsung kebaca. Snowflake = cukup tulis kode pos, lalu detailnya disimpan di tabel terpisah. Hemat, tapi tiap kali butuh detail kamu harus "menengok" tabel lain (JOIN tambahan).

2 · Galaxy / Fact Constellation — beberapa tabel fakta berbagi tabel dimensi yang sama. 3 · One Big Table (OBT) — semua digabung jadi satu tabel super-lebar, tanpa JOIN. 4 · Data Vault — pola untuk enterprise besar: Hub (kunci bisnis) + Link (relasi) + Satellite (atribut & riwayat).

// star schema

Star ⭐

Bentuk: 1 fakta + dimensi gepeng. Untung: simpel & cepat. Kasus: dashboard penjualan ritel di Power BI / Tableau — pola default kebanyakan BI.

// snowflake schema

Snowflake ❄️

Bentuk: dimensi dinormalisasi. Untung: hemat ruang, rapi untuk hierarki. Kasus: DW enterprise dengan dimensi besar & berjenjang (produk → kategori → departemen).

// galaxy schema

Galaxy / Constellation 🌌

Bentuk: banyak fakta berbagi dimensi. Kasus: perusahaan menganalisis penjualan & stok sekaligus, dua-duanya pakai dim_waktu & dim_produk yang sama.

// one big table

One Big Table (OBT) 📋

Bentuk: satu tabel super-lebar, tanpa JOIN. Untung: sangat cepat di warehouse columnar. Kasus: analitik event/clickstream di BigQuery + dbt; tabel produk analytics.

// data vault

Data Vault 🔐

Bentuk: Hub + Link + Satellite. Untung: jejak audit & riwayat penuh, tahan perubahan sumber. Kasus: bank, asuransi, pemerintah — banyak sumber & wajib auditable.

// normalized (3NF)

Normalized / Inmon 🏛️

Bentuk: 3NF terpusat (gaya Inmon), lalu diturunkan ke data mart. Kasus: korporasi besar yang mengutamakan satu model perusahaan yang konsisten.

◆ Mana yang dipilih?

Untuk mayoritas tim & pemula: mulai dari star schema — paling mudah dipahami & didukung semua tool BI. Naik ke snowflake/galaxy saat dimensi membesar atau proses bisnis bertambah. OBT cocok di warehouse cloud columnar yang JOIN-nya mahal. Data Vault hanya saat skala enterprise & kebutuhan audit benar-benar menuntut — jangan dipakai untuk proyek kecil, terlalu rumit.

Arsitektur layer · Medallion (Databricks)

Medallion: Bronze → Silver → Gold

Penting dibedakan: Medallion bukan schema tabel seperti star, melainkan cara menata data dalam beberapa lapisan kualitas. Polanya dipopulerkan oleh Databricks di arsitektur lakehouse. Data mengalir dari mentah ke siap-pakai lewat tiga tingkat: Bronze, Silver, Gold.

◆ Analogi — pengolahan air bersih

Bronze = air mentah dari sungai, apa adanya (kotor, lengkap). Silver = air sudah disaring & dibersihkan (siap diolah). Gold = air kemasan siap minum, dikemas untuk konsumen. Tiap tahap menaikkan kualitas & kegunaan. Kamu menyimpan ketiganya, jadi kalau ada salah olah, kamu bisa kembali ke air mentah dan memproses ulang.

aliran data di medallion architecturelayer
# BRONZE — mentah, persis dari sumber (disimpan apa adanya)
sumber (app, IoT, log, API)  ──>  bronze.events_raw

# SILVER — dibersihkan, divalidasi, digabung, ter-deduplikasi
bronze.events_raw  ──>  silver.events_clean
  - buang duplikat & baris rusak
  - samakan tipe, gabung dengan data referensi

# GOLD — agregat siap pakai untuk bisnis / BI / ML
silver.events_clean  ──>  gold.penjualan_harian
  SELECT tanggal, wilayah, SUM(omzet) ... GROUP BY ...
// bronze

🥉 Bronze — mentah

Salinan data sumber apa adanya, lengkap & tak diubah. Berfungsi sebagai arsip & titik proses-ulang kalau logika berubah.

// silver

🥈 Silver — bersih

Sudah divalidasi, dibersihkan, di-deduplikasi, & digabung antar sumber. "Satu versi kebenaran" tingkat detail.

// gold

🥇 Gold — siap pakai

Agregasi level bisnis untuk dashboard, laporan, & ML. Sering berbentuk star schema di sini.

◆ Contoh kasus program

Sebuah platform e-commerce mengalirkan clickstream (jutaan klik/hari): event mentah ditampung di Bronze (Delta Lake); job Spark/dbt membersihkan & menggabungkannya dengan data produk di Silver; lalu agregat "produk paling dilihat per jam" dibangun di Gold untuk dashboard tim marketing. Tools khasnya: Databricks + Delta Lake + Spark, atau kombinasi dbt di atas warehouse seperti Snowflake/BigQuery.

◆
Medallion & star schema tidak bersaing — mereka saling melengkapi. Medallion mengatur perjalanan data (mentah → bersih → siap), sedangkan star schema mengatur bentuk tabel di tujuan akhir. Lapisan Gold sering kali justru ditata sebagai star schema.
Di balik layar · Columnar storage

Kenapa warehouse bisa menjumlah miliaran baris dengan cepat

Rahasia teknis utamanya: data warehouse menyimpan data per kolom, bukan per baris seperti database biasa. Untuk analitik yang cuma butuh sedikit kolom dari jutaan baris, ini bedanya siang dan malam.

“Idenya sederhana: jangan simpan semua nilai dari satu baris bersama-sama, tetapi simpan semua nilai dari setiap kolom bersama-sama.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 3)
◆ Analogi — membaca satu kolom dari buku besar

Kamu punya buku besar berisi sejuta transaksi, tiap baris: tanggal, nama, produk, harga. Pertanyaanmu cuma: "berapa total semua harga?". Penyimpanan per baris memaksamu membaca seluruh isi tiap baris (tanggal, nama, produk) padahal cuma butuh harga. Penyimpanan per kolom = semua "harga" disimpan berdampingan, jadi kamu cukup membaca satu jalur angka dan menjumlahkannya. Jauh lebih sedikit yang dibaca.

row-based (OLTP)layout
# tiap baris utuh berdekatan
[2024, Budi, Kopi, 25000]
[2024, Sari, Teh,  18000]
[2024, Adi,  Roti, 12000]
# SUM(harga) -> tetap baca semua kolom
columnar (OLAP)layout
# tiap kolom berdekatan
tanggal: [2024, 2024, 2024]
nama:    [Budi, Sari, Adi]
harga:   [25000, 18000, 12000]
# SUM(harga) -> cukup baca 1 kolom ⚡

Bonusnya: karena nilai sejenis berkumpul (semua angka, semua tanggal), datanya jauh lebih mudah dikompres — hemat ruang sekaligus mempercepat pembacaan.

◆ Harga · Tidak ada makan siang gratis

Trade-off: yang kamu dapat & yang kamu korbankan

Data warehouse luar biasa untuk analitik — tapi ia bukan pengganti database produksi, dan punya konsekuensi yang harus disadari sejak awal.

// Yang kamu dapat

  • Query analitik masif yang sangat cepat.
  • Satu sumber data terpadu dari banyak sistem.
  • Sejarah bertahun-tahun untuk analisis tren.
  • Analis bebas bermain tanpa mengganggu produksi.

// Yang kamu korbankan

  • Data tidak real-time — telat menit/jam/hari (ikut jadwal ETL).
  • Buruk untuk transaksi & ambil satu baris per ID.
  • Pipeline ETL harus dibangun & dirawat (rapuh bila diabaikan).
  • Biaya penyimpanan & komputasi tambahan.
  • Data ganda — warehouse adalah salinan, perlu sinkronisasi.
◆ Inti trade-off-nya

Kamu menukar kesegaran & kelincahan transaksi demi kecepatan analisis dalam skala besar. Itu pertukaran yang sangat sepadan untuk pelaporan & pengambilan keputusan — tapi salah total kalau dipakai sebagai database utama aplikasi.

◆ Keputusan · Pakai atau jangan

Kapan pakai data warehouse (dan kapan tidak)

Aturan praktisnya sederhana: kalau pertanyaanmu bersifat "analisis lintas banyak data & waktu", pakai warehouse. Kalau bersifat "operasi satu transaksi sekarang", tetap di OLTP.

// Pakai warehouse saat…

  • Bikin dashboard & laporan bisnis (BI).
  • Menganalisis tren historis lintas tahun.
  • Menggabungkan data dari banyak sistem.
  • Query agregasi berat (SUM, AVG, GROUP BY masif).
  • Bahan untuk analitik & machine learning.

// Jangan, tetap OLTP saat…

  • Melayani transaksi aplikasi real-time.
  • Ambil/ubah satu baris per ID (profil, pesanan).
  • Butuh data detik-terbaru yang konsisten.
  • Banyak operasi tulis kecil & sering.
◆ Kerabat yang sering tertukar

Data lake = "danau" berisi data mentah apa adanya (termasuk file, gambar, log) — fleksibel tapi belum tertata. Data warehouse = data sudah bersih & terstruktur untuk analisis. Lakehouse = gabungan keduanya (mis. Databricks). Data mart = "warehouse mini" untuk satu departemen (mis. khusus tim keuangan).

◆
Untuk startup kecil dengan data sedikit, kamu belum tentu butuh warehouse terpisah — sebuah read-replica dari database produksi sudah cukup untuk laporan. Warehouse mulai masuk akal saat data & pertanyaan analitik membesar dan mulai mengganggu produksi. Jangan bangun gudang sebelum punya cukup barang.
⚙ Ekosistem · Alat yang dipakai di lapangan

Tools data warehouse modern

Sebagai pemula, kamu tidak perlu menguasai semuanya — cukup tahu kategorinya dan satu-dua nama populer di tiap kategori, supaya tidak bingung saat mendengar istilah-istilah ini.

// gudangnya (warehouse)

Snowflake · BigQuery · Redshift

Tempat data disimpan & dikueri. Plus Azure Synapse, ClickHouse, Databricks. Kebanyakan cloud, columnar, & bisa skala besar.

// memasukkan data (E/L)

Fivetran · Airbyte

Menarik data dari ratusan sumber (database, SaaS, API) ke warehouse secara otomatis & terjadwal.

// transformasi (T)

dbt

Standar de-facto untuk transformasi data di dalam warehouse pakai SQL, dengan versioning & testing.

// orkestrasi jadwal

Apache Airflow · Dagster

Menjadwalkan & mengatur urutan pipeline ("jalankan extract jam 1, transform jam 2").

// visualisasi (BI)

Tableau · Power BI · Metabase

Mengubah hasil query jadi dashboard & grafik yang dibaca tim bisnis. Plus Looker.

// open-source

ClickHouse · DuckDB

Mesin analitik columnar cepat & gratis. DuckDB bahkan jalan di laptop — bagus untuk belajar.

◆ Mau coba sendiri?

Untuk belajar tanpa biaya cloud, DuckDB pilihan terbaik: satu file, jalan di laptop, pakai SQL biasa, dan columnar. Kamu bisa merasakan kecepatan query analitik atas jutaan baris langsung dari komputermu sendiri.

Penutup

Tempat terpisah untuk bertanya besar

Data warehouse lahir dari satu kebutuhan: menganalisis data dalam skala besar tanpa melumpuhkan aplikasi yang melayani pelanggan. Ia menyalin data dari banyak sistem, menatanya untuk membaca, dan membiarkan tim bisnis bertanya sepuasnya.

  • OLTP vs OLAP — mencatat transaksi vs. menganalisis massal; dua dunia, dipisah.
  • Salinan, bukan pengganti — produksi tetap sumber kebenaran operasional.
  • ETL/ELT — ambil, bersihkan, muat dari banyak sumber ke satu gudang.
  • Star schema — fakta di tengah, dimensi mengelilingi; denormalisasi disengaja.
  • Columnar — simpan per kolom; menjumlah miliaran baris jadi kilat.
  • Trade-off — cepat & terpadu, tapi tidak real-time & butuh pipeline.

Aturan emasnya

Pakai data warehouse ketika pertanyaanmu berubah dari "ambil baris ini sekarang" menjadi "apa pola dari semua data ini sepanjang waktu". Saat analitik mulai mengganggu produksi atau data tercerai di banyak sistem, di situlah gudang mulai bernilai. Jangan bangun lebih awal dari kebutuhan — tapi saat dibutuhkan, ia mengubah data jadi keputusan.
