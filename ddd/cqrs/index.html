CQRS deep dive

Di materi DDD utama, CQRS cuma dapat satu bab. Di sini kita bedah tuntas: dari akar prinsipnya (CQS), naik pelan-pelan lewat 4 level adopsi, dua contoh lengkap dengan kode + tabel + diagram, sampai urusan paling nyebelin-nya: eventual consistency di layar user. Tetap pakai dunia ride-hailing (RideGo) biar nyambung.

◆ Buat apa ini? Kenapa pakai ini?

Given — model data yang sama dipakai buat baca (read) dan tulis (write) sekaligus.

When — traffic baca jauh lebih besar dari tulis, atau kebutuhan tampilan (dashboard, riwayat, laporan) makin kompleks dan beda bentuk dari model tulisnya.

Then — satu model itu jadi kompromi buruk buat keduanya: query jadi lambat/berat, atau model tulis dipaksa nampung field-field khusus tampilan — performa dan skalabilitas dua-duanya terganggu.

→ makanya kita pakai CQRS, pisahkan sisi command (tulis) dan query (baca).

01
Akar · 1988 → 2010

CQS: prinsip kecil yang jadi arsitektur

CQRS nggak muncul dari langit. Akarnya prinsip lama bernama CQS (Command-Query Separation) dari Bertrand Meyer (1988): sebuah method itu command (mengubah state, nggak mengembalikan data) ATAU query (mengembalikan data, nggak mengubah apa pun) — jangan dua-duanya.

DriverWallet.java — melanggar CQSCAMPUR ADUK
// satu method, dua kepribadian: ngubah state DAN balikin data
public Money withdraw(Money amount) {
    this.saldo = saldo.minus(amount);   // command: mutasi
    return this.saldo;                  // query: baca
}
// akibatnya: manggil buat "cek saldo" bisa nggak sengaja narik duit.
// method-nya nggak bisa dipercaya cuma dari namanya.
DriverWallet.java — patuh CQSJELAS PERANNYA
public void withdraw(Money amount) { this.saldo = saldo.minus(amount); }  // command: void
public Money saldo() { return saldo; }                                  // query: tanpa efek

Sekitar 2010, Greg Young ngangkat prinsip method ini ke level arsitektur: kalau memisahkan command dan query bagus di satu method, kenapa nggak dipisah di level model? Lahirlah CQRS: satu model buat menulis, satu (atau lebih) model buat membaca.

“
CQRS is simply the creation of two objects where there was previously only one.
Greg Young pencetus istilah CQRS · CQRS Documents
“
CQRS bukan arsitektur level atas aplikasi — ia pola yang diterapkan di bagian tertentu sistem, bukan di semua tempat.
Martin Fowler posisinya · bliki "CQRS"
02
Masalahnya

Satu model, dua tuan yang maunya beda

Kenapa repot-repot misahin? Karena sisi tulis dan sisi baca itu dua tuan dengan tuntutan yang bertolak belakang. Satu model yang melayani dua-duanya bakal kompromi di dua-duanya.

Sisi TULIS maunya…Sisi BACA maunya…
Bentuk dataNormalized, ngikutin aturan bisnis (aggregate kecil & ketat)Denormalized, gepeng, persis bentuk layar
Yang dijagaInvariant — data nggak boleh masuk kondisi tak sahKecepatan — user nggak mau nunggu
Pola aksesLoad satu aggregate by ID → ubah → simpanList, filter, sort, agregasi, join ke mana-mana
FrekuensiRelatif jarangBiasanya 10–100× lebih sering dari tulis
KonsistensiHarus strong (transaksional)Sering boleh telat sepersekian detik

Contoh nyata: layar "Riwayat Perjalanan" di aplikasi penumpang butuh: nama driver, plat motor, foto, alamat jemput/tujuan, tarif final, metode bayar, rating yang kamu kasih. Itu data dari 5–6 aggregate berbeda (Trip, Driver, Billing, Rating…). Kalau dipaksa lewat model tulis: load 6 aggregate × N baris riwayat = N+1 query, mapping berat, dan aggregate-mu mulai ditambahin getter aneh-aneh demi kebutuhan layar. Model tulismu pelan-pelan rusak justru karena dipakai buat baca.

◆ Gejala yang paling sering kelihatan

Aggregate yang tadinya rapi mulai numbuh method kayak getDriverNameForHistoryScreen() atau field yang cuma dipakai satu layar. Itu tandanya model tulis lagi disandera kebutuhan baca. CQRS bilang: lepasin — kasih layar itu model bacanya sendiri.

03
Peta keputusan

4 level adopsi — dari gratis sampai mahal

Kesalahan terbesar orang belajar CQRS: ngira ini pilihan biner "pakai / nggak pakai". Padahal dia spektrum. Naik level cuma kalau sakitnya nyata — tiap level nambah kompleksitas.

spektrum-cqrs.txt — makin ke bawah makin mahalPILIH SEPERLUNYA
LEVEL 0  satu model buat semua
         [ Model ] ◀──tulis+baca──▶ [ DB ]
         cukup buat CRUD & layar sederhana. mayoritas fitur hidup nyaman di sini.

LEVEL 1  pisah INTERFACE (CQRS "ringan")
         [ TripRepository ] ──tulis──▶ ┐
                                       ├─▶ [ DB yang sama ]
         [ TripHistoryReader ] ◀─baca─ ┘
         murah, hampir selalu worth it. reader boleh SQL join seenaknya.

LEVEL 2  pisah MODEL BACA, masih 1 database
         tulis ─▶ [ tabel utama ] ─(trigger/proyeksi)─▶ [ tabel/VIEW baca ] ◀─ baca
         buat layar berat yang join-nya mulai nyakitin.

LEVEL 3  pisah READ STORE (CQRS "penuh")
         tulis ─▶ [ DB transaksi ] ─event─▶ [ projector ] ─▶ [ DB baca ] ◀─ baca
         skala & bentuk beda total (dashboard, analytics, search). bayar: eventual consistency.
◆ Aturan mainnya

Per fitur, bukan per sistem. Satu aplikasi sehat biasanya campur: 80% fitur di Level 0–1, beberapa layar berat di Level 2, dan satu-dua kasus khusus di Level 3. Kalau ada yang bilang "sistem kita full CQRS Level 3 semuanya" — itu bukan prestasi, itu tagihan kompleksitas yang belum jatuh tempo.

04
Contoh 1 · Level 1–2

Riwayat perjalanan penumpang

Layar riwayat: daftar perjalanan sebulan terakhir, lengkap dengan nama driver, tarif, dan rating. Data dari banyak aggregate, tapi nggak butuh real-time banget dan masih satu database. Level 1–2 cukup.

port — sisi tulis dan sisi baca dipisah sejak interfaceLEVEL 1
// SISI TULIS — lewat aggregate, jaga invariant
public interface TripRepository {
    Optional<Trip> findById(TripId id);
    void save(Trip trip);
}

// SISI BACA — DTO siap-tampil. NGGAK lewat aggregate, nggak ada aturan bisnis.
public interface TripHistoryReader {
    List<TripHistoryRow> listByPassenger(PassengerId id, Month month);
}
public record TripHistoryRow(          // bentuknya = bentuk LAYAR, bukan bentuk domain
    String tripId, Instant completedAt,
    String driverName, String plateNumber,
    long finalFare, Integer myRating) { }
implementasi reader — SQL join bebas, satu kali jalanLEVEL 2 (VIEW)
-- reader nggak perlu sopan santun aggregate. join aja langsung:
CREATE VIEW v_trip_history AS
SELECT t.id, t.completed_at, t.passenger_id,
       d.display_name  AS driver_name,
       d.plate_number,
       b.final_fare,
       r.stars         AS my_rating
FROM   trips t
JOIN   drivers d  ON d.id = t.driver_id
JOIN   billing b  ON b.trip_id = t.id
LEFT JOIN ratings r ON r.trip_id = t.id
WHERE  t.status = 'COMPLETED';

Perhatikan yang terjadi: model tulis (aggregate Trip) nggak disentuh sama sekali — nggak perlu ditambahin getter buat layar. Reader hidup di dunianya sendiri: satu query, bentuk pas, kelar. Dan karena masih satu database, hasilnya selalu konsisten — nggak ada lag.

◆ Kenapa nggak lewat repository aja?

Coba bandingkan: lewat model tulis = load N aggregate Trip, terus per trip load Driver, Billing, Rating (N+1!), terus mapping manual ke DTO. Lewat reader = satu query view. Lebih cepat, lebih sedikit kode, dan aggregate-mu tetap perawan dari urusan layar.

05
Contoh 2 · Level 3

Dashboard pendapatan harian driver

Layar yang dibuka ratusan ribu driver berkali-kali sehari: "hari ini dapet berapa?". Agregasi (jumlah trip, gross, komisi, net) yang kalau dihitung on-the-fly dari tabel transaksi bakal ngebebanin DB utama. Ini kasus sah buat Level 3: read store terpisah, di-update lewat event.

alur — dari transaksi ke dashboardLEVEL 3 · ASYNC

  [ DB transaksi ] ──▶ [ outbox: TripCompleted ]
                              │ (publish andal)
                              ▼

                                                            │
                                        GET /driver/earnings/today ◀── aplikasi driver

EarningsProjector.java — dengar event, update read modelPROJECTOR
public final class EarningsProjector {

    // dipanggil consumer event (dari outbox) — BUKAN dari use case
    public void on(TripCompleted e) {
        var commission = e.fare().multiply(0.20);          // snapshot rate saat itu
        db.upsert("""
            INSERT INTO driver_daily_earnings (driver_id, tanggal, trips, gross, komisi)
            VALUES (?, ?, 1, ?, ?)
            ON CONFLICT (driver_id, tanggal) DO UPDATE SET
              trips = driver_daily_earnings.trips + 1,
              gross = driver_daily_earnings.gross + EXCLUDED.gross,
              komisi = driver_daily_earnings.komisi + EXCLUDED.komisi
            """, e.driver(), date(e.at()), e.fare(), commission);
    }

    // event lain yang relevan ikut didengar:
    public void on(TripCancelled e) { /* cancellation fee masuk gross juga */ }
}
◆ Yang dibeli dan yang dibayar

Dibeli: query dashboard = 1 baris by primary key — nggak peduli driver punya 10 atau 10.000 trip. DB transaksi nggak keganggu sama sekali. Read store-nya bahkan boleh mesin lain (mis. columnar DB buat analytics). Dibayar: dashboard bisa telat beberapa detik dari kejadian (eventual consistency — bab 08), plus ada komponen baru (projector) yang harus dimonitor: kalau projector mati, dashboard beku diam-diam. Kasih metric lag!

06
Zoom in · Sisi tulis

Anatomi sisi Command

Command = niat user untuk mengubah sesuatu, dinamai pakai kata kerja bahasa bisnis: BookTrip, CancelTrip, WithdrawEarnings. Bukan "updateTrip" — itu bahasa CRUD, bukan bahasa niat.

alur satu command — dari HTTP sampai eventCOMMAND FLOW
// 1. command = niat, immutable, bahasa bisnis
public record BookTripCommand(PassengerId passenger, Location pickup, Location destination) { }

// 2. use case = sutradara (application service)
public final class BookTripUseCase {
    public TripId handle(BookTripCommand cmd) {
        var fare = pricing.estimate(cmd.pickup(), cmd.destination()); // domain service
        var trip = Trip.create(idGen.next(), cmd.passenger(), fare);  // aggregate jaga invariant
        tripRepository.save(trip);                                    // + event ke outbox, 1 transaksi
        return trip.id();     // ← balikin ID doang. BUKAN data buat layar!
    }
}

Validasi (bentuk) — di tepi

  • "lat/lng keisi?" · "format bener?"
  • Dicek di controller / constructor VO
  • Gagal cepat, murah, tanpa DB

Invariant (bisnis) — di aggregate

  • "penumpang ini masih punya trip aktif?"
  • Dicek di dalam Trip / use case, transaksional
  • Nggak bisa di-bypass dari mana pun
◆ Kenapa command cuma balikin ID?

Kalau command balikin data layar, kamu diam-diam balik lagi ke "satu model dua tuan" — use case tulis mulai dijejali join buat kebutuhan tampilan. Kontraknya: command mengubah, query menampilkan. Setelah BookTrip sukses, UI ambil detail lewat query (atau pakai data yang dia kirim sendiri — bab 08).

07
Zoom in · Sisi baca

Anatomi sisi Query

Sisi query itu bodoh dengan sengaja — dan justru itu kekuatannya: ambil data, bentuk sesuai layar, kembalikan. Nggak ada keputusan bisnis, nggak ada mutasi, nggak ada aggregate.

contoh reader lain — pencarian trip oleh Customer ServiceQUERY = TANYA DOANG
// filter fleksibel khas layar admin — hal yang bikin aggregate nangis
public interface TripSearchReader {
    Page<TripSearchRow> search(TripSearchFilter f);   // status, rentang tanggal, driver,
}                                                        // area, metode bayar, keyword…

public record TripSearchRow(
    String tripId, String status, Instant requestedAt,
    String passengerName, String driverName,
    long finalFare, String cancelReason) { }         // gepeng. siap tampil. titik.

Boleh di sisi query

  • SQL join / view / index khusus layar
  • DTO per layar — 5 layar, 5 DTO, gapapa
  • Cache (data baca gampang di-cache)
  • Baca dari replica / read store terpisah

Haram di sisi query

  • Mutasi data (sekecil apa pun — "sekalian update counter")
  • Keputusan bisnis (if yang menentukan aturan)
  • Balikin domain object / aggregate ke controller
  • Manggil use case tulis dari dalam reader
◆ "Tapi kan duplikasi DTO…"

Lima layar, lima DTO yang mirip-mirip — kok nggak DRY? Sengaja. Layar riwayat penumpang dan layar pencarian CS itu berubah karena alasan berbeda (penumpang vs kebutuhan ops) — nyatuin DTO-nya berarti tiap perubahan satu layar ngerusak layar lain. Duplikasi bentuk yang murah > kopling yang mahal. Yang haram itu duplikasi aturan bisnis, bukan duplikasi bentuk tampilan.

08
Bagian tersulit

Eventual consistency & UX: jeda yang harus dijinakkan

Begitu naik ke Level 3, ada jeda antara "command sukses" dan "read model ke-update". Biasanya milidetik — tapi Murphy bilang user bakal nemu momen itu. Yang penting bukan menghilangkan jedanya (nggak bisa), tapi mendesain UX yang jujur terhadap jeda itu.

timeline — di mana jedanya hidupTHE GAP
t0   driver tap "Selesaikan Trip"  ─▶  command OK, DB transaksi commit  ✓
t0+ε (outbox → projector lagi kerja…)
t1   driver buka dashboard pendapatan
       ├─ kalau t1 > t0+lag  → angka udah bener  ✓
       └─ kalau t1 < t0+lag  → trip barusan BELUM kelihatan  ⚠ ← momen ini yang harus didesain

Strategi yang umum dipakai — pilih sesuai layarnya:

StrategiCara kerjaCocok buat
Optimistic UIUI langsung nampilin hasil dari data yang user kirim sendiri, tanpa nunggu read modelAksi user sendiri: habis complete trip, tampilkan "+Rp32.000" dari respons command
Read-your-own-writesKhusus data yang barusan ditulis user, baca dari sumber tulis (atau tunggu versi ≥ X)Form edit profil, setting — user nggak boleh lihat data lamanya sendiri
Status "diproses"Tampilkan badge pending sampai proyeksi selesaiPayout / pencairan — user paham uang butuh proses
Terima ajaNggak diapa-apain — lag sub-detik nggak akan disadariDashboard agregat, laporan, leaderboard
◆ Trik yang jarang disadari

Dunia nyata itu udah eventual consistent dari sononya. Struk belanja nggak langsung muncul di mutasi rekening; resi paket telat beberapa menit dari paketnya. User udah terlatih menerima jeda — asal UI-nya nggak bohong. Yang bikin marah bukan jedanya, tapi data yang kelihatan hilang tanpa penjelasan. Makanya optimistic UI + badge "diproses" hampir selalu cukup.

09
Keputusan

Kapan pakai, kapan jangan

Level 1 (pisah interface) itu hampir selalu layak — murah dan bikin kode lebih jelas. Pertanyaan sebenarnya: kapan layak naik ke Level 2–3?

Sinyal buat naik level

  • Beban baca jauh lebih besar dari tulis (10×+) dan mulai ganggu sisi transaksi
  • Bentuk data layar beda jauh dari bentuk domain (agregasi, search, dashboard)
  • Butuh mesin beda: full-text search, columnar/analytics DB
  • Aggregate mulai dijejali getter demi layar
  • Tim bisa monitor komponen async (projector lag)

Sinyal buat DIAM di level bawah

  • CRUD form biasa — create, edit, list sederhana
  • Data wajib selalu fresh dan strong-consistent di semua layar
  • Tim kecil, belum ada monitoring async
  • "Biar keren aja" / "biar kayak arsitektur Netflix"
  • Belum ada masalah performa yang terukur
◆ Framing yang sehat

Jangan tanya "sistem kita pakai CQRS nggak?" — tanya "layar INI butuh level berapa?". Riwayat trip: Level 1–2. Dashboard pendapatan: Level 3. Form edit profil driver: Level 0, udah, gitu aja. Keputusannya per kasus, dan boleh berubah seiring beban tumbuh.

10
Jebakan

Anti-pattern & smells

Kumpulan cara paling populer buat nyakitin diri sendiri pakai CQRS:

SMELL 1

Update dua model manual

Use case tulis sekalian update tabel read model di kode yang sama, tanpa event. Dua-duanya pelan-pelan beda isi, dan nggak ada yang tahu mana yang bener. Read model di-update dari event, titik.

SMELL 2

Reader yang sok pinter

Reader mulai berisi if aturan bisnis ("kalau VIP, diskon 10%"). Sekarang aturan hidup di dua tempat dan bakal beda. Aturan bisnis cuma boleh di domain.

SMELL 3

Command balikin data layar

BookTrip mengembalikan seluruh detail trip + nama driver + ETA buat layar. Selamat, kamu baru aja nyatuin lagi yang tadinya dipisah.

SMELL 4

Level 3 buat CRUD

Read store terpisah + projector + monitoring… buat form master data yang diakses 10 orang. Kompleksitasnya nggak beli apa-apa.

SMELL 5

Projector tanpa monitoring

Projector mati jam 2 pagi, dashboard beku, nggak ada alert. User yang jadi monitoring-mu. Ukur & alert-kan lag proyeksi.

SMELL 6

"CQRS = wajib Event Sourcing"

Salah kaprah paling umum. CQRS jalan normal dengan DB biasa. ES itu keputusan terpisah (lihat deck sebelah) — jangan beli dua-duanya sekaligus cuma karena sering disebut barengan.

11
Sintesis

Penutup

Kalau diperas: CQRS itu pengakuan jujur bahwa menulis dan membaca adalah dua pekerjaan yang beda — dan tiap layar berhak dapat model yang pas buat dirinya.

  • Akar: CQS (method) → CQRS (model). Command mengubah, query menampilkan.
  • Spektrum, bukan saklar: Level 0–3. Naik cuma kalau sakitnya nyata & terukur.
  • Per fitur, bukan per sistem — satu aplikasi sehat mencampur semua level.
  • Sisi baca boleh "bodoh" — DTO per layar, join bebas, tanpa aturan bisnis.
  • Level 3 dibayar pakai eventual consistency — desain UX-nya, monitor projector-nya.
  • CQRS ≠ Event Sourcing — dua keputusan terpisah yang kebetulan akrab.

Lanjut ke mana

Pasangan alami materi ini adalah Event Sourcing — karena begitu event jadi sumber proyeksi read model, tinggal selangkah lagi buat bertanya: "kenapa nggak sekalian event-nya yang jadi sumber kebenaran?" Jawabannya (dan bahayanya) ada di deck sebelah.
