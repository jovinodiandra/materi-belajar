Jangan hitung ulang soal yang sudah kamu jawab.

Sebagian masalah, kalau diselesaikan dengan rekursi polos, diam-diam menghitung subproblem yang sama berkali-kali — padahal jawabannya selalu sama tiap kali. Dynamic programming (DP) adalah teknik menyimpan jawaban subproblem itu — lewat memoization (top-down, disimpan saat rekursi jalan) atau tabulation (bottom-up, tabel diisi dari kasus dasar) — supaya tak pernah dihitung dua kali. Deck ini buat pemula: dari kenapa DP ada, dua syarat-nya, dua cara implementasi, sampai kapan dipakai di dunia nyata — diselingi kalimat dari buku & tokoh rujukan.

Akar masalah · Rekursi yang menghitung ulang

Subproblem yang sama, dihitung berkali-kali, padahal hasilnya selalu sama

Coba hitung fibonacci(5) secara rekursif murni: fib(5) memanggil fib(4) dan fib(3). Tapi fib(4) juga memanggil fib(3) — subproblem yang persis sama dengan yang sudah dipanggil sebelumnya. Semakin besar n, jumlah pemanggilan ulang ini meledak secara eksponensial, padahal fib(3) selalu menghasilkan angka yang sama, berapa kali pun dipanggil.

◆ Buat apa ini? Kenapa pakai DP?

Given — kamu punya fungsi rekursif yang benar secara matematis, misalnya fib(n) atau knapsack(i, sisaKapasitas), dan setiap pemanggilan memecah dirinya jadi beberapa subproblem yang lebih kecil.

When — kamu jalankan fungsi itu untuk input yang cukup besar (fib(40), knapsack dengan puluhan item), dan subproblem yang sama — misalnya fib(20) atau kombinasi (i, kapasitas) yang identik — dipanggil ulang ribuan bahkan jutaan kali dari cabang pohon rekursi yang berbeda.

Then — waktu eksekusi meledak secara eksponensial (O(2ⁿ)), program jadi lambat atau timeout padahal jawaban subproblem itu sebenarnya sudah pernah dihitung dan hasilnya pasti sama tiap kali.

→ makanya kita pakai Dynamic Programming — simpan (memoize/tabulasi) jawaban subproblem sekali, pakai ulang selamanya.

◆ Analogi — buku catatan jawaban ujian

Bayangkan mengerjakan soal ujian yang sama berulang-ulang tanpa mencatat jawabannya — tiap kali soal itu muncul lagi, kamu menghitung dari nol seolah belum pernah mengerjakannya. Orang yang cerdik akan mencatat jawaban di buku catatan: begitu soal yang sama muncul lagi, tinggal lihat catatan, tak perlu menghitung ulang. Itulah inti dynamic programming — catat jawaban subproblem, jangan hitung ulang.

“Banyak masalah optimasi bisa dipecah menjadi rangkaian keputusan berurutan, di mana keputusan optimal di setiap tahap hanya bergantung pada state saat itu — bukan pada seluruh riwayat keputusan sebelumnya.”

— parafrase gagasan Richard Bellman, pencipta istilah "dynamic programming" (prinsip optimalitas Bellman)

Rekursi biasa itu sendiri tidak salah — masalahnya adalah ia lupa. Setiap panggilan rekursif mulai dari nol, tanpa tahu bahwa subproblem yang sama sudah pernah diselesaikan di cabang lain dari pohon rekursi. DP menambahkan "ingatan" itu.

Konsep inti · Dua syarat DP

Overlapping subproblems & optimal substructure

DP hanya memberi keuntungan kalau masalahnya punya dua properti: overlapping subproblems (subproblem yang sama muncul berulang kali) dan optimal substructure (solusi optimal dari masalah besar bisa dibangun dari solusi optimal subproblem-nya).

“Dynamic programming cocok dipakai ketika masalah punya dua properti kunci: overlapping subproblems dan optimal substructure — tanpa keduanya, DP tidak memberi keuntungan dibanding rekursi biasa.”

— parafrase gagasan Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest, Clifford Stein, Introduction to Algorithms (CLRS)
Fibonacci.java — rekursif naifJava
static long fibNaive(int n) {
    if (n <= 1) return n;
    return fibNaive(n - 1) + fibNaive(n - 2);
}
// fib(3) dipanggil ulang di banyak cabang berbeda
// kompleksitas waktu: O(2^n) — meledak eksponensial
Fibonacci.java — memoization top-downJava
static long[] memo = new long[100];

static long fibMemo(int n) {
    if (n <= 1) return n;
    if (memo[n] != 0) return memo[n]; // sudah dicatat
    memo[n] = fibMemo(n - 1) + fibMemo(n - 2);
    return memo[n];
}
// tiap n cuma dihitung sekali → O(n)
// alternatif: HashMap<Integer, Long> kalau index-nya jarang/tak berurutan

Fibonacci memenuhi kedua syarat: subproblem-nya overlap (fib(3) dipakai ulang), dan hasilnya punya optimal substructure — fib(n) dibangun langsung dari fib(n-1) dan fib(n-2), tak ada cara lain menghitungnya yang lebih "optimal". Memoization cuma menambahkan satu array/HashMap sebagai cache — logika rekursifnya tetap sama, cuma tidak lagi lupa.

Konsep lanjutan · Bottom-up

Tabulation: isi tabel dari kasus dasar ke atas, tanpa rekursi

Tabulation adalah kebalikan arah dari memoization: alih-alih mulai dari masalah besar lalu turun ke subproblem lewat rekursi, tabulation mulai dari kasus dasar dan mengisi tabel maju ke atas secara iteratif — tanpa panggilan rekursif sama sekali. Contoh klasiknya: 0/1 Knapsack — dari n barang dengan berat & nilai masing-masing, pilih subset yang muat dalam kapasitas W dengan nilai total maksimal.

Knapsack.java — tabulation bottom-upJava
static int knapsack(int[] weight, int[] value, int capacity) {
    int n = weight.length;
    int[][] dp = new int[n + 1][capacity + 1]; // dp[i][w] = nilai maks pakai i barang, kapasitas w

    for (int i = 1; i <= n; i++) {
        for (int w = 0; w <= capacity; w++) {
            dp[i][w] = dp[i - 1][w]; // state: tak ambil barang i
            if (weight[i - 1] <= w) {
                dp[i][w] = Math.max(dp[i][w],
                    dp[i - 1][w - weight[i - 1]] + value[i - 1]); // state: ambil barang i
            }
        }
    }
    return dp[n][capacity];
}
// tabel diisi dari dp[0][*] (kasus dasar: 0 barang) naik ke dp[n][capacity]
rekursif naif — cabang meledakJava
static int knapsackNaive(int[] w, int[] v, int cap, int i) {
    if (i == 0 || cap == 0) return 0;
    if (w[i - 1] > cap) return knapsackNaive(w, v, cap, i - 1);
    int skip = knapsackNaive(w, v, cap, i - 1);
    int take = v[i - 1] + knapsackNaive(w, v, cap - w[i - 1], i - 1);
    return Math.max(skip, take);
}
// tiap barang: cabang "ambil" & "tidak" → O(2^n), banyak (cap, i) diulang
tabulation — tabel dp[i][w]Java
int[][] dp = new int[n + 1][capacity + 1];
for (int i = 1; i <= n; i++)
    for (int w = 0; w <= capacity; w++) {
        dp[i][w] = dp[i - 1][w];
        if (weight[i - 1] <= w)
            dp[i][w] = Math.max(dp[i][w],
                dp[i - 1][w - weight[i - 1]] + value[i - 1]);
    }
// tiap sel (i, w) cuma dihitung sekali → O(n × capacity), polinomial

Pola state-nya sama dengan yang cocok untuk Longest Common Subsequence (LCS): dp[i][j] menyimpan panjang LCS dari i karakter string pertama & j karakter string kedua, diisi baris demi baris dari kasus dasar (string kosong). Ide tabulation-nya identik — cuma bentuk transisinya beda.

◆ Praktik · Kebiasaan aman menulis DP

Best practice menulis solusi dynamic programming

DP sering terasa "sulit" bukan karena sintaksnya rumit, tapi karena orang langsung ngoding sebelum benar-benar mengerti state-nya. Kebiasaan berikut membantu menghindari kebuntuan itu.

  1. Identifikasi state & transisi dulu, sebelum ngoding — apa yang direpresentasikan dp[i] atau dp[i][j]? Bagaimana ia dibangun dari state yang lebih kecil? Tulis di kertas dulu.
  2. Mulai dari brute force rekursif — pastikan versi rekursif polos (tanpa DP) sudah benar dulu; DP cuma optimisasi dari solusi yang sudah benar, bukan pengganti cara berpikir.
  3. Baru tambahkan memoization — begitu rekursifnya benar, cek apakah subproblem-nya overlap. Kalau ya, tambahkan cache (array/HashMap) di atasnya, minim perubahan struktur.
  4. Pertimbangkan tabulation untuk hemat memori/stack — tabulation biasanya lebih hemat memori (tak ada overhead call stack rekursi) dan menghindari risiko StackOverflowError pada input besar.
  5. Perhatikan urutan pengisian tabel — pastikan saat mengisi dp[i][j], semua state yang jadi dependensinya (mis. dp[i-1][j]) sudah terisi lebih dulu.
  6. Cek apakah state bisa dipangkas — banyak solusi DP 2D sebenarnya cuma butuh baris sebelumnya, jadi bisa dioptimasi ke array 1D untuk menghemat memori lebih lanjut.
◆ Roadmap · Bertahap sesuai levelmu

Tier belajar dynamic programming

DP punya kurva belajar yang cukup panjang — dari mengenali overlapping subproblems paling sederhana, sampai state yang bersarang di banyak dimensi. Berikut jalurnya dari dasar sampai lanjut.

Beginner

DP 1 dimensi dengan memoization

Mulai dari masalah dengan satu state sederhana, di mana overlapping subproblem-nya paling mudah terlihat.

  • Fibonacci dengan memoization
  • Climbing stairs (berapa cara naik n anak tangga)
  • Jumlah cara memberi kembalian sederhana
  • House robber (maks nilai tanpa dua tetangga)
Middle

DP 2 dimensi & state klasik

State-nya mulai butuh dua indeks, dan transisinya melibatkan pilihan "ambil / tidak" atau "cocok / tidak".

  • 0/1 Knapsack
  • Longest Common Subsequence (LCS)
  • Coin change (minimum koin)
  • Edit distance
Advance

State kompleks & multi-dimensi

Di level ini, state-nya bisa berdimensi banyak atau menempel pada struktur data lain seperti tree/graph.

  • DP pada grid 2D (unique paths, min path sum)
  • Interval DP (matrix chain multiplication)
  • State compression (bitmask DP)
  • DP pada tree / graph (tree DP, DAG shortest path)
◆ Harga · DP vs Greedy

Trade-off: solusi optimal terjamin vs kecepatan

DP sering dibandingkan dengan Greedy: greedy mengambil keputusan "terbaik saat ini" di tiap langkah tanpa menengok kembali, sedangkan DP mempertimbangkan seluruh subproblem sebelum memutuskan. Keduanya punya harga masing-masing.

// Dynamic Programming

  • Menjamin solusi optimal untuk masalah dengan overlapping subproblem & optimal substructure.
  • Mempertimbangkan semua kemungkinan lewat state, bukan cuma pilihan lokal.
  • Cocok untuk "jumlah cara" & "maks/min" dengan pilihan yang saling memengaruhi.

// Greedy

  • Lebih cepat & hemat memori — tak perlu tabel/cache.
  • Tidak selalu optimal — cuma benar untuk masalah dengan "greedy choice property".
  • Sekali salah pilih di satu langkah, tak ada cara "mundur" untuk perbaiki.
◆ Cara memilih

Kalau kamu bisa membuktikan bahwa pilihan lokal terbaik di tiap langkah selalu mengarah ke solusi global terbaik (mis. memberi kembalian dengan pecahan koin standar), greedy cukup & jauh lebih cepat. Kalau tidak bisa dibuktikan — atau ada counter-example yang bikin greedy salah — DP-lah yang menjamin jawaban benar, dengan harga waktu & memori lebih besar. Lihat topik Greedy di situs ini untuk perbandingan lebih dalam.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai dynamic programming

Aturan praktisnya: kalau soal minta "jumlah cara", "maksimum", atau "minimum" dari pilihan-pilihan yang saling memengaruhi, dan subproblem-nya overlap — DP kemungkinan besar cocok.

// Sinyal soal butuh DP

  • Kata kunci: "berapa banyak cara", "maksimum", "minimum".
  • Ada pilihan-pilihan berlapis yang saling memengaruhi hasil akhir.
  • Rekursi brute force jelas menghitung subproblem yang sama berulang.
  • Bisa didefinisikan state & transisi yang jelas antar subproblem.

// Sinyal DP tidak perlu / tidak cocok

  • Subproblem tidak overlap — tiap subproblem cuma dihitung sekali secara alami.
  • Pilihan lokal terbukti selalu optimal → greedy lebih sederhana & cepat.
  • Soal murni pencarian/traversal tanpa optimasi (cukup BFS/DFS biasa).
  • State-nya terlalu besar sehingga tabel/cache tidak muat di memori.
◆ Pertanyaan penentu

Tanyakan ke masalahmu: "Kalau saya selesaikan ini dengan rekursi polos, apakah ada subproblem identik yang akan saya hitung lebih dari sekali?" Kalau ya, dan solusi optimalnya memang bisa dibangun dari solusi optimal subproblem-nya — itu sinyal kuat DP akan membantu.

Studi kasus · Di dunia nyata

Di mana DP benar-benar dipakai di production

Tiga contoh nyata di mana dynamic programming bukan sekadar latihan soal, tapi jadi algoritma inti di balik tool yang dipakai sehari-hari.

// bioinformatika

Sequence alignment (DNA matching)

Kasus: mencocokkan dua urutan DNA/protein untuk melihat seberapa mirip, walau ada penyisipan/penghapusan basa. Kenapa DP: algoritmanya (Needleman-Wunsch, Smith-Waterman) pada dasarnya adalah variasi Longest Common Subsequence — mengisi tabel dp[i][j] berdasar kecocokan karakter demi karakter.

// dev tools

Spell checker & diff tool

Kasus: menghitung edit distance antara dua string untuk koreksi ejaan, atau menampilkan baris mana yang berubah antar dua versi file. Kenapa DP: edit distance adalah algoritma DP klasik, dan git diff serta diff Unix memakai pendekatan berbasis LCS yang serupa untuk mencari perubahan minimal.

// bisnis

Resource allocation & optimasi budget

Kasus: memilih kombinasi proyek/investasi terbaik dari anggaran terbatas, tiap opsi punya biaya & keuntungan berbeda. Kenapa DP: ini secara struktur adalah masalah knapsack-like — memaksimalkan nilai total di bawah batas kapasitas (budget), pola yang sama dengan 0/1 Knapsack.

◆ Benang merahnya

Di ketiga kasus di atas, masalahnya bisa dipecah menjadi keputusan-keputusan bertahap (cocokkan karakter ini atau tidak, ambil proyek ini atau tidak) yang saling memengaruhi hasil akhir, dan subproblem yang sama (pasangan indeks, sisa budget) muncul berulang di banyak jalur keputusan berbeda — persis dua syarat DP yang dibahas di bab 02.

Penutup

Catat jawabannya, jangan hitung ulang

Dynamic programming lahir dari pengamatan sederhana: banyak rekursi diam-diam menghitung hal yang sama berkali-kali. Begitu kamu bisa mengenali overlapping subproblems & optimal substructure, tinggal pilih arah implementasinya — top-down dengan memoization, atau bottom-up dengan tabulation.

  • Overlapping subproblems — subproblem yang sama muncul berulang.
  • Optimal substructure — solusi optimal dibangun dari solusi optimal subproblem-nya.
  • Memoization — top-down, cache ditambahkan di atas rekursi yang sudah benar.
  • Tabulation — bottom-up, isi tabel dari kasus dasar, lebih hemat stack.
  • DP vs Greedy — DP menjamin optimal, greedy lebih cepat tapi tak selalu benar.
  • Sinyal soal — "jumlah cara" / "maks-min" dengan pilihan yang saling memengaruhi.

Aturan emasnya

Mulai dari rekursi brute force yang benar. Tanyakan: apakah ada subproblem identik yang dihitung berulang? Kalau ya, tambahkan memoization dulu — baru pertimbangkan tabulation kalau butuh hemat memori atau menghindari overhead call stack. DP bukan sihir, ia cuma cara jujur untuk tidak lupa jawaban yang sudah pernah kamu hitung.
