// Problem Solving — sebelum submit, uji dulu solusimu sendiri

"Kelihatan benar" bukan bukti kalau benar.

Solusi yang lolos di kepalamu, atau bahkan lolos satu-dua contoh kasus, belum tentu benar untuk semua kemungkinan input. Skill yang jarang diajarkan eksplisit: bagaimana caranya menguji solusimu sendiri, secara sistematis, sebelum orang lain — reviewer, judge, atau production — yang menemukan bugnya duluan. Deck ini soal dry run, edge case, dan kebiasaan menelusuri kode baris demi baris sebelum kamu yakin untuk submit.

◆ Buat apa ini? Kenapa pakai Edge Case Testing?

Given — solusimu sudah lolos dijalankan dengan contoh kasus yang diberikan di soal, dan kelihatan benar di kepalamu.

When — solusi itu dicoba dengan input yang tidak ada di contoh: array kosong, elemen tunggal, semua nilai sama, angka negatif/nol, atau data yang sudah terurut terbalik.

Then — kode diam-diam mengembalikan nilai salah, crash, atau lolos submit tapi gagal di hidden test/production — dan kamu baru sadar setelah reviewer, judge, atau user yang menemukannya duluan.

→ makanya kita pakai Edge Case Testing.

Akar masalah · Kenapa testing sendiri itu skill penting

Solusi yang jalan di kepalamu, belum tentu jalan di kenyataan

Pola yang sangat umum: kamu menulis solusi, jalankan sekali dengan contoh kasus yang diberikan, hasilnya cocok, lalu submit. Masalahnya, contoh kasus di soal biasanya dipilih supaya mudah dipahami — bukan supaya menjebak solusimu. Kasus yang benar-benar menjebak biasanya ada di tempat lain: input kosong, angka negatif, elemen yang semuanya sama.

Setelah solusi ditemukan, ada satu langkah yang paling sering dilewatkan padahal paling berharga: menengok kembali — memeriksa ulang hasilnya dan menelusuri lagi jalan argumennya. Justru di langkah inilah kesalahan yang tersembunyi biasanya baru ketahuan.

— parafrase dari George Pólya, How to Solve It, fase "Looking Back"
◆ Analogi — pilot yang tetap jalankan pre-flight checklist

Pilot dengan ribuan jam terbang tetap membaca checklist yang sama, satu per satu, setiap kali sebelum lepas landas. Bukan karena dia lupa cara terbang — tapi karena checklist menangkap hal-hal yang rasa percaya diri dan ingatan tidak bisa jamin selalu diperiksa. Programmer sering melewatkan langkah ini justru karena merasa sudah cukup jago atau terburu-buru mengejar deadline. Padahal makin rumit soalnya, makin besar kemungkinan ada sudut yang belum terpikirkan — dan checklist itulah yang menyelamatkanmu, bukan intuisi semata.

Testing terhadap solusi sendiri bukan langkah tambahan yang opsional kalau sempat — ia bagian dari proses menyelesaikan masalah itu sendiri. Solusi yang "kelihatan benar" tapi belum diuji ke ujung-ujung kasusnya, sebenarnya belum selesai; ia baru kandidat solusi.

Konsep inti · Kategori edge case standar

Tujuh kategori edge case yang wajib kamu cek

Sebelum memikirkan kasus yang spesifik untuk soalmu, ada daftar kategori generik yang hampir selalu layak dicoba: input kosong/null, elemen tunggal, semua elemen sama, angka negatif/nol, angka sangat besar/kecil (overflow), duplikat, dan urutan terbalik.

Pengujian yang efektif berarti secara sengaja memburu kondisi batas — titik-titik di mana program paling mungkin gagal — bukan sekadar menjalankan kasus yang "kelihatan normal". Bug hampir selalu bersembunyi di ujung-ujung kondisi, bukan di tengah-tengah kasus biasa.

— parafrase dari Steve McConnell, Code Complete
// 01

Input kosong / null

Array kosong, string kosong, atau null/undefined. Solusi naif sering langsung crash atau mengembalikan nilai yang salah tanpa disadari.

// 02

Elemen tunggal

Cuma ada satu elemen. Loop yang berasumsi "minimal dua item" (mis. bandingkan elemen ke-1 dan ke-2) akan meleset.

// 03

Semua elemen sama

Tidak ada variasi nilai. Logika yang mengandalkan "yang paling beda" atau "urutan unik" gampang salah di sini.

// 04

Angka negatif / nol

Banyak solusi diam-diam berasumsi semua angka positif. Nol juga sering jadi celah — pembagian, index, atau kondisi if yang salah tanda.

// 05

Angka sangat besar/kecil

Overflow tipe data, presisi floating point, atau angka yang melewati batas aman bahasa pemrogramanmu.

// 06

Duplikat

Nilai yang muncul berulang. Solusi yang berasumsi "semua nilai unik" (mis. cari elemen kedua terbesar) sering meleset di sini.

// 07

Urutan terbalik

Data yang sudah terurut menurun, bukan menaik. Algoritma yang diam-diam berasumsi data "biasanya" naik bisa gagal total.

Contoh: fungsi mencari nilai terbesar dalam array yang sudah menangani semua kategori itu secara eksplisit.

cariTerbesar.jsJS
function cariTerbesar(arr) {
  if (!arr || arr.length === 0) {
    throw new Error("array kosong atau null");
  }
  let terbesar = arr[0];
  for (let i = 1; i < arr.length; i++) {
    if (arr[i] > terbesar) terbesar = arr[i];
  }
  return terbesar;
}
test-cases.js — satu test per kategoriJS
// 1. elemen tunggal
cariTerbesar([5]) === 5

// 2. semua elemen sama
cariTerbesar([3, 3, 3]) === 3

// 3. angka negatif
cariTerbesar([-5, -1, -9]) === -1

// 4. campuran negatif & nol
cariTerbesar([-2, 0, -8]) === 0

// 5. urutan terbalik (menurun)
cariTerbesar([9, 7, 3, 1]) === 9

// 6. duplikat nilai terbesar
cariTerbesar([4, 9, 9, 2]) === 9

// 7. angka sangat besar (dekat batas aman)
cariTerbesar([Number.MAX_SAFE_INTEGER, 1]) === Number.MAX_SAFE_INTEGER

// 8. array kosong -> harus throw, bukan diam-diam return undefined
cariTerbesar([]) // Error
Teknik · Dry run & trace manual

Telusuri kodemu baris per baris sebelum orang lain yang menemukan bugnya

Dry run artinya menjalankan kode di kepala (atau di atas kertas) tanpa benar-benar mengeksekusinya di komputer — ambil satu input kecil yang "nakal", lalu telusuri tiap baris sambil mencatat nilai variabel yang berubah, baris demi baris, sampai selesai.

Kenapa harus input kecil? Karena tujuannya menelusuri logika, bukan menghitung. Array dengan 3-4 elemen yang dipilih khusus untuk memicu kasus tricky (duplikat, elemen tunggal, dst) jauh lebih berguna untuk trace manual daripada array dengan seribu elemen acak.

keduaTerbesar.js — belum di-dry runJS
function keduaTerbesar(arr) {
  let terbesar = -Infinity, kedua = -Infinity;
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] > terbesar) {
      kedua = terbesar;
      terbesar = arr[i];
    } else if (arr[i] > kedua) {
      kedua = arr[i];
    }
  }
  return kedua;
}
// dry run arr = [9, 9, 7]:
// i0: 9 > -Inf  -> kedua=-Inf, terbesar=9
// i1: 9 > 9 ? false -> else if 9 > -Inf -> kedua=9  (!! bug)
// i2: 7 > 9 ? false -> else if 7 > 9 ? false
// return kedua = 9  -> salah, harusnya 7
keduaTerbesarAman.js — sudah lolos dry runJS
function keduaTerbesarAman(arr) {
  if (!arr || arr.length < 2) {
    throw new Error("butuh minimal 2 elemen");
  }
  let terbesar = -Infinity, kedua = -Infinity;
  for (let i = 0; i < arr.length; i++) {
    const v = arr[i];
    if (v > terbesar) {
      kedua = terbesar;
      terbesar = v;
    } else if (v > kedua && v < terbesar) {
      kedua = v;
    }
  }
  if (kedua === -Infinity) {
    throw new Error("tidak ada nilai kedua yang berbeda");
  }
  return kedua;
}
// dry run arr = [9, 9, 7]:
// i0: 9 > -Inf -> kedua=-Inf, terbesar=9
// i1: v=9, 9>9 false; else if 9>kedua(-Inf) DAN 9<terbesar(9)? false -> skip
// i2: v=7, 7>9 false; else if 7>-Inf DAN 7<9 -> kedua=7
// return kedua = 7  -> benar

Bug di versi kiri tidak akan ketahuan kalau kamu cuma coba input seperti [3, 7, 5] — semua elemen berbeda, jawabannya kebetulan tetap benar. Bug itu baru muncul saat nilai terbesar duplikat, dan dry run dengan input kecil [9, 9, 7] menelusuri baris per baris cukup untuk menemukannya sebelum solusi ini di-submit. Versi kanan menambah satu syarat (v < terbesar) supaya duplikat dari nilai terbesar tidak dianggap sebagai "kedua terbesar".

◆ Kebiasaan · Best practice sebelum submit

Enam kebiasaan sebelum kamu tekan submit

Testing sendiri bukan soal bakat, tapi soal kebiasaan yang bisa dilatih. Berikut urutan yang biasa dipakai orang yang disiplin sebelum yakin solusinya siap.

  • Buat minimal 3 test case sebelum submit — satu kasus normal, satu kasus edge, satu kasus ekstrem. Jangan cuma andalkan contoh dari soal.
  • Trace manual dengan input terkecil dulu — coba array 0, 1, lalu 2 elemen sebelum mikirin input besar. Bug logika biasanya sudah kelihatan di ukuran kecil.
  • Cek tipe data & potensi overflow — apakah angkanya bisa melebihi batas aman tipe data? Apakah index bisa negatif atau keluar batas array?
  • Baca ulang requirement setelah dapat solusi — cocokkan lagi tiap kalimat di soal dengan kodemu. Sering ada syarat kecil (mis. "urutan harus dipertahankan") yang kelewat saat fokus ke logika utama.
  • Uji dengan input yang sengaja menjebak asumsimu — semua elemen sama, urutan terbalik, duplikat di posisi kritis. Tanyakan: "asumsi apa yang diam-diam kubuat di sini?"
  • Kalau ada waktu, tulis ulang dari nol tanpa lihat kode lama — bandingkan hasil keduanya. Kalau beda, salah satu (atau keduanya) masih ada bug.
◆ Level · Tier belajar

Dari sekadar tahu daftar, sampai menulis test otomatis

Kemampuan menguji solusi sendiri ini bertingkat. Kamu tidak perlu langsung jago fuzzing — mulai dari yang paling dasar dan naik pelan-pelan.

Beginner

Kenal & jalankan daftar standar

Bisa menyebutkan kategori edge case umum dan mencoba satu-satu secara manual, meski masih dari daftar template generik.

  • Ingat 7 kategori edge case standar
  • Mencoba input kosong & elemen tunggal
  • Trace manual dengan bantuan print statement
Middle

Menemukan edge case spesifik soal

Tidak cuma pakai template umum — mulai bisa membaca soal dan menebak di mana soal ini spesifik rawan gagal, bukan sekadar edge case generik.

  • Menganalisis constraint soal untuk cari celah
  • Dry run dengan kasus rancangan sendiri
  • Curiga pada asumsi implisit di kodenya sendiri
Advance

Test otomatis & fuzzing sederhana

Untuk soal yang kompleks, menulis test otomatis atau property-based test, bahkan fuzzing sederhana untuk menemukan kasus yang tak terpikirkan manusia.

  • Unit test otomatis untuk regresi
  • Property-based testing (invariant, bukan contoh tunggal)
  • Fuzzing sederhana / random input generator
◆ Kesalahan umum · Kebiasaan yang bikin celaka

Disiplin menguji vs. "submit and pray"

Perbedaan antara solver yang konsisten dan yang sering kebobolan bug bukan soal seberapa pintar — tapi soal kebiasaan sebelum menekan submit.

// ✅ Kebiasaan disiplin

  • Coba minimal satu edge case sebelum submit, bukan cuma contoh soal.
  • Trace manual saat kode "kelihatan" sudah benar tapi belum diverifikasi.
  • Curiga pada solusi yang berhasil di percobaan pertama tanpa dicek ulang.
  • Menuliskan kembali asumsi yang dipakai, lalu mengujinya satu per satu.

// ❌ "Submit and pray"

  • Langsung submit begitu compiler tidak error.
  • Hanya menjalankan contoh kasus yang diberikan di soal.
  • Menganggap "kelihatan benar" sama dengan "sudah benar".
  • Baru mulai berpikir soal edge case setelah dapat Wrong Answer / bug report.
◆
Ini bukan soal jadi paranoid dan menguji segalanya sampai lupa waktu — ada titik cukup. Tapi jeda beberapa menit untuk dry run sebelum submit hampir selalu lebih murah daripada biaya debug setelah gagal di hadapan reviewer, judge, atau — lebih parah — di production.
◆ Keputusan · Kapan cukup, kapan butuh lebih

Kapan dry run manual cukup, kapan butuh test otomatis

Tidak semua soal butuh test suite lengkap. Tapi ada titik di mana mengandalkan trace manual saja mulai berisiko.

// Manual/dry run biasanya cukup

  • Soal interview atau latihan dengan input kecil & jelas.
  • Logika algoritma sederhana, jumlah cabang kondisi sedikit.
  • Waktu terbatas (mis. sesi interview live, kontes cepat).
  • Kode sekali pakai, bukan yang akan dipelihara jangka panjang.

// Butuh test otomatis

  • Banyak kombinasi kondisi/cabang yang mustahil ditelusuri manual satu-satu.
  • Kode akan dipelihara & diubah berulang kali (butuh regresi).
  • Bug punya konsekuensi mahal (production, transaksi keuangan).
  • Soal kompetitif yang kompleks — property-based test / stress test lawan brute force.
◆ Pertanyaan penentu

Tanyakan: "Kalau aku salah menebak satu edge case saat trace manual, apa akibatnya?" Kalau cuma harus mengulang submisi, dry run manual biasanya cukup. Kalau akibatnya bug lolos ke production atau logikanya terlalu rumit untuk ditelusuri semuanya di kepala, saatnya menulis test otomatis.

Studi kasus · Di dunia nyata

Tiga konteks tempat edge case benar-benar menentukan

Bukan teori abstrak — ini pola yang berulang di tiga konteks yang sangat berbeda, tapi akar masalahnya sama: edge case yang tak terpikirkan sampai sudah terlambat.

// interview coding

Interviewer sengaja menambah edge case

Pola umum di interview: kandidat kasih solusi awal yang "kelihatan benar", lalu interviewer dengan sengaja menyodorkan input aneh — array kosong, semua elemen sama, angka negatif — untuk melihat reaksi kandidat. Yang dinilai bukan cuma apakah solusinya bertahan, tapi apakah kandidat terbiasa memikirkan kasus itu sendiri sebelum ditanya.

// bug production

Divide by zero & array kosong

Sebagian bug production yang paling klasik berakar dari edge case sederhana yang lolos dari testing: pembagian dengan penyebut nol, atau operasi terhadap array/list kosong yang seharusnya divalidasi lebih dulu. Bug ini sering baru muncul saat kondisi data di lapangan berbeda dari asumsi saat development.

// competitive programming

Wrong Answer karena n=0 atau n=1

Di kontes, solusi yang lolos contoh kasus tapi dapat status Wrong Answer sering kali gagal justru di batas kecil constraint — n = 0 atau n = 1 — kasus yang jarang eksplisit ditulis di soal tapi tetap valid menurut batasannya.

⚙ Ekosistem · Tools & referensi

Alat bantu untuk menguji solusimu sendiri

Kamu tidak butuh alat mahal untuk mulai disiplin menguji. Yang penting konsisten dipakai, dari yang paling sederhana sampai yang lebih formal.

// paling dasar

Print statement / debugger

Cara paling sederhana untuk dry run: sisipkan print/console.log di titik-titik kunci, atau pakai debugger untuk melihat nilai variabel baris demi baris — persis seperti trace manual, tapi dibantu komputer.

// soal lebih besar

Unit testing framework

Untuk kode yang lebih besar dari satu fungsi, framework seperti Jest, PyTest, atau JUnit membantu menjalankan banyak test case sekaligus dan menjaga agar perubahan baru tidak merusak test yang sudah lolos.

// reusable

Checklist edge case pribadi

Simpan daftar 7 kategori edge case (kosong, tunggal, semua sama, negatif/nol, overflow, duplikat, terbalik) di satu tempat yang gampang diakses, lalu jalankan checklist itu tiap kali sebelum submit — bukan mengarang ulang tiap kali dari nol.

Penutup

Uji dulu, baru yakin — bukan sebaliknya

Testing solusi sendiri bukan tanda kamu tidak percaya diri — justru tanda kamu cukup berpengalaman untuk tahu di mana biasanya bug bersembunyi.

  • "Kelihatan benar" bukan bukti — hanya lolos di satu contoh kasus, bukan semua kasus.
  • Tujuh kategori edge case standar — kosong, tunggal, semua sama, negatif/nol, overflow, duplikat, terbalik.
  • Dry run pakai input terkecil dulu — telusuri baris per baris sebelum submit.
  • Looking back itu bukan opsional — Pólya menyebutnya fase yang paling sering dilewatkan.
  • Bug bersembunyi di batas, bukan di tengah — cari kondisi batas dengan sengaja.
  • Manual cukup untuk soal kecil, otomatis untuk yang kompleks — pilih sesuai risikonya.

Langkah belajar berikutnya

Sudah terbiasa menguji solusimu sendiri? Langkah selanjutnya: apa yang kamu lakukan ketika testing itu menemukan bug. Lanjut ke halaman Debugging Strategy untuk mempelajari cara melacak akar masalah secara sistematis, bukan menebak-nebak.
