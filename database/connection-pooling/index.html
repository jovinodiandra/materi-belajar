// Database — fondasi yang sering dilupakan sampai server tumbang

Jangan buka koneksi baru tiap kali. Pinjam dari kolam.

Bikin koneksi ke database itu mahal — bukan soal uang, tapi soal waktu dan resource. Kalau tiap request aplikasi kamu buka-tutup koneksi sendiri, di trafik kecil aman, tapi pas rame database-nya bakal megap-megap. Connection pooling jawabannya: sekumpulan koneksi yang sudah siap pakai, dipinjam sebentar, lalu dikembalikan. Deck ini ngebahas kenapa dibutuhkan dulu, baru cara kerjanya, lengkap sama analogi dan kasus nyata yang bikin server orang beneran down.

◆ Buat apa ini? Kenapa pakai Connection Pooling?

Given — aplikasi kamu memanggil connect() baru setiap kali ada request yang butuh akses database, tanpa ada pool sama sekali.

When — trafik naik ke ratusan/ribuan request per detik bersamaan (jam sibuk, promo, lonjakan traffic).

Then — tiap request mengulang ritual mahal TCP handshake + TLS + auth (20–100ms) dari nol, database kehabisan slot max_connections, dan di Postgres tiap koneksi baru bahkan bikin proses OS baru yang memakan RAM sampai akhirnya database megap-megap atau menolak koneksi.

→ makanya kita pakai Connection Pooling.

Akar masalah · Kenapa pooling ada

Membuka koneksi database itu pekerjaan berat

Buat kita, connect() kelihatan kayak satu baris instan. Padahal di balik layar, buka satu koneksi database itu ritual panjang — dan tiap langkahnya makan waktu.

Begitu aplikasi minta koneksi baru, kira-kira ini yang terjadi:

◆ Apa yang sebenarnya terjadi pas "buka 1 koneksi"
1. TCPthree-way handshake (SYN → SYN-ACK → ACK)
2. TLSnegosiasi enkripsi + tukar sertifikat (kalau pakai SSL)
3. Authkirim user/password, server verifikasi
4. SesiDB alokasikan memori, proses/thread, set variabel sesi

Total bisa 20–100 milidetik hanya untuk siap pakai — padahal query-nya sendiri mungkin cuma 1 ms. Di Postgres, tiap koneksi bahkan bikin proses OS baru yang makan beberapa MB RAM. Bukan operasi yang ringan.

◆ Analogi — menelepon bank

Bayangin tiap mau tanya saldo, kamu harus: tekan nomor → tunggu nada → dengerin menu → masukin PIN → verifikasi → baru ngomong. Ritualnya jauh lebih lama dari pertanyaannya sendiri. Konyol kalau diulang tiap kali cuma buat nanya satu hal. Itu persis yang terjadi kalau aplikasi buka koneksi baru tiap query.

Sekali atau dua kali nggak kerasa. Tapi aplikasi web melayani ratusan sampai ribuan request per detik. Kalau tiap request mengulang ritual mahal ini dari nol, kamu membuang waktu dan resource yang sama, berulang-ulang. Di bab berikutnya kita lihat seberapa cepat ini jadi bencana.

Khusus Postgres · Satu koneksi = satu proses OS

Di PostgreSQL, koneksi jauh lebih mahal lagi

Semua database bayar pajak handshake. Tapi Postgres punya beban tambahan yang bikin koneksinya termasuk yang paling mahal: untuk tiap koneksi, server menjalankan fork() — membuat satu proses sistem operasi baru (disebut backend process). Bukan thread ringan, tapi proses penuh.

◆ Analogi — menyewa pegawai tetap, bukan menyeret kursi

Database lain (mis. MySQL) menambah koneksi seperti menyeret satu kursi ekstra ke meja — ringan. Postgres menambah koneksi seperti merekrut satu pegawai tetap baru: dia butuh meja sendiri, ruang sendiri, dan tetap digaji walau lagi nganggur. Sepuluh pegawai? Boleh. Seribu pegawai untuk kerja yang sama? Kantornya jebol.

Konsekuensinya berlapis, dan inilah kenapa pooling di Postgres bukan optimasi mewah tapi nyaris wajib:

// fork() mahal

Proses baru tiap koneksi

Tiap connect() memicu fork() di server — bikin proses OS itu sendiri butuh waktu & kerja kernel, jauh lebih berat dari sekadar handshake.

// RAM

~5–10 MB per koneksi

Tiap backend process makan memori sendiri. 500 koneksi nganggur bisa menghabiskan beberapa GB RAM — sebelum satu query pun jalan.

// work_mem

Memori dikali-kali

work_mem dialokasikan per operasi, per koneksi. Satu query rumit bisa pakai beberapa kali work_mem; kalikan ratusan koneksi → ledakan memori & risiko OOM.

// shared state

Rebutan resource bersama

Makin banyak proses, makin sengit rebutan lock manager, shared buffer, & perhatian scheduler OS. Banyak koneksi justru bikin semua lebih lambat.

◆ Kenapa max_connections default-nya cuma 100
Defaultmax_connections = 100
Naifmax_connections = 5000 -- "biar muat semua"

Menaikkan angka ini bukan solusi gratis: tiap slot = potensi satu proses + memorinya. Naikin ke ribuan = boros RAM, scheduler keteteran, dan throughput malah turun. Cara yang benar bukan "perbesar batas DB", tapi "perkecil jumlah koneksi nyata lewat pooling".

◆ Intinya

Karena tiap koneksi Postgres = satu proses OS yang mahal & rakus memori, jumlah koneksi adalah sumber daya langka yang harus dijaga ketat. Pool koneksi (di app) + pooler eksternal seperti PgBouncer (di depan DB) adalah cara standar untuk melayani ribuan client dengan hanya segelintir koneksi nyata ke Postgres. Itu yang kita bahas di Kasus #3.

Pendekatan naif · 1 request = 1 koneksi

“Ya udah, buka koneksi pas butuh, tutup pas selesai”

Ini cara paling polos — dan untuk skrip kecil yang jalan sekali, nggak apa-apa. Masalahnya muncul pas pola ini dipakai di server yang melayani banyak orang sekaligus.

handler.js — buka-tutup koneksi tiap requestNode.js
import { Client } from "pg";

// ⚠️ dipanggil di SETIAP request yang masuk
async function handler(req, res) {
  const client = new Client(DB_CONFIG);
  await client.connect();      // 🐢 ritual mahal 20–100ms, tiap request

  const { rows } = await client.query("SELECT * FROM users WHERE id=$1", [req.id]);

  await client.end();          // koneksi dibuang, sia-sia
  res.json(rows);
}

Dua hal jelek terjadi sekaligus di sini:

// Boros waktu

  • Tiap request bayar pajak 20–100ms cuma buat connect, sebelum query jalan.
  • Latensi yang dirasakan user jadi berlipat — query 1ms tapi total 80ms.
  • Throughput anjlok: server sibuk handshake, bukan kerja beneran.

// Boros resource DB

  • Database punya batas koneksi (mis. Postgres default max_connections=100).
  • 1.000 request bersamaan → 1.000 koneksi → DB nolak sisanya.
  • Tiap koneksi makan RAM; ribuan koneksi bisa bikin DB OOM / crash.
◆
Pesan error legendaris yang muncul gara-gara pola ini: "FATAL: sorry, too many clients already" (Postgres) atau "Too many connections" (MySQL). Kalau kamu pernah lihat ini di production, kemungkinan besar pelakunya: nggak ada pooling, atau poolnya salah setel.
Inti konsep · Connection pool

Siapkan sekali, pakai berulang kali

Ide connection pool sederhana: daripada bikin-buang koneksi terus-menerus, buat sejumlah koneksi sekali di awal, simpan dalam "kolam" (pool), lalu pinjamkan ke siapa pun yang butuh. Selesai dipakai, koneksinya dikembalikan ke kolam — bukan ditutup.

◆ Analogi — armada taksi di depan hotel

Bayangin hotel besar. Cara naif = tiap tamu yang mau pergi harus nelpon pabrik mobil, nunggu mobil diproduksi, baru jalan. Gila, kan? Cara pool = hotel menyiapkan armada taksi standby di lobi. Tamu datang → naik taksi yang sudah ada → balik → taksi nunggu tamu berikutnya. Mobilnya itu-itu lagi, cuma penumpangnya ganti-ganti. Koneksi = taksi. Request = tamu.

Analogi lain yang juga pas: loket bank. Bank nggak buka loket baru tiap ada nasabah datang. Mereka buka, katakanlah, 10 loket. Nasabah dilayani lewat loket yang kosong; kalau semua penuh, nasabah antri sampai ada yang selesai. Itu persis perilaku connection pool: jumlah koneksi terbatas dan dipakai bergantian, dengan antrian saat ramai.

// cepat

Tanpa pajak handshake

Koneksi sudah "nyala". Request langsung query — buang waktu 20–100ms per request hilang.

// terkendali

Jumlah dibatasi

Pool cuma punya N koneksi. DB nggak akan pernah kebanjiran melebihi N, berapa pun request masuk.

// efisien

Resource dipakai ulang

Memori & proses di sisi DB stabil, nggak naik-turun liar mengikuti trafik.

Siklus hidup · Acquire → Use → Release

Pinjam, pakai, lalu kembalikan

Tiga kata kunci yang harus nempel di kepala: acquire (pinjam koneksi dari pool), use (jalankan query), release (kembalikan ke pool). Kuncinya: kamu tidak pernah benar-benar menutup koneksinya — kamu cuma meminjam dan mengembalikan.

sebelum — Client per requestNode.js
const client = new Client(cfg);
await client.connect();   // mahal
await client.query(sql);
await client.end();       // dibuang

// tiap request ulang dari nol
sesudah — pinjam dari PoolNode.js
// dibuat SEKALI saat app start
const pool = new Pool(cfg);

// di tiap request:
const { rows } = await pool.query(sql);
// pool otomatis: acquire → query → release

Untuk query tunggal, pool.query() mengurus semuanya otomatis. Tapi kalau kamu butuh beberapa query dalam satu koneksi yang sama (misalnya transaksi), kamu pinjam manual — dan di sinilah release jadi wajib hukumnya:

transfer.js — pinjam manual untuk transaksiNode.js
const client = await pool.connect();   // ACQUIRE — pinjam 1 koneksi dari kolam
try {
  await client.query("BEGIN");
  await client.query("UPDATE akun SET saldo = saldo - 100 WHERE id=1");
  await client.query("UPDATE akun SET saldo = saldo + 100 WHERE id=2");
  await client.query("COMMIT");                    // USE — semua di koneksi yang sama
} catch (e) {
  await client.query("ROLLBACK");
  throw e;
} finally {
  client.release();      // RELEASE — WAJIB! balikin ke kolam, apa pun yang terjadi
}
◆ Catatan kunci

release() ditaruh di finally supaya koneksi selalu balik ke kolam — baik query sukses maupun error. Lupa release() = koneksi "hilang" dari kolam selamanya. Itu namanya connection leak, dan kita bahas khusus nanti karena ini penyebab insiden paling sering.

◆ Anatomi · Tombol-tombol pengaturan

Parameter yang wajib kamu mengerti

Tiap library pool (HikariCP di Java, pg.Pool di Node, SQLAlchemy di Python) punya tombol pengaturan yang mirip-mirip. Ini yang paling penting — pahami artinya, bukan cuma hafal namanya.

pool config — anotasi tiap parameterNode.js
const pool = new Pool({
  max: 20,                       // jumlah koneksi MAKSIMUM di kolam
  min: 2,                        // koneksi minimum yang selalu standby
  idleTimeoutMillis: 30000,      // koneksi nganggur 30s → ditutup (hemat resource)
  connectionTimeoutMillis: 5000, // nunggu pinjam max 5s, lewat itu → error
  maxLifetimeMillis: 1800000,    // koneksi diremajakan tiap 30 menit
});
// max (pool size)

Batas atas koneksi

Paling penting. Berapa koneksi maksimum yang boleh hidup. Inilah yang melindungi DB dari kebanjiran. Bab berikutnya khusus soal angka ini.

// min (idle)

Koneksi standby

Jumlah koneksi yang dijaga tetap hidup walau sepi, biar request pertama saat sepi nggak kena pajak handshake.

// connectionTimeout

Sabar menunggu giliran

Kalau semua koneksi lagi dipakai, request baru antri. Lewat batas ini → langsung error, daripada nunggu selamanya (hang).

// idleTimeout

Tutup yang nganggur

Koneksi yang lama nggak dipakai ditutup, balikin resource ke DB saat trafik turun.

// maxLifetime

Peremajaan berkala

Koneksi tua ditutup & diganti baru. Mencegah masalah memori, koneksi basi, atau "ketinggalan" saat DB di-failover.

// validation

Cek sehat dulu

Sebelum dipinjamkan, pool bisa tes koneksi (mis. SELECT 1) supaya kamu nggak dapat koneksi yang diam-diam sudah mati.

◆
connectionTimeout ≠ query timeout. Yang ini soal "berapa lama nunggu dapat koneksi dari kolam", bukan "berapa lama query boleh jalan". Sering ketukar dan bikin pusing pas debugging.
◆ Anatomi · Angka yang paling sering salah

Sebesar apa pool seharusnya?

Insting orang: "biar kencang, gedein aja poolnya, kasih max: 500." Ini salah besar dan justru memperlambat. Pool yang kebesaran sama bahayanya dengan yang nggak ada.

// Pool kekecilan

  • Banyak request antri nunggu koneksi kosong.
  • Latensi naik, request bisa kena connectionTimeout.
  • Resource DB nganggur padahal app megap-megap.

// Pool kebesaran

  • DB kebanjiran koneksi → rebutan CPU, disk, lock.
  • Context-switching makin sering → semua jadi lebih lambat.
  • Kalikan jumlah instance app → total koneksi meledak.
◆ Analogi — kasir minimarket

Buka 50 kasir buat toko yang cuma muat 10 antrian itu konyol: kasirnya bengong, lorong sesak, malah ribet. Buka 1 kasir pas jam ramai? Antrian ngular sampai luar. Yang benar: jumlah kasir pas dengan beban. Pool size juga gitu — bukan "sebanyak mungkin", tapi "secukupnya untuk kerja paralel yang nyata".

Patokan klasik dari tim HikariCP (dan ini mengejutkan banyak orang): pool yang kecil tapi pas hampir selalu mengalahkan pool besar. Rumus titik awal yang sering dipakai:

rumus titik-awal (bukan harga mati)rule of thumb
# Patokan untuk beban yang berat di CPU/disk DB:
koneksi = (jumlah_core_CPU_db × 2) + jumlah_disk_efektif

# Contoh: DB dengan 4 core, 1 SSD
koneksi = (4 × 2) + 1 = 9   # ya, cuma ~9-10, bukan 500!

# PENTING: ini total ke DB. Kalau app jalan di 10 instance,
# dan tiap instance max=10 → 100 koneksi ke DB. Hitung totalnya!
◆ Cara benar menentukan angka

Rumus cuma titik awal. Yang sahih: ukur. Pantau berapa koneksi yang benar-benar aktif saat beban puncak, lihat latensi & antrian pool, lalu setel. Dan selalu ingat: max_connections DB harus ≥ (pool size × jumlah instance app) + koneksi lain (admin, migrasi, monitoring).

Kasus #1 · Lonjakan trafik

Saat flash sale, pool jadi penjaga gerbang

Skenario nyata: aplikasi e-commerce, normalnya 100 request/detik. Jam 12 malam mulai flash sale, mendadak 5.000 request/detik. Apa yang terjadi?

// Tanpa pool (atau pool tak terbatas)

  • 5.000 request → coba buka 5.000 koneksi.
  • DB kena max_connections → tolak koneksi.
  • Error nyebar ke semua fitur, bahkan yang nggak ikut sale.
  • DB bisa crash total → seluruh situs down.

// Dengan pool (mis. max=20)

  • Max 20 query jalan paralel; sisanya antri rapi.
  • DB tetap sehat, kerja pada kapasitas optimalnya.
  • Request yang antri kelamaan kena timeout → bisa di-retry.
  • Situs melambat, tapi tidak mati.
◆ Analogi — pintu klub malam

Klub punya kapasitas aman. Pas rame, satpam di pintu nahan antrian: masuk satu kalau keluar satu. Nggak seideal "semua langsung masuk", tapi mencegah desak-desakan mematikan di dalam. Pool itu satpamnya database — dia rela bikin orang antri demi menjaga yang di dalam tetap hidup.

Pelajarannya: pool bukan cuma soal kecepatan, tapi perlindungan. Dia mengubah "kelebihan beban yang mematikan" jadi "antrian yang bisa dikendalikan". Ini wujud kecil dari pola backpressure — menahan laju masuk supaya sistem hilir nggak jebol.

Kasus #2 · Connection leak

Bug paling sering: lupa mengembalikan koneksi

Connection leak terjadi saat kamu meminjam koneksi tapi nggak pernah mengembalikannya. Koneksi itu "hilang" dari kolam. Lakukan beberapa kali, kolam habis, dan aplikasi hang — semua request nunggu koneksi yang nggak akan pernah balik.

BOCOR — release hilang saat errorNode.js
const client = await pool.connect();
const r = await client.query(sql);
// ⚠️ kalau query() di atas THROW,
// baris di bawah TAK PERNAH jalan →
// koneksi bocor selamanya
client.release();
return r.rows;
AMAN — finally menjamin releaseNode.js
const client = await pool.connect();
try {
  const r = await client.query(sql);
  return r.rows;
} finally {
  client.release();   // jalan APA PUN yang terjadi
}
◆ Analogi — buku perpustakaan

Perpustakaan punya 10 eksemplar buku populer. Tiap orang pinjam tapi nggak ada yang balikin. Hari ke berapa pun, rak kosong — bukan karena bukunya dibakar, tapi karena nyangkut di tangan orang. Pengunjung baru nggak kebagian, padahal bukunya "ada". Itu connection leak: koneksinya hidup, tapi nyangkut, nggak balik ke kolam.

◆ Gejala & deteksi

Gejalanya khas: aplikasi jalan normal beberapa jam, lalu perlahan melambat dan akhirnya semua request hang / timeout saat pinjam koneksi — tanpa lonjakan trafik. Tools pool (mis. leakDetectionThreshold di HikariCP) bisa nge-log koneksi yang dipinjam kelamaan. Pencegahan terbaik: selalu finally { release() }, atau pakai pola helper/wrapper yang otomatis melepas.

Kasus #3 · Skala & serverless

Saat pool di dalam app saja tidak cukup

Pool di dalam aplikasi bagus untuk satu proses yang hidup lama. Tapi ada situasi di mana dia kewalahan — dan kamu butuh pooler eksternal seperti PgBouncer yang duduk di antara app dan database.

Masalahnya muncul saat jumlah proses app meledak:

// banyak instance

Auto-scaling

App di-scale ke 100 pod, tiap pod punya pool max=20 → 2.000 koneksi nyerbu DB yang cuma kuat 100. Tiap pool merasa "sopan", totalnya tetap membunuh DB.

// serverless

Functions (Lambda)

Tiap invocation = proses baru & berumur pendek. Pool dalam-app nyaris percuma — koneksi nggak sempat dipakai ulang, malah bikin badai koneksi.

◆ Analogi — resepsionis bersama

Bayangin gedung dengan 100 kantor kecil. Kalau tiap kantor punya saluran telepon langsung ke pusat, kabelnya nggak cukup. Solusinya: satu resepsionis bersama (PgBouncer) memegang sedikit saluran ke pusat, lalu membagikannya bergiliran ke 100 kantor. Pusat (database) cuma "kenal" segelintir saluran, padahal melayani ratusan penelepon.

pgbouncer.ini — pooler di depan Postgresini
; ribuan koneksi dari app boleh masuk ke sini...
max_client_conn = 2000

; ...tapi PgBouncer cuma pegang segelintir ke DB asli
default_pool_size = 20

; transaction = koneksi DB dipinjamkan PER TRANSAKSI (paling hemat)
pool_mode = transaction
◆
Mode transaction pooling sangat hemat koneksi, tapi ada syaratnya: fitur yang nempel ke sesi (prepared statement tertentu, SET level sesi, advisory lock) bisa rusak, karena koneksi DB-nya gonta-ganti tiap transaksi. Untuk serverless modern, vendor menyediakan pooler bawaan (mis. Supabase/Neon/RDS Proxy) — prinsipnya sama: satu lapisan yang meredam ledakan koneksi.
◆ Mendalami · Pooler eksternal paling populer

PgBouncer: penjaga koneksi yang ringan

PgBouncer adalah connection pooler eksternal khusus PostgreSQL. Dia program kecil & ringan (satu proses, jejak memori cuma sekitar 2 MB) yang duduk di antara aplikasi dan Postgres. Aplikasi terhubung ke PgBouncer seolah-olah itu database-nya; PgBouncer-lah yang memegang sedikit koneksi nyata ke Postgres dan membagikannya bergiliran.

◆ Analogi — resepsionis vs. saluran langsung

Tanpa PgBouncer: 2.000 aplikasi menelepon langsung ke kantor pusat (Postgres) — saluran (proses) habis, pusat kewalahan. Dengan PgBouncer: ada satu resepsionis yang menerima 2.000 penelepon, tapi cuma memegang 20 saluran ke pusat, lalu menyambungkan bergiliran. Pusat merasa cuma melayani 20 orang. Ribuan client di depan, segelintir koneksi nyata di belakang.

Hal terpenting yang harus dimengerti dari PgBouncer adalah pool mode — seberapa "lengket" koneksi nyata dipegang oleh satu client:

// session

Session pooling

Koneksi DB dipegang selama client tetap terhubung. Paling aman & kompatibel (semua fitur sesi jalan), tapi paling sedikit menghemat koneksi.

// transaction ★

Transaction pooling

Koneksi DB dipinjam per transaksi, lalu langsung balik. Paling umum untuk web & serverless — rasio penghematan terbesar. Default pilihan kebanyakan orang.

// statement

Statement pooling

Koneksi dilepas tiap selesai satu statement. Paling agresif & hemat, tapi paling banyak batasan — multi-statement transaction dilarang.

◆
Makin agresif mode-nya, makin hemat koneksi — tapi makin banyak fitur level-sesi yang rusak (mis. SET sesi, advisory lock, beberapa prepared statement), karena koneksi nyatanya gonta-ganti. Transaction pooling adalah titik tengah yang paling sering dipakai. (PgBouncer versi baru sudah mendukung prepared statement di mode transaction.)

Selain pool mode, fitur-fitur yang bikin PgBouncer jadi standar de-facto:

// lightweight

Sangat ringan

Satu proses, ~2 MB memori, mampu menangani ribuan koneksi client tanpa membebani server. Overhead-nya nyaris tak terasa.

// limiting

Pembatas & antrian koneksi

Membatasi koneksi nyata ke Postgres (default_pool_size) dan mengantrikan kelebihannya — melindungi DB dari ledakan koneksi.

// pause/resume

PAUSE / RESUME

Bisa menahan sementara semua query lalu melepasnya lagi — memungkinkan restart/maintenance Postgres tanpa memutus aplikasi.

// reload

Reconfigure online

Ganti konfigurasi & muat ulang (RELOAD) tanpa menjatuhkan koneksi client yang sedang jalan.

// SHOW

Monitoring bawaan

Console admin lewat perintah SQL: SHOW POOLS, SHOW STATS, SHOW CLIENTS, SHOW SERVERS untuk mengintip kondisi pool secara real-time.

// security

TLS & autentikasi

Dukungan SSL/TLS, beragam metode auth (scram, md5, dll.), serta pemetaan user — aman ditaruh sebagai gerbang depan.

// multi-db

Banyak database

Satu instance PgBouncer bisa mem-pool ke beberapa database & server berbeda lewat satu titik masuk.

// online restart

Restart mulus

Bisa di-restart sambil "menyerahkan" koneksi yang ada, meminimalkan gangguan saat upgrade PgBouncer-nya sendiri.

pgbouncer.ini — konfigurasi intiini
[databases]
; alias 'app' diteruskan ke Postgres asli

◆ Pool di app + PgBouncer = dua lapis

Keduanya tidak saling menggantikan, tapi saling melengkapi. Pool di aplikasi menghemat handshake untuk satu proses; PgBouncer meredam total koneksi dari semua proses/instance ke Postgres. Untuk serverless & auto-scaling, PgBouncer (atau pooler bawaan seperti RDS Proxy, Supabase, Neon) inilah yang menyelamatkan Postgres dari badai koneksi.

Salah kaprah yang sering bikin celaka

Pooling itu sederhana konsepnya, tapi gampang salah praktiknya. Ini daftar jebakan yang paling sering ketemu di lapangan.

// pool per request

Bikin pool di tiap request

Pool harus dibuat sekali saat app start, lalu dipakai bersama. Bikin new Pool() per request = balik ke masalah awal, malah lebih parah.

// max = 9999

"Gedein biar kencang"

Pool raksasa bikin DB rebutan resource & lebih lambat. Kecil-tapi-pas hampir selalu menang.

// lupa release

Tak ada finally

Penyebab leak nomor satu. Koneksi yang dipinjam manual harus selalu dilepas di finally.

// lupa hitung instance

Abai jumlah replika

max dikali jumlah instance app = total ke DB. Sering kelewat sampai DB kebanjiran diam-diam.

// query lama nahan

Transaksi & query lambat

Satu query lama menahan koneksi dari kolam. Beberapa saja sudah bisa bikin kolam "kosong" walau pool size cukup.

// no timeout

Tanpa connectionTimeout

Kalau kolam habis, request nunggu selamanya → hang senyap. Selalu set batas tunggu supaya gagal cepat & jelas.

“Pool koneksi yang lebih kecil, secara mengejutkan, sering memberi throughput yang lebih tinggi.”

— Inti dari dokumentasi pool-sizing HikariCP
Penutup

Pinjam, jaga ukurannya, selalu kembalikan

Connection pooling lahir dari satu kenyataan: membuka koneksi itu mahal, dan database punya batas. Solusinya bukan teknologi rumit — cuma "siapkan secukupnya, pakai berulang, kembalikan dengan disiplin".

  • Koneksi itu mahal — TCP + TLS + auth tiap kali; jangan diulang sia-sia.
  • Pool = kolam siap pakai — pinjam (acquire), pakai (use), kembalikan (release).
  • Ukuran kecil-tapi-pas — bukan "sebesar mungkin"; ukur, jangan menebak.
  • Selalu finally release() — cegah connection leak, bug paling sering.
  • Hitung total koneksi — pool size × jumlah instance ≤ kapasitas DB.
  • Skala besar → pooler eksternal — PgBouncer dkk untuk serverless & banyak replika.

Aturan emasnya

Pool bukan cuma soal kecepatan, tapi soal perlindungan. Dia menjaga database tetap hidup saat dunia luar mengamuk, dengan cara mengubah beban yang mematikan jadi antrian yang terkendali. Setel ukurannya dengan sadar, lepas koneksinya dengan disiplin, dan database kamu akan berterima kasih saat trafik puncak datang.
