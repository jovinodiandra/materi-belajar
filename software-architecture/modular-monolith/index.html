Modular Monolith

Satu aplikasi, satu deploy — tapi di dalamnya dibagi jadi modul-modul yang rapi dan saling menjaga jarak.

$ Satu rumah, tapi kamarnya jelas.

Monolith biasa jadi “bola lumpur”. Microservices terlalu mahal untuk tim kecil.

🟤

Monolith tanpa batas

Semua kelas saling memanggil. Ubah satu, rusak tiga.

💸

Microservices terlalu dini

Jaringan, deploy, monitoring berlipat. Tim cuma 5 orang.

🎯

Butuh jalan tengah

Rapi seperti microservices, sederhana seperti monolith.

Satu deploy, banyak modul

batas jelas tanpa biaya jaringan

◆ Buat apa ini? Kenapa pakai ini?

Given — aplikasi makin besar tapi tim masih kecil-menengah.

When — kode tidak punya batas, atau langsung dipecah jadi microservices.

Then — bola lumpur yang susah diubah, atau sistem terdistribusi yang terlalu mahal.

→ makanya kita pakai Modular Monolith — supaya batasnya rapi tanpa biaya microservices.

ide dasar

Satu aplikasi, modul berbatas jelas

Tiap modul punya pintu depan. Isi dalamnya rahasia.

Satu aplikasi Spring Boot · satu deploy · satu database (skema terpisah)

Modul lain hanya boleh lewat API publik, bukan kelas dalam.
contoh

Jaga batas: lewat pintu depan saja

✗ Melanggar batas
// di modul order
import com.toko.payment.internal.PaymentRepo;

class OrderService {
  void pay(Order o) {
    paymentRepo.save(new Payment(..));
    // langsung ke isi dalam modul lain
  }
}
✓ Lewat API publik
// di modul order
import com.toko.payment.PaymentApi;

class OrderService {
  void pay(Order o) {
    paymentApi.charge(o.id(), o.total());
  }
}
// cek otomatis dengan Spring Modulith
// atau ArchUnit di unit test
Jaga batas otomatis dengan Spring Modulith atau ArchUnit.

Tiga hal untuk diingat

❯ ide

Satu deploy, tapi dibagi modul dengan batas jelas.

❯ batas

Lewat API publik saja. Dicek otomatis.

❯ jalan

Mulai dari sini. Pecah jadi microservices hanya kalau perlu.
