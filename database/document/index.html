// Database — saat datamu lebih mirip dokumen daripada tabel

Simpan data seperti bentuk aslinya, bukan dipotong jadi tabel.

Objek di kode kamu itu bersarang: seorang user punya banyak alamat, banyak pengalaman kerja, banyak preferensi. Memaksanya masuk ke tabel-tabel datar yang kaku sering terasa canggung. Database document menyimpan data persis seperti objek itu — satu dokumen JSON utuh. Deck ini buat pemula: dari kenapa ia lahir, contoh yang cocok & yang tidak, trade-off-nya, sampai kapan harus dipakai di production — diselingi kalimat dari buku rujukan.

Impedance mismatch — objek app susah dipetakan ke tabel

Simpan sebagai dokumen JSON — utuh, bersarang, apa adanya

◆ Buat apa ini? Kenapa pakai document database?

Given — katalog produk e-commerce: sepatu punya field ukuran & warna, powerbank punya field kapasitas & garansi. Tiap kategori produk butuh atribut yang beda-beda.

When — kamu coba modelkan itu di tabel relasional: bikin satu tabel besar dengan banyak kolom (banyak yang NULL untuk produk lain), atau pecah jadi tabel EAV (entity-attribute-value) supaya fleksibel.

Then — pilihan pertama bikin skema kotor penuh kolom kosong; pilihan kedua bikin baca satu produk butuh JOIN banyak baris EAV, lambat & ribet cuma buat menyusun ulang satu objek.

→ makanya kita pakai document database — tiap produk jadi satu dokumen JSON dengan field bebas beda-beda, tanpa skema kaku atau JOIN berlapis buat baca satu item.

Akar masalah · Impedance mismatch

Objek di kode tidak rapi masuk ke tabel

Di kode, sebuah profil itu satu objek bersarang: satu orang punya banyak pengalaman kerja, banyak pendidikan, banyak kontak. Di database relasional, kamu harus memecahnya jadi beberapa tabel lalu menyambungnya lagi dengan JOIN tiap kali dibaca. Penerjemahan bolak-balik ini yang terasa canggung.

“Ketidakcocokan antara model objek dan model relasional ini kadang disebut impedance mismatch.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 2)
relasional — 1 profil dipecah 3 tabelSQL
-- users
id | nama  | kota
1  | Budi  | Bandung

-- positions (pengalaman kerja)
user_id | jabatan   | perusahaan
1       | Engineer  | Acme
1       | Lead      | Globex

-- educations
user_id | sekolah | tahun
1       | ITB     | 2018
-- baca 1 profil = JOIN 3 tabel
document — 1 profil = 1 dokumenJSON
{
  "nama": "Budi",
  "kota": "Bandung",
  "pengalaman": [
    { "jabatan": "Engineer", "di": "Acme" },
    { "jabatan": "Lead", "di": "Globex" }
  ],
  "pendidikan": [
    { "sekolah": "ITB", "tahun": 2018 }
  ]
}
// baca 1 profil = ambil 1 dokumen
◆ Analogi — formulir utuh vs. lemari arsip terpisah

Relasional ibarat memecah satu formulir lamaran menjadi tumpukan-tumpukan terpisah: tumpukan "data diri", tumpukan "riwayat kerja", tumpukan "pendidikan", di laci berbeda. Tiap kali butuh satu pelamar, kamu harus mengumpulkan kembali dari semua laci. Document ibarat menyimpan satu map berisi formulir lengkap — ambil satu map, semua ada di situ.

Konsep inti · Document database

Datanya adalah dokumen, bukan baris

Database document menyimpan data sebagai kumpulan dokumen mandiri. Tiap dokumen adalah struktur bersarang berisi pasangan kunci–nilai, daftar, dan objek di dalam objek — biasanya berbentuk JSON.

“Sebuah dokumen biasanya disimpan sebagai satu string menerus, dikodekan dalam JSON, XML, atau varian biner seperti BSON milik MongoDB.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 2)

Beberapa istilah yang sepadan, supaya tidak bingung saat membaca dokumentasi:

◆ Padanan istilah relasional ↔ document
Tabel→ Collection (kumpulan dokumen)
Baris→ Document (satu objek JSON)
Kolom→ Field (kunci di dalam dokumen)
JOIN→ (sebisa mungkin) embedding / nested

Inti perbedaannya: di relasional data dipecah & dinormalisasi ke banyak tabel; di document, data yang biasa diakses bersama disimpan bersama dalam satu dokumen.

◆ Prinsip desain

"Data yang diakses bersama, disimpan bersama." — prinsip desain inti MongoDB. Kalau aplikasimu hampir selalu mengambil profil beserta pengalaman & pendidikannya sekaligus, masuk akal menyimpannya sebagai satu dokumen, bukan dipencar ke banyak tabel.

Inti keputusan · Cocok vs tidak cocok

Contoh: yang cocok jadi document & yang TIDAK

Kunci untuk memilih: lihat bentuk relasi datanya. Document jago untuk struktur pohon one-to-many (satu induk, banyak anak yang "milik" induk itu). Document lemah untuk relasi many-to-many (data yang dipakai bersama dari banyak tempat).

“Untuk struktur pohon one-to-many ... model document cocok: seluruh pohon bisa dimuat dalam satu kali baca.”

— inti pembahasan Martin Kleppmann, DDIA (Bab 2)

// ✅ COCOK jadi document (one-to-many)

  • Postingan blog + komentar + tag (milik postingan itu).
  • Profil/CV + pengalaman + pendidikan.
  • Pesanan + daftar item di dalamnya.
  • Produk katalog + spesifikasi yang beda-beda.
  • Konten CMS, dokumen, halaman.

// ❌ BUKAN buat document (many-to-many)

  • Mahasiswa ↔ Mata kuliah (satu kuliah diambil banyak orang).
  • Pertemanan sosial (teman-dari-teman).
  • Item stok yang dirujuk banyak pesanan.
  • Transaksi keuangan antar banyak akun.
  • Data yang butuh banyak JOIN & laporan lintas-entitas.
kenapa many-to-many bermasalah di documentJSON
// nama mata kuliah "Basis Data" DISALIN ke ribuan dokumen mahasiswa
{ "mahasiswa": "Budi", "kuliah": [ { "nama": "Basis Data", "sks": 3 } ] }
{ "mahasiswa": "Sari", "kuliah": [ { "nama": "Basis Data", "sks": 3 } ] }
// 🐢 nama kuliah berubah? harus update RIBUAN dokumen (update anomaly)

Inilah masalah duplikasi: di model document, data many-to-many cenderung disalin ke banyak tempat. Saat satu fakta berubah, kamu harus memburu semua salinannya. Di relasional, fakta itu cukup hidup di satu baris dan dirujuk lewat ID — itulah kenapa relasional menang untuk pola ini.

◆ Keunggulan · Kenapa harus document

Tiga alasan utama memilih document

Saat datamu memang berbentuk dokumen mandiri, model ini memberi keuntungan yang nyata — dan Kleppmann merangkumnya dalam satu kalimat.

“Argumen utama yang mendukung model data document adalah fleksibilitas skema, performa lebih baik karena lokalitas, dan untuk sebagian aplikasi ia lebih dekat dengan struktur data yang dipakai di kode.”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 2)
// locality

Lokalitas baca

Seluruh dokumen tersimpan berdekatan → ambil profil lengkap dalam satu kali baca, tanpa JOIN. Cepat saat kamu butuh seluruh isinya sekaligus.

// flexibility

Skema fleksibel

Tiap dokumen boleh punya field berbeda. Tambah field baru tanpa migrasi tabel — cocok untuk iterasi cepat & data yang bentuknya beragam.

// no mismatch

Cocok dengan objek kode

Dokumen JSON ≈ objek di aplikasi. Nyaris tanpa lapisan penerjemah (impedance mismatch hilang), kode jadi lebih lugas.

◆ Analogi — katalog dengan barang beragam

Toko menjual buku (punya: penulis, ISBN, jumlah halaman) dan baju (punya: ukuran, warna, bahan). Di tabel relasional kaku, kamu pusing bikin kolom yang cocok untuk semua jenis. Di document, tiap produk cukup membawa field-nya sendiri — buku bawa ISBN, baju bawa ukuran. Skema yang fleksibel ini pas untuk data yang bentuknya tidak seragam.

Konsep penting · Schema-on-read

“Fleksibel” artinya skema dicek saat dibaca, bukan ditulis

Orang sering bilang document DB itu "tanpa skema" (schemaless). Lebih tepatnya: skemanya tidak dipaksakan oleh database saat menulis — tapi tetap ada, secara implisit, di kode yang membacanya.

“Perbedaannya adalah schema-on-read (struktur data bersifat implisit, baru ditafsirkan saat dibaca), berlawanan dengan schema-on-write (pendekatan tradisional database relasional, di mana skema eksplisit & dipaksakan database).”

— Martin Kleppmann, Designing Data-Intensive Applications (Bab 2)

// schema-on-write (relasional)

  • Struktur didefinisikan di muka (CREATE TABLE).
  • Database menolak data yang tak sesuai.
  • Aman & konsisten, tapi ubah skema = migrasi.

// schema-on-read (document)

  • Apa saja boleh ditulis; bentuk diurus aplikasi.
  • Lincah untuk berubah & bereksperimen.
  • Risiko: data tak konsisten kalau tak disiplin.
◆
"Tanpa skema" bukan berarti tanpa aturan — hanya saja aturannya pindah dari database ke kode kamu. Tanpa disiplin, sebuah collection bisa berisi dokumen dengan bentuk berbeda-beda dari berbagai versi aplikasi, dan kode pembaca harus menangani semuanya. Banyak tim akhirnya menambah validasi skema (mis. JSON Schema di MongoDB) untuk mendapat sebagian keamanan relasional kembali.
◆ Harga · Tidak ada makan siang gratis

Trade-off: yang kamu dapat & yang kamu korbankan

Document bukan "lebih baik" dari relasional — ia berbeda. Kleppmann menutup perbandingannya dengan jujur: tidak ada pemenang mutlak; yang ada adalah kecocokan dengan bentuk datamu.

// Yang kamu dapat

  • Baca dokumen utuh sangat cepat (lokalitas).
  • Skema fleksibel, iterasi kilat.
  • Cocok dengan objek kode (tanpa mismatch).
  • Mudah di-shard / skala horizontal.

// Yang kamu korbankan

  • Lemah untuk many-to-many & JOIN.
  • Duplikasi data → risiko update anomaly.
  • Tanpa skema dipaksakan → bisa berantakan.
  • Query/agregasi lintas dokumen lebih ribet.
  • Transaksi multi-dokumen historisnya terbatas.

“Tidak ada satu model data yang menang untuk segala hal — masing-masing punya kekuatan untuk jenis aplikasi yang berbeda.”

— semangat pembahasan DDIA (Bab 2)
◆ Catatan zaman sekarang

Garis pemisahnya mulai kabur. Postgres & MySQL kini punya tipe JSON/JSONB (relasional yang bisa nyimpan dokumen), dan MongoDB modern mendukung transaksi multi-dokumen & agregasi kuat. Jadi pilih berdasarkan bentuk data & pola akses dominan, bukan karena ikut tren.

◆ Keputusan · Pakai atau jangan

Kapan harus pakai document database

Aturan praktisnya: kalau datamu berbentuk dokumen mandiri yang sering diakses utuh, pilih document. Kalau penuh relasi many-to-many & butuh banyak JOIN/laporan, pilih relasional.

// Pakai document saat…

  • Data = pohon one-to-many yang mandiri.
  • Hampir selalu baca seluruh dokumen sekaligus.
  • Skema sering berubah / antar item beda bentuk.
  • Butuh skala horizontal besar & tulis cepat.
  • Prototipe/startup yang beriterasi cepat.

// Jangan, pilih relasional saat…

  • Banyak relasi many-to-many antar entitas.
  • Butuh JOIN & laporan/analitik lintas-tabel.
  • Konsistensi & integritas ketat (keuangan).
  • Data dirujuk dari banyak tempat (hindari duplikasi).
  • Transaksi rumit lintas banyak entitas.
◆ Pertanyaan penentu

Tanyakan satu hal ke datamu: "Apakah aku hampir selalu mengambil benda ini secara utuh, sebagai satu kesatuan?" Kalau ya (sebuah postingan, sebuah pesanan, sebuah profil) → document. Kalau kamu lebih sering memotong-motong & menggabungkan data dari banyak entitas untuk menjawab pertanyaan → relasional.

Study kasus · Di dunia nyata

Kapan tim memilih document di production

Empat skenario nyata di mana document database jadi pilihan tepat — perhatikan polanya: data mandiri, dibaca utuh, atau skemanya beragam/berubah cepat.

// e-commerce

Katalog produk

Kasus: tiap kategori punya atribut berbeda (buku vs elektronik vs baju). Kenapa document: skema fleksibel — tiap produk bawa field sendiri tanpa tabel raksasa penuh kolom kosong. Tool: MongoDB.

// CMS / blog

Konten & artikel

Kasus: artikel + blok konten + metadata + komentar, semua milik satu halaman. Kenapa document: satu halaman = satu dokumen, dibaca utuh saat ditampilkan. Tool: MongoDB, Couchbase.

// real-time / mobile

Chat & aplikasi mobile

Kasus: aplikasi chat yang perlu sinkron real-time ke banyak perangkat. Kenapa document: data per-user/per-room mandiri & sinkronisasi mudah. Tool: Firebase Firestore.

// logging / IoT

Event & telemetri

Kasus: jutaan event log / sensor dengan bentuk yang berubah-ubah. Kenapa document: tulis cepat, skema bebas, skala horizontal. Tool: MongoDB, Elasticsearch.

◆ Benang merahnya

Di semua kasus di atas: datanya mandiri (tidak banyak relasi many-to-many), dibaca sebagai satu kesatuan, dan sering kali bentuknya beragam atau berubah cepat. Begitu kebutuhan bergeser ke laporan keuangan lintas-entitas atau analitik dengan banyak JOIN, tim biasanya menambah database relasional / warehouse di sampingnya — bukan memaksakan satu alat untuk semua.

◆
Anti-pola yang sering bikin menyesal: memilih document hanya karena "tidak mau repot bikin skema", lalu ternyata datanya penuh relasi. Beberapa bulan kemudian kode penuh JOIN manual di aplikasi & duplikasi data di mana-mana. Pilih karena bentuk datanya, bukan karena ingin menunda berpikir soal skema.

◆ Tips pemula

Bingung memilih? Kalau aplikasimu sudah pakai Postgres dan cuma butuh sedikit fleksibilitas, kolom JSONB sering sudah cukup — tak perlu menambah database baru. Tambahkan MongoDB/Firestore saat kebutuhan dokumen benar-benar dominan.

Penutup

Simpan sesuai bentuk data, bukan sesuai tren

Document database lahir dari keinginan menyimpan data seperti bentuk aslinya di kode — utuh, bersarang, mandiri. Ia bersinar saat datamu memang berbentuk dokumen, dan tersandung saat datamu penuh relasi.

  • Impedance mismatch — objek bersarang susah dipetakan ke tabel datar.
  • Dokumen = JSON utuh — data yang diakses bersama, disimpan bersama.
  • Cocok: one-to-many — postingan, profil, pesanan, katalog, CMS.
  • Tidak cocok: many-to-many — relasi rumit & JOIN bukan kekuatannya.
  • Schema-on-read — fleksibel, tapi disiplin pindah ke kode kamu.
  • Pilih dari bentuk data — bukan karena ingin menghindari skema.

Aturan emasnya

Tanya: "Apakah aku hampir selalu mengambil data ini sebagai satu kesatuan utuh?" Kalau ya, document memberimu kecepatan & kelincahan. Kalau datamu lebih sering dipotong & digabung lintas banyak entitas, relasional akan menyelamatkanmu dari duplikasi & JOIN manual. Tidak ada model yang menang untuk segalanya — pilih yang paling pas dengan bentuk data & cara kamu mengaksesnya.
