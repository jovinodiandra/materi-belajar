// Tool document database #3 — berbasis JSON, fokus pencarian

Elasticsearch — dokumen JSON yang dibuat untuk dicari.

Elasticsearch menyimpan dokumen JSON seperti document DB lain — tapi tujuannya berbeda: pencarian teks & analitik log dalam skala besar & sangat cepat. Rahasianya adalah inverted index: struktur yang membalik "dokumen → kata" menjadi "kata → dokumen". Inilah yang dipakai pada contoh kasus event/telemetri di deck induk, dan sering jadi pendamping MongoDB/Firestore untuk fitur search.

Simpan
Index berisi document JSON — dengan mapping
Pecah
Analyzer → token — teks dipecah jadi kata dasar
Balik
Inverted index — kata → daftar dokumen
Cari
Query DSL + skor relevansi — hasil paling cocok di atas

Kenalan · Apa itu Elasticsearch

Mesin pencari berbasis dokumen JSON

Elasticsearch adalah search engine terdistribusi yang menyimpan data sebagai dokumen JSON dan diakses lewat REST API. Ia dibangun di atas pustaka Apache Lucene, dan keahlian utamanya adalah menjawab pertanyaan "dokumen mana yang paling cocok dengan kata-kata ini?" dalam hitungan milidetik.

“Berbasis dokumen JSON, tapi fokus ke pencarian teks & analitik log. Sering jadi pendamping, bukan DB utama.”

— ringkasan dari deck Document Database (bab Tools)
// search

Full-text search

Cari kata di tengah teks, toleran typo, peringkat relevansi, sorot kata (highlight), saran (autocomplete).

// logs

Log & observability

Jantung dari "ELK Stack" (Elasticsearch + Logstash + Kibana) untuk menelan & menganalisis jutaan log/event.

// scale

Terdistribusi

Index dipecah jadi shard & direplikasi otomatis ke banyak node — skala & keandalan sejak desain.

◆ Posisinya — pendamping, bukan pengganti

Elasticsearch jarang jadi satu-satunya database. Pola umum: data resmi hidup di MongoDB/Postgres, lalu disalin/diindeks ke Elasticsearch khusus untuk fitur pencarian. Ia dioptimalkan untuk membaca-mencari, bukan untuk jadi sumber kebenaran transaksional.

Konsep · Model data

Index, document, mapping

Istilahnya mirip document DB lain, dengan satu tambahan penting: mapping — definisi tipe tiap field yang menentukan bagaimana field itu di-index & dicari.

◆ Padanan istilah
Tabel→ Index
Baris→ Document (JSON)
Kolom→ Field
Skema→ Mapping (tipe tiap field)

Catatan: kata "index" di Elasticsearch berarti kumpulan dokumen (seperti tabel) — beda dari "index" di MongoDB yang berarti struktur percepat-query. Di Elasticsearch, hampir semua field otomatis terindeks untuk dicari.

simpan dokumen produk — REST APIHTTP
PUT /produk/_doc/1
{
  "nama":      "Kabel USB-C 2 meter braided",
  "deskripsi": "Kabel pengisian cepat tahan lama",
  "kategori":  "aksesoris",
  "harga":     45000
}
// dokumen langsung terindeks & siap dicari
Inti · Inverted index

Rahasianya: membalik "dokumen → kata"

Ini konsep terpenting. Alih-alih menyimpan "dokumen 1 berisi kata A, B, C", Elasticsearch menyimpan kebalikannya: "kata A ada di dokumen 1, 5, 9". Jadi saat kamu mencari sebuah kata, ia langsung tahu dokumen mana saja yang memuatnya — tanpa memindai semua.

TERM (kata)→ DOKUMEN (posting list)
kabel→ doc 1, doc 3, doc 8
usb→ doc 1, doc 8
cepat→ doc 1, doc 5
braided→ doc 1
◆ Analogi — indeks di belakang buku

Persis seperti indeks subjek di halaman belakang buku teks: kamu tak membaca seluruh buku untuk menemukan kata "fotosintesis" — kamu buka indeks, ia bilang "halaman 88, 210", selesai. Inverted index adalah versi raksasa & otomatis dari itu, untuk setiap kata di setiap dokumen.

◆ Kenapa cepat untuk "cari kata di tengah teks"

Cari "kabel usb" = ambil posting list "kabel" (doc 1,3,8) ∩ "usb" (doc 1,8) → hasil doc 1 & 8. Ini operasi himpunan yang sangat cepat — jauh lebih efisien daripada LIKE '%kabel%' di SQL yang memindai tiap baris.

Inti · Analyzer

Bagaimana teks dipecah jadi token

Sebelum masuk inverted index, teks diproses oleh analyzer: dipecah jadi kata (tokenisasi), dijadikan huruf kecil, dan kadang disederhanakan ke bentuk dasar. Inilah kenapa pencarian bisa "pintar" — mencocokkan meski beda huruf besar/kecil atau bentuk kata.

satu kalimat → beberapa tokenFLOW
// input teks asli
"Kabel USB-C Tahan Lama"

      ↓  analyzer (tokenize + lowercase)

// token yang masuk inverted index
[ "kabel", "usb", "c", "tahan", "lama" ]

// → pencarian "usb" atau "tahan" sekarang cocok ✅
// tokenizer

Tokenizer

Memecah teks jadi kata berdasarkan spasi/tanda baca. "usb-c" → "usb", "c".

// filter

Token filter

Lowercase, buang stop words ("dan","yang"), stemming (bentuk dasar). Bisa dirangkai.

// bahasa

Analyzer bahasa

Ada analyzer khusus per bahasa (mis. indonesian) yang paham stop words & akar kata lokal.

◆
Aturan emas: analyzer saat menyimpan harus sepadan dengan saat mencari. Kalau teks disimpan di-lowercase tapi query dicocokkan apa adanya (lihat term di bab Query), hasilnya bisa kosong meski "terlihat" cocok. Ini sumber kebingungan #1 bagi pemula Elasticsearch.
◆ Operasi · Query DSL

Mencari dengan Query DSL

Query ditulis sebagai JSON lewat REST API — disebut Query DSL. Dua keluarga penting: match (full-text, lewat analyzer, untuk teks) dan term (cocok persis, tanpa analyzer, untuk kategori/ID). Ini jawaban langsung untuk kebutuhan query.

match — pencarian teks penuhHTTP
GET /produk/_search
{
  "query": {
    "match": { "nama": "kabel cepat" }
  }
}
// cocokkan "kabel" ATAU "cepat"; dokumen dgn keduanya skornya lebih tinggi
bool — gabungan must / filter (mirip AND + WHERE)HTTP
GET /produk/_search
{
  "query": {
    "bool": {
      "must":   [ { "match": { "nama": "kabel" } } ],   // pengaruhi skor
      "filter": [
        { "term":  { "kategori": "aksesoris" } },        // cocok persis
        { "range": { "harga": { "lte": 50000 } } }       // rentang harga
      ]
    }
  }
}
// must = relevansi; filter = ya/tidak (lebih cepat, bisa di-cache)
◆ match vs term — jangan tertukar

match melewati analyzer → untuk field teks (nama, deskripsi). term mencari token persis → untuk field keyword (kategori, status, ID). Memakai term pada teks ber-analyzer sering memberi nol hasil.

Indexing · Mapping

text vs keyword: dua cara meng-index field

Di Elasticsearch, "indexing" berarti menentukan tipe field di mapping — itu yang memutuskan apakah sebuah field bisa dicari sebagai teks bebas, dicocokkan persis, atau diurutkan/diagregasi. Ini inti dari indexing yang tepat.

mapping eksplisit — text + keyword sekaligusHTTP
PUT /produk
{
  "mappings": {
    "properties": {
      "nama": {
        "type": "text",                // full-text search (pakai analyzer)
        "fields": {
          "raw": { "type": "keyword" }  // nama.raw → cocok persis, sort, agregasi
        }
      },
      "kategori": { "type": "keyword" },  // hanya cocok persis
      "harga":    { "type": "integer" }   // rentang & agregasi numerik
    }
  }
}

// type: text

  • Diproses analyzer → token.
  • Untuk pencarian kata di tengah teks.
  • Pakai dengan query match.
  • Tidak ideal untuk sort/agregasi.

// type: keyword

  • Disimpan utuh, tanpa dipecah.
  • Untuk kategori, status, tag, ID.
  • Pakai dengan query term.
  • Bisa di-sort & di-agregasi.
◆
Kalau kamu tidak mendefinisikan mapping, Elasticsearch menebak otomatis (dynamic mapping) — biasanya membuat field string jadi text dan sub-field .keyword sekaligus. Praktis untuk eksperimen, tapi untuk production sebaiknya mapping eksplisit agar pencarian & agregasi berperilaku sesuai harapan.
⚙ Operasi · Relevansi & agregasi

Skor relevansi & analitik

Yang membedakan search engine dari database biasa: hasil diurutkan berdasarkan relevansi (skor _score), bukan sekadar cocok/tidak. Selain itu, Elasticsearch jago agregasi untuk dashboard & analitik log.

◆ Bagaimana skor dihitung (BM25)

Secara sederhana: kata yang jarang di seluruh koleksi tapi sering muncul di sebuah dokumen → dokumen itu dianggap sangat relevan & naik ke atas. Itulah kenapa hasil teratas Elasticsearch terasa "pas" — bukan urutan acak atau sekadar terbaru.

agregasi — berapa produk per kategori (untuk dashboard)HTTP
GET /produk/_search
{
  "size": 0,                          // tak perlu dokumen, hanya ringkasan
  "aggs": {
    "per_kategori": {
      "terms": { "field": "kategori" }   // kelompokkan per keyword
    }
  }
}
// pas untuk telemetri: "berapa event per tipe", "rata-rata latensi per jam"
◆ Kibana

Untuk kasus log/telemetri, Kibana adalah UI visual di atas Elasticsearch: bikin grafik, dashboard, & pencarian log tanpa menulis Query DSL manual. Inilah "K" di ELK Stack.

Praktik · Kapan pakai

Elasticsearch cocok untuk kasus apa

Polanya: saat pencarian atau analitik menjadi fitur inti — bukan saat kamu butuh sumber data transaksional utama.

// search

Search produk / konten

Kotak pencarian e-commerce/CMS: cari kata di nama & deskripsi, filter kategori, urut relevansi.

// logs

Log & telemetri

Contoh kasus event/IoT dari deck induk: telan jutaan log, cari & agregasi cepat lewat Kibana.

// observability

Monitoring & APM

Lacak metrik, error, & trace aplikasi secara terpusat dengan dashboard live.

// autocomplete

Saran & autocomplete

Ketik-sambil-cari, "did you mean", pencarian toleran typo (fuzzy).

// Pakai Elasticsearch saat…

  • Pencarian teks penuh jadi fitur inti.
  • Butuh peringkat relevansi, highlight, fuzzy.
  • Analitik/agregasi log dalam skala besar.
  • Sebagai pendamping DB utama.

// Jangan jadikan DB utama saat…

  • Butuh transaksi & konsistensi kuat.
  • Data sering di-update field demi field.
  • Sumber kebenaran (system of record).
  • Relasi many-to-many & JOIN kompleks.
◆ Harga · Trade-off

Yang kamu dapat & yang kamu korbankan

Elasticsearch menukar jaminan transaksional demi kecepatan & kecerdasan pencarian. Untuk search & analitik, itu pertukaran yang tepat — selama ia bukan satu-satunya tempat datamu hidup.

// Yang kamu dapat

  • Full-text search super cepat (inverted index).
  • Peringkat relevansi (BM25), highlight, fuzzy.
  • Agregasi & analitik kuat (Kibana).
  • Terdistribusi: shard + replica otomatis.

// Yang kamu korbankan

  • Bukan transaksional (eventually consistent).
  • Update berat; cocok untuk tulis-sekali-cari-banyak.
  • Butuh sumber daya (RAM) cukup besar.
  • Salah analyzer/mapping → hasil membingungkan.
  • Sinkronisasi dari DB utama jadi PR tersendiri.
◆ Pola arsitektur umum

Data ditulis ke DB utama (mis. MongoDB/Postgres), lalu diindeks ulang ke Elasticsearch lewat pipeline (CDC, message queue, atau job berkala). Pengguna mengetik di kotak pencarian → query ke Elasticsearch → ambil ID hasil → tampilkan detail dari DB utama. Inilah arti "pendamping, bukan pengganti".

Penutup

Elasticsearch dalam satu tarikan napas

Simpan dokumen JSON, biarkan analyzer memecah teks jadi token di inverted index, cari dengan Query DSL (match untuk teks, term untuk keyword), dan dapatkan hasil terurut relevansi. Tetapkan ia sebagai mesin pencari pendamping, bukan sumber kebenaran.

  • Index → Document → Field + Mapping — JSON yang dibuat untuk dicari.
  • Inverted index — kata → daftar dokumen, kunci kecepatan.
  • Analyzer — teks dipecah jadi token; samakan saat simpan & cari.
  • match vs term — teks (analyzer) vs cocok-persis (keyword).
  • _score relevansi (BM25) — hasil paling cocok naik ke atas.
  • Pendamping, bukan pengganti — untuk search & analitik, bukan transaksi.

Langkah belajar berikutnya

Jalankan Elasticsearch + Kibana lokal (Docker), buka Dev Tools di Kibana, lalu: PUT beberapa dokumen produk → coba match vs term dan lihat bedanya → pakai _analyze untuk melihat bagaimana teksmu dipecah jadi token → buat satu agregasi terms. Itu memperlihatkan inverted index & relevansi secara langsung.
